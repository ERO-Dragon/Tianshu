# Dubhe 搜索（`search`）

> **要点**
> - 只答**描述性知识**：这个物品/方块干什么、这个模组怎么玩、这个原版机制怎么运作。配方归舟楫、版本与依赖本地已知、崩溃不做。
> - 三层源按序降级：**本地手册（Patchouli）→ 中文站 → 英文站**。
> - 不引入任何需要 API key 的通道。
> - **纯内部技能**：不向舟楫注册任何能力（G66），本文只管天枢自己怎么查。

## 1. 边界：不管什么

| 问法 | 归谁 | 为什么 |
|---|---|---|
| 配方 / 合成表 | 舟楫 `tianshu:recipe.query` | 存档里的真实配方，含整合包魔改；网页必然可能错 |
| 支不支持我这版本、依赖什么 | 本地 `ModList` | 启动时已知，联网是绕远路 |
| 报错了 / 崩溃 | 不做 | 客户端日志不在我们手里 |
| 整合包推荐、下载站浏览 | 不做 | 不是游戏内会发生的事 |
| 世界动作 | 不做（A1） | 天枢无实体 |

剩下只有三问：**这是什么、怎么玩、原版机制怎么运作**。

## 2. 两个轴

- **轴一：问什么** → 决定去哪个源。唯一的轴。
- **轴二：怎么取**（API / HTML / jar 资源）→ 源的属性，模型不用管。

## 3. 语言 × 域：两条链，不是一条降级链

先按**玩家语言**选一条链，再按**原版还是模组**选站。不是"国外优先、国外不行再国内"。

| | 原版内容 | 模组内容 |
|---|---|---|
| **中文** | 中文 Wiki → BWIKI | **MC百科**（中文侧唯一综合源） |
| **英文** | `minecraft.wiki` | CurseForge / Modrinth（作者描述） |

- **语言由 `DubhePromptLanguageProvider` 决定**，跟对话语言走，不跟"哪个站更权威"走。
- **L1 本地手册在两条链之前**：装了就先用，与语言无关；手册自身的语言也按玩家语言取（见 §6）。
- 同一链内：源超时/报错/零结果 → 下一个；整条链都没有 → **说查不到**。
- **不自动跨语言兜底**：中文玩家查不到的英文模组，不会把英文原文塞给他。要切链先问一句。

**一个必须承认的服务缺口**：国外没有 MC百科 的对应物。英文的"模组检索"只能靠发布站的作者描述——那是"这是什么"，不是"怎么玩"。所以：

| | 原版机制 | 模组机制 |
|---|---|---|
| 中文 | 很强（Wiki） | 强（MC百科 有成文攻略） |
| 英文 | 很强（`minecraft.wiki`） | **弱**：官方 wiki 有就有、没有就没了，其余散在视频和 Discord |

这不是实现问题，是这个领域的资料分布就是这样。

## 4. 站点清单

### 中文

| 站点 | 覆盖 | 取法 | 状态 |
|---|---|---|---|
| MC百科 `mcmod.cn` | 模组词条（中文侧唯一） | HTML + 站内搜索 | robots 允许正文；无官方 API |
| 中文 Wiki `zh.minecraft.wiki` | 原版 | MediaWiki API（generator + 导语） | 实测可用 |
| BWIKI `wiki.biligame.com/mc` | 只有原版 | MediaWiki API，**无 extracts** | 只有标题和片段，本版不用 |

### 英文

| 站点 | 覆盖 | 取法 | 状态 |
|---|---|---|---|
| CurseForge | 作者原话（描述、文件） | `api.cfwidget.com` 公开镜像 | 实测可用；官方 API 需 key，不用 |
| Modrinth | 作者原话（描述、版本） | 官方 API | 实测可用，免 key |
| `minecraft.wiki` | 原版 | MediaWiki API | 实测可用 |

**英文侧没有 MC百科 的对应物**：模组资料只有「发布站的作者描述」这一种成文形态，其余靠官方 wiki（有就有、没有就没了）和视频/Discord（读不了）。这正是 §3 说的那个缺口。

**不收录**：9Minecraft（转载站）、Planet Minecraft（地图/皮肤）、Minecraft Forum（已衰退）、GitHub（开发视角）、B站/YouTube（视频读不了）。

**官方 wiki 不设计成链路上的一环**：CF 的 `links` 实测为空（Create 就是空），Modrinth 的 `wiki_url` 实测常为 null（Botania 就是 null），「从发布站跳到官方 wiki」不可靠。已有 URL 时只作事后补充。

## 5. 工具

| 工具 | 覆盖 | 状态 |
|---|---|---|
| `book` | 已装模组的手册 | **已实现**（§6） |
| `wiki` | 中文 Wiki / 英文 Wiki（`site` 不给就跟玩家语言） | **已实现** |
| `mcmod(query)` | MC百科 HTML | 待做 |
| `mc_modrinth` / `mc_cf` | 英文分发站 | **第一版不做**：只回答"这模组是什么"，而 L1 手册与 MC百科 覆盖更好；真撞上"没词条且没装手册"再补 |

- **`search` 不进 simple 工具表**（A3）：simple 恒为 `{delegate}`，结构上没有这条路。
- **纯内部**：工具名只在天枢内部出现，不对外发布（G66）。

**联网都走 `DubheWeb`**（G68）：8 秒、512KB、同主机最多 3 跳、不重试、不读系统代理。每个源只负责拼 URL 和解析，超时/大小/重定向只定义一次。

**BWIKI 不用**：它没有 TextExtracts 扩展（`prop=extracts` 直接报"未识别"），`action=raw` 拿到的是几十 KB 的信息框标记。清理它的成本超过它带来的信息，所以中文原版只留中文 Wiki。真要加，得单独写一条"只给标题和片段"的降级路径。

## 6. 本地手册（L1）：Patchouli

数据在**模组自己的 jar**（`assets/<ns>/patchouli_books/<book>/`），不在 Patchouli 的 jar 里——**没装 Patchouli 也能读**。

两级检索，不整本进模型：

| 步 | 做什么 |
|---|---|
| 建索引 | **首次查询时**读一遍所有模组的书，常驻内存；没人问就不读 |
| 匹配 | 问法切成词（英文按词、中文按二字滑窗），标题命中权重高于正文 |
| 取正文 | 只回命中的 1–3 条，整次回答的正文上限 1800 字 |

**检索方式**：内存线性扫描 + 词打分（不是 grep、不是向量）。语料量级是几百到几千条、每条两三百字，全表扫一遍是微秒级；上 embedding 要多一次模型调用或几十 MB 本地模型，不划算。

**三档动作**（模型自己选，用来补词匹配的短板）：

| action | 用途 | 代价 |
|---|---|---|
| `search`（默认） | 按说法找，回 1–3 条正文 | 一次 |
| `list` 不给 `mod` | 列出哪些模组有手册、各多少条 | 极小 |
| `list` 给 `mod` | 看该模组目录（每页 300 条标题） | ~1k token |
| `read`（`mod` + `title`） | 读指定条目；标题近似时自动退到模组内检索 | 一次 |

词匹配对"换了个说法"无能为力——问「怎么让机器转起来」、条目叫「传动轴」就一个词都对不上。`list` + `read` 补的正是这一段：模型认得那个词、只是拼不出来时，先看目录再精确读。只在命中不了时走，常规路径不多付成本。

实现落点：

- **端口**：`InstalledModIds` + `ModResources`（`tianshu-api/assembly`）。适配器实现，模块不接触加载器 API；两边共用的 IO 在 `mc.resource.ModResourceFiles`。
- **技能**：`agent/skill/book/`——`book` 是技能 id，目录、语言回退、格式控制清理全在解析器里，模型只看到"问什么 → 标题 + 正文"。
- **技能包 `search`**（`skills/search/SKILL.md`）：告诉模型先查手册、打不中怎么退（list → read）、配方交给 `recipe.query`、手册没写就说不确定。线上源接入后再加 `references/sources.md`。
- **缓存挂在技能实例上**，不挂静态字段：模块停掉缓存即消失，测试也不会互相污染。
- **真实 jar 回归**：`DubheBookJarSamplesTest` 读 `Tianshu-adapter/libs` 里的样本（jar 不入库），把 `DUBHE_BOOK_SAMPLES` 指向那个目录才跑，否则跳过。固定用例编码的是"我们以为书长什么样"，这个测的是"书实际长什么样"。

**对"书长得不一样"的兜底**（全部由真实 jar 验证过）：

| 差异 | 处理 |
|---|---|
| `book.json` 不在 `assets/` 而在 **`data/`** | **发现书目只看 `assets/<ns>/patchouli_books/<book>/<lang>/entries`**。实测 Botania / Ars Nouveau / Iron's Spells 三本都在 `data/`，按 `assets/` 找 `book.json` 会一本都找不到 |
| 正文页类型五花八门（`text` / `patchouli:text` / `spotlight` / `entity` / 模组自造） | **按"有没有 `text` 字段"取，不按类型名取**。裸写和带 `patchouli:` 前缀的两种命名都有，按名字匹配会漏 |
| 条目树的语言 ≠ 翻译的语言 | **分开选**：树取第一个存在的（Botania 只有 `en_us`），翻译取读者语言能用的（`zh_cn` 有就用）。两者绑死会得到"英文标题 + 没翻译" |
| 一套语言树直写中文 | 同一条规则覆盖：`name` / `text` 查表查不到就用原文（Iron's Spells 就是这样） |
| 条目没有 `name` | 退回文件名当标题，不整条丢掉 |
| 文件异常 | 剥 BOM；单文件 >2MB 跳过；单条目坏掉只丢那条；总条目上限 2 万 |

**实测三本真实手册**（1.20.1 / 1.21.1 的发布 jar）：

| 手册 | 条目文件 | 形态 |
|---|---|---|
| Botania `lexicon` | 246 | 单 `en_us` 树 + 15 份 lang（含 `zh_cn`），键引用 |
| Ars Nouveau `worn_notebook` | 262 | 单 `en_us` 树，页型带 `patchouli:` 前缀 |
| Iron's Spells `iss_guide_book` | 8 | **四套语言树**（`en_us`/`ja_jp`/`zh_cn`/`zh_tw`），中文直写 |
| Create / Ars Nouveau 5.x / Occultism | 0 | 不用 Patchouli（Ponder、自绘书），负样本 |

**已知限制（本版不解决）**：只读**模组自带**的资源，读不到**资源包**里的书与汉化覆盖。汉化补丁常以资源包装的形式覆盖 `lang/zh_cn.json`，那种情况下我们会回退到模组自带语言，可能拿到英文原文。补这一层需要另一个端口（资源包视图 + 覆盖优先级），等真有玩家反馈再评估。

实测（Botania `lexicon`，第 1 本）：

| 项 | 值 |
|---|---|
| 条目数 | 246 |
| 文本页 | 491（约占全部页一半；其余是配方/图片/多元块，跳过） |
| 单条目正文 | ~267 字（中）/ ~667 字（英） |
| 整本 | ~6.6 万字（中）/ 16.4 万字（英）——**不能整本进 prompt** |
| 中文覆盖率 | 100%（246/246 条目名、491/491 文本页） |
| 索引体积 | 246 条标题共 1030 字，≈ 650 token |

解析要点：

- **文本解析只有一条规则**：先查语言表，命中就当键解析，没命中就当正文原样用。这一条同时覆盖「翻译键」（`"text": "botania.page.apothecary0"`）和「硬编码」（`text` 就是正文）两种写法，也容忍缺翻的键。
- 只取 `text` 页；`crafting` / `spotlight` / `image` 跳过。
- 语言：优先 `<book>/zh_cn/`（模组自带分语言结构时），否则用 `en_us/` 结构 + 查 `zh_cn` 语言表，再否则原文。
- 硬编码的条目只有一套文字，通常没有中文——照常读，不因此降级。
- 宏与模板不展开；坏 JSON 跳过并记日志，不拖垮整体。

## 7. 频控与失败

| 项 | 规则 |
|---|---|
| MC百科 | 单轮合计 ≤2 次（搜索 1 + 页面 1）；同域名 60s 冷却；不重试 |
| 其余站 | 单轮 ≤3 次/站；不重试 |
| 同 URL | 进程内缓存，只取一次 |
| 失败 | 降级 + 回答里说明；**三层都无命中就说查不到**，给已知信息并标置信度，不许编 |

## 8. 输出

结论 + 依据（每条带来源站点）+ 不确定处，嵌进报告三字段的 `result`。
