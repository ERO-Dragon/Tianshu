# AX 运行架构

天枢（Tianshu）的运行期架构：模块分工、一轮请求的端到端数据流、跨模块不变量，以及这些不变量背后的成本与一致性理由。本文只写架构层面的结论；具体参数与算法见《AX_上下文编排》《AX_记忆策略》《AX_事件系统》《AX_Agent运行时》。

## 1. 分层与依赖方向

### 1.1 模块

| 模块 | 职责 | 依赖方向 |
|---|---|---|
| `tianshu-api` | 契约：服务接口、payload、日志与诊断面 | 不依赖任何业务模块 |
| `tianshu-core` | 运行时骨架：服务注册、协议运行时、会话与历史存储、模型/管线通用件 | 依赖 api |
| `tianshu-intake` | 语音输入（ASR）：模型装载、音频流、转写结果 | 依赖 api / core |
| `tianshu-weaving` | 语言模型引擎：请求调度、并发与配额、流式片段转发 | 依赖 api / core |
| `tianshu-echo` | 语音输出（TTS）：音色库、合成、播放投递 | 依赖 api / core |
| `tianshu-auxilium` | 对话智能体（AX）：轮次编排、提示词装配、记忆、事件、委派 | 依赖 api / core |
| `tianshu-client` | 客户端胶水：本地状态采集、界面、平台事件桥 | 依赖 api / core |
| `tianshu-adapter:neoforge-*` | 平台适配：NeoForge 事件、配置、注册表 | 依赖以上全部 |

三条硬约束：

1. **依赖单向**：api → core → 功能模块 → adapter。功能模块之间不互相 import，只通过 api 的服务接口与协议运行时通信。
2. **功能模块的 main 源不含平台依赖**：`net.minecraft`、`net.neoforged` 只出现在 adapter。功能模块因此可在无游戏环境下单测。
3. **能力发现用服务注册，不用构造注入链**：一个模块把自己的能力注册进 `coreManager`，另一个模块按类型取。跨模块调用点因此只有一处，便于替换与测试。

### 1.2 一次用户轮的端到端数据流

```text
输入（文本 / ASR 转写）
      │
      ▼
auxilium：轮次开始 ──► 事件缓冲并入历史（用户先开口）
      │
      ├─ 上下文采集：状态快照、记忆检索、近期对话、动态知识
      ├─ 提示词装配：单一 system + 追加式历史 + 尾部易变块
      │
      ▼
weaving：LLM 请求（流式）── 输出片段回投 auxilium
      │
      ▼
auxilium：输出解析（标签：委派 / 检索 / 正文）── 回答正文落历史
      │
      ▼
echo：TTS 合成与播放（播报不调模型）
```

四条关键分工：

| 环节 | 谁负责 | 不变量 |
|---|---|---|
| 历史 | auxilium 的近期对话系统 | 只追加；唯一改写来自压缩 |
| 提示词 | auxilium 的装配器 | 单一 system；易变内容只在尾部 |
| 模型请求 | weaving | 请求头确定性；不做内容改写 |
| 出声 | echo | 只播已经存在的正文，不为播出再跑模型 |

## 2. 跨模块不变量

违反任一条即为设计缺陷，不是取舍。

### 2.1 前缀与预算

| ID | 不变量 | 可检测信号 |
|---|---|---|
| P1 | **前缀稳定优先于内容新鲜度**：同一轮内"内容更新"与"前缀不变"冲突时，保留旧内容并降级到尾部块 | 同一会话序列内 system 哈希变化 |
| P2 | **单一 system 且字节冻结**：所有档位共用同一份文本，档位只改预算参数，不改 system 的任何字节 | system 哈希随档位变化 |
| P3 | **只追加**：历史只能追加；唯一的改写操作是压缩，且必须显式、一次性、可记账 | 同长度历史内容却变了 |
| P4 | **易变内容只在尾部**，且必须出现（不许为省 token 而整体不注入） | system 里出现坐标/血量/时间；或"因预算不足整体不注入状态" |
| P5 | **硬预算**：发出的请求满足 `prompt_tokens + maxTokens ≤ 上下文窗口`；不满足时必须先裁剪 | 出现上下文超限错误 |
| P6 | **确定性**：相同输入产出逐字节相同的消息序列（排序、数字格式、无时间戳、无浮点） | 两次装配的 prompt 哈希不同 |
| P7 | **计量口径分离**：本地估算只用于前瞻决策，账单与容量结论用 provider 返回的 usage，两者不得混用 | 用估算值下容量结论 |

### 2.2 内容与一致性

| ID | 不变量 | 理由 |
|---|---|---|
| C1 | **thinking/reasoning 绝不进历史、不进请求** | 它是过程产物；省下的是上下文容量与一致性，不只是钱 |
| C2 | **一条事实只有一个落点**：变化量只在事件里说，当前值只在状态块里说 | 同一事实两处各说一遍，模型会据此重复回答 |
| C3 | **语义单元不切开**：完整问答轮、完整记忆块、完整工具调用/结果对 | 切开的单元让模型看到孤立片段 |
| C4 | **记忆检索产物只进尾部块**，不写回 system、不改写历史 | 引入"每轮改写历史"的记忆方案会永久破坏前缀 |
| C5 | **正文与标签分离**：模型输出的正文是唯一播报内容，标签只表达意图 | 标签漏进 TTS 会被逐字朗读 |
| C6 | **不可信输入一律清洗**：模板渲染结果剥离尖括号、NFC 归一、按边界截断 | 防止提示词标签注入与不可复现字节 |

## 3. 前缀缓存友好

### 3.1 事实前提

模型侧没有显式缓存标记可用：命中来自"前缀逐字节相同"与提供方自身的自动缓存。单价上，缓存命中的输入 token 约为未命中的 1/50。因此**前缀每被改一个字节，成本杠杆即失效**。

### 3.2 三条设计

| 设计 | 做法 | 不做会怎样 |
|---|---|---|
| 只追加 | 历史 append-only，压缩是唯一改写且是显式成本事件 | 每轮拼一份新历史，前缀每轮 miss |
| 易变置尾 | 状态快照、记忆检索、待处理项全部放尾部块，每轮重建 | 状态进了前缀，命中率归零 |
| 确定性排序 | 固定槽位顺序、稳定排序键、无时间戳、无浮点 | 内容相同但字节不同，等于 miss |

### 3.3 边界

前缀缓存只保证"前缀相同的部分可能被复用"，不保证命中率。验收看的是实测 hit ratio，不是设计意图。

## 4. 尾部块的位置

尾部块承担"每轮必变、且必须被看见"的信息，与历史是两条平行通道：

| | 尾部块 | 历史 |
|---|---|---|
| 内容 | 当前状态、检索到的记忆、待处理项 | 用户与 AX 的对话、事件 |
| 生命周期 | 每轮重建，下一轮丢弃 | 追加后长期存在，可被压缩成记忆 |
| 能否被压缩 | 否 | 能（事件除外，见《AX_事件系统》§10） |
| 前缀影响 | 不影响（在末尾） | 影响很小（只追加） |

判定"该进哪一边"的唯一问题：**它有发生时刻吗？** 有（死亡、进入维度、别人说了话）→ 历史；没有（准星、血量、附近敌对数）→ 尾部。

## 5. token 计量

两条独立的口径，混用会得出错误结论：

| 口径 | 用途 | 性质 |
|---|---|---|
| 本地估算 | 每轮的前瞻决策：要不要裁剪、要不要触发压缩 | 近似，中文会被低估 |
| provider usage | 归档、校准、容量结论 | 真实计费值 |

估算器对中文与 JSON schema 系统性地低估（按"每 token 四字符"的启发式），因此：

1. 估算值只能用于"提前量"判断，阈值要按实测系数放余量。
2. 用 provider usage 反推校准系数，让估算在同模型、同请求形态下收敛。
3. provider usage 只在请求形态完全一致时可比（模型、工具集、配置任一变化都失效）。

## 6. 压缩的架构位置

压缩不是"顺手做的一步"，而是一次显式的后台作业：

| 属性 | 规定 |
|---|---|
| 触发 | 由窗口水位与容量决定，不在用户轮里临时决定 |
| 执行 | 后台车道，与聊天请求的响应隔离；聊天不因压缩而停等 |
| 输入 | system + 本次候选单元 + 边界摘要 + 指令；不含 thinking |
| 输出 | 结构化摘要（版本化 schema），分字段提交、字段级降级 |
| 记账 | 开始/结束成对记录，前后 token 落盘；原始事件不删 |
| 失败 | 不写空摘要、不静默降级；保留原文，下一轮再试 |

关键约束：**压缩只能缩减历史，不能碰前缀**；且在压缩进行时必须有快照点冻结，避免"压缩输入里的历史与随后发出的请求不一致"。

## 7. 线程与平台约束

| 约束 | 后果 |
|---|---|
| 游戏主线程是 tick 线程，不能在里面阻塞等模型 | agent 循环与模型调用放到独立执行器；结果通过队列回投主线程 |
| 单进程同步 append 在 MC 里不成立 | 同一会话的写入必须自己串行化（每会话一个串行队列） |
| 区域化多线程服务端（Folia 类） | 不能有"全局单例会话存储"当竞争点；按世界/玩家分片 |
| 客户端优先的前提 | AX 跑在客户端，不改变世界状态：只读旁听，事件与状态都不写回游戏对象；可选的服务端组件只做事实采集，不参与 AX 的任何判定 |

这三条决定了本项目里"看起来很自然"的许多写法不能用：任何在 tick 里 `.join()`、任何跨线程直接改会话容器、任何假定全局单例的缓存，都会在真实负载下炸掉。

## 8. 反模式

| # | 反模式 | 正确做法 |
|---|---|---|
| 1 | 用"每 token 四字符"的估算做容量结论 | 估算只做前瞻；容量用 usage + 余量 |
| 2 | 绕过追加直接改写历史/消息数组 | 只有压缩可以改写，且必须显式记账 |
| 3 | 频繁改写 system 的头节点 | 能追加就追加；system 字节冻结 |
| 4 | 工具/知识 schema 顺序抖动、动态开关 | 确定性排序；集合变化视为"新序列" |
| 5 | 每次追加都全量重算派生视图 | 增量 + 水位缓存，避免 O(n²) |
| 6 | 压缩参数互相矛盾（保留 ≥ 阈值等） | 参数校验前置，配置错误直接拒绝启动 |
| 7 | 切开会话中的语义单元（问答轮、工具对） | 以"整轮/整对"为切割粒度 |
| 8 | 假设"压缩后 token 一定下降" | 拿不到更小的摘要就不写；保留原文 |
| 9 | 为了省 token 整个块不注入 | 尾部块是信息完整性的底线 |
| 10 | 把 thinking 塞进历史或请求 | 只落 telemetry（长度、耗时） |
| 11 | 往事件/日志里塞非无损结构（NBT、循环引用、浮点） | 显式转纯 JSON，整数语义 |
| 12 | 给模型开一个"压缩工具"来自己控制上下文 | 压缩是后台策略，不是模型能力 |
| 13 | 靠"轮次预算"防跑飞 | 必须有显式的终止条件与无进展检测；上限由宿主强制 |

## 9. 观测与验收

每轮必须能回答四个问题，否则架构不可诊断：

| 问题 | 必落字段（概念） |
|---|---|
| 这一轮发了什么 | 请求字节哈希、system 哈希、前缀命中长度 |
| 花了多少 | 估算 token、provider usage、缓存命中/未命中 token |
| 为什么这么裁 | 各槽位预算、裁剪动作、被丢弃的候选 |
| 发生了什么 | 轮次状态、标签、委派票据、事件落点 |

验收口径：

1. 稳态前缀命中率达标（目标 ≥ 0.90）。
2. 首 token 延迟可控（语音场景的关键指标，与模型档位一起看）。
3. 上下文溢出次数为 0。
4. 任意一轮都能从落盘事件重建出同一份请求字节。

## 10. 不可迁移的外部设计

以下做法依赖外部产品的进程模型，本项目不具备，因此不作为参考：

| 外部做法 | 为什么不可照搬 |
|---|---|
| 多会话长期驻留 + 每会话独立折叠缓存 | 依赖单进程事件循环与对象生命周期 |
| 精确的资源级联释放 | 依赖框架的 fiber 拆除语义 |
| 协作式取消贯穿全链路 | 依赖统一的 AbortSignal 传递；本项目用显式的取消对象与世代号 |
| 后台任务/子代理的现成长驻机制 | 需要本项目的会话分片与执行器自重做 |
| 面向模型的会话树/分支 | 当前没有多分支需求，引入只会增加前缀不稳定的来源 |

本文保留的是结论，不是实现：**只追加 + 易变置尾 + 确定性排序 + 显式压缩 + 计量口径分离**。其余细节以本项目的三篇设计文档为准。
