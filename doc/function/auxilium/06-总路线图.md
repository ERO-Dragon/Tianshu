### 1.4 悬而未决（**6 条**，不钉死就会在实现时编数）

**1）R5 已解决（P1-1 执行完毕）。** 04 §10 的 R5 是"如果顺手让记忆参数跟随 `W` 就会放大 12 倍"。当时 A-3 已把真实 `W` 送进 `AXRuntimeLlmBudget.fromSnapshot`，而 `AXMemoryWindowPolicy.fromBudget` 里 `scale = W / REFERENCE_BUDGET(8000)` 还在，于是 100K 档下
`scale = 12.8` → `maxRawCharacters ≈ 120000 × 12.8 ≈ 1.53M`、`maxRawTokenCount ≈ 358400`、`recentRawKeepTokenMax ≈ 102400`、`chatInputBudget = 61440`、`systemTokenBudget = 6144`。
**现在 `REFERENCE_BUDGET` 与 `scale` 都已删除**，每个数值直接写成 `W` 的比例再 clamp：`shareOf(W, ratio, min, max)`（摘要块 `0.05W`、保持窗口 `0.10W`、水位 `0.70W`、压缩窗口 = 水位减去摘要块与保持窗口与尾部）。**100K 档对照值**：`maxRawCharacters` **262,640**（旧 1.53M）、`maxRawTokenCount` **65,660**（旧 358,400）、`recentRawKeepTokenMax` **10,240**（旧 102,400）、`chatInputTokenBudget` **71,680**（= `0.70W`，旧 61,440 = `0.60W`）、`summaryBlockTokenBudget` **5,120**、`shortTermCompressTokenMax` **55,420**。旧五槽比例（`RATIO_CHAT_INPUT` 与 knowledge/retrieved/recent/recentRaw/currentInput 五条）与 `systemTokenBudget` 一并删除，条数上限改由固定尾部 `TAIL = 900`（状态 256 / 检索 516 / 输入 128）除法派生，因此**不再随档位膨胀**（旧公式在 32K 档首轮就要 49 条）。

**2）OP7 的历史净增账未还（`<event>` 进历史）。** `AX_事件系统设计.md` §10.4 第 1 项与 §11-OP7 明确：`<event>` 改为追加进历史后，03 附录 A.1 的"每轮历史净增 ≈ 130 token"假设失效，于是 `C_low / K(换代间隔) / k(一代单元数) / 压缩摊销 / 首次换代轮数` **全部需要重算**；事件文档自己"不得给第二套数"，必须由 03/记忆再版统一裁定。
**本文的处理**：所有公式**照引用**（`C_low = 4096 + 1024 + SB + KEEP + 896`，`K = floor((T − C_low) / 130)`），**但把 130 标为待定**；P4-M3/P4-E1 的数字验收之前必须还账（§14-3）。

**3）`T3` 空置后"尾部 ≤ 900"的验收语义要改。** 运行时 §8.1 与 03 附录 A.2：`T3` 已空置，`T1/T2/Q = 256/512/128` 合计 ≤ 896 不变。于是"`tailTokens` P95 ≤ 900"（03 §10 P0 验收 4）实际是 **`T1 + T2 + Q`，且 `T3` 恒 0**。验收必须重写为这个口径，否则会出现一条永远"通过"的空断言。

**4）档位到底是"产品档"还是"预算档"，决定 `contextTier` 的落点。** 03 附录 A.1 与 04 A-1 写的是"产品档位，只决定 `W/B/P/T/R`，不参与 prompt 字节"；但实测它只影响一行 warn。若确认是"预算档"，则 P1-1 必须顺手把 `AXAssistantSettings.contextTier()` 补上并从 `AXModule` 读；若被认定为"仅展示档"，则它应当在 GUI 里降级为只读显示（避免"我选了 100K 却没生效"的 R3 抱怨，04 §10 R3）。

## 2. 遗留与清理审计（v2 新增）

### 2.4 清理阶段 P-C：产物、判据、穿插方式

**清单 schema**（一行一个对象，缺列即不算完成）：


**三条判据**（防止"看起来没人用就删"）：

1. **可达性 ≠ 调用点数量**：先查反射、注册表、资源键（`ax_prompt_texts.json`、`lang/*.json`）与配置键入口。一个没有 Java 调用点的方法，可能被资源键或枚举名引用。
2. **有测试守护的对象，删除/收编必须同提交改测试**（沿用 04 §8.1 的做法）；只删生产代码不动测试 = 未完成。
3. **"保留"必须写理由**（例如"灰度一个版本，04 Q4"），并写复核时点；**没有理由的一律删除**。

**穿插方式（硬要求）**：

- **每个功能阶段收尾跑一次**，单次 ≤ 1–2 人日：P1 收尾 → P-C1，P2 收尾 → P-C2，P3 → P-C3，P4 → P-C4，P5 → P-C5。

- **禁止攒到最后一次性大扫除**。三条理由：① 阶段之间文件集高度重叠，最后做时"这行是谁引进的"已不可追溯；② 一次性大扫除无法按阶段 revert，违反 §12 的回滚纪律；③ 残留会**在下一个阶段被当成"既有设计"继续复制**（R-g 三档 system 就是这么留下来的）。

### 10.1 两列布局

**现状**：HUD 是**单锚点单元素**。`PresenceHudLayout.resolve` 只解出一个 icon 中心点（并绑定经验条偏移，`:16-17,30-32`），`PresenceHudElementType` 只有 `STATUS_TEXT` / `ICON`，`PresenceHudRenderer.render(GuiGraphics)` 只渲染一个 frame（`:39,71`），控制器契约是 `update(PresenceHudElementUpdateContext) → Optional<PresenceHudElementFrame>`。

### 10.3 右列 = 统计表（字段与统计口径）

**（v2 修正）本节的边界先写清楚：分模块只到 token，不到钱。** 花费与余额一律是**全局**量。

**统计表字段（6 组，与需求逐条对应）**

| 7 | **剩余余额** | provider API 查询值，**全局** | `LlmBalanceProbe`（P4-L2，**未实现**） | `不可用（时刻）` |

**四条口径纪律（第 2 条是本次修正的核心，必须写进实现注释）**

1. **分模块只到 token，不到钱。** 不设"分模块花费"这一栏，因此**不存在分模块单价**。任何试图用"模块 token × 单价"得出的模块金额都是**未经授权的口径**——provider 只报总额，分模块推算不可靠，已明确放弃。
2. **分模块命中 token 的含义必须按字面理解**：它是"**该模块的请求中，provider 回报的命中量累加**"，**不是**"该模块的内容贡献了多少命中"。缓存由 provider 按**前缀**判定，同一前缀可能被多个模块的请求共享（例如多个模块共用同一 system + 历史前缀），因此：
   - ✅ 可以这样用：**各模块命中 token 之和 = 全局命中 token**（可逐日对账，也可用来回答"AX 辅星今天的请求里有多少是从缓存拿的"）。
   - ❌ 不可以这样用：比较两个模块的命中率高低、或说"某模块让缓存命中更多"。**缓存归因到内容来源在 provider 口径下不成立**，写清这一点是为了避免"数字看起来精确、口径却不是那个意思"。
   - 实现要求：该列的值必须由 `cacheHitTokens` 直接累加得到；**禁止**用 `promptTokens − cacheMissTokens`、`promptTokens × 命中率` 之类反推（04 D-1：不同 provider 口径不同，禁止推断）。
3. **花费与余额以 provider API 为准**（准确）；只有 API 不提供时，才允许用**全局** token × 单价本地折算，并**在界面上标注来源**。两者**永不互相校验**：不能用"API 余额差"去修正本地折算，那会把赠送额度/退款算进成本。
4. **单价全部来自配置，代码里不得出现任何金额常量**（AGENTS.md 硬编码红线 + 04 §3.3）。参考量级：DeepSeek 的命中单价约为未命中单价的 1/50（02 §0.1）——**这个比值只能写进配置默认值的注释里，不能写进代码逻辑**。

**价格配置项命名（全局，一组三键）**

```
llm.pricing.inputPricePerMillionMiss     未命中输入单价 / 百万 token（货币单位，如 ¥2.0）
llm.pricing.inputPricePerMillionHit      命中输入单价   / 百万 token（货币单位）
llm.pricing.outputPricePerMillion        输出单价       / 百万 token（货币单位）
llm.pricing.currency                     币种标识（空 = 不显示单位）
llm.pricing.effectiveFrom                价格生效时刻（留痕用，可选）
llm.balance.providerType                 provider 类型 → 余额探针实现的映射键
llm.balance.refreshIntervalSec           余额刷新间隔
llm.balance.failureBackoffSec            查询失败退避
```

**配置键 ↔ 已实现结构的映射（避免实现时各写一套）**：上述三键是**用户可见的配置名**，取值是"每百万 token 的货币金额"（`double`）。落进 `LlmPricing`（**已实现**）时要经 `LlmPricing.microsFromPrice(double)` 一次性量化成**微单位整数**（`inputMissMicrosPerMillion` / `inputHitMicrosPerMillion` / `outputMicrosPerMillion`），**之后所有运算只用整数微单位**（避免 `double` 累加漂移）。命名不同不是冲突，是"配置口径 vs 存储口径"的分层——代码里只出现微单位，配置里只出现货币金额。

> **多模型的隐患（记为 §14-9 拍板项）**：以上是三把全局单价。P4-L1 引入多模型后，不同模型单价不同，全局一把会把钱算错。建议保留全局三键作为默认，**另开可选覆盖层** `llm.pricing.<modelId>.…`（缺省回落到全局）。**在该拍板前，多模型默认只用同价模型，否则花费列按"混合单价"显示并在 UI 标注「单价未分模型」。**

**来源标注（界面必须显示）**

| 数值 | 标注格式 | 说明 |
|---|---|---|
| 今日/累计花费 | `¥1.23 · 本地折算 · 14:02` 或 `¥1.23 · provider API · 14:02` | 来源枚举只有这两个值 |
| 剩余余额 | `¥12.34 · provider API · 14:02` 或 `不可用 · 14:02` | **不允许**用本地账倒推余额 |
| 整体命中率 | `87.3% · 抽样 20 轮` | 分母窗口由配置（P5 看板）决定 |

### 10.4 数据流（谁产出 usage → 谁聚合 → 谁渲染）

```
① 产出（common，已有 + 一处新增出口）
   OpenAiChatStreamParser.Event{cacheHitTokens, cacheMissTokens}     [已有 :41,83-84]
     → OpenAiCompatibleInferenceClient.readStream 汇总              [已有 :532-576]
     → LLMStreamFinish（带 cache 数字）                             [P1-5 新增字段]
     → LlmPromptRequestHandler.handle(envelope, ctx)                [已有 :35]
           ├ 归属键 = envelope.header().sourceId()                  ← **在这里绑定一次**（信封必填字段）
           └ 调 LlmUsageLedger.record(sourceId, inputTokens,
                                       cacheHit, cacheMiss, outputTokens,
                                       cacheSplitReported)
                                  ↑ 只有 token 维度，**不含金额**     [**已接线**：LlmPromptRequestHandler.UsageRecording]

② 聚合（common，内存 + 待补的 append-only 落盘）
   LlmUsageLedger（TreeMap byModule + total + today，跨天 rollover）  [**已实现，纯内存**]
     → LlmUsageSnapshot（不可变只读 + 全局 todayCostMicros/totalCostMicros，-1 = 价格未配置）[**已实现**]
     → [待补] JSONL 按天分文件 + 启动回放最近 N 天                     [P3-H2 剩余项]
   LlmBalanceProbe（异步/定时/退避） → LlmBalanceSnapshot            [P4-L2 未实现]

③ 折算（common，只在全局维度，UI 之外）
   LlmUsageSnapshot.today/total（LlmUsageCounter）+ LlmPricing（微单位）
     → todayCostMicros / totalCostMicros → {值, 来源=本地折算}        [**已实现**]
   provider 提供总额时覆盖来源标注为 {值, 来源=provider API}          [P4-L2 未实现]
              ↑ 计价函数只接收全局 counter，**签名里没有模块维度**（结构上禁止分模块算钱）

④ 渲染（client/neoforge，主线程只读快照）
   PresenceHudStatsPanelController(update ctx) → PresenceHudElementFrame(PANEL_STATS)
     → PresenceHudRenderer.render(guiGraphics)                     [复用现有渲染栈]
```

**六条数据流纪律**：

1. **归属键只绑定一次**，位置在 `LlmPromptRequestHandler.handle`——那里同时拿到 `envelope.header().sourceId()`（信封，必填）与最终 `TokenUsagePayload`。`payload.requesterModuleId()` 可作交叉校验，但**不要**成为第二个归属键（两套键会分裂统计）。**禁止**在 client 侧维护"最后一次 usage"静态字段（04 D-2：TASK 车道并发会串号）。
2. **账本里不许有金额字段**：`LlmUsageCounter` 只有 `requests / inputTokens / cacheHitInputTokens / cacheMissInputTokens / outputTokens / cacheReportedRequests` **六个 token 维度**（第六维是"有多少请求真的报了缓存拆分"，缺了它就无法区分"命中 0"与"没上报"），金额只由 `LlmUsageSnapshot` 的全局方法派生。一旦金额进了计数结构，分模块算钱就会被顺手做出来（这是本条口径最容易被违反的方式）。
3. **UI 线程不碰 IO**：渲染只读 `LlmUsageSnapshot` / `LlmCostSnapshot`；账本写入与聚合在后台线程；快照按需替换引用（不可变对象，无锁读）。
4. **账本 append-only**，按天分文件，启动只回放最近 N 天（N 为配置项）以恢复"累计"——**不用全量扫描**。
5. **损坏行跳过并计数**（记 `usage_ledger_bad_line`），不得让一条坏行阻塞整个 HUD。
6. **`hitRatioPpm = -1` 直通到 UI 的"—"**：不可用与 0% 是两件事，混了会让"缓存坏了"和"没有缓存"看起来一样。

### 11.2 必须串行（有语义冲突或共享可变状态）

| 顺序 | 为什么不能反过来或并行 |
|---|---|
| **P1-1 → P1-2 → (P1-3, P1-4)** | P1-2 的派生函数是 P1-1 `ofTier` 的参数来源；P1-3 要用 `O`；P1-4 的阈值来自派生表。倒序会让 `ofTier` 先于它该读的表存在 |
| **P1-5 → P1-6** | P1-6 记账要用 payload 的 cache 字段 |
| **P1-1 → P2-2** | `S_LIMIT = 4096` 的校验意义建立在"预算不再按 `chatInput × 0.10` 推"之上；P1-1 之前 `systemTokenBudget` 是 6144，校验形同虚设 |
| **P1-2 → P1-4 的 GUI 展示** | "显示实际生效档"要用 `resolve` 结果 |
| **P2-1 → P2-2 → P2-3** | 只有单一 system 才有确定字节，`systemHash` 才有意义（04 2.2 第 4 条） |
| **P2-3 → P2-4** | 历史分区要靠 `addHistoryMessage` 这个新 API 落位 |
| **P2-4 ⇄ P2-5 同批** | `generation` 落盘与分区边界必须一致；单独上线 P2-4 会导致重启后边界与代次不一致 |
| **P2-3 / P2-5 → P4-M3** | 摘要块位置（P2-3）与代次持久化（P2-5）是压缩换代的两个结构前提 |
| **P3-M1 → P3-M2** | 三因子里的 `importance` 要能读字段 |
| **P1-6 → P3-H2** | 没有 `TOKEN_ACCOUNTING` 就没有右列的数字 |
| **OP7 还账 → P4-M3 / P4-E1 的成本验收** | `C_low/K/k/摊销` 的公式依赖"每轮净增 130"；`<event>` 进历史后该假设失效。**代码可以先写，但数字验收不能** |
| **R-a 去重定性 → P4-E1** | 新事件系统落地时，旧去重逻辑若仍在，会出现"新系统不去重、旧层去重"的静默不一致 |
| **P4-M3 ⇄ P4-A1 的 TASK 车道** | 两者共用 TASK 车道与 `taskPriority`；同时上线会让"谁的请求先跑"不可解释。建议 P4-M3 先行，Agent 的委派优先级在 `AXDetachedTask` 统一之后再加 |
| **P-C* ⊥ 一切功能阶段** | 清理改的正是刚被功能阶段改过的文件；并行会产生"删了又加回来"的冲突，且 revert 粒度失效（§9.3） |

### 11.3 推荐执行序列（含并行窗口）

```
窗口 1：P1-1 ──────────────────┬──────────────────────
        P1-5 ── P1-6 ──────────┤（并行，不同文件）
窗口 2：P1-2 ─ P1-3 ─ P1-4 ────┘ → P1-7 文档 → **P-C0 普查（紧跟 P1-1，必须做）**
窗口 3：P2-1 ─ P2-2 ─ P2-3 ─┬─ P2-4 ─ P2-5（同批）
        （HUD P3-H1 可在此窗口并行启动）      → P-C1
窗口 4：P3-H1 ─ H2 ─ H3 ─┬─ P3-M1 ─ M2        → P-C2
窗口 5：P4-M3 ─┬─ P4-L1 ─ L2 ─ L3             → P-C3
        P4-E1 ─┴─ P4-A1                       → P-C4
窗口 6：P5 收尾 ─ P-C5
```
