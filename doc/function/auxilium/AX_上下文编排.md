# AX 上下文编排

一轮请求的提示词怎么拼：消息序列、每段的变化规律、预算怎么分、压缩怎么触发与落地、系统提示词与语言表的纪律。以当前代码为准。

## 1. 目标与不变量

| 序 | 目标 | 度量 |
|---|---|---|
| G1 | 前缀缓存命中率最大化 | 稳态命中率 ≥ 0.90 |
| G2 | 语音首 token 延迟可控 | 首 token P50 ≤ 800ms（与档位一起看） |
| G3 | 上下文不溢出、不静默丢信息 | 溢出请求数 = 0；压缩有检查点可审计 |
| G4 | 可解释、可回放 | 任意一轮都能从落盘记录重建同一份请求 |

本编排层的硬约束（跨模块不变量见《AX_运行架构》§2）：

| ID | 不变量 | 检测信号 |
|---|---|---|
| L1 | 单一 system 且字节冻结：所有档位共用同一份文本 | system 哈希随档位/轮次变化 |
| L2 | 历史只追加；唯一改写是压缩 | 同长度历史内容却变了 |
| L3 | 每轮会变的内容只能出现在尾部（状态 / 检索 / 当前输入） | system 或摘要块里出现血量、坐标、时间 |
| L4 | 尾部是**尺寸**不是比例：不随窗口增长，每轮按未命中价全额付费 | 大档位的尾部明显大于小档位 |
| L5 | 空段不出现（输出空标签是错误） | prompt 里出现空标签 |
| L6 | 装配确定性：相同输入产出逐字节相同的消息序列 | 两次装配字节不同 |

## 2. 消息序列

装配器把内容分四类落位，`build()` 产出的顺序固定：

```text
[0]   system           ← 各上下文段以 \n\n 合并成的唯一一条（逐字节恒定）
[1]   user             ← STM 摘要块（累积的单元摘要，跨代存在）
[2..] user/assistant   ← raw turn 上下文，只追加；<event> 轮次是它的末尾部分
[..]  user             ← 每次追加的内容：<game_context> → <memory>
[n]   user             ← 当前输入，永远最后
```

`<event>` 是历史轮次（role=`world_event`），因此它会随窗口一起进入压缩、变成记忆；又因为事件总是在到达时立即追加，它实际落在历史段的末尾，紧贴逐轮追加的 `<game_context>` / `<memory>` 之前——看到的顺序与"raw turn 之后是逐轮追加段"一致。

| 段 | 内容 | 谁贡献 | 每轮变化 |
|---|---|---|---|
| system | 身份、行为规则、输出契约、禁止事项 | `ax_system` 段（唯一 system 文本） | 否（仅配置升级时变，需开新序列） |
| 摘要块 | 累积的单元摘要 | 记忆侧压缩任务产出 | 否（只有写入新单元摘要时才重渲染） |
| 历史 | 对话轮次与事件轮次 | 近期对话 | 只增长（每轮 +1 轮） |
| 尾部-状态 | 当前事实（准星、血量、维度、装备、背包…） | 游戏上下文 | 是（仅在状态变化时出现） |
| 尾部-检索 | 检索到的记忆与知识命中 | 记忆检索 / 知识库 | 是（仅有命中时） |
| 当前输入 | 玩家这一轮的话 | 本轮请求 | 是 |

### 2.1 段序（profile）

`sectionOrder` 决定贡献者的装配顺序，出厂配置为：

```text
ax_system → game_context → player_memory → recent_dialogue → current_input
```

摘要块的贡献者不在 `sectionOrder` 里：它写入的是独立槽位，位置由 `build()` 固定为 system 之后的第一条消息，与段序无关（见 §2.2）。段序只决定"谁先贡献"，最终消息顺序仍由 `build()` 决定：对话流在尾部段之前，当前输入永远最后。**不要**用 `messages.add(0, …)` 往前面插任何东西。

### 2.2 为什么摘要块是独立消息

- 并进 system → 每次写入新摘要都会让整段前缀从第 0 个 token 起失效。
- 落进尾部 → 它每轮都变，前缀永远不命中。

独立成 `system` 之后的第一条消息，让"写新摘要"的代价只等于摘要块本身，system 仍然命中。

## 3. 预算

### 3.1 唯一的输入是 W

`W` = 本轮模型报告的上下文总量（`contextTokenBudget`）。所有记忆侧数字都是 `W` 的函数，不存在"参考预算 × 缩放系数"：

| 段 | 公式 | 含义 |
|---|---|---|
| 摘要块 `SB` | `clamp(0.05 × W, 2048, 24576)` | 累积摘要的容量上限 |
| 保持窗口 `KEEP_MAX` | `clamp(0.10 × W, 2048, 49152)` | 逐字保留的最近原文 |
| 保持窗口目标 | `round(0.8 × KEEP_MAX)` | 裁剪回落目标（滞回，防抖） |
| 压缩水位 `WATERMARK` | `0.70 × W` | 触发压缩的 token 总量 |
| 压缩窗口 `COMPRESS_MAX` | `max(1, WATERMARK − SB − KEEP_MAX − TAIL)` | 等待被压缩的原文容量 |
| 压缩窗口目标 | `round(0.8 × COMPRESS_MAX)` | 压到这里就停 |
| 压缩单元 `UNIT` | `min(8192, COMPRESS_MAX)` | 一次压缩的候选量 |
| 原文总量上限 | `KEEP_MAX + COMPRESS_MAX` | 窗口硬上限 |

`W = 102400` 时依次是 5120 / 10240 / 71680 / 55420 / 65660——压缩窗口严格落在窗口内部，触发才可能真的发生。

### 3.2 尾部是固定尺寸

```text
TAIL = 900                                  尾部位硬上限，全档位一致
  T1 状态     = 256                          当前事实快照
  T2 检索     = 512                          记忆与知识共用
  Q  当前输入 = 128                          玩家自己的话
                ─── 三段合计 896，余 4 token
```

**为什么尾部不随窗口增长**：它每轮重发，每个 token 都按未命中价付一次。大窗口买到的是更长的保持窗口与更大的摘要块，不是更大的尾部。

### 3.3 条目配额由尾部减去估计值

| 项 | 算法 | 100K 档示例 |
|---|---|---|
| 检索池 | `tailRetrievalTokenBudget` | 512 |
| 记忆份额 | `round(0.85 × 池)` | 435 |
| 检索到的记忆块 | `记忆份额 / 40`（每块估 40 token） | 10 |
| 知识份额 | `池 − 记忆份额` | 77 |
| 知识命中条数 | `知识份额 / 20`（每条估 20 token） | 3 |
| 当前输入字符下限 | `max(1000, Q × 2)` | ≥1000 字符 |
| 保持窗口轮数 | `KEEP_MAX / 130`（每轮估 130 token） | 78 |

联合上限：记忆块 + 知识命中 ≤ 20 条；保持窗口轮数 ≤ 400 轮（该上限高于最大档位的合法保持窗口，只用于兜住错误配置）。

当前输入是唯一有下限的：截断玩家自己的话是产品错误。

### 3.4 预算的两个生命期

| 值 | 何时用 | 谁提供 |
|---|---|---|
| 构造期兜底 | 首轮预算尚未解析、或预算解析失败 | 模块构造时的固定值 |
| 每轮真实预算 | 正常路径 | 本轮模型报告的总量换算而来 |

**任何消费方都不得把构造期兜底当作本轮事实**：随真实上下文规模变化的量一律取每轮预算，只有解析失败才回退。

## 4. 状态块

### 4.1 内容与纪律

状态块只装**没有发生时刻的当前事实**：准星指向、血量与饥饿、维度与坐标簇、装备、背包摘要、附近敌对数量、时间与天气等。它每轮重建，不进历史、不进压缩、不出声。

三条纪律：

1. **只描述值**，不描述变化量，不带"上次是…"。变化由事件通道表达（《AX_事件系统》§2.3）。
2. **变化才出现**：与"上一次发送过的快照"比较，不是与"上一 tick 的状态"比较；否则玩家原地跳跃就会每轮产生新快照。
3. **空段不出现**：某段没有可注入的事实时整段消失，绝不输出空标签。

### 4.2 来源与形态

状态由平台侧采集，以**类型化字段**（数字 / 计数 / 标识符 / 文本 / 布尔 / 结构）提交，AX 侧负责措辞与排版：

- 事实行的载荷字段固定为 8 个：`factId` / `fields` / `priority` / `source` / `subject` / `tags` / `updatedAtMillis` / `ttlMillis`；正文由 `fields`（类型化值）渲染而成，载荷里没有"已渲染文本"字段。
- 事实行形如 `- <事实名>=<值>;…`，同一事实的多个字段并列。
- 数量类走语言表的口语量词（"少量 / 半组 / 一组多"），不写 `64x`、`3 stacks`。
- 玩家语义（"你"、"附近"）由措辞层决定，平台层不产出面向模型的句子。

## 5. 检索块

### 5.1 位置与数量

- 位置：尾部段（system、摘要块、历史之后，当前输入之前）。
- 数量：由 §3.3 的配额决定，不写死。
- 形态：一条尾部消息内的若干行，每行一条可独立引用的记忆或知识事实。

### 5.2 排序与去重

| 规则 | 做法 |
|---|---|
| 排序 | 按分数降序；同分用**稳定 tie-break**（时间、id），保证字节可复现 |
| 去重 | 按内容哈希去重，**先排序再去重**、保留首个 |
| 截断 | 只按完整语义单元截断（整条记忆、整条知识），不切半句 |

打分公式、档位与预算归《AX_记忆策略》§6，本文不复述，避免两处各写一套。

### 5.3 与状态的边界

检索产物是"历史里可能相关的旧事"，状态是"此刻的事实"。两者都在尾部，但互不替代：检索不到就是没有命中，不许用状态顶替；状态缺失也不许用检索结果冒充当前值。

## 6. 压缩

### 6.1 触发

- **水位触发**：原文总量超过 `WATERMARK`（0.70W）时进入压缩流程。
- **容量触发**：原文总量顶到 `MAX_RAW_TOKENS`，或窗口发生过容量硬裁剪。
- 触发判定在轮次之间的维护点做，不在用户轮的请求路径里临时决定。

### 6.2 输入与单元

```text
压缩输入 = system + 本代已产出的摘要块 + 本次候选单元的原文轮次 + 指令
```

- 候选单元 = 连续、**尚未被任何单元摘要覆盖**的对话轮次，按 `UNIT` 预算从旧到新取；保持窗口内的轮次永不进单元。
- 事件轮次不进单元（见《AX_事件系统》§10）。
- 单元边界以"轮"为粒度，不切半轮。

### 6.3 输出与落地

- 输出是**结构化摘要**（版本化 schema）：单元摘要、可抽取的事实与偏好、字段级置信与溯源。
- 分字段提交：某个字段解析失败只降级该字段，不整批作废。
- 摘要块按"新→旧"累积渲染，超过 `SB` 时淘汰最旧单元。
- **一句话摘要为空即不写**：宁可保留原文、下一轮再压，也不写空摘要占位。

### 6.4 快照点冻结

压缩开始时冻结输入快照（本轮请求用的历史版本），压缩期间新到的轮次只追加、不改写快照。这样"压缩看到的"与"用户轮发出的"永远一致，不会出现摘要覆盖了尚未进入请求的轮次。

### 6.5 执行位置与互斥

- 压缩在后台车道执行，与聊天请求的响应隔离：用户轮不因压缩而停等。
- 同一世界同一时刻只有一个压缩作业；作业进行中再次触发直接跳过（防压缩风暴）。
- 开始/结束成对记账，前后 token 落盘；中途崩溃可通过"有开始无结束"检出。

### 6.6 失败路径

| 失败 | 处理 |
|---|---|
| 模型返回不可解析 | 不写摘要，保留原文，记录诊断 |
| 摘要比原文更大 | 丢弃该候选单元的结果，保留原文 |
| 部分字段缺失 | 该字段降级（空值），其余字段照常写入 |
| 预算解析失败 | 用构造期兜底，不中断轮次 |

## 7. 确定性规则

同一状态两次装配必须逐字节相同。可执行清单：

| # | 规则 |
|---|---|
| 1 | 段排序用固定顺序常量，禁止依赖 Map 迭代序或 locale 排序 |
| 2 | 集合一律有序结构 + 显式比较器；禁止哈希序进 prompt |
| 3 | 时间戳、相对时间、"现在"、随机 id、会话 id 不进 system / 摘要块；需要就放尾部 |
| 4 | 数值：整数原样；无法避免浮点时用固定 locale 的固定小数位；前缀区禁止浮点 |
| 5 | 换行统一 `\n`，段落间 `\n\n`；文本入 prompt 前 NFC 归一、去行尾空白 |
| 6 | 空段整段不出现，不允许"有时空标签有时不出现" |
| 7 | 去重先排序后去重，保留首个 |
| 8 | 截断按码点，不切断代理对 |
| 9 | 并行装配按声明顺序合并，不按完成顺序 |
| 10 | 排序 key 里的浮点先定精度再比较，避免末位差异翻转 tie-break |

## 8. 系统提示词与语言表

### 8.1 系统提示词

- **单一文本、字节冻结**：所有档位共用同一份，档位只改预算参数，不改系统提示词任何字节。取消"按预算挑短/中/长三份"的做法——省下的几百 token 远小于前缀失效的代价。
- 出厂文本的分段主题（以资源为准）：身份与说话方式、一次只说一两句与标点纪律、边界（不改游戏状态、不执行动作）、`<delegate>` 标签契约（含正反例与标签位置）、没话说时的最短回应。
- **提示词只有一份中文**：`AXPromptLanguage.BASE = ZH_CN`，所有玩家拿到同一份字节；资源查找缺键时回退到 BASE，不回退英文。玩家说什么语言只影响"要求模型用什么语言回答"，不影响提示词本身。
- 系统提示词的任何编辑都等于换一份 system：必须开新序列，否则前缀从第 0 个 token 起失效。

### 8.2 语言表

所有面向模型或玩家的措辞都在语言资源里，代码里不出现自然语言：

| 资源 | 用途 |
|---|---|
| 系统提示词 profile | 唯一 system 文本 + 段序 |
| `ax_prompt_texts.json` | 各段包裹键与行模板（`section.*`、`game_context.*`、`dynamic_knowledge.*`、`memory_summary.*`、`player_memory.*`、`recent_dialogue.*`） |
| 记忆任务提示词 | 压缩与抽取的规则表与 schema |
| 回复文案 | 失败提示、拒绝、占位等对玩家说的话 |

渲染纪律：

1. 模板渲染只做 `{{var}}` 替换；变量缺失按空串处理并记录诊断，不抛到轮次里。
2. 渲染结果视为不可信输入：剥离尖括号、NFC 归一、按边界截断（长度上限由事件与轮次各自的契约规定）。
3. 模板键缺失时回退到键名或占位符，并留下可观测诊断，不静默产出半句。

### 8.3 语音可读性

玩家听到的就是模型写的字，链路里没有 SSML：

| 事实 | 推论 |
|---|---|
| 没有 `<break>` / `prosody` 等标记 | **标点是唯一的停顿与语调手段** |
| 符号默认按字面念 | 排版符号、列表前缀、emoji、URL、括号注释必须在提示词里降概率，并有确定性兜底剥离 |
| 标识符里的 `:` `/` `_` 会引入停顿 | 说中文名；必须给 id 时去掉命名空间 |
| 长数字串听感差 | 数量用口语量词，坐标改说相对方位 |

兜底层是 TTS 侧的文本规整器：只清洗送进合成的文本，**历史与界面保持原样**（历史要用于压缩与检索，不能被改写）。它必须纯函数、幂等、不产出本地化文案——只删字符或换成标点。

提示词侧的三条可执行要求：说成能念出口的话、一句一断、句末必须有标点（问句用问号）。

## 9. 观测与验收

每轮至少落以下字段（概念级）：

| 组 | 字段 |
|---|---|
| 请求 | 请求字节哈希、system 哈希、摘要块哈希、消息条数 |
| 预算 | W、各段实际 token、尾部各段占比、被裁剪项 |
| 缓存 | 前缀命中长度、命中/未命中 token、命中率 |
| 记忆 | 检索候选数、注入条数、最高/最低分、被去重条数 |
| 压缩 | 是否触发、单元 id、前后 token、字段级降级标记 |

验收：稳态命中率达标；溢出为 0；同一输入两次装配字节相同；任一轮可重建。

## 10. 禁止事项

| 禁止 | 原因 |
|---|---|
| 把每轮会变的内容拼进 system | 每轮全 miss，成本杠杆失效 |
| 给 system 做"按预算的多个版本" | 省不到钱，还制造档位与 system 的隐式耦合 |
| 往消息列表头部插内容 | 前缀从插入点起全部失效 |
| 每轮重渲染全部历史 | 一个字节不同即 miss |
| 往尾部塞调试字段（requestId 等） | 每轮必变，白白扩大未命中区 |
| 把 thinking/reasoning 回填进历史 | 污染内容、烧 token，且模型会当成自己说过的话 |
| 在尾部放"压缩工具"让模型自己控制上下文 | 压缩是后台策略，不是模型能力 |
| 让检索或状态两处各说一遍同一事实 | 模型会据此重复回答 |
| 在代码里写自然语言或直接写死模板 | 全部走语言资源 |
