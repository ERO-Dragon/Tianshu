## 1. 三个核心方向（基座本体）

| # | 方向 | 回答什么 | 代码 |
|---|---|---|---|
| 1 | **模块宿主** | 模块怎么被装配、启动、关停、出状态 | `api/assembly`、`core/lifecycle`、`client/runtime` |
| 2 | **协议中心** | 模块之间怎么互相说话（信封、优先级、取消、超时、死信） | `protocol`、`protocol/runtime`、`core/protocol` |
| 3 | **模块能力注册** | 模块怎么声明"我能处理哪些语义能力"（语音、对话这类） | `core/protocol/registry` |

这三个方向是"装模块、模块之间说话、模块登记能力"，缺一条就不叫基座。

## 2. 三个功能方向（给谁用）

| # | 方向 | 是什么 | 代码 |
|---|---|---|---|
| 4 | **模型工具能力** | 告诉模型有哪些工具可调，以及 skill / resource / prompt 这些可读材料 | `TianshuTools` + `CapabilityCatalog` |
| 5 | **玩家辅助** | 替玩家动手：合成、工作方块、容器搬运、方块交互与放置、挖方块、读状态 | `craft.recipe`、`block.machine`、`container.transfer`、`block.interact`、`block.place` 等 |
| 6 | **自定义实体** | 注册一种实体、驱动一个实体实例、与同一世界交互 | `api/entity` |

**互斥**：一个模组要么以玩家身份行事，要么派身体行事，不会同时用两套；两个方向各自自足，不互相引用。

## 3. 档位：两条轴，不折成一个数

| 轴 | 档位 | 问的问题 | 管什么 |
|---|---|---|---|
| 玩家辅助 | `ToolAutonomy.READ_ONLY` / `CONSERVATIVE` / `FULL` | 这是不是玩家在生存里不靠作弊能做的事 | 工具注册表 |
| 实体能力 | `BodyAutonomy.SURVIVAL` / `PRIVILEGED` | 这具身体能不能亲自做到 | 实体动作 |

两条轴各判一条，**取严**，不做"逐级映射"——两者回答的问题不同，映射出来只是假的一致。
`BodyAutonomy.allowedBy(ceiling)` 是唯一说明"服务器上限对身体意味着什么"的地方：
只读 → 不许干活；保守 → 只许生存级；全开 → 也允许特权级。
`entity.move` 这类"一个工具多个子模式"的，由工具按当次允许级别自查：walk 生存级，fly / teleport 特权级。

**`Tool*` 前缀只指模型工具**：`ToolPermission`、`ToolAutonomy`、`ServerAutonomyCeiling` 只对工具注册表生效，
对实体层与归属层一律不适用——`entity.*` 的放行只看归属，不看这两把尺。

## 4. 授权：三层，各管各的

| 层 | 判什么 | 依据 |
|---|---|---|
| **实体权限** | 这个实体在服务器上有多大权限（op 级别、领地、受保护） | 服务器既有体系；`playerLike=true` 时由假玩家自动继承 |
| **归属权限** | 谁能指挥这个实体 | `EntityActors` 的 owner + `EntityAccess` |
| **调用方权限** | 调用者自己的 op 与档位 | `ToolPermission` + `ToolAutonomy` + `ServerAutonomyCeiling` |

三层互不替代：有 op 不等于能驱动别人的身体，能驱动自己的实体不等于能改游戏规则。

## 5. 原子与分子：基座只做到原子

**原子能力**＝一次调用做一件事（`entity.mine` 挖一块、`entity.move` 走一次、`block.inspect` 报一块方块）。
**分子能力**＝把原子动作编排成工作流（挖一整条矿脉、搭桥铺路、盖房子）。**技能**＝给模型看的说明书，不是能力。

- 基座**只提供原子能力**，外加编排原语（`entity.sequence`、`tool.cancel`）；
- 分子能力属于具体模组——它们不是"基座缺的工具"，是模组该写的工作流；
- 能力表里的 `kind=WORKFLOW` 只是分类（订阅要用），不是另一种入口，见 [能力与工具](能力与工具.md) §6。

**不跟的做法**：同赛道有实现把工具面换成图灵完备脚本，理由是工具太多会淹没模型注意力。我们不做脚本层——
编排是模组的事，而且脚本层会把"能力标签 + 自主度门槛"这套授权模型复杂化，多模块归属正是本基座与其他实现的分界线。

## 6. 刻意不做

| 不做 | 为什么 |
|---|---|
| 沙箱 | 基座没有沙箱，档位约束的是**模型能碰到什么**，不是模块能干什么 |
| 通用 `invoke` 总入口 | 工具表长度由订阅决定，不值得用"每次调用多查一次参数"去换 |
| 把复合能力分成"引擎执行 / 提供方执行"两类 | 无安全差异，只是可观测性差异；两种都合法 |
| 寻路深度（搭桥、垫脚、挖隧道）、连挖 | 是分子能力，属模组层；基座给 `entity.sequence` 这类原语 |
| 对第三方模组的联动（光影包等） | 依赖特定第三方 API，由将来的扩展模组以 skill / tool 提供；舟楫只提供注册入口 |
| 工作流的循环 / 递归 / 变量运算 | 按证据再长，当前不需要 |

## 7. 默认开关的取舍

- **玩家辅助默认开**（合成、整理、操作方块）：这是替玩家做他用手能做的事。
- **`block.break` 默认关**：放错了能拆，拆错了回不来——这对不对称是有意的，不是遗漏。
- **作弊类（`FULL` 档）默认关且需要 operator**：传送、天气、时间、给物品、生成实体、广播、游戏模式、状态效果、
  经验、任意坐标放置、清除实体、附魔、难度、游戏规则。
- **`server.say` 不是作弊**：以玩家身份在聊天频道说一句，`LOCAL` 类、`CONSERVATIVE` 档、默认开；
  它和 `server.broadcast`（系统公告、`FULL` 档）是两个能力，不要合并。
- **实体写操作默认关、permission 为 EVERYONE**：放行只由归属决定，写世界仍受服务器开关约束。
