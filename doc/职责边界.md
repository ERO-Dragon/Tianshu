> 模组：跨模组（`tianshu-api` / `tianshu-core` / `tianshu-client` 共用）。

## 1. 三个核心方向（基座本体）

| # | 方向 | 回答什么 | 代码 |
|---|---|---|---|
| 1 | **模块宿主** | 模块怎么被装配、启动、关停、出状态 | `api/assembly`、`core/lifecycle`、`client/runtime` |
| 2 | **协议中心** | 模组按协议能力投递请求，按主题发布事件，由协议中心处理路由、优先级、取消和超时 | `protocol`、`core/protocol/registry` |
| 3 | **智能体能力中心** | 模组发布工具、技能、资源、提示词与工作流，智能体按订阅发现、读取或调用 | `TianshuTools`、`CapabilityCatalog` |

两个中心各有自己的注册入口。模组可以只处理协议消息，也可以把某项功能发布给智能体。玩家辅助和自定义实体共用智能体能力中心的工具契约与订阅规则。

## 2. 两个功能方向（给谁用）

| # | 方向 | 是什么 | 文档 |
|---|---|---|---|
| 4 | **玩家辅助** | 替玩家动手：合成、工作方块、容器搬运、方块交互、读状态。工具**以该玩家身份**执行 | [玩家辅助](玩家辅助.md) |
| 5 | **自定义实体** | 注册一种实体、驱动一个实体实例、与同一世界交互。工具**经身体**执行 | [实体操作](实体操作.md)、[实体](实体.md) |

两者结构同形：都有一组工具、都有一个技能装说明书、都受同一套工具契约约束（[智能体能力中心](智能体能力中心.md)）。
差别只在**执行者**，以及由此带来的授权方式。

**一个动作两个 id，各服务一种执行者**：玩家侧留原 id（`block.interact`、`container.transfer`、`craft.recipe`…），
实体侧是 `entity.*`（`entity.interact`、`entity.transfer`、`entity.craft`…），带 `body` 参数、默认要归属。
两侧不共用一个 id，也不共用一个 `body` 参数——"以谁的身份执行"在工具名里就定死了，
模型不需要先判断"这次算谁的"，文档也不必在一个文件里讲两种人。

**放方块与拆方块不在玩家侧**：那两件事是玩家自己的右手在干的，模组不替他决定（`entity.place` /
`entity.mine` 是身体用手，不是替玩家用手）。所以玩家侧没有 `block.place` / `block.place.line` / `block.break`。

## 3. 玩家辅助与实体能力

| 轴 | 档位 | 问的问题 | 管什么 |
|---|---|---|---|
| 玩家辅助 | `ToolAutonomy.READ_ONLY` / `CONSERVATIVE` / `FULL` | 这是不是玩家在生存里不靠作弊能做的事 | 玩家侧的 `minecraft:*` 工具 |
| 实体动作 | 生存能力 / 作弊能力 | 身体执行的是什么动作 | 经身体执行的动作，状态查询不占动作档位 |

服主用 `autonomy.ceiling` 设置玩家辅助上限，用 `npc.ceiling` 为全服 NPC 单独设置最高档。NPC 默认生存档。两项设置可任意组合。

模组只能驱动自己申请的身体。身体提供方通过 `EntityCapability` 声明能做哪些动作，通过 `nativeMovementModes()` 声明原生移动方式。鸟飞行、末影人原生瞬移属于生存；给只会步行的身体额外提供瞬移，需要作弊档。实体命令还需操作员逐次批准。

## 4. 授权：三层，各管各的

| 层 | 判什么 | 依据 |
|---|---|---|
| **实体权限** | 这个实体在服务器上有多大权限（op 级别、领地、受保护） | 服务器既有体系；`playerLike=true` 时由假玩家自动继承 |
| **归属权限** | 谁能指挥这个实体 | `EntityActors` 的 owner + `EntityAccess` |
| **调用方权限** | 调用者自己的 op 与档位 | `ToolPermission` + `ToolAutonomy` + `ServerAutonomyCeiling` |

三层互不替代：有 op 不等于能驱动别人的身体，能驱动自己的实体不等于能改游戏规则。

## 5. 原子与分子：基座只做到原子

**原子能力**＝一次调用做一件事（`entity.mine` 挖一块、`entity.move` 走一次、`block.inspect` 报一块方块）。
**分子能力**＝把原子动作编排成工作流（挖一整条矿脉、搭桥铺路、盖房子）。**技能**＝给模型看的说明书，不是能力。

- 基座**只提供原子能力**，外加编排原语（`entity.sequence`、`tool.cancel`）；
- 分子能力属于具体模组——它们不是"基座缺的工具"，是模组该写的工作流；
- 能力表里的 `kind=WORKFLOW` 只是分类（订阅要用），不是另一种入口，见 [智能体能力中心](智能体能力中心.md) §6。

**不跟的做法**：同赛道有实现把工具面换成图灵完备脚本，理由是工具太多会淹没模型注意力。我们不做脚本层——
编排是模组的事，而且脚本层会把"能力标签 + 自主度门槛"这套授权模型复杂化，多模块归属正是本基座与其他实现的分界线。

## 6. 刻意不做

| 不做 | 为什么 |
|---|---|
| 沙箱 | 基座没有沙箱，档位约束的是**模型能碰到什么**，不是模块能干什么 |
| 通用 `invoke` 总入口 | 工具表长度由订阅决定，不值得用"每次调用多查一次参数"去换 |
| 把复合能力分成"引擎执行 / 提供方执行"两类 | 无安全差异，只是可观测性差异；两种都合法 |
| 寻路深度（搭桥、垫脚、挖隧道）、连挖 | 是分子能力，属模组层；基座给 `entity.sequence` 这类原语 |
| 对第三方模组的联动（光影包等） | 依赖特定第三方 API，由将来的扩展模组以 skill / tool 提供；舟楫只提供注册入口 |
| 工作流的循环 / 递归 / 变量运算 | 按证据再长，当前不需要 |
| 完整的 JSON Schema 草稿校验 | schema 是给模型的指南，不是第二道夹取；只校验类型与必填，不拦数值/长度 |
| 工具层的排队与优先级 | 并发按调用者限到 8，满了就 `BUSY`；真正的排队是协议中心的 Broker |
| 流式进度、子 agent、长期记忆、代码执行 | 不是基座该管的事，属具体模组的编排 |
| 确认弹窗 | 用**风险分级**（档位 + 权限 + 开关）替代——每步弹窗会把助手变成点确认的机器 |

## 7. 默认开关的取舍

- **到 `conservative` 为止的工具不要开关**：档位就是闸门。合成、整理、操作方块、按按钮这些，把 `ceiling`
  设成 `conservative` 就该能跑；再叠一个"先把这个开关打开"只会让"我明明开了档位为什么还是 DISABLED"变成常态。
- **`FULL` 档默认关、每把一个开关、还要 operator**：传送、天气、时间、给物品、生成实体、广播、游戏模式、
  状态效果、经验、任意坐标放置、清除实体、附魔、难度、游戏规则，以及 `command.run`。
  这些是 operator 主动交出去的权，一个服务器可能只想给其中几个，所以逐个开关。
- **`server.say` 不是作弊**：以玩家身份在聊天频道说一句，`LOCAL` 类、`CONSERVATIVE` 档、默认开；
  它和 `server.broadcast`（系统公告、`FULL` 档）是两个能力，不要合并。
- **玩家的两只手不代做**：放方块、拆方块、用手里的物品，这三件事玩家自己干，基座不提供玩家侧工具
  （`entity.place` / `entity.mine` / `entity.item.use` 是**身体**用自己的手，不是模型替玩家用手）。
- 实体动作默认启用，实际调用受 `npc.ceiling`、归属和身体声明约束。

- **唯一每次都要批的实体动作是 `entity.command.run`**：跑命令不是实体的能力，是服务器权限，
  服主须允许作弊档，操作员再批准该行命令的一次性令牌。
