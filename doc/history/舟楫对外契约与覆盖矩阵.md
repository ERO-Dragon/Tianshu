# 舟楫对外契约 × 覆盖矩阵

> 用途：回答一句一直被含糊带过的话——**"这个平台验到什么程度了"**。
> 规则：一行一个对外契约单元；每行必须写清"**位置与规模 / 谁在验 / 验收台覆盖 / 缺口**"。
> 没有清单就没有"漏了"，只有"感觉差不多"。本文就是那张清单。
>
> 关联：[舟楫待修问题清单](../architecture/舟楫待修问题清单.md)（§16 验收开工判定、§17 验收台）、
> [平台契约回归](平台契约回归.md)、[工具层游戏内验收](工具层游戏内验收.md)。

## 0. 口径

- **规模**：`src/main/java` 下的文件数（`Tianshu-ferry` 三个模块合计 **504**：api 350 / core 57 / client 97）。
- **自动化测试**：JUnit（三个模块合计 133 个测试类 / 566 个 testcase）。
- **门禁**：`Tianshu-adapter/build.gradle` 里的 12 个 `verify*` 任务。
- **验收台**：`tianshu-lab` 的 `acceptance` 包（`ACC-*` 用例，见待修清单 §17）。
- **实机**：进游戏人工确认（三份既有清单）。
- 标记：✅ 有覆盖 / 🔶 部分 / ❌ 无 / ⏸ 明确不做（并写理由）。

## 2. 统计

| 结论 | 数量 |
|---|---|
| **对外契约单元** | 19（原 18，MCP 拆成 client / server 两行） |
| 有自动化测试覆盖（✅ 或 🔶） | 15 |
| 完全没有自动化 | 2（HUD、服务端动作六件事） |
| 明确不验（⏸） | 1（音频，归模块） |
| **验收台覆盖的单元** | **7 / 18**（工具契约、能力表、智能体门面、诊断、设置、模型下载、游戏上下文），38 条用例分 10 个面声明 |
| 验收台用例 | 41 条 + 1 条自检（实机 38 通过 + 2 SKIP + 自检变红，`accepted=true`） |

**一句话**：内部逻辑主要靠 566 个 testcase 和 12 个门禁；**验收台现在只覆盖 18 个对外单元里的 2 个**，"平台验收"这个说法目前不成立。

## 3. 缺口排序（照这个顺序补）

| 优先级 | 缺口 | 为什么排前面 | 建议手段 |
|---|---|---|---|
| 1 | `AgentSession` 无游戏内验证（第 3 行） | 功能模组唯一会碰的门面；它错了是全家一起错 | 验收台加 `ACC-AGT-*`（发现/调用/读取/订阅） |
| 2 | `body.*` 从没实机跑过（第 13 行） | 天枢的核心能力；单测只证状态机，不证真实世界 | B 档：lab 先摆现场（给物品/放方块）再调工具 |
| 3 | 服务端动作六件事（第 17 行） | 六个动作**完全没有自动化**，且不走工具层 | 实机脚本 + 每条记录返回与副作用 |
| 4 | HUD（第 10 行） | 玩家可见，零自动 | 实机截图对比 |
| 5 | 42 条 adapter 分支（第 18 行） | 结构性缺失，非质量 | 按 `DEC-8` 排期，先做构建矩阵 |
| 6 | `MDL-5` 删除/下载互斥（第 12 行） | 已定位未修 | 见待修清单 §13 剩余项 |

## 4. 明确"不验"的部分（每条都要有理由，否则就是漏了）

| 项 | 理由 | 谁来兜 |
|---|---|---|
| 语音的播放/打断/识别/设备切换 | 只有耳朵能判 | 听澜 / 回响 模组各自的验收（作者 2026-11-15 批注） |
| 纯内部逻辑（broker 记账、槽位代数、限流桶、下载重试） | 单测已经逐条钉住；验收台重复一遍不产生新信息 | 566 个 testcase |
| 42 条未检出的 adapter 分支 | 工作区没有源码，验不了 | `DEC-8`：功能完成后再拓展版本 |
| 运行时并发正确性 | 需要压测装置，不是验收台能提供的 | 待专项（待修清单 §15 已记） |

## 5. 实机首跑（2026-11-15，1.21.1-neoforge）

无头触发 `runClient -PtianshuLabAcceptance=1`，首跑 15 条 = **12 通过 / 1 跳过 / 2 失败**（1 条失败是自检按设计变红）。
证据两处同源：`run/tianshu-lab/acceptance-<ts>.json` 与 `run/logs/tianshu-diagnostics.log` 的 `acceptance.run` 事件。

首跑暴露并被修掉的两条：

- **`ACC-ARG-1` 首跑红**：给 `capability.read` 传未声明字段被**接受**。根因是 `ToolArgumentValidator` 只在 schema 写了
  `additionalProperties: false` 时才拒绝。**已修**：校验改为默认严格（要自由参数必须显式 `additionalProperties: true`），
  发布 schema 时同步补出这条严格性；新增 `ACC-ARG-3` 扫全表锁住（只读 schema，不调用工具）。
- **`ACC-EXP-4` 首跑跳过且永不可能通过**：开发客户端一启动 `serverAvailable()` 即为真。**已改成两态可判**：
  服务端行出现 ⟺ 通道可用。

**复跑**：16 条 = **15 通过 + 1 条自检按设计变红**，`accepted=true`、`selfCheckHeld=true`。
这条复跑同时是"严格性修复在真实客户端生效"的证明：`ACC-ARG-1`（严格 schema 拒绝额外字段）与
`ACC-ARG-3`（25 个已发布 schema 全部声明严格性）双绿。

**铺满后复跑**：28 条 = **27 通过 + 1 条自检变红**，`accepted=true`。之后又补了 3 条与"覆盖分组"输出，
**这 3 条未实机**（只过编译与 23 个单测），实机绿的最新证据是 28 条那一轮。
