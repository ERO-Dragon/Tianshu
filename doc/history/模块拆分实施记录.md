## 1. 施工顺序

每阶段结束的验收口径是**能 `runClient` 跑通语音对话**，否则不进入下一阶段——避免多阶段叠加后
无法定位是哪一步引入的问题。

| 阶段 | 内容 | 结果 |
|---|---|---|

## 2. 关键取舍

### 2.1 IR 并入听澜

没有独立生命周期需求，保留为独立模块是过度设计。代价：去掉"修复前查询映迹上下文"的异步链路
（300ms 超时 + pending + response handler），裸指代词（"用这个"）不再结合手持物品消歧——显式命名的
物品照常纠错，辅星自有上下文链路可覆盖。

后路：`IR_RESULT` 保持公共 topic，将来若要独立，搬文件即可，订阅方零改动。

### 2.2 映迹整体留在 client

映迹是双向枢纽：既向功能模组提供事实，又消费原型事件。搬到独立模块会让 `特征→映迹→特征` 成环，
而它本身不依赖任何功能模组——留在 client 是契约关系而非依赖，且天然自然降级（无活动就显示空闲）。
这也是 9 个映迹载荷留在 `tianshu-api` 的原因。

> **2026-10 修订（推翻本条）**：映迹改为拆成可选功能模组 `tianshu-presence`，独立演进；成环问题由
> 「听澜/辅星硬依赖映迹，回响/织言只保留对映迹 HUD 活动的可选边」解决。阶段一（端口化）与阶段二（建模组、
> 搬代码与载荷、宿主解耦、依赖矩阵）均已完成，取舍见 §7；只剩实机验收与外部文档。

### 2.3 设置框架留 client，内容随模块

设置页共 4562 行，依赖 client 的 `ClientScheduler` / `AudioDeviceCatalog` / `settings.registry`。
框架（布局、草稿、会话、校验）是共用渲染逻辑，留在 client；各模块通过 `addSettings` 贡献自己的页面。
若把框架也搬进功能模块，`feature → client → feature` 成环。

### 2.4 热词物化整条链路删除

内核契约里最后一个带功能语义的方法 `VoiceResourceConfiguration.getAsrBasePath()` 已删除，连同
`VoiceResourceManager` / `VoiceResourceAccess` / `VoiceResourceSnapshot`。ASR 引擎侧的"热词加权文件"
也一起移除：`AsrHotwordSupport`、引擎 `hotwordsFile` 参数、语料工厂的 hotwords 配置、听澜的
`HOTWORD_RELOAD` 重载状态机。

理由：热词支持本来就是按模型而定的（`AsrHotwordSupport.fromModel(...)` 只为部分模型返回
`reloadRequired()`），却要求内核知道听澜的目录并替它写文件。

替代保证：词表的唯一真相源是 `TriggerRegistry`（内核侧，共享命名空间 + 冲突仲裁 + 按 moduleId
注销），由 `AsrTextRepairer` 在每次修复时按需重建 trigger index；对象名走听澜自持的
`NamedObjectIndex`。因此"每个模块注册的 wakeword / 指令词能被识别并修复"不依赖热词文件。

### 2.5 包名不变，靠 Gradle 模块划边界

保持 `com.rheinmetal.tianshu.*` 不变，避免全量 import 变更带来的噪声。代价是包名不再表达模块边界，
`client` / `core` 这类顶层包会横跨多个模块——判断归属看 `src/main` 在哪个 Gradle 模块下。

### 2.6 内置模块也走 provider

ONNX 原生运行时、映迹、思衡与外部模组走同一条装配路径，不存在"内置写死 / 外置走 contributor"的
双路径。双路径是上一版架构里最容易漂移的地方。

`ProtocolModuleIds` 里的 `IR` / `IA` 仍是缩写（识意 / 思衡），按决定不重命名。

## 3. 施工中修掉的结构缺陷

| 缺陷 | 表现 | 处理 |
|---|---|---|
| `TianshuModuleHost` 直接依赖 `ProtocolRuntime` | api 层依赖内核实现 | 改为 `Consumer<String>` 依赖倒置 |
| 广播 topic 无订阅者被记为死信 | 正常降级被当成错误 | 已注册 topic 无订阅者静默完成；**未注册 topic 仍进死信** |
| `tianshu-client` `api` 依赖全部四个功能模组 | 只为读几个 `MODULE_ID` 常量 | 测试改用 `ProtocolModuleIds`，依赖降为只剩 `core` |
| adapter 按键测试实现听澜的 `AsrInputService` | 借传递依赖才编过 | 改实现 api 的 `VoiceInputPort` |
| `VoiceNotificationService` 是纯协议门面却无人取用 | 回响模块注册了但没人 `findService` | 移入内核，删除多余注册 |
| `AXGameEvent*`（持语言 key 的生产者）与 event 层混放 | 破坏 event 层 wording-free 规则 | 移入 `auxilium/producer` |
| `TestLlmSupport` 实现全部四个模块的配置接口 | 放在任何功能模块都会成环 | 移入 `tianshu-testkit` |

前两条里的后四条，是"北辰不得依赖功能模组"这条门禁跑起来之后才暴露的——它们在编译期一直合法。

## 4. 运行时才会暴露的坑

首次真正 `runClient` 时出现的两个问题，静态检查无论如何抓不到：

| 现象 | 根因 | 处理 |
|---|---|---|
| `tianshu` 不在 mod 列表，四个功能模组报 "requires tianshu" | `neoForge.mods` 被写成一个 `tianshu` 块、塞进全部 sourceSet，FML 因此把功能模组的 `neoforge.mods.toml` 也当成 tianshu 的，读到多份同名清单 | 改成「modid → 它的 sourceSet」映射：`tianshu` 只含 adapter + client + core + api，四个功能模组各自独立声明 |
| 修完后 `NoClassDefFoundError: LogSink` | 只声明 `sourceSets.main` 时，api/core/client 的类掉出了 mod 类加载器 | 把「无清单的依赖模块」重新并入 `tianshu` 的 sourceSet 列表 |
| 模组列表里有四个功能模组，设置面板却只有映迹 | 开发运行按 source set 装配，功能模组的 `mods{}` 只挂了 `main`；`@Mod` 入口类在 `neoforgeEntry`，于是模组被列出、构造器却从不执行，注册表为空，没有任何功能模组被装配 | 给每个功能模组的开发声明补上 `sourceSets.neoforgeEntry`；加门禁 `theDevelopmentRunDeclaresEveryEntrySourceSet` 防止再漏 |
| 在设置页关掉织言开关后，左下角一直显示"正在加载" | 设置页保存时直接调 `moduleService.unload()`，它只改服务内部状态，**绕过了模块自己的 `stop()`**，因此没有任何 `stopped` 状态被发布；而 lifecycle 状态**没有过期时间**，内核缓存里那条 `starting` 就永远留着 | 服务新增状态变更回调，模块据它发布 `lifecycleStopped` / `lifecycleFailed`；`prepare()` 里"未启用"也改为发布 `stopped`（禁用不是失败），且不再先发 `starting`；补测试钉住"每次状态变更都有人收到" |

**dev 装配与生产打包是两条不同的路径**：生产 jar 里含入口类，所以这个缺陷只在 `runClient` 出现——
而 `runClient` 恰好是手动验证注册路径的地方，最容易漏。修好之后，开发运行还按**启动位置**区分装配集合
（从根项目全装、从 adapter 只装内核、从某个功能模组只装它与它的硬依赖），细节见
[模块架构](../architecture/模块架构.md) §7.3。

**`neoForge.mods` 的正确语义**：它是「每个 mod 由哪些 sourceSet 组成」的表，**不是**「一个 mod 装了哪些
模块」。判定标准是该模块**有没有自己的 `neoforge.mods.toml`**——有就独立声明，没有就并入所属 mod。

**依赖解析顺序的坑**：`repositories` 里 `fabricmc` 必须排在 `neoforged` 之前。neoforged 镜像在开发
环境会重置连接，而 Gradle 在第一个抛 IO 异常的仓库处就中止解析，不会继续尝试下一个——`fabric-loader`
因此解析失败并拖垮 `runClient`。

## 5. 写门禁时踩的坑

| 坑 | 表现 | 正确做法 |
|---|---|---|
| Groovy 插值字符串是 `GString` 不是 `String` | 拿 `"tianshu_${target}"` 去 `Map.containsKey` / `Set.contains` 恒为 false，门禁误报"缺文件" | 键与比对值显式 `.toString()` |
| 用正则啃 JSON | `[^}]*` 在 `${mod_version}` 的 `}` 处提前截断，块内容只剩前半截 | 用 `JsonSlurper` 解析，占位符在 JSON 字符串里是合法值 |
| `file(...)` 写在 `doLast` 里 | 破坏配置缓存 | 在配置期建好 `File` 集合，`doLast` 只读 |
| `ConfigurableFileCollection` 塞进 `inputs.files` | 任务输入不稳定 | 取 `.files` 后的集合 |
| 并行构建 + 小堆在开发机上 | daemon 直接崩（`mmap` / 页面文件 1455） | `--no-parallel --max-workers=2`；内存紧张时降 `-Xmx` 并关配置缓存 |

门禁里断言源码字符串的那一类（如"装配上下文不得出现 `ProtocolRuntime`"）只能表达结构约束，
真正的行为由 JUnit 架构测试补（见 [模块架构](../architecture/模块架构.md) §11）。

## 7. 映迹拆分：阶段一（端口化）

目标：让「映迹」从北辰里可拆走——先把平台能力变成端口，再搬代码。阶段一结束时，宿主只剩**一个**
`PresenceClientFeature` 入口；阶段二把这个入口也删掉，换成模块在 `TianshuModuleProviderRegistry` 里自注册，
宿主对映迹的代码引用归零。

| 能力 | 端口 | 谁实现 | 备注 |
|---|---|---|---|
| 客户端世界采集 | `ClientGameContextPort`（六方法）+ `GameInteractionContext` / `GameTarget` / `GamePlayerStatus` / `GameInventoryEntry` / `GameEquipment` / `GameEffect` / `GameWorldEnvironment` | `NeoForgeGameContextPort` | 只按需采集：每次请求只读所需分组；空世界降级 |
| 客户端 tick | `TickSignals.TICK`（订阅/退订） | 宿主发布 | runtime 不再有 `tick()`，也就没有每次登录的轮询 |
| 输入门禁 | `RuntimeGates.setInputBlocked` | 映迹写入，宿主只读 | 只在状态变化时写，宿主按键判定不点名任何模块 |
| 世界事件 | `WorldEventPayload` / `WorldEventTypes`（api）、topic `GAME.WORLD_EVENT`、`WorldEventPublisher` | `ProtocolRuntime.publishWorldEvent` | 生产者只产**单次**原始事件；聚合窗口属于消费者 |
| HUD | `HudSurface` / `HudLayer` / `HudHost` / `HudFrameContext` / `HudProgram` / `HudProgramId` / `HudUniformSink` / `HudAnchorEditor` / `HudAnchorView` / `HudAnchorPoint` | `NeoForgeHudSurface`（落笔）、`NeoForgeHudHost`（门控/时钟/熔断）、`HudAnchorEditorScreen`（屏幕） | 表现计算与绘制调用全在映迹；宿主只管像素与渲染状态 |
| 模块配置 | `ModuleConfigStore`（`module.presence`） | `PresenceModuleConfig` | 7 个 HUD 键从 `ClientConfig` 移出，宿主只剩 `debug.enabled` |
| 世界会话 | `WorldSessionListener` 列表 | `PresenceClientRuntime` | client runtime 不认识映迹 |
| 装配 | `TianshuModuleProvider` / `HudLayer` | `PresenceModuleProvider`（阶段二） | 组合根只从 `TianshuModuleProviderRegistry` 取工厂，不点名映迹 |

**HUD 拆法的关键约束**：

- 不暴露 pose 栈/着色器状态。`HudSurface.blit` 自带 rotation/scale/alpha，宿主在内部压栈、设色、弹栈；
  一次渲染异常不会把 GUI 留在坏状态里。
- 程序资产与 uniform 绑定都在模块：`HudProgram` 携带模块自己的 id、参数类型和 binder；宿主只编译声明的
  shader、调用 binder、做失败永久降级与资源重载清缓存，不认识任何 uniform 名。新增/改名 uniform 不需要改
  api 或 adapter，映迹可以在不更新北辰的情况下调整渲染。
- 每帧零分配：映迹侧按值缓存并复用 `PresenceHudShaderParams`；宿主没有固定参数表；文本宽度与贴图解析是
  正负缓存；HUD 关闭时图层只读一个 `volatile boolean` 就返回。
- 异常隔离：图层连续失败 3 帧即摘除并记一条诊断，不让一个元素打断整帧 GUI。
- 位置编辑器留宿主（Screen/widget/鼠标/lang key），但预览必须走映迹的 `HudAnchorView.resolve`，
  否则拖动预览会和真实元素漂移。

**阶段二/三待办**：建 `tianshu-presence` 工程（universal + 两份清单 + 语言分片 + 资源）、把
`client/presence/**`、`client/settings/module/presence/**`、映迹载荷族与采集模型族搬过去、听澜/辅星改硬依赖、
回响/织言改 optional bridge、门禁与矩阵更新、`runClient` 验收。

**阶段二里程碑一（已完成）**：

- `tianshu-presence` 成为第五个 universal 功能模组，包根 `com.rheinmetal.tianshu.function.presence`
  （§2.5 的"包名不变"只适用于旧模块；新模组直接采用门禁约定的 `function.<feature>` 根，避免给门禁加特例）。
- 全部 45 个主源文件、14 个测试、语言分片（50 键）搬入；`module.presence` 配置与 HUD 图层随模块走。
- 宿主不再引用映迹：`ClientPorts` 提供 `gameContext` / `hud` / `debugEnabled`；`PresenceModuleProvider`
  从装配上下文构造运行时，注册模块与设置页；HUD 图层在模块 `register()` 时加入、`stop()` 时移除；
  世界会话由模块生命周期开合（provider 在 `contribute()` 里先开，保证早于任何模块发布启动状态）。
- `TianshuClientRuntime` 的会话监听列表与 `WorldSessionListener` 随 `PresenceClientFeature` 一起删除，
  客户端运行时不再有"特征会话"这个概念。
- 门禁/矩阵：`featureModules` + `runFeatureNames` + `host` 反依赖清单加入 presence；
  `verifyUniversalModuleJars` 直接按 `function.presence` 校验；根项目与 presence 各自的 `runClient` 自动生效。
- 内核 jar 已不含 `function/presence/**`，映迹 jar 自带两份清单与两个入口类（已用 jar 内容核对）。

**阶段二里程碑二（已完成）**：

- 映迹载荷与采集模型搬入 `tianshu-presence`：上下文查询/快照、伙伴标记、交互上下文、世界事件窗口、
  `PresenceContextFactIds`、10 个 `model` 类型与 `PresenceContextGroup`（`function.presence.payload` / `.model` / `.protocol` / `.context`）。
  引用方全部改包：听澜 6 个源文件 + 3 个测试、辅星 9 个源文件 + 9 个测试、适配器（改回 api `GameScreenKind`）。
- 依赖矩阵：听澜 → 映迹、辅星 → 映迹 两条**前置依赖**（`api project(':tianshu-presence')` + 两份清单 required），
  门禁 `verifyFeatureOptionalDependencies` 通过。
- 决策修正（评审批注后二次修正）：`PresenceActivity*`、`PresenceActivityIds`、三个 `PRESENCE_*` topic、
  五个 `PayloadType.PRESENCE_*` 与 `ProtocolCapabilities.PRESENCE_QUERY_CONTEXT`、`ProtocolModuleIds.PRESENCE`
  **全部移出内核**。内核只留机制（`PayloadType.of`、topic 注册表）；映迹在 provider 的 `contribute()` 里自注册
  topic 与载荷类别。回响/织言只报告 HUD 活动，改为 optional 边：`compileOnly` + `bridge` 包 +
  `InstalledMods.isLoaded("tianshu_presence")`；映迹缺席时 bridge 为 NOOP，不发布也不会进死信。
- 顺带清掉两处内核以映迹命名的词汇：模块状态键前缀 `tianshu.presence.` → 中性 `tianshu.runtime.`（各模块语言分片同步），
  HUD shader 资源整体随映迹（`assets/tianshu_presence/shaders/core/**`）：映迹在入口里通过 api
`HudShaderCatalog` 声明 program id 与资源 id，宿主只按声明创建 `ShaderInstance`，自身不再保留任何 shader 文件；
uniform 名与参数布局留在映迹的 `PresenceHudProgram` / `PresenceHudShaderParams`。
- 适配器的屏幕分类器改回宿主词汇：`NeoForgePresenceScreenClassifier` → `NeoForgeGameScreenClassifier`，
  直接返回 api 的 `GameScreenKind`，宿主对映迹的最后一个 import 消失。
- 附带修掉一个既有缺陷：`InstalledMods` 的守卫参数应为**加载器 mod id**（如 `tianshu_echo`），而辅星的两个
  bridge 选择器此前传的是协议模块 id（`module.tts` / `module.ia`），生产环境永远判为未安装；现已改为真实 mod id，
  相关测试同步。

**剩余（阶段三）**：`runClient` 五组启动矩阵实机验收（重点是"只装映迹""不装映迹"与"只装听澜"时加载器行为）、
安装说明与 `EXTERNAL_INTEGRATION_GUIDE` 的依赖说明、文档全面校对。

## 8. 映迹拆分等价性核对（对 74788a8）

`74788a8` 是拆分前最后一个提交。核对要回答的是：拆分后映迹是否仍按原来的方式读游戏、与其它模块通信。

方法分三层，前两层可对任意两个提交重做：

1. **词汇层**：静态比对拆分前后的常量值——topic、capability、载荷名、世界事件类型与字段名、上下文事实 id。
2. **代码层**：把拆分前 101 个映迹相关源文件按类名映射到当前文件，去掉 `package`/`import`/注释并归一已知改名后
   逐字符比对。
3. **行为层**：拆分前的映迹测试全部随模块搬家并保持通过；再新增契约测试，把词汇与采集映射钉死（见下）。

**结果**：

- 词汇：4 个 topic 的值、1 个 capability、5 个载荷名、23 个世界事件类型 + 22 个字段名（其中 3 个字段名
  此前是 AX 侧字面量）、6 个上下文事实 id 全部与拆分前一致；旧 `PresenceWorldEventPayload.TOPIC` 已并由
  `PresenceTopics.WORLD_EVENT` 单一来源。
- 代码：99 个可比对文件中 56 个归一后逐字符相同；43 个有实质变化，集中在四类：所有权搬家
  （topic 自注册、`PresenceModule`/`Installer` 装配）、端口化（采集拆成 `NeoForgeGameContextPort` 读值 +
  `PresenceContextSnapshotAssembler` 映射；HUD/配置/文本走端口）、词表归位（世界事件常量移入 api
  `WorldEventTypes`，映迹载荷保留别名）、测试同步（topic 注册、bridge、加载器 id）。
- 2 个旧文件没有同名后继：`ClientConfigPresenceHudSettings` 的 7 个 HUD 键并入 `module.presence` 配置；
  `NeoForgePresenceHooks` 拆成适配器的事件入口（`NeoForgeClientEvents` / `NeoForgeClientFactWatch` /
  `NeoForgeWorldEventHooks` / `NeoForgeAdvancementEventTracker` / `NeoForgeBossEventWatch`）。

**世界事件路由的变化**：旧版适配器直接调用映迹的 collector；现在是宿主发布单次 `GAME.WORLD_EVENT` →
映迹订阅 → 聚合窗口 → 重发 `PRESENCE.WORLD_EVENT`。窗口、分组、限流仍在映迹，时间戳仍取事件自带的
`occurredAtMillis`；映迹缺席时该 topic 无人订阅，宿主的发布静默完成，不进死信。

**新增守卫**（防止以后再漂移）：

- `PresenceWireContractTest`：钉死 4 个 topic 的名字/载荷/投递策略/限流、5 个载荷名与类绑定、query capability
  描述符和模块 id；这些值就是从 `74788a8` 抄下来的。
- `PresenceContextSnapshotAssemblerTest`：逐字段钉死游戏采集映射、按需读取分组、空世界降级。
- `ProtocolBootstrapFeatureNeutralityTest`：反向钉死"内核启动时没有任何 `PRESENCE.` topic，也没有
  `PRESENCE*` 载荷名"。
- `WorldEventTypesTest`：钉死宿主与消费者共用的世界事件类型/字段字面量（23 + 22 个）。

**已知且可接受的行为差异**：HUD 配置从 `tianshu-client.toml` 的 presence 段改为 `module.presence` 存储，
旧配置值不迁移（首次取默认值）；适配器事实通道 `tianshu:presence_fact` 更名为 `tianshu:game_fact`（双端同版本）。

## 9. 映迹 HUD 浏览器预览（开发工具）

调 HUD 不必每次都 `runClient`。`tianshu-presence/tools/hud-preview/` 是一个不需要服务器的网页，双击 `index.html`
即可切主状态（含正在听）、后台标记、预设、尺寸/位置与伙伴租约，观察图标、状态面板与伙伴标记的变化。映迹的模块设计、
产品活动协议与工具说明统一由 [Presence 文档索引](../function/presence/Presence_文档索引.md) 维护。

- 模型与 shader 由 `HudPreviewAssetExporter` 从真实源码生成（状态参数、布局常量、过渡时长、渲染器颜色/透明度、
  七条状态文案与两份 `.fsh` 原文）。重新生成：
  `.\gradlew.bat :tianshu-presence:exportHudPreviewAssets`；`PresenceHudPreviewAssetTest` 会在页面过期时让 `check` 失败。
- 图标完全由 `.fsh` 绘制：一个 quad，每个预设程序都包含 loading 液体簇、中心点交接、预设图案、聆听扩散环与后台小点；
  `Morph` 是唯一的 loading→球体参数，不再有独立 loading 程序。Java 只选程序、传 uniforms，不再画任何形状。
  程序不可用时图标不绘制，没有 Java 回退层。
- 预设一 / 预设二是两个可选图案，各自一个程序，分别移植自 `libs/ShaderToy/preset1.glsl` 与
  `preset2.glsl`；预设二的 200 步 raymarch 只在该图案被选中时付代价。
- 加载与预设通过中心实心点交接：进入加载时球体先收成点、loading 再从点展开成六点；退出时六点收成点、
  预设从点长成球体。整个过程在同一个预设程序里完成，不再切换 program。
- 预览的 2D 部分只剩示意背景、状态文字和伙伴标记；伙伴环仍按 `PresenceHudShapes` 的自适应密度绘制。
- 不是像素级复刻：字体用浏览器字体（状态面板宽度会差几像素），背景/热键栏/血量是示意画面，伙伴图标是占位图形。
- 深链示例：`index.html?primary=LISTENING&preset=PRESET_TWO&size=64&paused=1&t=1.5`。
