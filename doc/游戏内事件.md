# 游戏内事件

> 三个功能方向之一（[职责边界](职责边界.md) §2 的第 6 条）：游戏里发生的事怎么被看见、汇成一条流、交给模块消费。
> 模组：`tianshu-api`（`WorldEventPayload`、`WorldEventTypes`、`WorldEventPublisher`）+ 适配层（两端采撷、`WorldEventHooks`）+ `tianshu-core`（主题 `GAME.WORLD_EVENT` 的投递）。
> 它和前两个方向形状不同：玩家辅助与实体是"**调用**能力"，这一条是"**观察**发生了什么"——不产生工具，只产生事件。

## 1. 这个方向是什么

一条**单向的观察流**：游戏里发生一件事（解锁成就、聊天、合成、杀死怪物、摔伤、天气变了），平台把它变成一条
`WorldEventPayload`，模块订阅后决定要不要说话、记下来还是忽略。

三条边界决定了它长这样：

- **事件不是工具**：没有参数校验、没有调用方身份、没有档位。它只描述"发生了"，不描述"谁请求"；
- **一次发生就是一条**：不窗口、不聚合、不限流、不重发——那些是消费者的事，放进基座就会变成"基座替模块决定怎么说";
- **两端同时生产**：客户端能看见的（成就、聊天、Boss 条）和只有服务端能看见的（合成、击杀、交易）走同一个
  入口、同一种形状，消费者不需要知道一件事是在哪一侧被看到的。

## 2. 三段：产生、汇流、消费

```
客户端钩子 ─┐
            ├→ WorldEventHooks.publish ─→ WorldEventPublisher ─→ 协议中心主题 GAME.WORLD_EVENT ─→ 模块订阅者
服务端组件 ─┘        （唯一入口）              （宿主按会话绑定）
```

| 段 | 谁负责 | 代码 |
|---|---|---|
| 产生 | 适配层：客户端钩子 + 可选服务端组件 | `ClientEvents`、`*ClientFactWatch`、`GameFactCollector` |
| 汇流 | 适配层的单一入口 → 宿主绑定的发布器 | `WorldEventHooks`、`WorldEventPublisher` |
| 消费 | 模块 | 协议中心主题 `WorldEventPayload.TOPIC` = `GAME.WORLD_EVENT` |

关键一点：`WorldEventHooks` 是**唯一**调用宿主发布器的地方。生产者不认识模块，模块也看不出事件是哪一侧产生的。

## 3. 客户端自己看得见的

这些事件由客户端钩子产生，不需要服务端参与：

| 事件 | 触发方式 | 哪一侧有 |
|---|---|---|
| `advancement_unlocked` | mixin 抓 `ClientboundUpdateAdvancementsPacket`，只报**进度里新解锁**的那几条（进服不是"万事解锁"） | 两个加载器 |
| `chat_message` | 聊天行，携带发送者 id、名字与正文 | 两个加载器 |
| `dimension_changed` | 维度切换（`*ClientFactWatch`） | 两个加载器 |
| `container_open` | 打开容器（`*ClientFactWatch`） | 两个加载器 |
| `boss_engage` | Boss 条出现（`NeoForgeBossEventWatch`） | **仅 NeoForge** |

## 4. 只有服务端看得见的

可选的服务端组件（`GameFactCollector` / `FabricGameFactCollector`）把权威侧才能确定的事变成事实，发给**当事人**：

`item_crafted`、`mob_killed`、`fishing_catch`、`tamed`、`block_broken`、`block_placed`、`container_open`、
`mount`、`dismount`、`trade`、`damage_taken`、`fall_damage`、`sleep`、`respawn`、`player_death`、
`weather_change`、`eat_food`、`rare_item`、`exp_level`、`item_pickup`、`friend_join`、`friend_leave`。

口径写死在实现里：

- **只发给当事人**：别人的容器、背包、事件不发，客户端也没有用处；
- **不重复客户端已经看得见的**：成就与聊天不在这里再报一遍；
- **没有"要不要转发"的开关**：这个组件装没装，本身就是开关。

两个加载器在这张清单上不一样，差别不是“谁没写完”，而是**上游给不给事件**——见 [§9](#9-每个版本与加载器收不到什么)。

## 5. 传输与限额

服务端事实按 tick 汇总成一个批次（一次突发只花一个包，而不是每个事实一个包），走 `GameFactBatchPacket`
——它和工具通道同一个注册器、同一个协议版本，客户端没装时可退化（可选通道）。

批量与解码都有上限，而且**先验后分配**：`GameFactLimits` 在读取任何计数之前校验包字节数与事实数，
单个事实的键数不超过 64、文本不超过 32767（等于 `writeUtf` 能写出的最大值，所以本构建写的数据永远不会被它拒掉）。

这条来自一次真实教训：解码器曾把线上的值个数直接当成 map 初始容量，于是六个字节的报文就能让客户端申请
一张几 GB 的表并死在 `OutOfMemoryError` 上——那是 `Error`，任何诊断层都接不住。客户端连的是自己不能选的服务端，
所以计数必须先验。

## 6. 词表

`WorldEventTypes` 是平台与模块之间的契约，与用哪个 payload 承载无关：

- **事件类型**：24 个常量，从 `advancement_unlocked` 到 `chat_message`（见 [§3](#3-客户端自己看得见的)、[§4](#4-只有服务端看得见的)）；
- **字段名**：`itemId`、`itemName`、`count`、`entityId`、`entityName`、`deathMessage`、`dimension`、
  `dimensionName`、`blockId`、`blockName`、`effectName`、`amount`、`level`、`playerName`、`senderId`、
  `senderName`、`text`、`advancementId`、`title`、`description`、`type`、`iconItemId`。

空值在构造时被丢掉，所以"这个字段没有"和"这个字段是空串"能区分——消费者据此决定要不要补默认文案。

## 7. 约定

- **一条事件 = 一次发生**。聚合窗口、去重、限流、本地化都归消费者；基座只保证"发生过的都在这里、顺序是产生顺序"；
- **没有订阅者就不构建**。`WorldEventPublisher.hasSubscribers()` 让生产者跳过 payload 与信封的构造，没人读的流不花钱；
- **绑定按会话**。发布器由客户端引导按会话绑定，会话结束就清掉；会话没了之后才到的事件直接被丢弃，不会被投进
  一个已经死掉的协议。清除时按实例比对，晚到的清除不会解绑更新的会话；
- **换世界重置基线**。新世界从全新的进度基线开始，否则一次重进就等于把所有成就重报一遍。

## 8. 模块怎么接

```java
// 模块启动时订阅主题；收到的就是平台观察到的原始事件。
context.subscribe(WorldEventPayload.TOPIC, envelope -> {
    WorldEventPayload event = /* envelope 里的事件 */;
    if (WorldEventTypes.EVENT_CHAT_MESSAGE.equals(event.eventType())) {
        // 自己决定要不要说话、要不要记下来
    }
});
```

现有的两个消费者：

- `tianshu-dubhe`：把世界事件映射成记忆条目（`DubhePresenceWorldEventMapper`），成就、聊天、合成各有自己的措辞；
- `tianshu-presence`：把事件交给它自己的采集器（`eventCollector.setWorldEventSink(...)`）。

模块要产生事件而不是消费事件时，不需要经过这条流——那是协议中心的一般主题（见 [协议中心](协议中心.md) §3）。
这条流只承载"游戏里发生的事"。

## 9. 每个版本与加载器收不到什么

**这张表只列有差异的**。没列到的事件，在下面这两行覆盖的范围内都是两端可直接收到的：
客户端事件（`advancement_unlocked`、`chat_message`、`dimension_changed`、`container_open`）与服务端组件已经
接上的事实（`mob_killed`、`block_broken`、`block_placed`、`mount`、`dismount`、`damage_taken`、`fall_damage`、
`sleep`、`respawn`、`player_death`、`weather_change`、`eat_food`、`rare_item`、`exp_level`、`item_pickup`、
`friend_join`、`friend_leave`）。

性质只有三种，写清楚是为了避免把“上游没有”误读成“我们没写”：

| 记号 | 含义 |
|---|---|
| ✅ | 平台有事件，直接监听 |
| ◐ | **平台没有这个事件**，只能自己 mixin 或轮询去取；目前没做，所以收不到 |
| 组件 | 只有装了可选服务端组件才有；客户端单独看不见 |

### 9.1 MC 1.21.x

| 事件 | NeoForge | Fabric | 说明 |
|---|---|---|---|
| `item_crafted` | ✅ | ◐ | Fabric API 没有合成完成事件；要拿只能 mixin 结果槽 |
| `fishing_catch` | ✅ | ◐ | Fabric API 没有钓鱼完成事件 |
| `tamed` | ✅ | ◐ | Fabric API 没有驯服事件 |
| `trade` | ✅ | ◐ | Fabric API 没有与村民交易事件 |
| `effect_gained` / `effect_expired` | ✅ | ◐ | Fabric API 没有状态效果增删事件 |
| `boss_engage` | ✅ | ◐ | Fabric 没有 Boss 条事件；客户端其实可每 tick 读老板条列表，无需 mixin，只是还没做 |
| §4 的其余事实 | 组件 | 组件 | 两端都靠可选服务端组件 |
| `advancement_unlocked` / `chat_message` / `dimension_changed` / `container_open` | ✅ | ✅ | 客户端侧，两端同形 |

单机（集成服）另有一条：**§4 的全部事实都收不到**，因为采集器属于服务端组件，单机没有那个组件在跑。

### 9.2 其它 MC 版本

待定。加一个版本就加一张 `9.x` 的表，并先把“上一版能收到的、这一版收不到的”逐条列出来再动手——版本之间的
差距往往就是几个事件改名或换位置，先记下来比事后查日志便宜。

维护规则：

- **加版本或加载器时先加表**，哪怕整张表都是 ✅；
- **补上一条 ◐ 之后删掉那一行**；表与代码不一致时以代码为准，但表要当场改；
- 判定口径是**看上游有没有事件**（NeoForge 的 `*Event`、Fabric API 的回调），不是看我们的实现里有没有写监听。
