## 2. 架构速览（审阅时的理解基线）

```
玩家输入（键 / 文字）
      ↓  InputSignals（静态通道总线，平台 publish，模块 subscribe）
TianshuCoreManager ── ProtocolRuntime（信封路由 / broker / executor lane）
      ↓                          ↑
TianshuModuleHost（register→prepare→start，失败隔离）   Feature 模块（provider 自注册）
      ↓
ClientPorts（scheduler / ui / texts / filePicker / hud / gameContext / config）
      ↓
adapter（唯一碰 Minecraft 的一层）
```

三条设计承诺，我逐条核过：

1. **宿主不认识任何功能模组** —— 基本成立。装配只走 `TianshuModuleProvider`，`createModuleProviders()` 里只列内置 ONNX 运行时；设置页由模块 `contribute` 进来后自然出现。
2. **功能模组缺席 = 零代价** —— 成立。HUD 层为空时 `render()` 立刻 return；没有 provider 就没有 installer；设置页无该页。
3. **模块内部与平台无关** —— 成立且被门禁强制（`verifyNoPlatformImport`）。宿主自身也遵守：非 adapter 模块零 `net.minecraft.*`。

### 3.3 完备性小结

宿主自身的机制是完整的——凡是"宿主该提供的东西"都能找到落点。不完整的地方几乎都落在**产品入口**（怎么进来、怎么保存、怎么退），而不是**运行时**。这也解释了为什么它跑起来很稳，但用起来会觉得"少几步"。

## 4. 健壮性

### 4.1 做得好的地方（有据可查）

- **主线程纪律**：生命周期在独立 daemon 线程（`CoreLifecycleCommandQueue:13-17`），下载/模型加载在 lane 上，tick 路径里没有 `Thread.sleep`/`Files.`/`.join()`——而且有测试专门断言这一点（`NeoForgeMainThreadBoundaryTest:14-29`）。
- **失败隔离分层**：optional 模块失败 → 记状态 + `warn` + 继续；required 失败 → 抛 `ModuleLifecycleException` 由协调器收口并回滚（`shutdownModules` 双层 `finally` 保证每一级都跑到）。
- **跨会话防串台**：`TianshuClientRuntime` 用 `generation` 丢弃过期回调；`NeoForgeWorldEventHooks` 用 `compareAndSet` 防止旧会话的 `clear` 解绑新会话的 publisher（`:36-41`）。
- **资源清理由所有权栈统一管理**：`NeoForgeClientSession` 把 12 个清理动作压栈、逆序执行、异常聚合。
- **网络与文件传输**：超时、重试、退避、`Range`/`If-Range` 续传、长度校验、取消可中断（`ModelDownloadHttpClient`），并且**校验候选源协议白名单**（`:517-530`）。
- **Mixin 面极小**：只有 1 个 `client` mixin，`TAIL` 注入。我核对了 `PacketUtils.ensureRunningOnSameThread` 的实现——`TAIL` 不会在 netty 线程执行（异常会跳过 RETURN），所以这个注入点是**主线程、且在 `advancements.update()` 之后**，正确。

### 4.2 缺陷清单

> P1 共 6 条（按危害排序：崩溃/数据错 > 长期不回收 > 静默失效），P2 共 15 条。
>
> **本轮状态**（第一批只改错误路径与内部实现，第二批按批注补了一项交互；逐条见 §10）：
> - 已修复：P1-1、P1-2、P1-3、P1-4（批注批准）、P1-5、P1-6、P2-1、P2-2、P2-5、P2-6、P2-9、P2-11、P2-14；P2-7 修掉了线程安全，未动"部分生效"的产品语义。
> - 不改（设计如此，测试钉住）：P2-12 —— "模块启动失败"的状态要在会话拆除后仍然可见（`TianshuCoreManagerLifecycleTest#requiredPrepareFailureRemainsVisibleAfterCleanup`），清掉它反而是回归。
> - 未修：P2-3（静态门清理）、P2-4（服务端事实合并）、P2-8（玩家可见性与白名单）、P2-10（`SERVER_PACKET` 授权位）、P2-13（文件选择器已有取消路径，待实机确认）、P2-15（重复关闭与末行日志）。

#### P1-1 信封生命周期库只增不减，唯一清理方法是死代码

- 证据：`EnvelopeLifecycleStore.java:14-18`（5 个 `ConcurrentHashMap`，无上限）、`:20-27`（每个信封写 4 处）、`:78`（`cleanupTerminalTraces`）。
- 全仓 grep：`cleanupTerminalTraces` **只有定义，没有任何调用点**（main 与 test 都没有）。
- 影响：每个信封 = `TianshuEnvelope` + 1 条 `statuses` + 3–6 条 `EnvelopeTransition`（`CopyOnWriteArrayList`）+ 1 条 trace 索引。世界事件是"每次一个信封"（`ProtocolRuntime.publishWorldEvent:385-397`），聊一句、解锁一个进度、Boss 条出现各一条。**跑得越久越大，且永不回收**。
- 修法：在 `ProtocolRuntime` 里挂一个低频（如每 30 s 或每 N 次 submit）的 `cleanupTerminalTraces(now - 10min, 512)`；或者把清理内联进 `accept()` 的容量检查。

#### P1-2 麦克风硬件门的开/关竞态（实测可见）

- 证据：`AudioManager.ensureHardwareRunning:124-190` 用 `isHardwareRunning` CAS 做门，但 `releaseCaptureHardware:648-668` 会无条件把它设回 false 并关线；`startTtsPlayback`/`stopRecording` 等入口不校验线程。
- 实测日志（`tianshu-diagnostics.log`）同一毫秒内出现：`audio.microphone.opened` ×2 → `audio.microphone.worker_failed`（`LineUnavailableException`）→ `worker_started` → `worker_stopped`。两次 open 重叠，其中一次抢不到设备。
- 影响：用户看到 ERROR；语音输入在"进出世界很快"或"切麦克风"时偶发失败。
- 修法：门改成"打开中/已打开/已关闭"三态 + 单一 worker 状态机；`release` 只做"请求关闭"，由 worker 自己收尾；`stopRecording` 里的 `Thread.sleep(60)`（`:206`）换成对 `read()` 线程的显式完成信号。

#### P1-3 配置落盘失败被吞，UI 会谎报成功

- 证据：`PropertyModuleConfigStore.save:123-141` —— `catch (IOException) { logs.error(...) }`，方法返回 void；`SettingsSaveTransaction.commit:27-46` 依赖 `persist.run()` 抛异常来触发回滚，而它永远不会抛。
- 影响：磁盘满/权限/被杀软锁住时，玩家看到"已保存"，重启后设置回到旧值；`MutableSettingsValue.original` 已被 `accept()` 推进，内存与磁盘不一致。
- 修法：`save()` 失败时抛 `UncheckedIOException`，让事务回滚并把失败原因带回 UI；顺手把 `.tmp` 写入加 `ATOMIC_MOVE` 尝试、失败回退。

#### P1-4 设置页 Esc 静默丢草稿

- 证据：`TianshuSettingsScreen.onClose:494-496` 无 dirty 检查；`removed():499-502` 关闭会话。
- 影响：玩家改了十几项、按 Esc 想"先出去看看"，回来全没了，且没有任何提示。
- 修法：`dirty()` 为真时弹出确认（保存/放弃/取消），或 Esc 时自动保存并把结果落到状态栏。

#### P1-5 平台信号总线没有异常隔离：一个模块抛异常 = 客户端崩溃

- 证据：`InputSignals.publish:89-101`、`TickSignals.publish:48-59` —— 遍历订阅者直接 `handler.accept(...)`，**没有 try/catch、没有日志**。
- 触发：任一模块的订阅回调抛 RuntimeException（空指针、状态机非法迁移、已 `stop()` 但未退订）。
- 影响：`TickSignals.publish` 在 `NeoForgeClientEvents.onClientTick:96-97` 调用、`InputSignals.publish` 在按键/文字提交路径调用 —— 异常冒到 NeoForge 事件总线，以 "Exception in event handler" 崩溃报告结束；同一通道后续订阅者收不到这条信号（语音键/对话直到重启都失灵）。
- 对比：`NeoForgeHudHost.onLayerFailure:115-123` 对 HUD 层做了"连续 3 次失败即摘层"的隔离。同一套产品哲学，在两条路径上不一致。
- 修法：publish 内逐 handler `try/catch(RuntimeException)` + 计数 + 诊断，与 HUD 层同一策略；这同时覆盖"模块 stop 失败后残留订阅"（P2-3）。

#### P1-6 服务端事实包的 `size` 字段未校验，一条 6 字节包可 OOM 客户端

- 证据：`GameFactPacket.decode:65-75` —— `int size = buffer.readVarInt(); new LinkedHashMap<>(Math.max(0, size))`，`size` 完全由对端决定。
- 影响：客户端会连任意服务器（含被劫持/版本错配的服务端）。发送 `size = 1e9` 即在**解码阶段**预分配巨大 table → `OutOfMemoryError`，而 `Error` 不经过诊断层，玩家只看到崩溃。
- 修法：校验 `0 <= size <= 64`（当前事实最多 4 个 key）并先核对剩余可读字节；key/value 长度同样加上限（服务端 `writeUtf` 也有 32767 上限，物品名/死亡消息理论上可触发）。

#### P2-1 关服在主线程 `join()`，且没有任何超时

- 证据：`TianshuClientRuntime.shutdown:116-134`（`core.destroy().join()`，无超时）+ `ClientDiagnosticWriter.closeAndFlush:60-70`（`terminated.await(5, SECONDS)`）+ `AudioManager.shutdown:688-701`（`awaitTermination(500ms)`）。调用链是 `GameShuttingDownEvent` → `bootstrap.shutdown()`，全在主线程。
- 影响：退出游戏时界面冻结；确定项是 5 s + 0.5 s，而 `destroy().join()` 本身**没有上限**——若某个模块的 `destroy()` 卡住（例如原生库卸载），游戏会永久挂在这里，只能强杀。
- 修法：`destroy()` 加 `orTimeout(2, SECONDS)`；诊断 flush 的时间预算降到 1 s 并允许丢尾部记录。

#### P2-2 broker 的 `running` 表在"提交被拒"时会泄漏一格并发额度

- 证据：`AbstractQueueBroker.drain:57-71` —— 先 `running.put(...)`，再 `executorManager.submit(...)`；`ProtocolExecutorManager.submit:83-89` 在 TaskGroup 队列满时把 handle 置 `REJECTED` 并返回，**没有任何回调**。于是该条目永远留在 `running` 里，`maxConcurrency` 被永久占用一格。
- 触发条件：模块声明 `maxConcurrency > queueCapacity`（两者都来自 `ModuleDescriptor`，可自由组合）；或 lane 池 `AbortPolicy` 拒绝。
- 影响：极端负载下该 broker 的并发额度被逐步吃掉，最终整条链路停摆（不报错、只变慢）。
- 修法：`submit` 返回 `REJECTED` 时由 broker 移除 `running` 条目并转死信；或在 `ProtocolExecutorManager` 提供 `onRejected` 回调。

#### P2-3 静态输入门可能跨会话残留

- 证据：`RuntimeGates.java:16`（`static volatile boolean inputBlocked`）、`:29`（`clear()`），全仓**无 `clear()` 调用**；写方是映迹（`PresenceClientRuntime:168`）。
- 影响：若在一个"loading"状态下退出世界，`inputBlocked` 保持 true；下一局直到映迹再次上报才恢复。不装映迹时永远为 false（安全）。
- 修法：`NeoForgeClientEvents.onWorldLogout` 里调 `RuntimeGates.clear()`。

#### P2-4 世界事件在服务端"每个事实一个包"

- 证据：`GameFactCollector.send:249-261`，15 个监听器各自直发；`onPlayerJoin/Leave` 还对每个其他玩家各发一个（`132-137`）。
- 影响：连续挖掘/放置可到每秒数个包；多人服加入/离开是 O(N²) 条包。单个包很小，不致命，但没有合并窗口。
- 修法：按玩家做 100–200 ms 的合并（同 factId 计数），或对 `onPlayerJoin/Leave` 只发一次带名单的包。

#### P2-5 诊断写入每行一次 `Files.size()` + 一次 `flush()`

- 证据：`ClientDiagnosticWriter.run:92-100`。
- 影响：后台线程，不影响帧；轮转判断是每条一次 stat 系统调用。DEBUG 全开时（映迹会发播放指标）写放大明显。
- 修法：累计字节计数 + 定时 flush。

#### P2-6 `AudioManager` 的录音缓冲跨线程无同步

- 证据：`audioBuffer` 由音频线程写（`:163`），由 `stopRecording()` 在另一个线程读并 `toByteArray()`（`:209-210`），`ByteArrayOutputStream` 非线程安全；中间只靠 `Thread.sleep(60)` 祈祷写入已停。
- 影响：偶发读到半截/扩容中间态（`ByteArrayOutputStream` 扩容是数组替换，读到旧引用一般无害，但 `count` 与数组可能不一致）。
- 修法：`read()` 循环里写到一个带锁的双缓冲；`stopRecording` 只做"换缓冲 + 取走"。

#### P2-7 设置会话表非线程安全，且多模块保存"部分生效"

- 证据：`SettingsSessionRegistry:11`（裸 `ArrayList`）、`:26-36`（模块生命周期线程 `registerOrReplace`）、`:72-103`（渲染线程 `saveAll()/dirty()` 遍历）；`saveAll:90-98` 逐个落盘，第 N 个失败时前 N-1 个已持久化且 `dirty` 已清，却返回整体失败。
- 影响：并发注册/遍历可抛 `ConcurrentModificationException`（从按钮回调崩出去）；部分保存后界面说"失败"，玩家重进发现半数设置已改。
- 修法：`CopyOnWriteArrayList`；`saveAll` 返回"部分成功"并列出失败模块。

#### P2-8 诊断写入一次 IO 失败即永久关闭，且玩家看不到任何进度/失败

- 证据：`ClientDiagnosticWriter.run:102-105` —— `catch (Exception) { accepting.set(false); }`（无日志、无恢复）；`ClientDiagnosticPolicy:13-19,27-30` 只放行 5 个 moduleId 且要求 `isDebugEnabled()`；`ClientDiagnosticProgress:17-39` 按功能事件码 switch。
- 影响：① Windows 上日志文件被 Notepad/杀软占用 → 本次会话诊断全灭且无提示；② 默认配置下玩家在聊天栏**看不到任何进度**，映迹的事件连白名单都不在 → "装了但没反应"无法自证。
- 修法：失败退避重开 + 阈值后备 `System.err`；玩家可见通道路由不该依赖 debug 开关（见 §3.2 G10）。

#### P2-9 设置子屏用 `setScreen` 替换父屏，返回后草稿与保存路径都断了

- 证据：`TianshuSettingsScreen.removed:499-502` 无条件 `settingsSessions().close()`；`HudAnchorEditorScreen`（`NeoForgeClientBootstrap:145-148`）与 `NeoForgeClientKeyBindings.openRebindScreen:22` 都用 `Minecraft.setScreen(...)`。我已核对 1.21.1 原版 `Minecraft.setScreen`：**旧屏 `old.removed()` 会被调用**（`if (old != null && guiScreen != old) old.removed();`）。
- 后果：从设置页进锚点编辑/改键屏 → 会话被 `close()` 清空 → 返回时 `init()` 只重建控件，会话不会重建（会话在 `create()` 时由各模块 `contribute` 注册，如 `PresenceSettingsRegistrySource:53-54`）→ `saveAll()` 找不到 session，此前的拖拽/改键草稿无法落盘。
- 反差：同一份代码里的 `SettingsLayerHost` 走 `ClientHooks.pushGuiLayer`（`NeoForgeClientBootstrap:379-388`），明确保留了下层页面与草稿 —— 两条子屏通道，一条保状态、一条毁状态。
- 修法：子屏统一走 GUI layer 栈；或 `TianshuSettingsScreen` 在 `init()` 时重建会话并把草稿迁回（前者更干净，与已有的 layer 机制一致）。

#### P2-10 `SERVER_PACKET` broker 的授权位永远是 false

- 证据：`ServerPacketBroker:7,13,19` —— `serverAuthorized` 默认 false，`setServerAuthorized` **全仓无调用者**，而 `BrokerRegistry:52` 会为声明该类型的能力创建它。
- 影响：任何将来声明 `BrokerType.SERVER_PACKET` 的能力，其信封 100% 进 `PERMISSION_DENIED`。这是一个"存在但不可达"的公开状态位，等于给扩展者埋了一个必踩的坑。
- 修法：要么在装配期显式授权，要么删掉该 broker 类型（当前无使用者）。

#### P2-11 执行器关闭不等在途任务；`Error` 不落句柄

- 证据：`ProtocolExecutorManager.close:311-326`（只 `shutdownNow()`，无 `awaitTermination`）；`runManaged:141-165` 只 `catch (Exception)`。
- 影响：`destroy()` 返回后仍有任务在跑，可能触碰已释放的 ONNX session/音频设备（退出期偶发崩溃的典型形态）；`NoClassDefFoundError`/`OutOfMemoryError`/native `Error` 会让 `ProtocolTaskHandle` 永久停在 RUNNING，`isDone()` 永远 false。
- 修法：`close()` 加 `awaitTermination(2s)`；`runManaged` 补 `catch (Throwable)` 并把失败落进句柄后重新抛出 `Error`。

#### P2-12 会话重建后模块状态残留

- 证据：`TianshuModuleHost.clearActiveInstallations:159-164` 清了 4 个 list，**没清 `moduleStatuses`**（`clear()` 会清，但生产代码只调前者）。
- 影响：refresh/重进世界后，已移除或已失败的模块仍出现在 `status()` 与设置页状态里，直到下一次全量装配。
- 修法：`clearActiveInstallations()` 一并清 `moduleStatuses`，或在 `stopSession` 末尾清。

#### P2-13 文件选择器的模态对话框可能拖住进程退出

- 证据：`NeoForgeClientFilePicker:41-59` —— `close()` 只 `pending.cancel(false)`；`showOpenDialog(null)` 进入模态循环后 `cancelSelection` 无效，AWT EDT 非守护。
- 影响：玩家在 TTS 音色导入对话框开着时退出游戏，进程因这个（可能被游戏窗口遮住的）对话框而不退出。
- 修法：给 chooser 一个 owner（`Minecraft` 窗口）并把对话框创建放到可取消的 worker；退出路径 `dispose()`。

#### P2-14 配置读取对非法转义未设防

- 证据：`PropertyModuleConfigStore.loadOnce:143-156` —— `Properties.load` 对非法 `\uXXXX` 抛的是 `IllegalArgumentException`（不是 `IOException`），未被捕获；且 `loaded = true` 在读之前就已置位。
- 影响：玩家手改配置时打错一个转义 → `getString` 在模块 `prepare()` 里抛 `IllegalArgumentException`，该模块启动失败；若半读后又被 `save()`，截断内容会覆盖原文件（P1-3 的同源问题）。
- 修法：捕获 `IllegalArgumentException`，把坏文件另存 `.corrupt` 并回退默认值；`loaded` 只在读成功后置位。

#### P2-15 关服路径重复关闭与末行日志丢失

- 证据：`TianshuClientRuntime.shutdown:125-133` 与 `NeoForgeClientBootstrap` 的 `Ownership` 都注册了 `audioManager::shutdown` / `diagnosticRouter::close`；`shutdown()` 先 `session.close()` 再 `info("shutdown_completed")`（`NeoForgeClientBootstrap:328-345`）。
- 影响：靠 `release()` 顺序才没有双重关闭；`shutdown_completed` 永远写不进去（实测日志最后一条是 `shutdown_starting`），排障时看不到"是否正常收尾"。
- 修法：把"记录收尾"放在关闭诊断之前，或给 router 一个"final flush" 通道。

#### P3 其余（记录，不阻塞）

- `NeoForgeBossEventWatch` 的 `REPORTED` 静态 `LinkedHashSet` 跨会话累积（量级小）。
- `TianshuRuntimePorts.register` 在 `bootstrap.start()` 里注册了 `WorldFactsSource`/`NamedObjectDictionary`，但 `clearSessionReferences()` 不注销（只在测试 `clear()`）；重复 `start()` 会覆盖，不泄漏旧对象引用之外的东西。
- `TextDialogueScreen`、`HudAnchorEditorScreen` 的 `onClose` 均为 `setScreen(null)`，没有"返回上一层"的语义（从暂停屏进来时，退出后回到游戏而不是暂停屏）。

### 4.4 审阅中排除的两个怀疑（供下一位审阅者省时间）

1. **"成就 mixin 跑在 Netty 线程"——不成立。** 我读了 1.21.1 的 `PacketUtils.ensureRunningOnSameThread`：非主线程时它会 `executeIfPossible` 后**抛 `RunningOnDifferentThreadException`**，方法以异常退出，`@At("TAIL")` 的注入点（最后一个 RETURN）不会执行。因此 `NeoForgeAdvancementEventTracker.collect` 只在主线程、且在 `advancements.update(packet)` 之后运行；`completedAdvancementIds` 不存在跨线程写。**这个注入点是正确的**，不必改。
2. **"`Properties` 中文会乱码"——不成立。** `Properties.store/load` 用 ISO-8859-1 + `\uXXXX` 转义，中文往返正确。诊断日志里的中文乱码是**控制台按 GBK 读取 UTF-8 文件**造成的显示问题，不是落盘问题。


"崩溃"这一类风险基本被处理掉了：所有入口都有 try/catch 分层、失败有状态、有诊断、有降级。剩下的风险都属于**"不崩但会慢慢坏"**——内存单调增长、失败被吞、竞态偶发。这三类恰好是单元测试最难覆盖的，也和"只经过编译与单测、没跑长会话"的现状吻合。

## 5. 可扩展性

### 5.1 扩展路径的实测成本

| 加一个 topic | `context.protocol().registerTopic(...)`（映迹就是这么做的） | 零改动 | ✅ |
| 加一个设置页 | 模块 provider 里 `addSettings(page)` | 低 | ✅ |
| 加一项设置 | 模块自己的 `Panel` + `ModuleConfigStore` | 低 | ✅ |

### 5.2 内核词汇里仍焊着四个功能模组

这是**与文档冲突最明显的一处**，也是我这次审阅最看重的可扩展性问题。

- `PayloadType.java:28-55` 注册了 30 个常量，其中 **25 个是具体功能模组**的词汇：`ASR_*`（2）、`IR_RESULT`（1）、`LLM_*`（8）、`TTS_*`（5）、`DIALOGUE_*`（8）、`AX_WORLD_EVENT`（1）；只有 `NONE` / `TEXT` / `CANCEL` / `MODULE_STATUS` / `CUSTOM` 是内核自己的。
- `ProtocolBootstrap.registerTopics:38-49` 为听澜/织言/回响登记了 **9 个 topic**（`INPUT.ASR_*`、`IR.RESULT`、`LLM.STATUS`、`TTS.*`、`DIALOGUE.SESSION_EVENTS`）。
- 同一文件 `:50-51` 的注释写着"Feature topics are not registered here… the kernel's table is platform vocabulary only"——**注释与上方 10 行代码互相矛盾**；映迹确实做到了自注册（`PresenceProtocolAdapter.registerOwnedTopics`），但另外四个没做。

后果：
1. 删掉/改名任一功能模组，必须改 `api`（冻结契约 §10 里的 `PayloadType`）——"装谁是谁"在最底层不成立；
2. 新增一个模组时，读者会以为"载荷要进 api"，与 §5.1 的规则相反；
3. `ProtocolCapabilities` 同理（能力名也在 api）。

修法（按代价排序）：
- 短期：把注释改成事实（"四个既有功能的词汇仍留在内核，映迹已迁出"），避免"文档说 A 代码做 B"。
- 中期：把这 9 个 topic 的注册搬到各自模块的 `provider.contribute()`（映迹已是范本），`ProtocolBootstrap` 只留 `SYSTEM.RUNTIME_INTERRUPT`、`MODULE.STATUS`、`GAME.WORLD_EVENT`。
- 长期：`PayloadType` 的 30 个常量降级为"内置名字的便捷常量"，实际路由只认名字——这已经是现在的实现（`equals` 比名字），改起来主要是删常量。

### 5.4 抽象是否过度

设置子系统：**82 个文件 / 5,281 行，占宿主全部主代码的 28%**。分层是：
`ModuleSettingsPanel`（DSL 接口，每个方法 3 个重载：`id` / `+enabled` / `+enabled+visible`）→ `ModuleSettingsPanelModel`（596 行 builder + 内部 Group 类）→ `SettingsTemplateModel`（sealed 记录）→ `ModuleSettingsRenderer`（接口）→ `VanillaModuleSettingsRenderer`（776 行）+ `SettingsLayerElement` 一套并行的 layer 模型 → 布局引擎（`SettingsLayout`/`SettingsViewport`/`SettingsScrollRegion`/`SettingsDecoration`）。

- **合理的部分**：模块要能用声明式方式产出设置页，且宿主不认识具体控件——这条确实需要一层模型。
- **过度的部分**：(a) 每个入口 3 个重载，实际调用点几乎都只用最简单的那个；(b) `Panel` 与 `Template` 两套近乎同构的类型（`ToggleTemplate`/`ToggleEntry`/`ToggleGroup`/`ToggleGroupModel`）——一次"数据类爆炸"；(c) `SettingsLayer*` 是第二套独立 UI 栈，与主设置页不共享渲染器。
- **判断**：不是"为抽象而抽象"，而是把内部 DSL 当成了对外 API 来设计。可扩展性收益真实存在（加设置项确实只碰模块），但阅读成本和维护成本也真实存在——改动一个控件样式要穿过 4 层。同类问题还有两处更小的：`ModuleSettingsRenderer`/`ModuleSettingsRendererProvider`/`VanillaModuleSettingsRendererProvider` 是**只有一个实现**的三层接口（且 `TianshuSettingsModule:20,27` 直接持有具体类）；`SettingsLayer*` 那套独立弹层栈近 900 行，唯一消费者是织言的模型选择器。建议在下次动它时做一次收敛（`Panel` 与 `Template` 合并、删单实现 Provider），而不是继续加第 4 个重载。

协议子系统：99 个文件 / 3,141 行，大量是 5–20 行的 record/enum（`Priority`、`DeliveryPolicy`、`AckPolicy`…）。这属于"用类型系统表达策略"，可读性好，不算过度。

### 5.5 架构门禁是"源码文本断言"

- 例：`NeoForgeMainThreadBoundaryTest:14-29` 直接 `Files.readString(...)` 后断言 `!tick.contains("Thread.sleep")`；`ModuleAssemblyRuntimeBoundaryTest` 全文搜索 `"ProtocolRuntime"` 是否出现。
- 优点：零依赖、跨模块、能钉住"意图"，而且**真的抓到了**历史上的问题（文档里写"门禁跑起来之后才暴露"）。
- 缺点：脆弱且可绕过——注释里写一句 `Thread.sleep` 就会红；反过来，把逻辑搬进辅助类就能绕过。它守的是"写法"，不是"行为"。
- 建议：保留现有门禁（成本极低），但把**最关键的 3 条**（tick 不阻塞、宿主不 import 功能模组、跨加载器清单一致）改成字节码/依赖分析（Gradle 的 `jdeps` 或 ASM 扫描），其余留作文本断言。

### 5.6 版本与兼容：API 没有版本

- `tianshu-api` 里 `@Deprecated` / `@since` 数量为 0；唯一的"版本"是 `CoreCapabilityProbe:5-33`：`coreVersion` 写成字符串 `"tianshu-core"`（不是版本号），`apiVersion` 写成字面量 `"1"`，且 `supportedCapabilities` **没有任何校验方**（`IntegrationModuleRegistry:36-38` 的 `declarations()`/`find()` 无读者）。**版本握手目前是装饰性的。**
- 唯一的真实版本串在 adapter 私有常量 `TianshuNetwork:14-15`（`PROTOCOL_VERSION = "1"`），模块不可见、不可查。
- `PayloadType` 的身份就是名字（`equals/hashCode` 比 `name`）：改名是纯 breaking change，而加载期**不会给出任何提示**；唯一会被拒的是"同名绑定不同类"（`:80-85`）。
- 结论：`模块架构.md:307-328` 把一批类型列为"冻结契约"，但没有任何机制执行"冻结"。真要对外承诺 API，至少需要一个 `apiVersion` 从构建产物注入 + 一个 `@Deprecated` 约定。



## 6. 游戏性能

### 6.1 宿主自身的帧/tick 开销：很轻

| 路径 | 每次开销 | 评价 |
|---|---|---|
| `RenderGuiEvent.Post` | 1 个 `HudFrameContext` record + N 层 `render`；层为空直接 return | 可接受；但每层每帧都写一次 `consecutiveFailures.remove(...)`（`NeoForgeHudHost:92`），成功路径上是纯白做 |
| `ClientTickEvent.Post` | 1 次 tick 信号 publish + 2 个 `KeyMapping.isDown` + `consumeClick` 循环 | 极轻（< 10 µs 量级） |
| 每 tick 的 `moduleInputAvailable()` | **每次 `new CoreRuntimeStatus(...)` + 2 次 `List.copyOf` + 1 次 `stream().sorted()`** | 20 次/秒的纯垃圾，可直接读 `phase/initialized/enginePhase` 字段 |
| 世界事件 | 每事件一个信封（含路由 + 风暴防护 + 生命周期记录） | 事件稀疏，可接受；已有保留期回收（P1-1 已修） |
| 模块缺席 | 零 | ✅ |

### 6.2 真正会掉帧的地方：设置页 UI

这一块比游戏世界重一个数量级，且都发生在渲染线程：

1. ✅ **滚轮每格全量重建**（高，已修）：`mouseScrolled` 现在走 `requestRebuildCurrentPage()` 合并——高精度滚轮一帧的多条事件只重建一次。原来直接调 `rebuildCurrentPage()`（`:82-116`）：`clearWidgets()` + 重跑所有模块 `panelFactory` + 重建全部控件 + 每行 `font.split`。
2. ✅ **设置层每帧全量过滤**（中，已修）：`VanillaSettingsLayerRenderer.refreshRows` 现在按"源实例 + 搜索词"缓存 `visibleItems()`；命中时不再对每个条目做 `toLowerCase()`、不再新建 `ArrayList`/`List.copyOf`。顺带修掉了"选中一行但高亮不跟随"（`rows` 的选中色是烘焙的，现在选中变化也会重建）。
3. **列表卡片每帧重排文本**（中，未修）：`SettingsListCardWidget:73,78-81,91-94` 标题每帧 `font.split`，状态每帧 `toComponent() + getString() + font.width()`，`statusWidth()` 再算一遍。
4. **屏幕外列表项也构造控件**（中，未修）：`VanillaModuleSettingsRenderer.renderListGroup:428-449` 先建 `SettingsListCardWidget`（内含 `font.split`）再 `addIfVisible` 判断可见性，不可见的项白做一遍排版。
5. **每帧小对象**（低，未修）：`visibleRegion()` 同区域每帧算 3 次并新建 record（`TianshuSettingsScreen:466-472`）、`drawScrollRegionScrollbar` 每帧 `new ScrollState`、`chrome.layout()` 每帧 5+ 次。
6. **导航栏每帧 dirty 查询 + `Component` 构造**（低，未修）：`SettingsNavigationWidget:39,50`。

> 结论：**"游戏卡"的锅不该由宿主的 tick 逻辑背，而该由设置页的"全量重建"背。** 本轮已修掉最大的两项（滚轮全量重建、设置层每帧过滤），剩余三项都是"每帧小对象/重复排版"量级。

### 6.3 长时间会话的内存曲线

| 来源 | 是否无界 | 修法 |
|---|---|---|
| `EnvelopeLifecycleStore` 5 张表 | ✅ 已修 | 按策略每 N 个信封 sweep，只回收已终结 trace |
| `NeoForgeHudSurface.textWidths` | ✅ 已修 | 有界 LRU（256 条，访问序） |
| `HudAnchorEditorScreen`/导航栏的 `Component.translatable` | 否（短命） | 静态化即可（未修） |
| `DeadLetterQueue` | 否（512 上限，但每次 `size()` 是 O(n)） | 计数器（未修） |
| `ModuleStatusCache` | 否（按 module×type，且过期清理） | — |
| `neoforge.BossEventWatch.REPORTED` | 弱无界（每 Boss UUID 一条，跨会话） | 会话内实例（未修） |

### 6.4 线程与 IO 账本

- **按需创建**：`ProtocolExecutorManager` 的 8 条 lane 是懒创建（`ThreadPoolExecutor` 首次提交才起线程）；空闲时常驻的是 lifecycle(1) + scheduled(1) + diagnostics(1) + audio(2)。
- **全部有界**：每条 lane 是 `LinkedBlockingQueue(cap)` + `AbortPolicy`；音频池 `(2,2,queue 8)`；诊断队 `2048`。没有无界队列。
- **全部 daemon**：`threadFactory` 里 `setDaemon(true)`；不会阻止 JVM 退出。
- **关停**：`close()` 里 `cancel → shutdownNow`，之后最多等 1 s 让在途任务收尾（P2-11 已修）。
- **主线程阻塞点**：关服的 `destroy()` 现在最多等 5 s（P2-1 已修）；诊断 flush 仍最多等 5 s，但改成批量写后通常瞬间完成。
- **一次性卡顿**：资源重载时在主线程重建物品/实体词典（`NeoForgeClientBootstrap.onResourcesReloaded:283-290` → `ClientItemDictionaryBuilder`，逐项 `Component.translatable(...).getString()`）。原版 1,400 物品还行，重模组包 3,000+ 时可能 10–30 ms。

### 6.5 性能小结

宿主把"重活"全部赶出了主线程，这一点值得肯定：模型加载、下载、推理、音频、诊断都在各自的 lane 或专属线程上，tick 路径几乎不分配。剩下的性能问题分两类：**UI 全量重建**（体感明显、好修）和**无界保留**（不体感、会累积）。
