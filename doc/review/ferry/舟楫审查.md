# 舟楫审查

2026-11-24 · Minecraft 1.21.1 · Fabric / NeoForge

复核版本：入口 `d834d698`、舟楫 `b1568aba`、功能模组 `2525bc73`、适配器 `505aa1e0`。括号内编号对应原审查项。

## 高优先级

### 协议队列处理完第一条后可能停住（#8、#11、#28）

broker 为每条任务登记完成回调，用它移除 `running` 和 `handles` 里的记录并继续投递。任务进入工作线程池时，执行器用任务组的 `finishOne` 覆盖了这个回调。并发上限为 1 时，第一条虽已完成，broker 仍认为槽位被占用，下一条停在队列里。另一个窗口出现在组内排队时取消：任务先完成结算，随后仍可能进入 `inFlight`，失去再次释放槽位的机会。验收应覆盖连续投递两条，以及取消排队任务后再投递，检查回包顺序和最终占用数。[执行器](../../../../Tianshu-ferry/tianshu-core/src/main/java/com/rheinmetal/tianshu/protocol/runtime/ProtocolExecutorManager.java#L331) · [broker](../../../../Tianshu-ferry/tianshu-core/src/main/java/com/rheinmetal/tianshu/protocol/broker/AbstractQueueBroker.java#L102)

### Fabric 连开两个世界可能重复注册，关服后仍持有旧服务器（#3、#25）

Fabric 开服时为同一组动作创建新工具，直接写入进程级注册表。第一次关服后这些条目还在，第二次注册同 ID 的新实例会抛异常。执行、配方查询等端口也绕过会话登记，关服时清理不到，仍持有旧服务器。需要在同一客户端进程依次打开两个世界，检查第一次关服后的端口，以及第二个世界能否完成初始化。[Fabric 开服与关服](../../../../Tianshu-adapter/tianshu-adapter/1.21.1-fabric/src/main/java/com/rheinmetal/tianshu/fabric/FabricServerToolHandler.java#L109) · [工具注册](../../../../Tianshu-ferry/tianshu-api/src/main/java/com/rheinmetal/tianshu/api/tool/TianshuTools.java#L53)

### 模组调用缺少 NPC 归属校验（#22）

产品规则是**模组只能驱动自己申请的 NPC**。公共权限检查对非玩家调用直接放行，内建身体登记和保存的 owner 是玩家 UUID，没有申请模组的身份。验收应从实际模组入口检查：A 申请的 NPC 接受 A 的动作、拒绝 B 的动作，存档重启后结果一致。现行验收文档仍包含 operator 和授权玩家两种口径。[公共权限检查](../../../../Tianshu-ferry/tianshu-api/src/main/java/com/rheinmetal/tianshu/api/entity/EntityActors.java#L75) · [内建身体登记](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/body/BodyRegistry.java#L218) · [契约与验收](../../architecture/契约与验收.md#L69)

### 身体旧档无法重绑，读档失败还会影响下一个世界（#2）

- 旧 NBT 缺少维度，启动时区块又未加载，恢复逻辑就会把维度记为空。之后每次查找都因空维度提前返回，即使实体已加载，原背包和归属也无法重新关联。[旧档恢复](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/body/BodyPersistence.java#L187) · [载体查找](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/body/BodyRegistry.java#L286)
- 读档失败会设置进程静态标记 `loadFailed`。退出该世界后，若下一个世界尚无身体文件，加载函数直接返回，标记仍然生效，定时和关服保存都会跳过新世界的身体。[保存保护](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/body/BodyPersistence.java#L61) · [读档入口](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/body/BodyPersistence.java#L140)

### 玩家型 NPC 卸载后仍被身份对象持有（#26）

`BodyState.detach()` 清除了载体字段，但 `BodyState.identity` 仍指向保存原玩家实体的 `BodyIdentity.player`。只要身体登记仍在，旧实体就仍然可达。重新绑定时还应检查动作实际使用的是新载体。此处已确认强引用链，未测长期堆增量。[身份对象](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/body/BodyIdentity.java#L22) · [身体状态](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/body/BodyRegistry.java#L554)

### 合成会丢配方余物，也会丢未装下的产物（#34）

合成先扣材料、放入产物，再从已改变的背包重建合成格计算余物。例如制作蛋糕时，配方此时已读不到被扣除的奶桶。产物入包只判断放入数量是否为零，能放入一部分时其余数量直接丢失。验收应核对合成前后的物品总数，覆盖蛋糕返桶和背包只能装下部分产物两种情形。[合成结算](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/tool/CraftSource.java#L91)

### 回响把设备失败标为播放成功，旧音频桥收不到完成通知（#32）

回响收到设备的 `FAILED` 后只记日志，随后仍调用成功完成处理，运行时会把该句标为完成。另有一条兼容路径：旧音频桥仅实现 `Runnable` 回调注册，回响调用的新重载默认空实现，播放结束后队列等不到通知。两条路径应分别验证请求终态和下一句是否继续。[播放结果处理](../../../../Tianshu-features/tianshu-echo/src/main/java/com/rheinmetal/tianshu/echo/playback/TtsPlaybackController.java#L322) · [运行时完成处理](../../../../Tianshu-features/tianshu-echo/src/main/java/com/rheinmetal/tianshu/echo/runtime/TtsRuntime.java#L722) · [音频桥接口](../../../../Tianshu-ferry/tianshu-api/src/main/java/com/rheinmetal/tianshu/api/IAudioBridge.java#L56)

## 其他未解决问题

- **存档 ID 不可用时仍可能混写记忆（#1）。** 单人世界在取不到存档目录标识时，用显示名构造可写身份。两个同显示名存档若都走此分支，就可能指向同一记忆目录。[世界身份采集](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/host/WorldIdentityCapture.java#L73)
- **听澜的代理探测未走出网白名单（#9）。** 配置下载代理后，听澜会直接向 GitHub 建立 TCP 连接来选择来源。此探测也受已确认的统一白名单约束。另有 4 个听澜下载测试缺少本地测试策略，在真正发出 HTTP 请求前就失败。[来源选择与探测](../../../../Tianshu-features/tianshu-intake/src/main/java/com/rheinmetal/tianshu/intake/model/AsrModelDownloader.java#L310)
- **听澜自有模型下载器漏读后续页，也未复用成功镜像（#18、#33）。** 文件树读取只拿响应正文，既不跟随下一页，也得不到实际应答的来源。权重位于后续页时会被漏掉，首选源失效时后续文件还可能反复等待。应从听澜实际下载入口覆盖这两种情形。[文件树读取](../../../../Tianshu-features/tianshu-intake/src/main/java/com/rheinmetal/tianshu/intake/model/AsrModelDownloader.java#L355)
- **新旧版本工具目录格式不兼容（#4）。** 目录沿用原通道 ID，每项却多了必读的启用标记。如果新客户端按新版格式读取旧服的非空目录，会错位或读到包尾。混合版本协商和降级尚未实机验证。[目录编解码](../../../../Tianshu-adapter/tianshu-adapter/1.21-1.21.1-common/src/main/java/com/rheinmetal/tianshu/mc/network/ToolCatalogPacket.java#L47)
- **能力调用超时后仍可能开始执行（#30）。** 超时只施加在组合 future 上。提供方已经阻塞时会继续占用工作线程，尚在队列里的调用也可能在调用方收到超时后才开始执行。[能力调用](../../../../Tianshu-ferry/tianshu-api/src/main/java/com/rheinmetal/tianshu/api/capability/CapabilityCatalog.java#L236)
- **未结束的身体操作可长期留在静态表（#27）。** 底层动作一直不结束、相同身体也不再申请操作时，五分钟过期检查不会触发，身体 ID 和已绑定的取消信号可一直保留。[操作槽与取消信号](../../../../Tianshu-ferry/tianshu-client/src/main/java/com/rheinmetal/tianshu/client/tool/BodyOperations.java#L33)
- **协议历史清扫依赖后续流量（#29）。** 音频正文的字节预算和保留时长在清扫时检查。会话接收大载荷后若不再收消息，已结束的音频仍可超过保留时间，或在下一次清扫前超过预算。[清扫触发条件](../../../../Tianshu-ferry/tianshu-core/src/main/java/com/rheinmetal/tianshu/protocol/runtime/ProtocolRuntime.java#L401)

## 产品决策已确认（#36）

单轮录音长度按"**不限制玩家说话**"处理：固定 60 秒上限已移除，默认保留整段按住的内容。听澜新增可选配置 `maxUtteranceSeconds`（`0` = 不限，默认），由运维自己决定是否加护栏；触顶时明确记录"达到配置上限，其余未录制"，不再静默丢尾——静默截断与麦克风故障在玩家看来没有区别。`AudioCaptureServiceTest` 覆盖"默认不截断"与"配置上限截断且告知"两条。[听澜录音缓冲](../../../../Tianshu-features/tianshu-intake/src/main/java/com/rheinmetal/tianshu/intake/audio/AudioCaptureService.java#L29)
