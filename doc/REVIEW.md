## 2. 待议

### 2.1 `EXT-1` 外部模组自带实体与渲染时，平台边界在哪里

**要问的问题**：一个老牌实体模组（比如女仆类）把自己的 NPC 迁到舟楫上时，实体、模型、动画渲染仍由它自己注册；
平台这边只提供“谁能指挥这具实体、怎么调、结果是什么”。这个分工是否成立？要不要平台再提供一层“外部实体桥”。

**事实（当前代码）**：

- Minecraft 的视觉层是纯客户端数据驱动的（`EntityType` + `EntityRenderer` + 模型层/`EntityRenderState` + 贴图动画）；
  舟楫**完全没有介入**，也不打算介入——包装渲染等于把 GeckoLib、资源包和版本差异一起背进来。
- 模块可以自己注册实体与渲染（正常写模组即可），**不需要经过舟楫**。
- 但 `EntitySpawnPort` 只会创建适配层自己的载体实体（`WalkerBody`）：模块声明的类型只能给 id、尺寸、是否
  playerLike，**给不了实体类和渲染器**。也就是说：外部模组**无法用平台的生成接口创建“自己的实体”**。
- 桥接机制本身是通的：模块可以 `EntityActors.register(EntityProvider)` 把自己已有的实体接进平台，之后
  `entity.*` 与归属判定就作用于它（验收台的 `AcceptanceBodies` 就是这么做的）。
- 缺的是产品化那一层：**没有“给外部实体用的 provider 基座”、没有文档、也没有在真实自定义实体上验证过**
  （验收台那个是假 body，不是真实体）。

**两条路，需要人来定**：

| 选项 | 内容 | 代价 |
|---|---|---|
| A | 适配层提供 `EntityProvider` 的基类/范例 + 真实自定义实体的接入用例，外部模组只需包一层 | 平台要长期维护这层“半适配”代码，还得跟着实体 API 走 |
| B | 不提供基座，只写一页接入指南，外部模组自己实现 `EntityProvider` | 平台轻，但每家都得自己趟一遍，出错时不知道是它的问题还是我们的 |

**需要谁定**：产品（是否把“外部实体承接”当作基座能力），以及实现方（A 的基类要不要含能力位映射、背包与
移动的原生映射）。

### 2.2 `ACT-1` 动作能力在身体上没有验收证据

**现状**：`entity.move` / `entity.mine` / `entity.place` / `entity.craft` 这些主动作，一条实机用例都没有。
现在验过的都是“生成、读状态、读世界、释放”。验收台的身体类型 `acceptance_orb` 没有声明动作能力位，所以
用它测动作只会得到“能力位不满足”，不能当作证据。

**决定（用户）**：先只记录，等其他验收完成再讨论；做的时候走“数值断言 + 实机目视”两条腿（坐标真的变了、
方块真的没了，同时用户在游戏里看它动）。

## 3. 已记录、暂不处理

- **`entity.command.run` 需要操作员逐次批准**：用户明确“可以不考虑差异性”，不作为缺口。女仆类“让她去做某事”
  应走动作能力位，`command.run` 只当调试出口。
- **多实体规模**：用户判断“AI 接入实体不会太多”。记在这里，不上压测；真要做时按现实规模（个位数到几十）验，
  文档里只写已验证规模。
- **MC 版本**：当前只 build 1.21.1，其它版本暂不讨论。
