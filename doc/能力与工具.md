## 1. 能力表

`CapabilityCatalog` 是"有什么能力、谁能看见"的唯一一张表。一行是 `CapabilityDescriptor`：
id、种类、绑定、描述、端、权限、提供方、属性。

| 种类 | 是什么 | 谁发布 |
|---|---|---|
| `TOOL` | 模型可调的一步操作 | 工具经 `TianshuTools` 镜像进表，**不能直接 register** |
| `SKILL` / `RESOURCE` / `PROMPT` | 给模型读的材料（说明书、资料、模板） | 内容提供方（classpath 或目录） |
| `WORKFLOW` | 一串能力的编排 | 见 §6 |

**id 命名空间 ≠ 提供方**：`minecraft:*` 表示"操作的是原版能力"，提供方仍是 `tianshu`（基座）。
两个轴分开，是为了"这些能力是谁发明的"和"这条行是谁登记的"都能回答。

三个消费面共用一份判定：工具的 typed/JSON 入口、`capability.read`、`invoke`。同一个能力对同一个调用方
不会出现"工具表里没有、却能调通"。

## 2. 工具契约

**信封**：成功 `{"ok":true,"result":…,"durationMs":7}`；失败 `{"ok":false,"code":"…","message":"…","durationMs":7}`。
成功可以带 `bytes`，失败只带 `durationMs`。工具只回这两种形状，不自定义外层。

**参数**：`argsSchema()` 是权威。缺字段、类型错、枚举外、数组项不合格、多余字段 → `INVALID_ARGS`，
消息带 `args.x` 路径。**多余字段默认拒绝**；要自由参数必须显式 `additionalProperties: true`。

**取消与配额**：`tool.cancel` 取消一次在飞调用，客户端 pending 立即 `CANCELLED`，服务端在飞的 future 被取消。
同一调用者第 9 个在飞 → `BUSY`。传输失败 `UNAVAILABLE`，平台自身失败 `FAILED`。

**目录**：`minecraft:tool.catalog` 给出当前可用工具与 revision；`tool_catalog_v4` 是协议代数。
服务端目录**每一格都带 `enabled`**（登录推送、主动刷新、热重载同一形状）：客户端以服务端开关为准。

**两层入口**：模型走工具表（`TianshuTools` / `CapabilityExposure`），模块走 `CapabilityCatalog.invoke`。
两条都过同一套权限、档位与超时。

## 3. 档位怎么落地

`ToolPolicy.forCategory` 决定默认开关与权限，`requiredAutonomy()` 决定档位：

| 类别 | 权限 | 默认 | 典型 |
|---|---|---|---|
| `LOCAL` | EVERYONE | 开 | 读客户端数据、客户端偏好、`server.say` |
| `SERVER_READ` | EVERYONE | 开 | 配方、标签、世界事实 |
| `SERVER_WRITE` | OPERATOR | 关 | 作弊类动作（`FULL` 档） |
| `BODY_WRITE` | EVERYONE | 关 | `entity.*`——放行只看归属 |

生存动作（合成、搬物品、操作工作方块、按按钮、放方块）类别仍是 `SERVER_WRITE`，但逐个覆盖成
`EVERYONE` + 默认开启：它们就是普通玩家用手能做的事，**动作以该玩家身份执行**，原版权限、领地规则、
游戏模式照常拦截。

两条轴的完整语义见 [职责边界](职责边界.md) §3。

## 4. 共享与订阅

**两个维度，缺一不可**：提供方开放哪些行，消费方接受哪些行。两半都满足才可见。

**提供方**在注册能力时声明 `share`（`all` / `none` / 模块列表）。技能与文本类能力的声明写在
front matter 的 `metadata.share`——`metadata` 是 Agent Skills 规范留给平台私有数据的映射，顶层自造字段
会让文件不可移植（当年写过 `covers:`，结果那份技能不能被别的工具读）。

**默认跟随提供方**：基座 `tianshu` 与玩家自己的目录 `user` 不写就按开放算，第三方不写即私有。
未声明就开放等于"装两个模组就互相开门"，所以模块侧必须失败关闭。

**消费方**默认订阅"提供方开放过的原子能力"，分子默认不订。不需要维护"哪些提供方算本地"的名单——
那张名单第一次新增内建提供方时就会过期。

**订阅可以点名**：

```java
CapabilitySubscriptions.declare("changsui", CapabilitySubscription.only(
        CapabilityId.parse("minecraft:block.break"),
        CapabilityId.parse("minecraft:container.transfer")));
```

- 点名即白名单：没点名的工具看不见、调不动；
- 点名只做减法：够不到提供方没开放的行；
- 点名**不藏说明书**：技能/资源/提示词不是可调用的行，仍按提供方走——否则模型知道工具名却读不到怎么调。

**看不见就说"不存在"**：看不见的行 `invoke` 一律回 `UNKNOWN_CAPABILITY`，不回"禁止"——后者等于确认它存在。

`CapabilitySubscriptions.audit()` 把三种声明错误分开报：订阅了没向谁开放的提供方、订阅了没装的模组、
点名了没人发布的能力。

## 5. 工具文档与技能

**一个工具一份文档，文档住在装它的技能里**：

```
minecraft:entity.mine  →  <某个技能>/references/entity.mine.md
```

- 文件名由工具 id 推导（先试裸名，再试 `<命名空间>.<名字>`），没有索引可漂移；
- 查找由**技能自己提供**（`SkillReferences`）：按工具 id 问已注册的技能"你的 `references/` 里有没有这个文件"。
  类路径扫描只能扫到基座自己的文件，第三方模组和玩家目录的说明书永远查不到；
- 技能卸载，它的文档一起下线；
- 权限在**工具行**上：不会出现"文档读得到、工具调不动"，反之亦然。

**技能（`SKILL.md` + `references/`）讲成篇的东西**：调用约定、失败怎么读、一组工具共同的前提。
它不声明自己教哪几个工具——文档是工具行的附件，不是第二种能力。写法见 [技能撰写规范](技能撰写规范.md)。

**门禁**：`verifyEveryToolHasADocument` 要求每个 `ToolId.of` 都有同名 reference，缺了就失败。
没有它时，新增工具忘写文档是完全无声的——说明书就是不出现，谁也不知道少了。

## 6. 复合能力（工作流）

`kind=WORKFLOW` 只是分类（订阅要用），**不是另一种入口**：调用方式与原子能力完全相同，按 id 调。

- 每个复合能力**必须声明代价**：预计耗时、影响范围、有无副作用、是否响应取消；
- **步骤清单可以公开也可以不公开**：公开时基座执行器逐步执行（能数步、能在步边界停、逐步套调用者档位），
  不公开时提供方自己执行、靠"响应取消 + 超时硬截断"兜底；
- 两种都合法，区别只在可观测性与可中断性，不是安全性。

**不做的**：把两种执行方式再分成两类（无安全差异）；工作流的循环/递归/变量（按证据再长）。

## 7. 门禁与验收

### 7.1 一键门禁（改完必跑）

```bash
./gradlew :tianshu-api:test :tianshu-core:test :tianshu-client:test \
  verifyFeatureIsolation verifyFeatureOptionalDependencies verifyClientMediaWiring \
  verifyServerToolRegistration verifyHostHasNoFeatureDependency verifyCommonAdapterNeutral \
  verifyNoPlatformImport verifyUniversalModuleJars verifyAdapterProperties \
  verifyAdapterMatrixCoverage verifyProtocolVersionSingleSource verifySettingsRenderersCoverOptionEntries \
  verifyEveryToolHasADocument
```

**不要用 `./gradlew check`**：它会带上听澜的既有抖动用例（`IaModuleProtocolFlowTest` 的 `await` 超时），
与本模块改动无关。

游戏内那一层用 `:tianshu-adapter:1.21.1-neoforge:runGameTestServer`，
**判据是日志里的 `All N required tests passed`**——这个任务的退出码不反映游戏内崩溃。

### 7.2 验收台（`tianshu-lab`）

入口两个：无人值守（`-PtianshuLabAcceptance=1` / `=world`）与游戏内（设置 →【听澜】仲裁测试台 →「运行平台验收」）。
证据两处同源：`run/tianshu-lab/acceptance-<时间戳>.json` 与 `run/logs/tianshu-diagnostics.log` 的 `acceptance.run` 事件。

三条硬规矩：

1. 用例 id 与文档同源；覆盖声明与未覆盖清单都印在报告里；
2. 跑不了的显式 SKIP 并写原因，不许静默通过；
3. **`SELF-CHECK-1` 必须失败**，它若 PASS，整轮 `accepted=false`——验收台自己必须能证明会失败。

### 7.3 四层"可用"

「可用」＝下面四层都有**当轮**证据，跑不了的写明原因。

| 层 | 跑什么 | 判据 |
|---|---|---|
| A 门禁 | §7.1 的命令 | `BUILD SUCCESSFUL`，输出里没有 `FAILED` |
| B 验收台 | 每个加载器各一次，**必须进世界**（模块装配发生在世界会话里） | 报告 `accepted=true`、`selfCheckHeld=true`、失败 0；SKIP 带原因 |
| C 专用服与联机 | 起服 + 进服（`ceiling=full` 与相关开关打开）；单侧安装（原版客户端进服 / 服务端原版时远端工具不出现） | 见 §7.4 待实机项 |
| D 人工项 | 设置页改一项重进、命令非法参数报码、切 `en_us` 无缺键、被拒调用在诊断日志里有 `code`/`message` | 与界面提示一致 |

联机协议四条：未装舟楫的客户端可进服且保留本地功能；服务端装、客户端不装可进服且不发送无接收通道的包；
双端都装且有共同的版本化工具目录通道时启用远程工具，否则保留本地功能；声明自定义实体的内容模组缺装则拒绝连接。

### 7.4 尚未拿到的证据

| 项 | 怎么验 |
|---|---|
| 原版客户端单侧安装 | 服务端装舟楫，用原版 1.21.1 客户端进服：不掉线、`latest.log` 无 payload 报错 |
| 身体存档重载 | `save-all flush` → `stop` → 起服 → 进服或 `forceload` → `list` 里还在，背包、归属、访问设置都在 |
| 两个世界一进程 | 进世界 A → 退到标题 → 进世界 B：工具可用、世界记忆不串档；回 A 记忆恢复 |
| 双端实体验收台 | 测试服与客户端都装 `tianshu-lab` 时，内建 walker 与 `acceptance_orb` 可生成、同步、显示 |
| HUD | 只能在全装配入口（根工程 `runClient`）里看，验收台够不着 |

### 7.5 门禁的教训

- 13 个 `verify*` 里曾有 4 个在空转（路径写死、`inputs.dir` 不展开目录）——**"通过"只有在能证明它会失败时才算数**。
- 盲区仍在：本地文件系统故障、并发正确性、跨版本 API 存在性（后者要靠离线 API 签名索引）。
- 验收台抓出来的 bug 比人工点出来的多，所以新功能先加用例，再补人工项。
