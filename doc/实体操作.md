## 1. 这个方向管什么

**管**：让一具身体走、看、挖、打、捡、装备、放、交互、合成、搬、用物品、跑一组步骤，
以及读它自己的状态与周围世界。

**不管**：这具身体该会什么。那是**注册它的那个模组**说的，基座不评价——
一个注册了"酒狐"的模组、一个加了十种新怪物的模组，它的实体能飞能穿送、能挖能打，
是它自己的产品，不是基座的事了。

实体动作只有**生存能力、作弊能力**两档。读取位置、背包和能力清单属于查询。玩家辅助的三档用于代理以玩家身份行动，见 [职责边界](职责边界.md) §3。

## 2. 工具清单（29）

`minecraft:` 命名空间下 29 个。每份详细说明在 `skills/entity-tools/references/<id>.md`，
用 `capability.read` 按 id 读。

下表同时列出身体查询与动作工具。当前 29 个工具默认开启，执行时还会检查 NPC 上限、控制权与身体能力。

| id | 做什么 |
|---|---|
| `entity.list` | 列出所有身体与各自 id |
| `entity.status` | 自身位置、维度、血量、饥饿、手持物品、是否存活 |
| `entity.scan` | 按半径列周围方块与实体（必须给过滤） |
| `entity.inventory` | 背包槽位与数量 |
| `entity.inspect` | 按 id 读一个实体：类型、位置、维度、血量、归属 |
| `entity.block.inspect` | 身体读一个方块 |
| `entity.item.inspect` | 身体读自己背包某个槽位 |
| `entity.craft.available` | 身体能做的配方（答案由它背包里的东西决定） |
| `entity.world.info` | 身体所在位置的世界信息 |
| `entity.world.locate` | 以身体为原点查本维度已完整生成的区块，包括已卸载区块 |
| `entity.world.survey` | 以身体为原点勘探世界，包含未生成的地形。模组可分别订阅两种工具，范围见 [玩家定位](玩家辅助.md) |
| `entity.move` | 走到世界坐标（any / walk / fly / teleport） |
| `entity.look` | 转过 yaw/pitch，或朝向一个目标坐标 |
| `entity.mine` | 挖视线内、够得着的一个方块 |
| `entity.attack` | 对目标实体造成伤害 |
| `entity.pickup` | 捡起附近的掉落物 |
| `entity.equip` | 按槽位装备或卸下（`slot` 与 `entity.inventory` 索引一致） |
| `entity.drop` | 把手持或指定槽位的物品丢到地上 |
| `entity.give` | 把物品交给够得着的目标（玩家或容器） |
| `entity.use` | 对实体交互：喂食、驯服、挤奶、交易 |
| `entity.place` | 用**它自己的背包**放一个方块 |
| `entity.place.line` | 沿方向连放同种方块（最多 16） |
| `entity.interact` | 按钮、拉杆、门、活板门、栅栏门 |
| `entity.machine` | 操作炉子家族，物品进出都是它自己的背包 |
| `entity.transfer` | 容器槽位与**它自己背包**之间搬物品 |
| `entity.craft` | 按配方合成一次，材料从它自己背包扣 |
| `entity.item.use` | 用主手物品（即时生效；按住类会拒绝），`holdTicks` ≤ 100 |
| `entity.sequence` | 按顺序跑一组身体步骤（最多 32 步，失败即停） |
| `entity.command.run` | 身体申请执行一条命令：先令牌、operator 批准、单次有效 |

**放方块、拆方块、用物品这三件事只有这边有**：玩家的那两只手由玩家自己用，基座不替他做
（[玩家辅助](玩家辅助.md) §1）。身体做这些用的是**它自己的**背包、够得着的范围与权限。

## 3. 实体动作的判定

| 判定 | 规则 | 拒绝原因 |
|---|---|---|
| 归属 | 模组只能驱动自己申请的 NPC；身体只能驱动自身 | `body.controller.mismatch` 等 |
| 能力位 | 身体必须支持动作所需的 `EntityCapability` | `UNSUPPORTED_ACTOR` |
| NPC 最高档 | `npc.ceiling=survival` 允许身体原生能力，`cheat` 还允许服务端已实现的特权动作 | `NO_PERMISSION` / `body.autonomy.denied` |

默认上限是生存档。移动按具体身体判定；模组用 `EntityActor.nativeMovementModes()` 声明原生方式。单次移动与序列步骤共用判定。内建 walker 原生步行，marker、stand 的直接搬移需要作弊档。`entity.command.run` 还需操作员批准具体命令。

身体调用自身动作时可省略 `body`。模组或玩家驱动身体时须给出目标 ID。

完整的归属阶梯（controller 缺失、mismatch、未验证、self_only…）见 [实体](实体.md) §6。

## 4. 说明书与技能

- 技能 `tianshu:entity-tools`，随 jar 发布在 `tianshu/skills/entity-tools/`；
- 约定（信封、`body` 语义、失败怎么读）写在它的 `SKILL.md`；
- 每个工具一份 `references/<id>.md`，示例要求见 [技能撰写规范](技能撰写规范.md) §4。

## 5. 加一个工具

1. 先确认这具身体真的**声明了**对应能力位；没有就别加工具，加了也只会回 `UNSUPPORTED`；
2. 在 `tianshu-client/.../tool/` 写 `TianshuTool`，`category()` 用 `BODY_WRITE`（写）或 `BODY_READ`（读）；
3. 用 `requiredAutonomy()` 声明工具最低档位（默认生存）；身体提供方可通过 `requiredAutonomy(EntityCapability)` 标记某项能力需要作弊档；
4. 用 `ActorScope.body(caller, bodyId)` 拿执行者，它已经做了"没填 body 就拒绝"和归属检查；
5. 世界操作写在 `*Ops` 里，玩家侧（如果有）只适配参数——见下。

### 与玩家侧共用一份逻辑

同一个动作两侧都有时（`interact`、`transfer`、`craft`、`place`…），**逻辑放在一个谁都不属于的类里**：

```
PlaceOps / PlaceLineOps / InteractOps / MachineOps / BlockInspectOps / TransferOps
CraftOps / CraftAvailableOps / ItemUseOps / ItemInspectOps / WorldInfoOps
WorldLocateOps / CommandRunOps
```

两边的工具类只做六件事：`id`、`category`、`policy`、`description`、`argsSchema`、解析 `ActorScope` 再调 `Ops`。
操作类的签名吃 `ActorRef` 加具体字段，**不吃任何一侧的 `Args` 记录**——吃了就等于一侧拥有另一侧。
检查过：`*Ops` 不引用任何 `Tool` 类，工具类之间也不互调。

## 6. 跨侧驱动：客户端智能体驱动服务端身体

客户端智能体选择目标和动作。服务端从连接取得玩家 UUID，校验归属、工具开关、NPC 档位与身体能力，在游戏线程执行动作并返回结果。模型和密钥留在客户端。

| 谁发起操作 | 服务端核对什么 |
|---|---|
| 服务端模组逻辑 | 身体的 `ownerModule` 等于调用模组。 |
| 玩家客户端的模组或智能体 | 调用模组与 `ownerModule` 一致，连接玩家 UUID 与申请这具身体时登记的玩家一致。 |
| 玩家本人直接调用 | 由身体提供方检查玩家访问策略。内建载体默认仅限主人，可显式设置信任名单或开放访问。 |

服务端内容模组在自己的创建和释放工具中调用 `BodyController.forRequest(本模组 ID, context.caller())`，把结果交给 `EntitySpawnPort`。这样，申请人的 UUID 来自调用上下文。服务端模组自主生成 NPC 时可直接使用只有模组 ID 的入口，这类 NPC 由该模组在服务端驱动。

第三方实体通过 `EntityActor.ownerModule()` 和 `ownerPlayer()` 提供归属。例如驯服类实体可以直接返回自身已有的主人 UUID。模组不匹配返回 `body.controller.mismatch`，连接玩家不匹配返回 `body.access.denied`。

联机报文的 `callerModule` 用于标识调用模组，玩家身份由服务端连接提供。服务端能够区分玩家连接，同一客户端进程内的模组身份依赖该进程如实报告。

`ACC-XEN-2` 验证客户端经工具通道申请、查询并释放身体。`BodyAccessTest` 验证两个模组共用同一玩家连接、两个玩家使用同一模组时的归属限制。
