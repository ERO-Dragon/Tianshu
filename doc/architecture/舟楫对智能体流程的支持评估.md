# 舟楫（平台）对智能体流程的支持评估

> 状态：评估，2026-11-14。范围只包括平台层（`tianshu-api` / `tianshu-client` / 适配器），
> 不评估天枢（`tianshu-auxilium`）自身的循环与提示词。

## 结论

**对"短、同步、单步"的智能体流程，平台已经够用**：发现、调用、内容读取、错误信封、权限/档位、限流、
审计、MCP 双端都已具备，并且跨 43 个适配器一致。

**对"长、可取消、动态"的智能体编排，平台已补两块**：JSON Schema 执行前校验、能力目录修订号；
仍缺调用取消与 MCP 健康状态。

## 一、平台已经提供的能力

| 能力 | 入口 | 说明 |
|---|---|---|
| 工具发现 | `TianshuTools.catalog(caller, side)` | 按权限、侧可达性、风险档位、启用状态过滤 |
| 全能力发现 | `CapabilityCatalog.list/find`、`CapabilityExposure` | tool/skill/resource/prompt/connector，开放 kind |
| typed 调用 | `TianshuTools.handle(...).call(...)` | 模组代码用 Java 对象；失败抛 `ToolException` |
| JSON 调用 | `TianshuTools.callJson(...)` | 智能体/MCP/lab 用；失败是 `{ok:false,code,message}` |
| 服务端工具通道 | `ServerToolChannel` + `ServerToolDispatch` | 目录激活、幂等、限流、审计、异常单行化 |
| 权限与档位 | `ToolPermission`、`ToolAutonomyGate` | EVERYONE/OPERATOR × READ_ONLY/CONSERVATIVE/FULL |
| 内容读取 | `CapabilityCatalog.invoke`、`tianshu:capability.read` | skill 正文/附录/分页、resource、prompt 渲染 |
| 内容来源 | 目录 + classpath provider、`CapabilitySources` | 命名空间去重、第三方注册口 |
| MCP 客户端 | `McpClient`（HTTP/stdio） | tools/resources/prompts，后台连接，失败记录 |
| MCP 服务端 | `McpServer` | loopback 只读端点，外部 agent 可读能力 |
| 审计 | `ToolAudits` | 服务端写工具执行记录，可安装 sink |
| 错误格式 | `ToolError` + `ToolCallParser.parseDetailed` | 稳定 code；解析失败保留原因 |
| 多加载器 | 43 个适配器 | 1.20.1–26.3，三种网络形态 |

## 二、智能体流程真正需要、但平台还没给的

### 1. 调用取消（优先级最高）

现状：客户端 pending 可以失败，但**没有取消通道**。调用超时后服务端仍可能继续执行（写工具已经改了世界），
MCP 远端调用也无法中止。长任务（大批量扫描、MCP 远程操作）没有"停下"的语义。

平台需要：

- `ToolCallToken`（或 request id + cancel 消息）；
- 客户端 `ConnectionToolChannel.cancel(requestId)`；
- 服务端 handler 收到 cancel 后的协作式中止（至少让工具能看到取消标志）；
- MCP 调用映射到取消/关闭。

### 2. 目录变更通知 — **修订号已补齐（2026-11-14）**

`CapabilityCatalog.revision()` 在注册/注销/工具镜像/开关变化时单调递增；消费者可以轮询并在变化时刷新。
**主动推送（事件/包）尚未做**：客户端仍只在登录时拿服务端目录，MCP 工具晚到时需要消费者自己重拉。

### 3. JSON Schema 校验 — **已补齐（2026-11-14）**

`ToolArgumentValidator` 在 `callJson` 执行前按 `argsSchema` 校验 required/type/additionalProperties/enum/数组 items；
失败返回 `INVALID_ARGS` + `args.foo` 路径。数值与长度边界**故意不拦**：有些工具会把请求夹进自己的范围，
schema 是给模型的指南，不是第二道夹取。
未知 schema 关键字忽略，不会因为 schema 更丰富而拒调；typed API 不需要（编译期已约束）。

### 4. MCP 健康状态与重连

现状：`McpBridge.problems()` 只在内部；没有状态端口/事件；远端断开后不会自动重连。
智能体无法知道"某个 MCP 工具现在不可用"。

平台需要：

- 对外暴露连接状态（connected/tools 数/最近错误）；
- 指数退避重连；
- 工具调用失败时区分"工具报错"与"连接断了"。

### 5. 预算、并发与流式（次级）

- 结果目前只有线缆上限（32KB）与调用方自行截断；平台没有 token/上下文预算接口；
- 客户端 pending 上限 64，没有按调用者的队列/优先级；
- 长内容只有分页，没有流式/进度；
- 这些可以留给消费方，但平台至少应提供"结果大小/耗时"的元数据，方便编排层决策。

## 三、不需要平台做的

- **提示词、轮次、重试策略**：属于智能体（天枢）自己的编排，平台只提供 `parseDetailed` 这类原语；
- **确认弹窗**：已决定用风险分级替代，平台不需要 UI；
- **技能的具体内容**：属于内容作者/模组，平台只负责加载与读取。

## 四、建议的平台下一步

1. **取消语义**（token + cancel + 协作式中止）；
2. **目录修订号/变更事件**；
3. **JSON Schema 基础校验**；
4. **MCP 状态与重连**；
5. 再之后才是天枢侧的轮次、重试、提示词。

这四块都与天枢无关，先补齐，未来的智能体（不论是不是天枢）都能直接用。
