### P0-1 ✅ 语音播报的完成钩子被"开始播放"清空 🌉

- **级别**：P0 —— 用户可感知的功能失效
- **位置**：`tianshu-client/.../client/audio/AudioManager.java:355`、`:518-519`；
  `tianshu-echo/.../playback/TtsPlaybackController.java:320-321`
- **现象**：`startTtsPlayback` 的第一句是 `stopTtsPlayback()`，而后者执行 `onPlaybackFinished = null`。
  调用方在它**上一行**刚注册完钩子。
- **触发**：每一条语音回复，必然触发。
- **后果**：`onPlaybackFinished` 永不触发 → `sessionManager.complete(session)` 与
  `scheduleNextSpeechSentence()` 都不执行 → **多句播报从第二句起不再排队，会话卡在播放态**。
- **为什么没被测出**：`AudioManagerTest:16-19` 只测"设钩子 → 直接 finish"，恰好绕开了 `start`。
- **修法**：`startTtsPlayback` 里只调 `closeTtsChannel()`，不要连带清 callback；或让调用方在 `start` 之后注册。
  补测试 `TS-1`。
- **注意**：注释 `"An aborted utterance must never report playback completion."` 的意图是对的，
  错的是它被无条件执行在"每次开始播放"里。修的时候保留意图，只改位置。
- **验证**：✅ 四处调用点全部读过

### P0-3 ✅ MCP stdio 的请求与响应不配对，并发调用会互拿对方的结果

- **级别**：P0 —— 静默返回错误数据，比报错恶劣
- **位置**：`tianshu-client/.../capability/mcp/McpStdioClient.java:46-48`
- **现象**：`exchange()` 里 `write(request)` 与 `reads.submit(in::readLine)` 是两步，中间没有锁；
  `write()` 内部的 `synchronized (out)` 只保护写。响应也**不按 JSON-RPC `id` 校验**。
- **触发**：同一台 stdio 服务器上两个并发 `tools/call`。平台允许同一 caller 8 个在飞
  （`ToolConcurrency.MAX_IN_FLIGHT_PER_CALLER`），`McpTool` 又在 `supplyAsync` 里并发跑。
- **后果**：线程 A 写完后让出，B 先 submit 自己的 `readLine`，读到 **A 的响应**。A 拿到 B 的结果，无任何报错。
- **次生问题**：`:58-60` 把空行判成"进程结束"；`AbstractMcpClient` 对"没有 `result` 的响应"返回空 `JsonObject`
  → 子进程往 stdout 打一行日志就被当成响应，`tools/list` "成功返回 0 个工具"。
- **修法**：`write + read` 在一把 per-client 锁内做成原子 exchange；按 `id` 匹配，丢弃 `notifications/*`，
  不匹配的 `id` 判传输失败。补测试 `TS-2`。
- **验证**：✅
- **状态**：[ ] 未修

### P0-4 ✅ MCP 工具失败被平台包成 `ok:true`，模型眼里是成功

- **修法**：失败走 `CompletableFuture.failedFuture(new ToolException(ToolError.FAILED, ...))`，不自造嵌套错误对象。
  补测试 `TS-3`。
- **验证**：✅

### P0-5 ✅ `claimPrimary()` 把正在运行的 permit 当"上次遗留"清掉 → native 双载

- **级别**：P0 —— 该类注释里自述曾把进程 OOM 死
- **位置**：`tianshu-api/.../model/NativeModelLoadQueue.java:146-153`
- **现象**：`active` 一个字段同时承载"permit 已授予某次正在运行的加载"与"遗留 permit"，`claimPrimary()`

### P0-6 ✅ 配置读失败被当成"文件不存在"，下一次保存用默认值整份覆盖

### 维度（跨维度）事实核对 — 2026-11-15

> 起因：作者确认"涉及跨维度的操作，原设计是拒绝"。核对结果：**拒绝设计完好，本批一行未动**。

**拒绝发生在适配器层，五处硬拒绝 + 一处隐式：**

| 位置 | 拒绝文案 |
|---|---|
| `AgentMotionSource.java:76-77`（同步 move） | `this body cannot change dimension` |
| `AgentMotionSource.java:93-94`（异步 move） | `this body cannot change dimension` |
| `AgentMotionSource.java:178-179`（look） | `the target is in another dimension` |
| `AgentActionSource.java:74-76`（mine / attack） | `the target is in another dimension` |
| `AgentItemUseSource.java:83`（item use） | `the target is in another dimension` |
| `ContainerTransferSource`（`hasChunkAt` 判定） | `that chunk is not loaded`（隐式拒绝） |

**工具层从不给调用方选维度的机会**：`body.move` / `body.look` / `body.mine` / `item.use` 一律取
`body.position().dimension()`；`body.follow` 取**目标**自身的维度；`body.collect` 取扫描命中的维度。
**唯一例外是 `body.sequence`**：它在解析时取一次维度（`BodySequenceTool.java:162-163`）并用于全部步骤。

**因此 `BDY-8` 的真实性质**：不是"允许了跨维度"，而是**坐标过期**。序列执行中途身体被传送换维度时，
后续步骤仍带旧维度 → 被适配器拒成 "the target is in another dimension" / "this body cannot change
dimension"，读起来像智能体在尝试跨维度操作，实际是它拿的是过期坐标。

**需要你定的语义**（三种收法，互斥）：

1. **中止并报告**（推荐）：检出维度变化即停止，返回 `failedIndex` 与"身体在第 N 步改变了维度"。
   与"拒绝跨维度"一致，且**不会**静默作用到另一组方块上。
2. **重新定向到新维度**：每步取当前维度 → 同坐标在新维度生效，语义变了（可能挖到完全不同的东西）。
3. **维持现状**：继续冻结。

### 更正（第 10 轮）：三项架构门禁一直是空转

> **这不是新发现的缺陷，而是对前几批"门禁全绿"证据的更正。**

`verifyFeatureIsolation`、`verifyFeatureOptionalDependencies`、`verifyHostHasNoFeatureDependency`
三处都把模块路径写死成 `core/<module>/...`，而当前工作区把模块放在 `../Tianshu-features` 与 `../Tianshu-ferry`

即使路径正确，`inputs.files(目录)` 交给 `doLast` 的也只是那个目录本身（`getFiles()` 不展开目录），
配合 `path.endsWith(".java")` 的过滤，扫描循环同样看不到任何文件。

而第十三批之前的记录把它们的"全绿"当作证据。第十三批把三处一起修好（`moduleDir` 经 `include` 的项目解析、
文件列表改成扁平的 `fileTree(...).files`、匹配改成包前缀），并做了变异验证：在 `tianshu-presence` 里加一条指向
`auxilium` 的引用、在 `tianshu-api` 里加一条指向 `intake` 的引用，两处都能被对应门禁报出并 fail。

### 14-3 ✅ 已解决：`BDY-2` 跟随的超时语义（第十五批）

工具超时后身体还在走（`BodyFollowTool` 的 tick 继续排下一跳，release 挂在派生 future 上）。
两种收法：**① 超时即主动完成 result 并 release**（模型收到 TIMEOUT 时身体已停，代价是可能停在半路）；
**② 继续走完**，只把工具调用判超时（代价是期间任何 `body.*` 都 BUSY 5 分钟）。我倾向 ①。

### 14-4 ✅ 已解决：`BDY-5` 幂等键（第十七批，且查证后无需抬协议版本）

服务端的 120s 重放窗口只吃 `callerId|requestId`，而客户端每次重试都是新 UUID → 模型对超时的 `block.place`
重试会**真的写两次世界**。要真正解决需要把 `idempotencyKey` 放进请求并回传，这会**抬 `ProtocolWireVersion`**。
需要定：是否接受一次协议版本变更（以及是否要求 43 个 adapter 分支同步）。

### 14-5 ✅ 已解决：`BDY-13` 的落地口径

> **第十二批已按 `DEC-2` 实现**：本节提的两个小问题（`args.body` 是否必填、`BODY` 指别的 body 怎么处理）其实是 `DEC-2`
> 自己已经回答过的，实现时不需要再定——`AGENT` 必填 `args.body`（缺就 `INVALID_ARGS`），`BODY` 指别人就 `INVALID_ARGS`。

`DEC-2` 已定"智能体能驱动身体，且必须显式传 `body`"。落地时还要确认两件小事：
**① `args.body` 对 `AGENT` 调用方是否必填**（缺省时是否回落到"该会话正在驱动的身体"）；
**② `BODY` 调用方传了不同 `bodyId` 时**，报 `INVALID_ARGS` 还是允许（`DEC-2` 说报错，但需要确认这不会打断现在
天枢的调用方式）。

### 14-6 ✅ 已解决：`LIF-8` 跨模块保存（第十五批，取"如实记录已保存模块"）

`saveAll` 现在逐会话提交，第 2 个模块失败时第 1 个已落盘、UI 却报"保存失败"。两条路：
**① 两阶段提交**（全部 stage → 一次 persist，失败全回滚，代价是要给每个模块的 store 加 stage 能力）；
**② 保持现状但把失败消息改成"已保存 A、C，未保存 B"**（代价小，但用户仍可能只补存一个）。
我倾向 ①，但这是一次结构性改动，需要你确认投入。

### 14-7 ✅ 已解决：`LIF-14` 的 `ModuleSettingsSessionBuilder`

> **第十二批按选项 ① 实现**：`persist` 变成必填，`build()` 无 persist 即抛错，`save()` 走 `SettingsSaveTransaction`
> 并在持久化失败时回滚。取证后不需要决策——全仓 6 个功能模组都自己实现了 `ModuleSettingsSession`，没有一个用它。

它生成的会话 `save()` **没有任何持久化钩子**却返回"已保存"，全仓只有测试在用。需要定：
**① 加 `persist(Runnable)` 并强制走 `SettingsSaveTransaction`**（无 persist 时 `build()` 抛错）；
**② 直接删掉这条 API**（如果确认没有模组计划用它）。

### 14-8 ✅ 已解决：`MDL-1` 校验时机（第十五批，改为在 `.downloading` 上校验并重试）

现在 sha256/size 校验发生在**原子 rename 之后**（文件已经在最终模型路径上），且校验失败不进重试循环。
正确做法是"在 `.downloading` 阶段校验、通过后再 `moveIntoPlace`、校验失败当作可重试的传输失败"——
代价是**校验失败要重下几个 GB**。需要确认：是否接受这个流量成本，还是要保留"先落位再校验"以换取断点续传。

### 14-9 ✅ 已解决：`MDL-3` 镜像缓存（第十五批，取"会话内记住"）

回退成功过的镜像**不被记住**，下一个文件重新探测；在"API 可达但文件 CDN 被墙"的网络上，每个文件先跑满
`maxRetries × 120s` 才轮到镜像（TTS 一个模型十几个 ONNX，装一次几十分钟到小时）。修法可以是
**① 只在本次会话内记住**（内存，重启失效）；**② 写进配置文件**（跨会话，但要在设置页暴露一个"主机"字段，
属于产品界面变动）。需要定 ①还是②。

### 14-10 `MDL-5` 删除与下载的互斥

删除与下载之间没有平台级互斥，只由各模块用两个非原子布尔值互相探测，且 ASR 完全没查。
两种收法：**① 按 `modelId` 的共享"模型操作"状态**（下载/删除/加载同域，谁先占位谁赢）；
**② 单方拒绝**（删除时若在下载就拒绝删除，下载时若在删除就拒绝下载）。
①更彻底但要动三个模块；②改动小但用户体验是"稍后再试"。

### 14-11 `CLN-10` 与 `PRT-15` 的取舍

- ~~`CLN-9`~~：**第十三批已修**（见 §13 的更正），改完没有暴露现存违规——这三条不变量本来就成立，只是此前没被检查。
- `CLN-10`：76/440 个测试文件靠 `Files.readString` 读源码断言子串，重命名变量即误报。迁到行为断言是正确方向，
  但会动一批测试文件，需要你同意"这段时间红一批测试是正常的"。
- `PRT-15`：本轮取"如实注明"。如果你更希望**删字段**（单一事实来源），要改 40 处 `new ModuleDescriptor(...)`，
  横跨两个 worktree——请明确要不要现在做。

### 14-12 ✅ 已解决：`CAP-5` 剩余的一半（目录推送异步化）

> **第十二批已实现**：查了两个 adapter 的 `sendCatalog`，它们都自己 `server.execute(...)` 跳线程，所以从任意线程推送
> 都安全；变更驱动推送已移到守护线程并按突发合并。原来的顾虑（"推在错误线程上"）不成立。

`broadcast` 的成本已经从"玩家数 × 全表"降到"2 × 全表"，但仍在**写入方线程同步发出**。
异步化（合并突发变更 + 后台线程推送）需要先确认 adapter 的 `ToolCatalogPush` 是否自己跳服务端线程；
如果不跳，异步化会引入"在错误线程发包"的新问题。需要你确认 adapter 侧的线程契约，或授权我直接改 adapter。

## 15. 本轮新增的盲区

见 §12 的原有四条。**最重要的一条**：前三批把 `verifyFeatureIsolation` / `verifyFeatureOptionalDependencies` /
`verifyHostHasNoFeatureDependency` 的"全绿"当成了证据，而它们其实没有输入、在空转（见 §13 的更正）。
教训写在这里：**一个门禁"通过"只有在能证明它会失败时才算数**。第十三、十四批把 12 个 `verify*` 全部验过：
4 个原本什么都没检查（`verifyFeatureIsolation`、`verifyFeatureOptionalDependencies`、
`verifyHostHasNoFeatureDependency`、`verifyProtocolVersionSingleSource`），4 个缺空集断言，
现在都有真实输入、空集即 fail；其中 `verifyFeatureIsolation`、`verifyHostHasNoFeatureDependency`、
`verifyNoPlatformImport`、`verifyProtocolVersionSingleSource` 做过变异验证，其余 8 个仍只有"输入非空"这一层保证。

另一条边界（第 10 轮发现）：`./gradlew check` 会带上功能模组的测试，而 `tianshu-intake` 的
`IaModuleProtocolFlowTest` 有 2~3 个**既有失败**（`await` 超时，且失败集合在两次运行间会变，属抖动）。
用 `git stash` 把舟楫的改动全部退回到 `90daf715` 再跑同一类测试，**同样失败**——所以它与本轮的修改无关。
`tianshu-ferry` 的验证因此一直用"三个模块的 test + 两个 adapter compileJava + 门禁"这一组，
没有把功能模组的测试算进来。

本轮新增的边界：`McpBridge` 的每服务器锁、`ProtocolExecutorManager` 的槽位记账、
`CapabilityCatalog` 的处理器线程池都**没有并发压测**；`BodyTargets` 的越界拒绝只在校验层验证过，
未在实机上确认"世界边界 30,000,000"与自定义维度是否冲突。

## 17. 验收台（`tianshu-lab` 内，2026-11-15 第 18 轮）

> 结论：**验收由我们自己在 lab 里跑，不依赖第三方插件。** lab 早就随开发运行装入（`devRunFeatureEdges`
> 的 `root: [lab]`），本轮给它加的是"验收"这一层概念。

### 17.1 形状

`function/lab/acceptance/`：`AcceptanceCase`（id / 标题 / run）、`AcceptanceOutcome`（PASS / FAIL / SKIP）、
`AcceptanceRunner`（逐条隔离，抛异常与"返回 null"都记成 FAIL）、`AcceptanceReport`（表格 + JSON + 未覆盖清单）、
`LabAcceptanceCases`（用例集）。`LabAcceptance` 负责在工作线程上跑、发一条 `acceptance.run` 诊断事件、
把 JSON 写到 `tianshu-lab/acceptance-<时间戳>.json`。

入口两个：设置 →【听澜】仲裁测试台 →「运行平台验收」（需先开该页的调试开关）；
或无头触发 `runClient -PtianshuLabAcceptance=1`（等工具表填满后自动跑一次，见 §17.6）。

### 17.2 三条硬规矩

1. **用例 id 与本文编号同源**，报告里的名字能在本文查到对应的断言。
2. **跑不了的显式 SKIP 并写原因**；`AcceptanceReport.uncovered()` 每次运行都把 6 类未覆盖项连同"由谁覆盖"一起印在报告尾部，不许静默消失。
3. **验收台必须能证明自己会失败**：内置 `SELF-CHECK-1`，它**必须 FAIL**；一旦它 PASS，`accepted=false`，整轮作废。
   同一套逻辑有单测钉住（`AcceptanceRunnerTest`，9 例）。

### 17.3 覆盖与不覆盖

覆盖（**31 条 + 1 条自检**，按 6 个对外面分组，分组本身在报告里打印）：

- 工具注册与调用（5）：`ACC-EXP-1` 两视角一致、`ACC-EXP-2` 关闭的工具仍列出且回 `DISABLED`、`ACC-EXP-3` FULL 档工具对保守档不可见、
  `ACC-EXP-8` 放宽档位只增不减、`ACC-EXP-9` 连读两次表不变；
- 工具参数契约（3）：`ACC-ARG-1` 严格 schema 拒绝未声明字段并点名、`ACC-ARG-2` 未知 id 与工具 id 两种拒绝不混、
  `ACC-ARG-3` 每个已发布 schema 都声明了严格性；
- 能力表（14）：`ACC-CAT-1` revision 与监听器、`ACC-CAT-2` 旧快照保留自己的行、`ACC-CAT-3` 开关工具到达监听器、

所以报告里把它单独列成一条"不属舟楫契约"的未覆盖项，而不是算在舟楫的能力缺口里。

### 17.6 实机首跑（2026-11-15，1.21.1-neoforge）

无头触发：`runClient -PtianshuLabAcceptance=1` → `LabModule.start` 等工具表填满后自动跑一次，
报告写 `run/tianshu-lab/acceptance-<ts>.json`，同时发一条 `acceptance.run` 诊断事件到
`run/logs/tianshu-diagnostics.log`（两处证据同源）。

**结果**：15 条 = **12 通过 / 1 跳过 / 2 失败**（其中 1 条失败是 `SELF-CHECK-1`，即自检按设计变红）。
`ACC-CAP-1` 实测 `TIMEOUT after 5001 ms`——5 秒预算在真实客户端上是真的。

**首跑抓到的真问题（`ACC-ARG-1`）**：给 `capability.read` 传一个未声明的字段 `bogus`，
**平台接受了并正常返回**（`ok:true`）。根因：`ToolArgumentValidator` 只在 schema 声明了
`additionalProperties: false` 时才拒绝未声明字段，而 `capability.read` 的 schema 没有声明。

**已修（第 18 轮，取"严格"）**：校验改为**默认严格**——对象 schema 没写 `additionalProperties` 即按拒绝未声明字段处理，
想收自由参数的工具显式写 `additionalProperties: true`；同时 `CapabilityCatalog.publishTool` 发布 schema 时把这条
严格性补出来，模型看到的文档与真正执行的检查不再各说一套。新增 `ACC-ARG-3` 扫全表锁住这条规则（**不调用任何工具**，
只读 schema，因此对写工具也安全）。

**`ACC-EXP-4` 已改成两态可判**：原写法在开发客户端恒跳过（`serverAvailable()` 一启动即为真），
等于一条永远不产生信息的绿灯。现在断言"服务端行出现在客户端视野 ⟺ 服务端通道可用"，两个状态下都能判。

**复跑（同机同版本）**：16 条 = **15 通过 + 1 条自检按设计变红**，`accepted=true`、`selfCheckHeld=true`；
`ACC-EXP-4` 顺带报出"通道可用、服务端行 22 条"，`ACC-ARG-3` 报出"25 个 schema 全部声明了严格性"。

**再复跑（铺满后）**：28 条 = **27 通过 + 1 条自检变红**，`accepted=true`。

**终轮（34 条 + 自检 = 35）**：**33 通过 + 1 条 SKIP + 自检变红**，`accepted=true`。
新增的 `ACC-PRT-1`（模块执行通道）与 `ACC-BDY-1`（15 个 `body.*` 的注册与参数契约）实机绿。

两条实机才暴露的事实，记在这里免得下次重新发现：

- **写类 `body.*` 默认关闭**：直接调用得 `DISABLED`。`ACC-BDY-2` 因此要临时开启工具、调用、再还原。
- **所有带方块的 `body.*` 都要求 operator 权限**：模块作用域调用方即使把 `operator` 声明为真也拿不到
  （回 `NO_PERMISSION`），所以它的坐标校验从模块作用域**不可达**。`ACC-BDY-2` 对此如实 SKIP，
  原因写在报告里——这比"假装验过"重要。

**世界轮（38 条 + 自检 = 39）**：`runClient "-PquickPlayWorld=New World" -PtianshuLabAcceptance=world`
→ **37 通过 + 1 SKIP + 自检变红**，`accepted=true`。
自动运行会先等工具表填满、再等世界与玩家就绪（最多 180 秒），所以世界类用例这次真的跑起来了：
`ACC-GAME-1` 报出「有玩家、11 项采集齐全」、`ACC-GAME-2` 报出「11 项采集都不抛」。

**下载校验两条夹具**（`ACC-MDL-1/2`）用**进程内 loopback HTTP 服务器** + 环境桩跑，
没有依赖 `tianshu-testkit`（那是测试专用产物，开发运行里根本没有它，用了只会在运行期 `NoClassDefFound`），
所以 lab 只加了 `tianshu-core` 的 `compileClasspath`，不进任何 jar。

**身体归属（第 19 轮尝试，结论：需要你定）**：按"AI 有自己的实体"这条设计，验收台试着**自己注册一个内存身体**
（`AgentBodies.register` + `BodyAccess.OWNER`），再以所有者身份调 `body.look`。结果两种调用方都被挡：

```
{"ok":false,"code":"NO_PERMISSION","message":"tool tianshu:body.look needs an operator"}
```

- 调用方写成 `ToolCaller.player("lab", true)`（自报 operator）→ 挡。
- 调用方写成 `ToolCaller.body(bodyId, true)`（身体身份 + operator）→ 同样挡。

也就是说 **`body.*` 的 operator 门不接受"合成调用方"的自报**。这本身是正确的防护（`DEC-9` 的硬约束：
`ToolCaller.autonomy` 永不是授权依据），代价是**验收台无法验证身体的正面动作**。

因此当前如实记为：`ACC-BDY-4` 锁住"没有 operator standing 的调用方永远碰不到身体端口"（PASS），
`ACC-BDY-2`/`ACC-BDY-3` 对正面路径**如实 SKIP** 并写明原因。
要真正验身体动作，只有给开发运行一个**可被平台认可的 operator 通道**（dev-only），否则归实机人工验收。
此后又加了 3 条（`ACC-CAT-4` 重复注册被拒、`ACC-EXP-10` 失败信封无正文、`ACC-DIAG-4` 缺 severity 被拒）
与报告里的"覆盖分组"输出——**这 3 条与覆盖分组尚未实机跑过**，只过了编译与 23 个单测；
实机绿的最新证据是 28 条那一轮。

### 17.7 覆盖声明也进报告

`AcceptanceReport.coveredAreas()` 把"这台东西覆盖了哪几个对外面、各由哪些用例负责"作为**报告的一部分**打印，
并与 `uncovered()` 并排。两条不变量有单测钉住：声明里点到的用例必须真实存在（`everyCoverageClaimNamesARealCase`）、
每条用例必须被恰好一个面对应（`everyCaseIsClaimedExactlyOnce`）——否则"覆盖面"这个词会自己膨胀。

### 17.5 它到底覆盖了多少（初版）

**18 个对外契约单元里，验收台覆盖 5 个**（工具注册与调用、能力表、智能体门面、诊断、设置）；其余 10 个由单测或门禁覆盖，
2 个完全没有自动化（HUD、服务端动作六件事），1 个明确不验（音频，归模块）。
逐行清单见 [舟楫对外契约与覆盖矩阵](../history/舟楫对外契约与覆盖矩阵.md)；那张表是后续补用例的唯一依据，
不再凭印象挑条目。
