### P0-3 ✅ MCP stdio 的请求与响应不配对，并发调用会互拿对方的结果

- **级别**：P0 —— 静默返回错误数据，比报错恶劣
- **位置**：`tianshu-client/.../capability/mcp/McpStdioClient.java:46-48`
- **现象**：`exchange()` 里 `write(request)` 与 `reads.submit(in::readLine)` 是两步，中间没有锁；
  `write()` 内部的 `synchronized (out)` 只保护写。响应也**不按 JSON-RPC `id` 校验**。
- **触发**：同一台 stdio 服务器上两个并发 `tools/call`。平台允许同一 caller 8 个在飞

- **修法**：`write + read` 在一把 per-client 锁内做成原子 exchange；按 `id` 匹配，丢弃 `notifications/*`，
  不匹配的 `id` 判传输失败。补测试 `TS-2`。

### P0-5 ✅ `claimPrimary()` 把正在运行的 permit 当"上次遗留"清掉 → native 双载

- **级别**：P0 —— 该类注释里自述曾把进程 OOM 死
- **位置**：`tianshu-api/.../model/NativeModelLoadQueue.java:146-153`
- **现象**：`active` 一个字段同时承载"permit 已授予某次正在运行的加载"与"遗留 permit"，`claimPrimary()`
  只看 `active.tier == PRIMARY` 就 `active = null`，无法区分两者。
- **触发链**：`LlmModule.java:231`（每次进世界调 `claimPrimary`）；`LlmModule.stop():260` 只调
  `abandonQueuedLoad()`，不取消在跑的加载（`engineProvider.stop()` 只在 `destroy()` 里）。
  玩家**快速退世界再进** → 旧世界的 embedding load 还在 native 里跑 → 新会话的 claim 把 permit 清掉 →
  新请求看到 `active == null` → `GRANTED` → **两个 native 模型峰值相加**。
  旧 load 事后 `release()` 因 owner 检查（`:243`）变成 no-op，permit 归属彻底丢失。
- **讽刺点**：`:256-261` 的注释已经记下这个教训（"Clearing it here ... let the next session start a second
  native load while the first one was still running"），`claimPrimary` 仍在做同一件事。
  `:142-144` 的 javadoc 防错了方向（它在论证不能清 DEFERRED/LAST，而危险的是清运行中的 PRIMARY）。
- **修法**：把"已授予"与"遗留"拆成两个状态（记录 owner + 授予时间戳/尝试代数），或要求遗留清理只能由
  明确未授予的那次尝试调用。补测试 `TS-4`。
- **验证**：✅
- **状态**：[ ] 未修

### P0-6 ✅ 配置读失败被当成"文件不存在"，下一次保存用默认值整份覆盖

- **级别**：P0 —— 玩家数据永久丢失且不可恢复
- **位置**：`tianshu-core/.../core/config/PropertyModuleConfigStore.java:169-187`（`loadOnce`）、`:134`（备份分支）
- **现象**：只有 `IllegalArgumentException`（畸形 `\uXXXX`）会置 `corrupt = true`，而 `save()` 里唯一会
  **先备份原文件**的分支正是 `if (corrupt && Files.isRegularFile(file))`。`catch (IOException)` 只记一行日志。
  另外 `loaded = true` 在读之前就置位，本次会话不会重试。
- **触发**：Windows 上杀软/索引器占句柄、ACL 变化、共享盘抖动。`Files.isRegularFile` 读不了时也返回 false，
  于是连读取都不会尝试。
- **后果**：`values` 为空、`corrupt` 仍 false → 玩家改**任意一项**设置触发 `save()` → 临时文件写完直接
  `ATOMIC_MOVE` 覆盖 → **该模块全部键（含 API key、prompt、音色、模型路径）永久丢失**。
- **讽刺点**：这个文件其它设计极讲究（唯一临时名、原子移动、损坏文件保留为 `.corrupt`、失败抛
  `UncheckedIOException` 好让事务回滚）——**偏偏把"损坏"和"读不了"分成两类，只保护了前者**。
- **修法**：区分 ENOENT（可当无文件）与其它 `IOException`（置 `corrupt = true`，或让 `save()` 拒绝覆盖并上报失败）。
  约 5 行。补测试 `TS-6`。
- **验证**：✅
- **状态**：[ ] 未修

### 维度（跨维度）事实核对 — 2026-11-15

> 起因：作者确认"涉及跨维度的操作，原设计是拒绝"。核对结果：**拒绝设计完好，本批一行未动**。

**拒绝发生在适配器层，五处硬拒绝 + 一处隐式：**

| 位置 | 拒绝文案 |
|---|---|
| `AgentMotionSource.java:76-77`（同步 move） | `this body cannot change dimension` |
| `AgentMotionSource.java:93-94`（异步 move） | `this body cannot change dimension` |
| `AgentMotionSource.java:178-179`（look） | `the target is in another dimension` |
| `AgentActionSource.java:74-76`（mine / attack） | `the target is in another dimension` |
| `AgentItemUseSource.java:83`（item use） | `the target is in another dimension` |
| `ContainerTransferSource`（`hasChunkAt` 判定） | `that chunk is not loaded`（隐式拒绝） |

**工具层从不给调用方选维度的机会**：`body.move` / `body.look` / `body.mine` / `item.use` 一律取
`body.position().dimension()`；`body.follow` 取**目标**自身的维度；`body.collect` 取扫描命中的维度。
**唯一例外是 `body.sequence`**：它在解析时取一次维度（`BodySequenceTool.java:162-163`）并用于全部步骤。

**因此 `BDY-8` 的真实性质**：不是"允许了跨维度"，而是**坐标过期**。序列执行中途身体被传送换维度时，
后续步骤仍带旧维度 → 被适配器拒成 "the target is in another dimension" / "this body cannot change
dimension"，读起来像智能体在尝试跨维度操作，实际是它拿的是过期坐标。

**需要你定的语义**（三种收法，互斥）：

1. **中止并报告**（推荐）：检出维度变化即停止，返回 `failedIndex` 与"身体在第 N 步改变了维度"。
   与"拒绝跨维度"一致，且**不会**静默作用到另一组方块上。
2. **重新定向到新维度**：每步取当前维度 → 同坐标在新维度生效，语义变了（可能挖到完全不同的东西）。
3. **维持现状**：继续冻结。
