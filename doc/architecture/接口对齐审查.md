# 接口对齐审查：以 1.21.1-neoforge 为基线

审查日期：2026-11-02。基线：`tianshu-adapter/1.21-1.21.1-neoforge`（产品最初对接的版本，也是事实产出最全的一套）。
判定"这一版确实拿不到"必须有证据：要么游戏/加载器没有该钩子，要么该钩子在该版本实际解析到的依赖里不存在——用 jar 反查（`javap`），不靠印象。

## 1. 结论先写

1. **版本扩展没有造成能力退化。** 客户端 12 个 `ClientGameContextPort` 方法在全部 13 棵共享树上都有真实实现；事实产出在同一加载器内部完全一致（21 个 NeoForge 包彼此相同，22 个 Fabric 包彼此相同）。差异只在**加载器**这一维，与 Minecraft 版本无关。
2. **事实有两条通道，不能混着比。** NeoForge 侧有一半"事实"是**客户端本地**发布的（`NeoForgeClientFactWatch` 与 `NeoForgeBossEventWatch`），另一半才是服务端收集器（`GameFactCollector`）。Fabric 侧同样的分工是 `FabricClientFactWatch` 与 `FabricGameFactCollector`。
3. 按通道算，Fabric 比 NeoForge 少 **14 类**：客户端本地少 3 类（`DIMENSION_CHANGED`、`RESPAWN`、`BOSS_ENGAGE`），服务端少 11 类。其中 5 类有现成 Fabric 原生钩子可以补，9 类在 fabric-api 里没有钩子。
4. 另有 **2 个常量两个加载器都没产出**：`EVENT_ADVANCEMENT_UNLOCKED`、`EVENT_CHAT_MESSAGE`。这需要单独确认是刻意留白还是遗漏。

## 2. 实测矩阵（按通道）

### 2.1 客户端本地事实

| 事实 | NeoForge（21 个包） | Fabric（22 个包） |
|---|---|---|
| `EVENT_CONTAINER_OPEN` | `NeoForgeClientFactWatch`（`ScreenEvent.Opening`，容器界面） | `FabricClientFactWatch` |
| `EVENT_DIMENSION_CHANGED` | `NeoForgeClientFactWatch`（关卡加载） | **缺** |
| `EVENT_RESPAWN` | `NeoForgeClientFactWatch`（`ClientPlayerNetworkEvent.Clone`） | **缺** |
| `EVENT_BOSS_ENGAGE` | `NeoForgeBossEventWatch`（`BossEvent`） | **缺** |

### 2.2 服务端事实

| 加载器 | 种类 | 集合 |
|---|---|---|
| NeoForge（21 个包） | 17 | `BLOCK_BROKEN` `BLOCK_PLACED` `DAMAGE_TAKEN` `DISMOUNT` `EFFECT_EXPIRED` `EFFECT_GAINED` `EXP_LEVEL` `FISHING_CATCH` `FRIEND_JOIN` `FRIEND_LEAVE` `ITEM_CRAFTED` `ITEM_PICKUP` `MOB_KILLED` `MOUNT` `PLAYER_DEATH` `TAMED` `TRADE` |
| Fabric（22 个包） | 6 | `BLOCK_BROKEN` `DAMAGE_TAKEN` `FRIEND_JOIN` `FRIEND_LEAVE` `MOB_KILLED` `PLAYER_DEATH` |

Fabric 侧缺的 11 类正是 `ServerFactCoverageTest` 里 `ABSENT` 列出的那 11 个，两处一致——也就是说服务端缺口是**登记过的**，客户端 3 类则是**没登记的空白**。

## 3. 缺口逐条定级

证据：每个 Fabric 线实际解析到的 `fabric-api` 版本 → 对应模块 jar → `javap` 看类与成员是否存在。

### 3.1 客户端本地缺的 3 类

| 事实 | Fabric 原生手段 | 版本线 | 定级 |
|---|---|---|---|
| `EVENT_DIMENSION_CHANGED` | `ClientWorldEvents.AFTER_CLIENT_WORLD_CHANGE`（1.21.1 实测存在）；26.x 该包改名，对应 `ClientLevelEvents` | 全线 | **可补（原生）**，26.x 需按线分叉类名 |
| `EVENT_RESPAWN` | `ClientEntityEvents.ENTITY_LOAD` / `ENTITY_UNLOAD`（1.21.1 与 26.3 都有）：本地玩家实体被卸载又加载即为重生 | 全线 | **可补（原生，启发式）** |
| `EVENT_BOSS_ENGAGE` | 无原生 BossBar 事件；客户端每 tick 读 `BossOverlay`/`Gui` 的 Boss 列表即可 | 全线 | 可补（轮询，成本低） |

### 3.2 服务端缺的 11 类

| 事实 | Fabric 原生钩子 | 定级 |
|---|---|---|
| `EVENT_EFFECT_GAINED` / `EVENT_EFFECT_EXPIRED` | `ServerMobEffectEvents`（`AFTER_ADD`/`AFTER_REMOVE`…），**仅 1.21.11 起**（entity-events 3.1.1+）；1.20–1.21.10 无此类 | 4 条线可补，其余需 mixin/轮询 |
| `EVENT_BLOCK_PLACED` | 无（`UseBlockCallback` 是右键交互；26.3 的 `BlockEvents` 只有 `USE_ITEM_ON`/`USE_WITHOUT_ITEM`） | mixin 或轮询 |
| `EVENT_ITEM_PICKUP` | 无（26.3 `ItemEvents` 只有 `USE`/`USE_ON`） | mixin 或轮询 |
| `EVENT_ITEM_CRAFTED` | 无 | mixin 或轮询 |
| `EVENT_FISHING_CATCH` | 无 | mixin 或轮询 |
| `EVENT_TAMED` | 无 | mixin 或轮询 |
| `EVENT_TRADE` | 无 | mixin 或轮询 |
| `EVENT_MOUNT` / `EVENT_DISMOUNT` | 无 | mixin 或轮询 |
| `EVENT_EXP_LEVEL` | 无 | **轮询**（每 tick 比等级，零风险） |

"需 mixin 或轮询"是实现代价问题，不是产品取舍问题：数据在服务端本来就拿得到（背包、等级、BossBar、驯服/交易状态都能读），只是 fabric-api 没替我们挂好钩子。

## 4. 语义差（接口在，拿到的东西不一样）

| 事实 | 差异 | 证据 |
|---|---|---|
| `EVENT_DAMAGE_TAKEN` | 1.21 线只有 `ALLOW_DAMAGE`（结算前、可否决），记的是**入射伤害**；1.21.1 起是 `AFTER_DAMAGE`，可拿实际落地伤害 | `ServerLivingEntityEvents`：1.6.12 只有 `ALLOW_DAMAGE`/`AFTER_DEATH`，1.8.0 起才有 `AFTER_DAMAGE` |

## 5. 两个"两边都没产出"的常量：确认是遗漏（2026-11-02 用户确认）

设计意图（映迹时期）就是"玩家获得成就"与"玩家聊天"各发一个世界事件，所以这两类不是刻意留白，是漏了。事实键也早就在 `WorldEventTypes` 里备好：`VALUE_ADVANCEMENT_ID` / `VALUE_TITLE` / `VALUE_DESCRIPTION`、`VALUE_SENDER_NAME` / `VALUE_TEXT`。

| 常量 | 可用的原生钩子 | 结论 |
|---|---|---|
| `EVENT_CHAT_MESSAGE` | NeoForge `ServerChatEvent`（`getPlayer()` / `getRawText()` / `getMessage()`）；Fabric `ServerMessageEvents.CHAT_MESSAGE`（1.20 的 5.1.6、1.21.1 的 6.0.14、26.3 的 7.0.10 都有，签名 `onChatMessage(PlayerChatMessage, ServerPlayer, ChatType.Bound)`） | **两侧都能补，不需要 mixin** |
| `EVENT_ADVANCEMENT_UNLOCKED` | NeoForge `AdvancementEvent.AdvancementEarnEvent`（1.21.1 与 26.3 实测存在，`getAdvancement()` 给 `AdvancementHolder`；1.20.1 的 Forge 47 是 `net.minecraftforge` 同名事件） | NeoForge 可补；**Fabric 无原生钩子**——`AdvancementEvents` 只有 `REPLACE`/`MODIFY`/`ALL_LOADED`（数据包加载，不是"玩家获得"），需要 mixin 或客户端 toast 检测 |

## 6. 需要拍板的决策

1. **Fabric 侧是否允许 mixin？** 允许 → 11 类服务端事实可补齐，代价是每线一套 mixin（约等于现有 `ScreenWidgetMixin` 的 11 倍）；不允许 → Fabric 永远少这 11 类，必须在设置界面/文档里如实标注，不能静默。
2. **`EVENT_EXP_LEVEL` 用轮询还是 mixin？** 建议轮询（每 tick 一次整数比较）。
3. **第 5 节两个常量怎么处理？** 删掉常量（若确认不需要）或补产出（若需要）。

## 7. 建议实施顺序（尚未开始）

1. **Phase 1（原生 API，零/低风险）**：客户端本地 3 类——`DIMENSION_CHANGED`（全线，26.x 换类名）、`RESPAWN`（`ClientEntityEvents` 启发式）、`BOSS_ENGAGE`（轮询）。
2. **Phase 2（按线分叉）**：`ServerMobEffectEvents` 覆盖 1.21.11 + 26.1/26.2/26.3 的效果两类；`EXP_LEVEL` 轮询覆盖全线。
3. **Phase 3（待决策）**：其余 8 类，按第 6 节结论决定 mixin 还是登记为已知缺口。
4. 每补一类必须同步三处：收集器实现、该线 `ServerFactCoverageTest` 的期望集合、本文档第 3 节的表。

## 8. 本轮没有做的事

- 没有为 Fabric 补任何一类事实；本文档只做审查与定级。
- 没有改 `ServerFactCoverageTest`（等 Phase 1 一起按线分叉，避免 22 个包各改一次又对不齐）。
- 没有验证真机行为；本文档的"存在/不存在"全部来自依赖 jar 的字节码。

## 9. 决策记录：不做 mixin（2026-11-02 用户拍板）

结论：**第 3 层（mixin）全部放弃**，只做第 1 层（原生事件/回调）与第 2 层（每 tick 状态差分）。

因此以下 5 条在 Fabric 侧永久缺失，按"该版本确实拿不到"如实登记，不再视为待办：

| 事实 | 为什么只能 mixin | NeoForge 侧 |
|---|---|---|
| `EVENT_ITEM_CRAFTED` | fabric-api 无"制作完成"钩子 | 有原生 `PlayerEvent.ItemCraftedEvent`，保留 |
| `EVENT_FISHING_CATCH` | 无；轮询鱼钩状态不可靠 | 有原生 `ItemFishedEvent`，保留 |
| `EVENT_TAMED` | 无；轮询 owner 变化噪声大 | 有原生 `AnimalTameEvent`，保留 |
| `EVENT_TRADE` | 无；轮询商人界面不可靠 | 有原生 `TradeWithVillagerEvent`，保留 |
| `EVENT_ADVANCEMENT_UNLOCKED`（Fabric） | `AdvancementEvents` 只有数据包加载事件 | 有原生 `AdvancementEvent.AdvancementEarnEvent`，保留 |

保留并要补的（第 1、2 层）：

| 层 | 事实 | 范围 |
|---|---|---|
| 1 | `CHAT_MESSAGE` | 两侧全部包 |
| 1 | `ADVANCEMENT_UNLOCKED` | NeoForge 全部包 |
| 1 | `DIMENSION_CHANGED` | Fabric 全部包（26.x 用 `ClientLevelEvents`） |
| 1 | `RESPAWN` | Fabric 全部包（`ClientEntityEvents` 启发式） |
| 1 | `BLOCK_PLACED` | Fabric 全部包（`UseBlockCallback`） |
| 1 | `EFFECT_GAINED` / `EFFECT_EXPIRED` | Fabric 的 1.21.11、26.1、26.2、26.3 |
| 2 | `EXP_LEVEL`、`ITEM_PICKUP`、`MOUNT`、`DISMOUNT`、`BOSS_ENGAGE` | Fabric 全部包 |
