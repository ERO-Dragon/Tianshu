# 双端化实施方案：客户端必需、服务端可选

天枢原本是一个纯客户端模组。本方案把它改成"客户端必需、服务端可选"：客户端能力一条不变，装了服务端组件就多一类权威事实源，没装就退回到今天的能力。

## 1. 目标与边界

| 项 | 决定 |
|---|---|
| 客户端 | 必需。核心、模块、AX、映迹、语音全部照旧跑在客户端 |
| 服务端 | 可选。只做"采集事实 + 发给对应玩家"，**不装配核心、不装配模块** |
| 服务端组件职责 | 监听服务端事件 → 过滤 → 通过自定义 payload 发给该玩家客户端 |
| 不改的边界 | AX 仍然只读旁听、不改世界状态；服务端组件也只读事件、不回写世界 |
| 不做 | 客户端→服务端的反向通道（不需要）；服务端跑第二套运行时 |
| 安装形态 | 服务端只需要**内核 jar**（mod id `tianshu`，映迹随它一起走）；听澜 / 回响 / 织机 / 辅星四个特性 jar 仍然只装在客户端，服务端不需要也不应该装 |

**为什么服务端不装配核心**：核心装配需要客户端端口（`ClientPorts`）、语言表、音频桥。把这些搬上服务端，等于维护两套运行时和两套模块生命周期，收益只有"采集"，代价是双端分裂。采集是纯平台层的事，放在 adapter 里一小块就够。

## 5. 线上形状

**落点改了**：真正上线的类型放在平台层（`tianshu-adapter/.../network/GameFactBatchPacket`），不放 api。理由：这条通道是平台管线与协议协商的一部分，而 api 只放跨模块契约；接收端把它**立刻转成** api 的原始 `WorldEventPayload` 并发到 `GAME.WORLD_EVENT`，映迹订阅后聚合成 `PresenceWorldEventPayload`，下游消费者拿到的仍是既有形状，api 不必认识"网络包"这个概念。

```java
public record GameFactBatchPacket(List<GameFact> facts) implements CustomPacketPayload { }

public record GameFact(
        String factId,              // 与 PresenceWorldEventPayload.eventType 同一套词汇
        String dimensionId,
        long occurredAtMillis,
        Map<String, String> values  // 与 world event 的 values 同构
) { }
```

三条约束：

1. **单向**：只有 `playToClient`，没有客户端→服务端的载荷，客户端无法给自己伪造权威事实。
2. **版本**：registrar 的协议版本号参与握手（批量格式为 `2`）；发送前再查一次 `hasChannel`，客户端没装或版本不符时服务端直接不发。
3. **不开放**：这条通道只服务天枢自己；外部模组要服务端事实就自带通道（见接入指南）。

### 5.1 不携带来源

线上包和 `PresenceWorldEventPayload` 都**没有** source 字段，这是刻意的：客户端观测到的事实与服务端推来的事实在下游完全同形，消费者从不问"这条是哪来的"。想分辨来源只能靠发布点（平台各自的入口），不靠契约字段——给契约加一个来源，等于要求每个消费者都理解"来源"这个概念，而它不影响任何判定。

### 5.2 线上按 tick 批量，客户端逐条重放后按秒聚合

服务端在采集器里缓存本 tick 的事实，tick 末一次性 flush：一个 tick 的事实打成一个包（超过 `64` 条拆包），列表顺序就是生产顺序，每条保留自己的 `occurredAtMillis`。接收端在**同一个客户端任务**里按列表顺序逐条 publish，所以消费者看到的仍是单条事件，只是网络包变少了。

聚合仍只发生在映迹接收侧。`PresenceWorldEventPayload` 因此是"一个 kind 在 1 秒窗口里的全部发生"：`occurrences` 是分组列表（相同 `values` 发生 N 次合成一组），`totalCount()` 是总次数，`values()` 保留第一组以便旧的单条读法继续工作。

这意味着：**线上格式从"一条事实一个包"变成"一个 tick 一批"**，但事实的语义、时间戳和下游形状都没变——映迹不需要改，消费者也不用知道批量的存在。

## 6. 安全边界与限流

| 规则 | 理由 |
|---|---|
| 只发"与收件人本人相关"的事实 | 杀怪位置、容器内容、别人背包都是信息泄露 |
| 逐玩家过滤，不做全服广播 | 事件本身就要按 owner 投递 |
| 速率限制 | 归映迹（见 §6.1）：限流是接收方语义，服务端不做 |
| 服务端只发不收 | 客户端没有对应的上行包，杜绝伪造 |
| 客户端诊断只记 factId 与计数 | 正文与背包内容不进日志 |

**不发事件开关**：装没装服务端组件本身就是开关，不提供"是否转发事件"的配置项。

### 6.1 限流放在映迹里

服务端采集器保持"哑采集"：事件发生就发，不判断客户端此刻能消化多少。限流放在 `tianshu-client` 的映迹接收侧，原因有三条：

1. **接收方是唯一能看到全部事实的地方**：客户端自己观测的事实、服务端推来的事实、以后可能出现的第三方事实，都走同一个 `GAME.WORLD_EVENT` 入口（宿主发、映迹订）。限流只有放在这里才是一套策略，放到服务端就只是"服务端那一半"的策略。
2. **策略不重复**：如果两端各写一份，预算、窗口、丢弃语义迟早不一致；接收方那份才是玩家实际体验到的。
3. **预算属于产品**：每 tick 允许多少条、哪些 kind 单独定额，是映迹的产品参数，不是平台的连接参数。

代价要认：包仍然会过网络，限流只保护客户端的事件流与记忆，不省带宽。如果以后带宽真的成为问题，再在服务端加一个**连接层**的粗粒度上限（与语义无关的速率闸），那是另一件事，不替代这里的限流。

按 kind 定额而不是只设全局上限：全局额度会被方块/拾取的洪泛先吃掉，死亡这种稀有事件反而排不进去。每 kind 一个小额度，稀有事件就永远不会和洪泛事件抢同一个预算。

## 7. 降级路径

### 7.1 确定性原则

事件层只接受**确切事实**：有回调、有权威来源、"这件事确实发生过"。靠两次采样相减推出来的东西一律不做——算不准的事件比不报更糟，玩家没法验证，也不会相信。

三种确切来源：

| 来源 | 例子 | 前提 |
|---|---|---|
| 客户端回调 | 切换维度（level 重建）、进入世界/重生、界面与按键 | 只要客户端在 |
| 服务端配置事件 | 死亡、合成、拾取、方块、开容器、进度、驯服、交易、睡眠、上下坐骑、钓鱼、受伤数值、进食数值 | 服务端装了天枢 |
| 服务端权威判定 | 结构发现（`structureManager`） | 服务端装了天枢 |

**没有确切来源的一律删掉，不留差分兜底。** 已知会被删掉的：`biome_change`（两端都只能按坐标采样），以及客户端单跑时的 `health_change` / `health_critical` / `hunger_change` / `hunger_critical`（服务端才有受伤/进食的确切数值）。

### 7.2 环境行为

| 环境 | 行为 |
|---|---|
| 服务端未安装天枢 | 收不到包。只保留客户端回调那一档（维度切换、进入世界/重生）；其余事件静默，不做差分补偿 |
| 服务端版本不匹配 | 握手阶段就拒绝通道，收不到任何包；万一仍收到未知 `factId`（服务端比客户端新），协议层照常投递，AX 映射不到就作为记忆附件留下——不丢、不报错 |
| 单人（集成服务端） | 走同一条包路径，事件丰富度与双端一致 |
| 服务端装了但玩家没装客户端模组 | 服务端组件不发送任何东西（发送前查 `player.connection.hasChannel`） |

## 8. 验证

1. **单机**：`runClient` + 集成服务端 → 杀怪/合成/死亡各出一条历史 + 一条播报。
2. **双端**：新增 `runServer` + 连接一个 `runClient` → 同上。
3. **无服务端**：只跑客户端连一个原版服务端 → 退回今天的能力，不报错、不刷日志。
4. **边界**：`verifyServerSidePurity` **待补**（当前无此检查；补上之后服务端源集不得引用 `net.minecraft.client.*`）。

## 10. 明确不做

- 不在服务端装配核心、不跑模块生命周期。
- 不做客户端→服务端的上行通道。
- 不为"服务端事实"新造第二套判定：它们和内置事件走同一个 `AXGameEventService`。
- **不做差分推断**：没有确切来源就不产生事件（见 §7.1）。
- P1 完成后不再保留"AX 主动拉取事实"的路径。

## 11. 当前处境：按需扫描，不推送（P1，已更正为 pull）

**结论更正**：不做"映迹每 tick 维护最新快照并推送"。事实（事件）由事件驱动产生，**当前处境（背包、装备、效果、交互目标）只在被请求时扫描一次**。

### 11.1 为什么不推送

1. **扫描有成本**：背包、装备、效果、准星目标都是要遍历玩家状态才能算出来的，每 tick 扫一遍是纯浪费——它们绝大多数时候根本没变。
2. **推送会引进一整套复杂语义**：合并窗口、新鲜度、缓存过期、掉帧时的补发，全部要为"性能优化"服务，反而更重。
3. **现状已经是对的**：`PresenceContextQueryCoordinator` 在应答查询时现算快照，`PresenceEventCollector` 的注释也写明 "game context is read when a query is answered, so there is no per-input or per-screen state to keep warm"。这里不需要改。

### 11.2 唯一值得做的优化

同一 tick 内多个消费者（IA 仲裁、AX 装配、诊断面板）各自请求时，**共享一次扫描结果**：给查询应答加一个极短的复用窗口（同一 tick 内有效），或者干脆由协议层记住"本 tick 的应答"。

- 不引入过期语义、不发周期快照、不订阅 tick。
- 复用窗口一旦超过同一 tick 就失效，下一次请求重新扫描。

### 11.3 不做什么
