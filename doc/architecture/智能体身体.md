# 智能体身体（Actor 与能力）

> 状态：M1 已实现（Actor 收口与能力判定）；M2 已落地（两种载体、注册表、命令、craft/transfer/machine 的身体分支）；
> M3 已落地（动作/移动端口与五个身体工具）；A 已落地（动作玩家、`PLACE`、`USE`）；B 已落地（扫描与背包读取）；
> C 已落地（拾取与手持）。下一步是 walker 载体：真实寻路。

## 为什么需要 Actor

工具层原本只认一种行动者：玩家。`ToolCaller.PLAYER` 的 `id()` 就是玩家 UUID，服务端端口直接拿它去
`ServerPlayerList` 查玩家。智能体自己（`ToolCaller.AGENT`，id 恒为 `tianshu`）不在世界里，也没有 UUID，
于是所有会改变世界的工具都只能由玩家触发。

`ActorRef` 把"谁在行动"从一个 UUID 变成两种明确的身份：

```java
record ActorRef(String id, Kind kind, boolean operator)
enum Kind { PLAYER, BODY }
```

- `PLAYER`：id 是玩家 UUID，权限沿用玩家；
- `BODY`：id 是身体标识，权限由身体提供者决定。

平台只认 `ActorRef`，不再有"把 caller.id() 当玩家 UUID"的旁路。

## 身体不假设形态

身体**不等于玩家**，也不等于人形实体。它可能悬浮、没有血量、没有手、没有背包。平台因此只描述
"能做什么"，不描述"是什么"：

| 能力 | 含义 | 缺少它时 |
|---|---|---|
| `MOVE` | 改变自身位置，走/飞/传送都算 | 移动工具拒绝 |
| `LOOK` | 朝向世界中的一点 | 朝向工具拒绝 |
| `USE` | 对世界施加使用动作（按钮、容器、机器） | `block.interact` / `block.machine` 拒绝 |
| `MINE` | 破坏方块，用不用工具由适配器决定 | 挖掘工具拒绝 |
| `ATTACK` | 对实体施加效果，是否有伤害由适配器决定 | 攻击工具拒绝 |
| `INVENTORY` | 拥有可读写的物品栏 | 合成、容器转移拒绝 |

`AgentBody` 只有四件事：`id()`、`operator()`、`position()`、`capabilities()`。它不暴露实体类型、模型、
朝向轴、血量或背包；这些全部留在适配器里。

## 判定顺序与错误码

工具在调用端口之前统一判定一次：

```text
caller 不是 PLAYER/BODY        → NO_PERMISSION
BODY 但注册表里没有这个身体     → UNAVAILABLE
身体缺少该动作需要的能力        → UNSUPPORTED_ACTOR
能力具备但世界不允许            → REJECTED / FAILED（由端口返回）
```

`UNSUPPORTED_ACTOR` 是**拒绝**而不是失败：悬浮体没有手，不能挖掘是它的正常状态，不是故障。用一个独立的
错误码，智能体才能把"这个身体做不了"和"这次做失败了"分开表述。

## 端口与迁移桥

四个会改变世界的端口都提供两个入口：

```java
@Deprecated
CompletableFuture<X> op(String playerId, Request request);          // 适配器今天实现的方法

default CompletableFuture<X> op(ActorRef actor, Request request) {  // 新契约
    if (actor.kind() == PLAYER) return op(actor.id(), request);     // 玩家回落旧方法
    return failed(UNAVAILABLE);                                      // 身体尚未实现
}
```

这样平台可以先落地契约，43 个版本分支按需迁移，不需要一次全改。等所有分支都实现 `ActorRef` 版本后，
删掉旧方法和回落逻辑。迁移进度记录在 `doc/未完成事项.md`。

已迁移到 Actor 契约的端口：

- `BlockInteractPort`（`block.interact`）
- `ContainerTransferPort`（`container.transfer`）
- `CraftPort`（`craft.recipe`）
- `BlockMachinePort`（`block.machine`）

`InventoryQueryPort` 不在其中：它读的是**本地玩家**自己的背包，属于客户端能力，服务端身体不复用它。

## 动作端口（M3）

```java
AgentMotionPort.move(actor, target, options)   // WALK / FLY / TELEPORT / ANY
AgentMotionPort.look(actor, target)
AgentActionPort.mine(actor, blockTarget)
AgentActionPort.attack(actor, entityTarget)
```

- 结果用 `ActionOutcome`：`DONE` / `NO_EFFECT` / `REJECTED` / `FAILED`。`NO_EFFECT` 是合法结果——打了但没
  伤害、挖了但没破坏，都不是故障；
- 目标只用平台自己的坐标与实体 id，没有"手"、没有槽位、没有物品参数：用不用工具由载体决定；
- 1.21.1 的两个载体都只能**传送**，`WALK` / `FLY` 会被拒绝，而不是被悄悄当成传送。

## 身体工具（1.21.1）

| 工具 | 类目 | 需要的能力 | 说明 |
|---|---|---|---|
| `tianshu:body.list` | `SERVER_READ` | — | 列出身体：id、位置、能力。默认可用 |
| `tianshu:body.move` | `SERVER_WRITE` | `MOVE` | 传送到坐标；`mode` 可给 walk/fly/teleport/any |
| `tianshu:body.look` | `SERVER_WRITE` | `LOOK` | 朝向一个点 |
| `tianshu:body.mine` | `SERVER_WRITE` | `MINE` | 破坏一个方块 |
| `tianshu:body.attack` | `SERVER_WRITE` | `ATTACK` | 打一个实体；没伤害时返回 `NO_EFFECT` |
| `tianshu:block.place` | `SERVER_WRITE` | `PLACE` | 从背包里取一件物品放到坐标；朝向由 `face` 或身体方位决定 |
| `tianshu:block.interact` | `SERVER_WRITE` | `USE` | 按钮/拉杆/门/活板门/栅栏门；带 `body` 时按身体执行 |
| `tianshu:body.scan` | `SERVER_READ` | — | 扫描半径内的方块（按 id）与实体（按类型）；默认可用 |
| `tianshu:body.inventory` | `SERVER_READ` | — | 列出演员背包：槽位、物品 id、数量；默认可用 |
| `tianshu:body.pickup` | `SERVER_WRITE` | `INVENTORY` | 把附近的掉落物并入演员背包，返回实际拾取的条目 |
| `tianshu:body.equip` | `SERVER_WRITE` | `INVENTORY` | 选择身体的活动槽位（`-1` 清空）；后续攻击/破坏用它 |

身体写工具（`body.move/look/mine/attack/pickup/equip`）共用一个开关 `body_actions`；`block.place` 用独立的
`block_place`（NeoForge 配置 / Fabric `tools.properties`），都默认关闭。工具用
**显式身体 id** 指定身体，不靠会话绑定：服务端执行工具时会按真实玩家身份重建调用者，因此权限仍归玩家，
身体只是"被指挥的那具身体"。

`body` 参数在 schema 里是可选的：调用方运行时已经知道自己在指挥哪具身体，派发前填进去即可，模型不必重复
一个它没选过的 id；执行时仍然必须有值，缺了报 `INVALID_ARGS`。

`craft.recipe`、`container.transfer`、`block.machine`、`block.interact`、`block.place` 都接受可选的 `body`：带上就按那具身体的背包与位置执行，不带就是玩家自己。

`block.place` 与 `body.*` 共用 `body_actions` 之外的独立开关 `block_place`（两套 loader 各一项），默认关闭。

## 动作玩家（ActionContext）

放置与使用走原版玩家路径（`BlockItem.useOn` / `BlockState.useWithoutItem` 的签名都要求 `Player`），所以适配器
在调用期间造一个**动作玩家**。它不是身体的身份，只是 API 适配器：

1. **只在调用期存在**：`ActionContext` 打开时创建、`close()` 时丢弃；不进 `PlayerList`、不持有 chunk、不注册实体；
2. **状态是派生的**：位置、朝向、36 格背包从身体复制进去，`commit()` 把变化写回，动作玩家本身不留状态；
3. **能力门禁在它之前**：工具层先判定 `PLACE`/`USE`，不通过就 `UNSUPPORTED_ACTOR`，动作玩家根本不会被创建；
4. **属性取中性固定值**：生存、非创造、无经验，不从身体推断——身体没有玩家属性，不能假装有。

平台层完全看不到它：端口只收 `ActorRef`，动作玩家只存在于适配器的 `mc/body` 内。其他模组（保护插件、事件
监听）在一次调用期间会把它当玩家，这是预期的实现视角，验收时确认该行为可接受。

## 感知（B）

`tianshu:body.scan` 与 `tianshu:body.inventory` 都是 `SERVER_READ`、不需要能力、没有开关：

- **扫描必须给过滤条件**：`blocks`（方块 id）或 `entities`（实体类型 id），至少一个。没有"全都要"模式，
  避免一次调用把一整块立方体塞进对话；
- 半径与条数由适配器钳制（半径 ≤ 16、每类 ≤ 256），只读已加载区块，不生成新区块；
- 扫描结果不含演员自己；实体按 UUID、类型、维度与坐标返回，方块按 id、维度与坐标返回；
- 背包读取只列 36 个主槽位中的非空项，与 `container.transfer` 的槽位语义一致；
- 演员不存在时是 `UNAVAILABLE`，不是"空结果"——空结果意味着"看过了，什么都没有"。

## 手持与工具（C）

`body.equip` 只设置身体的活动槽位（`-1` 清空），状态存在注册表里，不改变世界：

- 攻击伤害 = 基础 1 点 + 装备物品主手的攻击力修饰符；
- 每次**成功**的攻击或破坏让装备物品扣 1 点耐久（载体是生物实体时）；
- **不建模挖掘速度**：破坏仍然是瞬时的，工具不改变破块时间。这是明确取舍——要模拟挥动时间，就得引入动作玩家的
  游戏模式与逐 tick 结算，成本远大于收益；如果以后要真实挖掘，再单独设计。

`body.equip` 只对 BODY 演员生效：玩家有自己的手，不需要"活动槽位"。

## 与智能体运行时的关系

`AXToolTurn` 目前固定用 `ToolCaller.agent(false)` 发起工具调用，因此智能体只能调用只读工具。身体接入后，
同一轮对话的调用者要变成 `ToolCaller.body(bodyId, operator)`，工具侧的判定与端口分发不需要再改。

这条绑定属于 M4；身体现在只能由 `/tianshu body` 命令创建，智能体运行时还不会自己要求一个身体。

## 1.21.1 的两种载体

适配器用两个刻意不同的原版实体证明"平台不假设人形"，都用 `/tianshu body spawn <kind>` 生成：

| 命令 | 载体 | 能力 | 能做什么 |
|---|---|---|---|
| `spawn marker` | `minecraft:marker` | `MOVE` `LOOK` | 世界里一个可定位、可移动的点：没有血量、没有碰撞、没有背包、没有手，也不能挖掘或攻击 |
| `spawn stand` | `minecraft:armor_stand`（无重力） | `MOVE` `LOOK` `USE` `PLACE` `MINE` `ATTACK` `INVENTORY` | 额外拥有 36 格背包：能破方块、能打实体、能放置、能开关门，`craft.recipe` 与 `container.transfer` 按它执行 |

`MINE` 与 `ATTACK` 走实体路径：`Level.destroyBlock(pos, drop, entity)` 和 `DamageSources.mobAttack(entity)`，
不借用玩家身份，所以原版的掉落、保护钩子与事件都照常生效。

`USE` 与 `PLACE` 走**动作玩家**：原版这两条路径的签名要求 `Player`，适配器用一次性的 `ActionContext` 提供，
用完即弃。平台侧仍然只看到 `ActorRef` 与能力集合。

## 当前边界

- 身体的生命周期由命令管理（`spawn` / `despawn` / `list`）；
- 已接通的身体分支：`craft.recipe`、`container.transfer`、`block.machine`、`block.interact`、`block.place`（都接受可选 `body`）；
- 身体工具：`body.list/move/look/mine/attack` 与 `block.place`，写操作默认关闭（`body_actions`、`block_place`）；
- 工具用显式身体 id 指挥身体，没有会话级绑定；
- 感知已可用：`body.scan`（按 id 找方块/实体）与 `body.inventory`（读演员背包）；
- 拾取与手持已可用：`body.pickup`、`body.equip`；装备影响伤害与耐久，**不影响挖掘速度**；
- 移动只有传送；`WALK`/`FLY` 被拒绝，两个载体都没有寻路（下一步的 walker 载体）；
- 注册表与背包都在内存里：重启丢失、不做持久化，也不跨维度查找；
- 身体的实体、背包、动作实现全部在适配器侧，平台不引入第三方寻路或身体框架。
