## 一、已经定下的决策（不要再翻案，除非有新证据）

1. **术语固定**：原子能力（一步操作）/ 分子能力（工作流，一串原子能力）/ 技能（给模型看的说明书）。
   三者不混用；**不把工作流叫原子能力**（那正是 Numen 工具爆炸的起点）。
2. **复合能力对模型只有"一个动作的外观"，内部怎么做由提供方决定。**

   两种都合法，不构成分类：
   - 提供方**发布步骤清单**：引擎照单执行，于是能数步、能在步边界取消、能逐步套调用者档位。
   - 提供方**不发布步骤**：引擎只调它一次，靠"提供方响应取消 + 引擎超时硬截断"兜底。

   发布清单里的每一步写的是**能力 id + 参数**，不是代码：运行时逐步解析到**各自的提供方**去执行
   （A 共享的流程里混用了 A 的原子能力和基座的原子能力，那两步就走各自的实现，调用方不需要、
   也拿不到 A 的代码接口）。**权限按调用者算，不按提供方算**，并在开跑前**预检全部步骤**：有一步
   调用者没权限就整体拒绝并列出是哪几步，而不是跑到一半留下半成品状态。
3. **复合能力只有一种**，不再按"谁执行"或"透不透明"分。两次修正记在这里免得以后绕回去：

   - **第一次错**：以为"提供方执行内部代码"是新风险。错——基座没有沙箱，模块的 Java 代码本来就同进程，
     它想直接 `level.setBlock` 谁也拦不住。档位系统约束的是**模型能碰到什么**，不是模块能干什么。
   - **第二次错**：改成按"透不透明"分。也没理由——既然"谁执行"不是安全差异，那"透不透明"也不该是分类。
     对开发者而言永远透明；对模型而言**只需要知道代价**；对操作员而言也只需要代价与副作用。
     提供方愿不愿意把步骤清单也发出来，是一个**可选的发布物**，不是一种能力种类。

   所以：**一种复合能力 + 一份必填声明 + 可选的清单发布**。
   - 必填声明：预计耗时、影响范围（动多少方块/实体）、有无副作用、**是否响应取消**。
   - 可选发布：步骤清单。发出来对调试、验收、以及"引擎替它执行并逐步约束"有用；不发也不影响它是个合法能力。
   - 兜底对所有复合能力一律生效：**引擎超时硬截断**。响应取消是义务，超时是保险。

   分类上只剩一件必须区分的事：**它是不是复合**——因为订阅粒度要用这个分类（见决策 7），与透明无关。
4. **基座不注册任何分子能力**。基座只提供四件事：登记、共享声明、订阅过滤、执行与超时兜底。
   唯一的参考实现在 `tianshu-lab` 里。
5. **工作流表达力先不定**：只按证据长。当前不实现循环嵌套、递归、变量运算。
6. **档位两轴**：玩家辅助 `READ_ONLY / CONSERVATIVE / FULL`；实体能力 `BodyAutonomy` 的
   `READ / SURVIVAL / PRIVILEGED`（读 / 身体亲自能做 / 身体做不到）。
   判定取两份声明里**更严的那个**（两把尺排的是同一个服务器旋钮）；`body.move` 这类"一个工具、多个子模式"的，
   由工具自己按子模式查当次允许级别。
7. **共享声明两边都要有**：提供方声明"开放给谁"，消费方声明"接受谁的"。
   基座的原版原子能力**全部声明为开放给所有**；消费方必须声明接受才读得到。

   **订阅粒度与共享声明正交**，两者各管一件事，不能合并：
   - 共享声明管**"谁能看"**（模块关系）
   - 订阅粒度管**"看哪一类、看到多细"**（原子 / 分子 / 两者，以及整包还是点名的能力）
   四种组合都是合法的：只接受 A 的原子能力、接受所有人的原子、接受 A 的原子加分子、全都接受。
   细则见工作项 7。
8. **默认开关保持现状**（贾维斯语义）：玩家辅助类默认开；`block.break` 默认关，理由写在类注释里
   （放错了能拆，拆错了回不来）。现在没有调用方，不改。
9. **入口就是具名工具，不做通用 `invoke` 总机。** 被订阅到的能力（原子的、复合的都算）各自成为一个
   具名工具，参数直接可见。工具表长度 = 基座 + 订阅者自己订的那些，是选择的结果，不是全局大列表。
   通用入口的后备条件写在工作项 2 里：只有在"订阅全部"真的把表撑到不可用时才考虑。

## 二、工作项

### [x] 1. 档位两轴：实体能力不再走玩家那条轴

**要解决的问题（现存的洞）**
- `TianshuTool.requiredAutonomy()` 的默认是"`SERVER_WRITE` → `CONSERVATIVE`，其他一律 `READ_ONLY`"，
  而 `BODY_WRITE` 落在"其他"里。于是**服务器设成 `readonly`（只读、写操作拒绝）时，身体照样能挖方块、打生物**。
- `body.move` 接受 `fly` / `teleport`，但整条轴管不到它：**只要允许了 `CONSERVATIVE`，模型就能让身体飞、传送**。

**改法**
- 新增实体能力自己的档位：`BODY_SURVIVAL`（身体亲自能做到的）与 `BODY_PRIVILEGED`（身体做不到、
  要靠特权或指令的）。
- 工具声明两份要求：玩家侧一份、实体侧一份。**分发时按解析出的执行者选轴**，不再按工具标签。
- `body.mine / body.attack / body.pickup / body.equip / body.drop / body.inventory / body.status`
  → `BODY_SURVIVAL`。（`body.place` 不是工具名：放方块只有 `block.place`，它按执行者换轴，见下一条。）
- `body.move`：walk → `BODY_SURVIVAL`；**fly / teleport → `BODY_PRIVILEGED`**。
- `block.place / block.break / container.transfer / craft.recipe` 这类**两种身份都能用**的：
  玩家侧 `CONSERVATIVE`、实体侧 `BODY_SURVIVAL`。
- 未来的 `command.run` → 实体侧 `PRIVILEGED`，且需要放行（**一次性**，见第四节）。

**验证**
- 单元测试：`readonly` 上限下，`body.mine` 被拒；`CONSERVATIVE` 上限下，`body.move(mode=fly)` 被拒、
  `mode=walk` 放行；玩家侧 `block.place` 在 `CONSERVATIVE` 下放行。
- 游戏内测试：一条"只读上限下身体挖不动"的用例（用现有 plaza 夹具）。

### [ ] 2. 复合能力的通道：执行器 + 代价声明（入口就是普通工具）

**入口形式：具名工具，和原子能力一样。**

被订阅到的能力（原子的、复合的都算）**各自成为一个具名工具**，模型直接调、参数直接看得见，
不走"通用总机"。理由是订阅已经控制了数量：**工具表长度 = 基座 + 你自己订阅的那些**，
是一条订阅者自己选的量，不是"全局什么都有"。之前想用 `capability.invoke` 通用入口换"长度恒定"，
这个交换不划算——它给每次调用都加一次查参数，而长度本来就已经被订阅约束住了。

（保留一个后备：真出现"订阅全部"导致表不可用的情况，再考虑给"订阅全部"这一档加通用入口。
现在不做，写在这里只是免得以后重新推导一遍。）

**要建的东西**
- 能力表 `kind` 增加 `WORKFLOW`（与 TOOL / SKILL / RESOURCE / PROMPT / CONNECTOR 并列）——
  它只表示"这是复合的"，供订阅分类用，不表示"另一种入口"。
- 复合能力的**必填声明**：预计耗时、影响范围、有无副作用、是否响应取消。
- 执行器（当提供方发布了步骤清单时由引擎执行）：四条硬规矩——
  1. **步数/时间上限**（超了就停并说明停在第几步）
  2. **可取消**（`tool.cancel` 到执行器，停在中途，报已做到第几步）
  3. **每步过调用者档位**（不是提供方的档位；计划本身不能放大权限）
  4. **失败归因到提供方**（"工作流 X（提供方 Y）第 N 步失败"，不是一句"失败了"）
- 提供方没发步骤清单时：引擎只调一次，靠"响应取消 + 超时硬截断"兜底。

**两个读者**
- **模型只读代价**：多久、动多少、有无副作用、能不能取消。**它不需要步骤**——需要步骤的是引擎和写代码的人。
- **引擎读步骤（如果有）**：逐条执行，能数步、能在步边界取消、能逐步套调用者档位。
  提供方没发步骤时，引擎只调它一次，靠"响应取消 + 超时截断"兜底。

**如果只把清单当 SOP 让模型照着逐步做，那就既没省 token 也没省延迟——这不是工作流的用法，是技能的用法。**

**验证**：见工作项 3（参考工作流就是它的取证手段）。

**完成标志**：执行器四条规矩都有对应的通过/拒绝记录。

### [ ] 3. 参考分子能力放在 `tianshu-lab`

**为什么放 lab**：基座不注册分子能力（决策 4）。lab 是一个真实模块，能走完整的模块注册路径，
所以它既当参考实现，又当"模块自建分子能力"这条路的证据。基座里不留例子。

**内容**：`workflow.gather`——采集附近一类方块若干个。步骤：`body.scan` 找目标 → 逐个
`body.move` → `body.mine` → `body.pickup`；数量够 / 背包满 / 超时即停。
它是"**发布步骤清单**"那一种，因为四条硬规矩要靠它取证。不发布步骤的那种，证据取"响应取消 + 超时截断"
两条就够，不需要再造一个参考实现。

- **游戏内测试侧（服务端）**：步数上限截停、中途取消、特步骤在不匹配档位被拒、失败归因正确。

### [ ] 4. 双向共享声明

**形状**
- 提供方：`sharedWith`——`ALL` / `NONE` / `ONLY(模块 id 列表)`。**基座的原版原子能力全部 `ALL`**；
  第三方模块默认 `NONE`。
- 消费方：`acceptsFrom`——`ALL` / `NONE` / `ONLY(...)`。**默认 `NONE`**：没声明就什么都拿不到。
- 两边都对上才可见。**自己的能力和自己可见，不受共享规则影响。**
- 装配期校验：消费方声明接受某模块、但对方没有向任何人开放 → 报出来（不是静默变不可见）。
- 与"原子/分子两个视图"结合：接受声明可以按视图分开（原子接受 `ALL`，分子只接受 `ONLY(某模块)`）。

**验证**：单元测试三条——两边都对上才可见；只有一边声明不可见；声明接受但对方没开放时给出诊断。

### [ ] 5. 技能覆盖链接

技能行声明它覆盖哪些能力（一个或多个，原子与分子都能覆盖）。作用：模型查到某个能力时，
能顺带拿到配它的说明书，不用猜。验证：目录按能力反查得到技能 id。

### [ ] 7. 订阅粒度：只原子 / 只分子 / 两者

**要解决的问题**：共享声明只回答"谁能看"，没回答"看哪一类"。一个模组可能只想用别的模组的工作流、
不想被一堆原子能力淹没，或者正好相反。这两件事必须分开，否则以后每加一种能力种类（比如技能、
资源），共享声明都要跟着改。

**形状**
- 消费方声明写成三段：**来源**（谁）× **种类**（原子 / 分子 / 两者）× **粒度**。
- 粒度支持两种写法，可以混用：
  - 按模块：接受 `modA` 全部（按种类）
  - 按具体能力：只接受 `modA:aim_at_block` 和 `modA:mine-vein`
- 默认：**只订基座自己的原子能力**，外部的一律不订（原子、分子都不订）。
- 基座的助手默认订"基座原子 + 基座没有分子"，外部的按需一个个加。
- 这也就是两个视图的来源：能力表的"原子视图 / 分子视图"是按这个粒度切出来的。

**工具表长度的实际后果**（写清楚免得以后再争）
- 工具表 = 基座 44 条 + 订阅到的外部能力。**默认就是 44 条。**
- 订阅 5 个模块、共 40 个能力 → 84 条。这是**订阅者自己选的**，不是"全局什么都有"。
- Numen 那堵墙是"一个全局列表，所有人看同一份"；我们是"按消费者过滤"，长度是选择的结果。

**验证**：单元测试覆盖这几种——只订原子时看不到分子行；只订分子时看不到原子行；两者都订时都看得到；
没声明接受时两边都看不到；点名只订 `modA` 的两条时，`modA` 的其他能力看不到。

**完成标志**：四条用例的通过/拒绝记录抄到此处。
