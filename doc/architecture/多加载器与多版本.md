# 多加载器与多版本

> 北辰按「平台 × 版本」出包，内核（api / core / client）与功能模组只有一份源码。
> 本文写三层怎么切、平台差异有哪些、门禁拦什么、加一个平台或版本要动哪些文件。
> 逐版本的实测记录（API 断点、构建插件坑、2026-10/11 的验证过程）在[多版本实测记录](../history/多版本实测记录.md)。

## 1. 三层

```
tianshu-adapter/
├── 1.21-1.21.1-common/                 共享层：只碰 vanilla Minecraft，不碰加载器（一份源码，两个 adapter 各编译一次）
├── 1.21-1.21.1-neoforge/        平台层：@Mod、事件、配置、网络注册、按键/HUD 挂载、mixin 配置
└── 1.21-1.21.1-fabric/          平台层：同上，Fabric 一侧
```

**共享层不是 Gradle 项目，是一份源码目录。** 一个 Gradle 项目只能有一个编译类路径，而 NeoForge 与
Fabric 提供的 Minecraft 产物不同；做成项目就得选一个加载器当"主人"。所以共享层由每个 adapter 用自己的
类路径编译，规则由 `verifyCommonAdapterNeutral` 保证：出现 `net.neoforged` / `net.fabricmc` /
`net.minecraftforge` / `cpw.mods` 任何一处就失败。

| 层 | 内容 | 典型规模 |
|---|---|---|
| 共享层 | 设置页与设置层、HUD 绘制与屏幕、游戏上下文采集、语言与字典、文件选择、诊断路由、世界事件钩子、网络载荷与编解码、**所有「游戏里发生某事该做什么」的判断** | 约 6,000 行 |
| 平台层 | 入口点、事件回调（只做转发）、配置读写、网络注册、按键注册、资源重载、着色器创建、mixin 配置 | 约 2,100 行 / 平台 |

判断放共享层、投递放平台层，是这一刀的分界：改「按下按键要做什么」不会分裂成两份，改「Fabric 怎么注册
按键」只影响一个平台。

## 2. 平台差异只有六处

| 差异 | NeoForge | Fabric |
|---|---|---|
| 入口 | `@Mod` + `FMLClientSetupEvent` | `ModInitializer` / `ClientModInitializer` + `CLIENT_STARTED` |
| 事件 | 事件总线 + `@SubscribeEvent` | 静态回调（`ClientTickEvents` / `ClientPlayConnectionEvents` / `ScreenEvents` / `HudRenderCallback`） |
| 配置 | `ModConfigSpec`（`config/tianshu-client.toml`） | 自读自写（`config/Tianshu/client.properties`） |
| 网络 | `PayloadRegistrar` + `PacketDistributor` | `PayloadTypeRegistry` + `ClientPlayNetworking` |
| 按键 | `RegisterKeyMappingsEvent` | `KeyBindingHelper` |
| 设置层与暂停菜单 | GUI 层栈（`pushGuiLayer`）+ `ScreenEvent.Init` | `setScreen` 换屏 + `ScreenInvoker` mixin 加控件 |

两个 vanilla 细节在共享层用一行分支吸收，而不是复制两份代码：

- **设置层叠放**：NeoForge 的层栈会在下面继续画设置页，Fabric 换屏后没人画。`SettingsLayerScreen` 用
  `drawParent` 标志决定要不要自己画那一页。
- **`Screen.addRenderableWidget` 是 protected**：NeoForge 的屏幕事件直接给 `addListener`，Fabric 只能开一个
  `@Invoker`（`FabricScreenInvoker`）。这是 Fabric 平台层唯一的 mixin。

## 3. 门禁

| 门禁 | 拦什么 |
|---|---|
| `verifyCommonAdapterNeutral` | 共享层引用任何加载器 API |
| `verifyAdapterProperties` | `adapter.properties` 钉错版本、清单放宽版本、共享层目录不存在 |
| `verifyAdapterMatrixCoverage` | 钉版链的起点、重复钉版、同一补丁线跳号 |
| `verifyProtocolVersionSingleSource` | 协议版本字面量被写进 adapter |
| `verifyUniversalModuleJars` | 功能 jar 缺清单或入口壳 |
| `verifySettingsRenderersCoverOptionEntries` | 内核新增一种设置行，某个共享层没跟着画 |

平台无关性的门禁（`verifyNoPlatformImport`、`verifyHostHasNoFeatureDependency`、
`verifyFeatureIsolation`、`verifyFeatureOptionalDependencies`）与全部 10 条清单见
[模块架构](模块架构.md) §11。

## 4. 加一个平台

1. 建 `tianshu-adapter/<版本线>-<loader>/`，写 `adapter.properties`：`minecraft_version`、`shared_layer`、
   `java_version`，NeoForge 加 `neo_version`（1.20.1 是 `forge_version`），Fabric 加 loader 与 API 版本。
2. `build.gradle` 把共享层的 `src/main/java`、`src/main/resources` 与 `src/test/java` 加进 sourceSets。
3. 写平台层：入口点、事件转发、配置、网络注册、按键、重载与着色器。**不写业务判断**。
4. 跑门禁 + 一次 `compileJava`。

## 5. 加一个版本

Minecraft 不承诺跨版本二进制兼容（1.21.1 → 1.21.3 实测 20 个编译错误，明细见历史记录）。所以版本维度是一条
**由端点编译挣来的区间**：

- 新版本先试复用相邻共享层：能编译就把 `shared_layer` 指向它，只加平台层；
- 编译不过才为它单开一份共享层，差异收敛进 `compat` 包；
- 每个 MC 版本仍然要有自己的 adapter 包与 jar——运行时名字不同，jar 不能跨版本。

### 5.1 版本声明规则（门禁强制）

- 一个 jar 只承诺编译验证过的版本，清单里的 Minecraft 区间默认就是钉版；
- 要覆盖补丁线（当前只有 26.1 / 26.1.1 / 26.1.2）必须在 `adapter.properties` 显式声明区间：
  NeoForge `minecraft_version_range=[26.1,26.2)`、Fabric `fabric_minecraft_version_range=>=26.1 <26.2`；
- 不能用 `~` 偷懒：`~1.21.1` 的语义是 `>=1.21.1 <1.22`，等于声称支持整条线，而实测证明它不成立。

功能 jar 的版本声明：Fabric `>=1.20`；NeoForge 由两份清单承担——`mods.toml` 的 `[1.20.1,1.20.4)`
（1.20.1–1.20.3，legacy FML）与 `neoforge.mods.toml` 的 `[1.20.4,)`（FML 10+）。实际兼容性由 `tianshu`
依赖兜底。

资源包元数据同样按版本走：`pack.mcmeta` 的 `pack_format` 是随 Minecraft 版本变化的数字（1.20.1 = 15、
1.21.1 = 34、1.21.5 = 55、26.3 = 97…），所以**每棵共享层各带一份**，放在该树的 `src/main/resources/`
（与 `tianshu.mixins.json` 同一处）。1.21.9 起该字段改名为 `supported_formats`（major.minor），因此
1.21.9+ 的三棵树只声明 `supported_formats`；跨多个版本的树用 `supported_formats` 声明整个区间
（如 1.21.2–1.21.4 是 42–46）。没有它，Forge/NeoForge 会在客户端启动时打 `Missing metadata in pack
mod:tianshu`。功能 jar 是跨版本通用的，因此不带 `pack.mcmeta`——它装进游戏时那一句提示会照旧出现，
是无害的（资源仍加载）。

### 5.2 加版本的步骤

1. 新目录 + `adapter.properties`（`shared_layer` 指向现有或新建的共享层）；
2. 平台层按上一版复制，按编译错误收敛；
3. `compileJava` 通过后，用 `verifyAdapterProperties` / `verifyAdapterMatrixCoverage` 确认清单与矩阵；
4. 更新本文 §6 与 README 的版本说明。

### 5.3 构建前置：网络与离线

1.20.2 / 1.20.3 / 1.20.5 三条线由 NeoGradle 7 服务，它在**配置期**解析 `net.neoforged:neoforge`：为选出依赖
版本，Gradle 要向已声明的每个仓库列一遍元数据，某个仓库连不上就整次配置失败——报出来的却是
`The run type 'client' was not found` 或某个 `2.11.+` 的 log4j，因为 run 类型与传递依赖都来自那份没解析成的
元数据。其余线（ModDevGradle、Loom）把解析放到任务期，配置不受影响。

所以：

- 依赖已下载齐全时，`./gradlew --offline …` 能配置并编译整个矩阵，不碰网络；
- 首次拉取依赖需要能连通各仓库；若到 `maven.neoforged.net` 的 TLS 握手被重置（本机实测过），开代理或 VPN 再跑，
  或改用 `--offline` 复用已缓存的依赖。

仓库根部的 `build-all.bat` 就是这两条的一键入口：默认在线、`--offline` 只走缓存、`--no-pause` 供脚本调用。
它把**任务级失败**（编译错）与**项目级失败**（配置错，三条 NeoGradle 线在网络不通时就栽在这一步）分开列出，
并按日志给出网络 / 内存两类提示。

## 6. 当前矩阵

43 个包（21 NeoForge + 22 Fabric）、13 棵共享层：

| 加载器 | 起点 | 覆盖 |
|---|---|---|
| NeoForge | 1.20.1 | 1.20.1–1.20.6、1.21–1.21.11、26.1–26.3 |
| Fabric | 1.20 | 1.20–1.20.6、1.21–1.21.11、26.1–26.3 |

每个 MC 版本一个 jar；26.1 线一个包覆盖 26.1 / 26.1.1 / 26.1.2。Java：1.20.1–1.20.4 用 17，
1.20.5–1.21.11 用 21，26.x 用 25。

## 7. 两个加载器的事实能力账

事实常量共 22 个。NeoForge 全部覆盖；Fabric 少 5 类永久缺口（合成 / 钓鱼 / 驯服 / 交易 / Boss 进入），
效果获得与到期只在 1.21.11、26.1–26.3 可用。缺口由每线的 `ServerFactCoverageTest` 固化，逐条依据见
[接口对齐审查](../history/接口对齐审查-2026-11.md)。对外的能力面见[平台能力清单](平台能力清单.md)。
