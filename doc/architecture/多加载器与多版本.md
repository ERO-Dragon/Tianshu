# 多加载器与多版本

> 北辰按「平台 × 版本」出包，内核（api / core / client）与功能模组只有一份源码。
> 本文写清三层怎么切、门禁拦什么、加一个平台或一个版本要动哪些文件。

## 1. 三层

```
tianshu-adapter/
├── 1.21-1.21.1-common/                 共享层：只碰 vanilla Minecraft，不碰加载器（一份源码，两个 adapter 各编译一次）
├── 1.21-1.21.1-neoforge/        平台层：@Mod、事件、配置、网络注册、按键/HUD 挂载、mixin 配置
└── 1.21-1.21.1-fabric/          平台层：同上，Fabric 一侧
```

**共享层不是 Gradle 项目，是一份源码目录。** 原因很硬：一个 Gradle 项目只能有一个编译类路径，而
NeoForge 与 Fabric 提供的 Minecraft 产物不同。把共享层做成项目，就得选一个加载器当「主人」，另一个
加载器编译时看到的是别人的类。所以共享层由每个 adapter 用自己的类路径编译，规则由
`verifyCommonAdapterNeutral` 保证：共享层里出现 `net.neoforged` / `net.fabricmc` / `net.minecraftforge`
/ `cpw.mods` 任何一处就失败。

层内分工：

| 层 | 内容 | 典型规模 |
|---|---|---|
| 共享层 | 设置页与设置层、HUD 绘制与屏幕、游戏上下文采集、语言与字典、文件选择、诊断路由、世界事件钩子、网络载荷与编解码、**所有「游戏里发生某事该做什么」的判断** | 约 6,000 行 |
| 平台层 | 入口点、事件回调（只做转发）、配置读写、网络注册、按键注册、资源重载、着色器创建、mixin 配置 | 约 2,100 行 / 平台 |

判断放共享层、投递放平台层，是这一刀的分界：改「按下按键要做什么」不会分裂成两份，改「Fabric 怎么注册
按键」只影响一个平台。

## 2. 平台差异只有六处

两个 adapter 的差异被压到可枚举的六件事：

| 差异 | NeoForge | Fabric |
|---|---|---|
| 入口 | `@Mod` + `FMLClientSetupEvent` | `ModInitializer` / `ClientModInitializer` + `CLIENT_STARTED` |
| 事件 | 事件总线 + `@SubscribeEvent` | 静态回调（`ClientTickEvents` / `ClientPlayConnectionEvents` / `ScreenEvents` / `HudRenderCallback`） |
| 配置 | `ModConfigSpec`（`config/tianshu-client.toml`） | 自读自写（`config/Tianshu/client.properties`） |
| 网络 | `PayloadRegistrar` + `PacketDistributor` | `PayloadTypeRegistry` + `ClientPlayNetworking` |
| 按键 | `RegisterKeyMappingsEvent` | `KeyBindingHelper` |
| 设置层与暂停菜单 | GUI 层栈（`pushGuiLayer`）+ `ScreenEvent.Init` | `setScreen` 换屏 + `ScreenInvoker` mixin 加控件 |

两个已知的 vanilla 细节差异，已在共享层用一行分支吸收，而不是复制两份代码：

- **设置层叠放**：NeoForge 的层栈会在下面继续画设置页，Fabric 换屏后没人画。`SettingsLayerScreen` 用
  `drawParent` 标志决定要不要自己画那一页。
- **`Screen.addRenderableWidget` 是 protected**：NeoForge 的屏幕事件直接给 `addListener`，Fabric 只能开一个
  `@Invoker`（`FabricScreenInvoker`）。这是 adapter 里唯一的 mixin，且只开一个方法。

## 3. 门禁

| 门禁 | 拦什么 |
|---|---|
| `verifyCommonAdapterNeutral` | 共享层引用任何加载器 API |
| `verifyHostHasNoFeatureDependency` | 内核（api / core / client / 每个 adapter / 共享层）依赖或引用功能模组 |
| `verifyNoPlatformImport` | 非 adapter 模块的字节码里出现 Minecraft / 加载器包名 |
| `verifyUniversalModuleJars` | 功能 jar 缺任一加载器的清单或入口类 |
| `verifyFeatureOptionalDependencies` | 依赖矩阵与 Gradle / `neoforge.mods.toml` / `fabric.mod.json` 不一致 |

## 4. 加一个平台

1. 建 `tianshu-adapter/<loader>-<mc版本>/`，照 `adapter.properties` 钉版本。
2. `build.gradle` 把 `../1.21-1.21.1-common/src/main/java` 与 `../1.21-1.21.1-common/src/main/resources` 加进 `sourceSets`。
3. 写平台层：入口点、事件转发、配置、网络注册、按键、重载与着色器。**不写业务判断**。
4. 跑 `gradlew build`：门禁与共享层测试会自动覆盖新平台。

## 5. 加一个版本（含小版本兼容）

**先纠正一个常见误解**：Minecraft 不承诺跨版本二进制兼容。1.21.1 编出来的 jar 装到 1.21.3 会因为 intermediary /
mojmap 名字对不上直接崩，NeoForge 与 Fabric API 也都是每个 MC 版本重新发布一套。所以"通用"只可能发生在**源码层**，
而且必须**编译验证**，不能靠感觉。

版本维度的结构：

```
tianshu-adapter/
├── 1.21-1.21.1-common/       共享层，按“编译目标版本”命名
├── 1.21-1.21.1-neoforge/     adapter.properties: shared_layer=1.21-1.21.1-common
├── 1.21-1.21.1-fabric/       adapter.properties: shared_layer=1.21-1.21.1-common
└──（新版本）common-1.21.4/ + neoforge-1.21.4/ + fabric-1.21.4/
```

**复用还是复制，是一个 adapter 的声明，由编译证明**：

- 补丁级升级（1.21.1 → 1.21.0 这类），或任何仍能编译通过的目标 → 新 adapter 的 `shared_layer` 直接指向
  旧的共享层（如 `1.21-1.21.1-common`），生成一份 `adapter.properties` + 平台层即可，共享层不复制；
- 一旦编译失败（例如 1.21.2 起物品注册要 `setId`、`GuiGraphics` 的绘制签名变化），才为该版本单开一份共享层，
  并把差异收敛到共享层的 `compat` 包里——共享层其余代码不感知版本。

门禁保证不会被"悄悄放宽"：

- `verifyCommonAdapterNeutral` 的输入是 `common-*/src/main/java` 的 glob，新共享层自动纳入；
- 该门禁**扫到 0 个文件会失败**（防止目录改名后门禁空过——本轮真的踩到过）；
- 共享层一旦被两个 adapter 声明，两边都会编译它，所以"某个版本改坏了另一版本"会在构建期暴露。

**北辰的版本声明规则**（已由 `verifyAdapterProperties` 强制）：一个 jar 只承诺它**编译验证过**的版本。
`adapter.properties` 默认只钉一个版本，清单随之精确声明（Fabric `"minecraft": "1.20.1"`，NeoForge
`versionRange="[1.20.1]"`）。要覆盖一个补丁线（如 26.1 / 26.1.1 / 26.1.2 共用一个 jar），必须在
`adapter.properties` 里**显式**写区间：NeoForge `minecraft_version_range=[26.1,26.2)`、
Fabric `fabric_minecraft_version_range=>=26.1 <26.2`，构建把它展开进清单。

**为什么不能靠 `~` 偷懒**：`~1.21.1` 在语义上是 `>=1.21.1 <1.22`，等于声称支持整条 1.21 线——而
§5.0.1 的实测证明 1.21.1 编出来的类在 1.21.3 上会崩。`~26.1` 恰好等于 `[26.1,26.2)` 只是个巧合，
把巧合写成巧合、把意图写成显式区间，才读得懂。

**功能 jar 的版本声明已按同一规则收口**：它们没有 Minecraft 类引用，所以范围覆盖整个北辰矩阵——
Fabric `>=1.20`，NeoForge `[1.20.1,)`。NeoForge 这一段由**两份清单 + 两个入口壳**共同承担：
FML 10（1.20.4 起）只读 `META-INF/neoforge.mods.toml` 并扫描 `net.neoforged.fml.common.Mod`；
1.20.1–1.20.3 只读 `META-INF/mods.toml`，其中 1.20.1 还是 legacy forge 的
`net.minecraftforge.fml.common.Mod`（1.20.2/1.20.3 已是 `net.neoforged`）。一个 jar 同时带两份清单、三个壳，
每个版本线只读自己那份、只实例化自己那个壳——**同级 `Tianshu-libs` 项目就是这么做的**（它的
`TianshuLibsForgeCompatMod` + `TianshuLibsMod` + 两份清单，universal jar 里同时存在，1.20–26.x 都能加载）。
`verifyUniversalModuleJars` 要求两份清单与三个壳齐备。

### 5.0.1 实测：1.21.1 与 1.21.3 之间不兼容

把 Fabric adapter 的 `minecraft_version` 指到 1.21.3（Fabric API `0.114.0+1.21.3`）跑 `compileJava`，共享层加平台层
共 **20 个编译错误**，全部集中在六处 API 变化：

| 变化 | 受影响文件 |
|---|---|
| `ShaderInstance` 的类型/构造变了 | `HudShaderPrograms`、`ShaderUniformSink`、`HudSurfaceRenderer`、`FabricShaders` |
| `GuiGraphics.blit(ResourceLocation,int,int,float,float,int,int,int,int)` 签名变了 | `HudSurfaceRenderer` |
| `RenderSystem.setShader(Supplier)` 变了 | `HudSurfaceRenderer` |
| `EntityType.create(ServerLevel)` 变了 | `FabricServerActionHandler` |
| `PreparableReloadListener.reload(...)` 的参数变了 | `TianshuFabricClient` |
| `LocalPresentation` 用到的客户端表现方法变了 | `LocalPresentation` |

结论：**共享层 `1.21-1.21.1-common` 只能覆盖 1.21 与 1.21.1**。1.21.2 起必须另开一份共享层，
把这六处收敛进 `compat` 包；这也是"区间名必须由端点编译挣来"的实证。
### 5.1 加一个版本的步骤

版本维度与平台维度是正交的，但共享层要按 MC 版本重取一份（vanilla 类会变）：



内核与功能模组不动。**成本主要在共享层**：UI 直接使用 `Screen` / `GuiGraphics` / `AbstractWidget`，跨版本
API 变化会落在这一层；平台层通常只是改版本号后重编译。

判断「能不能只加版本、不动内核」的标准：内核与功能模组仍然零 Minecraft 依赖（`verifyNoPlatformImport`），
所以它们天然跨版本；只有共享层的 vanilla 用法需要按版本核对。

### 6.1 投递覆盖（2026-10-30 补）

`ClientEvents` 是共享层的全部入口，平台层只负责转发。**漏一个转发在构建期看不出来**——产品照样编译、
照样启动，只是那条能力在某个平台上是死的。所以 Fabric 侧有一个 `DeliveryCoverageTest`：

- 反射式读出 `ClientEvents` 的每个 public 入口，断言本 adapter 的转发代码里都调用了它；
- 没有原生事件的入口必须写进 `DECLARED_GAPS`；反过来，某个入口既然声明为缺口，就**不许**被转发，
  否则测试失败——缺口表因此不会悄悄过期。

当前 Fabric 的缺口表：`onPlayerClone`（重生）。NeoForge 有 `ClientPlayerNetworkEvent.Clone`，Fabric 没有，
所以这条事实在 Fabric 上只能靠会话期已有的世界身份刷新兜底。

### 5.0.2 1.21.2+ 的着色器体系（实查 1.21.3 合并 jar）

`ShaderInstance` **已不存在**，替换为四个类型：

| 类型 | 作用 |
|---|---|
| `net.minecraft.client.renderer.ShaderProgram` | 程序标识：`record(ResourceLocation configId, VertexFormat, ShaderDefines)` |
| `net.minecraft.client.renderer.CompiledShaderProgram` | 编译后的句柄，uniform 与绘制都经它 |
| `net.minecraft.client.renderer.ShaderManager` | 资源重载时编译；`getProgram(ShaderProgram)` 取句柄 |
| `RenderSystem.setShader(ShaderProgram)` | **应用**一个程序，返回 `CompiledShaderProgram` |

移植路径已经清楚：`HudShaderPrograms` 存 `ShaderProgram`（标识）而非 `ShaderInstance`；绘制前
`RenderSystem.setShader(program)` 拿到 `CompiledShaderProgram`，uniform 经它设置；`FabricShaders` 不再“构造”
shader，而是构造 `ShaderProgram`（configId + `DefaultVertexFormat.POSITION_TEX` + `ShaderDefines`），由
`ShaderManager` 在资源重载时编译。

尚未确定、下一轮开工第一件事就要查的三处：

1. `ShaderDefines` 的构造方式（空值/自定义 define）；
2. `GuiGraphics.blit` 在 1.21.3 的重载（`HudSurfaceRenderer` 第 153 行）；
3. `LocalPresentation` 第 41/45 行调用的客户端表现方法替代品。

### 5.0.4 1.21.3 的着色器适配（已完成）

共享层里加了一个缝，而不是在每个绘制点判断版本：

- `mc.compat.HudShader`：渲染器只认这个接口——`HudUniformSink apply(float frameTimeSeconds)`，即“让这个程序成为当前程序，
  并把它的 uniform 写入口给我；当前资源里没有可用程序时返回 null”。
- `mc.compat.ShaderProgramHudShader`：1.21.3 的唯一实现，用 `new ShaderProgram(configId, POSITION_TEX, ShaderDefines.EMPTY)`
  描述程序，每次绘制前 `RenderSystem.setShader(descriptor)`。编译后的句柄**不缓存**：它属于某一次资源加载代，
  重载时由 ShaderManager 关闭，所以每次使用都重新解析。
- 程序 config id 是 `<ns>:core/<声明的名字>`：1.21.3 用 `FileToIdConverter.json("shaders")` 索引，而功能模组的资源仍在
  `assets/<ns>/shaders/core/<name>.json`，所以映迹的素材文件一个都不用改。
- `HudShaderPrograms` 的公开形状（register/get/clear）保持不变；`ShaderUniformSink` 移到 `mc.compat` 并改为包
  `CompiledShaderProgram`。

实测修正了一条先前写错的判断：`SystemToast.SystemToastId.PERIODIC_NOTIFICATION` 在 1.21.3 里**仍然存在**，
`LocalPresentation` 的真正错误只是 `Minecraft.getToasts()` 改名为 `getToastManager()`。

分组依据：Architectury API 在 Modrinth 上每个 release 声明支持的 MC 版本集合（413 个版本）。他们**合并**过的只有两处：
`1.21.7+1.21.8`、`26.1+26.1.1+26.1.2`。其余版本各自独立发布——这与我们实测的「1.21.1 与 1.21.3 不兼容」一致。

目标不是全覆盖，而是**每个大版本线取热门小版本，再以它为中心合并左右**：

| 波次 | 区间 | 合并依据 | 覆盖 | 状态 |
|---|---|---|---|---|
| A | `1.21-1.21.1` | 我们已验证；同属 1.21 首发补丁 | Fabric + NeoForge | ✅ 完成并实机验收 |
| B | `1.21.2-1.21.3` | Architectury 分 1.21.2；1.21.3 为其补丁 | Fabric | ✅ 编译/测试通过，实机待统一验证 |
| B′ | `1.21.2-1.21.3` | 同上 | NeoForge | 待做 |
| C | `1.21.4` | 独立版本，1.21.1 之后玩家基数最大 | 双端 | 待做（复用 B 的共享层，一次端点编译判定） |
| D | `1.21.5` / `1.21.6` / `1.21.7-1.21.8` | 5、6 独立；7+8 由 Architectury 合并 | 双端 | 待做 |
| E | `1.21.9`–`1.21.11` | 9/10/11 各自独立；若端点编译允许则合并 | 双端 | 待做 |
| F | `26.1-26.1.2` / `26.2` / `26.3` | 26.1 线由 Architectury 合并；26.x 起不再混淆 | 双端 | 待评估（构建体系不同） |
| G | `1.20.1` | 历史基数最大，但属上一代 API | 双端 | 视业务需要 |

**命名**：`<区间>-<层>`，如 `1.21.2-1.21.4-common`、`1.21.7-1.21.8-fabric`。区间是**对外承诺**，只写端点编译挣来的上界；
单版本区间就写自身，如 `1.21.4-fabric`。

**每个波次的成本** = 一份共享层（能被相邻区间复用时复用）+ 每加载器一个平台层 + 端点 `compileJava` 验证。
平台层不能跨 MC 版本复用（运行时名字不同），共享层可以——这就是「最大程度小版本合并」的全部空间。

### 5.0.8 26.x 一代：构建体系与渲染引擎都换了（2026-11-01 实测）

26.x 不是"再复制一个 adapter 改版本号"，它换了两层地基：

| 维度 | 1.21 线 | 26.x 线 |
|---|---|---|
| 混淆 | 混淆，需 mappings | **26.1 起不再混淆，没有 mappings 行** |
| Fabric 插件 | `net.fabricmc.fabric-loom-remap` | **`net.fabricmc.fabric-loom`**（原生） |
| Fabric 依赖 | `modImplementation` | **`implementation`** |
| Java | 21 | **25**（adapter 自设工具链，foojay 自动取 JDK） |
| NeoForge 插件 | ModDevGradle `2.0.141` | **`2.0.147`**（2.0.141 生成 26.2 产物会挂） |

26.x 的共享层按版本各自独立，三棵分别是 `26.1-common` / `26.2-common` / `26.3-common`——一代之内容量稠密到无法合并。

每版的 API 断点：

| 版本 | 断点 |
|---|---|
| 26.1 | `GuiGraphics` → **`GuiGraphicsExtractor`**，GUI 动词从 render 改 extract（`render`→`extractRenderState`、`drawString`→`text`、`renderOutline`→`outline`、`renderBackground`→`extractBackground`）；Fabric `HudRenderCallback` → `HudElementRegistry.addLast`；`KeyBindingHelper` → `KeyMappingHelper`；`PayloadTypeRegistry.playS2C/playC2S` → `clientboundPlay/serverboundPlay`；`displayClientMessage` 拆成 `sendSystemMessage`/`sendOverlayMessage`；时间走世界时钟（`clockManager().setTotalTicks`）；天气走 `WeatherData`；`DepthTestFunction` → `DepthStencilState` + `ColorTargetState` |
| 26.2 | 屏幕栈搬到 `Gui`（`gui.screen()`/`gui.setScreen`）；`ClientHooks.pushGuiLayer` 删除 → Neo 补丁 `Gui.pushScreenLayer`；`Tesselator` 删除（`ByteBufferBuilder`+`BufferBuilder`）；`withVertexFormat` → `withVertexBinding`+`withPrimitiveTopology`；`GpuDevice.createBuffer`；5 参 `drawIndexed` |
| 26.3 | 渲染引擎整体搬到 **`com.mojang.renderpearl.*`**；管线编译变**异步**（`compilePipeline` + `Pending.finishCompile`，渲染线程只轮询不 `join`）；`InputConstants.Type.KEYSYM` → `KEYBOARD`；GLFW 不在类路径；`DisplayInfo` 记录化；`ModConfig.Type.SERVER` → **`SYNCED`** |

**NeoForge 侧两处不对称值得记住**（靠 javap 而非类推得出）：

1. `RenderGuiEvent` 在 26.1/26.2/26.3 **仍然存在**，只是 payload 变成 `GuiGraphicsExtractor`——所以 NeoForge 侧 HUD 挂载点没变，而 Fabric 侧是被整个换掉的。同一件事两个加载器的命运不同。
2. NeoForge 的 **payload 注册在 26.x 没有改名**（仍是 `RegisterPayloadHandlersEvent.registrar` + `playToClient/playToServer`）；改名的是 Fabric 的 `PayloadTypeRegistry`。

26.x 的异步着色器编译（方案 A）：在资源就绪时用 `compilePipeline(pipeline, shaderSource, backgroundExecutor)` 起编译并按程序 id 缓存 future；渲染线程 `isDone()` 才 `finishCompile()`，**从不 `join()`**；未就绪就这一帧跳过该程序，不刷日志。`HudShaderSource` 照抄游戏自己的 UI 预载（`listAllIncludes` + `Type.idConverter().idToFile`），没有自造兼容层。

**当前 26.x 覆盖**：26.1.2 / 26.2 / 26.3，Fabric + NeoForge 双端，共 6 个包、3 棵共享层；Fabric 侧 63/63/64 用例、NeoForge 侧 81/81/82 用例，全部零失败。

### 5.0.9 1.20.3–1.20.6：网络 API 换了三代，渲染一处都没动（2026-11-02 实测）

补齐 1.20 系列剩下的六格。四种加载器组合各自的构建插件不是"跟最新走"，而是被上游发布内容决定：

| NeoForge 版本 | `.module` | 插件 | 依据 |
|---|---|---|---|
| 20.2.93 / 20.3.8-beta / 20.5.21-beta | **404** | NeoGradle `7.1.39` | universal/pom/sources 都是 200，只有 Gradle Module Metadata 没发布，ModDevGradle 找不到它要的 bundle 变体 |
| 20.4.253 / 20.6.144 | 200 | ModDevGradle `2.0.147` | 元数据齐全，走常规插件 |

NeoGradle 的两条硬约束：`java { toolchain 21 }` 必须在文件靠前处声明（它拿工具链自举，jst 是 Java 21 字节码）；而真正出包的 `options.release` 由 `adapter.properties` 的 `java_version` 推导——1.20.1–1.20.4 是 17，1.20.5 起是 21。另有一个坑：它会按 TTL 刷新 `caches/minecraft/launcher_metadata.json`，文件过期就直连 `piston-meta` 并失败（表现为整棵树配置阶段报 `The run type 'client' was not found`），重新种子那份 JSON 即可。

清单文件名断点（四份 jar 逐个拆开看过）：20.2 与 20.3 是 `META-INF/mods.toml`，20.4 起（FML 10）改成 `META-INF/neoforge.mods.toml`。

网络是三代的差别，且**不是随 MC 版本线性演进**：

| 世代 | NeoForge 侧 | 共享层的 payload 形状 |
|---|---|---|
| 20.2 / 20.3 | `SimpleChannel.registerMessage(id, class, encoder, decoder, handler)` + `NetworkEvent.Context` | `CustomPacketPayload` 带 `id()` 与 `write(FriendlyByteBuf)` |
| 20.4 | `RegisterPayloadHandlerEvent`（单数）+ `IPayloadRegistrar.play(channel, decoder, builder→client/server)` + `PlayPayloadContext` | 同上 |
| 20.5 / 20.6 | `RegisterPayloadHandlersEvent`（复数）+ `PayloadRegistrar.playToClient/playToServer(Type, StreamCodec, handler)` + `IPayloadContext`（`player()` 直接返回 `Player`，不再是 Optional） | `type()` + `StreamCodec.ofMember(...)`，`write`/`id` 已删除 |

1.20.5 这一代的 API 断点（对 1.20.5 与 1.20.6 用 javap 逐条核对，两版一致）：

- `ResourceLocation` 只有 `of` / `tryParse` / `tryBuild`；`fromNamespaceAndPath` 与 `withDefaultNamespace` **是 1.21 才有的**，照 1.21 抄会全红；
- `MobEffectInstance.getEffect()` 返回 `Holder<MobEffect>`，取名字要走 `.value()`；
- `TickEvent` 拆成 `ClientTickEvent.Post` 与 `event.tick.ServerTickEvent.Post`；
- 选项界面仍在 `net.minecraft.client.gui.screens.OptionsScreen` 与 `...screens.controls.KeyBindsScreen`（`screens.options` 同样是 1.21 才搬的）；
- **渲染完全没换**：`MeshData` 不存在、`BufferBuilder.build()` 不存在，仍是 `Tesselator` + `end()`/`endVertex()`。

最后一条决定了这棵共享层从 `1.20.4-common` 起而不是从 `1.21-1.21.1-common` 起：1.20.5 唯一真正断裂的是网络与 `Holder`，渲染要等到 1.21 才变成 `Tesselator.begin` + `MeshData`。1.20.6 相对 1.20.5 只多破一处：`PlayerEvent.ItemPickupEvent` → `ItemEntityPickupEvent.Pre/Post`（`Post` 同时给出 `getOriginalStack()` 与 `getCurrentStack()`，正好是原来算差值需要的两端）。

**当前 1.20 覆盖**：1.20.1 / 1.20.2 / 1.20.3 / 1.20.4 / 1.20.5 / 1.20.6 全部 Fabric + NeoForge 双端，共 12 个包（1.20 首发版见 §5.0.10，只有 Fabric）、4 棵共享层（`1.20.1-common`、`1.20.2-common`、`1.20.4-common` 供 1.20.3 与 1.20.4、`1.20.5-1.20.6-common`）。本轮新增的五个包用例数：`1.20.3-neoforge` 20 套、`1.20.5-fabric` 17 套、`1.20.6-fabric` 17 套、`1.20.5-neoforge` 20 套、`1.20.6-neoforge` 20 套，零失败；整树 `gradlew build` 844 个任务 BUILD SUCCESSFUL，门禁 `verifyCommonAdapterNeutral` / `verifyUniversalModuleJars` / `verifyFeatureIsolation` 均通过。

**仍然没有任何一版做过真机验证**，1.20.5/1.20.6 的结论目前只有编译、单元测试、字节码核对三层证据。

### 5.0.10 首发版 1.20 与 1.21：一个能补，一个上游就没有（2026-11-02 实测）

补齐了 1.20 与 1.21 两个首发版（此前只有 1.20.1 与 1.21.1 起的包），结果不对称，原因全部可查：

| 版本 | 结果 | 依据 |
|---|---|---|
| 1.21 | Fabric + NeoForge 双端 | NeoForge `21.0.167`（有 `.module`，moddev `2.0.141` 正常）；Fabric `0.102.0+1.21`；共享层直接复用 `1.21-1.21.1-common`，**一行代码都没改**（1.21 与 1.21.1 之间没有触及本产品的 API 差异） |
| 1.20 | **只有 Fabric** | NeoForge 从 1.20.1 才存在；1.20 的第二加载器是 Forge 46，属 MCP/ForgeGradle 时代 |

1.20 走不通的三条实测路径，都不需要再试第二遍：

1. `net.neoforged:forge` 的 maven 元数据里 63 个版本全是 `1.20.1-47.x`，没有 `1.20-46.x`；Forge 46 的 userdev 只在 `maven.minecraftforge.net`（200）。
2. 用 ModDevGradle `legacyforge 2.0.91` 硬顶 Forge 46，会死在 NFRT：`Unknown result: intermediaryToNamedMapping`——1.20 的 userdev config 只提供 `compiled/clientResources/sources/...` 八项，没有这个 result，而插件按 20.1 的形态要它。
3. 退路 ForgeGradle `6.0.36` 在 Gradle 9.3.1 上连插件都应用不了（`Failed to apply plugin: 'net.minecraftforge.gradle'`）。本项目全树只用一个 Gradle，为单个包再引入第二套构建器不划算，所以不做。

所以 1.20 是 **Fabric 单端**，第二个加载器由上游（NeoForge 不存在）与工具链（ForgeGradle 不兼容 Gradle 9）共同决定，不是遗漏。**北辰自 1.20.1 起每一版都是双端**；1.20.1 的 NeoForge 侧是 legacy forge 包名，功能 jar 的入口壳目前不覆盖它（见 §5 的功能 jar 版本声明）。

**一处真实的 Fabric 能力差（要记住，不是实现偷懒）**：1.21 的 `fabric-api 0.102.0+1.21` 捆绑 `fabric-entity-events-v1 1.6.12`，其 `ServerLivingEntityEvents` 只有 `ALLOW_DAMAGE` 与 `AFTER_DEATH`；`AFTER_DAMAGE` 要到 1.8.0+ 才有（1.21.1 线用的是 2.x）。于是 1.21 的 `damage_taken` 事实取的是**入射伤害**（结算护甲/附魔之前），而非最终落地伤害；接口还在，语义退一档，已写在 `FabricGameFactCollector` 的注释里。这类"该版本确实拿不到的数据"正是后续接口对齐审查要逐条登记的对象。

**顺带修掉一个会静默吞测试的 bug**：1.21 线的 7 个 adapter 把 `sourceSets.test` 指向 `../common/src/test/java`——一个早已不存在的目录（共享树早已按版本改名），而 Gradle 对不存在的 `srcDir` 是静默忽略的。结果是**整条 1.21 线的共享层单测从未运行过**，每包只跑了 adapter 自己的 2/5 个用例。改为 `${sharedLayerRoot}/src/test/java` 后，1.21.9 的 `remapJar` 还暴露过一次 loom 临时文件竞态（`NoSuchFileException: loom-remapJar-…-input.jar`，重跑即过，与代码无关）。

补跑后的全树数字：43 个包、826 个测试套件、0 失败、43/43 有 jar（1.20 线 239 套、1.21 线 464 套、26.x 线 123 套）。覆盖 24 个 Minecraft 版本 —— 1.20、1.20.1–1.20.6、1.21、1.21.1–1.21.11、26.1（含 26.1.1/26.1.2）、26.2、26.3；只差 26.4（尚未发布，且 NeoForge 无 26.4 线）。
