## 2. 三个功能方向（给谁用）

| # | 方向 | 是什么 | 代码 |
|---|---|---|---|
| 4 | **模型工具能力** | 告诉模型有哪些工具可调，以及 skill / resource / prompt 这些可读材料 | `TianshuTools` + `CapabilityCatalog` |

### 2.1 三档控制

| 档位（`ToolAutonomy`） | 产品语义 | 归谁 |
|---|---|---|
| `READ_ONLY` | **读客户端数据**；服务端也装了舟楫时，**同时可读服务端数据**（配方、标签、掉落、世界事实）。不改变任何状态 | 模型工具能力 |
| 生存动作的权限 | 合成 / 搬物品 / 操作工作方块 / 按按钮 / 放方块：类别仍是 `SERVER_WRITE`，但各自覆盖成 **`EVERYONE` + 默认开启**——它们是普通生存玩家用手就能做的事，既不需要 operator，也不需要先配置。**动作以该玩家身份执行**，因此玩家的原版权限、领地/保护规则、游戏模式限制照常拦截。`SurvivalToolPermissionTest` 钉住这条 |
| `LOCAL`（客户端偏好） | 玩家自己屏幕与耳朵的设置：音量通道、材质包开关。**不碰世界、不问服务器、不需要 operator**，默认开启 |
| 服务端端口的生命周期 | 服务端会话装的端口**随会话**：关服撤销、下次开服重装。这样"退出公共服 → 开单人/局域网"不会读到上一个服务器的实现。客户端常驻端口（聊天、设置、游戏上下文）不随会话撤销 |
| 出网闸门 | 任何模块的出网请求都过 `ExternalAccessPolicy`（`HostAllowListPolicy`：主机白名单 + 拒绝私网、默认拒明文 http、统一上限 `ExternalLimits`）。**端口缺失即拒绝**，不允许"没有策略 = 无限制"。服务商端点与密钥仍在模块自己的配置里 |
| 第三方模组联动 | **不归舟楫**：光影包（Iris / Oculus）这类能力依赖具体第三方模组的 API，由将来的扩展模组自己以 skill / tool 形式提供。舟楫只提供 `TianshuTools` 注册入口，不内置对任何第三方模组的依赖 |
| `CONSERVATIVE` | **普通生存玩家在服务器里本来就能做的事**：合成、工作方块交互、放置方块、移动物品、让身体做动作、说话（聊天）。不需要 op | 玩家辅助 |
| `FULL` | **作弊类**：传送、天气/时间、给物品、生成实体、系统广播、改游戏模式、状态效果、经验、任意坐标放方块、清除实体、附魔、难度、游戏规则 | 玩家辅助（作弊档） |

**已收口（2026-11-16）**：六个作弊动作（传送 / 天气 / 改时间 / 给物品 / 生成实体 / 广播）已经是 `FULL` 档工具（`server.teleport` 等六个 id），
默认关闭、需要 operator、并受服务端自己那六个开关与自主度上限约束。传输仍是原来的动作通道，但**入口只剩工具层一个**——
执行只走 `ServerActionExecutionPort`（api 端口，adapter 提供实现）：工具层拿参数、服务端拿玩家与权限，没有第二个入口。

**说话（`server.say`）不是作弊动作**：它是 `LOCAL` 类、`CONSERVATIVE` 档、默认开启，因为它就是"以玩家身份在聊天频道说一句"——任何玩家都能做，不需要 op、不需要服务端开关。它和 `server.broadcast`（系统公告、`/say` 同级、`FULL` 档）是两个能力，不要合并。

## 3. 实体模型（自定义实体）

### 3.1 可控实体

`EntityActor` 是"可被驱动的一个实体实例"：它声明身份与能力位，动作由可选端口实现，归属者独占指挥权。
自由度全部来自 **能力位 + 端口有无 + 基座选择** 这三处，实体之间靠这三处区分，不靠类型继承。

`EntityActions` 提供 11 个可选端口（感知、移动、动作、放置、交互、物品、使用、合成、容器、机器、实体交互），
缺省即"没有该能力"。能力位与端口的完整清单见 [实体与身体](实体与身体.md) §3。

### 3.2 身份

`playerLike` 是实体的身份声明：`true` 表示玩家型实体（拿玩家权限、受领地约束、参与玩家相关逻辑），
`false` 表示普通实体。外观不在平台职责内——模型与渲染决定它长什么样，与身份互不影响。

### 3.3 两件事分开

| 要做的事 | 落在哪 |
|---|---|
| 注册**一种新实体类型**（僵尸变种、NPC、光球模型） | 实体类型注册契约（adapter 提供），**不是**可控实体层 |
| 让**一个实体实例**可被驱动（走/看/挖/放、归属谁） | 可控实体层 `api/entity` |

### 3.4 两种基座（adapter 实现）

| 意图 | 基座 |
|---|---|
| 要玩家语义（拿工具改造世界、受领地约束、吃玩家逻辑） | fakeplayer 型（`ServerPlayer` 根） |
| 光球、装饰、跟随物、非玩家 | 自定义实体型（`Entity` 根） |

分派依据只有 `playerLike` 一个声明；调用方看到的始终是 `EntityActor`，基座是 adapter 的实现细节。
平台扩展新语义的方式是**给 `EntityActions` 增加可选端口**，注册面保持一个。

## 4. 授权（三层，各管各的）

| 层 | 判什么 | 依据 |
|---|---|---|
| **实体权限** | 这个实体在服务器上有多大权限（op 级别、领地、受保护） | 服务器既有体系；`playerLike=true` 时由 fakeplayer 自动继承 |
| **归属权限** | 谁能指挥这个实体 | `EntityActors` 的 owner + `EntityAccess` |
| **调用方权限** | 调用自己的 op 与自主度档位（模型工具能力的执行侧校验） | `ToolPermission` + `ToolAutonomy` + `ServerAutonomyCeiling` |

> **命名约定**：`ToolPermission` / `ToolAutonomy` / `ServerAutonomyCeiling` 里的 `Tool` 指的是
> **"模型工具能力的调用"**，与"实体"无关。这三者只对 §2 的模型工具能力（工具注册表）生效，
> 对实体层与归属层一律不适用——`body.*` 的放行只看归属，不看权限与档位。

`body.*` 走**实体权限 + 归属权限**：要求调用方是身体的 owner，实体自身受服务器权限约束。
领地保护由服务器既有体系提供（fakeplayer 天然吃这套），"能不能被攻击 / 被交互"由实体类型自身表达。
