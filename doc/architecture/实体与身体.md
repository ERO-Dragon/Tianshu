# 实体与身体

> 「自定义实体」这一功能方向的唯一落点：注册、归属、动作、两种基座、验收口径。
> 设计判据见 [舟楫职责边界](舟楫职责边界.md) §3–4；历史版本（`智能体身体.md`）在 `doc/history/`。
> 更新：2026-11-16。

## 1. 三层对象

| 对象 | 是什么 |
|---|---|
| `EntityActor` | 一个可被驱动的实体实例：身份 + 能力位 + 归属 |
| `EntityActions` | 它的动作实现：11 个可选端口，缺省即没有该能力 |
| `EntityActors` | 注册与查找：模组注册 provider，平台按归属取处理器 |

包位置：`com.rheinmetal.tianshu.api.entity`（`AgentSession` 仍在 `api.agent`，那是"AI 会话"层）。

### 1.1 两条正交的轴

身体的自由度来自两条彼此独立的轴，而不是一个类型树：

| 轴 | 表达 | 决定 |
|---|---|---|
| **形状** `BodyKind` | marker / stand / walker / 模组声明的实体类型… | 能力位、碰撞、外观、用哪个实体基座 |
| **身份** `Identity` | 普通 / 玩家型 | 谁代表它执行动作、是否享受玩家权限与领地判定 |

两者自由组合：walker + 普通 = 会走路的身子；orb + 普通 = 光球；walker + 玩家 = 受领地约束的 NPC；
orb + 玩家 = 轻量但有玩家身份的身体。

**硬规矩（防止走样）**：平台与工具层**不得出现任何"玩家型 / 非玩家型"的分支**。身份只影响两件事——
适配器选哪个实体基座、用哪个执行者。能力位、工具、授权链、归属对两种身份完全相同。
`EntityActor.playerLike()` 是身份的对外表达，只作数据（供适配器选基座、供 AI 模块推理），任何工具都不读它做判断。

## 2. 注册、归属与访问

```java
// 一个模组注册"我这些实体可被驱动"，并自己决定谁能指挥
Runnable unregister = EntityActors.register(provider);
Optional<EntityActor> actor = EntityActors.resolve(bodyId);
Optional<EntityActions> actions = EntityActors.actions(bodyId);   // 归属决定用哪套处理器
Optional<ToolException> refusal = EntityActors.checkAccess(caller, bodyId);
```

- `EntityProvider.resolve/all/actions/checkAccess` 是唯一实现面；
- 服务端模组从 `TianshuRuntimePorts` 取得 `EntitySpawnPort`，传入模组 ID、载体种类、维度与坐标即可申请 NPC，无需在线玩家。模组和智能体调用使用同一个模组 ID，只能驱动该模组申请的 NPC。第三方 provider 通过 `EntityActor.ownerModule()` 报告归属。
- 身体归属使用内容模组在加载器清单中声明的 ID。天枢为 `tianshu`，舟楫为 `tianshu_ferry`。通过舟楫命令生成的身体归舟楫；通过服务端生成端口申请的身体归申请模组。
- NPC 归属校验与创建失败使用稳定的错误码和原因标识。例如跨模组操作返回 `code=NO_PERMISSION`、`message=body.controller.mismatch`。玩家界面在展示时翻译原因，工具回复与诊断记录保留标识。
- 申请模组随存档保存。旧档缺少模组 ID 时保留身体和物品，任何模组都不能自动认领。
- `EntityAccess` 管理玩家访问。仅玩家命令创建的身体有初始玩家 owner，玩家访问策略与模组归属分别校验。远程工具连接只认证登录玩家，模组在权威服务端调用身体动作。
- 归属是"谁能驱动"的唯一依据，与调用方的 op、自主度**互不替代**。

## 3. 能力位与端口

**7 个能力位**（`EntityCapability`）：`MOVE`、`LOOK`、`USE`、`PLACE`、`MINE`、`ATTACK`、`INVENTORY`。
能力位决定"这个实体能不能做"，端口决定"怎么做"，缺省端口 = 没有该能力。

**11 个可选端口**（`EntityActions` 的 default 方法，返回 `Optional`）：

| 端口 | 覆盖 | 对应工具 |
|---|---|---|
| `EntityQueryPort` | 感知：方块/实体/射线 | 查询类 |
| `EntityMotionPort` | `move` / `look` | `body.move`、`body.look` |
| `EntityActionPort` | 挖、攻击、动作 | `body.mine` 等 |
| `BlockPlacePort` / `BlockInteractPort` | 放置、交互 | `body.place`、交互 |
| `EntityItemPort` | 背包、装备、拾取 | `body.equip`、`body.collect` |
| `EntityItemUsePort` | 使用物品（含持有时长） | `body.sequence` 的 `item_use` 步 |
| `CraftPort` | 合成 | 玩家辅助方向共用 |
| `ContainerTransferPort` | 容器搬运 | `container.transfer` 的身体分支 |
| `BlockMachinePort` | 熔炉家族 | `block.machine` 的身体分支 |
| `EntityUsePort` | 对其他实体交互 | 交互类 |

## 4. 声明与创建

**声明实体类型**：模组在 jar 里放一个纯数据文件，**不需要写任何加载器代码**。

```
<模组>.jar!/META-INF/tianshu/body_types.json
[ { "name": "orb", "width": 0.5, "height": 0.5, "fireImmune": true } ]
```

平台在**加载器的注册期**枚举所有模组、读这个文件、按 `<模组id>:<name>` 登记（`1.21.1` 的 neoForge 与 fabric 都已接入，
复用同一个 `WalkerBody` 类，按声明设置尺寸与耐火）。舟楫单独安装时仅提供使用原版实体的 `marker` 和 `stand`。至少一个内容模组声明了实体类型时，两端才会一起注册内建 `tianshu_ferry:walker` 和模组声明的类型。

联机世界中的自定义 NPC 由服务器生成并保存，客户端按相同的实体类型接收和渲染。声明这些类型的内容模组须在服务器和每个客户端安装，并由该模组在加载器上声明或校验对端依赖。仅添加本地渲染效果的客户端模组无需使用这条实体注册路径。

两条硬规则：

1. **声明只能在注册期被取走**。之后声明的类型不会被登记，`EntityTypes.declare` 直接抛 `IllegalStateException`——
   静默丢弃会让症状晚到"身体没生成"。
2. **文件必须保持版本中立**：只允许写"每条版本线语义都一样"的字段（名字、尺寸、怕火）。版本特有的东西一律放平台外壳，
   否则一个包通吃 43 个 adapter 的前提就被破坏。

**创建身体**（带身份与基座分派）：

```java
EntityBodies.create(new EntityBodySpec("mymod:npc-1", null, true));      // playerLike → 玩家型基座
EntityBodies.create(new EntityBodySpec("mymod:orb-1", "mymod:orb", false)); // 普通实体基座
```

`EntityCreationPort` 由适配器安装并按 `playerLike` 选基座；平台只负责把这条身份带到端口，不做分派。
没有安装端口时 `create` 抛 `IllegalStateException`（接线错误，而不是"暂时没有"）。

| 基座 | 何时用 | 现状 |
|---|---|---|
| fakeplayer 型（玩家语义） | 身份 = 玩家型 | **两个加载器都已实现**：NeoForge 用每个身体一个长期 `FakePlayer`（`NeoForgePlayerBodies`）；Fabric 自建 `ServerPlayer` + 回环连接（`FabricPlayerBodies`，1.21.1 的 Fabric API 还没有官方 `FakePlayer`）。动作都由该玩家执行、不拷贝背包；`/tianshu body spawn <kind> player` 在两个加载器上都已实机验证 |
| 普通实体型（`WalkerBody`） | 身份 = 普通 | NeoForge 已注册，尺寸按声明 |

执行者在 **创建时决定一次**（`BodyIdentity`）：普通身份每次动作借一个临时假玩家并把背包拷入拷出，
玩家身份直接用它自己的长期玩家（背包就是身体的背包，不拷贝）。五个动作源都从身份取玩家，**内部没有身份分支**。

持久化只存形状与背包，不存身份：重启后回来的身体一律是普通身份（玩家身份随它的玩家消失）。

**身体有三态，写盘时必须分清**：

| 状态 | 记录 | 载体 | 语义 |
|---|---|---|---|
| 已加载 | 在 | 在 | 正常 |
| 未加载（区块卸载 / 重启时还没加载） | **在**（归属、背包、装备、访问设置、最后位置与维度都留着） | 无 | 身体还在，只是不在场；区块回来时按 UUID 重新绑定 |
| 已删除（显式 `despawn`） | 删 | 删 | 这才是"不存在" |

保存时**用记录而不是"当前存活的实体"来决定写什么**，否则远处区块的身体会在下一次保存里被整条漏掉。写盘先落 `.tmp` 再原子替换；读失败时**禁止覆盖**，避免把一份好快照换成这一进程只看见的半份。


实体的自由度来自**能力位 + 端口有无**；身份由 `EntityActor.playerLike()` 表达（默认 `false`），
外观由模型与渲染决定，与身份互不影响。

> 现状（2026-11-16 已对齐）：`body.*` 归 `ToolCategory.BODY_WRITE`——**默认关闭、permission 为 EVERYONE**，
> 放行只由归属决定；写世界仍受服务器开关约束。player 型实体额外受服务器既有权限体系约束。

## 5. 行为语义与边界

| 项 | 约定 |
|---|---|
| 坐标范围 | 世界边界 ±30,000,000，越界在**值类型**上拒绝并翻译成 `INVALID_ARGS`；传送距离只受坐标范围约束 |
| 槽位 | `BodyOperations` 带代际的授予：占用与过期在同一次 CAS 决定，取消信号只认当前代 |
| 跟随 | `body.follow` 有**墙钟截止**，到点完成自己的 future 以释放槽位 |
| 序列 | 未跑完不再回 `ok:true`；中途维度变化即中止并给 `failedIndex`，不重新定向 |
| 物品使用 | 三坐标 all-or-none；`holdTicks` 上限 100 tick，与 schema 一致 |
| 单步超时 | 见各工具 `policy().withTimeout(...)`：move 35s / mine 70s / collect 125s / follow 305s |

## 6. 验收口径

| 用例 | 断言 | 现状 |
|---|---|---|
| `ACC-BDY-1` | 13 个 `body.*` 已注册、有描述与 schema、空参调用都回信封 | PASS（实机） |
| `ACC-BDY-2` | 越界坐标被拒 | SKIP：operator 门挡住合成调用方 |
| `ACC-BDY-3` | 所有者正面驱动自己的实体，命令到达端口 | SKIP：同上 |
| `ACC-BDY-4` | 旧口径：无 operator standing 的调用方碰不到身体端口（现行规则见 §2） | PASS（实机） |
| `ACC-BDY-5`（待加） | `playerLike=true` 的实体确实拿到玩家语义 | 待实现后加 |
| `ACC-BDY-6`（待加） | `playerLike=false` 的实体拿不到玩家权限 | 待实现后加 |

命令与报告位置见 [契约与验收](契约与验收.md) §3。

**玩家型身体的人工验收**（适配器侧能力，验收台够不着）：

```
/tianshu body spawn walker player     # 生成一个带玩家身份的身体
/tianshu body list                    # 确认它在列表里
# 然后：让它挖/放一次，看领地或玩家权限是否真的按玩家判定；切世界、断线各一次，确认没有残留
```
