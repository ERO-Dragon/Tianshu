# 技能撰写规范

> 依据：Agent Skills 开放规范（[agentskills.io](https://agentskills.io)、[规范原文](https://raw.githubusercontent.com/enuno/claude-command-and-control/main/docs/references/agent-skills-specification.md)）。
> 本文件只写**舟楫在规范之上加了什么**，以及踩过的坑。格式本身以规范为准，不在这里复述一遍。

## 1. 规范要求（照抄要点，便于自查）

| 项 | 要求 |
|---|---|
| 目录 | 一个技能一个目录，至少含 `SKILL.md`；可选 `references/`、`scripts/`、`assets/` |
| front matter | 必填 `name`、`description`；可选 `license`、`compatibility`、`metadata`、`allowed-tools` |
| `name` | 1–64 字符，小写字母/数字/连字符，不以 `-` 开头或结尾，无连续 `--`，**必须与目录同名** |
| `description` | 1–1024 字符，第三人称，说清"做什么"和"什么时候用"，带上让人能匹配到的关键词 |
| 正文 | 无格式限制，但要短：规范建议 `SKILL.md` 主体 **少于约 500 行**、约 5000 tokens 以内 |
| 参考文件 | 放 `references/`，**一层深**，按需读；不要深层嵌套引用链 |
| 正文语言 | 中文（与项目一致），工具 id、参数名、JSON 一律原文照抄 |

**我们的额外约束**：`SKILL.md` 的 front matter **只放规范认可的字段**。曾经往里塞过自造的 `covers:`，结果是这份技能不能被别的工具读——那是把平台内部的账写进了通用格式里。

## 2. 我们的分类法：一个技能 = 一组工具的门面

| 技能 | 装什么 | 不装什么 |
|---|---|---|
| `player-tools` | 以**玩家本人**身份行动的工具：约定（信封、档位、失败怎么读）+ `references/` 下每个工具一份 |
| `entity-tools` | 通过**身体**（实体化身）行动的工具：同上，一个工具一份 |

**两者互斥**：一个模组要么以玩家身份行事，要么派身体行事，不会同时用到两套。两份技能各自自足、不互相引用——
"也可以用另一组的那谁"这种句子把互斥关系说反了。

规则只有一条：**工具的说明跟着工具走**。每个工具在它所属技能的 `references/` 下有一份同名文件：

```
minecraft:container.transfer  →  skills/<技能>/references/container.transfer.md
```

- 文件名 = 工具名，**不带命名空间**：技能本身属于那个命名空间，每份再重复一遍 `tianshu.` 只是多花 token；
  需要显式时（外来模块）仍可写 `<namespace>.<name>.md`，查找两种都认。

- 文件名 = 能力名（去掉命名空间），**查找靠推导，不靠声明**；
- `capability.read` 带能力 id 就读它（`ToolDocs` 负责按 `skills/index.txt` 找）；
- 门禁 `verifyEveryToolHasADocument` 要求"每个 `ToolId.of` 都有同名 reference"，缺了就失败。

**为什么要有个门禁**：没有它时，新增工具忘写文档是完全无声的——说明书就是不出现，谁也不知道少了。

## 3. 每份能力说明写什么

四段，缺一不可：

```markdown
# minecraft:container.transfer

在一个容器的某个槽位与玩家背包的某个槽位之间移动物品。

## 调用
{"id":"minecraft:container.transfer","args":{"x":120,"y":64,"z":-30,"containerSlot":0,"playerSlot":36,"count":5,"toPlayer":true}}

## 返回
{"ok":true,"result":{"moved":5,"item":"minecraft:diamond","from":0,"to":36},"durationMs":7}

## 失败与下一步
- `toPlayer:false` 且目标槽位已有不可堆叠物品 → 先清空或换槽位
- 数量对不上：`count` 是上限，实际移动量看 `moved`
```

要求：

1. **调用**里的参数名必须来自该工具的 `argsSchema`，不能凭印象写；
2. **返回**里的字段必须能在代码里找到（`resultType()` 的记录/类），不能凭印象写；
3. **失败与下一步**要写这个工具**特有**的失败，以及"该做什么"——通常**不是**重发同一次调用；
4. 长度：一般 10–20 行。长到需要目录，说明该拆了。

### 反面例子（都真实出现过）

| 写法 | 为什么不行 |
|---|---|
| `参数：见 schema` | 读者还是要再查一次；这份文档等于没写 |
| `server.say` 的参数写 `message` | 真实参数是 `text`——猜的字段名比没有更糟 |
| `container.inspect` 返回写 `slots` | 真实返回是 `{open, title, entries[]}`；字段名错等于教错 |
| 把 `full.md` 写成 7 行"见 tool.catalog" | 全权档 14 个具体 id 一个没写，读者拿不到任何可执行信息 |

## 4. 写 `SKILL.md` 的几条硬规矩

1. **不写具体模组名**。"天枢没有实体所以不要传 body" 这种句子在换一个模组后就是错的；写成"没有身体的调用方不要传 `body`"。
2. **不重复别处的约定**。信封格式、档位含义写在各自技能的 `SKILL.md` 里一次；工具说明里不再复述。
3. **不列全参考清单**。40 多份参考逐个列进 `SKILL.md` 会让它变成目录；写清"`references/` 下按 id 命名，用 `capability.read` 带 id 读"即可。
4. **档位不是技能属性**，是工具属性：不要在技能里写"本技能属于保守档"。要写"这件事需要哪一档，去对应参考看"。
5. **例子必须是能照抄的形状**：真实 id、真实参数名、真实信封；不要 `{...}` 一带而过（除非字段确实随工具而变，且说明"字段由该工具决定"）。

## 5. 提交前自查

- [ ] `name` 与目录同名、全小写连字符；`description` 说清"做什么 + 什么时候用"，≤1024 字符
- [ ] front matter 没有自造字段（要放平台内部信息，只能进 `metadata`）
- [ ] 正文 < 500 行；细节在 `references/`，一层深
- [ ] 新增/改动了工具？`references/<namespace>.<name>.md` 同名文件存在且字段核对过
- [ ] 文档里出现的每个参数名、返回字段名，都能在代码里指出来
- [ ] `./gradlew verifyEveryToolHasADocument` 通过
- [ ] 没有把别的技能的约定抄一遍

## 6. 我们删掉过的东西（别再长回来）

| 曾经做过 | 为什么删 |
|---|---|
| front matter 里的 `covers:` | 自造字段，技能不再可移植 |
| `coverage.txt` 索引（技能 → 能力 id 列表） | 索引会和实际发货漂移；id 推导路径就够了 |
| 读技能时按可见性"拼装"参考段落 + 末尾"你能用其中哪几个" | 一个能力一份文档之后没有"半适用"这回事，补偿机制多余 |
| `docs/tools/` 独立目录 | 文档应住在技能自己的 `references/` 里 |
| 按"技能/文档"再分一层 `tool-docs`、`player-tools` | 分类法一拍脑袋就多一个目录；只保留"约定"与"能力说明"两类 |

判据一句话：**如果一个机制是为了弥补另一个机制造成的麻烦，先问那个机制该不该存在。**
