# 天枢模块架构

> 本文描述**当前生效的架构**：产物形态、模块职责、依赖模型、载荷归属、装配方式与边界门禁。
> 施工过程、阶段验收与踩坑记录见 [模块拆分实施记录](模块拆分实施记录.md)。

## 1. 系统形态

天枢 = **一个宿主（北辰）+ 一组可选功能模组 + 一个共享原生库**。

宿主不认识任何具体功能模组：它只认"提供者"这一层接口。功能模组各自独立成 jar，装谁是谁，
删掉哪个都不需要改宿主的代码，也不用重新编译。

| 层 | 组成 | 发布方式 |
|---|---|---|
| 北辰 | `tianshu-api` + `tianshu-core` + `tianshu-client` + 一个平台 adapter | 合成**一个** jar |
| 功能模组 | 听澜 / 回响 / 织言 / 辅星 | 各自一个 universal jar |
| 共享库 | `tianshu_libs`（native 运行时） | 独立 jar，保持现状 |
| 开发夹具 | `tianshu-testkit` | 永不发布 |

**包名不表达模块边界**。所有代码都在 `com.rheinmetal.tianshu.*` 下，`client` / `core` 这些顶层包会
同时横跨多个 Gradle 模块（例如 `client.settings.registry.TianshuSettingsRegistrySource` 在 api，
而 `client.settings` 其余实现类在 client）。**判断一个类属于哪个模块，看它在哪个 Gradle 模块的
`src/main` 下**，不要看包名。

## 2. 产物与标识

| 产物 | modid | 说明 |
|---|---|---|
| 北辰 | `tianshu` | 本体；config 目录 `config/Tianshu/`，与旧版一致 |
| 听澜 | `tianshu_intake` | ASR + IR + 思衡（IA） |
| 回响 | `tianshu_echo` | TTS |
| 织言 | `tianshu_weaving` | 云端 LLM + embedding |
| 辅星 | `tianshu_auxilium` | 对话大脑 |
| 共享库 | `tianshu_libs` | native 运行时，四个功能模组都依赖它 |

发布矩阵：**北辰按「平台 × 版本」出包，功能模组只有一份 universal jar**。当前平台目录只有
`tianshu-adapter/neoforge-1.21.1`；加平台 = 复制这个目录改名，内核与功能模组不动。

## 3. 模块职责

| 模块 | 中文名 | 负责 |
|---|---|---|
| `tianshu-api` | 契约层 | 信封与路由常量、协议基类载荷、装配 SPI（provider/registrar/registry）、宿主端口接口、映迹与事实载荷 |
| `tianshu-core` | 内核 | `CoreManager`、模块生命周期与能力注册表、`ProtocolRuntime`（broker / executor lanes）、模型传输与下载/删除状态机 |
| `tianshu-client` | 客户端 | 世界会话状态机、设置框架（布局/草稿/会话/校验）、映迹（presence）、音频实现、诊断 |
| `tianshu-adapter/neoforge-1.21.1` | 平台层 | **唯一**与 Minecraft / NeoForge 绑定的代码：`@Mod tianshu`、平台端口实现、按键与 HUD 挂载 |
| `tianshu-intake` | 听澜 | ASR 识别管线、IR 文本修复与词命中、思衡（对话仲裁与评分） |
| `tianshu-echo` | 回响 | TTS 合成、播放与语音克隆 |
| `tianshu-weaving` | 织言 | 云端 LLM 请求、流式响应、embedding |
| `tianshu-auxilium` | 辅星 | 对话大脑：上下文装配、提示编排、回合执行、记忆与检索 |

api / core / client / 四个功能模组**零 Minecraft 依赖**，平台无关性由门禁强制（见 §11）。

## 4. 依赖模型

### 4.1 方向

```
adapter ──→ client ──→ core ──→ api
                ↘        ↗
              feature-*
```

功能模组依赖 `api`（经 `core` 传递），彼此之间只按 §4.3 的矩阵互相引用。

### 4.2 模块间的三种关系

任意两个功能模组之间只可能处于三种状态之一，这是决定代码怎么写的前提：

| 关系 | 含义 | Gradle | 代码 | 守卫 |
|---|---|---|---|---|
| **前置依赖** | 没有它本模组就是残废 | `api` / `implementation` 硬依赖 | 直接 `import` | 不需要，类必然在 |
| **联动** | 装了多一项能力，不装照常跑 | `compileOnly` | 只能经 `bridge` 包触碰对方类型 | 必须，`InstalledMods.isLoaded(...)` 之后才加载该包 |
| **无关系** | 谁也不认识谁 | **不声明任何依赖** | 不 `import` | 不适用 |

**无关系是默认状态**，也是绝大多数组合的状态。它不是"待定的联动"——三条声明（Gradle、`neoforge.mods.toml`、
`fabric.mod.json`）里一条都不能留，否则就是在告诉加载器一个不存在的关系。

前两种关系的平台元数据还必须与 Gradle 对齐：前置依赖写 `type="required"` / `depends`，联动写
`type="optional"` / `suggests`。任一侧不一致都会出现"构建说必需、加载器说可选"的矛盾，门禁会拦（§11）。

### 4.3 当前依赖矩阵

| 边 | 类型 | 理由 |
|---|---|---|
| 辅星 → 织言 | 前置依赖 | 没有推理就没有回答 |
| 辅星 → 听澜 | 联动 | 对话域可选：有它就接入语音投递与仲裁，没有则只剩文字与事件路径；全部经 `bridge/IaDialogueBridge` 并由 `InstalledMods` 守卫 |
| 辅星 → 回响 | 联动 | 单向能力：装了才会说话，不装只是不出声 |
| 听澜、织言、回响 | 叶子 | 与任何功能模组都**无关系** |

叶子不是"暂时没有依赖"，而是明确的架构结论：听澜只做识别与仲裁，合成归回响、推理归织言，
它不需要也不应该认识它们。将来真要联动，按 §4.2 显式加边、三处同时声明，门禁会要求这条边真的有代码在用（§11）。

### 4.4 双向对话协议：词汇归仲裁者，依赖仍是单向

对话是双向的：`DIALOGUE_DELIVERY` 由思衡产出、辅星消费；`DIALOGUE_PARTICIPANT_REGISTER` /
`UNREGISTER`、`DIALOGUE_SESSION_CONTROL` 由辅星产出、思衡消费。

但**整套对话载荷只有一个所有者**：它们全部放在听澜一侧，听澜的源码对辅星**零 import**，而辅星有 12 个
文件直接使用这些类型。两条流向共用同一份词汇，因此**代码方向是单向的，不会形成依赖环**。

所以给这条边分类不是"能不能"的问题，是产品意图的问题：

| 选择 | 含义 | 代价 |
|---|---|---|
| **前置依赖**（当前） | 没有听澜就没有对话输入口，辅星装不上也不该装 | 无守卫、无桥接；但"没听澜的辅星"不存在 |
| **联动** | 辅星可独立安装，不经对话协议的那部分（事件采集等）照常工作，对话路径经 bridge + `InstalledMods` 守卫关闭 | 把上述 12 处直接引用收拢进一个 `bridge` 包并接口化，是实打实的重构 |

判断依据是**辅星有没有第二条输入通道**。等"辅星的第二输入口（文字模式）"落地后，联动的意义才完整——
没有听澜时辅星仍有一条对话入口。在此之前改成联动，只会得到"能装、但只能自言自语"的形态：
没有听澜就没有任何东西把对话投递给它。

现在按「联动」执行（见 §4.3）：整套对话词汇仍由听澜持有，辅星只经 `bridge/IaDialogueBridge` 触碰它，
且该桥仅在 `InstalledMods.isLoaded("module.ia")` 为真时实例化。所以"没装听澜"时辅星不会静默空壳——
它仍然有文字输入与事件路径，只是接不到语音投递与仲裁。

代价与收益都记在 [未完成事项](未完成事项.md)：桥只有 12 个文件里的一处引用，换来的是一条真正可选的边。

## 5. 载荷归属

一个 `*Payload` 类放在哪个 jar，由**谁生产它**决定，不由谁需要它决定。

### 5.1 判据

**第一步**：载荷归"生产者模组"（创建并投递它的模组）。协议基类载荷归 api。

**第二步**：消费者怎么用，取决于 §4.2 的关系——

1. 北辰（core / client / adapter）自己要引用 → 载荷**必须**在 `tianshu-api`。
2. 生产者对消费者是前置依赖 → 载荷留在生产者 jar，直接 import。
3. 生产者对消费者是联动 → 载荷留在生产者 jar，消费者只经 `bridge` + `InstalledMods` 守卫使用。
4. 只有一个模组用的载荷 → 它自己的 jar，用 `PayloadType.of(name, class)` 自登记，内核零改动。

**不允许**为了让消费者少写一个守卫而把功能载荷塞进 api——那是把两个模组之间的契约升级成内核词汇。

### 5.2 当前分布

| 位置 | 数量 | 内容 |
|---|---|---|
| `tianshu-api` | 15 | 协议基类 6（`Cancel` / `Empty` / `Text` / `ModuleStatus` / `RuntimeInterrupt` / `TriggerRegistry`）+ 映迹与事实 9（`Presence*` 7 + `FactField` / `FactValue`） |
| 听澜 | 16 | 对话/仲裁/会话/投递/参与者/评分 12 + `IrResultPayload` / `IrModuleMatch` / `IrObjectMatch` + `AsrSpeechActivityPayload` / `AsrTextPayload` |
| 织言 | 9 | 8 个 `LLM*` + `LlmStatusPayload` |
| 回响 | 12 | 7 个 TTS 内部类型 + 5 个契约类型（`TtsSpeak` / `TtsVoiceOptions` / `TtsTextInputMode` / `TtsPlaybackPlacement` / `TtsControl`） |
| 辅星 | 1 | `DialogueContextInputPayload` |

映迹的 9 个载荷留在 api，是因为映迹实现在 client，而四个功能模组都要读这些事实。

## 6. 装配

### 6.1 模块自注册

模块在自己的加载器入口里登记一个工厂；内核每个世界会话读一次注册表：

```java
// 模组的入口壳（见 §7.1）
XxxModuleRegistration.announce();

// 内核每个世界会话
new ClientTianshuModuleAssembler(kernelProviders, context, moduleSettingsSources)
```

- `TianshuModuleProviderFactory` 按会话拿到 `TianshuModuleAssemblyContext`，返回该会话的 provider；
- `TianshuModuleProvider.contribute(registrar)` 用 `addModule(installer)` + `addSettings(page)`
  两个入口完成装配，没有第三个入口；
- 内置模块（ONNX 运行时、映迹、思衡）与外部模组走**同一条**路径，没有内置特权；
- 模块缺席时 `addSettings` 根本不会被调用，设置页自然消失。

不用 `ServiceLoader`：FML 类加载器下不可靠，且无法表达顺序。

### 6.2 装配上下文给模块什么

`TianshuModuleAssemblyContext` 只交三样东西：`IGameEnvironment` / `IAudioBridge` /
`ModuleRuntimeAccess`、两个宿主信号、以及下列端口。**模块拿不到** `CoreManager`、`ProtocolRuntime`、
`ClientConfig`，也拿不到任何功能模组的类型。

| 端口 | 作用 |
|---|---|
| `ClientPorts` | 装配期客户端服务：`scheduler`、`uiHost`、`texts`、`filePicker`、`settingsLayers`、`audioDevices`、`configStores`、`modelLoadQueue` |
| `ModuleRuntimeServices` | 设置页需要的最小内核面：`findService` / `requireService` / `requestRefresh` |
| `ModuleConfigStores` | 按 moduleId 发放 `ModuleConfigStore`；`moduleDirectory()` 给模块数据根目录 |
| `NamedObjectIndex` / `NamedObjectDictionary` | 内核只持索引的**生命周期端口**；字典快照是平台事实，索引本体属听澜 |
| `WorldFacts` / `WorldFactsSource` | 平台只报事实（`kindId` 是字符串），辅星自己映射成 `AXScopeKind` |
| `InputSignals` | 输入通道总线：平台发布（按住 / 松开 / 提交文本 / 自定义按键 id），模块订阅 |
| `KeyBindings` | 模块声明自己的按键（`id` + 默认键码 + 分类），平台统一注册，按下时发 `key.<id>` 通道；默认键先声明者占用，后来者注册为未绑定 |
| `ClientKeyBindings` | 模块的设置行请求平台打开改键界面——绑定是 MC 对象，只有平台能碰 |
| `GameEventPort` / `GameEventFacts` | 平台只采样（血量/饥饿/维度/群系/死亡信息），探针与措辞在辅星 |
| `KeywordTableReloadPort` | 平台读资源包字节，听澜解析词表 |
| `InstalledMods` | 联动判据：问"某个可选伙伴装了没" |
| `TianshuRuntimePorts` | 会话**之前**就要用的端口（如词表重载、世界事实）由模块在 jar 加载期注册；查不到时的读法是"伙伴不在"（fail-closed） |

### 6.3 缺省语义

| 情况 | 行为 |
|---|---|
| 模块未注册 | 设置页无该页；能力未注册；投递进死信 |
| 模块注册但启动失败 | 保留失败状态供诊断，其他模块继续 |
| 能力缺失 | 调用方先用 `CoreCapabilityProbe` 探测再决定是否投递 |
| 联动伙伴缺席 | `InstalledMods.isLoaded` 为假 → 走 `NONE` 实现，安静降级 |
| 映迹无活动 | HUD 显示空闲，无需特殊处理 |

## 7. 加载器入口与产物构成

### 7.1 两个薄壳，一个公告点

功能模组的业务代码平台无关，所以每个模组只有两个入口类，且都只做一件事：

```
src/main/          XxxModuleRegistration.announce()   ← 「本模组公告什么」的唯一清单
src/neoforgeEntry/ @Mod 壳            → announce()
src/fabricEntry/   ModInitializer 壳  → announce()
```

入口类不放 `src/main`，这样 `verifyNoPlatformImport` 仍然只覆盖业务代码。**壳里不写注册逻辑**：
加一个 provider 只改 `announce()` 一处，两个加载器不可能漂移。

入口源集不是打包细节：**它才是"这个模组存在"的依据**。开发运行按 source set 装配，某个功能模组的
`mods{}` 声明若只含 `src/main`，它会被列进模组表，却没有任何 `@Mod` 构造器执行——不注册、不装配、
设置页不出现。生产 jar 因为带入口类不受影响，所以这类失配只在 `runClient` 里暴露（门禁见 §11）。

### 7.2 universal jar 的构成

每个功能 jar 由该模组的 `jar` 任务直接装配，同时包含：

| 内容 | 读取方 |
|---|---|
| `META-INF/neoforge.mods.toml` | NeoForge / FML |
| `fabric.mod.json` | Fabric Loader |
| `XxxNeoForgeMod.class` | NeoForge 入口 |
| `XxxFabricMod.class` | Fabric 入口 |

这就是 universal 的含义：**跨加载器**，而不只是跨操作系统。`verifyUniversalModuleJars` 校验这五项
齐备（§11）。

**当前缺口**：Fabric 版北辰（adapter）尚未实现，所以把功能 jar 装到 Fabric 上会因缺少 `tianshu`
而拒绝加载——这是预期行为，比"加载成功但什么都不干"更诚实。Fabric 侧的版本范围目前也是字面量
（`>=1.21 <1.22`），NeoForge 侧走 `minecraft_version_range` 属性，两套语法不能直接共用。

### 7.3 开发运行：从哪启动决定装什么

`runClient` 在每个项目里都有，但**只有 adapter 真正启动游戏**；根项目与四个功能模组的 `runClient`
只是委托给它，装配集合由启动位置决定：

| 启动位置 | 装配 |
|---|---|
| 仓库根 `gradlew runClient` | 四个功能模组全装（完整形态） |
| `tianshu-adapter/neoforge-1.21.1` | 只有北辰（第三方集成看到的形态） |
| `tianshu-intake` / `tianshu-echo` / `tianshu-weaving` | 北辰 + 该模组 |
| `tianshu-auxilium` | 北辰 + 辅星 + 听澜 + 织言（硬依赖），**不含回响** |

辅星那一行是这套设计的重点：从辅星启动不会装上回响，语音通道于是自然落到 `AXSpeechSink.NONE`，
**联动降级在日常开发里就被覆盖**，不用等到发布前才手拆 jar 验证。

模块集合来自 §4.3 的矩阵（adapter 读根项目的 `requiredFeatureEdges`），不是另维护的清单；
`-PfeatureMods=` 可覆盖，空值等价于"只装北辰"。启动时会打印一行
`tianshu dev run: started from '<位置>', installing <集合>`，不用猜。

## 8. 联动的落地范式

以辅星 → 回响为例。联动不是"加个 `if`"，它需要三件套，少任何一件，缺那个模组时就会在类加载阶段炸：

1. **消费者自己的值类型** —— `speech/AXSpeechUtterance` + `speech/AXSpeechSink`，不含对方任何类型；
   模块其余部分只认它。
2. **唯一的桥** —— `bridge/EchoSpeechBridge`：整个模块里**只有这个类** import 对方的载荷，负责把
   值类型翻译成协议投递。
3. **一个选择点** —— `bridge/AXSpeechSinks.forRuntime`：`InstalledMods.isLoaded(对方 moduleId)`
   为真才实例化桥，否则返回 `AXSpeechSink.NONE`。装配与模块都走这一个入口，决策不会分叉。

辅星对回响已按此范式落地：`AXOutputProcessor`、`AXProtocolSpeechOutlet`、`AXModule`、
`AuxiliumModuleProvider` 全部只认 `AXSpeechSink`，`tianshu-auxilium/src/main` 里出现 `Tts*` 载荷的
文件只剩 `EchoSpeechBridge` 一个。

双向协议不适用（§4.4）：辅星与听澜之间无法让词汇分居两侧。

## 9. 配置、语言与资产归属

| 内容 | 归属 |
|---|---|
| 功能模组设置 | `config/Tianshu/module/<moduleId>.properties`；键名与默认值在**模块内**（`IntakeConfig` / `EchoConfig` / `WeavingConfig` / `AuxiliumConfig`） |
| 内核设置 | `config/tianshu-client.toml`（debug、映迹 HUD） |
| 界面文案 | 每个模块持自己的语言分片 `src/main/lang/{zh_cn,en_us}.json`；无人认领的键（按键名）在根 `lang/`。`mergeLang` 合并成唯一的 `assets/tianshu/lang/*.json`，由北辰发出 |
| 模型清单与读取器 | `AsrModel*` → 听澜、`LlmModel*` → 织言、`TtsModelInfo` → 回响 |
| 模型传输与状态机 | `tianshu-core/model`（`ModelDownloadHttpClient`、`HuggingFaceDownloader`、`DownloadGate`、`ModelAvailabilityRefresher`、`ModelDeletionRunner`），作为**公开**的内核设施 |

语言分片的依赖方不是 Maven 依赖，语言归属由 `mergeLang` 与各模块的 `*LanguageBoundaryTest` 共同约束：
生产代码里不放界面文案。

模型清单这类 **classpath 资源的逐文件归属**（`asr_model.json` / `llm_models.json` / TTS 音色资源等）
另见 [资源归属清单](资源归属清单.md)，本文只给定归属原则。

## 10. 冻结契约

拆出模块后即为对外契约，改名即 breaking change：

- **信封与路由**：`TianshuEnvelope`、`EnvelopeHeader`、`PacketType`、`PayloadType`、`TargetMode`、
  `Priority`、`DeliveryPolicy`、`CancellationScope`、`FailurePolicy`、`BrokerType`、`ExecutionLane`
- **载荷**：全部 `*Payload` record、`ITianshuPayload`
- **常量**：`ProtocolCapabilities`、`ProtocolTopics`、`ProtocolModuleIds`
- **能力**：`RuntimeCapability`、`RuntimeCapabilityStatus`
- **装配**：`TianshuManagedModule`、`TianshuModuleInstaller`、`TianshuModuleProvider`、
  `TianshuModuleProviderFactory`、`TianshuModuleProviderRegistry`、`TianshuModuleRegistrar`、
  `TianshuModuleAssemblyContext`
- **端口**：`IGameEnvironment`、`IAudioBridge`、`LogSink`、`DiagnosticSink`、`ClientScheduler`、
  `ClientTextProvider`、`ClientUiHost`、`ClientFilePicker`、`InputSignals`、`KeyBindings`、
  `ClientKeyBindings`、`InstalledMods`、
  `TianshuRuntimePorts`、`KeywordTableReloadPort`、`GameEventPort`、`WorldFactsSource`
- **设置**：`TianshuSettingsRegistrySource` + 设置模型（Panel / Option / Status / Action）
- **对话**：`DialogueParticipantDescriptor`、`DialogueClaimProfile`、`DialogueClaimRule`、
  `DialogueClaimCondition`、`DialogueClaimConditionType`
- **映迹**：`PresenceActivityPayload`、`PresenceWorldEventPayload`、`PresenceChatMessagePayload`

**不冻结**：`ProtocolRuntime` 内部实现、broker 实现、executor 策略、各模块内部服务类。

`PayloadType` 是开放注册表（`of(name)` / `of(name, class)`），模块可以引入自己的载荷类型而不改内核。

## 11. 边界门禁

全部挂在 `./gradlew check` 上。规则跨模块，因此都注册在根项目。

| 门禁 | 断言 |
|---|---|
| `verifyFeatureIsolation` | 功能模组的 `src/main` 只能沿 §4.3 的边 import 其他功能模组 |
| `verifyFeatureOptionalDependencies` | 矩阵与代码双向相等：每条边在三处（Gradle / `neoforge.mods.toml` / `fabric.mod.json`）都有正确类型的声明，**且确有源码在用**；反过来，任何矩阵里没有的功能模组依赖或声明都报错。判"是否在用"按**目标模块实际拥有的包**算——思衡在听澜里但包名是 `function.ia` |
| `verifyHostHasNoFeatureDependency` | 北辰四个模块的源码无功能模组 import，**且** `build.gradle` 无功能模组依赖——没有 import 的构建依赖是同一件事的另一半 |
| `verifyNoPlatformImport` | 非 adapter 模块禁止 import `net.minecraft.` / `net.neoforged.` / `org.lwjgl.` / `com.mojang.blaze3d.` |
| `verifyUniversalModuleJars` | 每个功能 jar 真的含两套清单、两个入口壳与 `XxxModuleRegistration.class` |

除构建门禁外，还有一类用 JUnit 写的架构测试（同样随 `check` 运行）：

| 测试 | 断言 |
|---|---|
| `ModuleEntrypointRegistrationTest` | 每个加载器壳都调同一个 `announce()`；Fabric 清单的 entrypoint 就是随包发出的那个类；两份清单 modid 一致；对北辰的依赖是 required |
| `ModuleAssemblyRuntimeBoundaryTest` | 功能模组与平台装配代码不得接触 `ProtocolRuntime` / `ProtocolExecutorManager`；装配上下文不暴露聚合配置 |

**改动 §4.3 的矩阵时必须同时改 `build.gradle` 里的门禁表**，否则门禁会按旧矩阵放行或误拦。

## 12. 扩展指南

### 12.1 新增一个功能模组

1. 新建 Gradle 模块 `tianshu-<name>`，依赖 `api project(':tianshu-core')`；包名 `function.<name>`。
2. 写 `src/main` 的业务代码与 `XxxModuleProvider`（或若干 `TianshuModuleInstaller`）。
3. 写 `XxxModuleRegistration.announce()`，在里面对 `TianshuModuleProviderRegistry` 登记。
4. 加 `src/neoforgeEntry` 与 `src/fabricEntry` 两个薄壳，各自调用 `announce()`；`build.gradle` 照抄
   任一现有模组的 `sourceSets` 与 `jar` 段。
5. 加 `META-INF/neoforge.mods.toml` 与 `fabric.mod.json`，两份的 modid、依赖类型必须一致。
6. 若与其他模组有边，把边写进根 `build.gradle` 的 `requiredFeatureEdges` / `optionalFeatureEdges`。

### 12.2 新增一个平台或版本

复制 `tianshu-adapter/neoforge-1.21.1` 改名，改 `adapter.properties`，实现同名端口。内核与功能模组不动。

### 12.3 把单向下沉成联动

按 §8 的三件套做：先在消费者模组里定义不含对方类型的值类型，再写唯一的桥，最后加选择点。
**不要**把载荷搬进 api 来省掉守卫（§5.1）。

## 13. 范围外

以下明确不做，不要以"顺便修一下"的名义引入：

- GUI 渲染层重写
- 辅星内部算法改进（与拆分无关）
- native 库瘦身（体积不是目标）
- IR / IA 算法改进
- 新的产品功能
- 兼容 shim / 过渡层（未上线，直接切目标形态）

**要做但还没做**的事项不在这里，见 [未完成事项](未完成事项.md)。两者的区别是：范围外是决定不做，
未完成是决定要做、只是还没排到。
