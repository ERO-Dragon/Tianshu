# 资源归属清单

模块拆分之后，**资源文件也要跟着模块走**：一个功能模块的模型清单、提示词、词表，应该由该模块的
jar 发布，而不是被折进 `tianshu-core` 或 `tianshu-client`。本文是这份归属的**唯一清单**，也是迁移
记录。

## 1. 判定规则

| # | 规则 | 结果 |
|---|------|------|
| R1 | 只被**一个**功能模块的业务代码读取 | 资源随该模块发布（放在该模块的 `src/main/resources` 内） |
| R2 | 被**两个及以上**模块读取（拥有它的功能模块 + 客户端设置页 + 平台适配层） | 资源与读取器都随 owner 发布；若平台侧确实要读，只给**端口**（`api`），不在 kernel 里留功能模块包名 |
| R3 | 平台资源系统的资源（`ResourceLocation`：语言、shader、mixin 清单、loader 清单） | 留在 `tianshu-client`（语言）或 `adapter`（shader / mixin），因为它们不是"单文件 classpath 资源" |
| R4 | 同一种资源只允许存在一份 | 迁移后旧位置不得留副本，否则哪一份生效取决于 classpath 顺序 |

R2 早期版本的取舍是"数据随 owner、读取器留 kernel"，理由是读取器被"功能模块 + 设置页 + 平台配置"共用。
该理由已随拆分完成而失效（设置页进了各模块、`ClientConfig` 不再实现任何功能配置接口），因此
`AsrModelManager` / `LlmModelManager` / `TtsModelInfo` 现已**随 owner 一起搬进功能模块**，见第 5 节。

## 2. 模型清单（classpath 资源）

| 资源 | 迁移前 | 迁移后（随 owner 发布） | 读取器（随 owner 发布） | 使用方 |
|------|--------|------------------------|---------------------|--------|
| `asr_model.json` | `tianshu-core/src/main/resources/com/rheinmetal/tianshu/constant/` | **`tianshu-intake`** `…/model/catalog/asr_model.json` | `intake.model.AsrModelManager` | intake 引擎启动 / 热词；听澜设置页 |
| `llm_models.json` | 同上 | **`tianshu-weaving`** `…/model/catalog/llm_models.json` | `weaving.model.LlmModelManager` | weaving 采样默认值；织言设置页 |
| `llm_embedding_models.json` | 同上 | **`tianshu-weaving`** `…/model/catalog/llm_embedding_models.json` | `weaving.model.LlmModelManager` | weaving RAG / embedding 解析；织言设置页 |
| `tts-model.json` | 同上 | **`tianshu-echo`** `…/model/catalog/tts-model.json` | `echo.model.TtsModelInfo` | echo 下载 / 合成引擎；回响设置页 |

`tianshu-core/src/main/resources` 在本次迁移后不再持有任何模型清单（`constant/` 目录树已清空），
`tianshu-core/model` 只保留传输与状态机（见第 5 节）。清单缺失时读取器返回空集合，因此"文件没跟着模块走"不会在编译期报错——这
正是要出这份清单的原因；`ModelCatalogOwnershipTest` 把路径与 owner 钉成断言。

## 4. 迁移后必须同步的东西

1. **加载路径**：读取器里的 classpath 常量（本次改了 4 个：`AsrModelManager`、`LlmModelManager` ×2、
   `TtsModelInfo`）；`IntentKeywordLoader` 从"只接受平台推送"改成"自读 + 可覆盖"。
2. **源码级测试里的路径**：`ModelArchiveDownloaderTest` 直接按文件路径读 `tts-model.json`，已改指
   `../tianshu-echo/…`。
3. **打包**：模型清单现在跟模块 jar 走（`tianshu_intake` / `tianshu_echo` / `tianshu_weaving`），
   所以裁剪掉某个功能模块时，它的模型清单也一起消失——这是本次迁移要达到的效果。
4. **不要留旧副本**：`assets/tianshu/ir-intent-keywords.json` 与 `constant/*.json` 已删除，不再存在
   "两个位置哪份生效"的问题。

## 5. 读取器也已搬进功能模块（2026 修订）

早期版本把读取器留在 kernel，理由是"设置页与平台配置直接引用"它。这个理由**已经失效**：

- 设置页搬进了各自的模块（`IntakeSettingsRegistrySource` / `WeavingSettingsRegistrySource` / …）；
- 平台配置（`ClientConfig`）不再实现任何功能模组的配置接口，只剩内核自己的 debug 与语音资源路径。

因此 `AsrModelInfo/Manager/Downloader` → `tianshu-intake`，`LlmModelInfo/Manager/Downloader` → `tianshu-weaving`，
`TtsModelInfo` → `tianshu-echo`。`tianshu-core/model` 只保留**传输与状态机**：
`ModelDownloadHttpClient`、`HuggingFaceDownloader`、`ModelArchiveDownloader`、`ModelDownloadSourcePolicy`、
`ModelDownloadResumeMetadata`、`DownloadGate`、`ModelAvailabilityRefresher`、`ModelDeletionRunner`，
以及下载/删除回调接口。

传输层是**有意公开的 kernel 设施**（`public` 类与其 `RetryPolicy` / `DownloadControl` / `ProgressListener`
等成员），因为它是被多个模块复用的机制，而不是某个模块的实现细节。判据与配置一致：**机制留内核、清单与策略归模块**。

## 6. 事实语义化：presence 只产出字段

- **映迹不再渲染**：`PresenceContextFactMapper`（client）只写 `fields`（类型化事实），
  `tianshu.presence.context.*` 的 28 个语言键随之删除（在 `tianshu-client/src/main/lang/` 分片里）。
  事实的措辞只属于消费方：AX 侧由 `AXDynamicKnowledgeFormatter` + `ax_prompt_texts.json` 模板负责。
- **IA 自己摊平**：`DialoguePresenceContextMapper`（core）在自身范围内把 `fields` 摊平成
  `Map<String,String>`——`Number` 用 `%.1f`、`Count` 用十进制整数、`Record` 展开成 `slot.member` 点号名，
  空值丢弃。类型化值转字符串的规则因此只存在于消费方，生产者不再提供扁平镜像。
- **事实只给展示方用**：`CONTEXT_FACT` claim 条件已删除（没有生产模块使用），事实不再参与仲裁。
  `DialogueContextSnapshot.facts` 仅作为投递快照里的“本轮带上了哪些 fact”供消费方展示，值仍是字段摘要
  `name=value;name=value`，不是自然语言。
- **契约过渡字段已删除**：`PresenceContextSnapshotPayload.FactPayload` 不再有 `text` / `nativeValues`，
  `fields` 是唯一数据面；`isEmpty()` 只看 `fields`。
