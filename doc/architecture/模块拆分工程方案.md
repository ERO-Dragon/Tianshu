> 状态：方案定稿，执行中（阶段 0）

## 0. 命名与发布矩阵

| 项 | 决定 |
|---|---|
| 本体 modid | **`tianshu`**（保持不变，`config/Tianshu/` 与存档零迁移） |
| 本体中文名 | **天枢-北辰** |
| 功能模组 modid | `tianshu_asr` / `tianshu_tts` / `tianshu_llm` / `tianshu_ax` |
| Java 包名 | 全部保持 `com.rheinmetal.tianshu.*` |
| 本期发布矩阵 | **只做 neoforge-1.21.1**；其余平台后续加 adapter |

北辰 = api + core + client + **一个平台 adapter**，三者不混装。

## 1. 目标

把天枢从「一个整体模组」变成「一个平台 + 几个可选插件」：

1. **内核与游戏版本无关** —— 换 MC 版本只改 adapter，内核不重编
2. **功能可单独安装** —— 第三方可以只用 TTS 播报、只用 ASR 做指令，或完整对话
3. **同一 bug 只修一处** —— 公共逻辑单实例化，不再有三份漂移的副本
4. **可跨加载器** —— 换 Fabric 只写 adapter

**明确不追求**：安装体积。`tianshu_libs`（42MB native 库）作为共享库保持现状。

### 2.1.1 参照实现：Tianshu-libs 的 universal 范式

**参照工程**：`D:\AIPROJECT\Tianshu-libs`（与天枢同级目录），该范式已在 `tianshu_libs` 上验证可用。

#### 工程结构

```
tianshu-libs/
├── common/        平台无关核心（纯 Java；api 依赖全部 native）
├── neoforge/      NeoForge adapter（net.neoforged.moddev + com.gradleup.shadow）
├── fabric/        Fabric adapter
├── buildSrc/      共享构建逻辑
└── gradle.properties
```

#### universal jar 的构成（根 `build.gradle` 的 `universalJar` 任务）

```groovy
tasks.register('universalJar', Zip) {
    archiveFileName = "${mod_id}-${mod_version}-universal.jar"
    from({ zipTree(project(':neoforge').tasks.shadowJar.archiveFile) })   // ① 含 META-INF/neoforge.mods.toml
    from(project(':fabric').sourceSets.main.output)                       // ② 含 fabric.mod.json
    from('neoforge/src/main/templates/META-INF/mods.toml') { into 'META-INF' }  // ③ Forge 兼容
}
```

**三份元数据并存，各加载器只读自己那份**：

| 加载器 | 读取的元数据 |
|---|---|
| NeoForge / FML | `META-INF/neoforge.mods.toml` |
| Fabric Loader | `fabric.mod.json` |
| Forge | `META-INF/mods.toml` |

这就是 “universal” 的真实含义：**跨加载器**，而不只是跨操作系统。

#### 版本范围写法（宽范围覆盖多版本）

```properties
minecraft_version=1.20.4
minecraft_version_range=[1.20,1.22),[26.1,27)
neo_version_range=[20,22),[26.1,27),[47,48)
loader_version_range=[1,)
```

一个 jar 通过宽 `versionRange` 同时被多个 MC 版本接受。

#### 依赖打包策略

| 依赖类型 | 方式 | 原因 |
|---|---|---|
| `common` 模块 | `implementation project(':common')` + shadow | 平台无关代码合并进 jar |
| jjml（LGPL） | `jarJar` 嵌套 jar | 许可证合规 |
| ONNX / Sherpa 等 | `shade` 合并 | 简化分发 |

#### 对天枢的映射

| tianshu-libs | 天枢 |
|---|---|
| `common/` | `tianshu-api` + `tianshu-core` + `tianshu-client` |
| `neoforge/` | `tianshu-adapter-neoforge-1.21.1` |
| `fabric/` | `tianshu-adapter-fabric-*`（后续） |
| `universalJar` | 北辰的 universal 产物 |

#### 关键结论：功能模组可以是一个 universal 单 jar

因为听澜 / 回响 / 织言 / 辅星**代码零 MC 依赖**，它们可以按同一范式打包：

```
tianshu-feature-asr/
├── common/        业务代码（纯 Java）
├── neoforge/      空 @Mod 入口 + neoforge.mods.toml
├── fabric/        空 ModInitializer 入口 + fabric.mod.json
└── universalJar   三份元数据合成 → 单 jar 通吃
```

**发布矩阵因此收敛为**：

| 产物 | 数量 | 说明 |
|---|---|---|
| 北辰 | 平台 × 版本 | adapter 代码与平台绑定 |
| 功能模组 | **4 个 universal jar** | 通吃所有平台与 MC 版本 |

**唯一约束**：入口类需要平台 API（`@Mod` / `ModInitializer`），所以按平台各一个**空入口**，业务代码完全共用、字节级一致。

**本期范围**：只做 neoforge-1.21.1。功能模组先出 NeoForge 版 jar；Fabric 入口待后续，业务代码零改动。

### 2.2 依赖规则（严格单向）

```
adapter ──→ client ──→ core ──→ api
                ↘        ↗
              feature-*
```

| 规则 | 内容 | 门禁 |
|---|---|---|
| R1 | `api` 不依赖任何模块 | 无 import 外部 |
| R2 | `core` 只依赖 `api` | 编译期 |
| R3 | `client` 只依赖 `api` + `core` | 编译期 |
| R4 | `feature-*` 只依赖 `api` + `core` | 编译期 |
| R5 | `feature-*` 之间零依赖 | `verifyNoCrossFeature` |
| R6 | `client`/`core`/`feature`/`api` 禁止 import MC | `verifyNoPlatformImport` |
| R7 | `feature-*` 禁止 import `core` 内部实现（只许 `api`） | `verifyFeatureBoundary` |

R6 复用现有 `tianshu-client` 的 `verifyClientPlatformBoundary` 任务并推广。

### 2.3 契约清单（冻结）

以下类型一旦拆出模块就是对外契约，改名即 breaking change：

- **信封与路由**：`TianshuEnvelope`、`EnvelopeHeader`、`PacketType`、`PayloadType`、`TargetMode`、`Priority`、`DeliveryPolicy`、`CancellationScope`、`FailurePolicy`、`BrokerType`、`ExecutionLane`
- **Payload**：全部 `*Payload` record、`ITianshuPayload`
- **常量**：`ProtocolCapabilities`、`ProtocolTopics`、`ProtocolSourceIds`
- **能力**：`RuntimeCapability`、`RuntimeCapabilityStatus`
- **模块**：`TianshuManagedModule`、`TianshuModuleInstaller`、`TianshuModuleProvider`、`TianshuModuleRegistrar`、`TianshuModuleAssemblyContext`
- **平台端口**：`IGameEnvironment`、`IAudioBridge`、`LogSink`、`DiagnosticSink`、`ClientScheduler`、`ClientTextProvider`、`ClientUiHost`、`ClientFilePicker`、`ClientGameContextProvider`
- **设置**：`TianshuSettingsContributor` + 设置模型（Panel/Option/Status/Action 模板）
- **语音**：`VoiceTriggerRegistration`、`VoiceTriggerMatch`、`VoiceTriggerRegistry`、`VoiceResourceAccess`
- **对话**：`DialogueParticipantDescriptor`、`DialogueClaimProfile`、`DialogueClaimRule`、`DialogueClaimCondition`、`DialogueClaimConditionType`
- **映迹**：`PresenceActivityPayload`、`PresenceWorldEventPayload`、`PresenceChatMessagePayload`

**不冻结**：`ProtocolRuntime` 内部实现、broker 实现、executor 策略、各模块内部服务类。

### 2.4 装配模型

核心不认识任何具体模块，只接受提供者：

```java
// tianshu-api
public interface TianshuModuleProvider {
    void contribute(TianshuModuleRegistrar registrar);
}

public interface TianshuModuleRegistrar {
    void addModule(TianshuModuleInstaller installer);
    void addSettings(TianshuSettingsContributor contributor);
}
```

发现机制由平台各自实现：

| 平台 | 发现方式 |
|---|---|
| NeoForge | 触发注册事件，模块监听后调用 registrar |
| Fabric | `fabric.mod.json` entrypoint `tianshu:modules` |

**内置模块（如 IA）也走 provider**，由核心自己注册。内置与外置无特殊路径。

不使用 `ServiceLoader`：FML classloader 下不可靠，且无法表达模块顺序。

### 2.5 可缺席语义

| 情况 | 行为 |
|---|---|
| 模块未注册 | 设置页无该页；相关能力未注册；协议投递进死信 |
| 模块注册但启动失败 | 保留失败状态供诊断；其他模块继续 |
| 能力缺失 | 调用方先用 `CoreCapabilityProbe` 探测，再决定是否投递 |
| 映迹无活动 | HUD 显示空闲（自然降级，无需特殊处理） |

## 4. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | IR 并入听澜 | 文字场景暂无需求；为不存在的场景保留独立模块是过度设计 |
| D2 | `IR_RESULT` 保留公共 topic | 零成本保留后路，将来独立时订阅方零改动 |
| D3 | 装配用 Provider/Registrar + 平台发现 | 核心零平台依赖；换加载器只换发现方式 |
| D4 | 内置模块也走 provider | 消除内置/外置双路径 |
| D5 | 设置框架留 client，内容随模块 | 框架共用，渲染不重复 |
| D6 | 映迹整体留 client | 双向枢纽，与模块是契约关系而非依赖；天然自然降级 |
| D7 | 包名不变，靠 Gradle 模块划边界 | 避免全量 import 噪声 |
| D8 | 不保留过渡层/兼容 shim | 未上线，直接切目标形态 |
| D9 | 每阶段必须可运行 | 避免多阶段叠加导致无法定位问题 |

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 边界移动暴露循环依赖 | 阶段 1 早做，让编译器抓 |
| SPI 设计反复 | Registrar 最小化，不加预留方法 |
| 设置页迁移量大 | 逐模块迁移，先听澜验证模式 |
| 类加载不可见 | 用 FML 依赖声明，禁止各自 jarJar 嵌入 |
| 中间态不可运行 | 每阶段 `runClient` 验收为硬门槛 |
| 范围蔓延 | 见第 6 节 |

## 7. 验收总纲

最终必须同时成立：

1. 只装本体 + 回响：第三方发 `TTS_SPEAK` 能播报
2. 只装本体 + 听澜：第三方订阅 `INPUT_ASR_FINAL_TEXT` 能做指令
3. 完整语音对话：本体 + 听澜 + 回响 + 织言 + 辅星
4. 移除任一功能模组：北辰正常启动、设置页少一页、无异常
5. 换 MC 版本：只改 adapter，内核零改动
6. 换加载器：只加 adapter（北辰）；功能模组按 2.1.1 合成 universal jar
7. 功能模组 universal：同一 jar 在 NeoForge 与 Fabric 均被识别，业务代码字节级一致
8. 公共逻辑单实例：模型生命周期、下载状态机、可用性刷新、删除执行各只有一份实现
9. `./gradlew check` 全绿，含全部门禁
10. 反补丁检查通过：无 shim、无死代码、无双路径、无遗留 TODO
