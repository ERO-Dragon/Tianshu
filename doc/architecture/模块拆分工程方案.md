> 状态：方案定稿，执行中（阶段 0）

## 0. 命名与发布矩阵

| 项 | 决定 |
|---|---|
| 本体 modid | **`tianshu`**（保持不变，`config/Tianshu/` 与存档零迁移） |
| 本体中文名 | **天枢-北辰** |
| 功能模组 modid | `tianshu_asr` / `tianshu_tts` / `tianshu_llm` / `tianshu_ax` |
| Java 包名 | 全部保持 `com.rheinmetal.tianshu.*` |
| 本期发布矩阵 | **只做 neoforge-1.21.1**；其余平台后续加 adapter |

北辰 = api + core + client + **一个平台 adapter**，三者不混装。

## 1. 目标

把天枢从「一个整体模组」变成「一个平台 + 几个可选插件」：

1. **内核与游戏版本无关** —— 换 MC 版本只改 adapter，内核不重编
2. **功能可单独安装** —— 第三方可以只用 TTS 播报、只用 ASR 做指令，或完整对话
3. **同一 bug 只修一处** —— 公共逻辑单实例化，不再有三份漂移的副本
4. **可跨加载器** —— 换 Fabric 只写 adapter

**明确不追求**：安装体积。`tianshu_libs`（42MB native 库）作为共享库保持现状。

### 2.1.1 参照实现：Tianshu-libs 的 universal 范式

**参照工程**：`D:\AIPROJECT\Tianshu-libs`（与天枢同级目录），该范式已在 `tianshu_libs` 上验证可用。

#### 工程结构

```
tianshu-libs/
├── common/        平台无关核心（纯 Java；api 依赖全部 native）
├── neoforge/      NeoForge adapter（net.neoforged.moddev + com.gradleup.shadow）
├── fabric/        Fabric adapter
├── buildSrc/      共享构建逻辑
└── gradle.properties
```

#### universal jar 的构成（根 `build.gradle` 的 `universalJar` 任务）

```groovy
tasks.register('universalJar', Zip) {
    archiveFileName = "${mod_id}-${mod_version}-universal.jar"
    from({ zipTree(project(':neoforge').tasks.shadowJar.archiveFile) })   // ① 含 META-INF/neoforge.mods.toml
    from(project(':fabric').sourceSets.main.output)                       // ② 含 fabric.mod.json
    from('neoforge/src/main/templates/META-INF/mods.toml') { into 'META-INF' }  // ③ Forge 兼容
}
```

**三份元数据并存，各加载器只读自己那份**：

| 加载器 | 读取的元数据 |
|---|---|
| NeoForge / FML | `META-INF/neoforge.mods.toml` |
| Fabric Loader | `fabric.mod.json` |
| Forge | `META-INF/mods.toml` |

这就是 “universal” 的真实含义：**跨加载器**，而不只是跨操作系统。

#### 版本范围写法（宽范围覆盖多版本）

```properties
minecraft_version=1.20.4
minecraft_version_range=[1.20,1.22),[26.1,27)
neo_version_range=[20,22),[26.1,27),[47,48)
loader_version_range=[1,)
```

一个 jar 通过宽 `versionRange` 同时被多个 MC 版本接受。

#### 依赖打包策略

| 依赖类型 | 方式 | 原因 |
|---|---|---|
| `common` 模块 | `implementation project(':common')` + shadow | 平台无关代码合并进 jar |
| jjml（LGPL） | `jarJar` 嵌套 jar | 许可证合规 |
| ONNX / Sherpa 等 | `shade` 合并 | 简化分发 |

#### 对天枢的映射

| tianshu-libs | 天枢 |
|---|---|
| `common/` | `tianshu-api` + `tianshu-core` + `tianshu-client` |
| `neoforge/` | `tianshu-adapter-neoforge-1.21.1` |
| `fabric/` | `tianshu-adapter-fabric-*`（后续） |
| `universalJar` | 北辰的 universal 产物 |

#### 关键结论：功能模组可以是一个 universal 单 jar

因为听澜 / 回响 / 织言 / 辅星**代码零 MC 依赖**，它们可以按同一范式打包：

```
tianshu-feature-asr/
├── common/        业务代码（纯 Java）
├── neoforge/      空 @Mod 入口 + neoforge.mods.toml
├── fabric/        空 ModInitializer 入口 + fabric.mod.json
└── universalJar   三份元数据合成 → 单 jar 通吃
```

**发布矩阵因此收敛为**：

| 产物 | 数量 | 说明 |
|---|---|---|
| 北辰 | 平台 × 版本 | adapter 代码与平台绑定 |
| 功能模组 | **4 个 universal jar** | 通吃所有平台与 MC 版本 |

**唯一约束**：入口类需要平台 API（`@Mod` / `ModInitializer`），所以按平台各一个**空入口**，业务代码完全共用、字节级一致。

**本期范围**：只做 neoforge-1.21.1。功能模组先出 NeoForge 版 jar；Fabric 入口待后续，业务代码零改动。

### 2.2 依赖规则（严格单向）

```
adapter ──→ client ──→ core ──→ api
                ↘        ↗
              feature-*
```

| 规则 | 内容 | 门禁 |
|---|---|---|
| R1 | `api` 不依赖任何模块 | 无 import 外部 |
| R2 | `core` 只依赖 `api` | 编译期 |
| R3 | `client` 只依赖 `api` + `core` | 编译期 |
| R4 | `feature-*` 只依赖 `api` + `core` | 编译期 |
| R5 | `feature-*` 之间零依赖 | `verifyNoCrossFeature` |
| R6 | `client`/`core`/`feature`/`api` 禁止 import MC | `verifyNoPlatformImport` |
| R7 | `feature-*` 禁止 import `core` 内部实现（只许 `api`） | `verifyFeatureBoundary` |

R6 复用现有 `tianshu-client` 的 `verifyClientPlatformBoundary` 任务并推广。

### 2.3 契约清单（冻结）

以下类型一旦拆出模块就是对外契约，改名即 breaking change：

- **信封与路由**：`TianshuEnvelope`、`EnvelopeHeader`、`PacketType`、`PayloadType`、`TargetMode`、`Priority`、`DeliveryPolicy`、`CancellationScope`、`FailurePolicy`、`BrokerType`、`ExecutionLane`
- **Payload**：全部 `*Payload` record、`ITianshuPayload`
- **常量**：`ProtocolCapabilities`、`ProtocolTopics`、`ProtocolSourceIds`
- **能力**：`RuntimeCapability`、`RuntimeCapabilityStatus`
- **模块**：`TianshuManagedModule`、`TianshuModuleInstaller`、`TianshuModuleProvider`、`TianshuModuleRegistrar`、`TianshuModuleAssemblyContext`
- **平台端口**：`IGameEnvironment`、`IAudioBridge`、`LogSink`、`DiagnosticSink`、`ClientScheduler`、`ClientTextProvider`、`ClientUiHost`、`ClientFilePicker`、`ClientGameContextProvider`
- **设置**：`TianshuSettingsContributor` + 设置模型（Panel/Option/Status/Action 模板）
- **语音**：`VoiceTriggerRegistration`、`VoiceTriggerRegistry`、`VoiceResourceAccess`
- **对话**：`DialogueParticipantDescriptor`、`DialogueClaimProfile`、`DialogueClaimRule`、`DialogueClaimCondition`、`DialogueClaimConditionType`
- **映迹**：`PresenceActivityPayload`、`PresenceWorldEventPayload`、`PresenceChatMessagePayload`

**不冻结**：`ProtocolRuntime` 内部实现、broker 实现、executor 策略、各模块内部服务类。

### 2.4 装配模型

核心不认识任何具体模块，只接受提供者：

```java
// tianshu-api
public interface TianshuModuleProvider {
    void contribute(TianshuModuleRegistrar registrar);
}

public interface TianshuModuleRegistrar {
    void addModule(TianshuModuleInstaller installer);
    void addSettings(TianshuSettingsContributor contributor);
}
```

发现机制由平台各自实现：

| 平台 | 发现方式 |
|---|---|
| NeoForge | 触发注册事件，模块监听后调用 registrar |
| Fabric | `fabric.mod.json` entrypoint `tianshu:modules` |

**内置模块（如 IA）也走 provider**，由核心自己注册。内置与外置无特殊路径。

不使用 `ServiceLoader`：FML classloader 下不可靠，且无法表达模块顺序。

### 2.5 可缺席语义

| 情况 | 行为 |
|---|---|
| 模块未注册 | 设置页无该页；相关能力未注册；协议投递进死信 |
| 模块注册但启动失败 | 保留失败状态供诊断；其他模块继续 |
| 能力缺失 | 调用方先用 `CoreCapabilityProbe` 探测，再决定是否投递 |
| 映迹无活动 | HUD 显示空闲（自然降级，无需特殊处理） |

**feature 是 universal jar（对齐 `tianshu_libs` 范式）**：每个 feature jar 同时包含

| 内容 | 作用 |
|---|---|
| `META-INF/neoforge.mods.toml` | FML 读取 |
| `fabric.mod.json`（含 `entrypoints`） | Fabric Loader 读取 |
| `XxxNeoForgeMod.class`（`@Mod` 注解） | NeoForge 入口 |
| `XxxFabricMod.class`（`ModInitializer`） | Fabric 入口 |

入口类放在 `src/neoforgeEntry` 与 `src/fabricEntry` 两个独立 source set，**不在 `src/main` 内**——这样 `verifyNoPlatformImport` 门禁仍然只覆盖业务代码，入口类不被它检查。

`@Mod` 通过 `src/neoforgeStubs` 里的编译期 stub 提供（照抄 `tianshu_libs` 的 `forgeCompatStubs` 做法）：neoforged maven 在开发环境不可达，且平台无关模块本就不该依赖整个 NeoForge artifact。stub 只参与编译，**不打包**（验证过 jar 内无 `net/neoforged` 类）。Fabric 入口则直接依赖 `fabric-loader`（maven 可达）。

北辰本期**只出 NeoForge 1.21.1**，Fabric 版北辰留到阶段 7；因此现在把 feature jar 装到 Fabric 上会因缺少 `tianshu` 而无法加载——这是预期的，不是缺陷。

**与计划的偏差（已处理）**：计划要求「语言文件按模组拆分」。实际**未拆分**，原因是 MC 的语言文件按 namespace 合并——多个 jar 写同一个 `assets/tianshu/lang/*.json` 会互相覆盖。拆分需要每个模块独立 namespace 并迁移全部 key，属于独立工作。当前语言文件全部留在北辰，功能上等价。

**运行时验证（阶段 6 补充，2026-10-23）**：`runClient` 首次真正跑起来时暴露了两个只有运行时才会出现的问题：

| 现象 | 根因 | 修复 |
|---|---|---|
| `tianshu` 不在 mod 列表，四个 feature 报「requires tianshu」 | `neoForge.mods` 被写成一个 `tianshu` 块、塞进全部 sourceSet，FML 因此把 feature 的 `neoforge.mods.toml` 也当成 tianshu 的，读到多份同名清单 | 改成「modid → 它的 sourceSet」映射：`tianshu` 只含 adapter+client+core+api（这些没有自己的清单），四个 feature 各自独立声明 |
| 修完之后 `NoClassDefFoundError: LogSink` | 只声明 `sourceSets.main` 时，api/core/client 的类掉出了 mod 类加载器 | 同上：把「无清单的依赖模块」重新并入 `tianshu` 的 sourceSet 列表 |

**`neoForge.mods` 的正确语义**：它是「每个 mod 由哪些 sourceSet 组成」的表，**不是**「一个 mod 装了哪些模块」。判定标准是**该模块有没有自己的 `neoforge.mods.toml`**——有就独立声明，没有就并入所属 mod。

**另一个坑**：`repositories` 里 `fabricmc` 必须排在 `neoforged` 之前。neoforged 镜像在开发环境会重置连接，而 Gradle 在第一个抛 IO 异常的仓库处就中止解析，不会继续尝试下一个——fabric-loader 因此解析失败并拖垮 `runClient`。

**验证结果**：`runClient` 完整加载 8 个 mod（Minecraft、NeoForge、tianshu、四个 feature、tianshu_libs），无加载错误，进入渲染阶段。

### 9.2 装配：模块自注册（替代 §2.4 的"平台触发注册事件"）

```java
// 模块自己的 @Mod 构造
TianshuModuleProviderRegistry.register(XxxModuleProvider::new);

// 内核每个世界会话
new ClientTianshuModuleAssembler(kernelProviders, context, moduleSettingsSources)
```

- `TianshuModuleProviderFactory` 按会话接收 `TianshuModuleAssemblyContext`，返回该会话的 provider；
- `TianshuModuleProvider.contribute(registrar)` 里用 `addModule(installer)` + `addSettings(page)` 两个入口完成装配；
- 内置页与外置贡献合并到 `ModuleSettingsSourceRegistry`，**不再有"内置写死 / 外置走 contributor"的双路径**；
- 内核只注册自己拥有的三个模块：ONNX 原生运行时、映迹、思衡（IA 随 core 发布）。

### 9.3 装配端口（`api.assembly` / `api.game`）

会话级上下文 `TianshuModuleAssemblyContext` 只交三种东西：`IGameEnvironment` / `IAudioBridge` /
`ModuleRuntimeAccess`、两个宿主信号、以及下面这组端口。**模块拿不到** CoreManager、ProtocolRuntime、
ClientConfig 或任何功能模组类型。

| 端口 | 作用 |
|---|---|
| `ClientPorts` | 装配期可用的客户端服务：`scheduler`、`uiHost`、`texts`、`filePicker`、`settingsLayers`、`audioDevices`、`configStores`、`modelLoadQueue` |
| `ModuleRuntimeServices` | 设置页需要的最小内核面：`findService` / `requireService` / `requestRefresh` |
| `ModuleConfigStores` | 按 moduleId 发放 `ModuleConfigStore`；`moduleDirectory()` 给出模块数据根目录 |
| `NamedObjectIndex` / `NamedObjectDictionary` | 内核只持有索引的**生命周期端口**；字典快照是平台事实；索引本体属于听澜 |
| `WorldFacts` / `WorldFactsSource` | 平台只报事实（`kindId` 是字符串），辅星自己映射成 `AXScopeKind` |

### 9.5 测试并发策略

编译保持并行；`Test` 任务通过一个 `maxParallelUsages = 1` 的共享服务**串行执行**。
原因：若干套件驱动真实线程与墙钟窗口（协议仲裁、Swing 对话框存根），六模块测试 JVM 抢 CPU 时会变成
"单独跑必过、全量跑必挂"的 flake。配置必须写在 `allprojects` 下——根项目没有 Test 任务。

### 9.6 热词物化已删除（取舍记录）

内核契约里最后一个功能名 `VoiceResourceConfiguration.getAsrBasePath()` **已删除**，连同
`VoiceResourceManager` / `VoiceResourceAccess` / `VoiceResourceSnapshot`。

取舍：ASR 引擎侧的"热词加权文件"整条链路移除（`AsrHotwordSupport`、引擎 `hotwordsFile` 参数、
语料工厂的 hotwords 配置、听澜的 `HOTWORD_RELOAD` 重载状态机）。理由：
**热词支持本来就是按模型而定的**（`AsrHotwordSupport.fromModel(...)` 只为部分模型返回 `reloadRequired()`），
却要求内核知道听澜的目录并替它写文件。

替代保证：词表的唯一真相源是 `VoiceTriggerRegistry`（内核，共享命名空间 + 冲突仲裁 + 按 moduleId 注销），
由 IR 的 `AsrTextRepairer` 在每次修复时按需重建 trigger index；对象名仍走听澜自持的 `NamedObjectIndex`。
因此"每个模块注册的 wakeword / 指令词能被识别并修复"这条**不依赖热词文件**。

`ProtocolModuleIds` 里的 `IR` / `IA` 仍是缩写（识意 / 思衡），按用户决定不重命名。

### 9.7 载荷归属判据（前置依赖 / 联动 / 北辰）——规则正文

这是模块间"类放在哪、怎么用"的唯一判据。**修改工程前先读这一节**，违反它的写法一律在 code review 阶段退回。

**第一步：载荷类归"生产者模组"**（它创建并投递这种载荷的模组；协议基类归北辰 api）。

**第二步：消费者怎么用，取决于依赖类型**

| 依赖类型 | 含义 | 声明 | 代码 | 守卫 |
|---|---|---|---|---|
**前置依赖** | 没有它这个模组就是残废 | Gradle `api`/`implementation` 硬依赖 + `mods.toml` `depend` | 直接 `import` 生产者的类 | **不需要**（类必然在） |
**联动** | 有这个模组就多一项能力，没有照常跑 | `compileOnly` + `mods.toml` optional | **只能通过 `bridge` 包**使用生产者的类；该包只在对方存在时加载 | 必须：`InstalledMods.isLoaded(...)` 之后才触碰 |
**北辰要用** | core / client / adapter 自己要引用 | —— | 只有这种情况，载荷**必须**放在 `tianshu-api` | 不适用 |

**第三步：判据的推论（按顺序判断，不要跳步）**

1. 北辰（core/client/adapter）引用 → 载荷在 api。
2. 生产者的模组对消费者是**前置依赖** → 载荷可以在生产者 jar 里（编译期可见、运行期安全）。
3. 生产者的模组对消费者是**联动** → 载荷放在生产者 jar，消费者用 `bridge` + `InstalledMods` 守卫；**不允许**为了省事把载荷塞回 api（那是把两个模组之间的契约变成内核词汇）。
4. 只有一个模组用的载荷 → 它自己的 jar，`PayloadType.of(name, class)` 自登记，内核零改动。
