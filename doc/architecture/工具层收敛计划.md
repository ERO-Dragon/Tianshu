# 工具层收敛计划（审查 + Numen 对照）

> 状态：**计划**。本文把 2026-11 的子代理审查结论、能力目录设计与 Numen（minecraft-numen）的对照
> 合成一条施工顺序。审查编号（C1/H1/H2/...）沿用审查报告。
>
> 原则：每一阶段独立可交付；先安全与正确，再删重复，再做权限与能力消费。不做大爆炸式重写。

## 2. 决策（已定）

| 议题 | 决定 | 理由 |
|---|---|---|
| A3：主对话是否带工具 | **维持 Simple 带工具**（当前行为），P1 只修预算与安全；A3 文档改写放到天枢优化阶段 | 工具层的目的就是让助手能查/能做 |
| 回复 + 工具/委派的格式 | **暂不统一**：委派继续用 `<delegate>` 标签（正文 + 后台任务），工具继续用 JSON 调用；混合信封（`say` + `call`/`delegate`）放到天枢优化阶段再定 | 现在改协议会牵动流式闸、契约解析与既有测试 |
| H3：写工具由谁触发 | **玩家显式触发**为主；agent 只能发起「待确认」，由玩家确认后以玩家身份执行 | 不把 op 权限交给模型；与 Numen 的 `ask` 一致 |
| 权限模型 | 先做 `ToolAutonomy { READ_ONLY, CONFIRM, FULL }` 三档**自主度**（界面文案：只读 / 部分权限 / 完全权限，对应 DSH）；对象组（owner/nature/unknown）与 allow/ask/deny 规则放 P3 后段 | 先有可用的确认流，再上防火墙，避免一次做全 |
| L3：英文协议文本 | **保留英文**（模型向协议文本，与 Claude Code skill 同思路），集中在 `ToolCatalogText` 一处并标注版本；面向玩家文案走 lang | 模型对英文指令更稳；不把协议文本散落 |
| H4：去重方式 | 抽 `ServerToolDispatch` 到 `tianshu-api`；adapter 只保留 `ToolReplySink`（构包+发送）；`ToolCallClient` 收进 `tianshu-client`，sender 注入 | 一条执行链、一份客户端状态机；各世代只保留编解码 |
| Lua / program | **暂不做**。能力目录保留 `program` 为未来 kind，不引入脚本 VM | 没有真实需求前不引入第二执行语言；先做 skill 文本 |
| Weaving | 不改。能力表只在 `tianshu-api`；织言继续只做传输 | 现有依赖方向正确 |

## 3. 阶段计划

### P0 决策与文档（半天）

- 改写 `AX_Agent运行时.md` 的 A3：主对话允许带工具，说明预算与失败语义；
- 本计划入 `doc/README.md` 的「计划」；
- 检查 26.1/26.2 的 `ServerActionConfig` 注册类型（L6 全量确认）。

**验收**：文档一致；无代码变更。

### P1 安全与健壮（1–2 天）— **已完成（2026-11-13）**

已落地：
1. **限流**：`ToolRateLimiter`（api，独立类）：只拦 `ToolCaller.Kind.PLAYER`（通道是唯一不可信输入），
   读 10 次/秒、写 2 次/秒，按 `(tool, player)` 令牌桶；新增 `ToolError.RATE_LIMITED`。agent 与模组调用不受限。
2. **线缆上限单一来源**：`ToolWireLimits`（api）统一请求字段、结果 JSON、错误码与消息上限；
   13 棵共享树的 `ToolCallResultPacket` 只调用它。超长结果变成结构化失败，不再在异步回调里抛异常。
3. **断开处理**：1.20.1/1.20.2/1.20.3/1.20.4-neoforge 补 `ClientPlayerNetworkEvent.LoggingOut`。
4. **L6 核对结论**：26.3 的 `ModConfig.Type` 没有 `SERVER`（已重命名为 `SYNCED`），当前注册正确；
   注释已写明，不改代码。
5. **游戏工具进能力表**：工具注册时自动镜像为 `kind=tool`、`binding=local`，属性带
   `category` / `enabled` / `argsSchema`；`setEnabled` 同步镜像；`CapabilityExposure` 过滤已关闭工具。

有意暂缓（有明确理由，不是漏做）：
- **战利品缓存**：限流已挡住刷取；缓存需要数据重载钩子，否则 `/reload` 后返回旧表。宁可每次读新数据。
- **H2 工具轮预算**、**M3 超时单点**、**M4 异常脱敏**、**M6 结果进对话的预算**：都落在天枢的循环/分发上，
  与 P2 的 `ServerToolDispatch` 一起做，避免在 43 份 handler 里改一遍再删掉。
- **P1 旧检查项**（限流回归、超长结果、断开、26.x 类型）已由新增测试覆盖；限流测试位于 `ToolRateLimiterTest`。


1. **限流**：`TianshuTools` 增加 per-`(toolId, caller)` 令牌桶（读默认 20/s、写 2/s，可在策略覆盖）；
   新增 `ToolError.RATE_LIMITED`；服务端分发同一套（服务器侧按玩家身份判定）。
2. **战利品缓存**：`LootQuerySource` 按表 id 缓存解析结果，服务器启动/数据重载时清空；
   避免每次调用主线程读文件。
3. **截断与脱敏**：结果 JSON 超过 `MAX_JSON` 先截断再生包；`MAX_JSON` 改 32767；错误消息只给类型与短描述，
   不拼异常串/堆栈；`ToolCallResultPacket` 构造器不再承担校验抛点。
4. **H2 预算**：工具轮预算 = 主对话挂钟 + `maxToolRounds × 单轮上限`（默认 3×2s），写入 `AXRunPolicy`；
   `AXToolTurn` 的轮数从策略读，不硬编码。
5. **M2**：1.20.1/1.20.2/1.20.3/1.20.4-neoforge 补 `LoggingOut` → `toolCalls.onDisconnect()`。
6. **L6**：26.x 的 `ServerActionConfig` 从 `SYNCED` 改 `SERVER`（确认 26.1/26.2）。
7. **M3**：超时只保留注册表一处，channel 与 send 不再各自 `orTimeout`。
8. **M6**：工具结果进对话前按 8KB 截断并标注"已截断"。

**验收（CI）**：限流 1 秒 100 次出现 `RATE_LIMITED`；超长结果仍然回包且客户端不超时；
4 个包的断开监听存在；26.x 配置类型为 SERVER；现有测试全绿。

### P2 去重与生命周期（2–3 天）— **已完成（2026-11-13）**

已落地：
1. **`ServerToolDispatch`（api）**：解析、执行、信封、幂等（`(player, requestId)` 120 秒窗口）、
   异常单行化与线缆裁剪都在这一处；新增 7 个契约测试（重放只执行一次、非法 id/参数、异常不带堆栈、写工具权限）。
2. **42 份服务端 handler 瘦身**：只保留登录发目录、注册与 `respond` 的一行转调；`toResult`/`failure` 删除，
   不再各自解析 JSON 或拼错误。所有包编译通过。
3. **客户端状态机收进 `tianshu-client`**：`ToolCallClient` 一份，构造注入 `RequestSender`，
   目录与结果按原始字段接收；13 份网络副本删除，各世代只保留编解码。
4. **M4**（异常脱敏）在 dispatch 完成；**M3** 不再在 handler 里叠超时，注册表是唯一执行点。

仍留在 P3（与天枢循环一起改，避免第三次动分发层）：
- **M1** `.join()` 阻塞回调线程（要改 `AXToolTurn` 的 future 形态）；
- **H2** 工具轮预算与挂钟；**M6** 工具结果进对话的大小预算；**M3 的 channel 侧超时**（客户端仍有一道）。

> 下一步是 P3：自主度三档、确认流、写工具的玩家入口与审计。


1. **`ServerToolDispatch`（api）**：入参请求 id、玩家 id/op、工具 id、args JSON；输出结构化结果；
   内含权限、限流、幂等（`(player, requestId)` TTL 缓存）、审计钩子（`ToolAuditSink`，默认空实现）。
2. **adapter 瘦身**：每个 `ServerToolHandler` 只保留登录发目录 + `ToolReplySink` 实现（构包、`server.execute`、
   发送），`respond/toResult/failure` 删除；21+21 份收敛为「1 份 dispatch + 每包约 20 行」。
3. **客户端状态机**：`ToolCallClient` 移入 `tianshu-client`，构造时注入 `RequestSender`（发请求）；
   结果/目录用原始字段接收；13 份收敛为 1 份 + 每包编解码。
4. **M1**：`AXToolTurn`/`AXToolRoundHandler` 改为 future 链，不在回调线程 `.join`。

**验收**：43 个适配器编译；1.21.1/1.20.1/26.1 各启动一次；dispatch 单测覆盖非法 id/参数、权限、限流、
幂等重放；代码量净减可量化（删除约 5–6k 行）。

### P3 权限与写工具（3–5 天）— **语义层已完成（2026-11-14），UI 待做**

已落地（`tianshu-api`）：
1. `ToolAutonomy { READ_ONLY, CONFIRM, FULL }` 与 `ToolAutonomyGate`：模式由客户端/平台设置，默认 `CONFIRM`；
   `READ_ONLY` 在目录与调用两处都拒绝写工具；`CONFIRM` 对**客户端发往服务端**的写调用走 `ToolConfirmation`，
   没有安装确认实现时**拒绝**（缺 UI 不等于放行）；`FULL` 免确认但仍要 operator + 开关。
2. `ToolConfirmation` 端口：平台实现弹卡（下阶段），工具层不画任何界面；
   `Attempt` 带上工具 id、类别、描述、参数与调用者，够画一张精确的卡。
3. 服务端分发不重复询问：请求能到服务端，说明客户端已经确认；服务端仍按 operator + 开关判定。
4. 能力表 `CapabilityExposure` 在 `READ_ONLY` 下同样隐藏写工具。
5. 6 个测试：只读隐藏与拒绝、无确认实现即拒绝、确认通过/拒绝、FULL 仍需 operator、服务端不二次询问。

下一步（P3 收尾）：
- **确认 UI**：在客户端平台实现 `ToolConfirmation`（工具、参数、影响、允许/拒绝），并接入设置页的自主度选择；
- **玩家入口**：lab 工具控制台（工具 id + JSON + 执行），用于无 agent 的手工测试；
- M1/H2/M6 的 agent 侧收尾仍与下一阶段一起做。


1. `ToolAutonomy { READ_ONLY, CONFIRM, FULL }` 进 `ToolPolicy`；运行时模式按玩家/实例配置；
   有效自主度 = min(运行时, 工具默认)；写工具默认 `CONFIRM`。
   它和既有概念是**正交**的，不替换任何一个：
   | 概念 | 回答 | 取值 |
   |---|---|---|
   | `ToolCategory` | 工具在哪执行、是否写世界 | LOCAL / SERVER_READ / SERVER_WRITE |
   | `ToolPermission` | 谁有资格调用 | EVERYONE / OPERATOR |
   | `ToolAutonomy` | 调用者（agent）能自主到哪一步 | READ_ONLY（只能建议）/ CONFIRM（每次确认）/ FULL（免确认，仍需 operator + 开关） |
2. **确认流**：dispatch 返回 `PENDING_CONFIRM` 与一次性 ticket；宿主弹卡（工具、参数、影响），
   玩家同意后按同一 ticket 执行；ticket 单次、限时、审计。
3. **玩家入口**：lab 工具控制台（工具 id + JSON + 执行）用于测试；正式入口是控制台面板或命令（后续）。
   agent 只产生"待确认"请求，不直接带 op。
4. **对象组（后段）**：给写工具加 owner/nature/unknown 归属判断（放置记录 + 结构与自然标签），
   规则表 allow/ask/deny；没有记录的写操作默认 `ask`。参考 Numen 的权限层，但不做完整防火墙语法。

**验收**：op/非 op/确认矩阵；`block.interact`、`craft.recipe`、`container.transfer`、`block.machine` 各一次手工通过；
审计日志可查。

## 4. 与 Numen 的取舍

| Numen 做法 | 我们是否采用 |
|---|---|
| 服务端假玩家身体 | 不采用：我们是助手 + 能力层，没有自主身体 |
| Lua 程序 + 原子命令 | **部分**：保留 `program` kind 与沙箱预算思路，暂不引入 VM |
| 权限防火墙 + 对象组 | **部分**：P3 采用 autonomy + 确认流；对象组/规则表后段，不做完整语法 |
| skill 文件 + 三级披露 | **采用**（P4） |
| MCP 双向 | **部分**：先做客户端消费；server 暴露可选 |
| 纯 JVM 模块分层 | 已一致（api/client/agent）；继续遵守 |
| bench 真模型评测 | 可选，P5 后 |

## 5. 不做 / 暂缓

- 不做 Lua 执行引擎、不做完整防火墙规则语法、不做每工具独立 UI；
- 不把能力注册到织言；不改 `LLMPromptRequestPayload` 的传输职责；
- 不在 P1/P2 期间顺带改工具语义（避免一次改两层）。
