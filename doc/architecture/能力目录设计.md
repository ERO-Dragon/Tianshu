# 能力目录设计

> 状态：**核心已实现**（`tianshu-api` 的 `api.capability` 包，9 个契约测试）；智能体侧对
> skill / resource / prompt 的消费、MCP/HTTP 的绑定实现、确认与审计仍待做。
>
> 一句话：**能力表在舟楫，内容由提供方解析，编排方负责拼，织言只搬运。**
> 任何 AI 模块与非 AI 模块都通过这张表发现能力；织言不知道表的存在。

## 0. 为什么需要第二张表

协议中心已经有一张 `CapabilityDescriptor`，它描述的是"哪个模块能在 broker 上处理哪种消息"——传输层。
它回答不了"模型能用什么"，也不该被复用：混用会把消息路由和 AI 消费绑死。

所以这里是一张**新的、AI 消费视角的目录**，与协议中心平行，互不依赖。

## 1. 两个正交维度

| 维度 | 回答 | 取值（开放） | 谁关心 |
|---|---|---|---|
| `kind` | 它是"用来干什么的" | `tool` / `skill` / `resource` / `prompt` / `connector` / 任意命名空间值 | 编排方决定怎么给模型看 |
| `binding` | 通过什么执行/获取 | `local` / `mcp` / `http` / `command` / 任意值 | 调用时转发给谁 |

**MCP 是 binding，不是与 tool/skill 平级的语义。** 一个 MCP server 可以暴露 tool、resource、prompt，
也可能只是一个 connector。

## 2. 描述符

| 字段 | 说明 |
|---|---|
| `id` | `namespace:name`，与工具 id 同形 |
| `kind` | 消费方式；未知 kind 原样保留 |
| `binding` | 接入方式 |
| `description` | 给编排方与模型看的一句话 |
| `side` | 由哪一侧执行（`CLIENT` / `SERVER`） |
| `permission` | `EVERYONE` / `OPERATOR` |
| `provider` | 注册者（诊断与路由用） |
| `attributes` | kind 特定事实：`argsSchema`、`mediaType`、`size`、`timeoutMillis` 等；未知键保留 |

描述符**不带内容、不带实现**。resource 的正文、skill 的步骤、MCP 的凭据都留在提供方。

## 3. 注册

- **工具**：照旧 `TianshuTools.register(...)`，目录自动镜像一行 `kind=tool`、`binding=local`；
  执行仍走工具注册表（一条策略路径，不复制权限/侧路由逻辑）。`unregister` 时镜像行同步移除。
- **非工具**：`CapabilityCatalog.register(descriptor, handler)`；重复 id 直接报错，而不是静默覆盖。
  用目录注册 `kind=tool` 会被拒绝，避免绕过工具注册表。
- 生命周期与模块一致：模块卸载时调用 `unregister`。

## 4. 执行

`CapabilityCatalog.invoke(id, args, caller, side)` 返回与工具一致的 JSON 信封：

- 未知 id → `UNKNOWN_CAPABILITY`；
- `OPERATOR` 权限但调用者不是 op → `NO_PERMISSION`；
- `side=SERVER` 而客户端没有服务端组件 → `UNSUPPORTED_SIDE`（快速失败，不挂起）；
- `kind=tool` → 交给 `TianshuTools.callJson`（权限、超时、通道全部复用）；
- 其他 kind → 提供方的 `CapabilityHandler`，按 `attributes.timeoutMillis`（默认 5 秒）限时；
- handler 抛异常/超时 → 结构化错误，不把异常透给调用方。

## 5. 消费（参考实现）

`CapabilityExposure` 只是**一种**消费方式，不是唯一方式：

- `exposed(caller, side)`：过滤掉 connector、不可达的服务端能力、调用者无权的能力；
- `describe(descriptors)`：渲染成提示词块（tool 带 schema；skill/resource/prompt 带说明）；
- `textOf(envelope)`：从 resource/prompt/skill 结果里取文本。

AI 模块可以照这个实现 function-calling、MCP 工具列表或自己的提示词格式；非 AI 模组直接用
`CapabilityCatalog.invoke` 或 `TianshuTools` 类型化调用，不经过渲染层。

## 6. 与织言的关系

- 织言**不读这张表**，只接收调用方已经拼好的请求（`LLMPromptRequestPayload` 的形状）；
- 表在 `tianshu-api`，任何模块都能依赖它；游戏模组不依赖织言；
- 如果将来织言想提供"聚合好的能力集"便利，它可以依赖 api 做一个只读视图，但注册仍在舟楫。

## 7. 已实现与未做

| 项 | 状态 |
|---|---|
| 目录（五种 kind + 开放值、绑定、过滤、超时、权限、侧可达性） | **已实现**，9 个契约测试 |
| 工具镜像（注册/注销、`category`/`enabled`/`argsSchema` 属性、开关同步、exposure 过滤已关闭工具） | **已实现** | 游戏自身的查询/写工具注册后即出现在表里，无需第二套登记 |
| 参考消费层 `CapabilityExposure` | **已实现**，测试覆盖 |
| MCP 客户端 | **已实现**：HTTP 与 stdio 两种传输（协议层共用）、握手/会话、tools/resources/prompts；远程工具以普通工具注册，默认 FULL 档 |
| 天枢对 skill / resource / prompt 的消费 | **已做**：`capability.read` 桥接；skill provider（目录 + classpath、标准 `SKILL.md`、命名空间、去重、按需正文/附录/分页）；resource/prompt provider（目录文件、分页、`{{key}}` 模板）；索引注入工具轮系统提示。MCP 未做 |
| MCP / HTTP 绑定实现（连接、握手、JSON-RPC/REST） | 未做；由提供方实现，核心不内置 |
| 写工具的确认 UX 与审计、速率限制 | 未做（见工具层审查 C1/H3） |
| 事件/订阅、多模态、人类审批 | 不属于 kind；分别走事件总线、`attributes.mediaType`、autonomy 策略 |

## 8. 未决

1. kind 是否要带版本（`skill@2`）——目前靠 namespace 隔离，不引入版本；
2. resource 的分块/检索协议（目录只给 `size`/`mediaType`，分块由编排方与提供方约定）；
3. skill 的"可再调 tool"声明是否进描述符（目前由 skill 实现自行决定）；
4. 目录是否需要按调用者缓存——现在每次 `list()` 复制一份，规模在几十条内可接受。
