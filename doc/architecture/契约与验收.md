# 契约与验收

> 本文是**唯一的契约与验收落点**：门禁命令、契约清单、验收台、覆盖矩阵、游戏内清单都在这里。
> 历史依据（旧版清单、逐项表格的原始版本）在 `doc/history/`，本文只保留结论与入口。
> 更新：2026-11-25。

## 舟楫联机协议

以下规则以 Minecraft、加载器及其他模组兼容为前提。

| 服务器 | 客户端 | 预期结果 |
|---|---|---|
| 未装舟楫 | 仅装舟楫 | 可进服，保留本地功能。 |
| 仅装舟楫 | 未装舟楫 | 可进服。舟楫不注册自定义实体类型，也不向缺少接收通道的客户端发包。 |
| 装舟楫 | 装舟楫 | 可进服。有共同的版本化工具目录通道时启用远程工具，缺少该通道时保留本地功能。 |
| 装声明自定义实体的双端内容模组 | 缺少该模组 | 由内容模组拒绝连接。服务器和每个客户端都需安装该模组及其舟楫依赖。 |

当前工具目录使用 `tool_catalog_v4`。协议代数区分载荷格式；舟楫不再用工具目录通道判断玩家能否进服。开发验收台 `tianshu_lab` 声明了 `acceptance_orb`，联机验收时测试服和每个测试客户端均须安装验收台。

## 世界记忆的存档隔离

本地存档身份由游戏目录和存档目录共同确定。暂时取不到存档身份时，天枢暂停该世界的持久记忆读写；识别成功后恢复到对应存档。世界显示名仅用于界面展示，同名存档各自保有独立记忆。

## 1. 一键门禁

```bash
./gradlew :tianshu-api:test :tianshu-core:test :tianshu-client:test \
  verifyFeatureIsolation verifyFeatureOptionalDependencies verifyClientMediaWiring \
  verifyServerToolRegistration verifyHostHasNoFeatureDependency verifyCommonAdapterNeutral \
  verifyNoPlatformImport verifyUniversalModuleJars verifyAdapterProperties \
  verifyAdapterMatrixCoverage verifyProtocolVersionSingleSource verifySettingsRenderersCoverOptionEntries
```

**不要用 `./gradlew check`**：它会带上 `tianshu-intake` 的既有抖动测试（`IaModuleProtocolFlowTest` 的 `await` 超时），
那是既有失败，与本模块改动无关（已用 `git stash` 回退到基线复现过）。

门禁的教训写在 §6：**一个门禁"通过"只有在能证明它会失败时才算数**。

### 2.1 六个方向的外部可见面与验收映射

[舟楫职责边界](舟楫职责边界.md) §1–2 列的六个方向，外部模块实际触到的入口与对应证据：

| 方向 | 外部模块用的公开面 | 证据 |
|---|---|---|
| 1 模块宿主 | `TianshuModuleProvider` / `TianshuModuleRegistrar` / `TianshuManagedModule`（register → prepare → start → stop → destroy）；`ModuleRuntimeContext`（protocol、services、triggers、diagnostics） | `ACC-HOST-1`（阶段次数、顺序、是否跑到结束）；`verifyFeatureIsolation`、`verifyHostHasNoFeatureDependency`（模块只走公开面） |
| 2 协议中心 | `ModuleProtocolAccess`（`registerModule` / `registerTopic` / `registerResponseHandler` / `subscribeTopic` / `submit` / `triggers`）、`ProtocolRegistrationView` | `ACC-PRO-1`（能力登记可见 + 命令经中心到达处理器）、`ACC-PRO-2`（能力 id 归一个模块：第二个声明者被明确拒绝，第一个照常收）、`ACC-PRO-3`（topic 只登记一次，两个模块订阅，一条事件两边都收到）；`ACC-PRT-1`（执行 lane）；信封/取消/死信由 `tianshu-core` 单测覆盖 |
| 3 模块能力注册 | `AbstractProtocolAdapter.registerCapability`（落到 `registerModule`）；读侧 `capabilityRegistrations` / `capabilityProviderCount` | `ACC-PRO-1`（能力归属到 `module.lab`）、`ACC-PRO-2`（重复声明被拒，理由是能力 id 只能有一个主人）；听澜侧的 `DialogueParticipantContractValidatorTest` |
| 4 模型工具能力 | `TianshuTools`、`CapabilityCatalog` / `CapabilityExposure`、`TianshuTool` / `ToolSpec` / `ToolCaller` | `ACC-EXP-1..4`、`ACC-ARG-*`、`ACC-AGT-*`、`ACC-CAT-*`、`ACC-CAP-*` |
| 5 玩家辅助 | 工具 id：`craft.recipe`、`block.machine`、`container.transfer`、`block.interact`、`block.place`；端口：`CraftPort`、`BlockMachinePort`、`ContainerTransferPort`、`BlockInteractPort`、`BlockPlacePort` | `ACC-CNR-1`、`ACC-GIV-1`、`ACC-PLC-1`（客户端侧可达与拒绝）＋游戏内测试五条成功路径（`block.place` / `container.transfer` / `craft.recipe` / `block.machine` / `block.interact`，断言世界状态，见 §5.3） |
| 6 自定义实体 | `EntityActors` / `EntityProvider` / `EntityActor` / `EntityActions`、`EntitySpawnPort`（`spawn` + `release`）、`EntityTypes` / `EntityTypeSpec` | `ACC-ENT-2`（声明类型 → 生成 → 归属 → 外来释放被拒 → 自己释放）、`ACC-ENT-3`（自己声明的载体经 motion 端口真的走了 2 格）、`ACC-BDY-1..4`、`ACC-BDY-7`、`ACC-ENT-1`；`CarrierNameTest`、`EntityTypesTest` |

**这条证据链的含义要说清**：验收台是一个只依赖公开面的模块（`tianshu_lab`），所以上表证明的是
"同进程内的外部模块能正常声明与调用"。它**不**证明"独立编译、只依赖发布 jar 的第三方模块"也能编译通过——
那需要另做一个只依赖发布产物的 smoke 模块，目前还没有。

## 3. 验收台（`tianshu-lab`）

**入口两个**：

```bash
# ① 无人值守（启动后自动跑一次，等工具表填满；加 world 还会等世界与玩家就绪）
./gradlew :tianshu-adapter:1.21.1-neoforge:runClient -PtianshuLabAcceptance=1
./gradlew :tianshu-adapter:1.21.1-neoforge:runClient "-PquickPlayWorld=New World" -PtianshuLabAcceptance=world
# ② 游戏内：设置 →【听澜】仲裁测试台 →「运行平台验收」
```

**证据两处同源**：`run/tianshu-lab/acceptance-<时间戳>.json` 与 `run/logs/tianshu-diagnostics.log` 的 `acceptance.run` 事件。

**实机状态（2026-11-16，专用服务器 + op 玩家）**：**44 通过 + 2 跳过 + 自检变红，accepted=true，0 失败**。跳过的是两条身体用例——验收台的身体 provider 在客户端进程内，远程服务端没有它，因此按范围跳过。三条"服务端动作"用例在专用服上真实执行/被拒：`xp` 执行成功、`setblock` 非法方块名回 `INVALID_ARGS`、`teleport` 开关关着回 `DISABLED`。

要验证"动作真的被执行"这一半，需要 op 环境：① 专用服务器 + `ops.json`（首选，动作本来就是服务端职责）；② 或开作弊的单机世界。验收前还需把 `config/tianshu_ferry-server.toml` 的 `ceiling` 调到 `full` 并打开对应动作开关；验收后要改回 `conservative`。

**当前规模**：47 条 + 1 条自检，分 11 个面（新增"服务端动作"一面）：

| 面 | 条数 | 代表断言 |
|---|---|---|
| 模型工具能力注册与调用 | 5 | 两视角一致、关闭工具仍列出、FULL 档对保守档不可见、放宽档位只增不减 |
| 工具参数契约 | 3 | 严格 schema 拒绝未声明字段、两种拒绝不混、每个已发布 schema 都声明严格性 |
| 能力表 | 14 | revision 与监听器、快照不变、预算切断、`page` 透传、三类能力都能读 |
| 智能体门面 | 4 | 真实注册表上的发现/调用/读取、契约里的协议名与并发上限、退订 |
| 设置 | 1 | 无 `persist` 拒绝构建 |
| 实体工具 | 6 | 13 个 `body.*` 注册与参数契约；服务端验证模组归属，跨模组调用在到达身体端口前被拒绝 |
| 模块执行通道 | 1 | 任务在通道执行，抛异常不污染通道 |
| 模型下载校验 | 2 | 校验失败绝不提升；坏字节同主机重下 |
| 世界上下文 | 2 | 有世界时 11 项采集齐全且不抛 |
| 诊断 | 4 | 空白身份被拒、异常监听器不饿死别人、null 归一、缺 severity 被拒 |

**三条硬规矩**：

1. 用例 id 与文档同源；覆盖声明（`coveredAreas`）与未覆盖清单（`uncovered`）都印在报告里。
2. 跑不了的显式 SKIP 并写原因，不许静默通过。
3. **`SELF-CHECK-1` 必须失败**；它若 PASS，整轮 `accepted=false`——验收台自己必须能证明会失败。

## 5. 1.21.1 可用性验收

> 「可用」= 下面四层都有**当轮**证据。跑不了的项写明原因，不许静默通过。
> 入口分两种，别混：**验收台入口**（`:tianshu-adapter:1.21.1-*`，只加载 内核 + 验收台）够跑自动化；
> **全装配入口**（根工程 `./gradlew runClient`）才带听澜 / 回响 / 织言 / 天枢 / 映迹，语音与 HUD 只能在这里测。

判据：`BUILD SUCCESSFUL`，输出里没有 `FAILED`。**2026-11-25 已绿**（75 tasks）。

### 5.2 B 验收台（每个加载器约 3 分钟）

```bash
./gradlew :tianshu-adapter:1.21.1-neoforge:runClient "-PquickPlayWorld=New World" -PtianshuLabAcceptance=world --offline
./gradlew :tianshu-adapter:1.21.1-fabric:runClient   "-PquickPlayWorld=New World" -PtianshuLabAcceptance=world --offline
```

**必须进世界**：模块装配发生在世界会话里（客户端就绪只装工具与内容来源），标题界面上没有模块运行时，
验收台不会跑、也不会写报告。`-PtianshuLabAcceptance=world` 让它等进世界与玩家就绪后再跑。

**装的是哪些模块**：从适配器启动的开发运行 = 内核 + 验收台（`lab`），两个加载器同一套规则，由根构建按
模块矩阵算出；从仓库根启动才是全装配。要别组合就显式说：`-PfeatureMods=lab`（只内核+验收台）、
`-PfeatureMods=` （只内核）。验收台是普通模块，它的 jar 里带两个加载器的入口。

判据：

1. **窗口别关**。进世界后约 5–30 秒自动跑完，日志里出现
   `-- report: <run 目录>\tianshu-lab\acceptance-<数字>.json`。
2. 报告里 `accepted=true`、`selfCheckHeld=true`、失败 0；`SKIP` 必须带原因。
3. 预期 SKIP：联机下的身体 provider 两条（验收台的身体在客户端进程里，远程服没有它）。

证据两处同源：`tianshu-adapter/1.21.1-<loader>/run/tianshu-lab/acceptance-*.json` 与 `run/logs/tianshu-diagnostics.log` 的 `acceptance.run` 事件。

### 5.3 C 专用服务器与联机（约 30 分钟）

1. **起服**（NeoForge；`run/server.properties` 已是 `online-mode=false`、端口 25565，`Dev` 已是 level 4 op）：
   `./gradlew :tianshu-adapter:1.21.1-neoforge:runServer --offline`
2. **进服**：`./gradlew :tianshu-adapter:1.21.1-neoforge:runClient "-PquickPlayServer=127.0.0.1:25565" -PtianshuLabAcceptance=world --offline`
   （联机跑验收台会自动跳过两条身体 provider 用例：验收台的身体在客户端进程里，远端服没有它。）
3. **服务端动作真的执行**：编辑 `run/config/tianshu_ferry-server.toml`，`ceiling` 改 `"full"`、打开要测的开关
   （`set_time` / `teleport` / `give_item` / `set_weather` …，默认全 `false`），重启服务器；在对话里让助手做一次
   （"把时间设成白天"），看世界是否真的变。再把开关关回去要一次，应答 `DISABLED`。
   > 开关的"关着"路径要在关着的时候测：开着 `teleport` 时 `ACC-ACT-2` 会跳过并写明原因（off 路径不可观测）。
4. **单侧安装**（协议表前两行）：
   - 服务端装舟楫、客户端用**原版** 1.21.1 进服 → 能进、不掉线、`logs/latest.log` 没有 payload 报错；
     （所有 Ferry 通道都注册为 `optional()`，这是能进的前提，不是结论——要拿原版客户端证。）
   - 客户端装舟楫、服务端是原版 → 能进服，设置页可用，远端工具**不出现**（服务端目录为空）。
5. **身体**（服务端命令，不需要 op）：
   - `/tianshu body spawn walker` → `/tianshu body list` 里出现；
   - `/tianshu body give <id> minecraft:diamond 5`、`/tianshu body access <id> trusted` 都成功；
   - 让它走/挖一次（对话或验收台），看动作真的发生；
   - **存档重载**：`save-all flush` → `stop` → 起服 → **进服（或 `forceload add <x> <z>`）** → `list` 里还在，背包、归属、访问设置都在；
   - **归属**：非 owner 的命令调用应回 `NO_PERMISSION` + `body.controller.mismatch`；
     `/tianshu body access <id> open`（或 `trusted` + `/tianshu body trust <id> <玩家UUID>`）后放行。

   - **游戏内测试**（需要真实服务端世界的部分，例如"物品真的进了箱子"）：`:tianshu-adapter:1.21.1-neoforge:runGameTestServer`，
     它用自己的 `run-gametest` 目录，夹具在 `src/gametest/resources/data/tianshu_ferry/structure/plaza.nbt`。
     **判定看日志里的 `All N required tests passed`**——这个任务的退出码不反映游戏内崩溃，只看 exit code 会把失败当成功。     
     写这类用例有三件事必须记牢：端口请求收的是**绝对坐标**（夹具坐标要用 `absolutePos` 换算）、假玩家要**显式站到夹具旁并切成生存**（创造模式下什么都不消耗，断言会假通过）、端口的 future 就在服务端线程上完成，所以只能靠序列等待，不能在测试线程里阻塞。
   > 两件实测踩过的事：① 载体没被加载时 `list` 看不见它——**先让那块地加载**（玩家站过去或 `forceload`），
   > 等一两秒再查；② `stop` 之后要**等进程自己退**，中途强杀会让世界存档落后于身体存档（注册表已经写了、
   > 世界还没写完），看起来就像"身体没重载"。载体死在环境里（例如生成在方块内窒息）时，注册表条目会随死亡
   > 一起删掉，不留隐形记录。
6. **两个世界一进程**：进世界 A → 退到标题 → 进世界 B → 无异常、工具可用、**世界记忆不串档**；回 A 记忆恢复。

## 6. 门禁的教训

- 12 个 `verify*` 里曾有 **4 个在空转**（路径写死 `core/<module>`、`inputs.dir` 不展开目录），修好后两个做过变异验证。
- 教训写成一句：**"通过"只有在能证明它会失败时才算数**。验收台的 `SELF-CHECK-1` 就是这条规则的产物。
- 本地文件系统故障、并发正确性、跨版本 API 存在性仍是盲区（后者要靠离线 API 签名索引）。
