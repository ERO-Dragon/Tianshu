# 工具层设计（RFC）

> 状态：**契约层已实现**。`tianshu-api` 的 `com.rheinmetal.tianshu.api.tool` 包落地了工具描述、注册表、
> 调用者与策略、侧路由端口与 JSON 信封，10 个契约测试通过；平台侧通道与首批具体工具仍未做（见 §10）。
>
> 一句话：把基座的能力做成**命名工具**，让同一份契约同时服务两件事——天枢（Agent）的 function-calling，
> 以及其他模组的纯逻辑调用。工具不属于智能体，智能体只是调用者之一。
>
> 三条原则：**读默认开、写默认关**；**工具不绑定智能体**；**第三方工具通过既有接入 API 注册**。

## 0. 不做什么

- 不做「任意执行游戏逻辑」的万能接口——那是作弊面，不是能力面。
- 本轮不做实体移动与玩家移动（工具层机制上可以承载，先不排期）。
- 不改协议中心、模块生命周期，也不改现有服务端动作（给物品/传送/时间/天气）的语义。

## 1. 两个消费者，一个注册表

```
            ┌────────────────────────────────┐
            │   TianshuTools（tianshu-api）  │
            │   spec + 注册表 + 策略          │
            └───────┬───────────────┬────────┘
                    │               │
      ToolCaller.AGENT       ToolCaller.MOD("yourmod")
      （天枢的 function-calling）（其他模组的纯逻辑代码）
```

注册表只负责「有哪些工具、当前这一侧可不可用、谁有权限」。调用者是智能体还是模组，只影响策略判定，
不影响工具实现。

## 2. 工具描述

每个工具一份不可变描述，注册时登记：

| 字段 | 含义 |
|---|---|
| `id` | 带命名空间：`tianshu:recipe.query`、`yourmod:my.query` |
| `category` | `LOCAL` / `SERVER_READ` / `SERVER_WRITE` |
| `args` / `result` | 两个 Java `Type`；注册表用它们做 JSON 往返（typed 调用直接传对象，智能体调用传 JSON） |
| `timeout` | 单次调用上限，默认 2 秒 |
| `rateLimit` | 每秒/每轮次数上限 |
| `permission` | 普通玩家 / 需要管理员 |
| `description` | 一句话，给智能体与文档共用 |

## 3. 调用接口

同一份实现，两种入口：

```java
// 模组的工具实现：声明契约，执行一次
public interface TianshuTool<A, R> {
    ToolId id();
    ToolCategory category();
    String description();
    Type argsType();                  // 注册表用它做 JSON 往返
    Type resultType();
    CompletableFuture<R> invoke(ToolContext context, A args);
}

// 模组调用：类型化句柄，拿到 Java 对象
ToolHandle<RecipeQuery, RecipeList> recipes =
        TianshuTools.handle(ToolId.of("tianshu", "recipe.query"), RecipeQuery.class, RecipeList.class);
RecipeList list = recipes.call(new RecipeQuery("minecraft:iron_pickaxe", 3), ToolCaller.mod("yourmod"))
        .get(2, TimeUnit.SECONDS);

// 智能体调用：同一个工具，参数与结果都是 JSON，错误是结构化返回值
JsonObject json = TianshuTools.callJson(
        ToolId.of("tianshu", "recipe.query"),
        JsonParser.parseString("{\"output\":\"minecraft:iron_pickaxe\",\"limit\":3}"),
        ToolCaller.agent(false)
).get(2, TimeUnit.SECONDS);
```

契约层不引 DFU，因为 `tianshu-api` 必须保持与平台无关（`verifyNoPlatformImport` 会拒绝 `com.mojang.serialization`）。
JSON 往返用 gson（Minecraft 自带），typed 句柄负责把同一份实现暴露成 Java 对象。

`ToolContext` 携带调用发生的侧、玩家（如果由玩家发起）、以及只在该侧有效的数据句柄；工具实现不得缓存它。

## 4. 类目与默认策略

| 类目 | 例子 | 默认 | 执行位置 |
|---|---|---|---|
| `LOCAL` | 配方查询（客户端已同步）、物品/方块/标签、背包 | **开** | 客户端，本线程，即时返回 |
| `SERVER_READ` | 战利品表、结构位置、权威配方、游戏规则 | **开** | 服务端组件 |
| `SERVER_WRITE` | 方块交互、合成、容器搬运、机器操作 | **关** | 服务端组件，逐项授权 |

配置形状沿用 `ServerActionConfig`：全局开关 + 每类目默认 + 每工具覆盖 + 按玩家权限；写操作额外要求
管理员显式开启，并写审计日志。

## 5. 调用者与权限

| 调用者 | 身份来源 | 用途 |
|---|---|---|
| `ToolCaller.agent()` | 天枢 | function-calling 的可用工具列表 |
| `ToolCaller.mod(id)` | 第三方模组 | 纯逻辑调用，不经 LLM |
| `ToolCaller.player(uuid)` | 玩家 | 客户端发起、需要以玩家身份执行的工具 |

规则：

1. **注册不等于授权**：第三方注册 `SERVER_WRITE` 工具也不会默认开启；
2. 同一个工具可以按调用者区分策略（例如写工具只允许玩家显式触发，不允许智能体自主触发）；
3. 目录（`catalog`）按「当前侧 + 调用者权限 + 服务端组件是否在场」过滤，不可用的工具直接不出现。

## 6. 侧路由与降级

- `LOCAL`：本线程执行；如需游戏状态，由 API 内部切到客户端主线程；
- `SERVER_READ` / `SERVER_WRITE`：走现有请求/响应通道（复用 `ServerActionHandler` 的信封与结果包），带超时；
- 服务端没有舟楫组件：**立即**返回 `UNSUPPORTED_SIDE`，不重试、不挂起；智能体据此告知玩家「这台服务器未启用」；
- 两端都有的能力：标记 `EITHER`，客户端先用本地数据回答，服务端在场时以服务端为准。

## 7. 注册、命名与冲突

- id 必须带命名空间，禁止裸 `recipe.query`；
- 同一 id 重复注册：直接报错并列出两个注册者，不静默覆盖；
- 客户端与服务端各自注册各自侧的工具；同一 id 两侧都注册时按类目合并，不视为冲突；
- 第三方注册入口复用 `TianshuIntegrationAccess`（见[外部接入指南](../../EXTERNAL_INTEGRATION_GUIDE.md)）。

## 8. 线程、超时、限流、审计

- 统一返回 `CompletableFuture`；工具实现只允许在对应主线程访问游戏状态；
- 每个工具带 `timeout` 与 `rateLimit`；智能体侧另有「每轮工具调用次数」预算；
- `SERVER_WRITE` 审计：调用者（玩家/模组/智能体）、工具 id、参数摘要、结果状态，写服务端日志；
- 未知 id、参数不合法、超时、无权限都返回结构化错误，不抛异常穿透。

## 9. 代码落点

| 位置 | 内容 |
|---|---|
| `tianshu-api` | `TianshuTool`、`ToolId`、`ToolCaller`、`ToolContext`、`TianshuTools`、配置模型 |
| `tianshu-client` | `LOCAL` 工具实现（配方、物品、标签、背包） |

## 10. 首批工具

**只读（先做）**

| id | 类目 | 说明 |
|---|---|---|
| `tianshu:recipe.query` | `LOCAL`（`EITHER`） | 按产出/输入/配方类型查配方 |
| `tianshu:item.tag` | `LOCAL` | 查物品/方块的标签成员关系 |
| `tianshu:inventory.inspect` | `LOCAL` | 本地背包快照 |
| `tianshu:loot.query` | `SERVER_READ` | 按方块/实体查战利品表（定向查询，不下发整表） |

**写操作（默认全关，按复杂度排序）**

| id | 说明 |
|---|---|
| `tianshu:block.interact` | 以玩家身份操作无害方块：按钮、拉杆、门、工作台。破坏/放置/点火不进这一档 |
| `tianshu:craft.recipe` | 按配方合成，覆盖有序/无序与模组自定义配方类型 |
| `tianshu:container.transfer` | 容器槽位搬运，含容量与堆叠校验 |
| `tianshu:block.machine` | 让机器工作（熔炉燃料/投料、漏斗等），按方块实体类型做能力探测，不支持就明确拒绝 |

## 11. 与现有机制的关系

| 现有机制 | 关系 |
|---|---|
| `ServerActionHandler` | 动作目录、权限、开关、结果包——写工具直接复用这套信封 |
| `GameFactCollector` | 服务端事实推送；服务端读工具可复用它的请求/响应形态 |
| `TianshuIntegrationAccess` | 第三方注册工具的入口 |
| 协议中心 | 工具调用走信封，不新增 broker；不改变 topic 语义 |

## 12. 版本与兼容

- 工具 id 与 schema 属于协议面，变更按 [API 兼容策略](API兼容策略.md) 走；
- 协议版本仍由单一来源声明，工具**不单独引入版本号**；
- 旧工具退役先保留 id 并返回 `DEPRECATED`，一个次版本后再删。

## 14. 未决问题

1. 审计日志里的参数摘要保留多少（隐私 vs 可追溯），默认是否只记 key 不记 value；
2. 写工具是否需要按存档（serverconfig）覆盖，还是只按实例配置；
3. 第三方工具能否声明「需要另一个模组在场」的依赖，以及这种依赖在目录过滤里如何表达；
4. 智能体调用写工具时，是每次要求玩家确认，还是按工具配置一次授权。
