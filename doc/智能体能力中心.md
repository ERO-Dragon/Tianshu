## 1. 能力表

协议中心按协议能力 ID 向处理模组投递消息。模组希望把某项功能提供给智能体时，在本中心单独发布工具、技能、资源、提示词或工作流。工具实现可以在内部使用协议中心投递请求。

`CapabilityCatalog` 是"有什么能力、谁能看见"的唯一一张表。一行是 `CapabilityDescriptor`：
id、种类、绑定、描述、端、权限、提供方、属性。

| 种类 | 是什么 | 谁发布 |
|---|---|---|
| `TOOL` | 模型可调的一步操作 | 提供方通过 `TianshuTools.register` 登记工具及归属 |
| `SKILL` / `RESOURCE` / `PROMPT` | 给模型读的材料（说明书、资料、模板） | 内容提供方（classpath 或目录） |
| `WORKFLOW` | 一串能力的编排 | 见 §6 |

**id 命名空间 ≠ 提供方**：`minecraft:*` 表示"操作的是原版能力"，提供方仍是 `tianshu`（基座）。
两个轴分开，是为了"这些能力是谁发明的"和"这条行是谁登记的"都能回答。

**kind 与 binding 是两个正交维度**：`MCP` 是 binding，不是与 tool/skill 平级的 kind。
非工具行的超时默认 5 秒（工具默认 2 秒），可用该行属性的 `timeoutMillis` 覆盖。

**`invoke` 的三条拒绝**：未知 id 或看不见 → `UNKNOWN_CAPABILITY`（同一句话，不确认存在）；
OPERATOR 行而调用者不是 op → `NO_PERMISSION`；`side=SERVER` 而这一端没有服务端组件 →
`UNSUPPORTED_SIDE`（立即失败，不重试）。往目录里注册 `kind=tool` 会被拒——工具必须经 `TianshuTools`。

三个消费面共用一份判定：工具的 typed/JSON 入口、`capability.read`、`invoke`。同一个能力对同一个调用方
不会出现"工具表里没有、却能调通"。

## 2. 工具契约

### 2.1 信封

成功 `{"ok":true,"result":…,"durationMs":7}`；失败 `{"ok":false,"code":"…","message":"…","durationMs":7}`。
成功可以带 `bytes`，失败只带 `durationMs`。工具只回这两种形状，不自定义外层。

### 2.2 参数

`argsSchema()` 是权威。缺字段、类型错、枚举外、数组项不合格、多余字段 → `INVALID_ARGS`，
消息带 `args.x` 路径。**多余字段默认拒绝**；要自由参数必须显式 `additionalProperties: true`。

**校验故意不拦数值与长度边界**：schema 是给模型的指南，不是第二道夹取；不认识的关键字忽略，
不会因为 schema 比平台懂得多而拒调。真正的边界由工具自己判。

### 2.3 拒绝码、配额与线上限

| 码 | 含义 | 是否重试 |
|---|---|---|
| `DISABLED` | 工具开关没开 | 改开关后再说 |
| `NO_PERMISSION` | 需要 operator，或没有该权限 | 不要重试 |
| `RATE_LIMITED` | 调用太密（只拦玩家与身体：读 10 次/秒、写 2 次/秒，按「工具 + 调用者」分桶） | 不要立刻重试 |
| `BUSY` | 同一调用者已有 8 个在飞 | 等一个完成 |
| `UNSUPPORTED_SIDE` | 这一端没有该组件（例如客户端没有服务端组件） | 不重试 |
| `UNSUPPORTED_ACTOR` | 这个身体没声明该能力位 | 换执行者 |
| `UNAVAILABLE` | 传输失败 | 可以重试 |
| `FAILED` / `TIMEOUT` | 平台自身失败 / 超时 | 视情况 |

- **默认超时 2 秒**；长操作按工具策略覆盖（走 35s、挖 70s、物品使用 25s、序列 125s）。非工具能力默认 5 秒。
- **id 必须带命名空间**；同一 id 重复注册直接报错，并列出两个注册者。
- `UNSUPPORTED_SIDE` 与 `UNSUPPORTED_ACTOR` 都与"执行失败"分开——前者是这一端没有，后者是这具身体没这个能力，
  修法都不同。双端都实现的能力标记 `EITHER`。
- **幂等重放**：同一（调用者, `requestId`）在 120 秒内重放，返回缓存回执，不重复执行；最多缓存 512 条。
- **线上限**（`ToolWireLimits`）：requestId / toolId / code 各 64 字符，JSON 32767 字符，message 512，
  目录最多 64 个工具。**请求字段超限直接拒；结果超限变成结构化失败**，不丢包——丢包会让调用方在动作
  已经执行后干等超时。
- **取消是协作式的**：`tool.cancel` 先翻转 token 再取消 future；同步占满服务端线程的工具要跑完才看得到取消。
- **退役**先保留 id 返回 `DEPRECATED`，一个次版本后再删。

### 2.4 服务端动作

需要服务端真实状态的行为（传送、天气、时间、给物品、生成实体、广播、游戏模式、状态效果、经验、
任意坐标放置、清除实体、附魔、难度、游戏规则）是 **14 个 `FULL` 档工具**，写成一张 whitelist 表，
加一个动作＝表里一行 + 服务端执行器一个分支 + 一个开关。

- **默认全关，执行需要 operator**（`FULL` 档的默认策略，实际执行者是 OP 等级 2）；开关在服务端配置里，
  文件名随 mod id（`tianshu_ferry-server.toml`），存档可以用自己的 `serverconfig/` 覆盖。
- **执行只有一个入口**：`ServerActionExecutionPort`。工具层只拿参数，服务端拿玩家与权限。
- **回执五态**：`OK` / `DENIED` / `DISABLED` / `INVALID` / `FAILED`。服务端拒绝时保留原码，不本地伪造。
- 说话不在这张表里：`server.say` 是本地工具，任何玩家都能在聊天频道说一句。

**唯一的审批出口是 `command.run`**：第一次调用不执行，只回一个一次性令牌；`/tianshu approve <令牌>`（权限 2）
批准后才真正执行。令牌绑定**谁**与**哪一行**、单次有效、5 分钟过期——只写"已批准"的令牌能被挪去跑别的命令。

### 2.5 目录与刷新

会话目录给出工具 schema 与版本。服务端保留请求 `minecraft:tool.catalog` 返回当前可见的服务端工具 ID 和开关。
服务端目录**每一格都带 `enabled`**（登录推送、主动刷新、热重载同一形状）：客户端以服务端开关为准。
推送是主路径，**60 秒轮询兜底**（各 adapter 都已接推送，轮询留给旧对端）。

### 2.6 两个入口与智能体门面

模型走工具表（`TianshuTools` / `CapabilityExposure`），模块走 `CapabilityCatalog.invoke`。
两条都过同一套权限、档位与超时。

进程内还有一个统一门面 `AgentSession`（client / server 两端）：tools / capabilities / call / callHandled /
read / onChange / cancel，**不引入第二套注册表**。它的 `describe()` 返回 `tianshu.agent/1` 契约
（protocol + revision + caller + side + limits + tools + capabilities），其中
`maxInFlightPerCaller = 8`；线程与侧由调用方负责，跨进程仍走 MCP 只读端点。

**MCP 的边界**：MCP **服务端**（把能力暴露给外部）不属舟楫；MCP **客户端**（消费外部能力）在舟楫，
外部工具 id 形如 `mcp:<server>.<tool>`。

## 3. 玩家辅助与实体能力

玩家辅助使用 `READ_ONLY`、`CONSERVATIVE`、`FULL` 三档。实体动作按生存能力和作弊能力分为两档。读取身体状态不占动作档位。

### 玩家辅助

三道门决定一次玩家辅助调用能不能执行，各有各的回答者：

| 门 | 谁回答 | 不通过时 |
|---|---|---|
| **档位** | `requiredAutonomy()`（工具声明）+ 调用方的 ceiling | `NO_PERMISSION` |
| **权限** | `ToolPolicy.permission()` | `NO_PERMISSION`（要 op 而你不是） |
| **开关** | `enabledByDefault()`，`FULL` 档的工具另有服务器开关 | `DISABLED` |

`ToolPolicy.forTier` 给出档位默认值；类别只提供它的默认档位（`SERVER_WRITE` → `CONSERVATIVE`，玩家查询和本地工具默认 `READ_ONLY`）：

| 档位 | 权限 | 默认 | 谁落在这一档 |
|---|---|---|---|
| `READ_ONLY` | EVERYONE | 开 | 只读：读方块、读背包、查配方 |
| `CONSERVATIVE` | EVERYONE | 开 | 玩家用手也能做的事：合成、搬物品、按按钮、操作工作方块 |
| `FULL` | OPERATOR | 关 | 传送、给物品、天气、时间、跑命令…每把一个开关 |

**开关跟档位走，不跟类别走**：只有 `FULL` 档是 operator 主动交出去的权，所以只有它默认关、一把开关、还要 operator。
到 `conservative` 为止的工具**不要开关**——档位就是闸门，多一个开关只会让"我明明开了 conservative 为什么它还是
DISABLED"变成常态。

生存动作（合成、搬物品、操作工作方块、按按钮）类别是 `SERVER_WRITE`，默认档位 `CONSERVATIVE`，**因此默认就开着、
不需要 operator**：它们就是普通玩家用手能做的事，**动作以该玩家身份执行**，原版权限、领地规则、游戏模式照常拦截。
模块自己写一个同类工具也不用记任何覆盖——这是默认行为，不是四个工具的特例。

**类别只管默认档位，档位是每个工具自己声明的**：`requiredAutonomy()` 默认按类别给（`SERVER_WRITE` →
`CONSERVATIVE`，玩家查询和本地工具默认 `READ_ONLY`），要到 `FULL` 才需要显式覆盖——`client.audio.set` 改的是客户端但仍在
`CONSERVATIVE`，`command.run` 与 14 个服务端动作显式声明 `FULL`。各玩家工具落在哪一档见 [玩家辅助](玩家辅助.md) §2。

### 实体能力

工具统一通过 `requiredAutonomy()` 声明 `AutonomyRequirement`。玩家工具返回 `ToolAutonomy`，实体动作返回 `BodyAutonomy`，实体查询返回 `AutonomyRequirement.None.INSTANCE`。注册时校验档位与工具类别一致。

实体查询类别是 `BODY_READ`，无需动作档位。实体动作类别是 `BODY_WRITE`，目录用 `bodyAutonomy` 标记工具的最低档位。服主配置 `npc.ceiling`，可选 `survival`（默认）或 `cheat`。该上限对所有 NPC 生效，独立于玩家辅助的 `autonomy.ceiling`。

服务器同时检查工具最低档位、身体归属和执行该动作所需的能力。原生飞行或瞬移可在生存档使用；附加的特权动作需要作弊档。目录按工具筛选，实际调用再按身体和参数判断。`entity.command.run` 是作弊工具，命令须逐次获操作员批准。

**放方块、拆方块、用手里的物品没有玩家侧 id**：这三件事是玩家自己的手在干，模组不替他决定
（[职责边界](职责边界.md) §7）。要它们就派身体去做——`entity.place` / `entity.place.line` / `entity.mine` /
`entity.item.use` 用的是**身体**的手与背包。

玩家侧两条轴的完整语义见 [职责边界](职责边界.md) §3。

## 4. 共享与订阅

**两个维度，缺一不可**：提供方开放哪些行，消费方接受哪些行。两半都满足才可见。

**提供方**在注册能力时声明 `share`（`all` / `none` / 模块列表）。技能与文本类能力的声明写在
front matter 的 `metadata.share`——`metadata` 是 Agent Skills 规范留给平台私有数据的映射，顶层自造字段
会让文件不可移植（当年写过 `covers:`，结果那份技能不能被别的工具读）。

**默认跟随提供方**：基座 `tianshu` 与玩家自己的目录 `user` 不写就按开放算，第三方不写即私有。
未声明就开放等于"装两个模组就互相开门"，所以模块侧必须失败关闭。

**消费方默认零外部订阅。** 模组和智能体可以使用本模组发布的条目。来自舟楫、其他模组和玩家目录的条目都需要消费方主动选择，同时提供方须向该模组开放。玩家直接操作和实体执行沿用各自的身份与权限规则。

模组按条目 ID 订阅，工具、技能、资源、提示词和工作流都可以单独选择。例如，一个助手只需要方块交互和该工具的说明时，可以声明

```java
CapabilitySubscriptions.declare("changsui", CapabilitySubscription.only(
        CapabilityId.parse("tianshu:player-tools"),
        CapabilityId.parse("minecraft:block.interact")));
```

- `only()` 与未声明的外部目录都为空。安装新模组或新增公开条目不会扩大逐项订阅的范围。
- 工具的单项说明随工具可读。舟楫统一提供 `minecraft:capability.read`，消费方无需另行订阅阅读器。按技能 ID 读入口 `SKILL.md`，按工具 ID 读附件；通过技能内文件路径读取同一份工具说明也检查工具订阅。整本技能手册、资源或提示词各有自己的 ID，按需订阅。
- 消费方也可明确选择提供方范围。`atomicFrom(...)` 接受指定提供方的原子能力，`everythingFrom(...)` 同时接受其工作流。天枢助手逐项订阅舟楫的玩家技能入口与玩家工具。新增工具须由助手显式加入订阅清单。阅读器随平台提供。
- 实体工作流在 `WorkflowDeclaration` 声明 `ActorRef.Kind.BODY`，入口使用 NPC 档位；每一步仍按实际调用者的身份检查。工具开关、档位、端侧和执行权限继续生效。
- 普通工具通过 `TianshuTools.register(tool)` 发布时，以工具命名空间为默认提供方，范围为私有。需要共享或单独指定归属时，使用 `TianshuTools.register(tool, moduleId, CapabilitySharing.only("changsui"))`。

会话描述中的工具和能力清单取自同一份目录及订阅规则。修改或撤回订阅会更新会话版本，并向该消费方通知可见条目的增减。

能力目录、会话变更通知、正文读取与实际调用都检查共享和订阅。隐藏的能力在能力调用入口返回 `UNKNOWN_CAPABILITY`，在工具入口返回 `UNKNOWN_TOOL`。

`CapabilitySubscriptions.audit()` 把三种声明错误分开报：订阅了没向谁开放的提供方、订阅了没装的模组、
点名了没人发布的能力。

## 5. 工具文档与技能

**一个工具一份文档，文档住在装它的技能里**：

```
minecraft:entity.mine  →  <某个技能>/references/entity.mine.md
```

- 文件名由工具 id 推导（先试裸名，再试 `<命名空间>.<名字>`），没有索引可漂移；
- 查找由**技能自己提供**（`SkillReferences`）：按工具 id 问已注册的技能"你的 `references/` 里有没有这个文件"。
  类路径扫描只能扫到基座自己的文件，第三方模组和玩家目录的说明书永远查不到；
- 模组通过 `CapabilitySources` 分别注册技能、资源和提示词，每次注册返回独立句柄。模组卸载时调用句柄的 `close()`，撤下对应内容并释放注册位置，之后可重新注册。技能卸载时，其工具说明一同下线；
- 权限在**工具行**上：不会出现"文档读得到、工具调不动"，反之亦然。

**技能（`SKILL.md` + `references/`）讲成篇的东西**：调用约定、失败怎么读、一组工具共同的前提。
它不声明自己教哪几个工具——文档是工具行的附件，不是第二种能力。写法见 [技能撰写规范](技能撰写规范.md)。

**门禁**：`verifyEveryToolHasADocument` 按照启动时的声明检查玩家和实体工具的 reference 及调用示例。平台阅读器的用法和示例在两本技能入口中校验。
没有它时，新增工具忘写文档是完全无声的——说明书就是不出现，谁也不知道少了。

## 6. 复合能力（工作流）

`kind=WORKFLOW` 只是分类（订阅要用），**不是另一种入口**：调用方式与原子能力完全相同，按 id 调。

- 每个复合能力**必须声明代价**：预计耗时、影响范围、有无副作用、是否响应取消；
- **步骤清单可以公开也可以不公开**：公开时基座执行器逐步执行（能数步、能在步边界停、逐步套调用者档位），
  不公开时提供方自己执行、靠"响应取消 + 超时硬截断"兜底；
- 两种都合法，区别只在可观测性与可中断性，不是安全性。

舟楫安装的声明式工作流从工具入口和能力入口调用时共用开关、权限、档位和结果格式。步骤失败会使整次调用返回失败。主动取消在步骤边界返回已执行步数，达到截止时间则返回 `TIMEOUT`，后续步骤停止启动。已经开始的步骤能否中止取决于其实现。

**不做的**：把两种执行方式再分成两类（无安全差异）；工作流的循环/递归/变量（按证据再长）。

## 7. 对外 API 的兼容承诺

模块编译期能碰到的一切都算 API：**拿不准按"算"处理**。

- **0.x 内可以新增**：新增接口方法必须是 `default`；**id 改名要留旧名别名到 1.0.0**；不删公开类型。
- **`apiVersion` 由 MAJOR 推导**，写进构建产物、由能力探针读取，不手工维护；它只用于展示，
  **不作加载门槛**——门槛看模块清单里的 `versionRange`。
- **弃用** = `@Deprecated` + 运行时 WARN + 主仓库 `doc/api-deprecations.md` 登记；
  1.0.0 的移除清单从那份文档生成，不另立一份。

## 8. 工具清单的落点

工具清单不在这篇里——它按功能方向分成两份，各自只讲自己那一侧的 35 / 29 个工具：

两个方向共用阅读器。下表同时列出适配器的两项协议保留请求。

| id | 做什么 |
|---|---|
| `minecraft:capability.read` | 读取已订阅的技能正文或工具说明 |
| `tool.catalog` | 适配器请求服务端目录，返回 tools 数组，每项包含 id 和 enabled |
| `tool.cancel` | 适配器发送原调用的 requestId，结果 cancelled 表示是否找到并取消 |

两个方向的档位规则不同，这是**故意**的（[职责边界](职责边界.md) §3）：玩家侧有 `READ_ONLY` /
`CONSERVATIVE` / `FULL` 三档与 `ceiling`，实体动作分生存、作弊两档，并检查身体归属及能力位。
把两边的清单并在一张表里，读者会以为它们共用一套尺子。
