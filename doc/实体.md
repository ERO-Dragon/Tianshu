# 实体

> 「自定义实体」这一功能方向的唯一落点：三层对象、两条轴、能力位与端口、注册与创建、基座、写盘、行为边界。
> 模组：`tianshu-api`（端口与类型定义）+ 各加载器 adapter（基座实现）。
> 为什么是这些边界，见 [职责边界](职责边界.md) §2–4。

## 1. 三层对象

| 对象 | 是什么 |
|---|---|
| `EntityActor` | 一个可被驱动的实体实例：身份 + 能力位 + 归属 |
| `EntityActions` | 它的动作实现：11 个可选端口，缺省即没有该能力 |
| `EntityActors` | 注册与查找：模组注册 provider，平台按归属取处理器 |

包位置：`com.rheinmetal.tianshu.api.entity`。

## 2. 两条正交的轴

身体的自由度来自两条彼此独立的轴，不是一个类型树：

| 轴 | 表达 | 决定 |
|---|---|---|
| **形状** `BodyKind` | `marker` / `stand` / `walker` / 模组声明的 `<命名空间>:<名字>` | 能力位、碰撞、外观、用哪种实体基座 |
| **身份** `playerLike` | 普通 / 玩家型 | 谁代表它执行动作、是否享受玩家权限与领地判定 |

两者自由组合：walker + 普通 = 会走路的身子；orb + 普通 = 光球；walker + 玩家 = 受领地约束的 NPC。

**硬规矩**：平台与工具层**不得出现任何"玩家型 / 非玩家型"的分支**。身份只影响两件事——适配器选哪种基座、
用哪个执行者；能力位、工具、授权链、归属对两种身份完全相同。`playerLike()` 只作数据，任何工具都不读它做判断。

## 3. 能力位与端口

**7 个能力位**（`EntityCapability`）：`MOVE`、`LOOK`、`USE`、`PLACE`、`MINE`、`ATTACK`、`INVENTORY`。
能力位决定"能不能做"，端口决定"怎么做"，缺省端口 = 没有该能力。

**11 个可选端口**（`EntityActions` 的 default 方法，返回 `Optional`）：

| 端口 | 覆盖 | 对应工具 |
|---|---|---|
| `EntityQueryPort` | 感知：方块/实体/射线 | `entity.scan`、`entity.block.inspect` |
| `EntityMotionPort` | 走、看 | `entity.move`、`entity.look` |
| `EntityActionPort` | 挖、攻击、动作 | `entity.mine`、`entity.attack` |
| `BlockPlacePort` / `BlockInteractPort` | 放置、交互 | `entity.place`、`entity.place.line`、`entity.interact` |
| `EntityItemPort` | 背包、装备、拾取 | `entity.equip`、`entity.pickup`、`entity.drop`、`entity.item.inspect` |
| `EntityItemUsePort` | 使用物品（含持有时长） | `entity.item.use`、`entity.sequence` 的 `item_use` 步 |
| `CraftPort` | 合成 | `entity.craft`、`entity.craft.available` |
| `ContainerTransferPort` | 容器搬运 | `entity.transfer` |
| `BlockMachinePort` | 熔炉家族 | `entity.machine` |
| `EntityUsePort` | 对其他实体交互 | `entity.use` |

平台扩展新语义的方式是**给 `EntityActions` 增加可选端口**，注册面保持一个。

## 4. 声明与创建

**声明一种实体类型**：模组在 jar 里放一个纯数据文件，不需要写任何加载器代码。

```
<模组>.jar!/META-INF/tianshu/body_types.json
[ { "name": "orb", "width": 0.5, "height": 0.5, "fireImmune": true } ]
```

**尺寸要和渲染对得上**：`width` / `height` 是**碰撞箱**。沿用平台的类人载体渲染时按人写（`0.6 × 1.8`）；写成
`0.5 × 0.5` 就会变成"名字挂在肚子、判定箱只到膝盖"——渲染和碰撞箱各按各的来，游戏不会替你纠正。

平台在**加载器的注册期**枚举所有模组、读这个文件、按 `<模组id>:<name>` 登记。两条硬规则：

1. **声明只能在注册期被取走**：之后调 `EntityTypes.declare` 直接抛 `IllegalStateException`——
   静默丢弃会让症状晚到"身体没生成"。
2. **文件必须版本中立**：只写"每条版本线语义都一样"的字段（名字、尺寸、怕火）；版本特有的东西放平台外壳，
   否则"一个包通吃 43 个 adapter"的前提就破了。

**创建一个身体**：`EntitySpawnPort` 是唯一的创建入口，也是唯一的撤销入口。

```java
spawn("mymod", "marker", position, false);      // 内建形状
spawn("mymod", "mymod:orb", position, false);   // 自己声明的类型
release("mymod", bodyId);                       // 撤销自己申请的
```

它只由服务端会话注册（随服务器一起消失），按 `playerLike` 选基座，并在这里一次性解析 `kind`。
**生成与释放是一对**——只给生成不给释放，模块申请的 NPC 就只能靠运维手段清理。释放认归属：
只有申请它的模块能释放（他人 `body.controller.mismatch`，没有这个身体 `body.target.required`），
被释放的载体直接移除、不掉落。

**模块停止时平台替它收尸**：`TianshuModuleHost.stopAll()` 在模块自己的 `stop()` 之后调
`EntitySpawnPort.withdrawAll(moduleId)`，把这具模块名下的身体全部收回。身体就是模块的逻辑在外面走——
逻辑没了，留一具空壳只会挡路；只收它自己的，别人的身体仍归别人。崩溃或强杀不走 `stop()`，那种情况身体会
留在世界里（也会被写进存档），出口仍是操作员命令 `/tianshu body despawn`。

**`kind` 的判据是服务端注册表，不是调用方的说法**：内建形状 token 任何模组都可以要；模块声明的
`命名空间:名字` 只有声明它的模组能生成（命名空间必须等于自己的 ID），别人拿就是 `body.kind.foreign`；
查不到登记项一律 `body.kind.invalid`。没有第二个生成入口，也没有网络包携带自由的 `kind` 字符串。

## 5. 基座与执行者

| 基座 | 何时用 | 现状 |
|---|---|---|
| 假玩家型（玩家语义） | 身份 = 玩家型 | 两个加载器都已实现（NeoForge 长期 `FakePlayer`；Fabric 自建 `ServerPlayer` + 回环连接） |
| 普通实体型 | 身份 = 普通 | 内建 `walker`，尺寸按声明 |

执行者在**创建时决定一次**（`BodyIdentity`）：普通身份每次动作借一个临时假玩家并把背包拷入拷出；
玩家身份直接用它自己的长期玩家（背包就是身体的背包，不拷贝）。五个动作源都从身份取玩家，**内部没有身份分支**。

持久化只存形状与背包，**不存身份**：重启后回来的身体一律是普通身份（玩家身份随它的玩家消失）。

## 6. 归属与访问

- `EntityProvider.resolve/all/actions/checkAccess` 是唯一实现面；`actions` 按归属决定用哪套处理器。
- 身体归属用内容模组在加载器清单里声明的 ID（天枢 `tianshu`、舟楫 `tianshu_ferry`）。通过舟楫命令生成的
  身体归舟楫；通过 `EntitySpawnPort` 申请的身体归申请模组。
- 申请模组随存档保存。旧档缺少模组 ID 时保留身体和物品，**任何模组都不能自动认领**。
- `EntityAccess` 管玩家访问：玩家命令及玩家会话申请的身体都记录创建者 UUID。服务端模组自主申请的身体只记录模组归属。
- 归属是"谁能驱动"的唯一依据，与调用方的 op、档位**互不替代**。
- 跨模组操作用稳定错误码：`code=NO_PERMISSION` + `message=body.controller.mismatch`；
  界面按原因标识翻译，工具回复与诊断记录保留标识。

**判定阶梯（固定顺序，不要合并成一句"没权限"）**：

1. **没有归属方，或归属对不上** → `NO_PERMISSION`，具体原因标识分两种：`body.controller.required`（没人认领）、
   `body.controller.mismatch`（不是它的归属者）。跨侧调用不再另列一条：线上只声明"哪个模块在问"，玩家那一半由连接
   决定。客户端驱动还需匹配该 NPC 的申请人 UUID，详见 [实体操作](实体操作.md) §6。
2. **身体驱动自己** → 只许自己的身体（`body.controller.self_only`）
3. **玩家没过访问设置** → `body.access.denied`
4. **这具身体不在注册表里** → `UNAVAILABLE`
5. **身体没声明该动作的能力位** → `UNSUPPORTED_ACTOR`（走不到端口）
6. **能力具备、但世界不允许**（领地、游戏模式等） → `REJECTED` / `FAILED`，由端口回

客户端智能体驱动身体还须匹配申请人的 UUID。玩家本人直接调用时按身体的玩家访问设置判定。

**第三方载体接入**：平台只认三件事——身份、能力位、处理器。它**不提供**替换内置载体渲染的钩子；
自有载体要跨重启保留的东西（外观、自定义状态）自己持久化，平台只存内置载体的注册表条目与背包。
载体 id 用实体 UUID 字符串，`entity.list`、工具参数与日志才能对上。单操作槽位按身体 id 生效，
一条序列在整段多步里持着它——序列期间再调长操作回 `BUSY`。

## 7. 三态与写盘

| 状态 | 记录 | 载体 | 语义 |
|---|---|---|---|
| 已加载 | 在 | 在 | 正常 |
| 未加载（区块卸载 / 重启时还没加载） | **在**（归属、背包、装备、访问设置、最后位置与维度都留着） | 无 | 身体还在，只是不在场；区块回来按 UUID 重新绑定 |
| 已删除（显式 `despawn`） | 删 | 删 | 这才是"不存在" |

保存时**用记录而不是"当前存活的实体"来决定写什么**，否则远处区块的身体会在下一次保存里被整条漏掉。
写盘先落 `.tmp` 再原子替换；读失败时**禁止覆盖**，避免把一份好快照换成这一进程只看见的半份。

## 8. 行为语义

| 项 | 约定 |
|---|---|
| 坐标范围 | 世界边界 ±30,000,000；越界在值类型上拒绝并翻译成 `INVALID_ARGS` |
| 槽位 | `BodyOperations` 带代际的授予：占用与过期在同一次 CAS 决定，取消信号只认当前代 |
| 组合动作 | 一次调用内的有界多步（`entity.sequence`，32 步）到点完成自己的 future 以释放槽位；未跑完不谎报成功 |
| 序列 | 未跑完不回 `ok:true`；中途维度变化即中止并给 `failedIndex`，不重新定向 |
| 物品使用 | 三坐标 all-or-none；`holdTicks` 上限 100 tick |
| 单步超时 | 见各工具 `policy().withTimeout(...)`：move 35s / mine 70s / sequence 125s / item.use 25s |
| 走路停滞 | 40 tick 内位移小于阈值即 `FAILED(stalled)`，不必等满总超时——停滞与"还在走"是两件事 |
| 死亡 | `keepInventory=true`：取消死亡、回满血，背包与装备保留；`false`：先清空实体装备槽再移除注册表条目，
避免原版重复掉落 |
| 扫描 | 必须给 `blocks` 或 `entities` 过滤（没有"全都要"）；半径 ≤16、每类 ≤256、只读已加载区块；
身体不存在回 `UNAVAILABLE`，不回空结果 |
| 装备 | `entity.equip` 只对 `BODY` 生效，玩家调用回 `INVALID_ARGS` |
| 序列上限 | 32 步；发 33 步即 `INVALID_ARGS` |

## 9. 验收口径

| 用例 | 断言 |
|---|---|
| `ACC-BDY-1` | 29 个 `entity.*` 已注册、有描述与 schema、空参调用都回信封 |
| `ACC-BDY-4` | 没有归属的调用方碰不到身体端口 |
| `ACC-BDY-5/6` | 已撤销：曾经的第二条创建门面（`EntityBodies.create`）与"谁能生成"给了两个答案，删除后一并撤销 |
| 待加 | `playerLike=true` 的身体确实拿到玩家语义、`false` 的拿不到（需要实机，合成端口验不了基座） |

**玩家型身体的人工验收**（适配器侧能力，验收台够不着）：

```
/tianshu body spawn walker player     # 生成一个带玩家身份的身体
/tianshu body list                    # 确认它在列表里
# 让它挖/放一次，看领地或玩家权限是否真的按玩家判定；切世界、断线各一次，确认没有残留
```

命令与报告位置见 [验收](验收.md) §2。
