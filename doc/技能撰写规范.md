## 1. 规范要点（自查用）

| 项 | 要求 |
|---|---|
| 目录 | 一个技能一个目录，至少含 `SKILL.md`；可选 `references/`、`scripts/`、`assets/` |
| front matter | 必填 `name`、`description`；可选 `license`、`compatibility`、`metadata`、`allowed-tools` |
| `name` | 1–64 字符，小写字母/数字/连字符，**必须与目录同名** |
| `description` | 1–1024 字符，第三人称，说清"做什么"和"什么时候用" |
| 正文 | 建议少于约 500 行；细节放 `references/`（一层深，按需读） |
| 正文语言 | 中文；工具 id、参数名、JSON 一律原文照抄 |

**平台数据只能进 `metadata.`**：曾经往 front matter 塞过自造的 `covers:`，结果那份技能不能被别的工具读——
那是把平台内部的账写进了通用格式。

## 2. 命名空间、提供方与共享

一个技能目录注册出来就是一行能力，id 是 `命名空间:目录名`，而**命名空间就是提供方**：

| 来源 | id | provider |
|---|---|---|
| 基座自带（classpath） | `tianshu:player-tools` | `tianshu` |
| 玩家自己的技能目录 | `user:my-skill` | `user` |
| 第三方模组注册的目录 | `changsui:fight-tools` | `changsui` |

命名空间的作用是**防撞**，所以它必须是所有者，不是内容题材：`player-tools` 里的工具 id 是 `minecraft:*`，
但说明书是基座写的，它就住在 `tianshu:` 下。否则两个模组都想给原版工具补说明书时会撞在同一个 id 上。

**共享三选一**，写在 `metadata.share`：

```
metadata:
  share: all              # 全局公开
metadata:
  share: none             # 私人
metadata:
  share: changsui, dubhe  # 只对这些模组开放
```

共享是**声明，不是常量**：没有任何代码把 `share` 写死。不写就跟随提供方——基座与玩家自己的目录开放
（助手就是为这个人干活的），第三方模组私有（没声明就开放等于装两个模组就互相开门）。

共享只决定"谁能看见这一行"，**不决定谁能读某份工具说明**：那是工具行自己的事，见 §3。

## 3. 两本内建技能按执行者组织

| 技能 | 装什么 |
|---|---|
| `player-tools` | 以**玩家本人**身份行动的工具：约定（信封、档位、失败怎么读）+ `references/` 下每个工具一份 |
| `entity-tools` | 通过**身体**（实体化身）行动的工具：同上 |

按执行对象决定工具说明的位置。实体工具也可查询身体清单，清单查询无需 body 参数。订阅仍由消费方按能力 ID 声明。
两侧的 id 不同（`block.interact` 与 `entity.interact` 是两个工具，不是一个工具的两个入口），
完整清单见 [玩家辅助](玩家辅助.md) §2 与 [实体操作](实体操作.md) §2，不要在文档里把两侧并列成对照表。

配套的严格程度：一边的说明书只讲这一边——不写"如果传了 body 就……"，也不写"另一边有个等效的谁谁"。

玩家和实体工具的说明按工具 ID 放入 reference。平台阅读器 `minecraft:capability.read` 的用法写在两本技能的 `SKILL.md`，无需独立附件。

```
minecraft:container.transfer  →  skills/<技能>/references/container.transfer.md
```

专门发布工具说明的技能在 front matter 声明 `metadata.references: tools`。订阅技能即可读入口正文，读取任一工具说明还须能访问对应工具。普通技能可保留自己的补充阅读材料。

- 文件名 = 工具名，**不带命名空间**；需要显式时可写 `<命名空间>.<名字>.md`，查找两种都认；
- 查找先匹配工具命名空间，再在对应的技能目录中找文件。第三方目录默认对应模组自己的命名空间；基座随包技能对应 `minecraft`。技能卸载时说明书一起下线；
- `capability.read` 带工具 id 就读它；门禁 `verifyEveryToolHasADocument` 要求缺一即失败。

## 4. 每份工具说明写什么

每份工具说明写清何时调用，给出一份合法的 JSON 调用和一份成功结果，并说明哪些返回值决定下一步。字段从实际工具的 schema、结果类型和执行代码核对。说明失败时优先写能改变下一步的错误码、原因和已经产生的效果。命令审批这类分阶段流程可追加第二次调用。

以 [容器搬运说明](../tianshu-client/src/main/resources/tianshu/skills/player-tools/references/container.transfer.md) 为例，`count` 是请求上限，`result.moved` 是实际移动量。其他技能可以直接引用这一份示例。

`verifyEveryToolHasADocument` 根据实际内建工具声明检查对应附件，并解析其中标记为 JSON 的调用和结果。协议保留请求记录在开发者文档中。

## 5. 写 SKILL.md 的硬规矩

1. **不写具体模组名**。"天枢没有实体所以不要传 body" 换个模组就错；写"没有身体的调用方不要传 `body`"。
2. **不重复别处的约定**。信封、档位写在各自 `SKILL.md` 里一次，工具说明里不再复述。
3. **不列全参考清单**。五十多份逐个列会让它变成目录；写清"`references/` 下按 id 命名，用 `capability.read` 带 id 读"，全表在 [玩家辅助](玩家辅助.md) §2 与 [实体操作](实体操作.md) §2。
4. **档位不是技能属性**，是工具属性：不要写"本技能属于保守档"，要写"这件事需要哪一档，去对应参考看"。
5. **例子必须能照抄**：真实 id、真实参数名、真实信封；不要 `{...}` 一带而过。
6. **平台字段一律进 `metadata.`**，包括 `metadata.share`。

## 6. 提交前自查

- [ ] `name` 与目录同名、全小写连字符；`description` 说清"做什么 + 什么时候用"，≤1024 字符
- [ ] front matter 没有自造字段（平台信息只能进 `metadata`）
- [ ] 共享范围想过一遍：不写就跟随提供方
- [ ] 正文 < 500 行；细节在 `references/`，一层深
- [ ] 新增或改动了工具？`references/<name>.md` 存在且字段核对过
- [ ] 文档里的每个参数名、返回字段名，都能在代码里指出来
- [ ] [验收](验收.md) §1 的门禁通过，其中含 `verifyEveryToolHasADocument`
- [ ] 没有把别的技能的约定抄一遍

## 7. 删掉过的东西

| 曾经做过 | 为什么删 |
|---|---|
| front matter 里的 `covers:` | 自造字段，技能不再可移植 |
| `coverage.txt` 索引（技能 → 能力 id 列表） | 索引会和实际发货漂移；id 推导就够了 |
| 读技能时按可见性拼装参考段落 + 末尾"你能用其中哪几个" | 一个能力一份文档之后没有"半适用"这回事 |
| `docs/tools/` 独立目录、`tool-docs` 再分一层 | 文档应住在技能自己的 `references/` 里 |
| `ToolDocs` 直接扫 classpath | 只能扫到基座自己的文件，第三方与玩家目录永远查不到；改成由技能自己提供 |
| provider 叫 `tianshu-skills` / `tianshu-text` | 与命名空间重合的第二个名字，玩家目录的技能也被算成基座发布的 |
| `share: all` 硬编码在提供方里 | 三个选项一个都用不上；声明权应属于该技能自己 |

判据一句话：**如果一个机制是为了弥补另一个机制造成的麻烦，先问那个机制该不该存在。**
