1.  【枢机】协议中心（已完成）
{
    定位：枢机是天枢系统的底层基础设施，不是业务模块。它不理解雷达、换装、翻译等具体业务，不产生业务数据，不消费业务数据，也不直接执行任何 Minecraft 动作；它只理解协议层语义，并负责统一信封的路由、能力仲裁、生命周期托管、取消传播、超时清理与死信观测。
    核心原则：枢机不理解业务，但理解协议；不执行动作，但托管动作请求的生命周期；不拆载荷，但校验载荷类型；不关心模块内部，但强制模块注册能力；不编排业务流程，但保证信封链路可追踪、可取消、可过期、可降级。
    功能描述：所有跨模块交互必须封装为 TianshuEnvelope。信封由枢机可读的 Header 与类型化黑盒 Payload 组成。Header 记录 envelopeId、traceId、parentId、sourceId、TargetMode、Capability/Topic、PacketType、PayloadType、Priority、ThreadPolicy、Deadline、ExpireAt、CancellationScope 与 FailurePolicy；Payload 必须是不可变快照对象，禁止携带 Entity、ItemStack、Level 等 MC 活对象。
    调度与安全：模块启动时必须向枢机注册 ModuleDescriptor 与 CapabilityDescriptor。枢机只向已注册且 PayloadType 匹配的 Handler 投递信封；不同 Capability 通过不同 Broker 仲裁，如 TTS 使用可打断独占 Broker，LLM 使用限流并发 Broker，IR 使用无状态快速 Broker，高频 Tick/准星事件使用 LatestOnly Broker。涉及真实服务端状态变更的能力必须进入 ServerPacketBroker，不能仅凭 MUST_MAIN 直接修改背包或世界。
    生命周期：信封从 CREATED、QUEUED、DISPATCHED、RUNNING 流转到 COMPLETED、CANCELLED、EXPIRED 或 FAILED。失败与取消不再“一挂全杀”，而由 CancellationScope 与 FailurePolicy 决定只清理自身、取消子链、终止整条 Trace、降级 fallback、重试或仅上报。枢机维护 Trace 与 Parent 子任务索引，模块只负责响应针对自身 envelopeId 的 CANCEL。
    边界红线：业务模块禁止 import 其他业务模块实现类；跨模块通信只能通过枢机信封、Capability 或 Topic 完成。模块禁止绕过枢机直连 TTS 引擎、LLM SDK 或服务端动作接口。耗时任务必须设置合理 deadline/expireAt，或发送 HEARTBEAT/PROGRESS，否则会被标记为 EXPIRED/FAILED 并进入死信记录。
    详细设计：见同目录《TianshuProtocolCenter.md》。
}

2. 🎙️ 【听澜】ASR 语音识别模块（待完善）
{
    定位：天枢的语音输入入口，负责捕捉玩家语音并输出稳定的文本事件。
    特征：通过网络下载的ASR模型。
    功能描述：只负责听取与转写，不直接执行游戏动作，也不向业务模块广播原始识别文本。
    输出边界：听澜产出的 RawAsrText / AsrFinalText 属于内部受保护输入，只能投递给【识意】或受信任核心诊断链路。ASR 原文不作为公开 Topic，不允许外部模组、普通业务模块或对话参与者直接订阅。
    语音类型：
    - 普通语音：玩家闲聊的语音，负责提供给识意进行后续自然交互判定。
    - 指令语音：玩家通过语音指令触发的事件，如“打开雷达”、“打开MR”等等各种指令，仍须先进入识意进行本地解析。
}

3. 🧭 【识意】IR 意图识别模块（待完善）
{
    定位：天枢的本地确定性意图解析层，负责在不依赖 LLM 的情况下，对玩家文本进行快速指令识别、目标解析、MC 命名实体修复与外部模块指令词匹配。
    功能描述：识意优先处理高确定性的本地命令，例如内容讲解、实体查询、面板开关、确认/取消等。ASR 文本进入系统后应先走识意解析；若命中明确指令，则通过内部路由交由枢机投递到对应模块；若未命中明确指令但属于自然交互、闲聊、开放询问或模糊请求，则生成 OpenInteractionRequest 并通过内部链路交由【思衡】进行会话归属仲裁。
    输出边界：当前阶段识意默认不广播 IR 结果，不开放公共 IR Topic。识意输出只允许进入枢机能力路由、思衡仲裁链路或受信任核心诊断链路。未来若开放 IR 事件，也必须是经过权限控制、载荷裁剪和用途声明的受控事件，而不是向所有模块广播完整 ASR 原文或完整解析上下文。
    设计原则：识意只输出结构化意图或开放交互请求，不直接执行游戏动作；所有动作必须经由枢机路由与模块权限校验后执行。识意不决定自然对话最终由谁处理，该职责属于思衡。
}

4. ⚖️ 【思衡】IA 仲裁机构（规划中）
{
    定位：思衡是连接【识意】IR 与各业务对话参与者之间的开放交互仲裁层，不是 LLM 模块，也不是协议中心。它只处理“未被识意确定性消费的开放输入”，负责判断这次自然语言交互应由谁接管。
    核心职责：接收识意通过内部链路提交的开放交互请求；向辅星、外部模组适配器、NPC 模组、物品/方块/实体交互模块等 DialogueParticipant 收集 ClaimResult；根据 claim 强度、上下文置信度、当前会话焦点、权限、安全策略与默认兜底规则裁决本次输入归属。
    会话管理：思衡维护玩家当前正在与哪个参与者/目标对话，支持多轮对话续接、超时释放、显式切换、取消与默认助手兜底。当没有外部参与者认领，或外部认领被权限拒绝时，开放输入交由默认辅星处理。
    外部接入：其他模组若希望接入天枢语音/对话系统，应通过稳定 API 注册 DialogueParticipant。参与者只需要实现 claim 与 handle：claim 用于判断当前输入是否应由自己处理并返回认领强度、目标、理由与所需权限；handle 仅在胜出后处理 DialogueSession，可选择调用天枢能力、自行处理或交还默认助手。
    输入边界：思衡不接收 ASR 广播，也不监听公共 IR 广播；它只接收识意在内部链路上提交的 OpenInteractionRequest。Claim 阶段默认只向参与者提供受限上下文，不把完整 ASR 原文作为公共上下文分发；胜出参与者只能在 DialogueSession 内读取本次会话被授权的输入文本。
    边界红线：思衡不直接调用 LLM，不构造业务 prompt，不生成回复文本，不播放 TTS，不执行 Minecraft 动作，也不规定外部模组必须用何种方式声明交互。所有 LLM、TTS、IR、UI、ServerAction 等能力调用仍必须通过枢机信封与能力路由完成。
    主链路：听澜 ASR 产出文本后以受保护内部输入进入识意。识意命中明确指令时通过枢机路由到对应模块，不进入思衡；识意未命中明确指令或判断为自然交互输入时，将结构化后的 OpenInteractionRequest 交给思衡。思衡选出 winner 并创建或续接 DialogueSession，胜出参与者再通过枢机调用织言、回响或其他能力。
}

5. 🧬 【织言】LLM 语言生成模块（待完善）
{
    定位：织言是天枢的底层 LLM 能力模块，负责模型服务管理、推理请求接收、task 调度、流式文本生成与结果回传。它是语言生成与推理能力提供者，不负责 agent 人格、记忆生命周期、上下文编排、对话所有权或玩家可见输出授权。
    特征：通过网络下载不同参数的模型，最小为2B。
    功能描述：
     - 推理执行：接收辅星、外部 DialogueParticipant 或其他业务模块提交的 LLM task 请求，并按优先级、超时、取消与并发策略调度执行。
     - 对话生成：根据调用方已经组装好的 messages、dynamic facts、RAG 参数与 generation options 生成自然语言结果。
     - 意图辅助修复：对于识意未能确定解析但仍疑似指令的文本，可由相关模块向织言申请语义修复，修复结果可再次交回识意进行二次解析。
     - 模块分析辅助：为双鉴、天镜、行策、玄哨、余烬等模块提供解释、总结、提示词生成、状态分析等能力。
     - 流式输出：支持流式文本生成，但底层流不天然代表玩家可见输出；调用方必须结合自身会话、权限和归属语义再转发给 UI、TTS 或其他展示模块。
    边界红线：织言不主动接收 ASR 文本，也不订阅公共 IR 广播；开放输入必须先经过识意与思衡。织言不决定某句话归谁处理，不维护辅星或其他 agent 的长期记忆，不构造具体业务 prompt，不直接播放 TTS，不直接执行游戏动作。所有对织言的调用必须通过枢机能力路由，受优先级、并发、超时、取消与权限策略约束。
}

8. 🌐 【天镜】全息 MR 系统（验收中）
{
    当前定位：天镜是一个纯客户端的 2D GUI 层 MR 战术信息系统，目标是在不打断玩家操作、不污染世界渲染、不主动联网的前提下，把附近实体的关键战术信息投影成轻量牵引卡片。当前工程已经进入验收精修阶段，设计优先级以现有代码行为为准，旧版 MR Sysfem、MR Issues、MR System Plan 仅作为历史参考。

    一、交互分层与状态机
    默认处于 SILENT，不显示任何 MR UI。
    玩家通过功能开关或 MR 按键启用后进入 SCANNING；关闭时不硬切消失，而是让已有卡片播放关闭动画。
    SCANNING 状态下扫描玩家 32 格内实体，并在屏幕 GUI 层显示最多 6 张卡片。显示选择遵循“敌对优先、距离优先、数量上限硬约束”的原则，避免旧卡片和新目标叠加后突破上限。
    FOCUSING 状态由准星悬停触发：系统启动扫描后不再保留额外的 2 秒扫描预热；准星对准实体先经过 1 秒 aim warmup，再经过 2 秒 gaze focus 后进入聚焦。聚焦内容逐字输出，内容显示完成后等待 2 秒自动退出并回到 SCANNING。
    目标切换时聚焦计时跟随当前准星目标重置或切换；聚焦退出不关闭 MR 系统，只恢复普通扫描布局。

    二、数据边界与线程模型
    common 层负责状态、投影、布局、动画、卡片筛选、颜色文本预计算与快照产出；neoforge 层负责主线程 GUI 绘制和少量 Minecraft 对象解析。
    MrCardSnapshot 是 MR 渲染唯一跨层数据载体，只保存 float、int、boolean、String 等快照字段，不持有 Entity、ItemStack、Vec3 等 Minecraft 活对象。
    MrEngine 通过 IEnvironmentAwarenessProvider、IRenderContextProvider、IPlayerStateProvider 读取环境、投影、准星与玩家状态，按固定 tick 间隔产出快照队列。
    MrRenderer 从输出队列 poll 快照，保留 lastFrameSnapshots 防止 MR tick 间隙闪烁，并维护 displaySnapshots 做主线程显示平滑。
    物品图标解析只在 neoforge 渲染侧进行，使用 item id 到 ItemStack 的缓存映射；common 层只输出图标 id。

    三、渲染管线与当前视觉方向
    当前方向不再追求独立科技风贴图，而是优先使用 Minecraft 原版 GUI 绘制能力，后续再考虑 mixin 接入，让原版 UI 与资源包、GUI 修改类 Mod 能尽量参与显示效果。
    MR 不进入 3D 世界渲染，不使用世界内 OpenGL 特效；实体头顶 A 点通过相机朝向和 FOV 投影到 GUI 坐标，再在 GUI 层绘制。
    几何绘制统一走 GuiGeometryBatch，卡片背景、边框、血条、A 点标记、A-B-C 连接线、聚焦进度外框都进入同一个几何批次，最后统一 flush；图标和文字在几何批次之后绘制，保持层级稳定。
    A 点实体头标记和卡片一样受 scale 影响，近处更大、远处更小。
    出现和关闭动画中的线条透明度与卡片内容透明度解耦，连接线不会在动画中途因卡片 alpha 降低而提前消失。

    四、A-B-C 牵引几何与卡片稳定性
    A 点表示实体头顶投影点，实时跟随实体当前屏幕位置。
    B 点是 A-B 刚性段末端，用于把实体锚点和卡片主体分离；A-B 段长度受配置和 scale 影响，保持近大远小。
    C 点是连接线与卡片边框的连接点，不再等同于卡片左上角；卡片根据 connectorEdge、connectorEdgeRatio、connectorOnTopEdge 等快照字段确定连接边与展开方向。
    初始卡片方向按候选象限评估，不只看单一默认方向。候选会综合已有卡片遮挡、潜在实体遮挡和屏幕边界，优先选择遮挡最少的象限；实在无法完全避让时选择损失最小方案。
    C 点不强制长期锁死，当前验收重点是卡片本体稳定、初始方向合理、阻尼跟随自然。
    MrWhipLayout 负责卡片从当前显示位置追向目标卡片矩形。当前阻尼语义是“跟随系数”而非传统物理阻尼：近距离采用较低跟随系数保证稳定，拉开距离后动态提高跟随系数帮助快速追赶，避免快速转头时卡片过度晃动或断裂。
    tacticalMrCardDamping、tacticalMrCardMinDamping、tacticalMrCardMaxDamping 等配置已经通过 MrTuningProvider 传入 common 布局层，不只影响渲染侧平滑。

    五、卡片内容与实体优先级
    卡片显示实体名称、血条、距离、攻击力、护甲等极简战术数据。
    距离、攻击、护甲图标使用原版物品图标思路：指南针、铁剑、铁胸甲等 item id 由 common 侧写入快照，neoforge 侧解析后 renderItem。
    颜色系统当前保留敌对与非敌对二分：敌对偏橙红，非敌对偏亮蓝；透明度会叠加距离衰减和昼夜环境系数。
    卡片显示数量上限当前为 6，不再沿用旧文档中的 10。超过上限时由引擎在生成快照前统一筛选，避免“已有低风险卡片未退场，新敌对卡片继续生成”导致总数失控。

    六、聚焦模式当前实现
    聚焦触发只针对当前准星对准的实体。聚焦前反馈由 focusProgress 驱动，进度覆盖 1 秒 aim warmup + 2 秒 gaze focus。
    聚焦过程中，A-B-C 原始连接线外侧会绘制一层包裹式进度反馈：先画淡外框轨道，再按进度从 A 到 B、从 B 到 C 推进亮外框，最后把原始连接线画回中心。该反馈和原连接线同属同一个 GuiGeometryBatch，不新增独立渲染 pass。
    进入 FOCUSING 后，目标卡片放大并显示 focusedDetailText，文本逐字输出；输出完成后进入 2 秒自动退出倒计时。
    背景卡片不应被硬杀，当前工程倾向于降低透明度和缩放处理，使聚焦态仍保留空间上下文。

    七、集成与配置
    MR 与声学雷达共享环境感知 Provider，但扫描半径统筹取两者需求的最大值：雷达需要的半径与 MR 运行时的 32 格需求合并后下发。
    现行宿主入口由 TianshuNeoForge、NeoForgeClientBootstrap 与 NeoForgeClientEvents 分工：bootstrap 负责客户端运行时和功能装配，events 只转发 tick/渲染/输入等 Minecraft 事件；MR 自身的状态与布局逻辑不得重新堆回宿主总控类。
    FeatureManager 和用户开关共同决定 MR 是否运行；功能关闭时引擎进入 closing 流程，允许动画完成后再释放。
    ClientConfig 暴露卡片 scale、线段长度、卡片跟随系数、昼夜透明度等调试参数，用于验收阶段快速调校视觉手感。

    八、安全与未来边界
    当前 MR 是纯客户端显示功能，不主动向服务端发送自定义网络包。
    MR 只读取本地 Provider 提供的轻量实体快照，不把实体 NBT 或大体积模组数据直接发送给 LLM。
    后续若接入 LLM 深度解析，只允许在进入 FOCUSING 后发送经过清洗的极轻量文本摘要，并且应走统一协议/权限体系。
    后续若接入 mixin 或更多原版 UI 绘制能力，应保持当前原则：common 层不依赖 Minecraft 渲染对象，neoforge 层只做主线程适配，MR 几何绘制尽量复用原版 GUI 能力。
}

{
    痛点：战斗或跑酷中切换装备手忙脚乱；整合包物品繁多，理想套装部件缺失时无法灵活应对；背包满时换装卡死。
    功能描述：实现“宏观套装一键切换”与“微观快捷栏调度”，引入独特的智能降级机制与垃圾回收机制，确保玩家在任何极端状态下都能瞬间完成换装。
    宏观切换（套装模式）：语音输入“切换战斗套”，系统根据预设瞬间完成替换。
    微观调度（单槽模式）：语音输入“拿盾牌”，系统仅在快捷栏 1-9 寻找匹配物品并与手持物交换。
    极简预设录入：穿戴好目标配置后，语音“保存当前为战斗套”或其他类似保存的指令，直接将当前状态拍快照。
    技术实现：

    预设存储（期望结构体）：预设不存死板的 NBT，而是存“期望标准”。例如：{slot: chest, baseId: "diamond_chestplate", expectedEnchants: ["Protection IV"]}。保存的是“理想”，穿戴时做“妥协”。
    智能降级匹配算法：
    当触发套装切换时，遍历背包寻找满足该槽位的物品，按优先级排序：1. 完全匹配（ID 与附魔一致） -> 2. 同 ID 降级（附魔缺失） -> 3. 材质降级（如钻石退化为铁）。
    空间回退算法（垃圾回收）：
    针对背包已满的情况：1. 优先寻找背包内同类装备进行跨槽位 Swap。2. 若无同类装备，直接调用【功能 14】的“垃圾物品表”，丢弃第一件垃圾腾出空间，完成换装。
    严谨的 C/S 申请机制（核心突破）：
    彻底抛弃任何“模拟原版点击/模拟按Q”的降级妥协方案。坚决不绕过服务端，不伪装发包。
    客户端仅作为“纯意图收集器”，无论宏观套装切换还是微观单槽交换，一律发送自定义的 C2SRequestSwapPreset 包（内含预设 ID 或目标物品槽位映射表）：

    若服务端安装本 Mod 且开启功能： 服务端接管，在服务端执行上述的【降级匹配】与【垃圾回收】逻辑，直接调用 player.getInventory() API 修改服务端真实背包，再同步给客户端。(服主可通过配置彻底关闭此功能防作弊)。
    若服务端未安装本 Mod（或关闭功能）： 服务端丢弃该包。客户端检测到无 S2C 授权，在本地直接拦截语音指令，自动降级提示玩家“当前服务器不支持换装操作”。
    单人档/局域网： 等同于“服务端安装了 Mod”，直接走内部高速通道执行。
    指令路由：100% 本地 Ngram 拦截执行，严禁发送大模型，确保毫秒级响应。
    AI 反馈示例：

    *(单人/模组服完美切换)*：“战斗套已就绪。”
    *(单人/模组服触发降级)*：“战斗套已切换，未找到附魔钻甲，已临时装备铁甲。”
    *(单人/模组服触发垃圾回收)*：“背包已满，已为你丢弃泥土腾出空间，战斗套切换完成。”
    *(原版服务器)*：“当前服务器不支持套装切换。”
    设计亮点解读：

    真正的白名单逻辑：把“防作弊”变成了“权限管理”。服主拥有绝对控制权（配置文件开关），玩家在原版服务器不会因为乱发包被踢，而是会被模组温柔地告知“不支持”，体验极度平滑。
    算力下沉：把最核心、最容易出 Bug 的“降级匹配”和“丢垃圾”逻辑放在了服务端执行，这意味着就算玩家本地开修改器乱发请求包，服务端也会按照正常逻辑校验，杜绝了任何刷物品的可能。
}

11. 🧪 【星图】合成图谱（制作中）
{
    文档版本：V13.0 绝对终态 (彻底独立版)
    功能定位：取代传统的悬浮合成表，提供一个基于 2D 虚拟画布的、可无限推演的、防内存爆炸的“合成图谱编辑器”。这是一个完全独立的 Mod，绝非 JEI 的附属插件。

    一、 核心痛点与设计哲学
    传统合成表的局限：只能看单层配方，遇到复杂整合包（如工业模组的多步处理）需要不断点开点出，丧失全局规划能力。
    传统树形面板的灾难：如果允许无脑递归展开，整合包里的物品（如铁锭变铁粒，铁粒又变铁锭）会形成死循环；且多个面板互相嵌套，极其容易遮挡屏幕。
    本系统的解法：将背包/容器界面左侧剩余区域变成一张可滑出的“局部草稿纸”（左侧半侧 2D 画布）。玩家可以把各种合成表像贴卡片一样铺在这块半透明画布上，用发光连线标明逻辑关系。不替玩家做复杂判断，只提供最客观的图谱展示与极致流畅的交互，同时不遮挡背包主体区域。
    对 JEI 的态度 (生死红线)：JEI 只是可选的外挂数据源，绝非核心依赖！ 本系统 100% 基于 Minecraft 原生 RecipeManager 驱动。没装 JEI，本系统必须完美运行；装了 JEI，本系统通过兼容层获取更广泛的数据。
    二、 核心数据与逻辑架构 (防崩溃基石)
    2.1 数据源分层架构 (彻底解耦)
    第一梯队 (绝对核心)：直接读取 Minecraft.getInstance().level.getRecipeManager()。覆盖原版工作台、熔炉、高炉、烟熏炉、切石机、锻造台等所有标准 RecipeType。这已经解决了 80% 的需求，且开发效率极高。
    第二梯队 (可选增强)：仅当运行环境检测到安装了 JEI/REI 时，才实例化 JEICompatibilityLayer。专门用于抓取那些不按原版规则来的异构模组（如 Create 的顺序装配、部分神秘仪式等非标准配方）。
    分发逻辑：查询配方时，先查原生 RecipeManager，查不到且 JEI 存在时，再降级询问 JEI 插件。
    2.2 数据与视图的绝对隔离
    铁律：画布上有 5 个展示“铁锭”的面板，必须创建 5 个绝对独立的 UI 实例 (RecipePanelNode)。防止翻页状态互相覆盖导致闪烁。
    实现：底层维护全局唯一的 DAG (有向无环图) 缓存，只存配方数据。UI 面板仅读取 DAG 数据，各自维护坐标和翻页索引。
    2.3 祖先检测拦截器 (防死循环红线)
    铁律：每次准备生成新节点前，必须向上递归遍历当前节点的祖先链。
    命中处理：如果发现目标物品（如铁锭）已经是当前节点的祖先，直接阻断新节点的创建。镜头自动平滑飞到祖先面板并闪烁高亮 1 秒。
    2.4 适配器层架构 (Adapter Layer - 彻底消灭屎山代码)
    铁律：引入 UniversalRecipeViewModel (统一视图模型) 和 RecipeAdapter 接口。渲染引擎只认 ViewModel，绝不碰具体模组逻辑。
    ViewModel 结构：只包含 List<SlotViewData> (相对坐标、物品、类型枚举 INPUT/OUTPUT/CATALYST)。
    适配器实现：
    VanillaCraftingAdapter -> 吐出 3x3 坐标。
    VanillaFurnaceAdapter -> 吐出线性坐标。
    FallbackLinearAdapter -> 遇到任何异构但能拿到输入输出列表的配方，直接吐出“降维抽象线性流”坐标。
    JEICompatAdapter (可选) -> 从 JEI 偷取插槽相对坐标，吐出 ViewModel。
    三、 渲染与 2D 虚拟相机引擎
    3.1 渲染管线隔离
    绝对禁止：严禁使用 OpenGL 3D 世界坐标渲染。所有节点的绘制必须在 GUI 层的左侧图谱抽屉区域内完成，并通过裁剪区域限制到背包/容器左侧剩余空间。
    路线 B 基线：渲染风格采用原版 AdvancementScreen / 进度面板式视觉语言。common 层只提供图谱语义、节点、边、相机与 ViewModel；NeoForge 层负责把这些语义映射到原版风格 GUI。允许在 tianshu-neoforge 中使用 Mixin / Accessor / Invoker 作为平台桥接，但 Mixin 只能用于复用或暴露原版渲染资源、方法与生命周期钩子，禁止承载 CraftingGraph 的业务状态、配方语义、持久化或 Undo 逻辑。
    3.2 原版风格渲染基线
    铁律：不再坚持科技风和纯程序化外观。背景、按钮、节点边框、槽位底板、滚动条与弹窗统一向原版进度面板/容器 GUI 的灰黑、浅高光、深阴影风格靠拢；可优先复用 Minecraft 自带贴图、Sprite、九宫格或原版绘制方法。若直接复用贴图会造成缩放模糊，则节点内容区、连线和高频缩放元素仍可用代码绘制原版风格矩形/边框。
    性能原则：Mixin 不是为了把业务塞进原版类，而是为了让平台层尽可能吃到原版渲染路径和 ModernFix 等优化收益。Phase 0/1 先建立 AdvancementStyle 渲染适配基线；后续如发现某些原版私有绘制能力值得复用，再在 NeoForge 层补充最小 Mixin 桥。Fabric 或其他加载器只需要替换平台桥，不得要求 common 层修改。
    3.3 2D 虚拟相机系统
    维护 offsetX, offsetY, zoom, targetZoom。缩放锚点必须永远锁定在当前鼠标的屏幕坐标上。每 Tick 执行平滑插值。
    四、 交互状态机 (UX 核心，极易踩坑)
    4.1 Tab 按键：全权限通道
    外层 (主界面)：短按 Tab 可以滑入/滑出合成图谱面板的观察模式；长按 Tab 进入临时编辑态，松开 Tab 后若未锁定则退出临时编辑态但不强制收回观察面板；按住 Tab 的同时按下鼠标中键可以直接切换到完全编辑模式，不需要等待长按阈值。完全编辑模式可通过短按 Tab 退出，或者在通过 Esc 打开暂停页面时自动退出，也可以通过按 E 进入背包等操作退出。观察模式透明度 40%，编辑模式透明度 70%。
    内层 (背包/合成台/机器操作界面等)：默认 70% 透明度常驻。短按 Tab 可以滑入/滑出合成图谱面板，图谱抽屉仅占用背包/容器左侧剩余区域并接管该区域输入（仅当聚焦于这个面板时），按 E 随着背包等面板的关闭而退出编辑态。
    空态生根：图谱为空时，按住 Tab + 左键点击物品创建 SOURCE 根节点，按住 Tab + 右键点击物品创建 USAGE 根节点；这只是空图的入口交互，不允许在数据结构上把根节点特殊化。
    4.2 Shift 全局破坏性范式
    按下 Shift 进入 DestructiveMode。连线中点出现红叉，收藏栏项目上出现红 X，右键直接秒删，无二次弹框。释放 Shift 红叉消失并退出破坏模式。
    五、 节点内部 UI 与连线规范
    5.1 节点内部同构规范
    节点内部不含全局操作文本和收藏按钮。
    节点二分类是图谱基础结构，不是渲染标签：RecipePanelNode 必须携带 nodeType。SOURCE 表示“这个 item 如何合成出来”，USAGE 表示“这个 item 可以参与合成什么”。节点绑定主语必须是 itemId，而不是槽位实例；例如工作台配方里的四个木板作为“木板”主语时地位相同，不能因为点击的是第几个木板槽而产生不同主语语义。
    节点类型与边方向是两个维度：GraphExpansionDirection 只描述新节点相对父节点向上/向下布局和 PCB 走线方向；RecipePanelNodeType 描述节点自身查询语义、智能定锚、持久化与 Undo 恢复语义。Tab 交互下左键创建 SOURCE 节点，右键创建 USAGE 节点；根节点与子节点都遵循同一规则，不再存在“根节点默认只能是来源节点”的特例。
    节点外观不通过不同颜色区分 SOURCE/USAGE，统一使用同一套卡片色彩，只在标题区绘制小图标：SOURCE 使用三股箭头汇聚图标，USAGE 使用三分叉箭头图标。
    主语物品角标：节点内部所有代表绑定主语 itemId 的槽位都要绘制右下角小角标。SOURCE 节点只在匹配主语的 OUTPUT 槽绘制；USAGE 节点在匹配主语的 INPUT/CATALYST 槽绘制，且主语匹配按 itemId/tag 候选判断，不绑定某个具体槽位实例。角标使用同一青蓝色小三角/芯片点，不改变节点主色。

    左侧滚动分类器：纵向列表组（类似 JEI 分类栏），上下端有箭头用于组内翻页。
    配方快速选择按钮：在节点左上角、左侧垂直合成类型栏右侧放置一个小型可点击按钮，用于打开当前节点的“主语配方索引窗口”。该按钮不是全局搜索，也不创建新节点，只服务于当前 RecipePanelNode 内的快速跳页。
    主语配方索引窗口：点击按钮后，在当前节点附近弹出一个小窗口，窗口拥有最大宽度/高度限制，超出内容时使用平滑纵向滚动；窗口内部以类似 JEI 的网格排列一排排物品图标，每个格子代表当前节点绑定主语 itemId 下的一条可选配方，点击格子后将当前节点 selectedRecipeIndex 切到对应配方并关闭或保持窗口高亮当前项。窗口必须裁剪在左侧图谱抽屉内，不得溢出遮挡背包主体区域。
    索引图标语义：USAGE 节点的每条配方通常对应不同输出物，因此格子优先显示该配方的输出物图标；SOURCE 节点的多条配方输出都等于主语，不能重复显示同一个输出图标，格子应使用该配方输入材料的动态轮播图标来表达“这是一种合成方式”，例如每隔固定 tick 在主要输入材料之间切换显示，必要时叠加小型序号/配方类型角标辅助区分。
    索引窗口锁定规则：如果当前节点的整页配方翻页因 inputAnchorsLocked 或 outputAnchorsLocked 被置灰，那么索引窗口中会改变当前 ViewModel 输入/输出布局的点击也必须置灰并拦截；允许打开窗口浏览，但不允许切到会破坏已有支路语义的配方。后续如果实现输入侧/输出侧局部切换，则索引项也按相同侧锁规则判断。
    右侧焦点展示区：读取 UniversalRecipeViewModel 渲染物品。
    同配方翻页：合成表下方左右两侧的极简箭头，切换同分类下的不同排列；当同一节点配方数量很多时，优先使用主语配方索引窗口进行跳转，左右箭头只作为临近配方的轻量切换。
    底色状态法：根据 SlotType，已有材料“暗绿切角”，缺失“暗橙切角”。
    智能定锚：打开/切换分类时，自动将材料满足率最高的那一页置顶。
    5.2 连线锁定与翻页置灰机制
    连线锁定只看“是否引用了当前配方页里的具体槽位”。GraphAnchorKind.NODE_CENTER 表示引用的是节点绑定主语 itemId，这个主语不会因为切换当前节点配方而变化，因此不锁定配方切换；GraphAnchorKind.SLOT_CENTER 表示引用的是当前 ViewModel 中的具体 INPUT、OUTPUT 或 CATALYST 槽位，这类引用会随配方切换失效，必须锁定对应侧。
    确认规则表：
    | 当前节点 | 被引用对象 | 典型连线 | 是否允许切换当前节点配方 |
    |---|---|---|---|
    | SOURCE(X) | 输入槽 Y | SOURCE(Y) 中点 -> SOURCE(X) 的 Y 槽 | 不允许 |
    | SOURCE(X) | 输入槽 Y | SOURCE(X) 的 Y 槽 -> USAGE(Y) 中点 | 不允许 |
    | SOURCE(X) | 主语/输出 X | SOURCE(X) 中点 -> USAGE(X) 中点 | 允许 |
    | SOURCE(X) | 主语/输出 X 查来源 | 高亮 SOURCE(X) | 允许 |
    | USAGE(K) | 主语 K | SOURCE(K) 中点 -> USAGE(K) 中点 | 允许 |
    | USAGE(K) | 主语 K 查用途 | 高亮 USAGE(K) | 允许 |
    | USAGE(K) | 非主语输入 Y | SOURCE(Y) 中点 -> USAGE(K) 的 Y 槽 | 不允许 |
    | USAGE(K) | 非主语输入 Y | USAGE(K) 的 Y 槽 -> USAGE(Y) 中点 | 不允许 |
    | USAGE(K) | 输出 Z | SOURCE(Z) 中点 -> USAGE(K) 的 Z 输出槽 | 不允许 |
    | USAGE(K) | 输出 Z | USAGE(K) 的 Z 输出槽 -> USAGE(Z) 中点 | 不允许 |
    实现规则：节点内仍维护 inputAnchorsLocked 与 outputAnchorsLocked，但只有 SLOT_CENTER 才能写入这两个锁。INPUT/CATALYST 槽位引用写入 inputAnchorsLocked，OUTPUT 槽位引用写入 outputAnchorsLocked；NODE_CENTER 引用不写入任何锁。
    整页配方翻页：当前阶段的左右箭头和主语配方索引窗口点击都属于整页配方切换，会同时改变输入和输出 ViewModel，因此只要 inputAnchorsLocked 或 outputAnchorsLocked 任意一侧为 true 就置灰并拦截。只有节点中点引用时，两侧锁都保持 false，允许切换。
    删除解锁：删除某条支路或删除子节点后，必须重新扫描该父节点剩余连线，只按剩余 SLOT_CENTER 锚点重新计算 inputAnchorsLocked/outputAnchorsLocked，不能因为仍有 NODE_CENTER 连线就锁住配方切换。
    5.3 电路板连线规范
    交互方向：Tab 交互下左键查询来源，创建 SOURCE 节点；右键查询用途，创建 USAGE 节点。根节点和子节点都遵循这套左/右键规则。
    语义方向：数据边方向不再强制等于创建方向。查询来源时，SOURCE 节点作为“来源提供者”，连线从 SOURCE 节点整体中点指向被解释对象；查询用途时，USAGE 节点作为“用途集合接收者”，连线从被查询对象指向 USAGE 节点整体中点。
    锚点类型：被查询对象如果是当前节点绑定主语，则使用节点整体中点；如果是当前页某个非主语输入/输出/催化材料，则使用具体槽位中心。节点绑定主语永远是 itemId，不是某个槽位实例。
    确认规则表：
    | 当前节点 | 查询对象 | 查询类型 | 新节点 | 连线 |
    |---|---|---|---|---|
    | SOURCE(X) | 输入槽 Y | 查来源 | SOURCE(Y) | SOURCE(Y) 中点 -> SOURCE(X) 的 Y 槽 |
    | SOURCE(X) | 输入槽 Y | 查用途 | USAGE(Y) | SOURCE(X) 的 Y 槽 -> USAGE(Y) 中点 |
    | SOURCE(X) | 主语/输出 X | 查用途 | USAGE(X) | SOURCE(X) 中点 -> USAGE(X) 中点 |
    | SOURCE(X) | 主语/输出 X | 查来源 | 不新建 | 高亮 SOURCE(X) |
    | USAGE(K) | 主语 K | 查来源 | SOURCE(K) | SOURCE(K) 中点 -> USAGE(K) 中点 |
    | USAGE(K) | 主语 K | 查用途 | 不新建 | 高亮 USAGE(K) |
    | USAGE(K) | 非主语输入 Y | 查来源 | SOURCE(Y) | SOURCE(Y) 中点 -> USAGE(K) 的 Y 槽 |
    | USAGE(K) | 非主语输入 Y | 查用途 | USAGE(Y) | USAGE(K) 的 Y 槽 -> USAGE(Y) 中点 |
    | USAGE(K) | 输出 Z | 查来源 | SOURCE(Z) | SOURCE(Z) 中点 -> USAGE(K) 的 Z 输出槽 |
    | USAGE(K) | 输出 Z | 查用途 | USAGE(Z) | USAGE(K) 的 Z 输出槽 -> USAGE(Z) 中点 |
    起点横向偏移：同一合成面板内按材料所在行错开焊盘 X 坐标，第一行向左偏移，第二行不偏移，第三行向右偏移；更多行按左/中/右循环，避免同列多条来源/用途线完全重叠。
    样式：上下布局专用 PCB 走线，必须遵循“先沿实际目标方向垂直引出 -> 45°切角 -> 水平走线 -> 45°切角 -> 垂直接入目标锚点”的顺序，避免先水平再垂直造成线束穿插。注意：语义边方向不一定等于视觉布局方向，例如查来源时新 SOURCE 节点在下方但语义边从下方节点指回上方被解释对象，因此绘制端的垂直引出方向必须按 fromAnchor/toAnchor 的实际 Y 相对关系计算，不能单纯按 GraphExpansionDirection 取正负号。线宽定义在世界坐标系下（如 2.0f），绘制时乘以 camera.zoom，保证缩放时粗细比例协调，点击检测容差同步缩放。
    5.4 异构配方的“降维抽象”绘制 (兜底神技)
    在 FallbackLinearAdapter 中，无视模组特殊 GUI 形状，统一拍扁成“工业流水线图纸”：左侧输入流式布局 -> 中间机器图标(稍大+蓝底) -> 右侧输出流式布局。(注：原版工作台必须保留 3x3 网格)

    六、 画布固定 UI 层规范
    固定在左侧图谱抽屉的屏幕坐标层，不随画布缩放平移（恢复矩阵后绘制）：

    左上角：收藏列表入口与历史列表入口竖直排列。它们不是当前树操作按钮，而是顶部下滑面板的开关。未展开收藏或历史时，drawer 内只有一个合成图区；点击收藏或历史入口后，从 drawer 顶部丝滑下滑展开一个新的列表区，合成图区被该列表区向下排开。再次点击当前入口时列表区向上收起；收藏列表与历史列表互斥，打开其中一个必须收起另一个。列表区内部支持垂直滚动，点击条目恢复对应图谱。
    合成图区右上角：当前树操作按钮横向排列，包括搜索入口/搜索框、收藏当前树、创建副本/另存为、清空整棵树。搜索默认以一个小放大镜按钮存在；未展开时点击该按钮或 Ctrl+F 打开搜索框，展开后搜索框占据同一操作层。搜索结果展示区会在条目前置标识“来源/用途”，而虚空生根条目则会提供两个明确分按钮“来源 / 用途”供用户点选后创建对应根节点。它们始终属于合成图区本身，不属于顶部下滑的收藏/历史列表区；当收藏/历史列表区展开时，这组按钮会随着合成图区整体被向下排开。清空按钮显示为红色 X/删除符号，作用对象是当前画布内整棵图谱树；点击后清空所有节点、连线、打开的节点弹窗和锁定状态，并标记脏位。该按钮属于面板级全局操作，不参与单节点 Shift 破坏模式，也不进入 DeleteBranchCommand 的细粒度 Undo 语义；后续可由历史记录/崩溃恢复承担误删找回。
    左下角：全局操作提示文本（如“按住 Shift 右键连线可删除…”）。
    搜索层：Ctrl+F 唤出搜索框，搜索框固定在合成图区顶部的屏幕坐标层，和当前树收藏/副本/清空按钮横向排布；它不属于收藏/历史下滑列表区，因此会随合成图区被顶部下滑区向下挤开，且不随画布缩放平移。
    七、 持久化、容灾与双子抽屉系统
    收藏系统：永久保存图谱树，无限制。当前树收藏按钮位于合成图区右上角，收藏成功后该星星进入已收藏态，并在旁边显示“空加号星星”用于创建该收藏的副本/另存为；当前树发生展开、删除、切配方、撤销等语义变化后，已收藏态取消，副本按钮收起。
    历史记录系统：每次“虚空生根”自动存档，最多保留 5 条 (FIFO)，防止孤岛迷失。收藏/历史文件统一保存在当前游戏版本目录的 config/TianshuAIAX/cache/crafting_graph 下；其中 favorites/ 存放永久收藏，history/ 存放历史记录，crash_recovery.json 存放崩溃恢复快照。
    命令模式撤销栈：严禁序列化树快照。只记录 DeleteBranchCommand { UUID 列表 }，Ctrl+Z 时精准重建。撤销恢复时必须恢复 RecipePanelNodeType、节点绑定 itemId、RecipeGraphEdge 的语义方向与两端 GraphAnchorData；恢复完成后重新扫描剩余边重算 inputAnchorsLocked/outputAnchorsLocked，不能依赖删除前的脏锁状态。
    增量崩溃恢复：引入 isDirty 脏位。isDirty 只表示内存图谱结构发生过变化，不能在每次节点移动、展开、删除、翻页时立即写盘。自动保存采用低频节流策略：每次客户端 Tick 只做轻量判断，只有 dirty=true 且距离上次自动保存至少 60 秒、且当前没有正在进行的后台写入任务时，才生成一次 SaveData 并提交写盘。序列化写盘必须放入单线程后台 IO 队列，禁止在渲染线程、输入事件线程或 GUI 绘制流程中同步 Files.write。提交前对 JSON 内容计算 hash，如果和上次成功写入内容一致则跳过本次磁盘写入，只刷新节流时间，避免 selectedRecipeIndex 未变化或重复 tick 导致无意义覆盖。序列化字段至少包含节点 UUID、parentUuid、nodeType、itemId、displayName、selectedRecipeIndex、坐标、边 from/to、itemId、GraphExpansionDirection、fromAnchor/toAnchor；锁定状态优先在加载后按边锚点重算，避免旧存档锁状态与边集合不一致。下次上线弹窗提示恢复。
    八、 搜索与“虚空生根”系统
    Ctrl+F 唤出搜索框：

    画布内定位：模糊匹配已有节点，镜头平滑聚焦并高亮命中的节点。同一 itemId 可能同时存在 SOURCE 与 USAGE 两类节点，搜索结果必须在条目前置显示“来源/用途”标识，避免把“怎么合成”与“能做什么”混成一个结果。
    输入事件：搜索框由 ScreenEvent.KeyPressed 与 CharacterTyped 接管输入；Esc 关闭搜索框，Backspace 删除字符，方向键切换结果，Enter 聚焦当前已有节点结果。搜索打开时必须临时维持图谱交互态，避免用户松开 Tab 后输入框消失。
    虚空生根：画布无匹配但底层有配方时，底部显示 [+] 创建新根节点条目。该条目内部必须拆分为两个明确按钮：来源与用途；点击来源才创建 SOURCE 根节点，点击用途才创建 USAGE 根节点。没有对应配方的一侧必须置灰或不可点击，不能用整条目左键/右键隐式选择类型。新节点是完全独立的孤岛根节点并聚焦，不能默认为 SOURCE。

12. 📡 【玄哨】战术雷达预警（已完成）
{
    在危机四伏的世界里，提前一秒发现敌人就能扭转战局。天极战术雷达不是简单的“外挂透视”，而是一位时刻为你提供方位感知与语音战报的数字副官。

    它的核心设计理念是：报得少，但报得准；绝不吵闹，但在关键时刻能救你的命。

    🔭 两大感知半径
    雷达的工作区域被严格划分为两个同心圆：

    远距离雷达圈（32格）：负责“看”。在这个范围内被发现的敌人，会在你的屏幕边缘生成短暂的方向指示器，告诉你“那边有东西”。
    近距离警戒圈（16格）：负责“听与判”。一旦敌人踏入这个范围，雷达的语音系统才会真正激活，开始为你播报具体的战况。
    🟢 第一层：视觉方位感知（远距离）
    当敌人在 32 格内出现时，你不需要听语音，只需看屏幕：

    屏幕边缘会弹出提示（例如：[雷达] 左前方 僵尸 25格）。
    提示会精准标注敌人的相对方向和大致距离。
    同类型的怪物只会在刚进入范围时提示一次，不会在你跑动时疯狂刷屏。
    指示器存在 3 秒后会自动消失，保持界面清爽。
    🟡 第二层：模糊直觉预警（近距离 / 视线被挡）
    当敌人靠近到 16 格内，但你们之间隔着一堵墙，或者它在你的视线死角时：

    雷达会发出直觉预警语音：*“检测到僵尸进入警戒区域”*。
    静默规则：如果你当前正处于激烈的交火状态中，为了不干扰你听怪物的脚步声，这类模糊预警会被系统自动静默。它只在你处于安全状态时才会唠叨。
    🔴 第三层：精确交火告警（近距离 / 视线无阻挡）
    这是雷达最核心、最智能的阶段。当敌人不仅靠近到 16 格，并且它的视线直勾勾盯着你（射线无障碍）时，真正的战术播报开始：

    1. 首发接敌：360度全向洞察
    当你从安全状态突然遭到锁定，雷达会瞬间进行一次 360度 无死角的射线扫描（不局限于你的视野正前方，背后只要视线没被墙挡住的都能扫到）。
    它会一次性把底牌全亮给你：

    *“前方接敌。警戒范围内有2只僵尸，1只苦力怕。”*
    *“右后方骷髅接近。警戒范围内有1只骷髅。”*

    2. 盲区遇袭：最高优先级打断
    一旦进入战斗，雷达默认你看得见正前方的敌人，因此前方的新敌人不会再语音播报，避免骚扰。
    但是！如果有一只怪从你的背后或侧面悄悄摸过来锁定了你：

    雷达会瞬间打断当前正在播放的任何语音（甚至是 LLM 的长篇大论）。
    发出刺耳的警告：*“左后方蜘蛛接近！”*
    这是雷达唯一会强行打断其他音频的情况，因为你背后的刀比嘴里的情报更致命。
    3. 交火期静默
    在战斗中，只要怪物一直在你面前的视野里，无论来了多少只，雷达都会保持死一般的沉默，把听觉完全交还给你，让你专注走位和听声辨位。

    ⏳ 脱战判定：怎么才算“安全了”？
    雷达不会因为怪物被墙挡了一秒就立刻告诉你“安全了”。
    只有当 16格内所有敌人的敌意视线全部消失（被墙彻底挡住、走远或死亡），并且持续保持 3 秒钟，雷达才会解除交火状态。
    此时，所有的记忆清空，雷达重新回到安静待命的初始状态，等待下一次危机。

    💡 总结：如何配合雷达战斗？
    跑图时：看屏幕边缘的指示器，心里有数即可，不用理会偶尔的语音。
    进洞/拐角时：竖起耳朵听首发播报，它会告诉你这个房间到底有几只怪在看向你。
    打起来时：盯着前方打，完全不用管雷达。如果背后有险情，它会像拉响防空警报一样强行打断并警告你，听到背后报点，立刻转身即可。
}

{

    第一章：核心哲学与反模式警告
    在动笔写第一行代码前，必须深刻理解双生卡片与市面上 99% 的 Tooltip Mod 的本质区别。

    1. 我们的哲学：“寄生”与“同构”

    体验要求：玩家在视觉上绝对无法分辨哪行字是原版的，哪行字是我们的。无论玩家安装了什么字体模组、背景模糊模组，我们的表现必须与原版像素级一致。
    2. 绝对禁止的反模式（踩中即死）
    ❌ 反模式 A（自绘背景）：使用 Graphics.fill() 自己画一个黑色半透明背景，然后在上面写字。
    后果：如果玩家装了 ModernFix 或其他 UI 美化 Mod 把原版框改成了圆角/渐变，你的框还是方的。瞬间暴露 Mod 身份，极其廉价。
    ❌ 反模式 B（Hook 位置错误）：Mixin 注入 AbstractContainerScreen.renderTooltip 或某个具体的 Screen 类。
    后果：在原版背包正常，但在 JEI 悬浮窗、Curios 饰品栏、AE2 终端里完全失效。后期兼容维护将陷入地狱。
    ❌ 反模式 C（自由发挥式 AI）：把物品注册名 tconstruct:manyullyn_cleaver 丢给大模型说“请分析这把剑”。
    后果：大模型不知道这是啥，会一本正经地胡说八道（幻觉）。玩家只要被骗一次，永远不会再信这个功能。
    ❌ 反模式 D（延迟渲染占位符）：鼠标刚悬停时不显示占位符，等 300ms 后再显示 ⏳ 正在分析...。
    后果：原版框瞬间出现，但下面那行字过了 0.3 秒突然“蹦”出来。这种内部撕裂感是极其恶劣的视觉闪烁污染。
    第二章：架构底座（渲染与空间寻址）
    1. Mixin 下沉至 Layout 阶段
    你要找的注入点，不是某个具体的界面，而是原版将“文本列表”转换为“屏幕矩形坐标”的那个底层纯函数（通常在 GuiGraphics 处理 Tooltip 宽高计算的逻辑中）。

    你要做的事：在这个底层节点，拦截到原版准备渲染的 List<Component> 以及计算出的起始 (X, Y) 坐标和总宽度。
    为什么：因为无论是原版背包、JEI 还是 Curios，它们最终要画出那个小黄框，都必须经过这个底层计算节点。我们在这里截获，就能做到全 GUI 生态通杀。
    2. 寄生式同构渲染（零自绘）
    拿到原版的坐标和渲染上下文后：

    禁止调用任何绘制背景/边框的方法。
    强制：将我们计算好的文本，直接 add 到原版的 List<Component> 中（或者紧接着原版的列表，再调用一次原版的 drawOrderedTooltip 方法）。
    结果：原版画笔怎么描边、怎么填色，就会顺带着把我们的字也这么画。实现 100% 样式继承。
    3. 空间动态寻址算法（防越界四步曲）
    我们算出了自己文本的高度，接着要决定画在原版框的哪里。按以下顺序严苛判定：

    首选下方拼接：如果 屏幕高度 - 原版框底部 Y > 我们的高度，就画在正下方，X 轴左对齐。
    右侧顶部对齐：如果下方放不下，平移到原版框的正右侧。注意：Y 轴必须与原版框顶部完全对齐（因为 MC 原版框就在物品右上角，左对齐会盖住物品）。
    底线强制保底：如果右侧顶部对齐后，发现我们框的底部超出了屏幕底边。此时抛弃顶部对齐原则，强行将我们的框向上平移，直到我们的底部刚好贴着屏幕最底边。
    极端左侧兜底：只有当鼠标贴着屏幕最右侧，导致右侧也放不下时，才退回到原版框的左侧显示。
    第三章：数据流转引擎（三层解耦模型）
    我们将要添加的文本分为三层。它们在代码里是三个独立的方法，最后被拼接成一个 List。它们必须与原版框绝对同步渲染，严禁任何内部延迟显示。

    ▶ Layer 1：图谱引导区（常驻组装）
    无论什么物品，永远作为列表的第一行。

    固定输出：[Tab+左键] 查看来源 | [Tab+右键] 查看用途（使用灰色字体样式）。
    ▶ Layer 2：原版硬算 Diff 层（纯逻辑组装）
    这是体现硬实力的地方。绝对禁止读取任何模组自定义的 NBT 数据，只做原版数学差值。

    智能槽位映射（极其重要）：
    错误做法：永远拿悬停物品和 player.getMainHandItem() 比较。
    正确做法：写一个路由。如果悬停的是头盔，就去拿 player.getInventory().getArmor(3)；如果悬停的是 Curios 饰品，就通过 Curios API 获取对应类型的当前装备。
    主类型优先 + Tag 兜底判定（防误判红线）：
    错误做法：只判断两个物品有没有相同的 Tag（比如都有 #minecraft:tools）。这会导致“镐子”和“剪刀”被判定为同类进行对比，极其智障。
    正确做法：

    if (itemA instanceof SwordItem && itemB instanceof SwordItem) return true; // 优先精确匹配
    if (itemA instanceof DiggerItem && itemB instanceof DiggerItem) return true;
    // ... 其他主类型
    // 只有上面都不满足时，才退回看 Tag 交集（且要排除过于宽泛的 Tag）
    数学 Diff 计算：
    提取双方的 AttributeModifiers（攻击力、护甲值、攻速），计算差值，正数绿色带 ↑，负数红色带 ↓。
    提取双方的 Enchantments，比对等级差异。
    如果非同类，或者同类但没有任何差异：此层不输出任何文本（直接跳过，不占行数）。
    ▶ Layer 3：AI 赋能层（同生共死区块）
    此层由 Zone 2（深度对比）和 Zone 3（百科）组成。它们作为一个整体受控。

    整体显隐铁律：
    如果未配置 LLM API 密钥：整个 Layer 3 直接不存在。不要输出“AI未启用”，不要占位，当它不存在。
    如果配置了 LLM：Layer 3 的占位符立即参与组装，与 L1、L2 随原版框同步出现。
    Zone 2：受约束推理（防幻觉核心）
    占位态（有 LLM，且为同类物品）：输出 ⏳ 停留2秒分析差异...
    触发：悬停同类物品满 2 秒。
    生死线缓存（Cache Key 设计）：
    错误 Key：悬停物品ID + 对比物品ID。这会导致两把不同附魔的钻石剑共用缓存，显示错误分析。
    正确 Key (ItemSemanticHash)：必须组合 物品ID + 附魔列表Hash + 属性修饰符Hash + 当前耐久度 + Lore文本Hash + Capability快照Hash。30秒内相同 Hash 禁止发请求。
    价值白名单提取（Top 10）：不要去读具体的 NBT Key（如 Damage），要去读“机制”。通过 Capability 或 1.20.5+ 的 DataComponents 提取以下 10 个布尔值/字符串：
    1.可维修 2.可升级 3.可成长 4.可蓄力 5.资源消耗 6.技能绑定 7.触发条件 8.使用限制 9.耐久机制 10.特殊死亡惩罚。
    Prompt 强约束模板（直接复制使用）：
    “你是一个严谨的游戏数据比对器。已知：当前穿戴物品的特征为 [拼接Top10数据]，悬停物品的特征为 [拼接Top10数据]。请仅基于上述已知数据，回答这件装备相比当前装备有哪些明确存在的机制差异。严禁猜测、严禁使用你的背景知识补完、不知道请直接回答未知。限制30字以内。”

    Zone 3：RAG 百科
    占位态：全物品常驻输出 💬 说出"介绍下这个"查看百科
    触发：监听到语音指令或特定按键，将物品名发给本地 RAG 检索，流式打字输出（限40字）。
    Soft Fail 轻失败态（异常兜底）
    当发生网络断开、本地模型未启动等异常时，禁止抛出异常或弹 Toast。
    强制做法：捕获异常，将对应的占位符文本替换为低存在感的灰字：⚪ 深度分析暂不可用 或 ⚪ 百科查询暂不可用。
    第四章：生命周期与强杀机制
    伴生卡片没有复杂的状态机，它只有“生”和“死”。

    唤醒：每帧检测当前鼠标悬停的 hoveredStack，如果从空气变成了非空气物品，触发组装逻辑。
    瞬态销毁（核心）：一旦检测到 hoveredStack 变成了空气，或者变成了另一个不同的物品：
    立刻清空本地的流式文本缓冲区。
    如果有正在进行的 LLM 请求（通常是 CompletableFuture 或 WebSocket 连接），无条件调用 cancel(true)。
    本帧不渲染任何东西。下一帧原版框消失，我们的框也随之瞬间消失。绝不等待 AI 字打完。
    第五章：开发验收 Checklist
    开发完成后，请对照以下列表逐条测试。任何一条不满足，均视为未达标：

    [ ] 兼容性验收：安装 JEI、Curios、AE2 后，在它们的界面悬停物品，伴生卡片依然能在正确的位置同构显示。
    [ ] 样式继承验收：安装某款圆角/高斯模糊 Tooltip 美化 Mod 后，伴生卡片的背景和字体必须与其完全一致，无任何割裂感。
    [ ] 槽位路由验收：主手拿剑，在背包悬停一个头盔，卡片必须显示“对比:当前头盔（耐久等属性）”，绝不能显示对比主手剑。
    [ ] 防误判验收：主手拿铁镐，悬停剪刀，Layer 2 绝不能出现，绝不能进行属性对比。
    [ ] 防闪烁验收：鼠标在背包格子中快速来回扫过，伴随原版框的快速出现消失，伴生框（包括里面的 ⏳... 占位符）必须作为整体完全同步，绝不能出现下半部分延迟蹦出来的情况。
    [ ] 优雅降级验收：在配置文件中清空 LLM API Key，重启游戏。悬停任何物品，卡片只能有 L1 和可能存在的 L2，绝不能出现“未启用”之类的灰色提示。
    [ ] 防幻觉验收：拿一把极度冷门的模组武器（大模型训练集里绝对没有的），悬停 2 秒触发 Zone 2。AI 的回答必须是“未知”或只陈述 Top10 提取出的机制差异，绝不能自己编造该武器的背景故事或错误技能。
    [ ] 缓存隔离验收：准备两把附魔不同的钻石剑（一个锋利V，一个耐久III）。悬停第一把触发分析，然后移开；立刻悬停第二把，系统必须发起新的网络请求，绝不能直接显示第一把的缓存结果。
    [ ] 轻失败验收：触发 AI 请求的瞬间拔掉网线。对应的占位符必须平滑变成 ⚪ 深度分析暂不可用，游戏内不能弹出任何错误提示框，后台日志不能打印大段异常堆栈（只允许打一行 DEBUG 级别的警告）。
    [ ] 强杀验收：触发 AI 流式打字，在打到一半时瞬间将鼠标移开。后台网络请求必须被成功中断，下次悬停同一物品时，应该重新请求或显示缓存，绝不能接着上次截断的地方继续往外蹦字。

14. 🛑 【余烬】关键链路熔断预警系统
{
    痛点：传统的 10% 固定耐久预警极其智障——低频挖矿时疯狂打扰玩家，高频战斗（如拔刀剑模组、末地极速刷怪）时又根本来不及反应，导致关键武器碎掉或挖坏稀有矿石。
    功能描述：引入工业级的“预测性维护”概念。不再死守固定百分比，而是根据玩家当前的“消耗斜率”动态计算剩余寿命，结合高风险动作识别，在武器失效前进行“熔断干预”，并直接给出备选方案。

    技术实现：

    预测性消耗计算：
    维护一个 30 秒的环形缓冲区，每秒记录一次主手物品的耐久度。计算衰减斜率：消耗速率 = (30秒前耐久 - 当前耐久) / 30。
    将斜率转化为预计可用秒数 (TTL)。例如：耐久还剩 50，但每秒掉 10，TTL 就是 5 秒。
    动态熔断触发器（拒绝无效打扰）：
    绝对熔断：无论什么情况，只要 TTL < 5秒，瞬间触发最高级干预。
    情境熔断：当耐久低于 20%，且检测到玩家正在进行“高风险动作”（如正在挖掘钻石/深板岩等高价值方块，或正在受击状态），直接熔断。
    静默延迟：如果耐久低于 5%，但 TTL > 60秒（比如在闲逛挖泥土），不播报，等玩家停下来或者打开背包时再说。
    极简背包扫描（Solution-Oriented 核心）：
    在触发熔断的同一帧，瞬间遍历玩家快捷栏（Hotbar 0-8）和主背包前两排。寻找同类或更高级的替代品（例如：钻石镐碎了，找铁镐或备用钻石镐；弓没箭了，找弩或弩箭）。
    AI 反馈示例（流式打字，但极短）：
    AI 不报干瘪的数字，只报“后果”和“退路”。

    场景 A（高频 PVP 刷怪，TTL 极短，有备选）：
    *(急促打断)* “立刻切换！你的剑还有不到 3 秒就碎了！按 2 换铁剑！”
    场景 B（低频挖矿，即将挖到稀有矿，无备选）：
    *(警告)* “停下！镐子快碎了，背包里没有备用，别挖这块钻石了。”
    场景 C（弓箭手弹药枯竭，有备选）：
    *(提醒)* “箭矢耗尽，按 3 切换弩继续打！”
    场景 D（闲逛挖泥土，TTL 很长，无备选）：
    *(极其平淡，不占用听觉通道)* “*(仅在打开背包时在 UI 角落弹一行小字：主手武器耐久较低，记得修补)*”
}

15. 📦 【净囊】动态垃圾清单与语音清理
{
    痛点：传统清理 Mod 的“垃圾黑名单”是静态的，难以适应游戏不同阶段（如前期留泥土，后期扔泥土），且修改配置极其繁琐，打断游戏心流。
    功能描述：用语音彻底取代配置 UI。玩家在游玩过程中随口定义“什么是垃圾”，系统动态维护名单；当需要清理时，一句话触发物理级倾倒。

    核心交互闭环（两步走）：

    第一步：动态标记（消灭配置 UI）
    不需要任何菜单。玩家看到什么烦了，直接动嘴。
    玩家：“腐肉以后都当垃圾。” / “圆石标记为垃圾。”
    系统动作：底层将该 ItemID 写入自己的垃圾名单。可通过一个ui动画来表示将xx设定为垃圾。
    移除功能：玩家：“泥土先别扔了。” -> 系统瞬间从名单移除。
    视觉暗示：被标记为垃圾的物品，在背包里会被画上一个极淡的“废纸篓”小角标。
    第二步：盲操清空（解决双手被占用的痛点）
    当玩家在搭桥、游泳、战斗，背包满了，根本没手去一个个点的时候。
    玩家：“清空垃圾。” / “扔掉没用的。”
    系统动作（服务端接管）： 客户端发送自定义的 C2SRequestClearJunk 包。若拥有 S2C 授权，服务端接收后，在服务端遍历真实背包，将命中垃圾名单的物品直接移除。彻底杜绝客户端高频丢包触发反作弊。
    UI + 语音反馈（如果有TTS）： “已清理 42 个物品。” *(注：若在原版服务器或没开权限的服务器，则提示“服务器不支持自动清理”)*


    【当前实现补充】
    - 已完成模块骨架：客户端净囊控制器、语音意图解析、动态垃圾清单本地持久化、背包角标渲染、服务端授权清理包和服务端真实背包清理执行器。
    - 当前清单持久化位置：config/TianshuAIAX/module/junk/cache/junk-list.json。客户端只保存 ItemID，不保存 ItemStack、Player、Level 等 Minecraft 活对象，服务端不保存玩家分类清单。
    - 当前清理链路：IR 基于净囊注册的 hotwords/extraWords 做指令拦截，命中后向净囊模块投递结构化消息，消息包含命中的指令词以及解析到的物品信息；净囊模块据此决定 MARK/UNMARK/CLEAR。“清空垃圾/清理垃圾/扔掉没用的/倒垃圾”等清理意图会进入 JunkClearRequestClientGateway 申请门面。该门面调用 common 里的 JunkClearRequestGate 做瘫痪态权限判断、清单净化和数量限制，只有 FeatureManager.isAutoTrashAllowed() 已被服务端 S2C 授权包置 true 时，才允许发送 C2SRequestClearJunkPacket。服务端再次读取 ServerConfig.ALLOW_AUTO_TRASH 后遍历真实背包，命中客户端提交垃圾清单的物品由服务端执行等价于玩家按 Q 的抛弃操作，并通过 S2CJunkClearResultPacket 返回结果。
    - 分层边界：tianshu-common 只放纯 Java 规则，包括 JunkItemIdPolicy、JunkTextNormalizer、JunkVoiceRules、JunkVoiceWords、JunkClearRequestGate；NeoForge 侧只保留 Minecraft ItemStack 判定、配置路径、网络 payload、实际发包和服务端实体生成。业务控制器不得直接 PacketDistributor.sendToServer，必须走申请门面。
    - 语音词库资源：净囊模块已按通语模块同类结构提供 common 资源 com/rheinmetal/tianshu/constant/junk_cleaner_voice_words.json，只承载 hotwords/extraWords，用于后续协议中心/ASR/IR 词库登记；MARK/UNMARK/CLEAR 的业务判断仍由模块内部状态机和 JunkVoiceRules 负责，不把业务意图分类塞进词库 JSON。
    - 当前安全边界：客户端清单是玩家自己的本地分类缓存，服务端不做“物品价值保护”筛选，只做权限、ItemID 合法性和真实背包命中校验；是否把某物品当垃圾完全由玩家语音标记决定。
    - 暂未接入协议适配器：按当前架构阶段不新建净囊适配器、不改其他关键模块适配器。后续应注册 MODULE_ID=client.junk_cleaner，hotwords 建议包含“垃圾/清空垃圾/清理垃圾/倒垃圾/当垃圾/别扔”，extraWords 包含“以后/标记/取消/先别/扔掉/丢掉”。收到 VOICE_TRIGGER 后由本模块内部状态机决定 MARK/UNMARK/CLEAR，不把业务判断回写 IR。

## 客户端宿主边界（2026-07-15）

当前客户端采用 `tianshu-neoforge -> tianshu-client -> tianshu-common` 单向依赖。Common 持有 Core、Protocol 与功能模块；client 持有客户端 runtime、Presence、设置模型、IR 索引、音频和诊断；NeoForge 只持有加载器事件、Minecraft 对象快照转换、TOML、原版 Screen/HUD 和平台 adapter。

`TianshuCoreManager` 仍是模块生命周期唯一宿主。世界登录、退出和客户端关闭经 `NeoForgeClientLifecycleAdapter` 转发给 `TianshuClientRuntime`；runtime 使用 generation 防止旧世界启动回调恢复已退出 session。客户端级 IR/诊断/GPU 资源不随世界切换重复创建，世界级 Core session 和录音硬件在 logout 时停止。

Minecraft 活对象不能进入 client/common。NeoForge 必须先转换为不可变 snapshot、ID、字符串或 protocol payload。模型下载、索引、GPU 探测、推理、诊断写盘和阻塞等待严禁占用 Minecraft 主线程；主线程只做必要事件接收、快照读取、Screen/HUD 和 UI 更新。

配置唯一来源保持 `config/tianshu-client.toml`。各模块通过窄设置端口访问，禁止恢复全能配置接口。共享语言、纹理和客户端数据位于 `tianshu-client`；Mixin 与 NeoForge metadata 继续留在加载器项目。

详细规则见 `doc/client/NeoForge客户端架构说明.md`。
