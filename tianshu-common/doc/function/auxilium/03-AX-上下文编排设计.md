## 0. 文档定位

| 文档 | 回答什么 | 本文与它的关系 |
|---|---|---|
| 01 运行逻辑手册 | DSH 的循环、surface、装配、计量、压缩**怎么运作**，哪些能搬 | 本文**取其机制**（确定性排序、usage 锚定、阈值公式、检查点形态、标记对当锁），不重复其描述 |
| 02 对话记忆策略调研 | 业界方案的**取舍与证据**，推荐组合 | 本文**取其结论**（前缀缓存为第一杠杆、三因子打分、避免改历史的记忆方案），落成 AX 的可执行排布 |
| 03 本文 | AX 的**消息序列、状态快照、检索编排、压缩、预算、观测、演进** | 唯一作用：把 01/02 变成 AX 侧的硬规则与数值 |

**已由用户确定、本文不再讨论的 7 条基础策略**（写入设计，不作为选项）：

1. 游戏状态做变化检测，无实质变化时复用上一份快照，不每轮重建。（或者用户问到的时候我们主动提供全量）
2. CHAT 推理默认关闭 thinking；效果不佳再开最低档。
3. 压缩（compaction）时开启 thinking，并做成与 DSH 一致的可选强度面板项。
4. 接受"裁剪破坏前缀"这个代价，不追求零破坏。
5. **system 只有一份、字节冻结、全档位共用**；不存在"按预算选档"，也不存在"档位切换导致 system 变化"。
6. **thinking / reasoning 内容一律不进历史**，历史里只保留最终回复正文。
7. **压缩是后台任务**，走既有 TASK 车道并行执行，不阻塞当前轮次。

**术语**（全文固定，不再解释）：

| 记号 | 含义 |
|---|---|
| `S` | system 消息（**唯一一份**，全档位共用，字节冻结） |
| `S2` | system 内的工具 schema 槽位（当前为空，为 function calling 预留） |
| `H` | append-only 历史消息段（已发送过的 user/assistant/tool 消息原样保留） |
| `C` | 检查点消息（compaction 产物，替代被遮蔽的早期 `H`） |
| `T1` | 本轮状态快照消息（变化检测通过后才追加） |
| `T2` | 本轮检索注入消息（记忆 + 知识命中） |
| `T3` | 后台任务结果槽位（预留，见 §8.2） |
| `Q` | 本轮当前输入（ASR 完整句，最后一条消息） |
| 档位 | 用户选定的**可用上下文预算** `W`，取值 50K/100K/200K/500K，默认 100K。**与 `S` 无关** |
| 系列 | 一次连续的上下文生命周期；起点 = 会话建立 / **`S` 文本变更**。压缩后**不开新系列**，**换档位也不开新系列** |
| 水位 | 触发压缩的 prompt token 阈值 `T = 0.75×W`（四档数值见 §5.1） |
| miss-token 当量 | 成本单位：1 个按未命中单价计费的输入 token。命中 token = 0.02 当量（02 §0.1 的 1/50） |

## 1. 目标与不变量

### 1.1 目标（按优先级排序，冲突时上位胜出）

| 序 | 目标 | 度量 |
|---|---|---|
| G1 | 前缀缓存命中率最大化 | 稳态 `hit_ratio ≥ 0.90`，目标 0.95 |
| G2 | 语音首 token 延迟可控 | CHAT `first_token P50 ≤ 800ms`（thinking 关，50K/100K 档） |
| G3 | 上下文不溢出、不静默丢信息 | 溢出请求数 = 0；压缩有检查点可审计 |
| G4 | 编排可解释、可回放 | 每轮可从落盘事件重建同一份请求字节 |

### 1.2 不变量（I1–I13，违反即为设计缺陷，不是"取舍"）

| ID | 不变量 | 违反后的可检测信号 |
|---|---|---|
| **I1** | **前缀稳定优先于内容新鲜度**。同一轮内无法同时满足"内容更新"与"前缀不变"时，选择保留旧内容并把它降级到尾部块（`T1`/`T2`），永不回写前缀区 | 同一 `seriesId` 内 `systemHash` 变化 |
| **I2** | `S` 必须钉在 `messages[0]`，且**任何路径都不得删除、不得移位、不得被滚动窗口挤出**；压缩只缩减 `H`（01 §7.2 的 `firstIdx=1` 同义规则） | `messages[0].role != "system"` 或系统消息出现在非 0 位 |
| **I3** | `H` 只追加。**唯一**允许改写 `H` 的操作是 compaction，且它必须是显式、可记账、一次性的 | 出现"同样长度的历史，内容却变了" |
| **I4** | 所有每轮会变的内容只能出现在本轮尾部块（`T1`/`T2`/`T3`/`Q`），禁止出现在 `S`/`S2`/`C` | `S` 内出现坐标/血量/时间/玩家名 |
| **I5** | **确定性**：相同输入必产出逐字节相同的消息序列（规则见 §2.4） | 同一状态两次装配的 `promptHash` 不同 |
| **I6** | 硬预算：发出的请求 `prompt_tokens + maxTokens ≤ W`，且 `prompt_tokens ≤ T` 不成立时必须先裁剪 | 出现 `CONTEXT_WINDOW_EXCEEDED` 报错 |
| **I7** | 压缩是显式成本事件：必须单独记录 `compaction_flag` 与前后 token，可审计、可回滚（原始事件不删） | 找不到 `compaction/start`–`end` 配对 |
| **I8** | token 计量以 provider 返回 `usage` 为准，本地估算只用于"前瞻决策"；两者不得混为一谈（01 §6.2） | 用估算值做账单/容量结论 |
| **I9** | 不引入"每轮改写历史"的记忆方案（Letta 式 memory block prepend、A-MEM memory evolution）（02 §2.1/§2.4）。记忆检索产物只能进 `T2` | 记忆内容出现在 `S` |
| **I10** | 单个语义单元不切开：完整问答轮、完整 STM 块、完整知识命中、完整 `tool-call`/`tool-result` 对（01 §7.2、02 §6.2 铁律 4） | 出现孤立 `tool` 消息或无配对的 `assistant.tool_calls` |
| **I11** | **thinking / reasoning 内容绝不进入历史**。历史里只保留最终回复正文；`reasoning_content` 只能落 telemetry（长度、耗时），不得落 `AXRawTurn.content`、不得落 `H`、不得进 `C`、不得进后续任何请求 | 历史里出现 `reasoning` 文本；`turns[i].contentHash` 与 `payload.text()` 的 hash 不等 |
| **I12** | **`S` 单一且字节冻结**：全档位共用同一份文本，字节逐字相同；档位只改变预算参数（`W`/`B`/`P`/`T`/`R`），不得改变 `S` 的任何字节 | `systemHash8` 随 `contextTier` 变化；同 `seriesId` 内 `systemHash8` 变化次数 > 0 |
| **I13** | **易变内容只在尾部，且必须出现在尾部**：任何每轮可能变化的字节唯一合法落点是 `T1`/`T2`/`T3`/`Q`；既禁止进前缀（I4），也**禁止为了省 token 而丢弃**（尾部是信息完整性的唯一保证） | 出现"因预算不足而整体不注入状态/检索"的分支 |

> I1 是"成本不变量"，不是"效果不变量"。02 §0.1 的结论：DeepSeek 缓存命中单价约为未命中的 **1/50**，前缀每被改一个字节，cost 杠杆即失效。因此在"模型多知道一条状态"与"整段前缀重算"之间，永远选前者让步。
>
> I11 的代价为零：`reasoning_content` 本来就不该占用上下文预算（它是模型的过程产物，不是对话内容）。省下的不是钱，是**上下文容量与一致性**。当前协议层已把 `text()` 与 `thinkingContent` 分列（§9.3），本条是把"偶然满足"升级为"必须满足"。
>
> I13 与 I4 的分工：I4 管"不许进前缀"，I3 管"不许改写历史"，I13 管"必须进尾部"。

## 2. 消息排布规范

### 2.1 稳态消息序列

```
messages[0]                system           S      ← 唯一一份 system（+ 未来 S2 工具 schema）字节冻结
messages[1 .. p]           user/assistant   H      ← append-only：以往各轮的 T1/T2/Q 与 assistant 回复原样保留
messages[p+1]              user             T1     ← 本轮状态快照（变化检测通过才出现）
messages[p+2]              user             T2     ← 本轮检索注入（有命中才出现）
messages[p+3]              user             Q      ← 本轮 ASR 完整句（永远是最后一条）
--- 本轮结束，模型回复 → 追加为 messages[p+4] assistant，成为下一轮 H 的一部分 ---
```

压缩后的形态（只发生一次，取代 `H` 的早期部分）：

```
messages[0]                system           S      ← 不变（逐字节相同）
messages[1]                user             C      ← 检查点（替代被遮蔽的前段 H）
messages[2 .. p']          user/assistant   H'     ← 保留的最近历史（完整轮次）
messages[p'+1 .. p'+3]     user             T1/T2/Q
```

### 2.2 每轮变化表（这是全文档最需要被实现遵守的一张表）

| 位置 | 内容 | 每轮是否变 | 变化时的动作 | 前缀影响 |
|---|---|---|---|---|
| `S` | 唯一 system 文本 | **否**（**全档位、全系列恒定**） | 仅配置升级时变更，且必须开新系列 | 变更瞬间全 miss（正常路径下永不发生） |
| `S2` | 工具 schema（未来） | **否**（系列内恒定） | 仅系列起点写入 | 全 miss |
| `H` | 历史消息 | **只增长** | 追加，绝不重排/重写 | 无（前缀天然复用） |
| `C` | 检查点 | 否 | 仅压缩时产生 | 一次：从 `C` 起失效（`S` 仍命中） |
| `T1` | 状态快照 | 仅在状态向量变化时 | **追加新消息**（不替换旧消息） | 从本轮 `T1` 起未命中 |
| `T2` | 检索注入 | 仅在检索有命中时 | **追加新消息** | 本轮尾部未命中 |
| `Q` | 当前输入 | 是 | 追加 | 本轮尾部未命中 |

关键推论（必须写进实现注释）：**"未命中"的范围只等于本轮的 `T1+T2+Q`，永远不等于整个 prompt**。因为上一轮的 `T1+T2+Q` 已经是不可变的 `H` 前缀。这正是 02 §3.5 "请求边界持久化 cache prefix unit" 的直接利用：上一轮请求末尾的单元 → 本轮前缀可完整匹配。

**成本核算**（每轮稳态）：

```
miss_tokens   = |T1| + |T2| + |Q|                   ≤ 256 + 512 + 128 = 896
hit_tokens    = prompt_tokens − miss_tokens
price_factor  = miss_ratio × 1.0 + (1 − miss_ratio) × 0.02     // 命中 1/50 价，02 §0.1
```

以默认 100K 档的中位上下文 `prompt_tokens = 46928`、`miss = 896` 为例：`miss_ratio = 1.9%`，`price_factor ≈ 0.0392`，即**输入成本约为全 miss 的 1/25.5**（全档位数值见 §6.4）。

⚠ **尾部膨胀的代价随档位急剧变化**（这是四档制下新出现的结论）：若尾部膨胀到 2.5K token。
下表统一用 §6.4 的口径 `折扣 = Ctx / 每轮成本`，即"每轮成本 ÷ 同样上下文全 miss 的成本"：

| 档位 | 中位上下文 | 尾部 896 时的折扣 | 尾部 2.5K 时的折扣 | 退化倍数 |
|---|---|---|---|---|
| 50K | 25168 | 1/17.9 | **1/8.4** | 2.1× |
| 100K | 46928 | 1/25.5 | 1/13.7 | 1.9× |
| 200K | 90448 | 1/33.4 | 1/21.0 | 1.6× |
| 500K | 221008 | 1/41.5 | 1/31.9 | 1.3× |

所以 `|T1|+|T2|+|Q| ≤ 900` 是**全档位统一硬指标**，且**在小档位上更不可妥协** —— 50K 档尾部翻倍等于砍掉一半成本优势。

### 2.3 单一 system 与四档可用上下文预算

**2.3.1 取消三档后的直接后果（这是本次改动最省事的一处）**

旧设计里"三档 system 切换"要处理缓存失效（选 C 路径：系列起点定死、系列内不变）。新设计下这一整块问题消失，且带来两个额外收益：

| 收益 | 论证 |
|---|---|
| **档位切换不再破坏前缀** | 档位只改变 `W`/`B`/`P`/`T`/`R` 这五个**策略参数**，不改变任何已发出的字节（`S` 逐字节相同）。因此"改档 = 换系列"的约束**随三档取消而消失**：会话中途升档/降档是合法的、零缓存代价的操作 |
| **写全一份 system 的成本几乎为零** | `S` 落在**命中区**。从旧上限 1400 token 扩到 4096 token，稳态每轮只多 `+2696 × 0.02 = +54` miss-token 当量（50K 档中位成本的 +3.8%、500K 档的 +1.0%）。所以"模型能力足够、不需要靠裁剪提示词省钱"这个判断在成本上是成立的 |

`S` 的预算因此改为**容量校验阈值**而非**选档依据**：

```
S_LIMIT = 4096 token（硬上限，全档位相同）
  - 超过 4096 → 配置错误，拒绝启动（不允许自动裁剪，system 是原子文本）
  - 4096 同时是"腐化检测线"：一份纯静态 system 不该超过它。
    超了通常意味着有人把动态内容塞进了 S（I4/I12 违规），先查这个，不要先调大阈值。
```

**2.3.2 四档可用上下文预算**

档位是**产品级配置**（用户/部署选定），不是运行时决策，且**不参与 prompt 字节**。

| 档位 | `W` | 适用判断（依据见 §5.2 / §6.4 / §6.5） |
|---|---|---|
| 50K | 51200 | 断续游玩、成本敏感、单次会话 < 250 轮；尾部纪律要求最严 |
| **100K（默认）** | **102400** | 单次会话 250–600 轮；每轮成本与前三档的折中点 |
| 200K | 204800 | 长连续会话（> 600 轮），或需要携带大块知识与多步任务清单 |
| 500K | 512000 | 只在"必须一次装下巨量历史且连续不断"时用；断续场景下预热成本 ≈ 45 轮稳态成本（§6.5），且要求模型真实窗口 ≥ 512512 |

**定档与换档规则**：

```
档位是配置项，不是每轮决策：
  contextTier ∈ {K50, K100, K200, K500}，默认 K100
  W = tier.windowTokens；启动时校验 W + O ≤ modelContextWindow
     —— 不满足则该档位视为不可选，回退到满足条件的最大档位，
        并记 tier_downgraded(reason=window_too_small)。禁止静默按模型窗口放大 W。
  会话中途允许换档（只改 T/R/P），必须：
    ① 不改 S 的任何字节（I12）；② 不改 seriesId；③ 落 context_tier_changed 事件
  换档本身零缓存代价。唯一的可观测差异是"下一次压缩何时发生"。
```

**2.3.3 若要改 `S`：三条路径与唯一允许的做法**

**`S` 在系列内永不变。** 若业务上确实需要改（配置升级、人格改写），只有三种路径：

| 路径 | 做法 | 缓存后果 | 兼容性风险 |
|---|---|---|---|
| A 回写 `messages[0]` | 覆盖第一条 system 消息的文本 | **从第 1 个 token 起全部失效** | 无 |
| B 追加第二条 system 消息 | 保留旧 `S`，末尾追加新 `S'` | 追加点之前仍可命中 | 中：多 system 消息在 OpenAI 兼容层行为不一致（有的网关合并、有的报错、有的当普通消息） |
| C 开新系列 | 新 `seriesId` + 清空 `H` + 新 `S` | 每个系列只付一次全 miss | 无 |

**采用 C**：改 `S` 必须走"开新系列"接口（`seriesId` 递增、`H` 清空/归档、记 `series_switch` 事件），不允许隐式生效，不允许热更绕过。路径 B 永不使用（`C` 已经用 `user` 角色，见 §5.8，不需要第二条 system）。路径 A 只在"新系列第一次落盘"时等价出现。

### 2.4 确定性要求（I5 的可执行清单，D1–D12）

> 01 §8.1 的结论必须先钉死：**DeepSeek 侧没有任何 `cache_control` / 缓存断点标记可发**，命中完全依赖"前缀逐字节不变"。所以确定性不是风格问题，是功能问题。02 §2.1 的反面证据也在这：Letta 的 `<metadata>chars_current</metadata>` 一改，整段前缀作废。

| ID | 规则 | 典型坑 |
|---|---|---|
| D1 | 段排序用**固定 `order` 常量 + code-unit 名称序**（01 §5.3），禁止 `localeCompare`、禁止 `HashMap` 迭代序 | 中文 locale 下排序漂移 |
| D2 | 集合一律 `LinkedHashMap`/`TreeMap` + 显式 `Comparator`；禁止 `HashSet`/`HashMap.values()` 进 prompt | 同分事实顺序抖动 |
| D3 | **任何时间戳、相对时间、"现在"、随机 ID、会话 ID、在线人数、玩家名禁止进入 `S`/`S2`/`C`**（02 §6.2 铁律 1）；需要就给 `T1` | `system` 里塞"当前时间 12:34" |
| D4 | JSON 序列化 key 顺序固定（插入序）；工具 schema 按工具名 code-unit 排序（01 §5.3、R4） | Gson 默认 `LinkedTreeMap` 可以，但别用 `HashMap` 构造 |
| D5 | 数值格式：整数原样；浮点若无法避免，`String.format(Locale.ROOT, "%.1f")`；**前缀区禁止出现浮点** | 默认 locale 用逗号做小数点（德语/法语环境） |
| D6 | 换行统一 `\n`，段落间固定 `\n\n`；文本入 prompt 前做 NFC 归一 + 去行尾空白 | IME 全角/半角、`\r\n` |
| D7 | 空段处理规则固定：某段渲染为空 → **整段不出现**（不输出空标签）；不允许"有时输出 `<x></x>` 有时不输出" | 无事实时空标签 |
| D8 | 去重规则固定：按内容 hash 去重，**保留首个**（不是最后一个），且去重发生在排序之前 | `.distinct()` 在排序后 → 保留下来的条目不确定 |
| D9 | 截断只按完整语义单元（I10），且截断函数必须按**码点**而非 UTF-16 char，避免切断 emoji/SMP 字符 | 半截代理对 |
| D10 | 并行装配结果必须按**声明顺序**合并，不按完成顺序 | 异步检索谁先回谁在前 |
| D11 | 装配完成后计算 `promptHash = sha256(串接后的全部消息 role+content)`，随请求落盘；同状态两次装配 hash 必须相等（自检开关） | 漂移只能靠这个发现 |
| D12 | 浮点比较前统一 `round(score, 6)`；排序 key 里禁止直接用未 round 的 double | JIT/FPU 末位差异导致 tie-break 翻转 |

**新增 D13（I12 的可执行化）**：`systemHash` 必须在**部署时算一次并落盘**（`prompt_texts.json` 的元数据），运行期只读不重算；每轮把它与落盘值比对，不等即视为配置被绕过并拒绝启动会话。

### 2.5 明确的反例（不要做）

- ❌ 把 `game_context` 拼进 `S`（当前实现即如此，见 §9 缺陷 C）——每轮必变，等于每轮全 miss。
- ❌ **把 `S` 按预算拆成短/中/长三份，运行时挑一份**（本次已取消；见 §9 缺陷 T）。它既省不到钱（`S` 在命中区），又制造了一个"档位↔system"的隐式耦合。
- ❌ 用 `messages.add(0, …)` 插任何东西。
- ❌ 每轮重新渲染全部历史（哪怕渲染结果"看起来一样"）——只要有一个字节不同（空白、顺序、格式），缓存即失效。
- ❌ 给模型一个"压缩上下文"的工具（01 §R12：DSH 自己都没有，别自创）。
- ❌ 在 `T1`/`T2` 里放 `requestId`/`turnId` 之类的调试字段——它们每轮必变，白白扩大 miss 区。
- ❌ 把 thinking / reasoning 文本回填进 assistant 历史（I11）。模型下一轮会把它当成自己说过的话继续，既污染内容又白烧 token。

## 3. 状态快照策略

### 3.1 状态向量与变化判定维度

把要描述的游戏状态抽象成一个**纯函数状态向量** `stateVector`，只从世界/玩家客观事实取值，不含时间戳、不含格式化浮点。

| 维度 | 取值来源 | 桶化/判定规则 | 变化阈值 | 进 `T1` |
|---|---|---|---|---|
| 维度 + 群系 | `level.dimension()`、`biome` | 字符串枚举 | 变化即变 | ✅ |
| 区块坐标 | `player.blockPosition()` → chunk key | `(x>>4, z>>4)` | **跨区块才变**（不记精确坐标） | ✅ |
| 与上次落点距离 | 两个 chunk 中心距离 | 分档 `<32` / `32–128` / `>128` | 跨档才变 | ✅ |
| 生命值 | `getHealth()` | `heart = ceil(hp/2)` | 心数变化 ≥1（即 2 HP） | ✅ |
| 饥饿值 | `getFoodData()` | `meat = ceil(food/2)` | 半格变化 ≥1 | ✅ |
| 氧气 | `getAirSupply()` | `危急` / `正常`（`< 60`） | 跨档 | ✅ |
| 等级 | `experienceLevel` | `0` / `1–9` / `10–29` / `30+` | 跨档 | ✅ |
| 时段 | `level.getDayTime()` | `清晨/白天/黄昏/夜晚` 四档 | 跨档 | ✅ |
| 天气 | `isRaining` / `isThundering` | `晴/雨/雷` | 跨档 | ✅ |
| 主手物品 | `getMainHandItem()` | `itemId + 数量档`（0/1–15/16–31/32–63/≥64） | 物品或档变化 | ✅ |
| 护甲档 | 护甲总值 | `无/轻/中/重` 四档 | 跨档 | ✅ |
| 周围威胁 | 16 格内敌对实体数 | `0/1–2/3–5/6+` | 跨档 | ✅ |
| 附近实体 | 32 格内非敌对生物/玩家 | 仅 `玩家数档`（0/1/2+） | 跨档 | ✅ |
| 生命值绝对值 | `getHealth()` | —— | **不桶化，不进快照** | ❌ |
| 精确坐标 / 朝向 / 速度 | —— | —— | 每 tick 都变，禁止 | ❌ |
| 当前 tick / 系统时间 | —— | —— | 禁止（D3） | ❌ |

> 分档依据来自既有 AX 契约：背包数量按"少量/半组/一组/多组"表达，而不是要求 Presence 输出 AX 专属文本（见 `AX_辅星一期_自然交互基线设计.md` §Presence/映迹 段落）。分档是**去抖动**的核心手段：连续变化被压成离散状态，快照才能长期不变。

### 3.2 变化检测算法

```
observe(stateVector) -> SnapshotDecision:
    canonical = canonicalJson(stateVector)          // key 顺序固定、无浮点、无时间
    h = sha256(canonical)
    if h == retained.hash:                          // 与"上一次真正发送过的快照"比
        return REUSE                                  // 不追加任何消息
    return APPEND(newSnapshot(stateVector, h))

# 重要：比较对象是"上一次发送过的快照"，不是"上一 tick 的状态"
# 否则玩家在原地跳跃/走动就会不断产生新快照
```

三条补充规则：

- **R1 最小变更间隔**：同一轮最多追加一条 `T1`。一轮内多次状态变化合并成本轮结束时的最终状态。
- **R2 状态稳定的"确认滞后"**：血量在 1 轮内来回抖动（受到环境伤害后回血）时，以"轮次结束时刻"的状态为准，不做轮内多次判定。
- **R3 与检索联动**：`T1` 变化时，`T2` 的检索 query 应使用**新**快照（见 §4.1），保证同一轮内两条尾消息自洽。

### 3.3 未变化时：复用（注意"复用"的含义）

**复用 = 完全不追加消息**，而不是"追加一份一模一样的新副本"。

原因：`H` 里已经存在上一轮的 `T1`，模型看到的最新状态就是它。再追加一份相同文本，会让 miss 区无谓扩大一倍（约 +256 token），且违反 I3 的精神（无意义增长）。

```
// 正确
if (decision == REUSE) { /* 什么都不做 */ }
// 错误：看起来"复用"，实际每轮都多 256 token 的 miss
else { append(clone(previousSnapshot)); }
```

⚠ 与 I13 的边界：**REUSE 不是"丢弃"**。`H` 里已有的最近一份 `T1` 就是模型可见的最新状态；只有当"上一份快照"因压缩被遮蔽进 `C` 时，才必须在本轮重新追加一次全量 `T1`（这是 I13 要求的，不可省）。

### 3.4 变化时：追加，不替换

选择的理由与代价：

| 方案 | 前缀影响 | 模型看到的最新状态 | 历史可审计 | 结论 |
|---|---|---|---|---|
| 替换上一轮的 `T1` | 从该位置起全失效 + 位置变化 | 正确 | 被破坏 | ❌ 违反 I3 |
| 追加新 `T1` | 只从本轮 `T1` 起未命中（≈ 256 token） | 正确（最新在后） | 完整 | ✅ **采用** |

代价被明确接受（基础策略 4）：一次"状态变化"换来 256 token 的 miss，成本 ≈ 256 miss-token 当量，相对于"回写前缀导致整段重算"（四档下 34304–379904 当量，见 §5.7）是数量级更低的代价。

**频率上限**：`T1` 追加频率实测上限设为 **≤ 40% 的轮次**（语音场景下玩家多数时候不移动跨区、血量不跨档）。若实测超过 60%，说明分档过细，应收紧阈值而不是放任。

### 3.5 与 system 的边界（硬规则）

以下内容**永远不进 `S`**，只能进 `T1`：坐标/群系/血量/饥饿/等级/时段/天气/物品/护甲/威胁数/附近实体数/任何与"当前"有关的事实。

`S` 里允许存在的是：身份、行为规约、输出格式要求、安全策略、工具使用说明（未来 `S2`）。这些**全档位恒定**（I12）。

## 4. 记忆检索编排

### 4.1 位置、数量、时机

| 项 | 设计值 | 依据 |
|---|---|---|
| 放置位置 | `T2`，紧邻 `Q` 之前 | 02 §3.1：重要且易变的内容放**尾部**（recency bias 受益区），中段是垃圾场 |
| 注入条数上限 | **3 条**（硬上限 5） | 02 §2.10.4：检索文档 20→50 篇仅提升约 1.5%，recall 早已饱和；宁可少放 |
| token 预算 | `≤ 512`（`T2` 整块，**全档位相同**） | §6.3 分配表；尾部是每轮必 miss 区，不随档位放大 |
| 单条注入口 | `≤ 120 字`（2 行内） | 见 §4.5 的"检索单元 ≠ 注入单元" |
| 检索次数 | **每轮最多 1 次**，结果本轮固定 | 02 §2.6："注入的记忆集合在同一轮内不要变（不要在一次请求里检索两次）" |
| 空结果时 | 不追加 `T2`（不是追加空块） | D7 |

排序方向有一个反直觉的细节：**按分数升序排列，最高分放最后**（离 `Q` 最近）。理由是把最优证据放进 recency 受益区。这条必须与 tie-break 一起固定，否则每次重排都会改变注入字节。

### 4.2 打分公式（三因子 + 遗忘）

借鉴 Generative Agents 的线性加权（02 §2.6）与 MemoryBank 的遗忘曲线（02 §2.5），**全部本地计算、零额外 LLM 调用**：

```
# 1) recency：带记忆强度的指数衰减（MemoryBank R = e^(−t/S)）
ageHours = (now − lastRecalledAt) / 3_600_000
S        = clamp(memoryStrength, 1.0, 8.0)        // 初始 1.0，每次被召回 +1
tau0     = 18.0                                   // 小时；半个时间常数的语义尺度
recency  = exp(−ageHours / (S × tau0))            // ∈ (0, 1]，无需归一化

# 2) importance：规则近似，避免额外 LLM 调用（02 §2.6 建议）
importance_raw = ruleScore(memory)                // 1..10，见下表
importance     = importance_raw / 10              // ∈ [0.1, 1.0]

# 3) relevance：复用现成 bge-large-zh-v1.5 余弦
relevance = clamp(cosine(embed(query), embed(memory)), 0, 1)

# 4) 加权（Generative Agents 实现中 α 全为 1）
score = αr × recency + αi × importance + αv × relevance      // αr=αi=αv=1.0
```

**importance 规则表（纯本地，可配置，禁止硬编码中文文案，只给分值）**：

| 触发条件 | 分值 | 备注 |
|---|---|---|
| 含坐标 / 位置承诺（"我的家在这""矿洞入口在西北"） | 9 | 最高价值，易失 |
| 含玩家明示偏好 / 禁止项（"别动我的箱子"） | 8 | |
| 含承诺 / 计划 / 未完成任务 | 8 | |
| 含物品归属 / 已有量（"我有 20 个铁锭"） | 6 | |
| 含配方 / 机制知识询问 | 5 | |
| 普通任务指令 | 4 | |
| 寒暄 / 确认 / 语气词 | 1 | 低价值 |
| （未命中任何规则） | 3 | 默认中低 |

**遗忘（MemoryBank，02 §2.5）**——用于**淘汰与降级**，不用于改写历史：

```
retention R = exp(−ageHours / (S × tau0))         // 与 recency 同源，取同一值
if R < 0.05 and 未被召回 ≥ 30 天:  → 标记 Cold / 进入清理候选（不删除，只失效，02 §2.3）
if 被召回:                        → S += 1（上限 8），lastRecalledAt = now
```

明确**不做**的两件事（02 §2.4、§2.1）：不让记忆自我演化改写；不把记忆前置进 `S`。

### 4.3 确定性 tie-break（必须实现）

```
sort key（全部升序，最终结果按 score 升序输出，故"最好"在末尾）：
  (1) round(score, 6)          asc
  (2) importance               asc
  (3) relevance                asc
  (4) happenedAtMillis         asc      // 旧的在前
  (5) entryId                  asc      // 字典序，最终唯一锚
```

三点要求：

- 第 (5) 项保证**任何并列情形都有唯一解**，不允许"数据库自然序"充当隐式 tie-break。
- `round(…, 6)` 是 D12 的要求：未 round 的 double 在极少数情况下会因编译优化翻转比较结果。
- 去重必须在排序**之前**、按内容 hash 保留首个（D8）。

### 4.4 预算与截断

```
# 选条：按 §4.3 排好序后，从队首（低分）开始丢弃，直到总量落入预算
# 即"保高分"，而不是"保先来"
total = 0
for m in sorted_candidates:        // 低分在前
    if total + cost(m) > T2_BUDGET: drop(m) else keep(m)
# 注意：被丢弃的是低分项；这保证了高分项永远进注入
```

`cost(m) = estTokens(render_injection(m)) + 4`（每条消息 role/block 开销）。

**不允许**在单条记忆内部截断（I10）。放不下就整条跳过，并在 telemetry 记 `t2_dropped`。`T2_BUDGET = 512` 全档位固定（不随 `W` 放大）：尾部每 token 都是 1.0 单价（未命中），放大它等于线性抬升每轮成本。

### 4.5 与 `bge-large-zh-v1.5` 512 硬顶的配合（02 §6.5.2/§6.5.3）

必须区分两个长度概念，混用即出错：

| 概念 | 长度上限 | 理由 |
|---|---|---|
| **检索单元**（进 embedding 的 chunk） | **≤ 500 字**（硬上限 512，留 12 字余量） | `config.json` 的 `max_position_embeddings: 512`；中文 BERT 分词 1 字 ≈ 1 token，超出部分**静默截断**，向量失真且无报错 |
| **注入单元**（进 `T2` 的文本） | **≤ 120 字** | 每条 token 成本 × 3 条 × 每轮；也是 02 §4.4 "工具/结果要 token 高效"的同一条原则 |

落地规则：

1. **切 chunk 时就按 ≤480 字**，并且**只在语义边界切**（句末标点、事件行边界），不在句中切；单条知识超 480 字必须拆成多条 chunk 并用 `prevChunkId` 串起来。
2. **query instruction 只加在 query 上**（"为这个句子生成表示以用于检索相关文章："），passage 一律不加（02 §6.5.3）；语音输入是典型短查询，**必须加**，且上线前用真实语音转写实测确认收益。
3. **注入时用"展示摘要"而不是 chunk 原文**：chunk 承载检索精度，注入取该 chunk 的 `summaryLine`（预生成，≤120 字，稳定不变）。这样检索精度与注入成本解耦。
4. **ASR 同音错字兜底**（02 §6.5.4）：Minecraft 专有名词建别名词典 + 拼音/编辑距离兜底，走 hybrid（向量 + 精确/拼音）双路检索，而不是纯向量。纯向量在中文 ASR 噪声下最先崩（02 §3.2）。
5. **query 归一顺序固定**：原句 → 实体归一（别名词典）→ 截断到 480 字 → 加 instruction → embedding。顺序固定是 D5 的要求。

### 4.6 检索时机的取舍

| 模式 | 每轮成本 | 时效 | 结论 |
|---|---|---|---|
| 每轮必检索 | 每轮一次 embed + 检索（本地，毫秒级） | 最好 | ✅ **默认** |
| 话题固定，意图切换才检索 | 更省 | 可能拿到过期记忆 | 可选（配置项），上线 A/B 后决定 |

02 §2.2 提到"把检索结果按会话固定"是优化方向，但对语音单会话场景收益有限，先不做，留配置位。

## 5. 裁剪与压缩（compaction）

> 本节按新模型整体重写：**四档预算与水位（5.1）→ 压缩间隔（5.2）→ 触发与判定点（5.3）→ 快照点冻结（5.4）→ 切点（5.5）→
> 执行位置与响应隔离（5.6）→ 前缀复用（5.7）→ 检查点与替换语义（5.8）→ thinking（5.9）→ 失败降级（5.10）→
> 互斥与防风暴（5.11）→ 滞回（5.12）**。
> 与前版最大的差别：**压缩不再挂在轮次内同步执行，而是轮次结束后的后台 TASK 任务**。

### 5.1 四档预算：水位与保留的数值

先钉住 01 §6.5 的公式族，但**`B` 必须按 `W` 缩放，禁止沿用 DSH 的 `65536`**：

```
W  = 档位窗口（51200 / 102400 / 204800 / 512000）
O  = 512                                  // CHAT 输出预留（语音回复短，见 §6.3）
M  = W − O
B  = ceil_to_1024( clamp(0.0625 × M, 4096, 32768) )     // 余量：必须缩放
P  = M − B                                // 压力预算（硬上限，I6）
T  = floor( min(0.75 × W, P) )             // 水位（触发阈值）
R  = ceil_to_1024( 0.10 × W )              // 保留量（压缩后留下的最近历史）= 10%×W
```

**为什么 `B=65536` 是结构性错误**（不是"数值偏大"）：

- `W=50K` 时 `W − O − 65536 = 50688 − 65536 = −14848 ≤ 0` → 插件直接拒绝加载（01 §R6 的同款故障）；
- `W=100K` 时 `B` 吃掉 64% 的窗口，`P` 只剩 36352，`T` 被压到 36352，比 50K 档的水位还低；
- 它是给 128k 级窗口调的**单点常数**，而档位化产品需要的是**随 `W` 变化的函数**。

`B(W)` 的缩放规则与三点理由：

| 理由 | 说明 |
|---|---|
| 斜率 `0.0625`（1/16） | 使 `B/W` 从 8.0% 递减到 6.4%：`W` 越大，固定误差项（chat template 包装、单轮尾部估算误差、网关重试的重复记账）被摊薄，不需要等比例放大 |
| 下界 4096 | 覆盖**绝对值型**误差：chat template 附加（数百 token）、单轮尾部估算误差（≤900×20%）、一次网关重试的重复记账。这些与 `W` 无关，不能小于 4096 |
| 上界 32768 | 超过它就是浪费：`headroom` 是"用不完的容量"，`W=512000` 时 32768 已是 6.4%，再大等于给自己留 1/10 的空转区 |

四档结果（**这是本节唯一权威数值表**）：

| 档位 | `W` | `O` | `M = W−O` | `B` | `P = M−B` | `T = 0.75W` | `R = 0.10W` | `P−T`（到达水位时的空闲安全余量） | 压缩后硬目标 `T−B` |
|---|---|---|---|---|---|---|---|---|---|
| **50K** | 51200 | 512 | 50688 | **4096** | 46592 | **38400** | **5120** | 8192 | 34304 |
| **100K** | 102400 | 512 | 101888 | **7168** | 94720 | **76800** | **10240** | 17920 | 69632 |
| **200K** | 204800 | 512 | 204288 | **13312** | 190976 | **153600** | **20480** | 37376 | 140288 |
| **500K** | 512000 | 512 | 511488 | **32768** | 478720 | **384000** | **51200** | 94720 | 351232 |

`B/W` 实测：8.00% / 7.00% / 6.50% / 6.40%。`R < T` 全档位成立（5120 < 38400 …）。

**硬校验（不满足应拒绝启动该档位，不允许静默降级，01 §R6）**：

```
P > 0                          ✓ 四档全部成立
R < T                          ✓ 四档全部成立
O ≥ 1 且为显式配置              ✓ maxTokens = 512（0 视为配置缺失，直接报错）
T1 + T2 + Q ≤ 0.05 × W         ✓ 896 ≤ 2560（50K 档最紧）
W + O ≤ modelContextWindow      ← 新增：档位不得超出模型真实窗口
S ≤ S_LIMIT (4096)             ← 新增：单一 system 的容量校验（I12）
```

**同一条公式用于将来加档**（证明它是函数不是四个魔数）：

| `W` | `M` | `0.0625×M` | `B` | `B/W` |
|---|---|---|---|---|
| 65536 | 65024 | 4064 | 4096（下界生效） | 6.25% |
| 131072 | 130560 | 8160 | 8192 | 6.25% |
| 262144 | 261632 | 16352 | 16384 | 6.25% |
| 1048576 | 1048064 | 65504 | 32768（上界生效） | 3.13% |

**触发判定**（两个判定点，见 §5.3）：

```
判定点 A（轮次收尾后，后台）：shouldCompactAsync =
      pressureTokens ≥ T
   and not compactInFlight
   and turnsSinceLastCompaction ≥ cooldown(8)
   and consecutiveFailures < 3                 // 连续 3 次失败则降级，不再尝试摘要

判定点 B（构建请求前，同步）：mustTrimSync =

```

### 5.2 压缩间隔：按每轮净增 130 token 计算

`promptTokens` 的稳态增长只有两项：历史净增（≈130/轮）与本轮尾部（≤896，不进历史但计入当轮）。压缩后的落地基线是：

```
footprintAfterCompaction = S 4096 + S2 1024 + C 800 + R + 尾 896 = 6816 + R
footprintCold            = S 4096 + S2 1024 +        尾 896 = 6016      // 从没压缩过
```

| 档位 | 压缩后基线 `6816+R` | 到水位的余量 `T−基线` | **稳态复压间隔**（÷130） | **冷启动首压轮数**（`T−6016`÷130） | 600 轮会话内压缩次数 |
|---|---|---|---|---|---|
| **50K** | 11936 | 26464 | **203 轮** | **249 轮** | 2 |
| **100K** | 17056 | 59744 | **459 轮** | **544 轮** | 1 |
| **200K** | 27296 | 126304 | **971 轮** | **1135 轮** | 0 |
| **500K** | 58016 | 325984 | **2507 轮** | **2907 轮** | 0 |

三条必须写进结论的推论：

1. **在 100K 及以上档位，单次语音会话（≤300 轮）根本不会触发压缩。** 压缩从"每会话 2–4 次的常态事件"变成"50K 档或超长连续会话的罕见事件"。
2. 因此**"后台化"是零风险的**：没有需要阻塞的等待对象；同时意味着这条代码路径在生产里几乎不被走到 —— **必须提供手动触发（`/ax compact`，语义等同 DSH 的 `compactNow`，01 §7.1）**，否则崩溃注入测试与降级路径只能靠单测覆盖。
3. **净增仅 130/轮 → "水位被历史推上去"只在 200+ 轮后发生**，所以 §5.10 的溢出兜底真正防的是**单轮巨型尾部**（一次注入 2–3K）与**一次性补历史**（离线多日后的批量回填），而不是历史累积。

### 5.3 触发条件与判定点：谁检测、在哪一层检测

| 项 | 设计 | 理由 |
|---|---|---|
| **谁检测** | 单一组件 `AXCompactionScheduler`（新）。它只读三样东西：① 最近一次 `usage`（envelope 锚定后的 `promptTokens`）；② 落盘的 `turns` 与 `compactedThroughTurn`；③ 自身的冷却/失败计数 | 与 DSH 一致：压缩是**步骤边界上的监听器**，不是循环的一个阶段（01 §1.3）。AX 侧同理：不塞进装配链路 |
| **判定点 A（主）** | **轮次收尾层**：`AXTurnOrchestrator` 把 assistant 正文落盘**之后**（`appendAssistantVisibleText` 成功返回处）触发一次 `scheduler.onTurnSettled(scope)`。调度器立即返回（非阻塞），真正的判定与提交在 TASK 线程 | 必须等本轮 assistant 落盘才可能成为"已关闭轮次"，否则快照点会指向半个轮次 |
| **判定点 B（兜底）** | **请求构建前**：`AXPromptAssemblyBuilder.build()` 之前的一次同步前置检查，只判 `pressureTokens ≥ P` 并按需硬裁剪 | 硬预算（I6）不能等后台；这是唯一允许同步改历史的位置 |
| **禁止的判定点** | ① 装配链路内部（`AXPromptContributor` 里）——装配必须是纯函数、无副作用（I5）；② 每轮都算 `promptTokens` 全量重估——用 §6.2 的 envelope 锚定做 O(新增) 增量 | —— |

```
onTurnSettled(scope):
    // 轮次收尾线程，必须快速返回
    pressure = anchoredPressure(scope)                  // 见 §6.2
    if pressure < T: return
    if compactInFlight.compareAndSet(false, true) == false: 
        telemetry.compactionPendingWhileInflight = true
        return                                          // 队列深度硬上限 = 1（§5.11）
    taskLane.submit(() -> runCompaction(scope))         // TASK 车道，见 §5.6
```

### 5.4 快照点冻结（本次设计的核心不变式）

**判定一发生，就冻结，之后整个事务不再重读水位。**

```
freeze(scope) -> Snapshot:
    N              = lastClosedTurnIndex(scope)         // 最后一个"user+assistant 都已落盘"的轮次
    fromTurn       = compactedThroughTurn(scope)        // 单调水位，本事务的起点
    basePrefixHash = sha256(render(S) + render(C?) + Σ renderTurn(turns[fromTurn..N]))
    pressureAtFreeze = anchoredPressure(scope)
    return Snapshot{ fromTurn, N, basePrefixHash, pressureAtFreeze,
                     T, R, W, tier }                    // T/R/W 一并冻结：换档不影响在飞事务
```

冻结的三条强制语义：

| 语义 | 含义 |
|---|---|
| **摘要范围 = `[fromTurn .. N]`** | 只摘要这一段。`N+1`、`N+2`… 在压缩期间继续追加的轮次**不参与本次摘要**，也不受本次摘要影响（它们本来就在 keep 区） |
| **提交前必须复核** | 提交时重读 `compactedThroughTurn`，**必须等于 `fromTurn`**；否则说明水位已被其他路径推进（并发硬裁剪、另一个压缩、手动 `/ax compact`）→ **abort，丢弃摘要**，记 `compaction_aborted_superseded` |
| **换档不改变在飞事务** | 压缩期间用户换档，只影响下一次判定；在飞事务用冻结的 `W/T/R` 完成 |
| **不可分单元不可跨 `N`** | `N` 由"已落盘的完整轮次"定义（I10），从不按 token 数取整到消息中间 |

**为什么必须冻结**：压缩要发一次真实的模型调用（数百毫秒到数秒）。若提交时按"当前水位"重算范围，就会把压缩期间玩家新说的话也摘要进去——那等于**改写了刚刚发生的历史**（违反 I3），而且用户还没听到回复。冻结把"要改哪一段"提前成常量，是这个后台设计能被证明正确的唯一办法。

### 5.5 切点选择

```
selectCompactRange(turns, snapshot):
    # 1) 起点固定：S 之后的第一条（I2：system 永不被遮蔽）
    first = snapshot.fromTurn                       # 压缩后是 C 之后
    # 2) 从尾部向前累加到 R，得到保留边界（尾部固定为快照点 N，不是"当前水位"）
    keepFrom = last index such that sum(tokens[keepFrom..snapshot.N]) ≥ R
    # 3) 边界必须平衡：无未应答的 tool-call 跨越它（01 §4.5 的三行算法）
    while keepFrom > first and not toolPairingBalancedBefore(keepFrom):
        keepFrom -= 1
    # 4) 边界必须落在完整问答轮起点（I10）
    while keepFrom > first and not isTurnStart(keepFrom):
        keepFrom -= 1
    # 5) 无可压缩区间 → 什么都不写，记 noop（01 §7.2：一个字节都不写）
    if keepFrom <= first: return null
    return { from: first, to: keepFrom − 1 }        // 必须 ≤ snapshot.N
```

**不允许**的切法：按 token 数硬切（会切断轮次）、按时间切（会切出无配对的 `assistant` 回复开始）、在 `assistant.tool_calls` 与对应 `tool` 结果之间切（01 §R7）。

### 5.6 执行位置：TASK 车道，以及与聊天请求的响应隔离

**5.6.1 请求形态**（复用既有 AX 后台任务写法，见 `AXMemoryMaintenanceService.compressionRequest`）

```
LLMPromptRequestPayload(
    requestId          = "ax.compaction.summarize." + worldId + ".turn" + snapshot.N   // 稳定、可预测、可关联
  , lane               = "TASK"
  , maxTokens          = 1024                        // 摘要 ≤800 + 余量
  , temperature        = 0.2                         // 抽取任务要稳定
  , thinking           = true                        // 见 §5.9
  , captureThinkingContent = false                   // I11：不要回传推理正文
  , taskPriority       = 200                         // 低优先：晚一轮压缩无害，不许抢聊天相邻任务
  , taskPreemptible    = true                        // 可被抢占（§5.11）
  , chunks             = [ message(S), (C?), H[fromTurn..N], instruction ]
)
提交：AXLlmClient.submitDetached(payload, compactionHandler)
```

**5.6.2 为什么不会与聊天响应"串"**（必须写进代码注释）

| 机制 | 事实 | 结论 |
|---|---|---|
| 关联键 | `submitDetached` 返回 `TianshuEnvelope`；`AXLlmClient` 用 `envelopeId` 索引 `PendingRequest`，`handleResultResponse(envelope, context)` 只在 envelope 匹配时回调对应 handler | 压缩的响应只会进压缩的 handler |
| 状态隔离 | 压缩 handler 持有**独立的 `CompletableFuture`**，与 `AXTurnExecution`、`outputTurn`、`statusPublisher` 无任何共享可变状态 | 无法写进当前对话的输出流 |
| 硬禁令 | 压缩 handler **禁止**调用 `appendDisplayedText` / `outputTurn.append` / `statusPublisher.active` / `markAssistantPersisted` | 压缩永不产生面向玩家的可见内容 |
| 车道 | `lane="TASK"`；`AXLlmClient.PendingRequest.expired()` 对 TASK **直接返回 false**（即 TASK 请求不会自动超时） | 见下条 ⚠ |

⚠ **现有代码特性带来的坑（必须处理）**：因为 TASK 车道不参与 `expireAtMillis` 超时，压缩任务**必须自己加超时**，否则上游挂住就永久占住 `compactInFlight`（= 永久阻塞后续压缩）。沿用 `AXMemoryMaintenanceService.withTaskTimeout` 的写法：`future.orTimeout(12, SECONDS)` + `llmClient.cancelRequest(envelope.envelopeId(), AXTurnCancellation.expired(...))`。
> 工程要求：把 `withTaskTimeout`（含取消回收）从 `AXMemoryMaintenanceService` 抽成公共工具（`AXDetachedTask`），压缩与既有记忆任务共用一份实现——**不要复制一遍**。

**5.6.3 压缩期间 CHAT 的行为**：完全不感知。CHAT 请求照常构建、照常发出；`compactInFlight` 只被调度器读写。**唯一例外**是判定点 B 的同步硬裁剪（`pressureTokens ≥ P`），它会取消在飞压缩（§5.11）。

### 5.7 摘要请求如何复用前缀缓存

**这是"压缩成本"能否接受的分水岭。**

```
摘要请求 messages =
    [ S ]                             // 与会话真实请求逐字节相同的同一份字节（I12）
  + [ C ]  （若存在）
  + turns[fromTurn .. N] 的全部消息    // 就是 H 的头部，原样
  + [ user: COMPACTION_INSTRUCTION ]   // 唯一新增：该前缀的"真后缀"
```

四条硬要求：

1. **必须与原请求逐字节相同**，而不是"重新渲染一份看起来一样的"。实现上所有渲染都走同一份 `renderTurn(turn)` 纯函数 + 按 `contentHash` 缓存结果（`AXRawTurn.contentHash` 已存在，可直接做缓存键）。
2. **指令必须是真后缀**：只能追加在最末，不能插在 `H` 中间，不能塞进 `S`（那会改 `S`，违反 I2/I12），也不能作为第二条 `system`（§2.3.3 路径 B 已否决）。
3. **前缀恰好停在"模型输出结束"这个已持久化的 cache prefix unit 上**（02 §3.5 第 1 条：用户输入结束、模型输出结束各产出一个单元）。`S + C + H[..N]` 的末尾就是第 N 轮的 `assistant` 消息，正好落在一个单元边界 → 可全命中。只有那条指令（≈120 token）与摘要输出未命中。
4. **摘要模型必须与会话模型相同**。若为了 thinking 换到推理模型名（如 `deepseek-reasoner`），前缀缓存跨模型不共享 → **命中归零**，代价见下表。

**命中的成本含义**（`实测一次压缩的输入成本`）：

| 情形 | 输入成本 | 说明 |
|---|---|---|
| 同模型 + 真后缀（目标形态） | `Ctx × 0.02 + 120` miss-token 当量 | 500K 档：`384000×0.02+120 ≈ 7800` |
| 放弃前缀复用（换模型 / 非头部范围） | `Ctx` miss-token 当量 | 500K 档：`384000` ≈ **45 个稳态轮的成本** |

即：**复用成功时压缩的输入成本只有不复用时的 1/50**。这一条决定了 §5.9 的 thinking 策略必须优先"同模型 + 推理开关"，而不是"换模型"。

### 5.8 检查点形态与替换语义

**5.8.1 产物：一条 `user` 消息**（选 `user` 而非 `system` 的理由见下）

```
<context_checkpoint turn_from="{snapshot.fromTurn}" turn_to="{snapshot.N}">
{摘要正文}
</context_checkpoint>
```

摘要正文的生成要求（写进压缩用的 instruction）：

1. **必须包含**：已确定的事实（位置、归属、偏好、承诺）、未完成的任务与进度、玩家明确要求过的事。
2. **必须丢弃**：寒暄、重复确认、已被后续事件推翻的状态（血量/坐标这类会变的绝不写入摘要，它们属于 `T1`）、**以及任何 thinking/reasoning 正文（I11）**。
3. **长度**：`≤ 800 token`（`C` 的槽位预算），且必须 **≤ 被遮蔽区域的 50%**（否则拒绝，见 §5.10）。
   ⚠ 四档制下这条约束会变紧：`R` 为 5120–51200 后，一次遮蔽的跨度可达 200+ 轮（§5.2），
   而 800 token ≈ 1300 汉字要覆盖这 200+ 轮。**若实测摘要频繁触顶或频繁 `NotShrinking`，
   要动的是 `C` 的槽位预算，不是 `R`**——`R` 影响的是"保留多少原文"，`C` 影响的是"压进去多少"。
4. 文案里必须有 **"不要复述、不要确认这段摘要"** 的指令——否则模型下一轮会把摘要重复一遍，白花 token（01 §7.3 三个设计点之一，值得直接照抄）。
5. 摘要正文**另存**（`compaction/summary` 事件），`C` 里的框定只是模型可见视图；原始轮次一个都不删（I7）。

`turn_from`/`turn_to` 只用整数序号，**禁止写时间戳**（D3）。

**5.8.2 提交语义：一条 checkpoint 替换 `[fromTurn..N]`，其余一个字节不动**

```
commit(snapshot, summary):
  1) 复核：compactedThroughTurn(scope) == snapshot.fromTurn                        否则 abort(superseded)
  2) 复核：tokens(summary) ≤ min(800, 0.5 × tokens(turns[fromTurn..snapshot.N]))    否则 abort(NotShrinking)
  3) 复核：summary 正文非空                                                        否则 abort(empty) 
  4) 追加事件（append-only，永不改写旧事件）：
       compaction/start   { fromTurn, toTurn = snapshot.N, basePrefixHash, W, T, R, tier, model, lane }
       compaction/summary { text, tokens }
       compaction/end     { checkpointId, outcome=summarized }
  5) 推进水位：compactedThroughTurn = snapshot.N + 1（单调递增，永不回退）
  6) 不变量：turns 文件一个字节都不改；turns[snapshot.N+1..] 全部原样；S 原样
```

模型可见视图的执行结果：

```
[S] + [C] + H[N+1 .. ] + T1/T2/Q
```

**5.8.3 失效范围：不是"从第 1 个 token 起"，而是"从 `C` 起"**

| 项 | 值 |
|---|---|
| 失效起点 | `C` 的第一个字节（因为 `S` 逐字节未变，`S` 段仍命中） |
| 失效 token 数 | `Ctx − len(S)`（水位处：38400−4096 … 384000−4096） |
| 四档数值 | 34304 / 72704 / 149504 / 379904 miss-token 当量 |
| 折合稳态轮数 | 20.6 / 29.8 / 37.6 / 44.3 轮 |
| 摊销到每轮（按 §5.2 稳态间隔） | **+10.1% / +6.5% / +3.9% / +1.8%** |

> 前版写"从 `messages[0]` 起全 miss 一次"是照搬 DSH 的表述。精确结论是 `S` 仍命中——这只是省了 ≤4096 token，但它是 I12 的直接红利，也让"摊销后的压缩开销"有一个诚实上限：**最坏 10%**（50K 档），最好 1.8%（500K 档）。

**5.8.4 为什么 `C` 用 `user` 角色**

① `S` 必须唯一且在最前（I2），插第二条 `system` 会引入 §2.3.3 路径 B 的兼容风险；
② `C` 本质是"对历史前段的替代陈述"，`user` 角色语义上成立，且所有 OpenAI 兼容实现都接受历史里的 user 消息；
③ 用 `user` 可以让 `C` 与 `H` 处于同一角色流，避免网关对连续同角色消息的合并策略差异。

### 5.9 thinking：开启，而且只在后台

| 项 | 值 | 说明 |
|---|---|---|
| `thinking` | **开启**（强度可选，默认最低档） | 基础策略 3；强度做成与 DSH 一致的面板项 |
| `captureThinkingContent` | **false** | I11：只要正文，不要推理内容回传 |
| 对成本的影响 | 输出从 ≤800 升到 ≤1024 预留 | 每次压缩 ≤1024 输出 token；按稳态间隔 203–2507 轮摊销，等于 **5–0.4 输出 token/轮**，可忽略 |
| 对延迟的影响 | 单次压缩从 ~1s 升到 ~2–4s | **用户无感**：TASK 车道后台执行，CHAT 不等待它 |
| 硬约束 | 必须与 `maxTokens=1024` 联立。thinking 会消耗 completion 预算，`maxTokens` 太小会让正文被截断 | 若实测正文经常被截断，说明该降 thinking 强度而不是提高 `maxTokens`（否则摘要成本失控） |

⚠ **现状约束**：云端 `OpenAiCompatibleInferenceClient.supportsThinking()` 返回 `false`（`LlmRuntimeInspector.supportsThinking` 透传）。若 provider 无法按请求切换 thinking，只能换模型名（DeepSeek 侧 `deepseek-reasoner` 一类）——**此时必须显式记账 `prefix_reuse_lost = true`**（§5.7 表格第二行）。这笔账可以接受：500K 档一次放弃复用 = 384000 当量 ≈ 45 轮稳态成本，而该档压缩间隔 2507 轮 → 摊销仍 < 2%。但**必须先把"同模型"路线试掉**。

### 5.10 失败路径与降级

优先级：**摘要压缩 > 硬裁剪（无摘要） > 靠估算硬发 > 溢出恢复**。

```
runCompaction(scope):
  snapshot = freeze(scope)                     // §5.4，失败即返回并释放 compactInFlight
  try:
     range = selectCompactRange(turns, snapshot)
     if range == null: → 记 noop，直接走同步硬裁剪判定（可能是不可分单元撑爆，01 §R8）
     summary = summarize(range)                // TASK 车道，thinking 开，超时 12s
     if tokens(summary) > min(800, 0.5 × tokens(range)): 抛 NotShrinking
     commit(snapshot, summary)                  // §5.8.2；内部含 superseded 复核
  catch 超时/网络/取消/NotShrinking/其它:
     记 compaction_failed(reason, attempt = k)
     保留原历史（一个字节都不动）→ 排下次判定：
        k = 1 → nextEligibleTurn = N + 3
        k = 2 → nextEligibleTurn = N + 10
        k = 3 → compactionDegraded = true；此后只走 hard_drop，直到水位回落到 T−B 以下
  catch superseded:                             // 水位被别的路径推进了
     静默丢弃摘要，记 compaction_aborted_superseded，不重试、不计失败
  finally:
     compactInFlight.set(false)                // 必须无条件释放
     记 compaction_flag ∈ {none, summarized, hard_drop, noop, failed, superseded, ineffective}

hard_drop（只在 compactionDegraded 或判定点 B 触发）:
   丢弃 [compactedThroughTurn .. N'] 的完整轮次，不写 C；
   要求丢弃后 promptTokens ≤ T − B（= P），且至少保留最近 4 轮；
   触底仍超 → 走溢出通道
   推进 compactedThroughTurn = N' + 1；写 compaction/hard_drop 事件

onProviderError(CONTEXT_WINDOW_EXCEEDED):        // 溢出兜底（01 §7.1 特权路径）
   绕过水位与冷却，立即 HARD_DROP 25% 的现有历史（保留最近 4 轮），只重试 1 次；
   仍失败 → 向玩家回退一句"这轮信息太多了"（走既有输出通道，不在 prompt 里解释机制），
   并记 overflow_unrecovered 告警。
```

**锁与崩溃可检测**（01 §7.4）：`compaction/start` 写在 `checkpoint` 落盘**之前**，`compaction/end` 写在**之后**，两次都不带任何 surface 语义，只作日志标记。未闭合的 `start` 即为"忙"信号；跨会话遗留的 `start`（其 `sessionId` 不是当前进程）在会话恢复时清除并记 `stale_compaction_lock`。顺序若反了，崩溃就变成"历史已改但无人知晓"。

### 5.11 互斥与防压缩风暴

**5.11.1 三道互斥闸**（防并发重复压缩）

| 闸 | 机制 | 拦住的情形 |
|---|---|---|
| ① 单飞标志 | `compactInFlight` per-scope `AtomicBoolean`，`compareAndSet` 抢占；`finally` 无条件释放 | 同一 scope 同时起两个压缩 |
| ② 提交前复核水位 | `compactedThroughTurn == snapshot.fromTurn`，否则 abort | 在飞期间被同步硬裁剪或手动压缩推进了水位 |
| ③ 检查点合并校验 | 新 checkpoint 的 `turn_from` 必须等于提交时的 `compactedThroughTurn`，且 `turn_to ≤ snapshot.N` | 两个压缩试图覆盖重叠区间 |
| ③' 跨进程 | `compaction/start` 未配对存在 + 其 `sessionId` 属于历史进程 → 不清除则拒绝启动压缩（stale 判定见 §5.10） | 上次进程崩溃遗留的锁 |

**5.11.2 压缩期间又越过水位：如何避免风暴**

```
if (compactInFlight == true && pressure ≥ T):
    不排队第二个任务（队列深度硬上限 = 1，永远）
    只记 compaction_pending_while_inflight = true
    下一次判定点是"本次提交后的下一轮收尾"，不是现在

提交后回看：
    if (pressureAfterCompaction > T − B):
        记 compaction_ineffective
        nextEligibleTurn = N + 8               // 不为"没效果的压缩"立刻再来一次
        // 说明摘要太大或保留量 R 相对于该档位过肥 —— 先查 summary tokens，不要先调冷却
```

**5.11.3 三条风暴护栏**

| 护栏 | 值 | 作用 |
|---|---|---|
| 并发度 | 同 scope 同时 ≤ 1 个压缩事务 | 从根上不允许并发 |
| 频率上限 | 连续两次压缩起点之间 ≥ **8 轮**（失败重试的冷却另计，见 §5.10） | 防"压完立刻又压" |
| 收益下限 | 一次压缩必须让 `promptTokens` 减少 ≥ `max(2048, 0.10 × R)` 且摘要 ≤800；否则记 `ineffective` 且**不推进水位** | 拒绝"压了等于没压"的死循环 |

**5.11.4 硬预算永远优先**：若压缩期间 `pressureTokens` 涨到 `≥ P`（判定点 B），同步硬裁剪立即执行，并 `cancelRequest` 取消在飞压缩；在飞压缩提交时因 ② 复核失败而 abort。**优雅压缩给硬预算让路，这是无条件的。**

> 边界成立的现实基础：净增仅 130/轮，而稳态复压间隔为 203–2507 轮，压缩期间（≤12s）增长越水位的概率极低。这条边界真正防的是**单轮巨型尾部**与**离线多日后的一次性历史回填**。

### 5.12 水位的滞回（防抖）

| 机制 | 值 | 作用 |
|---|---|---|
| 压缩后硬目标 | 压缩结束必须使 `promptTokens ≤ T − B`（四档：34304 / 69632 / 140288 / 351232），否则记 `ineffective`（01 §7.6："拒绝不缩小源内容的摘要"） | 保证压缩真有效 |
| 冷却 | 一次压缩后至少 **8 轮**不再检查水位 | 防连续压缩 |
| 失败退避 | 3 轮 / 10 轮 / 降级（§5.10） | 摘要通道不可用时不反复烧钱 |
| 粗粒度切点 | 切点对齐到**轮次边界**，且必须是 4 的倍数轮（便于与将来的分组/tool 批对齐） | 减少"差一点又要压" |

## 6. token 预算

### 6.1 估算方法：中文与英文分开

**先钉死事实**：`4 chars/token` 用于中文会严重低估（01 §R1，DSH 官方自述 "CJK 文本与 JSON schema 在每 token 四字符下严重低估"）。02 §6.5.1 给了官方换算：**1 汉字 ≈ 0.6 token、1 英文字符 ≈ 0.3 token**。换算成"每 token 字符数"：

| 文本 | 官方 token/字 | 等效 chars/token | 相对 4 chars/token 的偏差 |
|---|---|---|---|
| 纯中文 | 0.6 | **1.67** | 低估 **2.4×** |
| 纯英文 | 0.3 | 3.33 | 高估约 20% |
| 中文 + 标点 + XML 标签 + 数字 + 术语（本场景典型） | —— | —— | 低估常达 **3× 以上**（标点/符号单独计 token，标签名按子词切） |

所以估算器必须按字符类别分开算，不能用一个常数：

```
estimateText(text):
    cjk   = countCodepoints in [U+3400–U+4DBF, U+4E00–U+9FFF, U+F900–U+FAFF,
                               U+3000–U+303F, U+FF00–U+FFEF]        // 汉字/扩展/兼容/中文标点/全角
    other = totalCodepoints − cjk
    return ceil(0.62 × cjk + 0.30 × other)
    // 0.62 而非 0.60：向上偏置 3% 作安全边际（预算宁高勿低）

estimateMessage(role, content):
    return estimateText(content) + 4 /* block */ + 4 /* role */        // 01 §6.1 的 overhead 常数

estimateTools(toolsJson):
    return ceil(0.30 × length(toolsJson)) + 4                          // JSON 子词切分，按英文字符计
```

### 6.2 校准：用 provider usage 把误差归零

01 §6.3 的锚定机制值得整套照搬——**估算器可以粗糙，只要每隔几步能用真值纠偏**：

```
# 每 (model, lane) 维护一个校准系数 k，初始 1.0
收到 usage 后：
    if actualPromptTokens ≥ 1024 and estimatePromptTokens > 0:
        k_obs = actualPromptTokens / estimatePromptTokens
        if 0.7 ≤ k_obs ≤ 4.0:                  // 越界视为异常（截断/统计口径变化），丢弃
            k = clamp(0.8 × k + 0.2 × k_obs, 0.8, 3.5)     // EMA α = 0.2
            持久化 k（按 model×lane）

前瞻估算：estimateUsed = ceil(estimateRaw × k)
```

**envelope 锚定**（省掉全量重估，并让"历史只增长"这件事变成 O(新增) 的增量计算）：

```
若 (model, maxTokens, thinkingFlag, toolsHash) 与上次 usage 报告完全一致：
    pressureTokens = lastActual.prompt_tokens + Σ estimateUsed(新增消息)
否则：
    pressureTokens = estimateUsed(全部消息) + estimateTools(tools)
```

三点纪律：

1. **只采纳"不低于估算"的真值做基线**（01 §6.3 第 2 条）。这条防御挡的是 provider 少报导致预算被低估、进而溢出。
2. 同一轮的重试会贡献**另一次**计费用量，所以"轮次用量 ≠ 单次请求用量"（01 §R9）。
3. 估算值只做前瞻决策，**不得用于账单或对外结论**（I8）。

### 6.3 四档的槽位分配表

`S`/`S2`/`C`/尾块**四档完全相同**（I12 + 尾部成本纪律）；唯一变化的是 `H` 的可用量。

| 槽位 | 四档共同值 | 占 `T` 比例（50K / 100K / 200K / 500K） | 说明 |
|---|---|---|---|
| `S` system | **≤ 4096**（`S_LIMIT`） | 10.7% / 5.3% / 2.7% / 1.1% | 单一、字节冻结（I12）；在命中区，加大几乎不增成本 |
| `S2` tools（未来） | ≤ 1024 | 2.7% / 1.3% / 0.7% / 0.3% | 系列内恒定 |
| `C` 检查点 | ≤ 800 | 2.1% / 1.0% / 0.5% / 0.2% | 仅压缩后存在 |
| 尾块 `T1+T2+Q` | ≤ 896（T1 256 / T2 512 / Q 128） | 2.3% / 1.2% / 0.6% / 0.2% | **每轮必 miss**，故全档位不放大 |
| `H` 可用上限（无 `C`）= `T − 6016` | — | **32384 / 70784 / 147584 / 377984** | 84.3% / 92.2% / 96.1% / 98.4% of `T` |
| `H` 可用上限（有 `C`）= `T − 6816` | — | 31584 / 69984 / 146784 / 377184 | |

三条分配纪律：

- **预算上限，不是填充目标**。`P` 是天花板、`T` 是触发器，实际 prompt 通常远低于两者（02 §6.2 的同一原则）。
- **尾块 ≤ 900 是全档位硬指标**，且小档位更敏感（§2.2 的退化表：50K 档尾部翻倍直接砍半成本优势）。
- **`Q` 不是预算矛盾**：语音输入一般 50–100 token，完整保留，不做截断（截断输入是产品错误，不是优化）。
- **档位放大不放大槽位**：`W` 从 50K 涨到 500K 只增加 `H` 的可用量，`S/S2/C/尾` 一律不变。这是 I12 在预算层的投影。

### 6.4 每轮费用对比（miss-token 当量）

公式（用户给定的口径，与 §2.2 一致）：

```
每轮成本 ≈ miss 区(~900) + 当前上下文 / 50
1 个命中 token = 0.02 miss-token 当量（02 §0.1：命中价 = 未命中的 1/50）
```

三个运行点：**压缩后低点**（`6816+R`）、**中位**（低点与水位的中点）、**水位处**（`T`）。

| 档位 | 上下文@低点 | 上下文@中位 | 上下文@水位 | 成本@低点 | **成本@中位** | 成本@水位 | 相对 100K 中位 | 实际折扣 vs 全 miss（水位处） |
|---|---|---|---|---|---|---|---|---|
| **50K** | 11936 | 25168 | 38400 | 1139 | **1403** | 1668 | 0.76× | 1/23.0 |
| **100K** | 17056 | 46928 | 76800 | 1241 | **1839** | 2436 | 1.00× | 1/31.5 |
| **200K** | 27296 | 90448 | 153600 | 1446 | **2709** | 3972 | 1.47× | 1/38.7 |
| **500K** | 58016 | 221008 | 384000 | 2060 | **5320** | 8580 | 2.89× | 1/44.8 |

**为什么大档位成本近似线性增长**：`成本 = 900 + Ctx/50` 是一条**截距 900、斜率 1/50 的直线**。截距（尾部 miss 区）是常数，不随档位变；斜率是常数，所以**档位之间的成本差严格等于上下文差 ÷ 50**：

| 跨档 | `ΔCtx`（中位） | `ΔCtx/50` | 实测 `Δ成本` |
|---|---|---|---|
| 50K→100K | 21760 | 435 | 1839−1403 = **436** ✓ |
| 100K→200K | 43520 | 870 | 2709−1839 = **870** ✓ |
| 200K→500K | 130560 | 2611 | 5320−1839−870 = **2611** ✓ |

三点结论：

1. **边际成本恒定**：多装 1 token 上下文，每轮固定多花 0.02 当量。大档位不是"更贵一点点"，而是**按装载量线性计费**。
2. **截距被摊薄**：50K 档中位成本里 900/1403 = 64% 是固定截距（尾部 miss + 常数项），500K 档只占 17%。所以**小档位的成本几乎与"用了多少历史"无关**（它主要在为每轮尾部付钱），大档位的成本几乎全部由历史规模决定。
3. **折扣上限是 1/50，实际拿不满**：尾部 miss 区把实际折扣压到 1/23–1/45。这正是 02 §6.7 第 6 条要求"必须算清这个账"的量化答案。

**折算成钱的参考**（按 02 §0.1 的 `$0.3/M` 未命中单价；单价变动时按比例缩放）：

| 档位 | 每轮（中位） | 每 20 轮 | 每 200 轮 | 600 轮连续会话（中位成本 + 1 次预热） |
|---|---|---|---|---|
| 50K | $0.000421 | $0.0084 | $0.084 | **$0.264** |
| 100K | $0.000552 | $0.0110 | $0.110 | **$0.354** |
| 200K | $0.000813 | $0.0163 | $0.163 | **$0.534** |
| 500K | $0.001596 | $0.0319 | $0.319 | **$1.073** |

### 6.5 缓存过期风险：重新预热的一次性成本

DeepSeek 的前缀缓存是 **best-effort**，且"不用后数小时到数天"清理（02 §3.5）。闲置后回来，**整个上下文变成 miss**：

```
预热成本 = Ctx（全部按未命中计）
折合稳态轮数 = Ctx / (900 + Ctx/50)        // 理论上限 = 50 轮
```

| 档位 | 预热成本@水位（当量） | = 多少稳态轮 | 折合美元@水位 | 占 20 轮会话总成本 | 占 50 轮会话总成本 |
|---|---|---|---|---|---|
| **50K** | 38400 | **23.0 轮** | $0.0115 | **53.5%** | 31.5% |
| **100K** | 76800 | **31.5 轮** | $0.0230 | **61.2%** | 38.7% |
| **200K** | 153600 | **38.7 轮** | $0.0461 | **65.9%** | 43.6% |
| **500K** | 384000 | **44.8 轮** | $0.1152 | **69.1%** | 47.2% |

**对断续游玩场景的三个判断**：

1. **大档位的成本由"预热"决定，而不是"稳态"**：每段 20 轮、中间歇几小时的游玩模式下，500K 档有 **69%** 的输入花费在重新预热上，只有 31% 花在真正有用的推理上。而且它与"玩家说了多少话"完全无关——纯粹是"上次留下的缓存还在不在"。
2. **打平点**：会话长度必须超过 **23–45 轮**（随档位递增），预热成本才低于该会话的全部稳态成本。**50K 档 23 轮就打平，500K 档要 45 轮**。所以：
   - 断续游玩（每段 < 30 轮）→ **必须用 50K 或 100K**；
   - 200K/500K 只在"连续玩一小时以上（> 300 轮）"时才划算。
3. **这是"档位 = 成本档"而不是"档位 = 能力档"的根本原因**：模型能力不随档位变（`S` 相同，I12），只有"装载量"变。装载量大在断续场景下是纯粹的负担。
   **工程要求**：每轮记录 `cacheWarmEvent = (cacheHitTokens == 0 && promptTokens ≥ 8192)`，单独统计——它是"档位选错"的最直接信号（§7.4）。

> 可选优化（需拍板，见末节）：会话前 N 轮用低档、确认会话够长后**自动升档**。因为档位只改 `T/R/P`、不改 `S`（I12），**升档是零缓存代价的** —— 这是本次决策带来的一个新自由度。

### 6.6 首 token 延迟的定性影响

延迟模型（定性，系数需实测）：

```
TTFT ≈ a（网络+排队+首层调度） + b × miss_tokens + c × total_tokens
       命中省掉的是 b 项（prefill 算力），省不掉 c 项（KV 读取 + 逐层注意力对上下文的扫描）
```

四条判断：

1. **命中缓存不等于零延迟**。即使 `hit_ratio = 1.0`，服务端仍要把整段 KV 拉起来、每层仍要对全部上下文做注意力。`c × total_tokens` 这一项随档位单调增长。
2. **档位之间的延迟差在"未命中"时才明显**。命中时差距来自 `c` 项（较小但不可忽略）；未命中时 `b × Ctx` 在 500K 档是秒级量级——这就是 §6.5 的预热在延迟上的同一次代价。
3. **语音场景的阈值**：`first_token P50 ≤ 800ms`（thinking 关）在 50K/100K 档立项验收；200K/500K 档放宽到 **≤ 1200ms** 并标注"待实测标定 `b`/`c`"。若实测超标，**降档位比调任何参数都有效**（因为 `c × total_tokens` 是唯一随档位变化的项）。
4. **压缩不进入这条链路**（§5.6）：压缩时的 thinking 只抬高压缩自己的时长，CHAT 的 TTFT 不受影响。验收口径：压缩进行中的 CHAT `firstTokenMs` 增量 P95 ≤ **+50ms**（只是 TASK 车道并发带来的服务端排队，不应有本地的额外开销）。

### 7.3 "策略有效"的判据（数值化）

| 判据 | 阈值 | 说明 |
|---|---|---|
| **稳态命中率** | 滚动 20 轮 `hit_ratio ≥ 0.90`（目标 0.95），**按 `contextTier` 分组统计** | 仅统计 `promptTokens ≥ 8192` 的轮次；短会话（<8K）命中率天然低，不纳入验收 |
| **system 字节冻结** | 全档位、全系列内 `systemHash8` 变化次数 = **0**（I12） | 变一次即缺陷，不是优化项 |
| **档位无关性** | 同一 `seriesId` 内 `systemHash8` 与 `contextTier` 的相关系数 = 0（即换档不换 hash） | 这是 §9 缺陷 T 的迁移回归信号 |
| **意外前缀破坏次数** | 每会话 `prefixBreak` ≤ `compaction次数 + 1`（+1 = 会话起点）。**换档不计入 prefixBreak** | 多出来的每一次都要能定位到具体原因 |
| **估算精度** | 前 5 轮后 `\|est−actual\|/actual` 的 P50 ≤ 10%，P95 ≤ 20% | 校准机制是否生效 |
| **尾块守门** | `tailTokens` P95 ≤ 900（按档位分组；50K 档 P99 也 ≤ 900） | 守住 §2.2 的成本折扣 |
| **压缩有效** | 每次压缩后 `≤ T − B`；摘要 token ≤ `min(800, 遮蔽区 50%)` | 拒绝"压了等于没压" |
| **压缩不阻塞轮次** | 压缩进行中的 CHAT `firstTokenMs` 增量 P95 ≤ **+50ms**；压缩 `Ms` P95 ≤ 12s（超时即降级） | 后台化的核心验收 |
| **压缩频率** | 冷启动首压轮数 ≥ 表值（§5.2）的 **80%**；稳态复压间隔 ≥ 表值的 **50%** | 实测更早 → 尾部膨胀，先查 §2.2，不要先调 `R` |
| **成本** | 每轮 miss-token 当量 P50 ≤ 该档中位值 × 1.15（即 ≤ 1613 / 2115 / 3115 / 6118） | §6.4 的直接守门 |
| **预热** | 每会话 `cacheWarmEvent` ≤ **1** 次（一次进入）；> 2 次 = 会话反复失效，先查网关/连接生命周期 | §6.5 |
| **延迟** | `firstTokenMs` P50 ≤ 800ms（50K/100K，thinking 关）；≤ 1200ms（200K/500K，待实测） | 语音体验底线 |
| **检索有用性** | ≥ 60% 的轮次 `t2Items ≥ 1`；`t2TopScoreMilli` P50 ≥ 450 | 长期低于此说明检索链路无效，不如关掉省 token |

### 7.4 告警规则（反例阈值）

| 触发 | 结论（第一条怀疑对象永远是这个） |
|---|---|
| 命中率骤降到 < 0.5 | **有人在改前缀**：`game_context` 又进了 `S`、分区排序抖动、装配非确定 |
| `systemHash8` 在系列内变了 | 配置热更绕过了"开新系列"，或单一 system 里混入了动态内容（I4/I12） |
| **`systemHash8` 与 `contextTier` 相关** | **三档选择逻辑没删干净**（§9 缺陷 T 的专属回归信号） |
| `promptHash8` 两次相同输入不相等 | 确定性规则 D1–D13 有遗漏 |
| `tailTokens` 持续 > 1200 | `T1` 分档过细或 `T2` 未做摘要化（50K 档最先崩，见 §2.2） |
| `cacheWarmEvent` 频繁 | 断续游玩 + 档位过高；或连接/网关在重建会话。考虑降档（§6.5） |
| `compactionDegraded = true` | 摘要通道连续 3 次失败：查 thinking 支持、provider 报错、`S` 是否超限 |
| `prefixReuseLost` 频繁 | 压缩被路由到了别的模型名（§5.7/§5.9） |
| `hitRatio` 高但账单没降 | 输出 token 或 TASK lane 占比过高，查 `outputTokens` 与压缩频率 |

### 8.1 function calling（工具调用）

**已预留**：

- 协议层已有 `LLMPromptRequestPayload.toolsJson` 字段（`LLMPromptRequestPayload.java:30`），AX 目前传 `null`。

- `tool` 角色消息天然落入 `H` 的 append-only 语义，无需新机制。

**设计规则**：

| 项 | 规则 |
|---|---|
| 工具定义位置 | `S2`，**并入 `S` 之后、紧随其后**；序列化 key 顺序固定、按工具名 code-unit 排序（D2/D4） |

| 结果精简 | **源头精简**：工具返回结构化摘要，单条结果 `≤ 400` token（02 §4.4/§5.2："在源头让工具结果就小，比事后裁剪便宜一个数量级"） |
| 对裁剪的影响 | `tool-call`/`tool-result` 是**不可分单元**（I10）；切点必须通过配对平衡校验（§5.5 第 3 步）。工具结果**不做每轮裁剪**，只在压缩时一次性处理（02 §3.3 的 P0/P1 划分） |
| 轮数守卫 | **必须新增**：单轮最多 6 次工具往返、单轮挂钟 ≤ 20s，超限强制收尾（01 §R13：DSH 都没有内置轮次预算，MC 里一个循环挖矿能吃满服务器） |
| thinking | 工具回合可用最低档 thinking（与压缩同一档），CHAT 纯对话仍关 |

**还需扩展**：`AXLlmPromptRequestBuilder` 增加工具装配入口；`LLMPromptRequestPayload` 的流式解析要能读 `tool_calls` 增量（当前 `OpenAiChatStreamParser` 只解析 `delta.content`/`delta.reasoning_content`）；会话内需要一张"待应答工具调用"表来支撑 §5.5 的配对校验。

### 8.2 后台任务

**已不再"预留"**：压缩本身就是第一个后台任务（§5.6），TASK 车道的 `submitDetached` + `AXLlmRequestHandler` + `taskPriority`/`taskPreemptible` + `orTimeout` 回收这套模式已经在用。
