**术语**（本文固定，全文不再解释；与 03/记忆同名者标"沿用"）：

| 记号 | 含义 |
|---|---|
| `AgentLoop` | **唯一的**循环实现。一个循环 = 一串"模型请求 → 解释输出 → 决定下一步"。它本身不含任何业务语义 |
| `RunPolicy` | 循环的**策略参数集**（步数上限、时长上限、终止条件、是否允许工具）。本文只有两种：`SIMPLE` / `COMPLEX` |
| **Run** | 一次 `AgentLoop` 执行实例。一次 Run 有独立上下文（自己的一组消息），生命周期结束即丢弃 |
| **主对话 Run** | `SIMPLE` Run，跑玩家可见的那一轮对话。**不再发 `tools[]`**（§4） |
| **Complex Run** | `COMPLEX` Run，跑一次异步委派任务。**只允许带检索类工具**（§7） |
| **Ticket** | 一次委派的凭据（`taskId`）。它在主对话侧是"欠玩家一个答案"的记录，在后台侧是"一次 Complex Run" |
| **事件线**（event line） | 会话级的**本地登记簿**：委派结论、失败、超时、取消各登记一条终态记录。它是"投递"的载体，**不等于 prompt 里的字节，也不等于播报**（§6.1） |
| ~~`delegateKey`~~ **（v2 已取消）** | 原委派幂等键。**D2 删除**：重复提问由**记忆召回**天然解决（§5.4）；只保留"同会话 **5s** 内相同 `query` 复用结果"的极小防护 `replayKey`。它与记忆文档 §10 G7 的 `idempotencyKey` 仍是两个不同对象（A9） |
| **投递 / 进 prompt / 播报** | 三个**互相独立**的通道：① 登记进事件线（必达，A4）② **`<event>` 追加进历史**（`world_event` 角色消息，**发生即写一次**；**⚑ v4/F1：不再是 `T3` 里每轮重建的块**，因此**不受 896 尾部预算约束**，改受历史容量与压缩约束）③ 出声（受播报门槛约束）。**三者不可互相替代**（§6.1） |
| **事件** vs **状态**（v4/F2） | **事件** = 有发生时刻的**变化**（一次发生、有先后、可计数）→ 走 `<event>`，**追加进历史**；**状态** = 无发生时刻的**当前事实**（可重复观测、幂等）→ 走 `T1`，**每轮重建、不进历史**。分界判据见 §6.3；档位、冷却与聚合归事件 §4–§8 |
| **尾块** | `T1` / `T2` / `Q`，合计 ≤ 896（沿用 03 §6.3、附录 A.2）。**⚑ v4/F1：`T3` 已空置**（`<event>` 改为历史条目）；**896 上限与 `T3` 的 300 预留位本文都不动**，回收归 03 再版 |

### 1.3 本文的不变量（A1–A10，违反即为设计缺陷，不是取舍）

| ID | 不变量 | 违反后的可检测信号 |

| **A2** | **委派不回传原始材料**：跨 Run 边界只允许「≤3 句结论 + 可选来源」通过；原始材料留在 Complex Run 自身上下文内，任务结束即丢弃 | 事件线上出现长于 3 句的正文，或出现网页/文档片段 |
| **A3** | **主对话无工具**：主对话请求**不带 `tools[]`**（`toolsJson = null`），其历史里 `tool_calls` / `tool` 消息计数**恒为 0** | 主对话 payload 出现 `tools`；`H` 里出现任何 `tool` 消息 |
| **A4** | **投递必达**：每个 ticket 在事件线上留下**恰好一条**终态记录（成功/失败/超时/取消），不因播报门槛、预算裁剪或会话空闲而丢弃 | `tickets − delivered ≠ 0` |
| **A5** | **状态与检索不进历史；事件必进历史**（**⚑ v4/F1 改写**）：`T1/T2`（及空置的 `T3`）是**一次性注入**；`H` 只追加两样 —— ① assistant 的**最终正文**（03 I3 在运行期的执行口径）② **`<event>` 历史条目**（`world_event` 角色，**发生即写一次、不每轮重建**；来源含委派终态与游戏内事件，§6.3） | ① `H` 里出现状态快照 / 检索块的原文；② `<event>` 缺失（`emitted − appended ≠ 0`）；③ `<event>` 出现在尾部块里、或被每轮重建 |
| **A6** | **禁止嵌套**：`COMPLEX` Run 内不得再发起委派（不得再起第二个 `COMPLEX`）；同理主对话 Run 内不得同步起 `COMPLEX` | Complex Run 的上下文里出现 ticket 创建 |
| **A7** | **单 ticket 单 run**：一次委派只对应一次 Complex Run。**唯一允许的复用**是"同会话 5s 内相同 `query`"（`replayKey`，§5.4）；窗口之外一律新建 ticket 与新的 Run | 5s 窗口内同一 `query` 出现两个 Run 记录（**窗口外出现新 Run 是正常行为，不算违反**） |
| **A8** | **上限闭集**：`SIMPLE`(3 步/10s) 与 `COMPLEX`(25 步/120s) 的参数是闭集，**调用方不得覆盖** | 出现第 4 个 policy 或运行时改写上限 |
| **A9** | **委派不做键级去重**：本文**没有** `delegateKey`（v2 取消，D2）。去重只靠 ① 记忆召回 ② 同会话 5s 的 `replayKey`。记忆 §10 G7 的 `idempotencyKey`（压缩重放）**不得**被委派链路读取或复用字段名 | 委派代码里出现"问题正文 → 键"的哈希表；或委派读记忆的批次键；或两个键写成同一字段名 |
| **A10** | **结论自足**：投递的结论必须能脱离 Complex 上下文读懂（不出现"如上所述""该页面第 3 节"这类指代） | 投递正文含指代词/引用编号 |

> A2 与 A10 是一对：**A2 限制了能带回来多少，A10 保证带回来的那点够用**。只守 A2 会得到一个"很短但没用"的结论；只守 A10 会把原始材料拖回来。两条必须同时上线。

> **A5 的逻辑依据（v4/F1，必须记住，不许再改回去）**：**事件是长期记忆的唯一原料。** 记忆只能从**历史**里抽取（记忆 §5.1：压缩输入只有 raw 轮次）。若 `<event>` 只是尾部临时块，**"第一次挖到钻石"这类事件下一轮就消失**——它永远不会进入压缩单元的输入，也就永远不可能被抽成记忆，而这类"一次性、不可逆、玩家会被问起"的事件恰恰最值得记。**尾部是每轮丢弃的，历史是随窗口滚动并被压缩的**：事件必须走后者。**推论**：把 `<event>` 挪回尾部，等于让事件系统对长期记忆贡献为零（只剩播报）——这是缺陷，不是取舍。

### 1.4 输出边界：**禁止"没事找话"，允许"有事报事"**（v2 定案 D3，**v4/F3 收窄措辞**）

**AX 仍然只有一个输出引擎、只有三种触发源，没有第四种**。但"没有第四种触发源"**不等于"不许出声"**——判据是**有没有触发源**：

| # | 触发源 | 形态 | 章节 |
|---|---|---|---|
| 1 | **玩家提问**（`Q` 到达） | 一轮主对话：`answer` 或 `delegate` | §4 |
| 2 | **游戏内事件**（事件总线提交，事件 §3/§6） | **`<event>` 追加进历史**（`world_event` 角色）；**高/中档按播报门出声**（事件 §4.1/§7.1），低档与黑名单**不出声** | 事件 §4 / §7；本文 §6.3 |
| 3 | **后台任务完成**（ticket 终态） | 事件线登记（必达，A4）+ `<event>` 追加进历史 + 播报（受 §6.2 门槛） | §5 / §6 |

> **⚑ v4/F2 更正（触发源 2）**：v3 及以前写作"游戏事件触发（03 §3 的状态变化判定通过）→ `T1` 快照进本轮尾部，**静默，不单独出声**"。那句话把**游戏事件**和**状态变化**混成了一件事。裁决后的口径：**状态变化走 `T1`（静默、每轮重建）；游戏内事件走 `<event>`（追加、按档位出声）**——分界判据见 §6.3。

**A. 禁止"没事找话"（D3 的原意，全部保留）**：

| 不做 | 说明 |
|---|---|
| 主动搭话 / 闲聊 | 没有"没事找话"的分支：没有定时器驱动的开场白、没有随机话题、没有"玩家在位就打个招呼"；**也不许模型自己发起话题** |
| 主动提醒 / 主动推荐 | 不因为"背包快满了""天黑了""这个配方你查过"就自己开口。这类信息只有在**玩家提问的那一轮**里，才允许作为 `T1`/`T2` 的一部分被模型看见 |
| 社交媒体式长周期自主行为 | 不做关注列表 / 每日推送 / 关系维护 / 自主日程这类跨会话的自主行为（**D3 原文保留**） |
| 主动追问 / 补问 | 模型只能凭**本轮**契约（§4.1）追问；不存在"过一会儿再问他一句"的挂起对话 |
| 无触发源的开口 | 没有 `Q`、没有事件、没有 ticket 终态时，AX **保持完全静默**（"没有第四种触发源"这条不变） |

**B. 允许"有事报事"（v4/F3 新增的边界，只对有触发源的情况开放）**：

| 允许 | 条件 | 归属 |
|---|---|---|
| **事件驱动的高/中档播报** | 事件总线提交的 `high` / `mid` **非黑名单**事件；过播报门（档位、黑名单、冷却、忙碌、空闲） | 事件 §4.1 / §7.1 / §7.2 |
| **委派回执与终态播报** | ticket 创建（"我查一下"）/ 终态（成功 / 失败 / 超时 / 取消） | §5.1 / §6.2 |

**"允许"的全部边界只有两条**：① **每条播报必须能指到一条具体触发源**（一条事件条目或一个 ticket 终态），**播报不调模型**（事件 `EV5`、§6.2 措辞纪律）；② **门槛一条都不许放宽**——全局最小间隔、同 `kind` 冷却、忙碌排队、低档永不主动，全在事件 §7.1 与本文 §6.2 里。**"有事报事"不是"多说几句"的许可，是"有触发源时不许装没看见"。**

**理由（一句话版）**：**游戏内玩家有明确意图——没有触发源就不该开口；但有触发源时闭嘴同样不对。** 展开三条：

1. **语音是抢占式通道**：屏幕上多一行字可以忽略，喇叭里多一句话必须"听完或打断"。**没事找话**是纯消耗；**有事报事**（"你着火了""钻石挖到了"）的注意力成本，玩家本来就要付（他迟早得知道）。
2. **没有退出机制**：聊天式助手可以"关掉对话窗"，而语音助手在游戏里**只有静音这一种降级手段**。所以判据必须落在**可验证**的一侧："**这句话有没有触发源**"可验证；"这个提醒对他有没有用"不可验证。判错一次，处置只有把整条功能关掉。
3. **意图判定不成立，但事件不是猜**：本设计里唯一的**提问意图**信号是 `Q`（03 §2.1）；凭世界状态猜意图（"他站在工作台前，大概想合成"）是高误报启发式，**一次误报就会被记住**。**但事件不是猜**——它是有人（或模组）在那一刻**明确声明"这件事发生了"**，触发源客观存在。这正是"有事报事"与"没事找话"的分界线。

> **与既有条目的关系**：§6.4 末注与附录 A.4 第 3 条禁止"为了投递及时而主动触发一轮模型请求"（**成本/前缀**角度）；§1.4 是**产品边界**角度。三条一起读：**AX 不为说话而多跑一轮模型，也不为关心而多说一句；但凡有触发源，该说的必须说，且必须进历史。**

## 2. 项目约束（前置，决定整套设计）

### 2.1 Tianshu 是纯客户端模组 → 能力收敛为信息查询

**这一条不是"当前实现限制"，而是设计前提**：模组跑在客户端，没有服务端权威，任何"改世界"的意图在多人服务器上要么被拒绝、要么只在自己客户端上假生效（本地世界与服务器世界分叉）。因此：

| 推论 | 后果 |
|---|---|
| **没有动作类工具** | 工具集只剩"取信息"，也就没有 `setblock`/`place`/`give` 这一整族；没有"执行后回读确认""权限校验""回滚/撤销"这些配套机制 |
| **工具都有"读"的确定性** | 检索类工具可以带 `failure` 而没有 `partial effect`；失败重试是安全的（幂等天然成立） |
| **不存在"操作确认"交互** | 不需要"你要我挖这块石头吗"这类二次确认轮次——这省掉了一整类状态机 |
| **"取消"是本地动作** | 取消一个 Run = 本地状态机置位 + 丢弃后续结果，不需要通知任何外部系统（§7.4） |
| **状态由本地读取后注入** | 背包数量、附近生物这类"我需要知道的世界状态"**不做成工具**，由 AX 在本地读世界后注入 prompt（§7.2） |

> ⚠ **不要因为"玩家说'帮我把这个箱子理一下'"就反推出动作类工具**。纯客户端做不了这件事，正确的回应是模型用 `answer` 说明做不了，而不是加一个注定在多人生效不了的工具体。这条写在这里，是为了让将来的人先看到结论、而不是先看到"工具表怎么扩"。

### 2.2 对外接口不属于本阶段

将来可能有**服务端模组**通过我们的 API 发起请求、拿到内容后**自行操作世界**（那时"改世界"发生在服务端，与我们无关）。那属于**对外接口**，**本阶段不设计**。

本阶段只登记三条"将来必须回答的问题"，避免以后才发现整个 Run 模型是按"单玩家、单会话"写的：

| 将来要回答 | 为什么现在不答 |
|---|---|
| 成本记谁的？ | 对外请求的 token 花在服务端玩家的配额上还是请求方的配额上，取决于部署形态 |
| 上下文用谁的？ | 服务端请求不该看到客户端玩家的记忆（记忆按玩家 UUID + world 分片，见记忆 §7）；是否要一个"无记忆的匿名 scope"是新产品问题 |
| 失败怎么回？ | 现在失败=往事件线投一句（§6）；对外接口失败要变成 HTTP/协议层的错误码，语义不同 |

**边界**：本文的所有设计只覆盖"本机玩家 ↔ 本机 AX"。凡出现"别的进程/别的玩家来问"的情形，一律不在本文范围内。

## 3. Loop 原语与 RunPolicy

### 3.1 一套循环，策略参数化

**只实现一个 `AgentLoop`**。两种运行不是两套代码，而是同一份循环的两组参数。这决定的不是"少写代码"，而是**终止语义只有一处**——否则"步数算不算工具执行""超时从哪一刻开始算"会在两处给出不同答案。

```text
AgentLoop.run(policy, initialMessages, registry):
    step = 0
    startedAt = now()

    loop:
        # ① 安全阀（先于任何 I/O，避免"最后一步还发了一次请求"）
        if step >= policy.maxSteps:            return finish(ABORT_MAX_STEPS)
        if now() - startedAt > policy.maxMs:   return finish(ABORT_TIMEOUT)

        # ② 一次模型请求（policy 决定带不带 tools）
        resp = request(initialMessages + 本次累积, tools = policy.toolsOrNull)
        step += 1

        # ③ 输出解释（两种 policy 的解释器不同，见 §4.1 / §5.5）
        out = policy.interpreter.parse(resp)

        # ④ 终止判定（SIMPLE 只有 ①②；COMPLEX 还有"显式完成"与"无进展"）
        if out.kind == FINAL:                  return finish(OK, out)
        if policy.hasNoProgressGuard and noProgressHit(history, out.call):
                                               return finish(ABORT_NO_PROGRESS)
        if policy.hasNoProgressGuard and step >= policy.maxSteps:
                                               return finish(ABORT_MAX_STEPS)

        # ⑤ 执行这一步的工具（仅 COMPLEX 会有）
        result = execute(out.call)
        history.append(out.call, result)
```

**"步"的定义要钉死（实现分歧多数出在这里）**：

```
1 步 = 1 次模型请求（含它触发的工具执行）
- 一个请求里并发 n 个工具，只算 1 步
- 工具执行耗时计入本 Run 的挂钟（受 maxMs 约束），但不单独计步
- 被安全阀打断的"未发出的请求"不补发（第 ① 步在请求之前）
```

### 3.2 两种 RunPolicy

| | **SIMPLE** | **COMPLEX** |
|---|---|---|
| 步数上限 | **3**（安全阀，正常 1 步内终止） | **25 步**（安全阀） |
| 时长上限 | **10s** | **120s** |
| 工具 | **无**（`toolsJson = null`） | **检索类**（§7.3） |
| 终止条件 | ① 显式完成 ② 步数安全阀 ③ 时长超限 | ① **显式完成（结构化结果）** ② **步数安全阀 25** ③ **无进展检测**（连续 3 步相同工具+相同参数） ④ **时长超限** |
| 谁能发起 | **任何模块**（不是 AX 专属，§3.6） | **只通过异步委派**（§5.2） |
| 执行位置 | 调用方所在车道（主对话 = `CHAT`） | **`TASK` 车道**（后台，可抢占） |
| 输出形态 | 由调用方定义（主对话见 §4.1；压缩见记忆 §5.2 的三要素 JSON） | 固定的"结论 + 来源"（§5.6） |
| 超时回收 | 调用方自己 `orTimeout` | **必须显式 `orTimeout`**（`TASK` 车道不自动超时，03 §9 差距 P） |

**为什么 `SIMPLE` 是 3 步 / 10s**：

- 3 不是"计划步骤"，是**安全阀**。主对话正常在**第 1 步**就产出 `answer` 或 `delegate` 而终止；压缩正常也是 1 步出 JSON。
- 余下的 2 步留给**"输出不合契约"的修复**：形态外输出、三要素 JSON 字段缺失/不可解析。修复策略归各调用方（压缩侧见记忆 §5.7 字段级降级），**本文只给上限**，不定义修复动作。
- 10s 与语音体验对齐：03 §7.3 要求 `firstTokenMs P50 ≤ 800ms`、`maxTokens = 512`（03 附录 A.1），一次正常的主对话请求的挂钟远低于 10s。**10s 一旦被撞到，说明不是慢，是卡住了**。

**为什么 `COMPLEX` 是 25 步 / 120s**：

- 25 步来自 03 §8.1 的"工具往返"预留量级，但本文把它放大到 25（覆盖"先查 wiki 再查配方再核对"，即 3 层检索各几个往返）。**这是安全阀，不是预算**：正常检索任务 5–8 步收敛。
- 120s 与 03 附录 A.4 的"压缩超时 120s"**取同值**，不是巧合：两者都是 `TASK` 车道上"一次模型调用链"的上限，运维上只该有一个数字。
- 四条件里 **"无进展检测"是最重要的一条**——它比步数更早生效，且是唯一能区分"任务重"与"模型在打转"的条件（§3.4）。

### 3.3 终止条件优先级

```
判定顺序（第一个命中的即终态，不再往下判）：
  1. 显式完成        → OK
  2. 无进展检测      → ABORT_NO_PROGRESS      # 只在 COMPLEX
  3. 步数安全阀      → ABORT_MAX_STEPS
  4. 时长超限        → ABORT_TIMEOUT
  5. 外部取消        → CANCELLED              # §7.4
  6. 内部错误        → FAILED
```

**必须按这个顺序判，不能按"发生时间"判**：如果一个 Run 在最后一步既产出了结果又撞上步数上限，它是**成功**的。反过来，"超时前一刻命中无进展"记 `ABORT_NO_PROGRESS` 而不是 `ABORT_TIMEOUT`——因为诊断时这两个的处置完全不同（前者改提示词，后者查性能）。

**终态一旦写成不可改**（与 ticket 状态机一致，§5.3）：`OK` 之后不得因为"后来发现结果不好"回改成 `FAILED`；要重答就新建 ticket。

### 3.4 无进展检测（`COMPLEX` 专用，定义必须可离线判定）

```text
noProgressHit(history, call):
    key = toolName + "|" + canonicalJson(call.args)
    连续 3 步的 key 逐字节相等 → hit
    （只看最近 3 步，不累计；中间插入其它工具即清零）

canonicalJson(args):
    - key 按 code-unit 排序（复用 03 D1/D2）
    - 字符串做 NFC 归一 + 去行尾空白（复用 03 D6）
    - 不排序数组元素（数组序是语义）
    - 浮点禁止（03 D5：无法避免时 String.format(Locale.ROOT, "%.1f")）
```

- **必须是"相同"而不是"相似"**。加相似度判断会让这个判据变成不可测试的启发式；而且检索类工具的相似重试（换个关键词再查一次）**是正常的**，不该被判无进展——它换了参数，`key` 就不同了。
- **"相同工具+相同参数"连做 3 次**只可能是：工具返回空/报错而模型没看懂、或提示词让它误以为失败要重试。两种都要人看，不该再烧步数。
- 与 03 §5.10 的失败降级同风格：命中后**降级收尾**（返回当前已有结论或失败终态），**不自动重试**（记忆 G6 同款理由：重试放大成本并掩盖提示词问题）。

### 3.5 谁来调用哪个 policy

| 用途 | policy | 车道 | 是否带工具 | 备注 |
|---|---|---|---|---|
| **主对话**（玩家说一句，答一句或委派） | `SIMPLE` | `CHAT` | 否 | §4 |
| **压缩**（每 60 轮一份单元摘要 + 事件链 + 偏好） | `SIMPLE` | `TASK` | 否 | 内容契约归记忆 §5.2；本文只管它走同一套循环与上限 |
| **异步委派**（一次检索任务） | `COMPLEX` | `TASK` | 是（检索类） | §5 |
| **元能力**（取消 / 查询任务状态） | **无 Run** | 本地 | —— | 本地状态机，同步返回（§7.4） |

> `SIMPLE` 的步数上限对压缩同样生效：压缩的"3 步"= 1 次生成 + ≤2 次字段级修复。这与记忆 §5.7 的"字段级降级"是同一件事的两种描述，**不要再给压缩单开一个 policy**。

### 3.6 `SIMPLE` 不是 AX 专属

`SIMPLE` 是**运行期公共原语**：任何模块（不止 AX）只要需要"一次带结构化输出的模型调用 + 一个安全阀"，就用它。因此有三条约束：

| # | 约束 | 理由 |
|---|---|---|
| 1 | 调用方**只提供** `initialMessages` 与 `interpreter`，**不得**改 `maxSteps`/`maxMs` | A8；否则"3 步"会变成每个调用方一个数，超时诊断失去公共口径 |
| 2 | 调用方**不得在 `SIMPLE` 内部再起 Run**（不得嵌套） | 阻塞车道 + 递归成本；需要多步就应设计成 `COMPLEX` 并由委派触发（A6） |
| 3 | 产生的事件/结论**回给调用方**，由调用方决定投递到哪里 | 循环本身不知道"玩家""播报""事件线"的存在。**`AgentLoop` 里出现 `player`/`broadcast` 字样即为分层破坏** |

### 3.7 与 03 的关系（一句话）

`AgentLoop` **不装配消息**。它拿到的 `initialMessages` 由 03 §2.1 的五段装配器产出；它产生的输出如何落 `H`，由 §8.5 决定。**循环里不得出现任何 `prompt` 拼装逻辑**。

### 3.8 `taskPriority` 的收敛边界（v2 定案，D4）

`taskPriority` 是 `TASK` 车道的排队参数。**字段保留**，但它的**语义面收窄了**：

| 项 | 定案 |
|---|---|
| **保留的理由** | `ASR` / `TTS` / `embedding` 是**本地独占资源**（一次只能跑一个），它们之间必须有一个"谁先跑"的次序——这是 `taskPriority` 现在**唯一的职责** |
| **清除的对象** | **仅服务于"本地 LLM 聊天"的取值与排序逻辑**：本地 LLM 聊天已封存，它的优先级常量/枚举、为它排的专用比较器、以及"聊天请求永远优先"这类抢占规则**全部删除**。留着就是死代码，更糟的是会让后来者以为本地聊天还活着 |
| **不在此定数值** | `COMPLEX` / 压缩等后台任务的**具体取值不散落在本文**：统一按 `TASK` 车道优先级表排布（03 再版时与 `ASR/TTS/embedding` 的既有取值**一并重排**）。本文**只给边界、不给数字**（与 A8 同风格：同一件事只有一个定义处） |
| **分层** | `AgentLoop` / `RunPolicy` **不感知** `taskPriority`（§3.6 第 3 条：循环里出现车道概念即分层破坏）。优先级只活在车道侧 |
| **与 A8 的关系** | 它**不是** `RunPolicy` 的参数。把"调优先级"实现成"改步数/时长上限"是越界 |

> **一句话**：`taskPriority` 从"聊天 vs 后台的排序"退化成"本地独占资源之间的排序"——**字段不动，语义变小**。03 里那组自相矛盾的默认值（§8.2 与附录 A.4 各写一个数）在 03 v8 已删除，本文也不再另立一套。

## 4. 主对话不带 `tools[]`：核心决策与理由

### 4.1 主对话的输出契约（只有两种形态）

```json
{ "action": "answer",   "text": "……" }
{ "action": "delegate", "query": "暮色森林的进入方式" }
```

| 字段 | 语义 | 约束 |
|---|---|---|
| `action` | 二值枚举 | **只有 `answer` / `delegate`**。没有第三种，没有 `tool`（A3） |
| `text` | `answer` 时的回复正文 | 进 `H`（A5）；受 `maxTokens = 512`（03 附录 A.1）约束；**voice 友好**：短、可朗读、无 Markdown 标记 |
| `query` | `delegate` 时的检索意图 | **要能脱离上下文读懂**（与 A10 同源：它会被送进一个独立上下文）；不带指代、不带"这个" |

**形态外输出（含解析失败、`action` 缺失、多余字段）的处置**：

```text
第 1 次违约 → 用 SIMPLE 的余量重问一次（原输出作为 assistant 消息一并带上，让模型看见自己的错）
第 2 次仍违约 → 降级为 answer，正文取资源键 local.ax.degraded_reply（文案在资源里，不写死在代码）
               记 main_contract_violated = true
```

- 降级用的兜底句**必须是资源键**，不许硬编码中文/英文字符串（工程规约：文案一律资源化）。键名只是登记，措辞归资源文件。
- **绝不把违约输出当答案直接发给玩家**。一个不合契约的 JSON 被当正文读出来，比"我没查清楚，你再说一次"严重得多。

### 4.2 为什么主对话请求不带 `tools[]`

四条理由，按重要性排：

| # | 理由 | 展开 |
|---|---|---|
| **1** | **纯客户端只需要检索，不需要"调用能力"** | §2.1 已把能力收敛成信息查询。而信息查询在主对话里只有两个去处：本地读（注入，§7.2）或异步委派（§5）。这两个都**不需要** `tool_calls` —— 一个在**发请求之前**就完成了，一个在**本轮结束之后**才开始。`tools[]` 在这个位置**没有任何一件事可干** |
| **2** | **不带 tools 使前缀更短、更稳** | `S2`（工具 schema 槽位，1024 token，03 §6.3）在主对话上是**空置**的。一旦带上 `tools[]`，sha 序列化、key 顺序、schema 版本、工具描述文案任何一处变动都改前缀。更关键的是：**工具集的增删不与会话节奏同步**（今天加个 wiki 工具，明天调个描述），"工具集变化 ⇒ 前缀失效"会把 03 I1（前缀稳定优先）直接破掉。不带 tools，这条风险**整条消失** |
| **3** | **历史天然干净，不需要"run 后剪除"这类补丁** | 一旦主对话带 tools，就必然出现 `assistant.tool_calls` + `tool` 消息。它们在 `H` 里意味着：① 03 I3（`H` 只追加、唯一改写是 compaction）要额外接纳一种"事后删除"；② 03 I10（`tool-call`/`tool-result` 是不可分单元）要把每种分区切点都做配对校验；③ 03 §5.5 的换代切点要保证不把一对调用切到两代。**三条都是纯负担，收益为零**。不带 tools 则 `H` 里只有 `user`/`assistant` 两种角色，"剪除"这个补丁**从设计里消失** |
| **4** | **少一类流式解析的边界情况** | 当前流式解析只读 `delta.content` / `delta.reasoning_content`（03 §8.1）。带 tools 就要解析 `tool_calls` 增量：分片跨 chunk、`index` 乱序、参数是**字符串拼接**而非 JSON 增量、`finish_reason` 是 `tool_calls` 而非 `stop`。这些边界全是"偶发、难复现、只在弱网出现"的类型 |

**收益的定量参照**：主对话因此**永远不付** `S2` 的 schema 前缀成本，也**永远不产生** tool 消息的 token；`H` 的净增维持 03 附录 A.1 的 ≈130 token/轮，`K`、`k`、摊销与成本表（03 §5.2、附录 A.3）**全部保持成立**。也就是说：这条决策不是"省一点"，而是**保住了 03 的整套成本模型**。

### 4.3 `S2` 槽位归属（写清楚，避免以后有人回收它）

| 情况 | `S2` 内容 |
|---|---|
| **主对话**（`SIMPLE`，无工具） | **空**。03 §6.3 的 1024 token 预算在**主对话上不被占用** |
| **Complex Run** | 其**独立上下文**里的 `S` + `S2`（检索类工具 schema），与主对话**零共享**（§5.5） |

**本文不改 03 的任何数值**：`C_low = 6016 + SB + KEEP` 仍然含 `S2` 的 1024（03 附录 A.1）。不要因为"主对话不用 `S2`"就去动 `C_low`——那会连带改 `K`/`k`/摊销/成本四张表（03 §5.2、附录 A.3），属于跨文档的另一件事。**要回收也是 03 再版时统一回收，不是运行期私下扣**。

### 4.4 反例（不要做）

- ❌ **"既然主对话也要能查 wiki，那顺手给它加个 `search` 工具"** —— 这正是本条决策要防的。要查就 `delegate`（§5）。
- ❌ **把 Complex Run 的 `tool_calls` 摘录成一条历史消息**（"我刚才查了 3 个页面"）。它同时违反 A2、A3、A5，且会让模型下一轮以为自己有工具。
- ❌ **`toolsJson = new ArrayList<>()`（空数组）代替 `null`**。空数组在部分 OpenAI 兼容网关等于"声明支持工具但一个都没有"，语义与 `null` 不同，且**改前缀字节**。沿用 03 §8.1 的现状：**传 `null`**。
- ❌ **为了让模型"知道能力边界"而在 `S` 里写工具清单**。`S` 字节冻结（03 I12），工具清单会变；要说明边界就写"能力摘要"这种稳定文本，具体工具不进 `S`。
- ❌ **把 thinking / reasoning 内容回填进主对话历史**（03 I11）——`delegate` 决策的推理过程尤其诱人，但违反 I11。

### 5.1 时序图

 ├─────────────►│                  │                  │                  │                │          │

 │              │                  │ ① 装配五段（含 T1/T2，§8）          │                │          │

**时间轴上的两条硬约束**：

| 约束 | 值 | 说明 |
|---|---|---|
| 步骤 ⑤ 必须在步骤 ③ 之后**立刻**发生 | **≤ 1s 出声** | 委派**不得阻塞本轮**：ticket 登记后立即结束本轮，不等待任何检索 I/O。1s 是"03 §7.3 的 `firstTokenMs P50 ≤ 800ms` + TTS 排队"的合成预算 |
| 步骤 ⑦ 到 ⑧ 的挂钟 | **≤ 120s** | 与 `COMPLEX.maxMs` 同值；`TASK` 车道不自动超时，必须显式 `orTimeout`（03 §9 差距 P） |

### 5.2 各阶段与失败路径

| 阶段 | 动作 | 失败/异常 | 处置（都必须落终态记录，A4） |
|---|---|---|---|
| ③ 返回 ticket | 解析 `query` → 生成本轮 ticket 引用 | `query` 为空/不可读 | 不建 ticket；本轮按 `answer` 降级（资源键兜底句），记 `delegate_invalid_query` |
| ④ 复用查询（5s 窗口） | `replayKey` 查**本会话最近 5s** 的委派（§5.4） | 命中活 ticket / 已终态 ticket | **不新建 Run**（A7），直接复用；仍然按期出声（玩家感知一致）。**窗口外一律新建**——v2 起没有键级去重 |
| ④ 提交 | 投 `TASK` 车道 | 车道拒绝/队列满 | 立即终态 `FAILED(reason=rejected)`，投一句失败（§6.2） |
| ⑥ 执行 | `COMPLEX` Run | 撞任一条终止条件（§3.3） | 终态 `ABORT_*`，**仍按成功路径投递**（带上"没查全"的语义，§6.2） |
| ⑦ 收尾 | 结论 + 来源过 A2/A10 校验 | 结论超 3 句 / 含原始材料 / 含指代 | 本地整句裁剪到 3 句 + 记 `complex_result_overflow`；含指代则记 `complex_result_not_selfcontained` 并**照常投递**（不许静默丢，A4） |
| ⑧ 写终态 | 事件线登记一条 | 重复写（重放） | 按 `taskId` 幂等：同一 `taskId` 只允许一条终态 |
| **⑨ 结论入记忆库**（v2，D2） | `OK` 的结论作为一条事件写入记忆库（字段契约归记忆 §5，写入幂等由记忆的 `idempotencyKey` 兜） | 写入失败 | 本地重试 1 次；仍失败则记 `memory_write_failed` 并**照常投递**（A4 不因记忆失败而破），同时**该问题的召回替代失效**需按 §10.1 的 `recall_hit_on_repeat` 告警 |

### 5.3 Ticket 状态机

```text
PENDING ──提交成功──► RUNNING ──终态──► {OK | ABORT_MAX_STEPS | ABORT_NO_PROGRESS
                                          | ABORT_TIMEOUT | FAILED | CANCELLED}
   │                     │                        │
   └──车道拒绝──► FAILED(rejected)                └── 终态一律写入事件线，恰好一条（A4）
```

| 规则 | 内容 |
|---|---|
| **一次性** | `AgentLoop` 与 `COMPLEX` Run 都是**一次性**的：终态之后不复用、不重启；要重答就新建 ticket（**v2：只有 5s 复用窗口会阻止新建**，§5.4） |
| **终态不可变** | 见 §3.3。`OK` 不因"结果不好"回改 |
| **取消** | `CANCELLED` 只由本地状态机产生（§7.4），不允许模型取消自己的任务（主对话没有工具，A3；Complex 内也禁止发起委派，A6） |
| **归属隔离** | ticket 归属 `sessionId`/`scopeId`（沿用 03 §8.2 的 `AXScope`）；跨会话不可读 |
| **丢弃语义** | 任务结束即丢弃 Complex 的整个上下文（A2 的另一半）。**不允许**为了"以后可能还问"把它的 `H` 落盘 |

### 5.4 委派去重：**不做键级去重**（v2 定案，D2）

**决定：删除 `delegateKey`。** v1 用 `sha256(normalize(query))` 给"同一个问题"做键，防止重复委派。**v2 起整条机制删除**——理由不是"实现麻烦"，而是**它要解决的那个问题在记忆就位后不存在了**：

| v1 的动机 | 现在的答案 |
|---|---|
| 玩家问同一个问题两次 → 烧两次 Complex Run | **Complex 的结论必须写入记忆库**（§5.5/§5.2 第 ⑨ 步）；同一问题下次由主对话的 `T2` 本地检索**直接召回**，模型自己 `answer`，**根本走不到委派** |
| 重复问题会把事件线塞满 | 事件线是**投递登记簿**（A4），本来就必须每条终态一条；去重键不是它的护栏 |
| 去重键能"省一次检索" | 它省的是"召回"的活，而召回**每轮都在做**（`T2` 必配）。用一层哈希键替代已有检索入口 = **同一件事两条实现路径**，且两条会各自漂移 |

**替代机制（两条，缺一不可）**：

1. **记忆召回（主路径）**：`OK` 的结论在收尾时写入记忆库（§5.2 第 ⑨ 步、§5.5）。主对话每轮都装配 `T2`（记忆命中在前，03 §6.3），所以"问过的问题"会以 `<memory>` 命中形式回到模型眼前。
2. **5 秒复用（极小防护，只防一件事）**：同一会话内、**5 秒窗口**里出现**逐字节相同的 `query`** 时，直接复用既有 ticket / 既有结论。它防的是"模型同一轮连发两次 `delegate`"或"相邻两轮被重复触发"，**不是去重机制，也不构成任何跨轮记忆**。

```text
replayKey      = sha256( normalize(query) )     # 只比较"同一句话"，不做同义/相似
replayWindowMs = 5000                           # **可配置项，不硬编码**（配置键见附录 A.2）

normalize(query):                               # 与 03 D6 同源
    NFC 归一 → 去全部空白与全半角差异 → 去句末标点 → 英文小写化
    # 不做同义改写、不做向量相似、不做拼音归一 —— 那会把"两个不同的问题"合成一个

onDelegate(query):
    key = replayKey(query)
    if 本会话在 [now − replayWindowMs, now] 内有 key 相同的 ticket:
        return 既有 ticket          # 不新建 Run（A7）；若已终态则直接复用其结论
    else:
        新建 ticket → 提交 COMPLEX Run → return ticket
                                    # 无任何持久化去重状态
```

**三条实现纪律**：

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **5s 窗口不落盘、不进记忆、不进事件线** | 它是一次运行期近似，不是"这个问题问过"的持久判断。落盘就等于把 `delegateKey` 换个名字又装回来 |
| 2 | 窗口**只与时间 + 规范化文本**有关，与"结论是否还在上下文里"无关 | v1 的"结论仍在可见上下文内"作用域**作废**（§11-2）：那是去重键的语义；键没了，语义跟着消失 |
| 3 | 窗口命中**不算** A7 的"两个 Run"违反 | A7 的判据随之改为"5s 窗口内出现两个 Run 才算违反"（§1.3） |

**⚠ 必须补上的实现要求（D2 的另一半，列为验收项）**：

> **Complex 结论写入记忆库之后，检索阈值必须保证"问过的问题能被召回"。** 否则替代机制**整条失效**：问题既没有 `delegateKey` 挡着，又召不回来，玩家会看到"同一个问题被反复委派，每次重烧一遍 120s"。
>
> 落成两条可执行验收（§10.1）：
>
> | 验收项 | 定义 | 阈值 |
> |---|---|---|
> | **`recall_hit_on_repeat`** | 同会话内同一 `normalize(query)` 的**第二次及以后**提问中，由 `T2` 记忆召回直接 `answer` 的比例 | **≥ 0.90**（低于此值即认定替代机制失效，**缺陷优先级等同 A4**） |
> | **`delegate_repeat_rate`** | 上述重复提问仍然走到 `delegate` 的次数 ÷ 重复提问总数（千分比） | **≤ 100‰** |
>
> 调整的**唯一合法方向**是"让召回把问过的结论带回来"（放宽检索的相对线/绝对地板、提高该事件的 `importance`、确保结论真的以事件形式落库），**不是**把 `delegateKey` 加回来。**加回键 = 本决策被回滚，需重新拍板。**

**与记忆 `idempotencyKey` 的关系（A9，最容易写错的一处）**：

| | 本文（v2 起） | 记忆 §10 G7 `idempotencyKey` |
|---|---|---|
| 有没有键 | **没有委派幂等键**；只有 5s 的 `replayKey`（内存态、不落盘） | 有：`sha256(batchId\|turnRef\|factHash)`（分隔符为竖线） |
| 目的 | 防"模型同一轮连发两次" | 防"同一份压缩输入被写两遍" |
| 生命周期 | ≤ 5 秒，会话内 | 批次内（写完即过） |
| 结论写入时的幂等 | **由记忆侧负责**：结论作为一条事件写入时走记忆的 `idempotencyKey` | 同批次同一条事实写两次 → 跳过/合并 |

> 一句话：**委派不再自己做去重，写入记忆的那一步由记忆侧的幂等键兜住。** 任何"委派自己算一个键去查重"的实现，都是把 v2 的决定回滚了。事件线的 `taskId` 仍然是**投递**的幂等主键（A4），与"同一个问题问过几次"无关。

### 5.5 Complex Run 的内部上下文

| 项 | 规则 |
|---|---|
| 上下文 | **独立**：自己的 `S`（同一份文本，03 I12/§8.3）+ 自己的 `S2`（检索类工具 schema）+ 自己的裸历史。**不复用主链前缀**，因此也**不共享主链缓存**（03 §8.3 已明确） |
| 输入 | 只有两样：**同一份 `S` 文本** + 本次 `query`（可能再带一条"已注入的状态快照"作为廉价上下文）。**不带主链的 `H`**——那是隐私与成本双重问题 |
| 工具 | 检索类（§7.3）。工具集**系列内恒定**（03 §8.1），增删工具 = 新 ticket 的新上下文，**不影响主对话前缀**（这正是 §4.2 理由 2 的兑现处） |
| 输出 | 结论 ≤3 句 + 可选来源（A2）；**不发回** tool 消息、原始页面、检索命中列表 |
| 收尾 | Run 结束 → 上下文整份丢弃（只留结论）。**⚑ v4/F1 更正**：结论（≤3 句 + 可选来源）**以 `<event>` 历史条目追加进 `H`**，因此它 **进历史、进压缩**——这是它最终能被抽成记忆的唯一路径；**不进**的是 Complex 的 `tool_calls`、原始材料、思考内容与整份上下文（A2）。**⚑ v2（D2）**：结论同时必须写入记忆库（作为一条事件，字段契约归记忆 §5，写入幂等走记忆的 `idempotencyKey`）——否则重复提问只能靠再委派一次，D2 的替代机制失效 |

### 5.6 Complex 输出约束（可执行判定）

```text
conclusion = 模型的结构化结果（伪 schema，字段名实现阶段定）
约束 1（A2）：只回传 conclusion.text（≤3 句）+ conclusion.sources?（可选，短标识）
            raw 材料（正文片段/表格/命中列表）一律丢弃
约束 2（A10）：text 中不得出现指代（"上述/该页面/第 N 节/如上"）与引用编号
约束 3（预算）：结论渲染后 ≤ 300 token（沿用 03 §8.2 的 300 预留位；**⚑ v4/F1**：这 300 的尾部位已空置，**上限口径不变**——它现在约束的是**该 `<event>` 历史条目的渲染长度**）
约束 4（句数）：按句末标点（。！？；.!?;）切分，> 3 句 → 整句裁剪 + 记 complex_result_overflow
```

> **为什么"8 句被裁到 3 句"是可接受的**：投递物的职责是"让模型知道答案在哪个方向"，不是"把答案完整搬过去"。玩家若追问，会触发一次新的委派（新的 ticket、更具体的 `query`）——那是有信息增益的第二次检索，比拖着一坨原始材料便宜且准。**注意这与 A4 不冲突**：裁剪不丢"投递记录"，只压缩"投递正文"。

## 6. 结果投递与播报门槛

### 6.1 三个通道必须分开（本节最容易含混的地方）

| 通道 | 载体 | 是否必达 | 受什么约束 |
|---|---|---|---|
| **① 登记** | 事件线（本地，append-only） | **必达（A4）** | 无。**任何终态都要登记恰好一条** |
| **② 进 prompt** | **`<event>` 历史条目**（`world_event` 角色消息；**⚑ v4/F1：不再走 `T3`**） | **必达**（A4；游戏事件侧见事件 `EV3` 非黑必达） | **历史容量与压缩**（03 §5）；**不占 896 尾部预算**。唯一不落历史的是"低档 + 黑名单"，且它在**入口**就被丢弃（事件 `EV7`），发生在 ① 之前 |
| **③ 出声** | 播报器（TTS） | 按门槛（§6.2） | 播报门槛与队列 |

**这条分离是设计的一部分，不是实现细节**：如果把它合成一条，"失败也必须投递一句"会退化成"失败也要立刻打断玩家说话"；反过来，"空闲时不打扰"会被实现成"干脆不登记"，于是 A4 破掉而没人发现。**登记与落历史永远发生，出声看门槛。**

> **⚑ v4/F1 的连带影响**：通道 ② 的载体从"`T3` 块"换成"历史条目"以后，**"块被 896 挤掉"这条失败路径消失了**——`event_block_dropped` 因此失去触发条件（§10.1 已标记待收口，诊断位改由 `events_per_turn` 承接）。代价是历史净增变高，登记为 `事件 §10.4`／`OP7`，**本文不改任何预算数值**。

### 6.2 播报门槛

**两条正交的规则**：① **什么时候能出声**（门槛）；② **一次能出声几条**（D1：不合并、FIFO 逐条）。

| 场景 | 判定 | 动作 |
|---|---|---|
| **玩家空闲**（无进行中的轮次、无正在播报） | 立即 | 立即出声，播报结论（或失败说明）；队列里还有待播则**接着逐条播**（条间 ≥ `minGapMs`） |
| **正在对话**（有 `CHAT` 轮次在跑，或在播报别的） | 排队 | 入队；**在本轮结束时**开始出队，不打断当前轮 |
| **失败 / 超时 / 被取消** | 无差别 | **必须出声一句**（措辞来自资源键，分级：失败 / 超时 / 取消各一键）。**不允许静默失败** |
| **同一时刻有 ≥2 条待播** | **不合并** | **v2（D1）定案：分多次播报，先回来的先说（FIFO）**——出队序 = 事件线登记序（`createdAt` 升序，同刻按 `taskId` code-unit 序）。**相邻两条之间至少间隔 `minGapMs`**，否则两条紧挨着会被听成一句话。**不得静默丢弃**，也**不得把它们拼成一条** |
| **会话结束/退出** | 丢弃队列 | 队列里的播报丢弃，但**事件线记录保留**（① 与 ③ 的分离再次生效） |

**为什么 FIFO 分条而不合并（D1 的依据）**：

- 每条结论对应一次**独立的委派**（不同的 `query`、不同的终点）。合并成一句等于丢掉"哪条是哪条"，玩家追问时**无法指代**。
- 合并必然要做一次"串联改写"（加连接词、去重措辞），那是**第二次自由生成**：既多一次成本，又把 A2/A10 刚校验过的正文改坏。
- FIFO 不需要新规则：**队列顺序 = 登记顺序 = 完成顺序**，与 §8.3 的 `<event>` 合并序完全一致，两处不会给出不同答案。

**`minGapMs` 是配置项（不硬编码）**：

```text
配置键：ax.runtime.broadcast.minGapMs     // 取值属产品调参（语速/口播节奏），默认值放配置文件
约束：  代码里不得出现字面量；两条播报之间的最小静默间隔由它决定
作用：  "两条播报不粘成一句"的唯一护栏（D1 的实现提示）
```

**门槛的措辞纪律**：

- 播报文本**一律走资源键**（`ax.runtime.delegate.ack` / `.failed` / `.timeout` / `.cancelled`），代码里不出现任何自然语言。
- 出声的"我查一下"（委派回执）与"查到了…"（结论播报）是**两条不同资源键**，不要复用。
- 结论播报读 `conclusion.text` 本身（≤3 句），不再二次改写——二次改写等于多一次模型调用，且会引入没被 A2 约束的新材料。

### 6.3 事件线记录形态

```text
事件线条目（每条一份，append-only）：
    taskId             # 幂等主键（同一 taskId 只允许一条终态）；游戏事件侧用事件 seq 充任
    replayKeyHit       # bool（v2：该条是否由 5s 复用窗口产生；无持久化键，§5.4）
    kind               # 委派终态：delegate_ok | delegate_failed | delegate_timeout | delegate_cancelled
                       # 游戏内事件：命名空间化名 tianshu:death / mymod:ritual_complete（事件 §3.2）
    status             # §5.3 的终态枚举（游戏事件为 emitted）
    text?              # kind=delegate_ok 或游戏事件时的正文（≤3 句 / ≤300 token / 事件侧 ≤ payload.maxTextChars）
    sources?           # 可选，短标识列表
    createdTick/createdAt
    appendedToHistory  # bool（② 是否已写成 <event> 历史条目；A5 的硬判据）
    spoken             # bool（③ 是否出声过）
```

**事件线条目的 `kind` 有两个来源，都以 `<event>` 追加进历史（v4/F2 改写）**：

| 来源 | `kind` 形态 | 登记与必达 | 归属 |
|---|---|---|---|
| **委派终态**（运行期发生的事） | 裸名 `delegate_*` | A4：每个 ticket 恰好一条 | **本文**（§5/§6） |
| **游戏内事件**（世界里发生的事） | 命名空间化 `ns:name`（44 条内置见事件 §6） | 事件 `EV3`：非黑必达（低档 + 黑名单在入口丢弃，`EV7`） | **事件文档**（§3–§8）；本文只消费其"已落历史"的结果 |

**两类信息的分界判据（v4/F2，写死，不许各自解释）**：

> **有发生时刻的变化 = 事件（走 `<event>`，追加进历史、按档位播报）；无发生时刻的当前事实 = 状态（走 `T1`，每轮重建、静默、不进历史）。**

- **归入事件**（`<event>` 追加）：死亡、进入下界、获得 buff、被苦力怕炸了、挖到钻石、合成成功、成就达成……它**发生一次就是一次**，有先后、可计数。
- **归入状态**（`T1` 尾部）：**准星目标、附近生物、背包剩余格数、当前血量、当前维度、坐标**……它**每轮都能重新算一遍**，算出来一样就一样，**没有"发生"这一说**。
- **两个典型失败形态**（都是把一类塞进另一类的通道）：① 把"当前血量 2 心"写成事件 → 每轮都发一条"你血量很低"；② 把"刚被苦力怕炸了"写成状态 → 下一轮就消失了，模型永远不知道发生过。
- **`T1` 里不许出现"上次是…""掉了 6 心"**（那是变化量，属事件）；**`<event>` 里不许出现"现在是…"**（那是当前值，属状态）。同一条事实只在一个落点说一遍（事件 `EV1`／§2.3）。

> **⚑ v4/F2 更正了什么**：v3 此处的原文是"**事件线的 `kind` 里没有'游戏内事件'**：区块变化、血量变化这类不是事件线的条目，**它们是状态，走 `T1`**"。那句话把**整类世界侧信息**划给了状态，于是"刚被炸了"这类有发生时刻的变化无处落脚。**裁决后**：44 个内置 `kind` 走 `<event>`；`T1` 只保留**持续存在的当前事实**。原文防的那件事（**把纯状态当事件刷屏**）依然有效，只是判据从"是不是游戏内事件"换成了上面那条**发生时刻判据**。

### 6.4 播报与投递的时序（三种分支）

```text
分支 A：空闲
  ticket 终态 → ①登记 → ②把 <event> 追加进历史 → ③立即出声
  实际顺序：①②③ 可以同 tick；历史条目一旦写成就永久可见（下一轮装配随分区带出，
  不因投递而重发 prompt）

分支 B：正在对话（最常见，也最容易写错）
  ticket 终态 → ①登记 → 排队
  历史条目照写（不等本轮结束，② 与 ③ 无关）
  当前轮结束后：③出队出声（在 assistant 最终文本之后，不与它抢发言）
                多条按 FIFO 逐条出队，相邻两条之间停 ≥ minGapMs（D1，§6.2）
  下一轮装配：<event> 条目已在历史里，随 compWindow/keepWindow 切片自动带出

分支 C：失败 / 超时
  同一路径，只是 kind 与资源键不同。
  ⚠ 分支 B 里"当前轮结束"指的是**玩家那一轮**，不是 Complex 那一轮（两者不是一个东西）
```

> **不要为了"投递及时"而主动触发一轮模型请求**。那会打破 03 的五段稳态（多出一次请求 = 多一个尾部 = 前缀复用点位移），成本远高于"等玩家下次说话再带上"。**投递的时效性由播报保证，不由 prompt 保证。**

## 7. 工具分类

### 7.1 四类，只保留一类

| 类型 | 例子 | 处理 | 理由 |
|---|---|---|---|
| **状态查询** | 背包里有多少圆石、附近有什么生物、当前维度/坐标 | **不做成工具**。由 AX 本地读取后**注入** prompt（`T1`） | 见 §7.2。**⚑ v4/F2**：这里只装"**无发生时刻的当前事实**"；有发生时刻的变化属事件，走 `<event>`（§6.3 判据） |
| **外部检索** | 百科、wiki、知识库、本地配方 | **走异步委派**（`COMPLEX` Run 内的检索类工具） | 见 §7.3 |
| **世界动作** | 放置、破坏、给予、攻击、开箱 | **不存在**（纯客户端，A1） | §2.1 |
| **元能力** | 取消任务、查询任务状态 | **本地状态机，同步** | §7.4 |

**为什么只有一类需要"工具"**：工具存在的意义是"让模型在**同一轮**里多拿一次外部信息"。而状态查询在**发请求之前**就能完成（本地读，零延迟、零成本、零不确定性），异步检索在**本轮之后**才需要（耗时秒级，绝不能阻塞语音轮次）。剩下的世界动作不存在。**所以 `tools[]` 只在 Complex Run 内部才有意义**——这正是 §4.2 的结论。

### 7.2 状态查询为什么必须注入而不是工具

| 论据 | 展开 |
|---|---|
| **确定性与成本** | 本地读一次背包是微秒级；做成工具要一次模型往返（~1s）加一次工具结果注入（`≤400 token`，03 §8.1）。**玩家问"我有多少圆石"，答案在本地就是一行数字** |
| **与 03 的状态快照机制直接冲突** | 03 §3 已经定义了状态向量、变化检测、`REUSE/APPEND` 决策、`T1` 槽位。做成工具等于**同一份状态有两条注入路径**：一条走 `T1`（每轮检测）、一条走 `tool` 结果（模型按需问）。两条会打架：`T1` 说"血量 3 心"，工具回"血量 3.0"，且**两条都在历史里**，模型看到两份 |
| **会破坏主对话的干净历史** | A3/A5。状态一旦走 `tool`，主对话历史就有 `tool` 消息了 |
| **"模型不知道要问什么"** | 玩家的问法千变万化（"我够黑曜石吗""这个能合成吗"），让模型自己决定查哪个字段，远不如**按 03 §3.1 的状态向量稳定注入**。注入的内容是确定的，工具参数是不确定的 |

**注入纪律**（与 03 §3 完全一致，此处只重申运行期边界）：

- 状态只在 `T1`，**不进 `S`**（03 I4），**不进 `H`**（A5）。
- 每轮**重新判定**是否变化（03 §3.2），变化则**追加新消息**（不替换旧消息）。
- 状态不够用时，正确做法是**扩状态向量**（03 §3.1 加维度），不是加工具。

### 7.3 检索类工具集（Complex Run 内部）

| 工具 | 用途 | 备注 |
|---|---|---|
| `wiki.search` / `wiki.page` | 百科/游戏 wiki | 网页工具与它的区别：后者是"任意 URL 抓取" |
| `knowledge.search` | 本地知识库（RAG） | 与主对话 `T2` 里的知识命中**是同一个库但不同入口**：主对话是"顺手带上的",委派是"专门去查的" |
| `web.fetch` | 任意网页 | 只在 wiki 覆盖不到时用；**必须有域名/长度/时间三重限制** |
| `recipe.lookup` | 本地配方数据 | 纯本地、最快、最确定，**优先于任何网络工具** |

**工具集纪律**：

| # | 规则 |
|---|---|
| 1 | schema 序列化 key 顺序固定、**按工具名 code-unit 排序**（03 D2/D4）；否则同一份 schema 两次序列化不同 |
| 2 | 工具集在**一个 ticket 的生命周期内恒定**；增删工具只影响**下次** ticket 的上下文，**不影响主对话前缀**（§4.2 的兑现处） |
| 3 | 单条工具结果 **≤400 token**，超长**在工具侧**就摘要化（"源头精简"，03 §8.1）——不要指望 Complex Run 自己去截断 |
| 4 | 工具失败返回**结构化错误**而非异常字符串（`{ok:false, reason:...}`），否则模型会去重试不可重试的错误 |
| 5 | **工具不做动作**（A1）。任何"返回执行结果"的接口都在越过这条线 |

### 7.4 元能力：本地状态机，同步

| 能力 | 入口 | 语义 |
|---|---|---|
| 取消 | 玩家指令 / 会话结束 | 按 `taskId` 或"当前会话全部"置 `CANCELLED`；丢弃后续结果；**终态记录照写**（A4） |
| 查询任务 | 玩家指令 | 读注册表，同步返回状态；**不进 prompt、不占 token** |

**为什么不做成模型工具**：

1. 主对话没有工具（A3）；Complex Run 内禁止发起委派（A6），也就不需要"取消我自己"。
2. 取消是**本地即时动作**，交给模型只会绕一圈：模型输出 `delegate(cancel)` → 起一个 Run → 再取消。**玩家说"别查了"应该在下一 tick 就生效。**
3. "查询任务状态"是诊断/运维用的，玩家很少需要，它的读者是人，不是模型。

> ⚠ 取消的实现必须**同时**做两件事：置终态 + 让 `TASK` 车道的在途请求可回收（`cancelRequest`，03 §9 差距 P 的 `AXDetachedTask`）。只置标志而不取消在途请求，会出现"已经取消了但 120s 后又投递一条"——这是最容易漏的半边。

## 8. 运行期消息编排

> **本节与 03 不重叠**：五段排布、角色、标签结构、每轮变化表**全部以 03 §2.1/§2.2 为准**。本节只写"运行期在什么时候、按什么规则填哪一段"，不重复定义形态。

### 8.1 运行期动作表（谁在什么时候动哪一块）

| 段 | 运行期动作 | 触发时机 | 是否进 `H` |
|---|---|---|---|
| `S` | 只读 | 永不 | —— （本身就是消息，见 03） |
| **摘要块 `SB`** | 只读（由记忆侧压缩产出、本地渲染） | 换代时（03 §5.8） | 否 |
| **压缩窗口 / 保持窗口** | 只读（切片索引） | 每轮 | 是（它们**就是** `H`） |
| `T1` 状态快照 | **每轮重判**：变化则本轮替换 | 装配前（03 §3.2） | **否**（A5） |
| `T2` 检索命中 | **每轮新建** | 装配前 | **否** |
| ~~`T3` 事件线~~ **（⚑ v4/F1：空置）** | **不装配**：`<event>` 已改为历史条目，`T3` 不再承载任何标签（预算位暂留，回收归 03 再版） | —— | —— |
| **`<event>` 历史条目**（v4/F1 新增行） | **发生即追加一条**（委派终态 / 游戏内事件），按发生序；**不合并成块、不每轮重建、不参与装配** | **事件发生当下**（不是装配时） | **是**（A5：它就是 `H` 的一部分，随窗口滚动） |
| `Q` 玩家输入 | 每轮一条 | 装配时 | **是**（它成为 `H` 的下一轮起点） |

**"每轮替换但不进 append 流"这句话的准确含义**（这是最容易实现错的一条）：

```text
尾部两块（T1/T2）每轮重新构造，**不写回任何持久数组**。
下一轮装配时，它们既不参与"上一轮的消息序列"，也不影响 H 的字节。

H（append-only，⚑ v4/F1）里严格只有三样：
    [user Q] [assistant 最终正文]        成对追加（+ 摘要块在 messages[1]）
    [world_event <event> 条目]           事件发生当下追加一条（不每轮重建、不合并成块）
```

### 8.2 状态快照与准星

- `T1` 的内容与变化判定**完全归 03 §3**，本文不定义维度。
- **`T1` 只装"无发生时刻的当前事实"**（**⚑ v4/F2**）：准星目标、附近生物、背包剩余格数、当前血量、当前维度、坐标。判据一句话 —— **有发生时刻的变化 = 事件（`<event>` 追加）；无发生时刻的当前事实 = 状态（`T1` 尾部重建）**（§6.3）。带"上次是…""掉了 6 心"的句子属于事件，**不许写进 `T1`**（事件 `EV1`／§2.3）。
- **准星目标**是易变内容，属于 `T1` 的一部分：每轮重判、**每轮替换、不进 `H`**。
- **准星无目标时必须注入"准星：无目标"**（文案走资源键）：

| 情况 | 注入 | 理由 |
|---|---|---|
| 准星对着方块的某面 | 方块 id（+ 可选 NBT 摘要） | 玩家"这个能合成吗"的指代对象 |
| 准星对着生物 | 生物 id | 同上 |
| **准星无目标** | **"准星：无目标"** | **防止模型编造**。不注入 = 模型不知道"没有目标"，会把玩家上一句里的东西当成"这个"；注入"无目标"= 模型知道"这里没有指代对象"，会追问 |

> 这条不是"多此一举的一行字"：它是**负数事实的注入**（"没有"本身是信息）。凡是"缺省即歧义"的槽位，都要显式注入空值语义——同样的道理在用 `<memory>` 空着的时候也成立（03 D7：空段**整段不出现**，而不是输出空标签；这里"无目标"是**有内容的负数事实**，与"空段不出现"不冲突）。

### 8.3 三个标签的每轮合成规则（**⚑ v4：`<event>` 例外 —— 发生即追加，不参与每轮合成**）

| 标签 | 槽位 | 每轮合成规则 | 累积？ |
|---|---|---|---|
| `<memory_summary …>` | `messages[1]` | **换代才整块替换**（03 §5.8.1；v2 起本文与 03 用同一个名字，**不再有简称/规范名之分**，见 §9.4） | **禁止**（跨代累积违反记忆 N1/N2） |
| `<event>` | **`H`（历史条目，`world_event` 角色）** | **⚑ v4/F1 改写：发生即追加一条，不参与每轮合成** —— 追加序 = 发生序（`createdAt` 升序，同刻按 `kind` + `taskId` code-unit 序）；**同一条事件只允许一个历史条目**（幂等键 = `taskId` / 事件 `seq`）；不合并成块、不每轮重建 | **是 —— 这就是它存在的理由**：随窗口滚动，最终被压缩抽成记忆（记忆 §5.1） |
| `<memory>` | `T2` | **每轮新建**：记忆命中（12 条 / 单条 ≤40 token）在前，知识命中在后（记忆优先、知识让位，03 §6.3/记忆 §6.6） | **禁止** |
| **玩家输入** | `Q` | **无标签**，**永远最后一条** | —— |

**`<event>` 的追加纪律（v4/F1 改写；原文"每轮合并待投递条目"作废）**：

```text
追加时机：事件发生当下（不是装配时），与轮次边界解耦
一条事件 = 一条历史消息（world_event 角色）；字节只由 (kind, payload, 顺序) 决定（事件 EV9）
幂等：taskId（委派终态）/ seq（游戏事件）—— 同一条事件只允许一个历史条目
聚合：mid/low 的事件在**写入历史之前**按事件 §8 折成一条；high 永不聚合（事件 §8.4）
装配前 flush：任何一轮装配开始前必须先 flush 聚合窗口（事件 §8.5），否则窗口内事件会漏进历史
空集：没有事件发生 → 不追加任何字节（不存在"空块不出现"的问题了：没有条就没有字节）
```

> **逻辑依据（v4/F1，与 A5 的注同一条，此处再写一次防止走回头路）**：**事件是长期记忆的唯一原料**。记忆只从历史里抽取（记忆 §5.1 的压缩输入只有 raw 轮次）。若 `<event>` 是尾部临时块，**"第一次挖到钻石"这类事件下一轮就消失**，永远进不了记忆——而它恰恰是玩家最会被问起、也最值得记住的那一类。**一次性事实必须落在"只写一次、会滚进压缩区"的通道里，那就是 `H`。**

> ⚠ **"事件 `<event>`"与"记忆的 Event（E）"不是同一个东西**：前者是**运行期发生的事**（委派结论/失败/超时），后者是**被检索回来的历史原子事件**（记忆 §4.3）。**后者进 `<memory>`，前者进 `<event>`**。这两个词撞名是记忆文档的历史包袱，实现时不要合并成一个类型。

### 8.4 标签外泄防护（**只登记需求，措辞在写 `S` 时定**）

| 项 | 登记 |
|---|---|
| **需求** | 在 `S` 中加入一条约束：上下文中形如 `<xxx>` 的块为**系统注入**，回复中**不得复述、不得模仿、不得当作可引用内容** |
| **为什么必须有** | 模型见到结构化块会倾向"引用"，而玩家会听见"记忆窗口摘要说…"。这是语音产品里最刺耳的失败形态 |
| **落点** | `S` 的静态文本（03 I12：字节冻结、全档位共用）；**不是**运行期注入 |
| **约束** | `S` 的字节一旦定稿即冻结；加这条要在**部署时一次写定**并重算 `systemHash`（03 D13） |
| **验收** | 回复中出现 `<` 加已知标签名 → 记 `tag_leak`；目标 **0**（§10） |
| **措辞** | **待定**（§11 第 4 项）。本阶段只保证"这条约束存在"，不保证句子怎么写 |

### 8.5 运行期与 append-only 的边界（A5 的执行口径）

```text
一轮结束时写入 H 的（⚑ v4/F1 后是两样）：
    ① assistant 的最终正文（= payload.text()，不含 reasoning，03 I11）
    ② 本轮的 <event> 历史条目（world_event 角色，≤3 句 + 可选来源；
       游戏事件按事件 §8 聚合后写入：一条事件 = 一条消息）

"一轮结束时写入"≠"事件只能在一轮结束时写"：事件发生在轮次中途也照写（§8.3），
它与轮次边界解耦——装配器只负责把已存在的条目随分区切片带出。

一轮结束时绝不写入 H 的：
    T1/T2 的任何字节（T3 已空置）、tool 消息、委派 query、
    Complex Run 的 tool_calls / 原始材料 / thinking 内容
    （注意：委派结论本身**要**写——它作为 <event> 条目写入，见第 ② 项与 §5.5）

自检（每条都能落成断言）：
    turns[i].contentHash == sha256(payload.text())
    H 中不存在 role == "tool" 的消息（A3）
    H 中不存在 <memory> / <memory_summary> 标签（A5）：检索块只占 T2，摘要块只占 messages[1]
    H 中的 <event> 只允许以整条事件消息形态出现（world_event 角色，A5）：
        不得混进 user / assistant 正文，不得出现在尾部块里
    emitted_events − appended_events == 0（A5 + 事件 EV3）
```

### 8.6 装配伪代码（只示意调用顺序，形态以 03 为准）

```text
assembleTurn(session, playerInput):
    aggregator.flushAll()                              # 事件 §8.5：先让聚合窗口落成历史条目（EV3）
    S      = systemText()                              # 只读，字节冻结（03 I12）
    block  = summaryBlock(session.generation)          # 只读，≥ 空占位（03 §5.8）
    [compWindow, keepWindow] = slide(session.turns)    # 纯切片；<event> 条目就在其中（⚑ v4/F1）
    T1     = stateSnapshot(session)                    # 变化检测；含准星（含"无目标"）
    T2     = retrieve(playerInput)                     # 记忆在前、知识在后
    # ⚑ v4/F1：没有 T3。事件已是历史条目，随上面两个窗口的切片自动带出
    Q      = playerInput                               # 无标签，最后一条

    return [S, block] + compWindow + keepWindow + [T1?, T2?, Q]

    # 为什么这样最省：装配器不需要为 <event> 做任何事——没有第二个渲染点，
    # 也没有"块被尾部预算挤掉"这条失败路径（§6.1、§8.3）。
```

> 三个 `?` 的处理统一为 03 D7：**空段整段不出现**。**禁止**输出空标签占位（那会让"有/无"两种状态产生不同字节，且都在前缀的尾部位置漂移）。

### 8.7 四级白名单与压缩输入边界（**v4 新增**）

本节回答一个只有一处能答的问题：**什么样的字节能进 `H`，什么样的字节能进压缩输入。** 完整口径在事件 §9.1（两级白名单）与 §9.5（压缩侧过滤伪代码）；本节只登记**运行期边界**，并给出四类事件 × 两级白名单的判定表。

**两级白名单的定义（先记住这两行，下面全是它的推论）**：

| 级别 | 问题 | 白名单 | 出口 |
|---|---|---|---|
| **历史级** | 能进 `H` 吗？ | **玩家输入 + 助手回答 + `<event>`**（高 / 中 + **低档非黑**） | 下一轮模型能不能看见（03 §2.1 的 raw 窗口） |
| **压缩级** | 能被抽成记忆吗？ | **玩家输入 + 助手回答 + 高/中档 `<event>` + 低档非黑事件的聚合条目** | 记忆库（记忆 §5.1 的压缩输入只有 raw 轮次） |

**四类事件 × 两级白名单（"四级"就是档位 × 黑名单的四种组合）**：

| 事件类别 | 历史级（进 `H`） | 压缩级（进压缩输入） | 出声 | 依据 |
|---|---|---|---|---|
| **`high` 非黑** | ✅ 追加一条 | ✅ **逐条**进 | ✅ 立即（过门槛） | 事件 §4.1 |
| **`mid` 非黑** | ✅ 追加一条（可被聚合） | ✅ **逐条**进 | ✅ 空闲时（过门槛） | 事件 §4.1 |
| **`low` 非黑** | ✅ 追加一条（通常被聚合） | ⚠️ **只有聚合条目进**，单条明细不进 | ❌ 永不 | 事件 §9.1 |
| **`low` + 黑名单** | ❌ **连历史都不进**（入口丢弃，只累加计数） | ❌ **物理上不存在**，不可能进 | ❌ 永不 | 事件 `EV7`/§9.4 |

**五条必须写死的边界**：

1. **低档黑名单事件连历史都不进，因此不可能进压缩。** 这不是靠过滤器保证，而是靠"它根本没被写进 raw 轮次"——**物理不存在比过滤更可靠**（事件 §9.4）。**禁止**在压缩侧再加一层"过滤低档黑名单"：那是多余机制，还会掩盖入口的 bug（过滤掉多少没人看；入口只有计数器 `ax.events.dropped`）。
2. **状态类尾部块（`T1`）与检索块（`<memory>`）永不进历史、永不进压缩。** 它们是**每轮重建的易变块**（A5）：既不是历史条目，就不在 raw 轮次里，也就没有"被压缩抽成记忆"这条路。**这是设计要的**：状态是"值得现在知道"，不是"值得记住"；检索块更是**派生物**——拿派生物去生成记忆会自我循环。
3. **历史级进、压缩级不进的那一档确实存在**：低档非黑的**单条明细**。它进 `H`（模型这一代看得见，玩家三分钟后问"我这把镐还能挖多久"，模型答得出），但逐条灌进压缩单元会**污染摘要**（5 次掉血各写一句，摘要就会写 5 句废话）。
4. **两级白名单解决的就是这一点**：**低档单条明细不该污染摘要，但它的聚合规律应当被记住。**"这片区域在持续掉血""长期缺粮"是记忆该有的东西；"第 37 次掉了 2 点血"不是。所以低档的**聚合形态**才是压缩的原料——**只有重复发生到值得记的事，才配变成记忆**（事件 §9.2 的两句需求口径由此同时成立）。
5. **`<event>` 能进压缩，是因为它在历史里**（v4/F1 的直接后果）。这就是 A5 那条不变量的全部经济学：**落点决定它有没有资格成为记忆原料**。

> **口径归属**：档位 / 黑名单 / 聚合规则 = 事件 §4–§8；两级白名单的完整定义 = 事件 §9.1；压缩输入的内容契约 = 记忆 §5.1。**本文只做一件事：确认运行期不给 `<event>` 加第二条落点、也不让 `T1`/`<memory>` 的字节混进 `H`。** 出现"事件另存一份到尾部"或"把状态快照写进历史以便压缩"即回归。

### 10.1 新增指标

| 指标 | 定义 | 目标 / 阈值 | 违反时的第一嫌疑 |
|---|---|---|---|
| **`delegate_rate`** | `delegate` 轮数 ÷ 有效轮数（千分比） | **区间型**：不宜过高也不宜过低。建议观测基线后钉在 **80‰–350‰**（§11 第 6 项待确认） | 偏高：提示词把 `answer` 也赶去委派，或状态注入不足让模型"什么都要查"；偏低：`delegate` 形态未被模型采用，或 `.query` 字段定义不清 |
| **`delegate_ok_rate`** | `OK` ÷ 全部 ticket | ≥ **0.85** | 工具侧（wiki 超时/限流）或 `COMPLEX` 步数不足 |
| **`complex_run_steps`** | 每次 `COMPLEX` Run 的实际步数（P50/P95/max） | **P95 ≤ 12，max ≤ 25，撞 25 的比例 ≤ 1%** | P95 逼近安全阀 = 工具设计让模型反复试；max 分布长尾 = 某类 query 无解但没被无进展检测拦住 |
| **`complex_run_ms`** | `COMPLEX` Run 挂钟（P50/P95/max） | **P95 ≤ 60s**；撞 120s 的比例 ≤ 1% | 网络工具慢；或 `orTimeout` 没生效（`TASK` 车道不自动超时，03 §9 差距 P） |
| **`no_progress_abort`** | 命中无进展检测的次数 ÷ ticket 数（千分比） | **≤ 30‰** | 偏高：工具返回的错误模型读不懂（§7.3 第 4 条），或提示词没给它"查不到就收尾"的出口 |
| **`abort_reason_dist`** | 六种终态的分布（§5.3） | `ABORT_MAX_STEPS` 与 `ABORT_TIMEOUT` 各 ≤ 1% | 任一超标都是设计问题，不是"任务难" |
