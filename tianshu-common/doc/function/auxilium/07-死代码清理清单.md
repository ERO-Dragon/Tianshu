## 0. 本文怎么用

### 0.1 引用情况四分类（与路线图 §2.4 一致，本文用词固定）

| 引用情况 | 定义 | 本文写法 |
|---|---|---|
| **完全零引用** | main 与 test 里都找不到除自身声明外的任何引用 | `零引用` |
| **仅测试引用** | main 里除自身文件外零引用，test 里有引用 | `仅测试引用`（附测试文件:行） |
| **仅配置/注释引用** | 只被 JSON 资源键、`mixin` 配置、文档或注释提到，Java 侧零引用 | `配置/注释引用` |
| **生产可达** | main 里存在真实调用点 | `可达`（附调用点） |

> **重要口径差异**：路线图 §2.4 把"仅测试可达"单列为一项可达性；本文把"仅测试引用"并入 A 组（生产不可达 ⇒ 删除只影响测试），但在「引用情况」列如实标注，并写明"同提交必须改哪个测试"。理由：路线图判据 2 要求"删除必须同提交改测试"，那它就不是"不安全"，只是"要一起改"。

### 0.2 四组定义

| 组 | 含义 | 处置动作 |
|---|---|---|
| **A** | 可安全删除（生产零引用） | 直接删；只被测试引用的同提交改测试 |
| **B** | 需先改调用方再删 | 删之前必须先落一个前置改动（改测试/改调用点/改资源） |
| **C** | 保留但需修正（语义与既定架构冲突） | 不删，但要改语义或改注释；属功能阶段的任务 |
| **D** | 不确定，需人工判断 | 定性之前不许动 |

### 0.3 一句话结论

**这次普查把路线图 §2.3 的 10 条线索全部复核，其中 2 条判错了、4 条只是"冰山一角"。**
`R-a`（事件去重 4 处）里只有 **1 处是真去重**；`R-d`（STM 只增不删）经查是**设计已改成 append-only，缺的不是方法而是定性**；而 `R-f`（本地 GGUF 残留）真实面不是 18 个文件，而是 **1 个 1250 行的设置页 + 1 个 342 行的推理客户端 + 4 个本地引擎配置键 + 约 60 个 lang 键**；另外发现路线图完全没提的 **protocol/gui + protocol/lifecycle 两个死岛屿（9 类 + 2 类）** 和 **`AXMemoryWindowPolicy` 的 6 个零读者字段**。

## 附录 A · grep 命令与统计口径（可复现）

### A.1 统计口径（三条）

1. **引用 = 类型名/方法名在全仓 `.java` 文本里的词边界命中**（`\bName\b`），不是"import 数"。理由：Java 同包内引用**不需要 import**，按 import 统计会漏掉同包调用（本次普查中 `AXSystemPromptSet`、`AXPromptSectionRenderer` 都属同包引用）。
2. **"生产可达"= main 里除自身文件外至少一处命中，且该处本身可达**。第二段是人工复核的结果——本次有 5 处"有调用点但调用点在死代码里"的链（B1-3、A3-2、A3-5、A3-6、B4-1 的 `vulkanPriority`），全部靠人工回溯到 `LlmModule` 的真实入口才判死。
3. **资源排除**：所有统计排除 `**/bin/**`、`**/build/**`、`**/run/**`（构建产物与运行配置里有同内容副本，会让命中数翻倍）。
