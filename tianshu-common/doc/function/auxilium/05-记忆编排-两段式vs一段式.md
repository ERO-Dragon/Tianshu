## 1. 事实表：旧版设计核准

### 1.1 总体数据流（文档口径）

```
Raw Turn -> STM -> E -> 检索 -> STM 注入
```
出处：记忆 §1（L11-13）。逐项职责：Raw Turn 保真 / STM 语境 / E 定位 / STM 链恢复前因后果 / 检索预算控成本（记忆 §1 L15-21）。

代码实现的真实流向（同一条链，但**多了世界事件直生通道**）：

```
AXRawTurnWindow（内存窗口）
  └─ selectCompressionBatch ──> 调用1：raw 逐行 → 摘要 ──> AXStmBlock（JSONL 追加）
                                        └─> 调用2：摘要 → {"fact"} 数组 ──> AXMemoryEvent（JSONL）
  └─ 附属世界事件缓冲区 ──> 成就类直生 E（绕过 LLM）──> AXMemoryEvent
                                        └─> embedding（EMBED）──> L1/L2 私有 RAG 投影 ──> 检索
```
出处：`AXMemoryMaintenanceService.java:151-217`（run 主流程）、`:187`（直生 E）、`:203-212`（向量 + 投影）、`AXWorldEventMemoryPolicy.java:7-15`（成就直生、其余只 ATTACH）。

### 1.2 STM 队列的确切语义

| 编号 | 事实 | 出处 |
|---|---|---|
| **S1** | STM 是"一段连续对话的压缩语境，不是事实库，是检索命中后恢复前因后果的**叙事容器**"。必须具备：稳定 ID、内容哈希、生成时间与来源时间范围、前后 STM 时序链、完整压缩文本、可携带运行时附属事件视图 | 记忆 §3.2（L96-107） |
| **S2** | 文档对"STM 队列"只有一句：**"STM 队列保留近期若干块。超过保留范围的旧 STM 进入 LTM 原子化流程。"** 队列长度、触发淘汰的判据、每块粒度**均未给出数值（文档未载明）** | 记忆 §4.2（L178） |
| **S3** | 入队时机：实时窗口达到上限时，从**最老对话开始剥离完整轮次**，直到窗口回落到目标范围；剥离内容分两路（世界事件流 / 纯聊天压缩），纯聊天那一路交 LLM 压缩为 STM | 记忆 §4.2（L169-178） |
| **S4** | 剥离粒度是**完整问答轮**：同一 IA turn 下的 user/assistant 与夹在中间的游戏聊天必须同一边界处理，单轮放不下则整轮不注入 | 记忆 §4.1（L160-161） |
| **S5** | 代码里**没有 STM 队列容量、没有淘汰、没有出队**。STM 是 append-only JSONL；`loadRecent(limit)` 只取尾部 N 块供 prompt 的"最近"槽使用，`limit = shortTermChatBlockLimit`，默认 **3** | `AXStmBlockStore.java:28-35`、`AXMemorySystem.java:80`、`AXMemoryWindowPolicy.java:65`（`fromBudget(REFERENCE_BUDGET, 3, 60000L)`）、`:121` |

| **S7** | 单批压缩规模由 token 预算三兄弟决定：触发门槛 `recentRawKeepTokenMax`、压缩后回落目标 `recentRawKeepTokenTarget`、单批目标 `shortTermCompressTokenTarget`。100K 档（`scale = 102400/8000 = 12.8`）≈ **102400 / 64000 / 89600**；单批上限 `shortTermCompressTokenMax` ≈ 128000 | `AXMemoryWindowPolicy.java:58-63,96-125`；`AXRawTurnWindow.java:113-165` |
| **S8** | 但 tokenizer 侧若不可用（云端现状，见 03 §9 差距 B），`selectCompressionBatch` 走**字符预算**分支：`maxRawCharacters = 120000×scale ≈ 1.54M 字符`，且**没有任何轮数上限**。此时一批可以吞掉远超模型窗口的原文 | `AXRawTurnWindow.java:123-143`；`AXMemoryWindowPolicy.java:63,121`；03 §9 差距 B（L1144） |

### 1.3 旧版两次 LLM 调用的确切流程

文档只规定"LLM 干两件事"，没规定调用形态（记忆 §2.2 L35-39）：

> LLM 只做两类工作：① 将原始对话压缩为 STM 文本；② 从 STM 中抽取客观事实列表。

代码把这两件事落成**两次独立的后台 TASK 请求，串行、同一 maintenance run 内 `.join()` 阻塞等结果**：

| 次序 | 调用 | 输入 | 输出 | 参数 | 出处 |
|---|---|---|---|---|---|
| **①** | `ax.memory.compress.{batchId}` | system = `memory.compress.system`（"压缩为一个忠实的对话摘要段落…"）；user = 该批 raw turn 逐行渲染（`{{role}}: {{content}}` / `{{sender}}说：{{message}}`） | **纯文本段落**。无结构、无字段、**无长度上限、无解析校验**（只做 `strip()`） | `maxTokens=0`、`temperature=null`、`stream=false`、`thinking=true`、`lane=TASK`、`taskPriority=600`、`preemptible=true`、超时 120s | `AXMemoryMaintenanceService.java:415-438,219-251,46`；`ax_memory_tasks.json:5-12,21-28` |
| **②** | `ax.memory.extract.{stmId}` | system = `memory.extract.system`（"**从下面这段对话摘要中**抽取客观原子事实…严格 JSON 数组"）；user = `{{stm}}` ＝ **调用①的输出文本** | 严格 JSON 数组 `[{"fact":"..."}]`；失败降级按行解析 | `maxTokens=0`、`thinking=true`、`lane=TASK`、`taskPriority=500`、超时 120s | `AXMemoryMaintenanceService.java:440-456,270-289`；`ax_memory_tasks.json:13-20`；`AXMemoryFactExtractionParser.java:32-94` |

**严格顺序与触发点（代码实测）**：

```
requestMaintenance(scope)                       AXMemoryMaintenanceService.java:106-140
  ├─ 触发点1：提问前   AXRuntimeMaintenanceCoordinator.beforeQuestion      :18-20
  ├─ 触发点2：回答后   AXRuntimeMaintenanceCoordinator.afterAssistantAnswer :22-24
  ├─ 由 running.compareAndSet 串行；车道 ExecutionLane.LONG               :107,113
  └─ run():
       1) batch = selectCompressionBatch(scope)            :156   （空批则整段跳过）
       2) 取该批时间窗内的未挂接世界事件                     :161-165
       3) stm = existingStmFor(batch) ?: compress(batch).join()   :166-167   ← 调用①
       4) appendStmBlock → 回读                            :171-180
       5) if(!hasEventsForStm(stm)) extractEvents(stm).join()     :182-194   ← 调用②
       6) + worldEventLinker.directEventsFor(...) 成就类直生 E     :187
       7) events.appendAll(...)                            :190
       8) confirmConsumed(batch)                           :195-197   ← raw 出窗口
       9) 向量重建 → L1/L2 投影 → 派生维护（链补齐 + stats）  :203-212
```

**关键事实（三点，全部会进后面的对比）**：

1. **调用②紧跟调用①，中间没有"STM 老化"这一步**。文档写的是"旧 STM 进入后台任务…抽取"（记忆 §4.3 L184），代码是同一 run 内紧接执行（`:182-194`）。文档与代码不一致 #2。
2. **两次调用都是"全 miss"**：请求体是 `[system=任务提示词, user=批内容]`，与 CHAT 会话前缀（`S`）**没有一个字节共享**，因此拿不到前缀缓存折扣（03 §5.7 L645-669 的机制在这条链路上**未被使用**）。
3. **两次调用都 `maxTokens=0` + `thinking=true`**。03 §5.9（L733-743）已经写明"thinking 会消耗 completion 预算，`maxTokens` 太小会让正文被截断"，且 03 §附录 A（L1262）明确 `O=0` 视为配置缺失。**今天的摘要与事实抽取就运行在这个组合上**。

补充：调用②是否执行由 `hasEventsForStm` 决定——该 STM 已有**任意一条**事件就整批不再抽取（`:262-268`）。因此"抽了 3 条 / 本该 40 条"不会被发现，也不会补抽。

### 1.4 EventChain 的数据结构、链式发散、深度/广度约束

**(a) 事件（E）字段**

| 层级 | 字段 | 出处 |
|---|---|---|
| 文档要求 | 稳定 ID、文本事实、所属 STM 的 ID 或可校验引用、时间/世界/维度/可选位置、是否空间绑定、可选 MC 实体标签、embedding 引用或可重建版本、embedding 空间标识；**不保存完整父 STM 文本** | 记忆 §3.3（L121-132）、§8.2（L373-380） |
| 代码现状 | `id, fact, factHash, stmId, sourceKind, worldId, dimension, position, spatiallyBound, createdAtMillis, happenedAtMillis, entityTags` | `AXMemoryEvent.java:11-24` |
| 文档要求但**代码没有** | importance、权重、保留建议、命中次数、召回时间、事件级链指针、turn 级来源 | 全仓 grep `importance\|hitCount\|lastHit\|recallCount\|memoryStrength` **零命中**；记忆 §11（L471）"禁止让单条记忆维护动态热度或动态 importance" |

事实抽取时 `dimension/position/entityTags` **一律写空**（`AXMemoryMaintenanceService.java:461-474` 只填 fact/stmId/worldId/时间），只有世界事件直生路径会带 dimension/position/tags（`AXAttachedWorldEvent.java:50-66`）。

**(b) 链的定义**

- 文档：**STM 链**。"STM 链是逻辑链，不要求实现为数据库双向链表。只要能从一个 STM 找到相邻 STM，即可满足链式发散。"（记忆 §3.2 L115）
- 代码：`AXStmBlock.previousStmId / nextStmId`（`AXStmBlock.java:18-19`），由 `AXMemoryDerivedMaintenanceService.normalizeStmChain` 按文件顺序重写补齐（`:31-71`）。**事件之间没有任何链指针**，事件到链的唯一入口是 `stmId`。

**(c) 链式发散的约束**

| 维度 | 文档 | 代码实现 |
|---|---|---|
| 触发条件 | "命中非常集中且置信度较高"才发散；命中分散或问题宽泛时优先选多个不同 STM | `maxRelevance ≥ topScore × chainExpansionScoreRatio(0.82)` **且** `≥ chainExpansionMinScore(0.35)`（`AXMemoryRetriever.java:355-363`，`AXMemoryRetrievalPolicy.java:28-29`） |
| **深度** | "链式发散深度**必须与当前模型档位预算挂钩，不能固定成一个全局常量**"（记忆 §5.3 L254；Prompt §7 L239） | `chainExpansionRadius = 1`（`AXMemoryRetrievalPolicy.java:30`）。**策略恒取 `DEFAULT`，没有任何按档位注入的路径**——`AXModule.java:187` 是 `new AXMemoryRetriever(memorySystem, ragClient)`，测试亦然 |
| **广度** | **文档未载明** | 列表索引窗口 `[center−1, center+1]` 再叠加 `sameChain`（只认直接 prev/next）→ **上界 2 块/中心**（`AXMemoryRetriever.java:336-352,365-376`） |
| 输出顺序 | "按 STM 时序链恢复顺序，并做物理去重；同一 STM 最多出现一次；不因分数高把叙事顺序倒置"（记忆 §5.2 L238） | `selected` 按 `blockOrder`（文件顺序）排序后输出（`AXMemoryRetriever.java:167-173`），`seen` 集合防重复（`:304`）——**与文档一致** |

**在链式发散这条上，这是唯一一处"文档写了硬约束、代码完全没落地"的检索策略**（档位驱动）。它对新方案的影响见 §3.5。

**(d) 检索打分机制（现状）**

| 编号 | 事实 | 出处 |
|---|---|---|
| **R1** | 两层路由，不是全局 Top-K：L1 簇 → L2 事件。阈值 `l1ClusterThreshold=0.56`、`l2EffectiveMappingThreshold=0.92`、`minRoutedL1Clusters=4` | 记忆 §5.1（L205-206）；`AXMemoryRetrievalPolicy.java:21-24`；`AXMemoryRetriever.java:94-121` |
| **R2** | 因子只有两个：**RAG 向量相似度**（L2 hit score）× **线性时间衰减** | `AXMemoryRetriever.java:143,197-206` |
| **R3** | 时间衰减是**乘法**，不是加权项：`relevance = baseScore × factor`；`factor = max(1−0.10, 1−min(0.10, ageDays/3650))` → **10 年才衰到 0.9**，实践中≈常数 | `AXMemoryRetriever.java:203-205`；`AXMemoryRetrievalPolicy.java:26-27` |
| **R4** | **没有 importance**、没有独立 recency 项、没有记忆强度 S、没有召回次数自增 | grep 零命中；对照 03 §4.2（L340-381）、§9 差距 K（L1171） |
| **R5** | STM 贡献分 = `max + log1p(sum)`，且 `sum` 只累加"首次出现的 effectiveMapping"（同一 L2 簇的重复命中不计入 sum） | `AXMemoryRetriever.java:405-425` |
| **R6** | **有 chain 相关逻辑**：选块时把中心 + 相邻 STM 一起纳入（`chainExpansionCandidates`），再受层预算与总预算约束 | `AXMemoryRetriever.java:296-319` |
| **R7** | 三层分档依据是 **STM 的 `maxRelevance`**，不是事件分 | `AXMemoryRetriever.java:229-238` |
| **R8** | 文档设计的三因子 + exp 遗忘 + 5 级 tie-break **均未实现** | 03 §4.2/§4.3；实现见 R2 |

### 1.5 Hot / Warm / Cold 三级流转

| 编号 | 事实 | 出处 |
|---|---|---|
| **H1** | 文档定义：Hot 承接当前语义最强、实体最稳的候选；Warm 补足同簇/近簇相关 STM；Cold 承接低频但仍有恢复价值的历史片段。**比例、阈值、发散深度由预算策略配置化，不写死在代码里** | 记忆 §5.1（L217-223）；Prompt §9（L307） |
| **H2** | 代码把三层落成**三个分数阈值 + 三个预算比例**：`hot=0.60 / warm=0.35 / cold=0.15`；块预算比 `0.6 / 0.3 / 0.1`（cold 由 1−hot−warm 推得） | `AXMemoryRetrievalPolicy.java:20-36,56-85` |
| **H3** | 选择算法：三层各按 `min(本层块预算, 剩余块数)` 与 `min(本层 token 预算, 剩余 token)` 挑；三层挑完若还有余量，再用**全层候选**补一轮 | `AXMemoryRetriever.java:248-266` |
| **H4** | 三层之间**没有流转**：不存在"某记忆从 Hot 降到 Warm"的持久状态。分档是**每次查询的瞬时函数**（依据当次 query 的向量分 × 时间因子）。文档也未要求持久热度状态——二者一致 | 记忆 §11（L471）"禁止让单条记忆维护动态热度或动态 importance"；`AXMemoryStatsSnapshot.java:5-15` 统计只有计数，无命中次数 |
| **H5** | 三层与 STM/EventChain 的关系：**分层对象是 STM 候选**（H2/R7），影响"本次注入选哪些 STM"；E 只在 L2 阶段作为定位锚点，不进 prompt | 记忆 §5.2（L227-238）；`AXPlayerMemoryPromptContributor.java:28-57` 只消费 `AXMemoryBlockView`（其 `block()` 类型为 `AXStmBlock`） |
| **H6** | Cold 还有一条旁路：分数低于 cold 阈值但 >0 的事件，其所属 STM 会被记入 `subColdStmIds`，在链式发散时**被跳过** | `AXMemoryRetriever.java:144-149,345-347` |

## 2. 两个候选方案的形式化

### 2.1 两段式（旧版现状）

```
raw 批（N 轮，约 38.4K token @100K 档）
  ├─ 调用1  [system=compress, user=raw 逐行]   ──> 摘要文本（无结构/无上限）
  │      └─> STM 入队（"最新位"）。注意：代码没有"弹出最老 STM"，见 §1.2 S5
  └─ 调用2  [system=extract, user=摘要文本]     ──> [{"fact"}] ──> E 入库 ──> 检索库
```

- 语义主轴：**摘要 → 事件**（事件必然是摘要的子集）。
- 代价主轴：两次串行 TASK 往返 + 一次不可审计的信息降维。

### 2.2 一段式（新构想）

用户口径 + 本文落成的形式：

```
raw 原文永久保留（归档，压缩只把 raw 移出"注入窗口"）
  └─ 压缩时一次调用 [system=compact, user=raw 逐行]
        ──> 单个 JSON：
              { schemaVersion, batchMeta, summary, events[], coverage }
        ├─ summary ──> M（常驻摘要，紧跟 system，替代被遮蔽前段历史）
        └─ events  ──> 事件库（客观事实，**不去重合并**）──> 检索库
```

- 语义主轴：**raw → 摘要 + 事件（同源、同批、原子）**。
- 关键差异不是"省一次调用"，而是"事件不再从二手摘要抽"。

### 2.3 中间选项 B′（评估用，非用户提出）

保留两次调用，但把**调用②的输入从摘要换成 raw**：

```
调用1 [raw] → 摘要 → M
调用2 [raw] → 事件（保真度与一段式相同，但 raw 被读两遍）
```

这个选项必须放进对比，否则无法回答"保真度到底值多少钱"。

## 3. 十维度对比

先钉住三个公共参数（全部来自 03 与代码，不另行假设）：

| 参数 | 值 | 出处 |
|---|---|---|
| 净增 | ≈130 token/轮 | 03 §5.2（L524）、附录 A.1（L1273） |
| 100K 档每轮成本（中位） | 1839 miss-token 当量 | 03 §6.4（L927） |
| 单批 raw（100K 档稳态） | ≈38.4K token ≈ **295 轮**（102400 触发 − 64000 回落） | §1.2 S7；`AXMemoryWindowPolicy.java:116-119` |
| 命中价 | 未命中的 1/50（0.02 当量） | 03 §0.1（L52）、§6.4（L919） |

### 3.1 保真度：事件从 raw 抽 vs 从摘要抽

| 项 | 两段式 | 一段式 | B′ |
|---|---|---|---|
| 事件的事实来源 | 摘要文本（**已降维**） | raw 原文 | raw 原文 |
| 信息损失层数 | 2 层（raw→摘要的有损 + 摘要→事实的取舍） | 1 层（raw→事实的取舍） | 1 层 |
| 摘要取舍对事件的连带损伤 | **有**。摘要提示词明确要求把"建议/请求/计划/疑问"改写成历史叙述、不保留裸建议句（`ax_memory_tasks.json:6-7`）；被改写得越"叙事化"，可抽的具体事实越少 | 无（事件与摘要并行产出，摘要的修辞规则不作用于 events 字段） | 无 |
| 丢失可检测性 | **不可检测**：摘要里没有的东西，第二次调用永远不会输出；`hasEventsForStm` 只要有 1 条就算"抽过"（`AXMemoryMaintenanceService.java:262-268`） | 可检测：raw 在手上 + provenance(轮号) 在手上 → 覆盖率可算 | 同左 |
| 数量级估计 | 摘要通常压到 300–800 token（03 §5.8.1 给 `C` 的槽位是 ≤800，虽然 STM 当前没有这个上限），事件数量受摘要信息量封顶 | 同一次调用的上下文里保有 38.4K 原文，事件数量上限由输出预算而非输入信息量决定 | 同左 |

**结论**：保真度的差距**不是"两次 vs 一次"造成的，而是"输入是摘要还是原文"造成的**。一段式之所以更好，是因为它天然把 raw 放在模型眼前；若一段式仍要求"先写摘要、再照抄摘要做事件"，它和两段式等价，只是少一次往返。

**判据（写进验收）**：同一批 raw 分别跑 A/C 两方案，比较 `事件数`、`含具体物品/坐标/数量/承诺的事件占比`、`每轮事件覆盖率`。三者至少两项显著优于 A，才值得切换。

### 3.2 隐式过滤 vs 显式判定规则

**两段式的过滤是两处隐式选择**：
1. 摘要阶段：提示词说"保留具体语境和先后顺序"（`ax_memory_tasks.json:6`），但**什么算具体、什么算语境，没有任何清单**；同时被要求"改写成历史叙述"。
2. 抽取阶段：提示词给了 4 条禁令（不输出重要性/保留建议/偏好/性格结论），但**没有一条"必须抽"的正向清单**，也没有"未命中任何规则"的默认动作（对比 03 §4.2 的 importance 规则表，它有 `默认 3`）。

后果：两个模型的两次独立判断叠加，且都不可审计——**你无法回答"这条事实为什么没进库"**。

**一段式的过滤可以做成一份显式规则**（一次调用内）：

| 类 | 判据 | 动作 |
|---|---|---|
| 动作 | 玩家/AX 做了什么（放置、取走、进入、击杀、死亡、合成、丢弃） | **必抽** |
| 状态变更 | 数量、耐久、等级、归属、位置发生变化 | **必抽**（带新旧值） |
| 承诺/计划 | 玩家或 AX 说要做什么、未完成 | **必抽**（记"谁提出"） |
| 偏好/禁止 | 玩家明示喜欢/讨厌/不许 | **必抽** |
| 位置/归属 | 家、矿洞、箱子、领地 | **必抽**（带维度/坐标粗信息） |
| 询问 | 玩家问了什么（不是答案） | **必抽**（记"玩家问了X"） |
| 寒暄/确认 | 嗯、好的、收到、复述 | **不抽** |
| 模型自评/元讨论 | 关于记忆机制、prompt、能力的对话 | **不抽**（记 `meta` 标记） |
| 其他 | —— | **默认抽，且标 kind=other**（宁可多留，符合"不去重、不删真实历史"） |

**关键诚实点**：这份规则写在提示词里，仍然只是"让模型遵守"，不是硬保证。真正的"显式"必须落在代码侧：
- schema 校验（字段/类型/长度）；
- **覆盖率自检**（`coverage` 字段 + 代码侧 `eventsPerTurn`）；
- 低产出告警（如 <0.15 事件/轮 → 诊断 `extraction_low_yield`）。

一段式在这条上仍优于两段式：**规则只有一份、漂移只有一个点**；两段式要维护两份互相耦合的提示词（改摘要风格会静默改变事件分布）。

### 3.3 调用次数与成本（按我们的规模算）

**先说结论：调用次数不是成本杠杆。在 100K 档下，第二次调用只占压缩成本的约 2.6%、每轮成本的 0.19%。真正的杠杆是"压缩请求能不能吃前缀命中"（差 50 倍）与"单批覆盖多少轮"。**

**单次压缩的 token 账（100K 档，38.4K raw/批 ≈ 295 轮）**：

| 项 | 两段式 A | 一段式 C | B′（调用②喂 raw） |
|---|---|---|---|
| 调用1 输入 | 38.6K | 38.6K | 38.6K |
| 调用1 输出 | 0.5–0.8K（摘要） | 1.2–2.2K（摘要+事件 JSON） | 0.5–0.8K |
| 调用2 输入 | ≈1.05K（摘要 + system） | — | ≈38.85K |
| 调用2 输出 | 0.8–1.5K（`{"fact"}` 数组） | — | 1.2–1.5K |
| **合计输入（全 miss）** | **≈39.6K** | **≈38.6K** | **≈77.5K** |
| 合计输出 | ≈1.3–2.3K | ≈1.2–2.2K | ≈1.7–2.3K |
| 每次压缩成本（当量） | ≈39.6K | ≈38.6K | ≈77.5K |
| 摊销到每轮（÷295） | **≈134** | **≈131** | **≈263** |
| 占 100K 中位每轮成本(1839) | **+7.3%** | **+7.1%** | **+14.3%** |
| 相对 A | — | **−2.6%** | **+96%** |

**三个衍生结论**：

1. **A→C 省不出钱**：每轮 −3.5 当量（−0.19%）。若把合并后的 `maxTokens` 从 600+500 提到 1500（输出单价远高于输入），很可能**净成本反而略升**。所以"省一次调用"不能作为选 C 的理由。
2. **C 相对 B′ 省一半**：B′ 用 +7% 的成本买同一份保真度；C 免费拿到。**若保真度是目标，C 严格优于 B′**。
3. **最大的成本项被忽略了**：压缩请求**完全没有复用 CHAT 前缀**（§1.3 事实 2）。若按 03 §5.7 把记忆压缩请求改造成 `S + M + H[..N] + instruction` 形态（压缩批就是 `H` 的头部，逐字节可得）：

   | 形态 | 压缩输入成本/次 | 摊销/轮 | 占每轮成本 |
   |---|---|---|---|
   | 全 miss（现状） | 38,400 当量 | 130 | **+7.1%** |
   | 前缀命中（03 §5.7） | `38,400×0.02 + 120 ≈ 888` | **3.0** | **+0.16%** |

   **这一项的价值（−127 当量/轮）是"合并两次调用"（−3.5 当量/轮）的 36 倍。** 若真要优化记忆链路成本，先做前缀复用，而不是砍调用次数。
   （前提：同模型、同一份 `S` 字节、渲染走同一 `renderTurn`；03 §5.7 L655-660 四条硬要求全部适用。）

**敏感性**（换批次规模时 C 相对 A 的差额基本不变，因为差额是一次固定的小请求）：

| 单批覆盖 N 轮 | A 摊销/轮 | C 摊销/轮 | 差额 | 差额占每轮成本 |
|---|---|---|---|---|
| 150 | 264 | 257 | −7 | −0.38% |
| 295 | 134 | 131 | −3.5 | −0.19% |
| 600 | 66 | 64 | −2 | −0.11% |

### 3.4 摘要与事件的一致性

| 项 | 两段式 A | 一段式 C |
|---|---|---|
| 因果方向 | 摘要 →（派生）→ 事件。**一致性由构造保证**：事件跑不出摘要语义 | 同一份 JSON 的两个字段，**同源同批同版本** |
| 失败原子性 | **非原子**。调用②超时/失败走 `withTaskTimeout` 的 `fallback = List.of()`（`AXMemoryMaintenanceService.java:288,291-300`）→ **STM 已提交、事件全无**，且代码无法区分"失败"与"确实没事实"（都是 0 条） | **原子**：要么拿到完整 JSON，要么整批不提交（`summary` 单独成功时可只提交 M） |
| 静默丢失 | 有：摘要有、事件没有，无人知晓 | 只在 events 字段损坏时发生，且可被 `coverage`/`eventsPerTurn` 发现 |
| 互相污染风险 | 低（单向） | **有**：模型可能为"让事件自洽"改写摘要，或把事件写成摘要复述。需在 instruction 里钉死"两字段独立生成；摘要不得由事件拼接；事件不得引用摘要措辞" |
| 重试语义 | 事件失败只重发 1K 的小请求，**不碰 M、不破坏前缀** | 重发要整批重跑（38.6K 输入）。**但 raw 已归档 → 可以只补抽**（用 raw 走一个纯抽取小请求，不再跑压缩）→ 见 §4.2 护栏 G5 |

**结论**：一致性上 C 是结构性优势（原子 + 同源），A 是结构性缺陷（可产生"有摘要无事件"的中间态且不可检测）。C 的代价是"重试粒度变粗"，可用"分字段提交 + raw 补抽"消掉。

### 3.5 与"保留 raw 原文"新前提的契合度

先把新前提的**现状差距**钉住：**今天 raw 是不保留的**。

```
压缩成功 → confirmConsumed → raw 逐条移出窗口 → checkpoint 整份覆盖写
```
（`AXRawTurnWindow.java:167-194`、`AXRecentDialogueSystem.java:50-64`、`AXRawTurnCheckpointStore.java:28-39`；`writeJsonLines` 是全量重写，被移除的轮次从此任何地方都没有。）

在这个旧前提下，两段式的**立论是成立的**：

> STM 是 raw 被丢弃后唯一的保真替身，所以"先降维成 STM，再从 STM 抽事实"是不得已的次优选择。
> —— 这正是记忆 §3.2（L96）"STM 是叙事容器"与 §4.3 "旧 STM 原子化"的隐含逻辑。

**一旦 raw 常驻，这个立论失效**：

| 问题 | raw 被丢弃（旧） | raw 常驻（新） |
|---|---|---|
| STM 的角色 | 保真替身 + 语境容器（两者合一） | **只剩语境容器/检索折叠单元**；保真由 raw 承担 |
| "从 STM 抽事件"的合理性 | 必要（没别的来源） | **自我限制**：手上明明有原文，却坚持从二手摘要抽 |
| 两段式的额外价值 | 提供降维（省 token） | 只剩"省 token"，而 STM 已不再承担注入主体（M 常驻 + 检索返回 raw 片段） |

**逐条对照**：

1. **契合度 A（两段式）**：中低。它能跑，但它的一半设计动机（保真替身）被新前提抽掉了；剩下的是"先花 38.6K 生成摘要，再从摘要抽事件，而原文就在隔壁"。
2. **契合度 C（一段式）**：高。压缩的唯一职责被明确成两件事——**打索引标签（事件）+ 生成常驻摘要（M）**——两者都从原文一次产出。新前提还额外送来一个红利：**压缩变成可重放操作**（raw 归档在，失败重跑即可，不需要"幂等恢复摘要"）。
3. **必须同时改的一点**：raw 常驻要求窗口与归档分离——`selectCompressionBatch` 仍按 `recentRawKeepTokenMax` 决定"哪些轮次退出注入窗口"，但**不能再删除**，只能打 `archived=true`。否则"新前提"落不了地（§1.2 S6）。

**结论**：新前提削弱两段式、强化一段式。若坚持两段式，就必须重新回答："raw 已经常驻，为什么事件还要从摘要抽？"——本节找不到文档依据支持这个选择（**文档未载明** raw 常驻后的抽取来源规则）。

### 3.6 复用现有代码的程度

|---|---|---|---|

### 3.7 JSON schema 复杂度与失败模式

**两段式**：schema 极简，且已有完整降级实现。

```
输出：[ {"fact": "..."} , ... ]        // 单字段
解析：严格 JSON → 失败则按行降级 → 逐条过滤
```
（`ax_memory_tasks.json:14`；`AXMemoryFactExtractionParser.java:32-94`）

| 失败模式 | 现状处置 |
|---|---|
| 非 JSON / markdown 围栏 | 行降级（`:51-60,126-152`） |
| 元素不是 `{"fact"}` 单键对象 | 该条丢弃（`:80-94` 要求 `size()==1`） |
| 单条超 512 字符 | 丢弃（`:26,97`） |
| 同批重复文本 | 去重（`:100`）← **与新要求冲突** |
| 输出 `[]` | 无法区分"没事实"与"抽取失败" |
| **输出被截断** | JSON 解析失败 → 行降级可能抽到半句话；且**当前 `maxTokens=0` + `thinking=true`**（`AXMemoryMaintenanceService.java:445-455`），截断风险是活的 |

**一段式**：schema 复杂度上去一档，失败模式也上去一档。

```jsonc
{
  "schemaVersion": 1,                       // 必填，未知版本 → 整批不提交
  "batch": { "fromTurnId": "raw_...", "toTurnId": "raw_...", "turnCount": 37 },
  "summary": "……（叙事段落，无条目符号、无 markdown）",
  "events": [
    { "fact": "玩家把钻石镐放进了末影箱",
      "kind": "action",                     // action|state|commitment|preference|location|query|other
      "turnRefs": ["raw_xxx", "raw_yyy"],   // 必填，≥1；用于 provenance 与覆盖率
      "dimension": "minecraft:overworld",
      "position": "",                       // 可选
      "entities": ["minecraft:diamond_pickaxe"] }
  ],
  "coverage": { "turnsWithEvent": 31, "turnsWithoutEvent": 6 }
}
```

**规则**：`events` **不做任何合并**——同一事实重复出现必须各自成条（`turnRefs` 不同即不同条）；`summary` 与 `events` 独立生成。

| 失败模式 | 一段式的处置（必须在实现前定死） |
|---|---|
| **输出截断**（最大风险：摘要 + 事件共用一个 completion 预算，且当前 `maxTokens=0`） | ① 显式设 `maxTokens`（建议 1500–2000，且与 thinking 联立，见 03 §5.9 的警告）；② 输出顺序固定为 `summary` 在 `events` **之前**，截断时仍能拿到摘要；③ salvage 解析：截到最后一个完整的 event 对象为止，其余丢弃并记诊断 |
| **字段漂移**（events 写成字符串数组 / summary 塞进 events[0] / 键名换大小写） | 严格校验 + 显式容错读法（`string | {fact}` 双读；只接受白名单键）；不认识的键忽略但记诊断 |
| **抽取遗漏**（3 件事压成 1 条） | 单靠 JSON 无法发现 → 靠 `coverage` + 代码侧 `eventsPerTurn`；低于阈值告警，**不自动重试**（防风暴，同 03 §5.10 的退避思路） |
| **摘要与事件互相污染** | instruction 显式禁止；抽查规则见 §4.2 G1 |
| **半成功**（摘要好、事件坏） | 分字段提交：提交 M、标记该批 `pending_extraction`、用 raw 走小请求补抽（不重跑压缩） |

**判断**：一段式的 schema 复杂度是可控的（一个对象 + 一个数组），但它把"两个独立的小失败"合成"一个整体的失败"，所以**护栏必须一起上**，不能裸上。

### 3.8 对缓存的影响

| 项 | 两段式 A | 一段式 C |
|---|---|---|
| M（常驻摘要）更新时机 | 每次压缩成功 | 每次压缩成功（同频：≈295 轮一次 @100K） |
| M 变更导致的前缀失效 | **从 M 的第一个字节起**（`S` 仍命中），失效量 = `Ctx − len(S)` | 同左 |
| 100K 档摊销 | +6.5%（03 §5.8.3 L723） | 同左 |
| 是否破坏 `S` | 否（`M` 是独立消息） | 否（只要 M 不被拼进 system） |
| 额外破坏源 | 事件抽取失败后重试**不碰 M** → 不额外破坏前缀 | 若把 events 也塞进 M → **每批都多破一次**（用户口径是 events 进检索库，正确） |
| **实现陷阱（当前代码）** | —— | `AXPromptAssemblyBuilder` 把所有 section 拼成**唯一 system**（`:40-48`）；`player_memory` 现在就走这条路（`AXPlayerMemoryPromptContributor.java:56`）。若 M 顺着这条路径进 system，就是**每 N 轮重新全 miss**（03 §9 缺陷 C 的同款错误） |
| 结论 | 缓存影响相同 | 缓存影响相同，但**必须新增"独立消息"能力**才能不踩坑 |

**补充**：`M` 常驻后，`player_memory.recent`（最近 3 块 STM，`AXMemoryWindowPolicy.java:121`）与 M 内容重叠，若不删就是"同一段历史在一份 prompt 里说两遍"，既费 token 又制造矛盾陈述（对比 03 §3.3 L289-291 的"复用不是追加副本"）。

### 3.9 可追溯性

**现状（两段式）能定位到哪儿？**

```
事件 → stmId → STM.sourceFromMillis/sourceToMillis + sourceTurnCount
```
（`AXMemoryEvent.java:16`；`AXMemoryMaintenanceService.java:461-474` 把 `happenedAtMillis` 直接设成 `stm.sourceToMillis`；`AXStmBlock.java:16-20`）

| 问题 | 事实 |
|---|---|
| 能回答"这条事件来自哪几轮"吗 | **不能**。STM 只存时间区间与轮数，**不存轮 id 列表**（`AXStmBlock` 无 turnIds 字段） |
| 文档是否要求更细 | **不要求**。记忆 §3.2（L101-102）只要求"生成时间和来源时间区间"→ 代码与文档一致 |
| 能否回答"这条事件来自哪句话" | **不能**。`dimension/position/entityTags` 在抽取路径全为空，`sourceKind` 只是 `stm_fact` |

**一段式能拿到什么**：

- 输入就是这批 raw turn（含 `id` / `iaSessionId` / `iaTurnId`，`AXRawTurn.java:7-19`）；
- schema 里要求 `turnRefs`，代码侧映射回 `AXRawTurn.id` 落 `AXMemoryEvent.sourceTurnIds`；
- 于是：**事件 → 轮 → 原文**三级可回溯，且 raw 常驻让第三级真的可达。

**这是两段式结构上做不到的**：第二次调用的输入只有摘要文本，turn 边界信息在第一次调用后就不在上下文里了，模型没有能力给出轮级 provenance。

**顺带的检索红利**（不进本次范围，但要记）：有了 provenance，注入时可以把"120 字摘要行"换成"从 raw 抽 2 行原文"（03 §4.5 L428 的注入摘要问题），证据强度更高且长度可控。

### 3.10 迁移成本与风险

| 项 | 两段式 A（保持现状） | 一段式 C |
|---|---|---|
| 改代码量 | 0 | maintenance 主链路 + parser + 事件 schema（新增字段）+ 提示词资源 + 装配器（尾部/独立消息） |
| 改数据结构 | 0 | `AXMemoryEvent` 加 provenance 字段（**只加不删**，符合记忆 §8 L347-348 的向后兼容红线）；`schemaVersion` 递增 |
| 老数据 | —— | 历史事件无 provenance → 留空，检索不受影响；**不需要迁移脚本**（记忆 §8 L352 "可重建派生数据失效重建，不牵连权威记忆"） |
| 行为变化 | —— | 事件粒度与数量会变（这是目的）。需要灰度开关（按 world 或按 STM 生成时间 cutover），否则老世界的事件分布突然变化无法归因 |
| 失败回滚 | —— | 单批失败不提交 → raw 仍在 → 可重放。**这是新前提给的保险**，必须在实现前先落地（见 §4.4 P-0） |
| 主要风险 | 保真度持续损失且不可自愈；`hasEventsForStm` 让"漏抽"永久固化 | 截断（输出预算不够）与字段漂移；合并输出让"重试"变粗 |
| 风险等级 | 低（不改）但收益为零且持续欠债 | 中（一次性切换），有明确的护栏清单 |

### 3.11 汇总矩阵

| 维度 | A 两段式 | C 一段式 | 胜方 |
|---|---|---|---|
| 1 保真度 | 二手摘要 | 原文 | **C**（决定性） |
| 2 隐式/显式过滤 | 两处隐式 | 一处显式规则 + 可审计 | **C** |
| 3 成本 | +7.3%/轮 | +7.1%/轮 | 平（差 0.19%，忽略） |
| 4 摘要-事件一致性 | 可产生"有摘要无事件" | 原子 / 同源 | **C** |

**计分**：C 赢 5（其中 2 项决定性），A 赢 3（其中 0 项决定性），平 2。

## 4. 推荐

### 4.1 推荐一段式（C），并先落地 raw 归档

**四条理由，按权重排序**：

1. **保真度**：唯一能让事件从原文抽取的方案，且不需要额外成本（对比 B′ 的 +7%/轮，C 是免费拿到同一保真度）。旧版"从摘要抽"在 raw 常驻后没有任何文档依据支持（§3.5）。
2. **可追溯性**：轮级 provenance 是两段式结构上给不出的东西（§3.9）。它同时是"事件不去重合并"的必要配套——不去重就必须能区分"两次相同的死亡"分别是哪两轮，否则库里就是两条无法区分的重复行。
3. **一致性**：原子提交消除了"STM 有、事件无"的不可检测中间态（§3.4）；`hasEventsForStm` 这种"抽过就算过"的判断可以整块删掉。
4. **减债**：净删 3 个方法 + 2 个提示词资源 + 1 个状态判断（§3.6），符合"不留死代码"的要求。

**但必须纠正一个立论**：选 C **不是**因为"省一次调用"——那省的是每轮 3.5 当量（0.19%）。选 C 是因为保真度与可追溯性，成本上 A/C 等价。真正的成本优化项是**压缩请求吃前缀命中**（−127 当量/轮，36 倍于砍调用次数），那是独立的一项，见 §4.4 P-3。

### 4.2 一段式必须补的护栏（G1–G8）

**G1 事件判定规则（资源化，不写进 Java）**
落 `ax_memory_tasks.json` 新键 `memory.compact.system`，内容 = §3.2 的规则表（必抽 6 类 / 不抽 3 类 / 默认抽并标 `other`）。硬要求：
- 规则表与 schema 出现在**同一个 system 提示词**里，不允许拆成两份提示词（否则又回到"两处漂移"）；
- 代码里不允许出现任何中文规则文本（AGENTS.md 硬编码红线）；
- 版本号随 schema 一起递增，旧版本资源不静默覆盖（记忆 §8 L353）。

**G2 单次覆盖轮次上限（双上限）**
现状只有 token/字符上限、**没有轮数上限**（§1.2 S7/S8）。一段式的输出要同时装摘要与事件，批越大漏抽越多。建议：

```
maxTurnsPerCompression = 200         // 轮数硬上限
maxTokensPerCompression = 40000      // token 硬上限（约 300 轮）
选择时取两者先到者；仍超出 → 只取前半批，后半点在下一次压缩
```
理由：输出预算 1500–2000 token 只能容纳约 40–60 条事件（每条 25–35 token）；200 轮按 1 事件/轮的上界刚好压满。超过就是必然漏抽，且漏抽不可检测。
**这条同时也是 §1.7 不一致 #9（字符分支无上限）的修复**——一条配置修两个问题。

**G3 JSON 版本号**
`schemaVersion` 顶层必填，与 `AXStmBlock.SCHEMA_VERSION` / `AXMemoryEvent.SCHEMA_VERSION` 同族。未知版本 → **整批不提交** + 诊断（拒绝静默降级：静默降级等于用旧解析器读新 schema，字段会静默丢）。

**G4 provenance**
每条 event 必须带 `turnRefs`（≥1，指向 `AXRawTurn.id` 或 `iaTurnId`）。校验：
- 空 `turnRefs` 的 event **一律拒绝**（除 `batch.turnCount==0`）；
- `turnRefs` 中出现本批之外的 id → 整条拒绝 + 诊断（防模型编造）；
- 落库时写入 `AXMemoryEvent.sourceTurnIds`（新增字段，只加不删）。

**G5 分字段提交 + 字段级降级**

```
parsed = parse(rawOutput)
if parsed.summary ok      → 提交 M（STM append）
if parsed.events  ok      → 提交 events（不去重）
if summary bad            → 整批不提交；raw 保持未归档；不消费窗口
if events bad && summary ok → 提交 M；标记 batch=pending_extraction
                             下次维护用 raw 走"纯抽取小请求"补（不重跑压缩）
```

**G6 覆盖自检与低产出诊断**
`schema.coverage` + 代码侧 `eventsPerTurn = events.size()/turnCount`。低于 0.15 → 记 `extraction_low_yield`，**不自动重试**（防风暴；对齐 03 §5.10 的退避思路，而不是立刻重发）。

**G7 幂等键（不是去重键）**
`batchId = sourceHash(batch)`（`AXRawTurnBatch.java:54-73` 已有），落库幂等键 = `batchId + turnRef + factHash`。
**幂等 ≠ 去重**：幂等键含批次与 provenance，只防"同一次压缩被重放两次"；不含"纯文本相同就合并"。

**G8 删除现有去重（这是用户明确要求的落地动作）**

| 位置 | 现状 | 改为 |
|---|---|---|
| `AXMemoryFactExtractionParser.java:96-101` | 同批内 `seen.add(sha256(fact))` → 重复事实只留 1 条 | **删掉**（保留 512 字符上限与 U+FFFD 过滤） |
| `AXMemoryEventStore.java:42-48` | 按 `stmId + factHash` 去重 | 改为按 G7 的幂等键去重 |
| `AXStmBlockStore.java:66-76` | 按 id 或 `时间区间+内容hash` 判重 | 保留（STM 是唯一的，去重是对的），但语义改成"同一批只产生一个 STM" |

收益：与记忆 §2.4（L60）"相似事件只要真实发生就都应保留"、§11（L470）"禁止删除真实发生过的相似历史来追求去重"**终于一致**（现状是文档与代码相反，见 §1.7 不一致 #5）。

### 4.3 若坚持两段式：必须承认的四个失效点

1. **STM 的"降维替身"作用不成立**。它原本替代"被丢弃的 raw"（记忆 §3.2 L96）。raw 常驻后，STM 只是"可检索的段落摘要 + 链节点"，不再是保真的唯一来源。继续"只从 STM 抽事件"就是主动放弃手边的原文。
2. **"STM 队列溢出才原子化"从未成立，也不可能成立**。文档的两阶段时序（记忆 §4.2 L178 → §4.3 L182）在代码里是同一 run 内串行（`AXMemoryMaintenanceService.java:182-194`）；而且 STM 根本没有队列淘汰（§1.2 S5）。**两段式的"两段"是两次调用，不是两个时间阶段**——这一点在设计讨论里最容易被说错。
3. **可追溯性天花板**：轮级 provenance 拿不到（§3.9）。而这正是"事件不去重"的前提条件。若选两段式，"不去重"就只能退化为"库里有多条无法区分来源的重复行"。
4. **必须补一条新规则**（文档未载明）：事件只从 STM 抽时，"抽过就算过"的 `hasEventsForStm` 需要改成"按 STM 的 token 数与事件数比例"判定是否补抽，否则漏抽永久固化。

**如果只能做一件事**：把调用②的输入从摘要换成 raw（B′）。它保住保真度，代价是压缩成本翻倍（`39.6K→77.5K`，摊销后每轮 +7%）。**但同一件事用一段式做是 0 成本**——这是选 C 的最直接理由。

### 4.4 分阶段落地
