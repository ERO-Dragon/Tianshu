### 2.2 三条依赖的"为什么"

1. **A 必须最先**：B/C 的所有验收数字都挂在 `W` 上。`tailTokens ≤ 900` 是"全档位硬指标"；`hit_ratio ≥ 0.90` 要按档位分组；`P`（硬预算）与 `T`（水位）由 `W` 算出。在预算还等于 8000 时验收 B/C，等于用错误的标尺量正确的改动，结论无法解释。
2. **D 必须在 B/C 之前**：B/C 改的都是"前缀是否稳定"。没有 `prompt_cache_hit_tokens`，唯一能证明改动有效的观测是"prompt 看起来变短了"——这不是判据。D 把 `hit_ratio` 变成每轮落盘的整数，B/C 才有可执行的验收口径。
3. **B-7（变化检测）的收益依赖 C-1（append-only）**：若历史仍每轮重渲染，即使 T1 判定为"未变化、不追加"，上一轮的 T1 也会在下一轮被重新渲染进历史，前缀照样每轮变。所以 B-7 的代码可以在 B 阶段写完并单测，但**它的线上收益只能在 C-1 之后观测到**——这是本计划最容易做错顺序的一处。
4. **B-1 必须早于 B-4/B-5**：B-1 是唯一"删代码"的起点。先删掉三档，system 才有确定字节，`systemHash` 才有意义；否则 B-9 的 `systemHash8` 会随 B-5 的改动反复漂移，看不出问题。

## 7. P0-D 缓存命中观测（建议纳入 P0）

### 7.1 为什么建议纳入 P0

P0 的全部价值都写在"前缀命中率"上：A 修的是"预算标尺"，B 修的是"system 不再变"，C 修的是"历史不再重渲染"。**这三项的最终效果只有一个度量：同一档位、稳态下 `hit_ratio` 是否从 0 走到 0.90 以上。**

把观测推到 P1 的后果是：

1. **无法验收**。没有 `prompt_cache_hit_tokens`，B/C 的验收只能退化成"看 prompt 变短了"——而 prompt 变短既可能来自"内容搬到尾部"（好），也可能来自"内容被丢了"（坏）。两者无法区分。
2. **无法定位回退**。03 §7.4 的反例清单全部以命中率为第一信号：命中率降到 <0.5 → "有人在改前缀"；`systemHash8` 与 `contextTier` 相关 → "三档没删干净"。这些判断在 D 到位前一个都做不了。
3. **成本不可归因**。DeepSeek 命中单价约为未命中的 1/50（02 §0.1）。没有命中 token 数，就连"这次 P0 省了多少钱"都算不出来，只能凭感觉。
4. **代价极小**。D 只涉及 3 个类 + 1 个 payload 字段扩展，工程量约为 B-6 的三分之一，却让其余 21 步变成"可度量"。

一句话：**A/B/C 是手术，D 是术后监护。没有监护的手术不能算成功。**

### D-1 解析 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`

- **目标**：让字段从 HTTP 帧一路进到 AX。
- **涉及文件**：
  - `.../function/llm/service/OpenAiChatStreamParser.java:31,65-71,112-122`
  - `.../function/llm/service/OpenAiCompatibleInferenceClient.java:446-493`（`readStream` 内的累加）
  - 新建 `.../function/llm/runtime/LlmPromptCacheUsage.java`（`record(int hitTokens, int missTokens)`）
  - 测试：`OpenAiChatStreamParserTest`（若不存在则新建）
- **改动描述**：
  ```
  Event 增加两个字段（可空 Integer）：cacheHitTokens / cacheMissTokens
  解析 usage.prompt_cache_hit_tokens / usage.prompt_cache_miss_tokens
  readStream 累加进结果并在 finish 回调里带出（见 D-2）
  兼容：字段缺失 → 记 0 并不推断（不同 provider 口径不同，禁止用 prompt_tokens 反推）
  ```

- **验收标准**：解析单测覆盖：① 两字段都在；② 只有 hit；③ 都没有（老 provider）；④ 值为字符串/负数（丢弃，不抛）。`mc_gradle(task="tianshu-common:check")` 通过。
- **风险与回滚**：风险 = 各家字段名不一致；缓解 = 缺失即 0，不报错。回滚 = revert。

### D-2 扩 `TokenUsagePayload`，**经 `LLMStreamFinish` 绕开 libs 类型**

- **涉及文件**：

- **风险与回滚**：风险 = `TokenUsagePayload` 是协议 payload，加字段会改变 JSON 形状（若将来序列化到网络）。当前 envelope 是进程内对象直传，无序列化风险；但仍应放在 record 末尾并保留旧构造。回滚 = revert。

## 附录：本批不做但会被反复问到的三件事

1. **"压缩什么时候做？"** —— P2。P0 只有 `hard_drop`（丢整轮、无摘要），它唯一的职责是让长会话不溢出。检查点内容、摘要上限、thinking 用法全部依赖尚未确定的记忆系统设计（见 §1.2）。
2. **"为什么 system 不跟着档位变？"** —— 因为 `S` 落在**命中区**：写全一份的额外成本约 `+54 miss-token 当量/轮`（03 §2.3.1），而按档位切换 system 会让前缀在切换瞬间全 miss。I12 是成本不变量，不是风格偏好。
3. **"命中率没到 0.90，先查什么？"** —— 按 03 §7.4 的顺序：① `systemHash8` 是否在系列内变过；② `game_context` 是否又回到了 system（`grep addContextSection` 应为 0）；③ `snapshotState=appended` 占比是否 >40%（→ B-6 分档不够）；④ `promptHash8` 同输入是否不等（→ B-8 排序不确定）。**不要先调参数。**
