## 0. 术语与记号

| 记号 | 含义 |
|---|---|
| **事件**（event） | 有**发生时刻**的**变化**：一件事从"没发生"变成"发生了"。它一次性、有先后、可计数（§2.1） |
| **状态**（state） | 持续存在的**当前事实**：某一刻世界是什么样。它可重复观测、无"发生"这一说（§2.1） |
| **`<event>`** | 事件在 prompt 里的**载体标签**。**落点已裁决（v2）：作为一条历史消息追加进 `H`**（`world_event` 角色，§2.4）——**三份文档一致**，不再有"同一标签两个落点"（§10.1 第 1 项已关闭，`OP1` 已按"两边都进历史"关闭） |
| **档位**（tier） | 事件的**静态重要性分级**：`high` / `mid` / `low`。它是 `kind` 的属性，**不是实例的属性**（§5.2） |
| **黑名单**（blacklist / `suppress`） | 对某个 `kind` **压制播报权**的标记。**它压的是"出声"，不是"记录"**（§4.4 是唯一例外） |
| **播报**（speech） | 走 TTS 出声。**播报不调模型**（`EV5`） |
| **落历史**（append to `H`） | 追加成一条 `world_event` 角色的历史消息（记忆 §4.1 的角色枚举已预留该值），下一轮及以后模型都能看到 |
| **聚合**（aggregate） | 把窗口内同 `kind` 的多条事件折成**一条**带计数与端点的条目。它只压**粒度**，不压**事实**（§8） |
| **噪音**（noise） | 被聚合门吸收、且不承载任何增量因果信息的单条事件（§9.1） |
| `kind` | 事件的类型标识，**强制命名空间化**：`tianshu:death`、`mymod:ritual_complete`（§3.2） |

| **EV7** | **入口丢弃不登记**：低档 + 黑名单的事件在**入口**就丢弃，不留正文、不进事件环、不参与聚合；**只允许**累加一个计数（`ax.events.dropped`） | 低档黑名单事件的文本出现在任何日志/文件/内存环里 |
| **EV8** | **`payload` 是不可信输入**：调用方文本禁止携带任何尖括号标签，入口做结构性清洗（§3.3） | prompt 里出现 `<event>` 嵌套 `<event>`；或 `tag_leak`（运行时 §8.4 的验收项）上升 |
| **EV9** | **渲染确定性**：事件条目的字节只由 `(kind, payload, 顺序)` 决定，**不含绝对时间戳、不含浮点、不含 `tier` 字段**（§6.4） | 同一条事件两次渲染字节不同；或渲染结果随配置改档位而变化 |

> `EV9` 的后半句（**不渲染 `tier`**）值得单独说：档位是**产品参数**，可被配置覆盖。一旦把 `tier` 写进历史字节，改配置就会让**已发出的历史**与**新渲染**不一致，重放时得到不同 prompt。这与 03 §2.4 的确定性要求（排序、JSON key、NFC、无浮点、无时间戳）是同一类要求。

## 2. 两类信息的分界

### 2.1 一张表定死

| | 事件 `<event>` | 状态（尾部注入 `T1`） |
|---|---|---|
| **本质** | 有发生时刻的**变化** | 持续存在的**当前事实** |
| **例子** | 死亡、进入下界、获得 buff | 准星物品、附近苦力怕、背包剩 3 格 |
| **处理** | **追加进历史**、按档位播报 | **每轮重建**、不播报、不进历史 |
| **可否重复观测** | 否。发生一次就是一次，有先后、可计数 | 是。每轮都可以重新算一遍，算出来一样就一样 |
| **归属文档** | **本文** | 03 §3（维度/阈值/变化检测）+ 运行时 §8.2（`T1` 的装配口径） |
| **典型失败形态** | 把"当前血量 2 心"写成事件 → 每轮都发一条"你血量很低" | 把"刚被苦力怕炸了"写成状态 → 下一轮就消失了，模型永远不知道发生过 |

### 2.2 为什么必须分开（三条理由，一条比一条硬）

| # | 理由 | 展开 |
|---|---|---|
| 1 | **语义不可互换** | 状态是**幂等**的（问一千次答案一样），事件是**非幂等**的（问第二次就是"另一件事发生了"。）把它们塞进同一个通道，模型就分不清"他现在血少"和"他刚才掉血"——而这恰好是两种完全不同的反应：前者该建议吃东西，后者该问"被什么打了" |
| 2 | **成本结构相反** | 状态**每轮重算、每轮必 miss**（03 §2.2：`T1` 是每轮 256 的固定 miss），因此它必须**可重复生成**；事件**只发生一次**，若也走尾部，就要靠"已投递标记"防止重复渲染（运行时 §8.3 的 `deliveredToPrompt`），而历史天然有先后、天然只出现一次。**把一次性事实放进每轮重建的槽位，等于给一个不需要去重的东西专门造一套去重** |
| 3 | **可复现性** | 历史是 append-only 的、可 audit、可压缩成记忆；尾部是每轮丢弃的易变块。**要能被压缩抽成长期记忆的信息，必须先进历史**（记忆 §5.1 的压缩输入只有 raw 轮次）。事件是"值得记住发生过"的那一类，状态是"值得现在知道"的那一类——**记忆只该记住前者** |

### 2.3 落点纪律：同一事实只说一遍（`EV1`）

这是 `T1` 与 `<event>` 双轨运行时唯一的重叠风险，也是运行时 §7.2 已经踩过一次的坑（当时是"状态查询做成工具"导致同一份状态两条注入路径）。这里是同一类错误的另一个入口：

```text
正确：
  T1       : 准星：无目标 | 血量：2 心 | 维度：下界 | 附近敌对：3-5
  <event>  : tianshu:fall_damage  从高处坠落，失去 6 心

错误（同一件事说两遍）：
  T1       : 血量：2 心（上次 8 心，下降 6）
  <event>  : 血量从 8 心掉到 2 心
```

纪律写成三句：

1. `T1` **只描述值**，不描述变化量、不带"上次是…"（03 §3.1 的状态向量本来就是纯当前值，这条只是把纪律说出来）。
2. `<event>` **只描述变化**，不带"现在的值是…"；变化之后的最新值由**同轮或下一轮的 `T1`** 负责。
3. 若某一轮 `T1` 因预算或空段规则未出现（03 D7），**不得**用 `<event>` 顶替它说明当前状态——那是"用事件通道发状态"，理由见 §2.2 第 1 条。

### 2.4 落点：**`<event>` 进历史**（v2 已裁决，三份文档一致）

**定论（v1 是本文的"待裁决提案"，v2 起是三家一致的口径）**：`<event>` 是**追加进历史的消息**（`world_event` 角色），与 `T1` 的"尾部注入"是两条平行的通道。**它不是尾部 `T3` 块，不是每轮重建。** §10.1 第 1 项已关闭，`OP1` 也按"两边都进历史"关闭。

| | 落点 | 每轮是否重建 | 是否进 `H` | 谁负责 |
|---|---|---|---|---|
| `T1` 状态快照 | 尾部 `T1` | **是** | **否** | 03 §3 + 运行时 §8.1 |
| `<event>`（游戏事件） | **历史消息**（`world_event` 角色） | **否**（发生即写一次） | **是** | **本文** |
| `<event>`（委派终态） | **历史消息**（`world_event` 角色） | **否**（终态即写一次） | **是** | 运行时 §6.3/§8.3（⚑ v2：落点已同步；**定档/播出仍归运行时**） |
| ~~`T3`~~ | ~~尾部~~ | —— | —— | **⚑ v2：空置**（无承载者；300 预留位是否回收归 03 再版） |

**为什么必须是历史（本文对"事件是长期记忆唯一原料"的完整论证）**：

1. **记忆只从历史里抽取**（记忆 §5.1：压缩输入 = `S + C_g + 单元内 raw 轮次 + 指令`）。**不在 raw 轮次里，就没有任何被抽成 `E` 的路径**。
2. **尾部块每轮丢弃**。若 `<event>` 是尾部临时块，**"第一次挖到钻石"这类事件下一轮就消失**——它进不了压缩单元，于是永远不会变成记忆。而这恰恰是玩家三天后还会问起的那一类事（"我第一把钻石镐呢"）。
3. **历史天然"只出现一次"**。尾部块需要 `deliveredToPrompt` 这类"已投递标记"去防重复渲染（运行时 v3 的 §8.3 就是这么设计的）；**历史按 append-only 排序，天生不会有重复**——把一次性事实放进每轮重建的槽位，等于给一个不需要去重的东西专门造一套去重（§2.2 第 2 条）。
4. **尾部装不下**。尾块 896（`T1+T2+Q`，`T3` 已空置）里原本给事件留的那 300（03 附录 A.2）根本容不下 44 个 `kind` 的高频事件，必然被总预算挤掉并触发 `event_block_dropped`（运行时 §10.1）报警——**一个"信息永远在丢"的通道不该承载长期记忆。**

> **口径原话（用户裁决）**：**"状态类信息走尾部注入、变化类信息走 `<event>` 追加"**。v1 曾指出"追加"在 03/运行时里被读作"加进本轮尾部"，两种读法字节层面不同；**v2 已按"写进 `H`"统一**（03 v10 §2.1/§2.2、运行时 v4 `A5`/§8.3）。**判据也因此写死**：**有发生时刻的变化 = 事件（追加）；无发生时刻的当前事实 = 状态（尾部重建）**（运行时 §6.3）。

## 3. 对外接口（模组可调）

### 3.1 字段表

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `kind` | **是** | string | **命名空间化**的事件类型：`tianshu:death`、`mymod:ritual_complete`。命名空间 = 提交方 mod id；本地名小写、下划线分词。格式校验见 §3.2 |
| `tier` | 否 | enum | `high` / `mid` / `low`。**省略则查内置映射表（§6）；查不到默认 `low`** |
| `suppress` | 否 | bool | `true` = **强制进黑名单**：只记录（追加进历史）、不播报。**与 `tier=low` 组合时退化为"完全丢弃"**（§4.3） |
| `payload` | **是** | object | `text`（必填，短句）、`count`（可选，int ≥ 1）、`magnitude`（可选，int，语义由 `kind` 定义）、`ref`（可选，短标识：物品 id / 实体 id / 结构 id）。约束见 §3.2 |
| ~~`time`~~ | —— | —— | **不接受调用方时间戳**。时刻由事件总线在入口打（仅用于窗口/冷却计算，**不进 prompt**，`EV9`） |
| ~~`seq`~~ | —— | —— | 由总线单调分配，用于渲染排序与聚合计数。调用方不得提供 |

> **为什么 `payload` 必填而 `tier` 可选**：`kind` 只能表达"发生了什么类型的事"，而"发生了什么"本身需要一点文本。**没有 `payload` 的事件进历史等于往历史里写一个空壳**，模型看到 `tianshu:death` 一个词只会瞎猜。反过来 `tier` 是产品判断，模组作者不该被迫决定 AX 该不该出声——**默认由内置表替他决定，这是"未知一律低档"的落地方式**。

### 3.2 字段纪律

| # | 纪律 | 说明 |
|---|---|---|
| 1 | `kind` 匹配 `^[a-z0-9_.-]+:[a-z0-9_./-]+$` | 不匹配 → **拒绝并记 `event_kind_invalid`**（不是"宽容接受"，否则渲染层要面对非法字节） |
| 2 | 内置表只占 `tianshu:` 命名空间 | 第三方用自己 mod id 的命名空间，**不得**伪造 `tianshu:` 前缀来借用内置档位 |
| 3 | **未知 `kind` 一律 `low`** | **宁可少说，不可乱说**：一个 AX 不认识的事件获得高档播报权，意味着一个陌生模组可以随时打断玩家 |
| 4 | `payload.text` ≤ `ax.events.payload.maxTextChars`（默认 60 字符） | 超长按**整词/整句**裁剪，记 `event_text_truncated`；**不切断多字节字符** |
| 5 | `payload.text` **不得含尖括号** `<` `>` | 入口剥离并记 `event_text_sanitized`（`EV8`；防 `tag_leak`，运行时 §8.4） |
| 6 | `payload.text` 走 NFC 归一化 | 对齐 03 §2.4 确定性规则（同一句的两个 Unicode 写法必须渲染成同一字节） |
| 7 | `count` / `magnitude` 必须是**整数** | 禁止浮点（03 §2.4：无浮点）。血量类语义**统一用心数**，不出现 `6.5` |
| 8 | `payload` **不得携带原始材料** | 不传 NBT、不传多行文本、不传网页片段。这是运行时 `A2`（不回传原始材料）在事件侧的对应物：**进历史的每一行都必须是最终形态**，历史里不做二次改写 |

### 3.3 入口校验与清洗（伪代码）

```text
submitEvent(raw) -> Accepted | Rejected(reason):
    # ① 结构校验（拒绝即丢，不登记）
    if not match(KIND_PATTERN, raw.kind):      return Rejected(event_kind_invalid)
    if raw.payload?.text is null:              return Rejected(event_no_text)
    if not isInteger(raw.payload.count):       return Rejected(event_count_not_int)      # 缺省视为 1
    if not isInteger(raw.payload.magnitude):   return Rejected(event_magnitude_not_int)  # 缺省视为无

    # ② 文本清洗（不拒绝，只清洗）
    text = stripAngleBrackets(NFC(raw.payload.text))     # EV8
    if length(text) > cfg.payloadMaxTextChars:
        text = truncateOnWordBoundary(text, cfg.payloadMaxTextChars)   # 记 event_text_truncated
    if text == cleanTextWasDifferent: 记 event_text_sanitized

    # ③ 补全总线侧字段
    e = Event{
        kind        : raw.kind,
        tier        : raw.tier ?? lookupTier(raw.kind) ?? LOW,        # §3.2 第 3 条
        blacklisted : raw.suppress || lookupBlack(raw.kind) || cfg.blacklist.contains(raw.kind),
        payload     : { text, count: raw.payload.count ?? 1, magnitude: raw.payload.magnitude, ref: raw.payload.ref },
        seq         : nextSeq(),
        atMillis    : now()                            # 只用于窗口与冷却，不进 prompt（EV9）
    }
    return Accepted(e)
```

### 3.4 谁可以提交

| 项 | 规则 |
|---|---|
| 提交方 | **本地客户端模组**（含 AX 自己的采集器）。本设计按纯客户端前提写，对齐运行时 `A1`（无世界动作） |
| 通道 | **本地事件总线，同步投递**。不跨进程、不走网络、不允许异步回调里再提交（避免重入聚合窗口） |
| 反转 | 事件系统是**只读旁听**：它不改变世界状态，也不写回任何游戏对象（`A1` 的推论） |
| 触发模型 | **不得**因提交事件而发起模型请求（`EV5` 的推论）。事件只改历史与播报，**不为它多跑一轮**（对齐运行时 §6.4 末注：成本理由） |

## 4. 操作矩阵（档位 × 黑名单 → 动作）

### 4.1 核心表

| 档位 | **非黑名单** | **黑名单** |
|---|---|---|
| **高**（`high`） | **立即主动播报（1–2 句）+ 追加进事件流** | **只追加，不播报** |
| **中**（`mid`） | **追加 + 缓冲**；玩家空闲 ≥ `midIdleSec` 秒后可主动一次 | **只追加，不播报** |
| **低**（`low`） | **只追加，不播报**（永不主动） | **完全丢弃**（连历史都不进） |

**"追加进事件流"在这里的确切含义**：产出一条 `<event>` 历史条目（§2.4 的落点）。**不是**"登记到某个环形缓冲"，也不是"渲染进尾部"。**⚑ v2**：这也是委派终态的落点（`delegate_*`），两者共用同一标签、同一落点，只靠 `kind` 命名空间区分。

### 4.2 逐格解释

| 格 | 动作细节 | 为什么 |
|---|---|---|
| **高 + 非黑** | ① 立刻产出历史条目；② 若玩家空闲且冷却满足 → **立即出声**（模板句）；③ 忙碌 → 入播报队列（不打断） | 高 = 有即时威胁或不可逆转折。**这类事"晚了就没意义"**——玩家已经在岩浆里了，再等空闲三十秒才说"你正在燃烧"毫无价值 |
| **高 + 黑** | 只有 ①。**永不出声** | 黑名单的唯一含义就是"这件事我知道，但不该由我开口"。典型场景：某个模组的高频高价值事件（如"仪式完成"），玩家不希望每次都被打断，但希望 AX 记得 |
| **中 + 非黑** | ① 产出历史（可能被聚合，§8）；② 入"中档缓冲"；③ 玩家空闲且冷却满足 → **一次播一条**（FIFO）；④ 不满足 → **留到下一个窗口，不丢** | 中 = 有明确游戏收益但不紧迫。**"等你闲下来我再说"正是中档的定义** |
| **中 + 黑** | 只有 ① | 同"高 + 黑"：压播报不压记录 |
| **低 + 非黑** | 只有 ①（且通常被聚合，§8） | 低 = 纯状态波动或肉眼可见。**但"低"不等于"没价值"**：它进历史，其**聚合形态**可被压缩抽成长期记忆（§4.3、§9.1） |
| **低 + 黑** | **入口丢弃**（§3.3 第 ① 步之前就返回）。不计入历史、不参与聚合、不留文本，只累加计数 | 低 + 黑 = **确认无任何后续价值**的噪音。它进历史只会污染压缩单元、推高每轮历史净增、还可能被错误地抽成"记忆" |

### 4.3 低 + 非黑 与 低 + 黑的差别（本文最容易被实现成同一个分支的一处）

两者**都不播报**，于是最省事的写法是"低档直接丢"。**这是错的**，区别在历史与记忆：

```text
低 + 非黑：进历史 ──> 聚合（§8）──> 聚合条目进压缩单元 ──> 可能被抽成记忆（例："玩家在下界持续掉血"）
低 + 黑  ：入口丢弃 ──> 不进聚合窗口 ──> 压缩单元里根本不存在 ──> 永远不可能变成记忆
```

> 单条低档非黑事件**进历史但不独立进压缩**（逐条会灌满压缩单元）；只有它的**聚合形态**进压缩白名单。这条边界在 §9.1 定死，此处先记住"低档非黑能被记住，但要先重复到值得记"。

举两个具体例子把差别钉住：

| 事件 | 档位 | 黑名单 | 结果 |
|---|---|---|---|
| `tianshu:durability_low`（镐子耐久剩 12） | 低 | 否 | 不播报；但下一轮起模型看得到"耐久剩 12"，玩家三分钟后问"我这把镐还能挖多久"时，**模型知道** |
| `tianshu:block_break`（挖掉一个石头） | 低 | **是** | 不播报、不进历史。玩家问"我挖了多少石头"，答案是**读本地状态/统计**，不是读事件流 |

一句话记住：**低档非黑是"留档不扰民"，低档黑是"当作没发生"**。前者是记忆的原料（须先经聚合），后者是噪音。

### 4.4 黑名单只压播报权，不压历史权（唯一例外）

| 说法 | 正确性 |
|---|---|
| "黑名单 = 不进历史" | ❌ **错**。高/中档 + 黑名单**照常进历史**（矩阵第 1、2 行右列） |
| "黑名单 = 不出声" | ✅ 对，这是黑名单的**唯一**语义 |
| "低档 + 黑名单 = 连历史都不进" | ✅ 对，这是**唯一**一处同时压掉历史权的组合（矩阵第 3 行右列） |

> **为什么允许这个例外**：`suppress` 是给模组作者的工具，语义必须可预测。如果 `suppress` 能压掉历史权，作者就会发现"我压了播报，结果 AX 什么都不记得了"——那是**一个开关两种后果**。本文把后果拆开：**`suppress` 永远只管播报；要不要连历史一起丢，由 `tier` 决定**。与 `tier=low` 组合才是"完全丢弃"，且这个组合会在 `OP3` 里复核是否该直接拒绝提交（见 §11）。

### 4.5 三个通道必须分开（与运行时 §6.1 同构）

运行时 §6.1 把委派链路拆成"登记 / 进 prompt / 出声"三个不可互替的通道。本文的事件链路是**同一结构的另一条实例**，拆法也必须是三个：

| 通道 | 载体 | 是否必达 | 受什么约束 |
|---|---|---|---|
| **① 定档** | 内置表 / 调用方 `tier` / `suppress` / 配置黑名单 | 必达（每条事件都要有档位） | 无。判定失败时的兜底是 `low`（§3.2 第 3 条） |
| **② 落历史** | `<event>` 历史条目 | **非黑必达（`EV3`）** | 无。**冷却、忙碌、聚合都不许让它丢失** |
| **③ 出声** | 播报器（TTS） | 按门槛（§4.1 矩阵 + §7 冷却） | 档位、黑名单、冷却、空闲、忙碌 |

**这条分离是设计的一部分**，理由与运行时 §6.1 相同：合成一条就会退化成"冷却期间干脆不记录"，于是 `EV3` 破掉而没人发现。**落历史永远发生，出声看档位与门槛。**

## 5. 档位判定标准

### 5.1 判据表

| 判据 | 高 | 中 | 低 |
|---|---|---|---|
| **有即时威胁**（现在不做点什么就会继续受伤/死亡） | ✅ | — | — |
| **不可逆**（死亡、进入新维度、世界状态永久改变） | ✅ | 部分 | — |
| **有明确游戏收益**（拿到、做成、达成、解锁、交易成） | — | ✅ | — |
| **纯状态波动**（数字变了，但没有新的因果） | — | — | ✅ |
| **玩家肉眼可直接看到**（屏幕/画面上已经有这个信息） | — | — | ✅ |

**读法**：从上往下第一条命中的判据决定档位；**同一 `kind` 命中多条时取最高档**（例：`death` 同时命中"即时威胁"与"不可逆"，取高）。

### 5.2 判据的使用方式（`EV2`）

- 判据是**评 `kind` 的工具**，不是**判实例的工具**。评的对象是"这类事发生时会怎样"，而不是"这次事件的具体数值"。
- 因此判定结果必须能写成一张**静态表**（§6 就是这张表的落地）。**任何需要读实例数值才能定的档位都是设计缺陷**：它会让同一 `kind` 时而高档时而低档，冷却、聚合、观测全部失去意义，且 prompt 字节不再可复现。
- 新增 `kind` 时的动作：按判据评一次，**写进表里**（`tianshu:` 命名空间）或**留给第三方显式给 `tier`**（第三方命名空间）。

### 5.3 "玩家肉眼可直接看到"这一条，为什么必须存在

这一条最反直觉，但它是**噪音控制的主力**：

> **玩家自己能一眼看到的信息，不值得播报。**

展开三句：

1. **语音是抢占式通道**（运行时 §1.4 理由 1）。血条就在屏幕正下方，二分之一秒前那个数字从 8 变成 2，玩家已经看到了。此时 AX 再说"你掉血了"，**信息增量为零，注意力消耗为正**。
2. **"看到了"不等于"懂了"，但这要由 `kind` 来分**。同一个血量变化，`tianshu:health_change`（数字变了）是低档；`tianshu:health_critical`（进入危急档）是高档——因为后者意味着"**现在需要行动**"，那是**语义**，不是数字。**把"可见的数字"和"不可见的语义"分开，是这张判决表能同时防噪和防漏的全部诀窍**。
3. **漏报的代价远小于误报**（同向依据：运行时 §1.4 理由 2——语音助手在游戏里只有"静音"这一种降级手段，**一次误报就会被记住**）。所以判据的取向是**宁可漏，不可多**，这也正是"未知 `kind` 一律 `low`"的同一个取向。

### 5.4 三个裁决惯例（评表时用，避免每次拍脑袋）

| 惯例 | 内容 | 例 |
|---|---|---|
| **H1 成对事件只让一头占高档** | 一对因果相连的事件（A 导致 B），只让**触发因**占高档，**结果**降一档。否则一次流程会被说两遍 | `death` 高 → `respawn` 中；`boss_engage` 高 → `mob_killed`（boss 版）中 |
| **H2 威胁是否仍在** | 威胁**持续存在** → 高；威胁**已经过去但留下因果** → 中；**只剩数字** → 低 | `on_fire` 高 / `fall_damage` 中 / `health_change` 低 |
| **H3 可见 ≠ 可解释** | 屏幕上**看得见形状但看不懂含义**的，可评中档；**连含义也看得见**的，必评低档 | 看得见火焰图标但不知道是"抗火 3s"（`effect_gained` 中）；看得见等级数字（`exp_level` 低） |

> `H2` 是 `damage_taken`（中）与 `health_change`（低）分家的唯一理由：前者带**来源**（被什么打的），后者只有**差值**。`H1` 是 `respawn`（中）与 `death`（高）分家的唯一理由：同一次死亡流程只允许一次高档播报。

## 7. 冷却与频率

### 7.1 四条硬规则

| # | 规则 | 归属 |
|---|---|---|
| **R1** | **全局主动播报间隔 ≥ 60 秒**：任意两次**出声**之间至少 `ax.events.speech.globalMinGapSec`（默认 60）。跨 `kind` 生效 | 防"连珠炮" |
| **R2** | **同一 `kind` ≥ 5 分钟**：同一 `kind` 两次出声之间至少 `ax.events.speech.sameKindMinGapSec`（默认 300） | 防"同一个坑反复提醒" |
| **R3** | **一律排队、不打断**：玩家**正在说话**（ASR 进行中 / 有 `CHAT` 轮次在跑）、**正在听 TTS**、**正在战斗**（最近 `combatQuietSec` 内受到或造成过伤害）→ **入队，不出声** | 同向依据：运行时 §6.2 门槛表（"正在对话 → 排队"） |
| **R4** | **频率不参与档位判定**。频率只决定**聚合粒度**（§8），不决定"这件事重不重要" | `EV2` 的推论：档位是 `kind` 的静态属性，与"发生了几次"无关 |

> **R4 单独强调的理由**：最自然的错误是把"这个事件最近太多"写成"降档到低档"——那会让档位变成实例属性（破 `EV2`），并且一旦玩家安静了十分钟，同一个 `kind` 又"升档回高档"，行为变得不可预测。**正确的旋钮是聚合：不动档位，动粒度。**

### 7.2 播报门（伪代码）

```text
speechGate(e, now, player) -> SPEAK_NOW | ENQUEUE | NEVER:
    # ① 档位/黑名单先拦（矩阵，§4.1）
    if e.blacklisted:                 return NEVER        # 只追加，不播报
    if e.tier == LOW:                 return NEVER        # EV4：低档永不主动

    # ② 忙碌：一律排队（R3）。绝不打断
    if player.isSpeaking() or player.isListeningTts():     return ENQUEUE
    if now - player.lastCombatAt < cfg.combatQuietSec:     return ENQUEUE

    # ③ 冷却（R1/R2）。不满足 → 排队，不丢
    if now - lastAnySpeechAt            < cfg.globalMinGapSec:   return ENQUEUE
    if now - lastSpeechAt[e.kind]       < cfg.sameKindMinGapSec: return ENQUEUE

    # ④ 中档：还要等"玩家空闲够久"（§4.1 第 3 行）
    if e.tier == MID and player.idleMillis() < cfg.midIdleSec*1000:
        return ENQUEUE

    return SPEAK_NOW
```

**三条与队列有关的纪律**：

| # | 纪律 | 说明 |
|---|---|---|
| 1 | **排队不等于丢弃** | 入队的事件**已经进历史**（§4.5 通道 ② 先于 ③）。队列只影响"出不出声"，**永不影响"记没记住"** |
| 2 | **出队序 = 发生序**（FIFO） | 与运行时 `D1`（不合并、FIFO 逐条、相邻两条间隔 ≥ `minGapMs`）**完全一致**。条间间隔**复用**运行时的 `ax.runtime.broadcast.minGapMs`，**不新造同名参数**（"同一个数只有一个定义处"，见运行时 §9.3 的纪律） |
| 3 | **队列有上限，丢播报不丢历史** | 上限 `ax.events.speech.queueMax`（默认 3，对齐运行时 §10.1 的 `speech_backlog ≤ 3`）。溢出时**丢弃最旧一条的播报权**并记 `event_speech_dropped`——历史里那条仍在 |

### 7.3 播报文本的形状（`EV5` / `EV6`）

```text
播报文本 = resourceKey(tier, kind) 渲染 payload 槽位
  资源键命名：ax.events.speech.<namespace>.<localname>      // 例：ax.events.speech.tianshu.death
  槽位：{text} / {count} / {magnitude} / {ref}              // 由 payload 提供，不生成新内容
  句数：1–2 句（高档允许 2 句：一句事实 + 一句指向行动；中档 1 句）
```

| 纪律 | 说明 |
|---|---|
| 不调模型 | 播报**不做二次生成**（`EV5`）。想"带语境点评"是**下一轮对话**的事——玩家开口时，`T1` 与历史里都已经有这条事件 |
| 不出现裸中文 | 代码里只允许资源键（`EV6`；同源要求：运行时 §6.2 措辞纪律） |
| 一条资源键一种语气 | 高档与中档**不复用**同一条资源键（高档可以说"你着火了"，中档不该这么说）。缺失资源键时**降级不出声**，并记 `event_speech_key_missing`（**禁止**用硬编码兜底句） |

### 7.4 冷却与频率的全部配置项

| 配置键 | 含义 | 默认 |
|---|---|---|
| `ax.events.speech.globalMinGapSec` | 全局两次出声的最小间隔（R1） | **60** |
| `ax.events.speech.sameKindMinGapSec` | 同一 `kind` 两次出声的最小间隔（R2） | **300** |
| `ax.events.speech.midIdleSec` | 中档缓冲后，玩家需空闲多久才可主动一次 | 30 |
| `ax.events.speech.combatQuietSec` | 多久没有伤害往来即视为"脱离战斗"（R3） | 15 |
| `ax.events.speech.queueMax` | 播报队列上限（丢弃最旧播报权，不丢历史） | 3 |
| `ax.runtime.broadcast.minGapMs` | **复用**运行时的条间最小间隔，本文不新增 | 见运行时 §6.2 |

> **两个"≥"是产品下限，不是初始值**：`globalMinGapSec` 与 `sameKindMinGapSec` 的默认值本身就是下限语义（60 / 300）。允许部署方**调大**；调小时必须在配置文档里写明"违反 §7.1 的 R1/R2 设计意图"。默认值不得改小。

## 8. 聚合规则

### 8.1 目的：只压粒度，不压事实

聚合解决的是"一个 `kind` 在短时间内发生很多次"的情况。它**不改变档位**（R4）、**不丢事件**（`EV3`）、**不改变历史的先后语义**——它只把"5 条单条"换成"1 条带计数的条目"。

```text
聚合前（5 条历史条目）：
  tianshu:health_change  失去 3 心
  tianshu:health_change  失去 2 心
  tianshu:health_change  失去 4 心
  tianshu:health_change  失去 1 心
  tianshu:health_change  失去 2 心

聚合后（1 条历史条目）：
  tianshu:health_change  血量多次下降（5 次，20→8）
```

### 8.2 触发与窗口

| 项 | 规则 |
|---|---|
| **适用档位** | **只对 `mid` 与 `low` 生效。`high` 永不聚合**（§8.4） |
| **窗口** | 同 `kind` 的连续事件，相邻两条间隔 < `ax.events.aggregate.windowSec`（默认 30）即视为同一窗口；超过则关窗 |
| **折与不折** | 窗口内条数 ≥ `ax.events.aggregate.threshold`（默认 3）→ 折成一条聚合条目；< 阈值 → 关窗时把单条**原样**写出（不聚合，因为聚合本身是额外损失） |
| **关窗时机（三个之一）** | ① 窗口超时；② **任一"轮次装配"开始前强制 flush**（关键，见 §8.5）；③ 会话结束（flush 后写出） |

### 8.3 聚合条目的形态

| 字段 | 内容 | 例 |
|---|---|---|
| `kind` | 原 `kind`（不变） | `tianshu:health_change` |
| `count` | 窗口内条数 | `5` |
| 端点 | **首值 → 末值**（有 `magnitude` 时必给） | `20→8`（心数） |
| 极值 | 窗口内 `min` / `max`（有 `magnitude` 时给，用于"最大单次伤害"这类追问） | `max 4` |
| `text` | **模板渲染**的聚合句（资源键 `ax.events.aggregate.<kind>`），**不是把原文拼起来** | "血量多次下降（5 次，20→8）" |

**为什么端点 + 极值就够**：玩家与模型真正会问的是"掉了多少""最狠的一次多少""现在还剩多少"。前两个在聚合条目里，最后一个在 `T1` 里（§2.3 的分工在这里又生效一次）。**把 5 条原文拼起来既超长又会让模型以为发生了 5 次独立事件**，那是信息失真，不是信息保留。

### 8.4 高档永不聚合

`high` 档的事件**逐条**落历史、逐条过播报门。理由两条：

1. **高档的语义是"这次很要紧"**，折成"死亡 5 次"会把"第几次"这个序丢掉，而玩家恰恰会问"我刚才是怎么死的"（第一次还是第三次）。
2. **高档本身已经有两道节流**：全局 60 秒（R1）与同 `kind` 5 分钟（R2）。**聚合对它是多余的**，而多余的机制一律不加。

### 8.5 装配前 flush（否则会丢事件）

聚合窗口会推迟"事件进历史"的时刻。若在此刻**恰好有一轮装配开始**，历史里就会缺掉窗口内的事件——玩家问"我刚才掉血了吗"，模型会说"没有"。

```text
assembleTurn(session, playerInput):
    aggregator.flushAll()          # ① 关掉所有未超时的窗口，写出条目（一条或原样多条）
    ...                            # ② 之后才做 03 §2.1 的五段装配（顺序与形态归 03，本文不动）
```

这条 flush **不改变任何预算与字节结构**（它只是让 `<event>` 条目就位），因此与 03 的装配顺序不冲突。它也是 `EV3`（非黑必达）在实现上唯一的正确落点。

### 8.6 聚合伪代码

```text
aggregator.onEvent(e, now):
    if e.tier == HIGH:                        # §8.4
        appendHistory(e); return

    w = windows.get(e.kind)
    if w == null or now - w.lastAt >= cfg.windowSec:
        w = newWindow(kind=e.kind, firstAt=now)
        windows.put(e.kind, w)
    w.items.add(e); w.lastAt = now

aggregator.flush(kind):
    w = windows.remove(kind); if w == null: return
    if w.items.size >= cfg.threshold:
        appendHistory(aggregateEntry(
            kind    = w.kind,
            count   = w.items.size,
            first   = w.items.first.magnitude,
            last    = w.items.last.magnitude,
            min, max= extremes(w.items.magnitude),
            text    = resource(cfg.aggregateKey(w.kind)).render(...)   # 模板，非拼接
        ))
    else:
        foreach e in w.items: appendHistory(e)                     # 未达阈值：原样写出

aggregator.flushAll():  foreach kind in windows.keys: flush(kind)   # §8.5
```

## 9. 与压缩白名单的关系

### 9.1 两级白名单（本文对"压缩只接收什么"的完整口径）

压缩输入（记忆 §5.1：`messages = S + C_g + 单元内 raw 轮次 + 指令`）里允许出现的内容，**分两级定义**：

| 级别 | 白名单 | 谁定义 | 作用 |
|---|---|---|---|
| **历史级**（能进 `H` 吗） | 玩家输入 + 助手回答 + **所有非黑名单的 `<event>`**（高 / 中 / 低非黑） | 本文 §4.1 矩阵 | 决定"模型下一轮能不能看到" |
| **压缩级**（能被抽成记忆吗） | 玩家输入 + 助手回答 + **高/中档 `<event>`** + **低档的聚合条目** | 本文 + 记忆 §5.1 | 决定"能不能变成长期记忆" |

**关键点：低档非黑事件单条不独立进压缩白名单，但它的聚合条目进。**

> **⚑ v2：这条口径已被运行时文档镜像为 §8.7「四级白名单与压缩输入边界」**（v4 新增）——它用"高 / 中 / 低非黑 / 低黑"四类事件 × "历史级 / 压缩级"两级白名单给出同一张判定表，并写死两条：① **低档黑名单连历史都不进，因此不可能进压缩**；② **状态类尾部块（`T1`）与检索块（`<memory>`）永不进历史、永不进压缩**。**完整定义仍在本节与 §9.5**，运行时那边只做运行期边界登记，不重复定义档位与聚合规则。

### 9.2 为什么这样切（对一句口径差异的收敛，登记在 §10.2）

本设计的原始要求里有两句话看起来互相矛盾：

- **需求口径 · 矩阵那一节**：**"低 + 非黑 进历史，可能被压缩抽取成记忆"**
- **需求口径 · 白名单那一节**：**"压缩输入只接收玩家输入、助手回答、档位为高/中且未被聚合成噪音的 `<event>`"**

如果把"压缩只收高/中"读成逐字结论，那低档非黑就永远抽不成记忆，前一句就成了一句空话。**本文用两级白名单把两句同时兑现**：

```text
低档非黑单条：  进历史 ✅      进压缩 ❌（逐条出历史，构成压缩输入的噪音）
低档非黑聚合条：进历史 ✅      进压缩 ✅（5 次掉血 → 一条"持续掉血"，这才是记忆）
```

这样得到三个好处：① 低档的记忆化路径存在且**只走聚合**（也就是只有"重复发生"才值得记）；② 压缩单元的 token 不被逐条低档事件灌满（否则每轮历史净增会失控，见 §10.4）；③ 后一句"未被聚合成噪音"获得了**精确含义**（§9.1 表格第二行）。**这不是折中，是把"低档非黑有价值"这句话具体化成"它的聚合形态有价值"。**

### 9.3 送入压缩的形态（不新造结构）

| 项 | 落法 | 对齐处 |
|---|---|---|
| `<event>` 在 raw 里的角色 | `world_event` | 记忆 §4.1 的 Raw Turn 角色枚举**已预留** `world_event`，本文直接使用，**不新增角色值** |
| 压缩单元内边界 | 一条 `<event>` 计为**该轮的一部分**，不独立成轮 | 记忆 §4.1 规则 7 / 03 P1：分区与切分以「一轮对话」为粒度，绝不切断单轮 |
| 是否成为 E | 由压缩指令层判断（"这条事件是否构成值得长期记住的事实"），本文**不规定**抽取结果 | 记忆 §5.2 的 `eventChain`；本文不改其 schema |
| 低档聚合条目 | 作为**该窗口所在轮的**一部分进入压缩 | 同第一条 |

> ⚠ **再次强调（运行时 §8.3 已有同款警告）**：`<event>` 里的"事件"与记忆里的 **Event（E）** 不是同一个东西。前者是"刚刚发生的事"，后者是"被压缩抽出来的、可检索的历史原子事实"。**本文产出的 `<event>` 是压缩的输入之一，不是输出。**

### 9.4 低档黑名单为什么"不可能"进压缩

不是靠过滤器保证，而是靠**物理不存在**：

```text
低档黑名单 → 入口丢弃（§4.3）→ 不进聚合窗口 → 不产生历史条目
          → 压缩单元的 raw 里没有它 → 无法被抽取
```

这是三级挡板的第一级（最前面那一级）。**在压缩侧加"再过滤一次"是多余机制**，而且会掩盖入口的 bug（过滤掉的数量没人看）。唯一允许的观测是入口计数器 `ax.events.dropped`（只计数，不记正文，`EV7`）。

### 9.5 压缩侧过滤伪代码（只处理"历史里有但压缩不要"的那一类）

```text
buildCompactInput(unitTurns):
    out = []
    foreach turn in unitTurns:
        out.add(turn.user); out.add(turn.assistant)
        foreach e in turn.events:                       # world_event 角色的条目
            if e.tier in {HIGH, MID}:      out.add(e)   # 高/中：逐条进
            elif e.isAggregate:            out.add(e)   # 低档聚合条目：进（§9.1）
            else:                          skip(e); compactSkipped++   # 低档单条：只计诊断，不记正文
    return out
```
