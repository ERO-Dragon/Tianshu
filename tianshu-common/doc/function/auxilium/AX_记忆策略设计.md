## 1. 文档定位

本文是 AX 记忆系统的架构大纲 + 已冻结的关键数值表，不是最终字段协议或实现规格。字段全集、索引格式、聚类参数仍需在实现阶段冻结；但 §5/§6/附录 A 里的数值是**决策结果**，实现不得自行改动，改动必须回到本文。

AX 是记忆策略的所有者；LLM 模块只提供推理、embedding、RAG cache 与协议通信能力，不决定 AX 记住什么，不维护 AX 记忆生命周期。

总体思路（数据流）：

```text
注入窗口: [压缩窗口（待换代）][保持窗口 KEEP_rounds 轮真实原文（39/78/157/378）]

Raw Turn ──(每 60 轮一个压缩单元)──> 压缩（单次调用）
   ├─> summary ──> 单元摘要块（generation=g, unitIndex=i，持久保存；**不进 prompt**）
   ├─> eventChain（每条含 importance）──> E / LTM ──> 向量投影（**state=active 期间不可检索**）
   └─> preferences ──> E（kind=preference；按玩家 UUID 跨世界）
Raw 归档（append-only，永不移除）←── 换代时整段移出压缩窗口

换代（压缩窗口占满，纯本地动作，不发模型调用）：
   本代 k 份单元摘要 ──> 摘要块 C_{g+1}（≤ SB(tier)，装不下时久远的先淘汰）
   压缩窗口整段 ──> 归档并移出 prompt
   旧代 state: active → superseded ──> **其事件从此刻起参与检索**

检索：query ──> E 命中 ──(沿 EventChain 链式发散)──> Event 列表（≈12 条 / ≈360 token）──> T2（尾部）
                 └──(Event → 单元摘要块 → generation/unitIndex)──> 具体那份摘要正文
                   （回查 / 发散遍历 / 审计；本版不作为注入正文）
```

各层职责：

- **Raw Turn** 负责保真，且是**唯一**的原文权威层；压缩、摘要、事件抽取都是它的派生。
- **STM（单元摘要块）** 负责语境；本版里它兼任三件事：① 摘要块 `C` 的组成单元 ② 链式发散的可遍历链 ③ **检索归集的目标**（`E.stmId → (generation, unitIndex)`）。
- **E（EventChain 的元素）** 负责定位，带轮级溯源 `turnRefs`，自带走抽取时打好的 `importance`，并带**检索可见性**（由所属代的 `state` 决定）。
- **检索**负责在"封存代"的历史里捞回事实——**这是摘要不跨代累积的前提**（§5.3）。
- **注入**的载荷是 **Event 列表**，不是摘要正文（D2），且必须与 03 的尾块纪律一致（§6.6）。

## 2. 设计原则

### 2.1 模型无关

2B、本地 12B、云端模型走同一套流水线。模型切换只影响档位（`W`）、prompt 复杂度、注入条数与发散深度，不改变记忆架构。

不同档位可以拥有不同的检索布局：链式发散深度（`chainDepth`）与广度、检索候选池大小。这些**必须**通过 `AXMemoryRetrievalPolicy.forTier(tier)` 与 `AXMemoryWindowPolicy.forTier(tier)` 提供，**不得硬编码**（现状违反此条：策略恒 `DEFAULT`，见 §11.1 B14/B15）。

> **v3 更正（D2）**：**记忆注入预算不再随档位放大**。注入载荷是 Event 列表（典型 12 条 ≈ 360 token），落在 `T2` 的 512 预算内；尾部是每轮必 miss 区，按 03 §2.2 的纪律**全档位不放大**。档位在记忆侧的差异只剩"能发散几跳"与"候选池多大"。

### 2.2 工程代码兜底

时空坐标、世界归属、实体标签、记忆选择、聚类、预算分配、链式扩展、**打分与分档**全部由 AX 代码负责。

LLM **只做一件事**：把一个**压缩单元**（≤60 轮，§5.4）的 raw 对话**一次性**产出为三要素 JSON（§5.2）——`summary` / `eventChain`（**每条自带 `importance` 与 `turnRefs`**）/ `preferences`。上一版的"两件事、两次调用"作废；**`importance` 由这一次调用顺带产出，不新增任何调用**（D4）。

这条改动的实质不是"省一次调用"（05 §3.3 已算清：省的是每轮 3.5 当量，占 0.19%，可忽略），而是**事件不再从二手摘要抽取**：原文就在同一次调用的上下文里，保真度与轮级溯源才有结构上的保证。

### 2.3 客观事实第一性 + 偏好限界（改写）

长期记忆的主体是**客观事实型原子事件**。允许：

- 玩家把钻石镐放进末影箱。
- 玩家在下界死亡一次（同日死亡第二次就再记一条，§2.4）。
- 玩家说自己正在寻找村庄。
- AX 曾提醒玩家带食物。

仍然禁止：主观重要性判断、情绪价值判断、"应该永远记住"这类保留建议、**由模型推断出的**性格结论。

**关于 `importance` 的边界（v3 新增，D4）**：`importance` 允许由模型在抽取阶段打分，但它与上面禁止的"主观重要性判断"不是一回事——

| | 被禁止的 | 被允许的 `importance` |
|---|---|---|
| 形态 | 自然语言结论（"这条很重要，应该永远记住"） | 单一整数 `1–10`，是**检索权重**，不是保留建议 |
| 语义 | 情绪 / 价值判断 | "这条事件对后续问答的信息量"，可比、可回放、可校验 |
| 校验 | 无从校验 | 代码 `clamp(1,10)`；漏填/越界走规则表兜底；与规则分偏差 ≥3 计入 `importance_drift`（§6.3） |

一句话：**允许给分，不允许给结论**。

**偏好要素（新增）的三条限界**——它是对上一版"禁止一切偏好"的**有限放开**，不是推翻客观性原则：

| 限界 | 规则 |
|---|---|
| L1 只收明示 | `preferences[].confidence` 只能是 `explicit`；判定依据是**玩家原话里出现明示倾向表达**（喜欢 / 不喜欢 / 别 / 不要 / 以后都 / 每次都）。模型推断出的倾向一律丢弃，代码侧校验：`explicit` 且 `evidenceTurnRefs` 非空，否则整条不落库 |
| L2 不落性格结论 | 禁止"玩家性格急躁""玩家是新手"这类跨事件概括；`preferences[].target` 必须是**具体对象**（物品 / 方块 / 行为 / 地点），不是人格形容词 |
| L3 可被覆盖，不可被删除 | 新偏好与旧偏好冲突时**追加**新条目（`supersedes` 指向旧条目），不删除旧记录——与 §2.4 一致 |

### 2.4 真实历史不可篡改（加强）

- 相似事件只要真实发生，就都应保留。**存储层不为"去重"删除真实历史**（上一版 §2.4 已写，但代码全反，见 §11.1 A6/A7）。
- 本版把这条升级为**判定规则**：两条事件只要 `turnRefs` 不同即为两条不同事件；任何以"文本相同"为由的合并都是缺陷，不是优化。
- 检索层可以为了本次 prompt 预算做候选到 STM 的有效映射、代表选择和结构化截断，**只影响本次注入，不改变记忆本体**。
- 压缩、摘要、抽取都是 raw 的派生；派生出错时重放 raw 即可，**不得反向修改 raw**。

### 2.5 不过早冻结细节

以下内容**仍不在本文冻结**：具体字段全集、相似度阈值（`l1ClusterThreshold` 等）、聚类分裂/合并参数、embedding 维度与空间标识、归档文件的物理格式。

以下内容**本版已冻结**，实现不得自行取值：四档 `W/T/B/R`（03 §5.1）、压缩单元判据 60 轮 / 40,000 token 与队列串行（§5.4）、**摘要生成长度"不设限"这条结论**与**摘要块上下文预算 `SB = clamp(0.05×W, 2048, 24576)`**（§4.4、附录 A.2）、注入条数与 token 预算（§6.4、附录 A.2）、衰减常数与地板（§6.2）、importance 的模型打分契约与规则兜底表（§6.3）、分档线与比例（§6.4）、发散档位表（§6.5）、护栏 G1–G8（§10）。

> **⚑ v5 冻结项变更**：v4 冻结的是"摘要软指引与硬上限"；**v5 冻结的是"不设上限"这条结论本身**——任何人给摘要加字数上限（包括 200–600 的软指引）都算破坏冻结项。`SB` 也不再用固定值，而是按档位公式算，**不得硬编码 2560/5120/10240/24576 之外的自定义值**。

| **窗口边界 / 分区边界** | 两条：① `压缩窗口` 与 `保持窗口` 之间；② **压缩窗口的头部**（换代时整段移出） | 无 | §5.3 的核心 |

| **护栏 Gn** | 一段式必须同时上线的 8 条硬约束 | 05 §4.2 提出 | §10 |

### 3.2 两组必须钉死的易混术语

**(a) STM 链 ≠ EventChain**

| | STM 链 | EventChain |
|---|---|---|
| 节点 | STM 块 | 事件（E） |
| 指针 | `previousStmId / nextStmId`（双向） | 无事件间指针；靠 `stmId` 归集 + `turnRefs` 溯源 |
| 用途 | 链式发散，恢复故事线顺序 | 轮级可追溯、覆盖率自检、跨会话检索 |
| 本版是否改动 | 不改（沿用 §3.2 原文"逻辑链，不要求实现为数据库双向链表"） | 新增 |

一句话：**"记忆链"是 STM 链，不是事件链**（05 §0 的结论）。事件到链的唯一入口仍然是 `stmId`，本版只是给它补上了 `turnRefs`。

**(b) "摘要" 与 "E → STM 归集" 是两件事**

- 摘要：对一个**压缩单元**做的**语义接续**，先入记忆库（**不进 prompt**）；**换代时**整代的 k 份一起渲染成摘要块 M（§4.4）。
- E → STM 归集：把**检中的** E 沿 `stmId` 映射回它所属的 **STM 摘要块**。v3 把它的两种用途分开写清：
  1. **可达性（D1）**：命中 E 就能取回那一段的摘要正文——所以"摘要滑出窗口就再也用不到"**不成立**；
  2. **注入载荷不是它（D2）**：进 prompt 的是 **Event 列表**；摘要正文只用于发散遍历、回查与审计。
- 两者都不改变记忆本体；归集不是去重（§2.4）。

## 4. 核心对象

### 4.1 Raw Turn（保留 + 两态）

Raw Turn 是玩家与 AX 的原始对话轮次记录，是最接近真实历史的保真层。表达内容沿用上一版 §3.1：

- 角色（`user` / `assistant` / `world_event` / 游戏聊天来源）。
- 文本。
- 可选发送者，用于游戏聊天 topic 等非二元对话来源。
- 时间。
- 与 IA session / turn 的关联（`iaSessionId` / `iaTurnId`）。
- 精确 token 或可用于窗口控制的长度信息（`tokenCount` / `characterCount`）。

**本版新增：raw 只有两种状态，没有第三种。**（**v4（F1）补充：raw 在 prompt 侧还按「压缩窗口 / 保持窗口」分区，但那是渲染切片，不是状态——状态只有下面两种。**）

| 状态 | 含义 | 可否回溯 | 触发转移 |
|---|---|---|---|
| **在窗口**（`inWindow=true`） | 属于当前注入窗口，会被渲染进 prompt 的历史段。**v4：它内部再分两段——压缩窗口（已出摘要、原文仍在）与保持窗口（最近 `KEEP_rounds` 轮）** | 是 | 移出窗口（只在**换代**时发生） |
| **已归档**（`archived=true`） | 不在 prompt 里，但在 append-only 归档文件中 | 是 | 无（终态） |

规则：

1. **raw 永不删除**。"压缩成功 → 从窗口移除 → 归档"三件事必须原子完成：归档写成功后才允许标记移出窗口（否则 replay 会丢原文）。
2. 归档文件 **append-only**，不得与 checkpoint 混写，不得整份覆盖（上一版 checkpoint 是 `writeJsonLines` 全量重写，见 `AXRawTurnCheckpointStore.java`）。
3. "按容量裁剪"这一条从上一版保留，但语义收窄：只裁"尚未归档的窗口内轮次"，且只在**崩溃恢复**路径允许（把超长窗口压回容量），正常路径由**换代**驱动。
4. 压缩任务必须基于**只读快照**执行，不阻塞当前对话（沿用上一版约束）。
5. 游戏聊天消息属于 Raw Turn 来源之一，参与压缩与摘要；不等同于世界事件，不直接作为 E（沿用上一版 §3.1）。
6. **v4 新增（F1）：保持窗口是硬约束（⚑ v6：按档位 `KEEP_rounds` 轮 = 39/78/157/378，且不得低于 20 轮）。** 它们永远 `inWindow=true` 且永远逐字渲染；`archived` 转移只发生在压缩窗口上。**任何让保持窗口缩短的路径都是缺陷**（崩溃恢复也不行——恢复时宁可用 `hard_drop` 记录一次降级）。
7. **v4 新增（F1）：分区边界以「一轮对话」为粒度**。一轮的 `user` 与其 `assistant` 回复永远同属一个分区（对应 03 的 P1 分区纪律）。

### 4.2 STM（保留 + 代次与槽语义）

STM 是短期记忆块，保存一段连续对话的压缩语境。上一版 §3.2 的必备项全部保留：稳定 ID、内容哈希、生成时间与来源时间范围、前后时序链、完整压缩文本、可携带运行时附属事件视图。

**本版新增与改写：**

| 项 | 规则 |
|---|---|
| `generation`（改写，**v4 F5**） | **代次**：该块属于第几代摘要。**换代时 +1**，同一代内所有单元块共享同一个 `generation`。只加不删（存储向后兼容红线） |
| `unitIndex`（**v4 新增，F5**） | **代内序号**：`1..k`，与 prompt 里 `<unit_summary index="{i}">` 的属性**必须一一对应**。这是"`Event → 摘要块` 能定位到具体哪一份"的关键字段 |
| `sourceFromTurnId` / `sourceToTurnId`（沿用） | 本块**摘要覆盖的** raw 轮次区间端点；必须等于**一个压缩单元**的首尾轮 id |
| `sourceTurnCount`（沿用） | 必须等于该单元的轮数，且 `≤ 60`（§5.4） |
| `content`（语义收窄） | 只包含**本单元**的摘要文本；**不得**包含更早代次的内容，也**不得**包含同代其他单元的内容（§5.3） |
| `state`（**v4 新增，F4**） | `active`（本代，在 prompt 的摘要块里 → **其事件不可检索**）/ `superseded`（已被下一代替换 → **其事件可检索**）。**换代时整代一起翻转** |
| 链关系 | `previousStmId / nextStmId` 按**提交顺序**补齐（同代内按 `unitIndex`，跨代按 `generation`），语义不变（供链式发散） |
| **块内可见性（v4；⚑ v5 改措辞）** | prompt 的摘要块只渲染 `state == active` 那一代里**通过淘汰规则**的单元（v5：= `unitIndex` 的连续后缀，最靠边界的那批）；`state == superseded` 的代与被淘汰的单元都只在存储里 |

> ⚠ 上一版说"STM 队列保留近期若干块，超过保留范围进入 LTM 原子化"。**这句话作废**：代码里从来没有 STM 队列、没有淘汰、没有出队（05 §1.2 S5）。本版改为：STM 是 append-only 的 `(generation, unitIndex)` 二维序列；"注入哪些块"由**摘要块（当前代 + 淘汰规则）**与**检索（N 条事件）**两处分别决定。**⚑ v5：按档位 5% 给预算后，淘汰在常态下不发生**——块内通常是**整代**；只有单份摘要偏长时才退化成"最新的一段"。
>
> ⚠ **v4 特别提醒**：`generation` 的语义**变了**。v3 的 `generation` 是"每次滑出 +1"，也就是**每个单元 +1**；v4 的 `generation` 是"每次**换代** +1"，**同一代的单元共享同一个值**。迁移时必须提供 `(generation, unitIndex)` 二元组，不能只留一个自增计数——否则"同一代"这个关系无法恢复。

#### 4.2.1 摘要块的持久化、两级归集与检索时机（v3 新增 D1，**v4 重写：F4/F5**）

**结论先说**：① 每一份**单元摘要块**都持久保存、永不删除，只是"不在 prompt 里"；② 取回链路走 **`E → 单元摘要块 → (generation, unitIndex)`** 两级**归集**，不靠文本相似度；③ **事件参与检索的时机是"该代被下一代替换时"**，不是单元压缩时。

```text
第一级（代）： prompt 的摘要块 C = 当前 active 代（generation = g）里通过淘汰规则的单元（v5：通常就是整代）
第二级（单元）： 每一份 = 记忆库一个 STM 块（generation=g, unitIndex=i）

检索命中 E1, E2 …
   │  stmId（E 自带）
   ▼
单元摘要块（generation=g', unitIndex=i）       ← 定位到"具体哪一份"
   ├─► 取回正文：回查 / 审计 / 链式发散遍历      ← 用途不变
   └─► 取回它的 EventChain 成员：作为注入候选 → 注入的是 Event 列表（D2）
```

**六条硬规则**：

1. **存储层不得删除任何一代、任何一份单元摘要块**。换代只改 `state`（`active → superseded`），不改"谁存在"（与 §2.4 同源：派生不得反向删改权威）。
2. **取回必须走 `stmId` → `(generation, unitIndex)` 归集，不得靠文本相似度反查**。相似度只能用来找 E；找块必须用归属键。**v4 强调**：块内是多份并列，所以"哪个单元"必须能答出来，否则审查"这段话来自哪一段历史"就断了。
3. **取回是只读操作**：不产生新块、不刷新 `generation`、不写回任何字段（读路径零写入）。
4. **取回结果与注入载荷分离**：取回的是"块 + 它的 EventChain"，进 prompt 的是其中 **Event 列表**（每条 `importance` + 事件文本），**不是块正文**——理由见 §6.4 的体积账（360 token vs 数百上千 token，且不另开槽位）。
5. **检索可见性按代翻转（v4 新增，F4）**：
   ```
   检索候选池 = { E | E.stmId 所属块的 state == superseded }
   排除      = { E | E.stmId 所属块的 state == active }
   ```
   **理由（必须写进实现注释）**：单元压缩时那批 raw 原文**还在 prompt 的压缩窗口里逐字可见**。若此刻事件也可检索，同一段历史会在 `T2`（注入）与 `[压缩窗口]`（原文）里各出现一遍 → 既浪费 token，又可能让模型把同一件事说两次。换代把原文移出后，事件才成为**唯一**的表示方式，此时开放检索。
   **代价**：检索池滞后一代。但滞后期间那部分历史**在 prompt 里**，所以**信息零丢失**，只是"检索召回"这条通道晚用一代。
6. **可观测（v4 扩展）**：每轮记 `memoAggregationHits`（命中 E 数）、`memoBlocksReached`（能归集到块的个数）、**`memoUnitReached`（能定位到 `(generation, unitIndex)` 的个数）**、**`memoSearchableGenerations`（当前可检索的代次数量）**。`memoUnitReached` 偏低 = `unitIndex` 写入有缺口；`memoSearchableGenerations` 长期为 0 = 换代从未发生（会话太短，属正常）或 `state` 翻转没落盘（缺陷）。

> 三处容易混的边界：① `C_g`（本代摘要块）出现在**单元压缩请求**里（§5.5）是**缓存需要**，与取回链路无关；② 取回 ≠ 回注：禁止的是**跨代累积**，同代集合本来就在 prompt 里（§5.3.2）；③ **被淘汰的单元摘要**虽然不在 prompt，但其 `state` 与同代一致（`active` 时不可检索、`superseded` 后即可检索），**不要**给它单独开一条"永远不可检索"的旁路。

### 4.3 E 与 EventChain

E 是原子事件，来自 EventChain 落库或硬事件直通。E 是检索探针，用于精准定位，不负责承载完整语境。

上一版 §3.3 的必备项保留：稳定 ID、文本事实、所属 STM 的 ID 或可校验引用、时间/世界/维度/可选位置、是否空间绑定、可选 MC 实体标签、embedding 引用或可重建版本、embedding 空间标识。**E 不保存完整父 STM 文本。**

**本版新增字段（只加不删）：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schemaVersion` | int | 是 | 本版 `2`；未知版本读路径降级、写路径拒绝（§10 G3） |
| `kind` | enum | 是 | `action / state / commitment / preference / location / query / world_event / other`；importance 规则兜底表的主输入（§6.3） |
| `turnRefs` | string[] | 是 | 轮级溯源，指向 `AXRawTurn.id`；`≥1` 条，且必须属于本批（§10 G4） |
| `importance`（v3 新增） | int | 是 | **抽取阶段由模型打分**（1–10 整数）；代码 `clamp(1,10)`；缺失/非整数/越界 → 规则表兜底并记 `importance_fallback`（§6.3） |
| `idempotencyKey` | string | 是 | `sha256(batchId + "\|" + turnRef + "\|" + factHash)`（§10 G7） |
| `supersedes` | string | 否 | 仅 `kind=preference`：被本条覆盖的旧偏好事件 id（§2.3 L3） |

**重要边界（v3 改写）**：

- `importance` **现在是** E 的字段，但它是**一次性静态分**：抽取阶段由模型产出，落库后**永不改写**、不随召回次数变化。这仍然满足"禁止让单条记忆维护动态热度或动态 importance"（上一版 §11，本版 §12 保留该禁令）——禁令针对的是**读路径上的动态派生**，不是"字段在写入时被赋值"。
- `recency`、`lastHit`、`hitCount`、`memoryStrength` **仍然不是** E 的字段：它们是检索时对 E 现有字段求值的**纯函数**（§6.1），不落盘、不自增。
- 可检验判据：写入后任意时刻重算 `importance / 10` 必得同一数值；若某实现让它在读路径上变化，即违规。

### 4.4 摘要块 M（滑动窗口边界摘要，**v4：一代的单元摘要集合**）

**位置**：`messages` 序列里 **system 之后、压缩窗口之前**。这就是上一版 `player_memory.recent`（最近 3 块 STM）所在的逻辑位置（05 §3.8 指出该槽与 M 重叠，结论是"应删或改"，本版选择**改内容、不删槽**，见 §0.2 #4）。

**内容（v4 重写，F6）**：**同一代**（`generation = g`）的**全部单元摘要并列**，受预算 `SB(tier)` 与淘汰规则约束。**不是单份摘要，也不是"多代摘要的叠加"。**

**硬规则**：

1. **不跨代累积**。M 的正文只包含**当前这一代**的内容；一旦换代，旧代整块被新代整块替换。注意这不是"把上一代从请求里拿掉"——为了前缀命中，上一代摘要块**必须**作为 `C_g` 留在**单元压缩请求**的前缀里（§5.5，它当时本来就在 prompt 里）。所以"不累积"由**代次 + 指令 + 代码侧 n-gram 护栏**共同保证：见 §5.3.5。
2. **槽内是「一代集合」，不是「一份」（v4 改写，F6）**。块里可以有 `units` 份 `<unit_summary index=i>`，它们**属于同一代**。**先前的"槽里永远只有 1 份"表述作废**——那条是"每压一个单元就换代"时代的规定，与本版的"单元压缩静默、换代才替换"直接矛盾。
3. **换代即失效，且换代是唯一的失效时刻**。M 一替换，prompt 从 M 的第一个字节起不命中（`S` 仍命中）——与 03 §5.8.3 的失效范围口径一致：**失效起点 = M 的第一个字节，不是第 0 个 token**。**v4 关键差别**：`commitUnit`（单元压缩）**绝不改 M**，验收判据是 `promptHash` 前后相等。
4. **必须是独立消息，不得拼进 system**。上一版 `player_memory` 走 `addContextSection`（`AXPlayerMemoryPromptContributor.java:56`）被合进唯一 system（`AXPromptAssemblyBuilder.java:40-48`）——若 M 顺着这条路走，每换代就是"从第 1 个 token 起全 miss"，属 03 §9 缺陷 C 同款错误。
5. **长度（⚑ v5 定稿：两个层面，别混）**：
   - **摘要生成长度 = 不设上限、不设目标**。提示词**只对内容提要求**（事实完整、准确、不遗漏关键信息），**不得出现任何 token 数 / 字数 / "通常 200–600" / "本份不超过 N"**。**理由（用户口径）**：干货多就长、干货少就短，这样压出来的质量更固定；人为截断等于在生成端丢信息。
     - 唯一保留的量化约束是 **`tokens(summary) ≤ 0.5 × tokens(单元原文)`**：它是**压缩比护栏**（防模型复述原文），**不是长度上限**，且**不得写进提示词**。60 轮单元 ≈ 7,800 token 原文 → 上限 3,900，实测几乎不会绑到。
   - **摘要块上下文预算 `SB = clamp(0.05 × W, 2048, 24576)`** = **2560 / 5120 / 10240 / 24576**（**按档位，不再固定**，03 §5.1/§5.8.5）。它管的是"这块在 prompt 里占多少"，与单份摘要写多长无关。
   - **`SB / k` 不再作为单份目标下发**（v4 那句"单份目标长度 ≈ `SB/k`"**作废**）。`SB/k` = **640 / 640 / 683 / 630** 现在只是**事后对照的临界值**：单份均值低于它 → 一代整装得下；高于它 → 才会淘汰最旧的几份。
6. **不写时间戳**，只写 `turn_from / turn_to` 的整数序号或轮 id（对齐 03 §5.8.1 D3）。
7. **淘汰的处理（v4 新增 F7；⚑ v5 重写方向）**：一代内的单元摘要总和超过 `SB(tier)` 时，**从最新往回装、装不下就停**——先放最靠近压缩窗口边界（`unitIndex` 最大）的那份，剩下的更旧的整段淘汰。
   - 被淘汰的单元摘要**仍在记忆库**、`state` 与同代一致、其事件在换代后**仍可检索**。
   - 保留集必须是 `unitIndex` 的**连续后缀** `(k−kept+1 … k)`，块内 `index` 写**真实 `unitIndex`**（因此不从 1 起；**禁止**重编号成 `1..kept`）。
   - 外层标签必须写 `units="{kept}"` 与 `dropped="{dropped}"`，**禁止静默截断、禁止把落选摘要压成一句话塞进去、禁止跳着装**。
   - **⚑ v5 的频率预期**：按档位 5% 给预算后，`ū=400` 时四档覆盖 **1.58–1.71×**，**一代应完整进块 → `dropped=0`**。**淘汰只在单份摘要实际偏长（> `SB/k`）时发生**，是异常信号而非常态。
8. **保持窗口不属于 M 的职责**（v4 新增，F1）。v3 的 M 是"唯一边界接续"；v4 起 **M 负责"一代之前的语义接续"，保持窗口负责"最近 `KEEP_rounds` 轮逐字原文"**（⚑ v6：39/78/157/378 轮，`clamp(0.10×W, 2048, 49152)`），两者不可互相替代、也不可互相挤占。

**M 的消息形态（v4：外层代 + 内层单元）**：

```text
<memory_summary generation="{g}" turn_from="{genFrom}" turn_to="{genTo}"
                       units="{kept}" dropped="{dropped}">
  <unit_summary index="6" stm="{stmId}" turn_from="{a}" turn_to="{b}">
  {第 6 份单元摘要正文}
  </unit_summary>
  <unit_summary index="7" stm="{stmId}" turn_from="{b+1}" turn_to="{c}">
  {第 7 份单元摘要正文}
  </unit_summary>
  …
</memory_summary>
```

> **⚑ v7 命名说明**：外层标签名是 **`<memory_summary>`**（v4–v6 曾写作旧名，**已作废**）。四份文档（本文 / 03 v9 / 运行时 v3 / 04 v4）**逐字相同**；实现里出现两种标签即违规，且改标签名会改 `messages[1]` 的字节 → **必须与"开新系列"一起做**（运行时 §11-9）。内层 `<unit_summary>` 不变。

> **⚑ v5 形态说明（举例是一次"淘汰了前 5 份"的渲染）**：`index` 是**真实 `unitIndex`**，所以当块里只保留最后几份时，`index` **从 `k−kept+1` 起、不从 1 起**（上例假设 `k=9, kept=4`，于是 `index` 为 6..9）。**不得**为了"看起来整齐"重编号成 `1..kept`——那会让 `E.stmId → unitIndex` 的归集对不上存储。整装下（常态）时 `index` 才是 1..k。

用 `user` 而不新增第二条 `system` 的三条理由见 03 §5.8.4，本文不重复。**v4 补充**：`index` 与记忆库 `unitIndex` **必须一致**（F5），这是 `Event → 具体单元摘要` 的唯一定位依据。

### 4.5 preferences（第三要素）

| 字段 | 取值 | 校验 |
|---|---|---|
| `subject` | `player` / `ax` | 必填 |
| `polarity` | `prefer` / `avoid` | 必填 |
| `target` | 具体对象（物品/方块/行为/地点），≤40 字 | 必填；出现人格形容词 → 整条拒绝（§2.3 L2） |
| `evidenceTurnRefs` | string[]，`≥1`，属于本批 | 必填（§2.3 L1） |
| `confidence` | `explicit`（唯一允许值） | 非 `explicit` → 整条丢弃并计诊断 |
| `supersedes` | 旧偏好事件 id，可空 | 可选 |

落库后 `preferences` 的每一项都变成一条 `kind=preference` 的 E（`sourceKind=compact_preference`），进入与普通事件相同的嵌入式投影与检索链路。**不为偏好新建存储表**——这是控制复杂度的硬要求。

**作用域（v3 新增，D6）：偏好的归属键是玩家 UUID，不是世界。**

| 项 | 规则 |
|---|---|
| 存储键 | **`players/{playerUuid}/preferences.jsonl`**（append-only）；**键内不含 `worldId`** |
| 跨世界 | 换存档 / 换维度 / 换服务器世界，偏好仍在——偏好是"这个玩家怎么玩"，不是"这个世界发生了什么" |
| 跨用户 | **完全隔离**：不同 UUID 之间不共享，也不互相 `supersedes` |
| 检索过滤 | 偏好类事件在召回**之前**先按 `playerUuid` 过滤；不得因为"别的存档里有同一条偏好"而放宽匹配 |
| 离线模式代价 | 离线 UUID 由玩家名派生，**改名即视为新玩家**（偏好不继承）。这是已知代价，**不做**名字→UUID 的模糊匹配 |
| 与普通事件的分界 | 普通事件仍按 `worldId` 隔离（§7.1）；只有 `kind=preference` 走玩家级作用域。这一条是 §12「禁止跨世界共享」禁令的唯一例外，必须写成显式条件而不是隐式默认 |

### 4.6 Token 统计与轮数判据（改写）

上一版 §3.4 的约束保留：会直接参与 prompt 预算的历史正文对象保留 `tokenCount`；只有 provider 缺失/超时/失败/tokenizer 不可用时才写 `0`；E 不保存 `tokenCount`。

**本版新增一条硬要求（针对 03 §9 缺陷 B）**：

> **凡是"容量判断"都必须有一个不依赖 tokenizer 的判据。** 当前云端 `TOKEN_COUNT` 恒不可用，raw `tokenCount` 恒 0，于是 `AXRawTurnWindow.selectCompressionBatch` 走字符分支且**没有轮数上限**（05 §1.2 S8）。本版把**轮数**升为主判据：
>
> - 轮数永远可精确计数（数 `AXRawTurn.id` 即可），不依赖任何 provider；
> - token 阈值降级为"上限保护"，tokenizer 可用时才生效；
> - 字符等效上限只在 tokenizer 不可用时生效，且由 token 上限按 03 §6.1 的 1.67 字/token 换算得出（`40,000 × 1.67 ≈ 66,800`）。
> - **压缩单元的主判据就是轮数：60 轮**（v3 D-E）。token 判据只在"单轮异常巨大"时才可能先到（§5.4），常态下单元大小由轮数决定，**因此单元原文规模可预测**。**⚑ v5 更正**：可预测的是"单元原文 ≈ 7,800 token"这个**输入规模**（它是摘要大概有多少干货的**代理指标**），**不是摘要的生成长度**——后者不设限。中文 token 估算误差（03 §6.1 实测可达 3×）不影响切点。

## 5. 一段式压缩

### 5.1 单次调用形态

```text
输入：一个压缩单元（≤60 轮，**主判据**；安全阀 ≤40,000 token / ≤66,800 字符）
请求：messages = S + C_g + 单元内 raw 轮次 + 指令          // §5.5（v4：C_g = 本代摘要块）
      lane       = TASK
      maxTokens  = 4096                               // 三要素共用输出预算，显式设置；构成见下表
      thinking   = true                              // 对齐 03 §5.9；与 maxTokens 联立
      temperature= 0.2
      taskPriority = 500（可抢占）
      超时       = 120s（TASK 车道不自动超时，必须自加，对齐 03 §9 差距 P）
输出：一个 JSON（§5.2）→ 解析 → 分字段提交（§10 G5）
```

**`maxTokens = 4096` 的构成（v3 重算）**：

| 成分 | 上限态 | 典型值 |
|---|---|---|
| `summary` | **无上限**（⚑ v5：只受 4,096 输出总预算约束，且不得在提示词里写长度） | 按内容伸缩（实测均值记为 `unitSummaryTokens`，**不是配额**） |
| `eventChain` | 60 条 × ~45 token（含键名/字段）≈ 2,700 | 30–40 条 ≈ 1,500 |
| `preferences` + `coverage` + 包装 | ≈ 200 | ≈ 100 |
| **正文合计** | **≈ 4,900** | **≈ 1,800–2,500** |

→ 常态留足余量；**上限态会先撞 4,096 上限**，此时按 §5.2 R6 的 salvage 顺序收尾（先保完整 `summary`，再从尾部丢不完整 event），记 `compact_truncated`。若实测**常态**触顶，说明单元过大：**回 §5.4 把单元轮数从 60 调小（如 40）**，不要抬高 `maxTokens`——抬高只会让摘要越写越长（03 §5.9 同款结论）。

**为什么必须是"一次调用"**（结论取 05 §3.1/§3.4，本文不重复论证）：

- 事件与摘要同源、同批、同版本，一致性由构造保证；
- 事件的事实来源是 raw 原文，只有**一层**取舍，而不是"raw→摘要（有损）→事实（再取舍）"两层；
- 轮级 `turnRefs` 只有在模型看得见 raw 边界时才拿得到——第二次调用时轮边界已经不在上下文里了。

**必须显式否定的三条错误立论**：

1. 选一段式**不是**为了省一次调用（省 3.5 当量/轮 = 0.19%，见 05 §3.3）。
2. 一段式**不是**"先写摘要、再照抄摘要做事件"——那样与两段式等价，只是少一次往返。指令里必须钉死"`summary` 与 `eventChain` 各自面向原文独立生成"。
3. 摘要**不是**历史信息的存储形式——它是窗口边界的语义接续（§5.3）。

### 5.3 摘要语义：两级窗口、代与单元（**v4 重写，本版最需要说清的一节**）

#### 5.3.1 正确模型（v4）

```text
raw 原文 ── 连续、永不删除
     │
     ├── 注入窗口 ┌─ 压缩窗口：已出单元摘要、原文仍在 prompt 里（攒够一代就整段移出）
     │            └─ 保持窗口：最近 KEEP_rounds 轮真实原文（39/78/157/378，永远逐字保留，永不移出）
     │                  ↑ 边界（窗口水位 T）
     └── 归档（append-only，全部历史）
```

**两个方向的移动（v4 与 v3 最大差别）**：

```text
① 单元压缩（静默，每 60 轮一次）——prompt 一个字节都不改
   压缩窗口: [ t1 … t60 | t61 … ]            ← 原文全部留下
             └ 单元 U1 → { summary₁, eventChain₁, preferences₁ } → 单元摘要块 (g, index=1)
               summary₁ 不进 prompt；eventChain₁ 落库但 state=g → 不可检索

② 换代（压缩窗口占满，约每 K 轮一次）——唯一的 prompt 改动时刻
   换代前: 摘要块 C_g（i 份） + 压缩窗口 [ U1 U2 … Uk ] + 保持窗口 KEEP_rounds 轮
   换代后: 摘要块 C_{g+1}（k 份并列，受按档位的 SB 与淘汰规则约束）
           + 压缩窗口（空） + 保持窗口 KEEP_rounds 轮（原样）
           + 代 g 的 state: active → superseded（其事件从此刻起可检索）
```

#### 5.3.2 摘要的六条铁律（v4 改写）

1. **一份摘要 = 一个压缩单元**（≤60 轮，§5.4）。不做"新摘要 = 旧摘要 + 新段落"这种演进式生成；**没有跨代累积**。指令里必须写明：只摘要 `turn_from..turn_to` 这一段，**不得复述更早代次或同代其他单元的内容**。
2. **摘要块 = 同一代的全部单元摘要并列**（v4 改写，F6）。它的职责是"承接这一代之前的对话"。**块内并列 ≠ 累积**：并列的是**同一代的不同时间段**，累积的是**不同代**——前者是设计，后者是禁止。
3. **更早代次的信息不由摘要承载**。它们在被封存（`state=superseded`）后即可经 EventChain **检索召回**（§6）回到 prompt。这是本版唯一的长期记忆通道。
4. **旧代摘要不消失，只是不在 prompt 里**。`(generation, unitIndex)` 序列在存储里 append-only 保留，且**可通过 `E → 单元摘要块` 两级归集取回**（§4.2.1）；摘要块只渲染 `state == active` 的那一代。
5. **同代并列、跨代不回注（v4 定案，F6+F4）**：一代的 k 份**全部进块**（v5：按档位 `SB` 通常整代装得下；只有单份偏长时才按新→旧淘汰最旧的几份）；**上一代及更早代的摘要不做任何形式的回注**——不进块、不进尾部、不作为"次级接续块"。那些段的信息由**各自的 Event 承载、靠检索召回**。想补信息就提高抽取覆盖率与召回，不是回注摘要。
6. **单元压缩与换代是两个时刻，不得合并**（v4 新增，F3）。任何"压完一个单元就更新 prompt"的实现都算回到 v3，会直接把 03 §5.8.3 的摊销从 `+8.1%` 打回 `+53%`。

#### 5.3.3 信息断层如何补偿（v4 更新，必须写进实现注释）

摘要块只覆盖"当前这一代"，因此 prompt 里必然存在**语义断层**：比它更早的那些轮次既不在窗口里，也没有可见摘要。补偿手段按强度排序：

| 序 | 手段 | 覆盖什么 | 强度 |
|---|---|---|---|
| 1 | **检索 E → 链式发散 → 注入 Event 列表** | 任何被抽成事件的客观事实（位置、归属、承诺、偏好、动作），跨会话有效 | **主通道**。注入典型 12 条 ≈ 360 token（§6.4）；这是摘要不累积能成立的**唯一前提** |
| 2 | **单元摘要块归集取回** | 命中 E 沿 `stmId → (generation, unitIndex)` 取回具体那份摘要 | 支撑通道：供发散遍历、回查、审计；**本身不作为注入正文**（§4.2.1） |
| 3 | **raw 归档回溯** | 原文（诊断、补抽、重建、玩家追问"具体哪次"） | 不进 prompt，只在 AX 侧使用 |
| 4 | **摘要块 M（一代集合）** | 当前这一代（覆盖 `K` 轮，= 一代之前的历史接续） | 边界接续，不承担更早代次 |
| 5 | **保持窗口 `KEEP_rounds` 轮**（v4 新增；⚑ v6 改为按档位 39/78/157/378） | 最近 `KEEP_rounds` 轮**逐字原文**（`clamp(0.10×W, 2048, 49152)`；DSH 用 16%，我们取 10% 更保守） | 近期保真，任何情况下都在 |

**四条由此推出的硬要求**：

1. **EventChain 的抽取质量优先于摘要质量**。摘要写差了只影响边界接续；事件漏抽等于那段历史在封存后永久丢失（既不进 prompt、检索也捞不到）。所以 §10 G6 的覆盖率自检必须常态开。
2. **检索命中率是本设计的生命线**。若实测"窗口之外"的问题命中率低，**不许**用"把旧代摘要也塞进块里"或"把更早代次的摘要放进尾部"来救——前者是不可审计的跨代累积，后者是变相回注。正确动作是提高事件抽取覆盖率与分档召回（§6.3/§6.4）。
3. **每一份单元摘要的覆盖区间必须可校验（v4 改写，v5 修正编号口径）**：对块内第 `i` 份，`sourceFromTurnId..sourceToTurnId` 必须等于**第 i 个压缩单元**的首尾，且区间长度 ≤60 轮；同时 `unitIndex` 必须在**保留集内连续**（`k−kept+1 .. k`，中间不得跳号、不得重复）。**⚑ v5**：v4 写的"连续 `1..kept`"只在"从未淘汰"时成立；按新→旧淘汰后应断言**连续后缀**，否则归集会错位。断言它，就能断言"没有跨代累积、也没有同代错位"。
4. **断层是可观测的（v4 扩展）**：每轮记 `compressionWindowTurns` / `keepWindowTurns` / `generation`；检索命中项若全部落在 `turnRefs` 早于当前代的 `turn_from`，记 `retrieval_beyond_boundary`（正常现象），用于统计"长期通道"的实际承担比例；**新增** `memoSearchableGenerations` 观测可检索代次数量。

#### 5.3.4 明确的反模式（不要做）

- ❌ 把上一代摘要喂给模型让它"接着写"。
- ❌ 摘要块里放**多代**摘要（跨代并列 = 累积）。
- ❌ 用摘要去替代事件抽取（"反正摘要里有"）。
- ❌ 一次滑出多单元时，为了"补断层"把更早单元的摘要塞进槽或尾部（D7 禁止回注）。
- ❌ 为了让摘要"更全"而把它越写越长**并且设个人为上限**。**⚑ v5**：长度由内容决定（干货多就长），**不得设字数目标**；但这**不是**"写得越长越好"的理由——摘要写长了会挤掉同代其他单元（见 §4.4 规则 7）。真正该动的是检索与抽取覆盖率（03 §5.8.1 同款结论）。

#### 5.3.5 "不累积"的代码侧护栏（不能只靠指令）

前提已经钉死：为了前缀命中，请求里**必然**存在`C_g`（本代摘要块，§5.5）。模型能看见它，所以"不累积"必须有**代码侧**判据，否则就只是"让模型遵守"。

**v4 关键改写：「参照集」不再是"上一份摘要"，而是一个集合**

```text
参照集 R(M_new) = ① 上一代（state=superseded）的摘要块全文
                ∪ ② 同代已提交的其他单元摘要全文
理由：v4 里 prompt 的摘要块是一代集合，模型能看见的是"所有旧代 + 同代已写的"；
      只跟"上一份"比，等于放任它把同代其他单元的内容抄过来。
```

| 护栏 | 判据 | 违反时 |
|---|---|---|
| **G-M1 长度锚**（**v5 改定义**） | `M_new.tokenCount ≤ 0.5 × 单元原文 token`（**压缩比护栏**；**v5 删除"单份 ≤ 2000"**）；~~块内总量 ≤ `SB`~~ → **块总量不再在这里判**，它是渲染层的事 | 单份超 50% → 拒绝提交（`NotShrinking`）；**块总量超 `SB` → 渲染时按新→旧淘汰，不拒绝换代**（§4.4 规则 7） |
| **G-M2 区间锚**（**v4 加强，v5 修正编号口径**） | `M_new.sourceFromTurnId..sourceToTurnId` 必须**精确等于**本次提交单元的首尾；`sourceTurnCount ≤ 60`；**`unitIndex` 在保留集内连续**（`k−kept+1..k`，不跳号、不重复；**v5：不是 `1..kept`**） | 拒绝提交（`summary_range_mismatch`） |
| **G-M3 无继承**（关键，**v4 改写**） | 对**参照集里每一份**：`longestCommonSubstring(M_new, ref) < 40 字` **且** `jaccard(8-gram(M_new), 8-gram(ref)) < 0.25` | 记 `summary_contaminated`，**摘要字段作废**（按 G5 走"只有 events 成功"的分支）；单元因此不齐 → **换代自动被挡住**（P3），不会退化成 `hard_slide` |
| **G-M4 不含越界轮号** | `M_new` 正文中出现的轮号/轮 id 不得超出 `turn_from..turn_to`（**v4：也不得出现其他单元的轮号**） | 同上 |

**为什么这两个数值**：40 字 ≈ 一句完整中文陈述的长度——两份"各自独立"的摘要共享超过 40 字的连续片段，几乎只可能是复制。8-gram Jaccard 0.25 用来挡住"改几个字再抄一遍"（40 字连续串抓不到的那种）。两条都可用纯 Java 实现，无额外依赖、无 LLM 调用。**v4 的成本提示**：参照集从 1 份变成 `(k_prev + 已提交份数)` 份，G-M3 的比较次数从 O(1) 升到 O(k)。`k ≤ 39`（500K 档）、比较对象是"摘要正文"，总开销仍在毫秒级，**不需要优化**；但不要把参照集扩大到"全部历史代"（那是 O(n) 且无收益）。
> **⚑ v5 成本提醒**：摘要生成长度不设限后，**比较对象长度不再有上界**（v4 假设"≤600 token"已不成立）。G-M3 必须实现成**单一早期退出**（一旦发现 ≥40 字连续片段即刻判定污染，不再算完整 Jaccard），否则最坏情况是 O(k × 摘要长度)。正常摘要仍只有数百 token，因此实际开销不变。

> ⚠ **⚑ v5 重写：G-M1 现在只剩一条判据**。v4 的"单份 ≤ 2,000"**已删除**（生成长度不设限），所以真正起作用的只有 `≤ 0.5 × 单元原文`：60 轮单元 ≈ 7,800 token → 上限 3,900。保留这条的理由**不是**限长，而是**防复述原文**（压缩比护栏）；它也天然挡住"3 轮对话写 2,000 token"这种异常（10 轮单元 ≈1,300 → 上限 650）。
> **v5 补充**：与容量相关的不再是"单份上限"，而是**事后对照值 `SB/k`**（**640 / 640 / 683 / 630**）：单份均值低于它 → 一代整装得下（常态）；高于它 → 渲染时淘汰最旧的几份。见 §4.4 规则 5/7 与 §14.2 Q3。

> 这条护栏的存在本身说明一件事：**"摘要不累积"是代码的可验证属性，不是提示词的语气问题**。它和 G4（`turnRefs` 必须属于本批）是同一类护栏——都是拿"模型给的元数据"去反证"模型有没有越界"。

### 5.4 压缩单元：60 轮（主判据）+ 代（v4：单元与代是两个粒度）

**问题现状（已核准）**：字符分支下 `target = max = removableBudget`（`AXRawTurnWindow.java:132-140`），既没有 `shortTermCompressTokenTarget` 约束，也没有轮数约束；100K 档 `maxRawCharacters = 120000 × (102400/8000) = 1,536,000` 字符（≈92 万 token @1.67 字/token），是窗口的 9 倍。一批吞下去必然截断，且漏抽不可检测。

**v4 必须钉死的三层粒度（别再混）**：

| 粒度 | 大小 | 数量关系 | 谁决定 |
|---|---|---|---|
| **压缩单元** `U` | ≤ **60 轮** / ≤ 40,000 token（取先到） | —— | 输出预算（4,096 ÷ ~45 token/条 ≈ 90 条事件） |
| **代** `g` | `K` 轮 = **190 / 426 / 898 / 2340** 轮（⚑ v6 重算） | `k = ceil(K/60)` = **4 / 8 / 15 / 39** 个单元 | 03 §5.2：`K = floor((T − C_low)/130)`，`C_low` 按档位（含按档位的 `SB` 与 `KEEP`） |
| **保持窗口** | **`KEEP_rounds` = 39 / 78 / 157 / 378 轮**（`clamp(0.10×W, 2048, 49152)` ÷ 130），永远不动 | 独立于上面两者 | 03 §5.1（⚑ v6 按档位；不得低于 20 轮） |

**本版判据（双判据取先到者）**：

```text
compressionUnitTurns      = 60      // 主判据：对话轮次，精确可数，不依赖 tokenizer
compressionUnitTokenGuard = 40000   // 安全阀：单轮异常巨大时才会先到
compressionUnitCharGuard  = 66800   // = ceil(40000 × 1.67)；仅 tokenizer 不可用时作安全阀等效判据
keepWindowBudget          = clamp(0.10 × W, 2048, 49152)   // ⚑ v6：保持窗口 token 预算（按档位 5120/10240/20480/49152）
keepWindowTurns            = floor(keepWindowBudget / 130) // = 39 / 78 / 157 / 378 轮；语义底线 ≥ 20 轮
summaryBlockBudget     SB = clamp(0.05 × W, 2048, 24576)   // 摘要块上下文预算：按档位 2560/5120/10240/24576（03 §5.1/§5.8.5）
                                                           // ⚑ v5：v4 的固定 2000 已作废；缩放变量必须是 W，不能是 k（循环定义）

splitIntoUnits(compressionWindow):                 // v4：切的是「压缩窗口」，不是"滑出段"
    units = []
    cur   = {turns:0, tokens:0, chars:0, items:[]}
    for turn in compressionWindow:                 // 轮是不可分单元（I10：绝不切断单轮）
        if cur.turns  + 1             > 60    : flush()
        if cur.tokens + turn.tokens   > 40000 : flush()
        if !tokenKnown and cur.chars + turn.chars > 66800 : flush()
        cur.add(turn)
    flush()
    return units                                   // 切点全部落在轮边界
```

**八条配套规则（第 2/3/5 条 v4 改写）**：

1. **切点必须落在轮边界，绝不切断单轮**（03 I10 / P1）。`flush()` 只发生在"轮与轮之间"，永不在一轮的 user/assistant 之间切。
2. **常态是"按 60 轮节拍静默压缩"，不是"一次滑出才压一堆"**（v4）。压缩窗口是一个持续蓄水的水池：每攒够 60 轮就压 1 个单元，**原文不移出**。所以稳态下队列深度通常 ≤ 1，**不存在 v3 的"一次滑出吐出 N 个单元"**（那是"压回 `T−B`"的产物）。
3. **换代时压缩窗口的轮数必须全部已出摘要**（v4，对应 03 的 P3 分区纪律）。`generationUnitsReady == k` 才允许换代；不齐就**只等不换**（记 `generation_switch_waiting_units`）。这是"换代把整段移出"能成立的唯一前提——否则移出的是没被摘要的原文。
4. **单元之间互不阻塞**：某单元失败只影响该单元（§5.7 的退避按单元计），后续单元继续；同一时刻只有 1 个在跑。
5. **冷却只约束"换代"，不约束单元压缩**（v4 改写）。单元压缩有 60 轮的自然节流，再叠 8 轮冷却只会让"本代单元齐备"推迟，反而拖住换代。冷却 8 轮只作用在 §5.6 的判定点 A2 上。
6. **单轮就超安全阀** → 该轮不可压缩，记 `compact_noop_oversized_turn`，摘要退化为"该轮首尾各 200 字摘录 + `truncated=true`"；**不允许**为它破 40,000 上限。
7. **单元判据与档位无关**。60 轮 / 40,000 token 是**四档统一值**：单元大小由"输出预算能装多少条事件"决定，而输出预算全档位相同（附录 A.3）。
8. **`k` 与 `SB` 的关系（⚑ v5 已解决，不再是张力）**：`k` 随档位线性增长（4→39），`SB` **也随档位线性增长**（2560→24576）——`0.05 × W` 恰好覆盖一整代。`ū=400` 时四档覆盖 **1.60/1.60/1.71/1.58×**，**一代能整装下、`dropped=0`**。临界单份均值 `SB/k` = **640/640/683/630**，超过它才会淘汰。见 §14.2 Q3（已决策）与 03 §5.8.5。

**为什么用轮数而不是 token（写进代码注释）**：

| 理由 | 说明 |
|---|---|
| **精确可数** | 数 `AXRawTurn.id` 即可，零依赖 provider；中文 token 估算误差实测可达 3×（03 §6.1），用 token 定切点等于让切点抖动 |
| **单元规模可预测**（⚑ v5 改述） | 60 轮 ≈ 7,800 token 原文 → **单元原文规模稳定**，因此"这份摘要大概有多少干货"有代理指标。**注意：可预测的是输入规模，不是摘要生成长度**（后者不设限，见 §4.4 规则 5） |
| **漏抽有上界** | 按 1 事件/轮的上界，60 轮最多 60 条事件，稳装进 4,096 输出预算；不存在"批太大必然漏抽且不可检测" |
| **成本可摊** | 单元输入 ≈7,800 token，前缀命中后 ≈276 当量 ≈ 4.6 当量/轮（§5.5） |

**验算（100K 档，⚑ v6 重算）**：水位 `T = 76,800`、`SB = 5,120`、`KEEP = 10,240` → 换代低点 `C_low = 4,096 + 1,024 + 5,120 + 10,240 + 896 = 21,376`（03 §5.1）→ **换代间隔 `K = floor((76800 − 21376)/130) = 426 轮**，一代 `k = ceil(426/60) = 8` 个单元。按 `ū=400` 需要 3,200 token ≤ `SB` 5,120，**整装下、不淘汰**（临界 640）。而三个"长度"概念要分清：60 轮单元 ≈ 7,800 token 的**输入**、3,900 token 的**50% 压缩比上限**、`SB=5,120` 的**块容量**——**后两者不是"单份摘要的长度上限"**。**"60 轮"只决定单元原文规模，不决定换代频率**（换代由 `K` 决定，见 03 §5.2）。

**多单元规模量级（写成告警阈值，⚑ v5 重算）**：

| 情形 | 一代轮数 | 单元数 `k` | 处置 |
|---|---|---|---|
| 50K 档换代 | 190 | **4** | 队列串行，接不到就被 `generationSwitchPending` 挡住 |
| **100K 档（默认）** | **426** | **8** | 同上；单元节拍 60 轮，换代节拍 426 轮 |
| 200K 档 | 898 | **15** | 同上 |
| 500K 档 | 2340 | **39** | 同上；这是队列积压最深的一档（39 个单元 ≈ 39 分钟级 TASK 占用，若每单元 60s） |
| 崩溃恢复后的补压 | 视残留轮数 | ≤ 39 | 同上；先由判定点 B 的**同步硬裁剪**保证不溢出（不摘要），后台队列按序补摘要 |

> **v4 提醒**：v3 那张表里的"离线多日回填 → 2–10 个单元""500K→50K 降档 → 10–40 个单元"**不再出现**。原因是 v4 的单元压缩是**持续节拍**（每 60 轮一次），而不是"一次滑出才批量压"，所以不存在"一次性吐出几十个单元"的突发——**除非**离线期间攒了远超 `K` 的轮数（此时同样按 60 轮切片排队，且 `k` 的上界就是该档位的 45）。

> 这条同时修掉 05 §1.7 不一致 #9（字符分支无轮数上限）：现在的上限是"60 轮"，而且它**不可能**被 tokenizer 状态影响。

### 5.5 单元压缩请求必须复用前缀缓存（v4：`M_prev` → `C_g`）

**这是记忆链路唯一真正的成本杠杆**（05 §3.3 的算法，按 60 轮单元重算：**−125.4 当量/轮**，是"砍掉第二次调用"的 30 倍以上）。

```text
单元压缩请求 messages =
    [ S ]                      // 会话唯一 system，逐字节相同（03 I12）
  + [ C_g ]（若存在）           // **本代摘要块**：该单元这几轮被发出时，messages[1] 放着的那一份
  + 单元内 raw 轮次             // 按 renderTurn 原样渲染，与它会话时发出的字节相同
  + [ user: COMPACT_INSTRUCTION ]   // 唯一新增：该前缀的真后缀（≈120 token）

换代请求：**不存在** —— 换代不发模型调用，只是"已就绪的 k 份单元摘要 → 渲染成新块"的本地动作（03 §5.7）。
```

**`C_g` 的取法（v4 改写，务必纠正 v3）**：同一代内**所有单元的前缀都是同一个 `C_g`**。
> **v3 写"第 k 个单元的 `M_prev` = 第 k−1 个单元的产出"是错的。** 那个规则的前提是"每压一个单元就替换摘要槽"，而 v4 起单元压缩**静默**，摘要块只在换代时替换。所以 `C_g` 是一个**每代才变的常量**，不是逐单元滚动的变量——实现反而更简单。

**为什么是 `C_g` 而不是"换代后的新块"**：单元内的轮次是在**本代摘要块生效期间**被发出的，缓存里存在过的字节是 `S + C_g + H[unit]`；此刻若已换代成 `C_{g+1}`，用新的就是"重新渲染一份看起来一样的"，必然 miss。这要求**摘要块按代次 append-only 存储**（§4.2 已保证），并能按 `generation` 取 `state == active` 那一代。

**四条硬要求（对齐 03 §5.7）**：

1. 与历史请求**逐字节相同**，不是"重新渲染一份看起来一样的"；渲染统一走 `renderTurn(turn)` 纯函数，按 `contentHash` 缓存结果（`AXRawTurn.contentHash` 已存在，可直接做缓存键）。
2. 指令必须是**真后缀**：只能追加在最末，不能插进 raw 轮次中间，不能塞进 `S`（改 `S` 违反 03 I2/I12），不能作为第二条 `system`。
3. 前缀恰好停在**已持久化的 cache prefix unit** 上：`S + C_g + H[unit]` 的末尾就是该单元最后一轮的 assistant 消息（03 §5.7 第 3 条）。
4. **压缩模型必须与会话模型相同**。为 thinking 换到推理模型名 → 前缀缓存跨模型不共享 → 命中归零，必须记 `prefix_reuse_lost=true`（03 §5.9）。

**量化（单单元 60 轮 × 130 token = 7,800 token；100K 档中位每轮成本 1770，03 §6.4 v5）**：

| 形态 | 单单元输入成本（当量） | 摊销/轮（÷60） | 占 100K 中位每轮成本 |
|---|---|---|---|
| 全 miss（现状） | 7,800 | 130.0 | +7.34% |
| **前缀命中（目标形态）** | `7,800 × 0.02 + 120 = 276` | **4.6** | **+0.26%** |
| **差额** | — | **−125.4** | **−7.08%** |

> 摊销/轮之所以与"批大小"无关：成本与会话历史增长都按 ≈130 token/轮 线性，比值恒定。**换单元大小的意义不在摊销比，而在漏抽上界与摘要长度可预测性**（§5.4）。
> **v4 特别提示**：这 4.6 当量/轮 是**单元压缩调用本身**的成本，与 03 §5.8.3 的**压缩摊销**（换代导致前缀重建，100K 档 +143 当量/轮）是两笔不同的钱。v3 把两者混在一张表里，v4 分开记。

> 前提检查（必须在实现里断言）：单元内轮次全部 `createdAtMillis > C_g.createdAtMillis`。若有轮次早于 `C_g` 的生成时刻，说明单元跨越了换代边界 → 记 `prefix_reuse_partial`，并如实按 miss 记账。
>
> ⚠ 与 §4.4 的张力必须显式处理：`C_g` 出现在请求里是**缓存需要**，不是"喂给它续写"。因此"不跨代累积"必须由 §5.3.5 的 G-M1..G-M4 代码护栏兜住。这两件事（缓存命中 + 摘要不继承）互相拉扯，是本设计里最容易实现成"悄悄累积"的地方。

### 5.6 时序：两级——静默单元压缩 / 换代（v4 重写）

```text
① 触发（同一挂载点，两件事分开判，沿用现有维护协调器）
   点 A：回答落盘后        afterAssistantAnswer(scope)   —— 主判定（判 A1 与 A2）
   点 B：提问前的硬预算     beforeQuestion(scope)        —— 仅判"窗口是否超硬边界"，超了立即 hard_drop

   A1 判据（单元压缩，静默）：
     compressionWindowTurns ≥ 60 或 pendingRawTokens ≥ 40000
     且 无在飞单元任务 且 连续单元失败 < 3
     → 产 1 份单元摘要 + 事件链 + 偏好，写记忆库；state = active（不可检索）
     → **prompt 一个字节都不改**（验收：promptHash 前后相等）

   A2 判据（换代，改 prompt）：
     C_low(tier) + 压缩窗口轮数×130 ≥ T（= 压缩窗口占满；⚑ v6：不再重复加 KEEP，C_low 已含）
     且 generationUnitsReady == generationUnits（**P3：缺一份都不换**）
     且 无在飞换代 且 turnsSinceLastSwitch ≥ 8（冷却）且 连续换代失败 < 3
     → 渲染新块、归档并移出压缩窗口、翻转 state

② 冻结（两种粒度，见 03 §5.4）
   UnitSnapshot      = { fromTurn/toTurn（≤60 轮）, generation, basePrefixHash }
   GenerationSnapshot= { generation, fromTurn/toTurn（整段）, unitStmIds[],
                         renderedBlock（含 kept/dropped）, C_low, T, tier }

③ 单元提交（commitUnit，**不改 prompt**）
   前置复核：generation 未变；summary ≤ 0.5 × 单元原文（⚑ v5：删除"≤2000"）；非空、轮号不越界
   写入（append-only）：
     1) 追加单元摘要块（generation, unitIndex = 下一个序号, content = summary）
     2) 追加事件（eventChain + preferences 展开，按幂等键）
     3) 登记本代已就绪（generationUnitsReady += 1）
     4) **原文轮次一字节不动**（不归档、不置 archived、不移窗）
   不变量：promptHash 前后逐字节相等

④ 换代提交（switchGeneration，**改 prompt**）
   前置复核：本代单元齐备；压缩窗口首轮 == snapshot.fromTurn
   写入（顺序固定：先归档、再换代、最后移窗）：
     1) 归档压缩窗口整段 raw 轮次        → raw_archive（append-only）  ← 必须先成功
     2) 渲染并落盘新块 C_{g+1}            → 记 keptUnitIds/droppedUnitIds/renderedBlockHash
     3) 旧代 state: active → superseded  ← **此刻起其事件参与检索**（§4.2.1 规则 5）
     4) 新代 state: → active
     5) 压缩窗口整段移出注入窗口；**保持窗口 `KEEP_rounds` 轮原样保留**
   推进：curGeneration = g+1（单调递增，永不回退）

⑤ 替换（prompt 视角）
   旧：messages = [S][C_g][压缩窗口 t1..tm][保持窗口 KEEP_rounds 轮][尾块]
   新：messages = [S][C_{g+1}][               ][保持窗口 KEEP_rounds 轮][尾块]
   失效范围 = 从 C 第一个字节起；S 段仍命中（03 §5.8.3 口径）
   摊销到每轮（甲口径）@100K = 72704 ÷ 426 ≈ **+171 当量（+9.1%）** —— v3 的 "+6.5%"、v4 的 "+53.3%"、v5 的 "+8.3%" **都作废**（⚑ v6：`KEEP` 按档位后重算）
```

**必须写进代码注释的五条**：

1. **冻结是正确性的前提**。压缩要发一次真实模型调用（数百毫秒到数秒）。若提交时按"当前窗口"重算范围，就会把压缩期间玩家新说的话也摘要进去——等于改写了刚刚发生的历史（违反 03 I3）。
2. **先归档后移窗**。顺序反了就是"raw 被移出窗口但归档没写成功" = 原文永久丢失，直接违反 §2.4。
3. **替换只换摘要块，不重写 raw**。`turns` 文件在压缩前后一个字节都不变（03 §5.8.2 同款）。
4. **两级提交的可见性不同（v4 新增）**：`commitUnit` 只能让记忆库变、不能让 prompt 变；`switchGeneration` 必须让两者同时变。**判据可测**：前者 `promptHash` 相等，后者必须不等。
5. **换代前必须等齐（v4 新增）**：`generationUnitsReady < k` 时**只等不换**，不允许"先把 raw 移出、摘要以后补"。那正是 `hard_slide` 的语义（永久丢失边界接续），必须走 §5.7 的降级通道而不是正常路径。

### 5.7 失败与字段级降级

| 失败 | 处置 | 恢复 |
|---|---|---|
| 超时 / 网络 / 取消（**单元压缩**） | **该单元**不提交，raw 保持"在窗口"、prompt 不动，记 `compact_unit_failed(attempt=k)` | 退避 k=1→+3 轮，k=2→+10 轮，k=3→`unitCompactDegraded=true`（**只阻断换代**，不触发 `hard_slide`——原文还在 prompt 里，没有信息损失） |
| 超时 / 归档写失败（**换代**） | 整次换代回滚，prompt 不动，记 `generation_switch_failed(attempt=k)` | k=3→`generationSwitchDegraded=true`，此后只走 `hard_slide`，直到压缩窗口回落到 `SB` 可承载范围 |
| 输出被截断 | salvage：保 `summary`，从尾部丢不完整 event/preference；记 `compact_truncated` | 不自动重试（§10 G6 防风暴） |
| JSON 完全不可解析 | 行降级**只用于 summary 兜底**（把整段输出当成摘要文本，**取输出预算内全部内容**——⚑ v5：不再按"前 2,000 token"截断，长度不设限）；事件字段置空 | 标记 `batch=pending_extraction` |
| `summary` 坏、`eventChain` 好 | 原则：**摘要坏则该单元不提交**（单元缺一份，就不会齐，换代自动被挡住——这正是 P3 的好处） | 记 `compact_rejected_no_summary` |
| `summary` 好、`eventChain` 坏 | **提交单元摘要**；标记 `batch=pending_extraction`；下次维护用 raw 走"纯抽取小请求"补抽（**不重跑压缩**，不碰摘要块、不破坏前缀） | 补抽成功后清标记 |
| `importance` 缺失/越界 | **不失败**：规则表兜底 + `clamp(1,10)`，记 `importance_fallback` | 事件照常落库；兜底率 > 5% 进告警（提示词要改，不是代码要改） |
| 块渲染超 `SB` | **不失败**：按 §4.4 规则 7 **从新到旧保留、久远的整段淘汰**，记 `summariesDropped>0` | 被淘汰的摘要仍在库、其事件仍可检索。**⚑ v5：这是异常而非常态**（按档位 5% 后 `ū=400` 时四档都整装下），出现即说明单份摘要偏长 |
| 提交复核失败（superseded / 代次已推进） | 静默丢弃，不重试、不计失败 | 下一次判定点重新冻结 |
| 窗口被同步硬裁剪推进 | 同上 | — |
| **队列里还有其他单元** | **继续推进**：一个单元失败不阻塞后续单元（§5.4 规则 4）；`unitCompactInFlight` 按单元释放 | 队列深度与卡住的单元 id 记 `memoCompactionBacklog` |

> `hard_slide`（只移出不摘要）是**最后手段**，必须记 `compactionDegraded=true` 并进告警：它意味着摘要通道连续 3 次失败，此时 prompt 的边界接续恢复为"无"，长期信息只能靠检索。
> **v4 的关键改进**：因为"单元压缩"是静默的，**单元压缩失败不再等于信息丢失**（原文还在 prompt 里）；只有"换代时单元不齐"才会退化成 `hard_slide`。所以 v3 的"连续 3 次单元失败即降级为 hard_slide"在 v4 不再成立，降级门槛落在**换代**上。

## 6. 检索与打分

### 6.1 三因子公式（乘法）

```
score = relevance × recency × importance          // ∈ (0, 1]
```

| 因子 | 取值 | 来源 | 是否持久化 |
|---|---|---|---|
| **relevance** | `clamp(cosine(embed(query), embed(event.fact)), 0, 1)` | 复用现有 `bge-large-zh-v1.5` 私有 RAG 投影的 L2 命中分（`AXMemoryRetriever.java:143` 的 `hit.score()`），**不改 embedding 链路** | 否（向量本身已持久化） |
| **recency** | `0.05 + 0.95 × 2^(−ageHours / (168 × S))` | 只读 `happenedAtMillis` | 否 |
| **importance** | `event.importance / 10`，`event.importance ∈ [1,10]` | **E 的字段本身**：抽取阶段由模型打分（D4）；缺失/越界时由 §6.3 规则表兜底 | **是**（随 E 落库，写入后永不改写） |

**为什么乘法而不是加法**（这是与 03 §4.2 的口径差异，§11.2 已登记）：

- 加法（`αr·recency + αi·importance + αv·relevance`，03 §4.2）会让"任意一项很高"就进候选：一条 relevance 0.9 但 importance 0.1、recency 0.05 的噪声事件得 `(0.05+0.1+0.9)/3 ≈ 0.35`，比一条三项均衡（0.5/0.5/0.5 = 0.5）的实质事件更容易被描述成"差不多"。用户决策要求乘法，语义上更贴合"三个条件都必须成立"。
- 乘法的代价：任一项接近 0 就把整条压到 0。**因此三个因子都必须有地板**（见下），否则会出现"全部候选挤在 1e-4 量级、阈值失效"。

**地板与上下界（必须实现）**：

| 因子 | 下界 | 上界 | 原因 |
|---|---|---|---|
| relevance | 0 | 1 | 余弦天然有界 |
| recency | **0.05** | 1.0 | 与 03 §4.2 的遗忘淘汰线 `R < 0.05` **同源同值**：低于它就是"已遗忘"，但保留 5% 是为了让极旧的高价值事件仍能通过分档下限进 Cold |
| importance | **0.1**（raw=1） | 1.0（raw=10） | raw 下界 1 → 除法后 0.1，永不为 0，保证乘法不会因 importance 归零 |

于是 `score ∈ [0, 1]`，理论最小值 `0 × 0.05 × 0.1 = 0`，实际候选（relevance > 0）最小值 `> 0`。

**与"禁止动态 importance"的关系（v3 改写）**：

上一版 §11 写"禁止让单条记忆维护动态热度或动态 importance"。D4 之后，落实口径是：

- ✅ `importance` **是** E 的字段，但**只在写入时赋值一次**（模型打分），此后**只读**——任何时刻重算 `importance/10` 必得同一数值；
- ✅ `recency` 是**当次查询**对 `happenedAtMillis` 与 `turnRefs` 求值的纯函数，不落盘；
- ❌ 禁止 `hitCount / lastHit / recallCount / memoryStrength / decayedScore` 这类**读路径回写**字段；
- ❌ 禁止任何"因为被召回了就调高 importance"的机制（正是 03 §4.2 的 `S += 1`；本版用静态 `supportStrength` 代替，§6.2）。

> 一句话：**写入时赋值可以，读路径上变化不行**。这条边界同时解释了为什么 §6.3 的规则表从"主路径"降级为"兜底与校验"——它不再参与读路径计算。

### 6.2 recency：真指数衰减

```
ageHours = max(0, (now − event.happenedAtMillis) / 3_600_000)
S        = clamp(supportStrength, 1.0, 8.0)
         supportStrength = 1.0 + min(7.0, 0.5 × (turnRefs.size() − 1))
HALF_LIFE_HOURS(S) = 168 × S          // S=1 → 7 天；S=8 → 56 天
recency  = 0.05 + 0.95 × 2^(−ageHours / HALF_LIFE_HOURS(S))
```

**为什么用 `happenedAtMillis` 而不是 `lastRecalledAt`**：后者需要召回计数（§6.1 已禁止）。用"事件发生时间"意味着衰减只随客观时间流逝，可回放、可重算、与 03 §2.4「确定性」兼容。

**为什么 `S` 用 `turnRefs.size()` 而不是召回次数**：`turnRefs` 越多 = 同一事实在被压缩的那段里被反复提到 = 语义上更"扎实"。这是间隔效应（复述强化）的**静态**代理，且 `turnRefs` 本来就是 §10 G4 的必填字段，零额外成本。上界 8 与 03 §4.2 的记忆强度上界一致。

**衰减对照表**（`recency` 实际取值）：

| 事件年龄 | S=1（7 天半衰期） | S=8（56 天半衰期） |
|---|---|---|
| 1 小时 | 0.996 | 1.000 |
| 12 小时 | 0.954 | 0.994 |
| 1 天 | 0.910 | 0.988 |
| 3 天 | 0.756 | 0.965 |
| 7 天 | **0.525** | 0.921 |
| 14 天 | 0.288 | 0.849 |
| 28 天 | 0.109 | 0.722 |
| 30 天 | 0.099 | 0.705 |
| 42 天 | 0.065 | 0.615 |
| 60 天 | 0.052 | 0.502 |
| 90 天 | **0.050（趋近地板）** | 0.362 |

> 读数：S=1（只被提到过一次的事实）约 **7 周**后落到 0.065、**10 周**后基本贴住 0.05 地板；S=8（在窗口内被反复提到 ≥15 轮的事实）在 **3 个月**后仍有 0.36。地板本身保证"极旧的高价值事件"不会变成 0，只是必须靠较高的 `importance` 与 `relevance` 才能进入 Cold（§6.4）。

**与旧实现的对比（这是本项改动的全部意义）**：

| | 旧实现 | 本版 |
|---|---|---|
| 公式 | `factor = max(0.90, 1 − min(0.10, ageDays/3650))` | `0.05 + 0.95 × 2^(−ageHours/(168S))` |
| 一年后 | 0.99 | 0.050（S=1）/ 0.060（S=8） |
| 十年后 | 0.90 | 0.050 |
| 形态 | 线性、上限 10%、**等于常数** | 指数、半衰期 7–56 天、有地板 |
| 结论 | 时间维度完全不参与排序 | 时间维度成为真正的排序因子 |

出处：旧实现 `AXMemoryRetriever.java:203-205` + `AXMemoryRetrievalPolicy.java:26-27`（`maxTimeDecay=0.10`、`timeDecayDaysToMax=3650`）；旧值评估见 05 §1.4 R3。

### 6.3 importance：模型打分（主路径）+ 规则表（兜底与校验）

**v3 定案（D4）**：`importance` 由**大模型在抽取阶段一并打分**，作为 Event 结构体字段随同一个 JSON 产出——**零额外调用、零额外往返**。规则表不再决定分数，只做三件事：**兜底、校验、回归基线**。

#### 6.3.0 主路径

```text
模型侧：eventChain[i].importance ∈ [1,10]（与 fact 同批产出，见 §5.2 示例）
代码侧：
    raw = modelValue
    if raw 缺失 / 非整数 / 越界:
        raw = ruleScore(event)                  // 兜底：下面的规则表
        diag(importance_fallback)
    raw = clamp(raw, 1, 10)
    importance = raw / 10
```

**四条硬约束**：

1. **必填但不阻塞**：`eventChain[].importance` 缺失或非法时，事件**照常落库**（§5.2 R9），只记 `importance_fallback`。
2. **不可改写**：落库后只读；任何"读路径重算 importance"都违规（§6.1）。
3. **兜底率可观测**：`importance_fallback` 占比 > 5% → 告警（提示词没要求打分，或模型没遵守）。
4. **偏差可统计**：每条事件同时算一次 `ruleScore`，`|model − rule| ≥ 3` 记 `importance_drift`；**只统计、不覆盖模型分**（§6.3.6）。

**兜底与校验用的规则表（原主路径，v3 降级为参考实现）**

**计算模型**：

```text
raw = clamp( base(kind) + Σ modifier(event), 1, 10 )
importance = raw / 10
```

**全部输入都是 E 的已存在字段**（`kind`、`dimension`、`position`、`spatiallyBound`、`fact`、`turnRefs`、`supersedes`），因此：

- 零额外 LLM 调用（这正是它适合做兜底的原因，对齐 03 §4.2 "避免额外 LLM 调用"）；
- 零持久化（§6.1）；
- 可回放、可单测、可调权重（改表即生效，不需要重算历史）。

> 规则表的存在理由变了：v2 用它**代替**模型，v3 用它**兜住**模型。**表内数值一个都不用改**——它同时是兜底实现与回归测试基线，且 §13 P-4 的"12 条示例逐条断言"照旧有效。

#### 6.3.1 第一级：`base(kind)` —— 单调性的锚

| `kind` | 归属类 | `base` | 依据 |
|---|---|---|---|
| `location` | 客观事实·位置/归属 | **8** | 位置与归属是**无法从别处重建**的信息，且极易失（换机器、记错坐标就永久错）；03 §4.2 给"含坐标/位置承诺"最高 9 分 |
| `preference` | 偏好 | **7** | 明示偏好对后续所有回答有持续约束力（§2.3 L1 已限界为 explicit） |
| `commitment` | 客观事实·承诺/计划/未完成 | **7** | 跨轮依赖：不完成会持续被追问，且"未完成"状态本身有价值 |
| `state` | 客观事实·状态变更 | **5** | 有新旧值可对照，但会被后续状态合法覆盖（因此低于 location） |
| `action` | 客观事实·动作 | **4** | 高频；单条信息量低于状态变更，靠数量与聚合补 |
| `world_event` | 事件 | **4** | 与 action 同档：世界侧事实客观性强，但（死亡/进出维度）频率极高 |
| `query` | 客观事实·询问 | **3** | "玩家问过 X"是弱事实：只表达关注点，不含结论 |
| `other` | 客观事实·兜底 | **3** | 与 query 同档，宁可多留（§2.4），但不抬高排序 |
| `noise` | 噪声 | **1** | 寒暄/确认/复述/元讨论；**不落库**（见 6.3.4） |

**单调性（形式化）**：`base` 对所有 `kind` 给出全序 `location > preference = commitment > state > action = world_event > query = other > noise`。由于 modifier 对任意两条事件是同一组加法项，`base` 的全序在 modifier 相同时**严格保持**。这是"单调"的可检验表述：**同修饰集合下，`raw` 的大小关系必须与 `kind` 的偏序一致**（单测断言）。

#### 6.3.2 第二级：`modifier` —— 全部为 ±1/±2 的确定性判定

| # | 判定（可执行） | 分值 | 依据 |
|---|---|---|---|
| M1 | `position` 非空 **或** `fact` 匹配 `\d{1,3}\s*[,， ]\s*-?\d{1,3}`（形如坐标） | **+2** | 具体坐标是最易失、最难重建的信息 |
| M2 | `fact` 同时匹配数量正则 `\d+` **且**含单位/物品白名单词（个/组/块/颗/瓶/级/耐久/itemId） | **+2** | "12 个远古残骸"比"远古残骸"信息量高一档 |
| M3 | `fact` 含容器/归属白名单词（箱子/末影箱/背包/熔炉/领地/家/矿洞/仓库） | **+1** | 归属类事实（03 §4.2 "含物品归属/已有量"给 6 分） |
| M4 | `fact` 含玩家明示否定白名单（别/不要/不许/禁止/不能用）**且** `kind ∈ {preference, commitment}` | **+1** | 禁令比建议的约束力强（03 §4.2 "含玩家明示偏好/禁止项"给 8 分） |
| M5 | `turnRefs.size() ≥ 3` | **+1** | 同一事实跨越 ≥3 轮被反复提及 → 反复强化 |
| M6 | `spatiallyBound == true` | **+1** | 有空间绑定的事件可用空间衰减二次利用（本版只取一次） |
| M7 | `fact` 的码点数 `< 8` | **−1** | 极短事实信息量低（"玩家死亡"4 字） |
| M8 | `fact` 命中噪声词表（嗯/好的/收到/谢谢/哈哈/在吗/明白） | **−2** | 与 `noise` 类同效，用于兜住被错标成 `action` 的寒暄 |
| M9 | `kind == preference` 且 `supersedes` 非空 | **+1** | 覆盖旧偏好意味着"规则变更"，比新增偏好更该被检索到 |

**modifier 的界**：`Σ modifier ∈ [−3, +9]`（M1+M2 互斥不加同分：同时命中取 `max(2)` 而非相加 → 实际 `[−3, +8]`）。**这条"同一维度不重复加分"是防止分数堆叠失真的关键**，必须写成代码：M1 与 M2 属于同一维度（"具体性"），取最大值而非求和。

#### 6.3.4 判定阈值（落库与分档用）

| 阈值 | 值 | 动作 |
|---|---|---|
| **不落库线** | `kind == noise` **或** `raw ≤ 1` | 不写入 events；只计入 `coverage.turnsWithoutEvent` |

#### 6.3.5 与"事件不去重"的兼容性（必须说明）

importance 只**读单条事件自身的字段**，不做任何跨事件比较、等价判定或合并动作：

- 不构成"相似即合并"的依据；
- 两条文本相同、`turnRefs` 不同的事件各自独立打分，各自独立落库（§2.4）；
- 因此"事件不去重"与"importance 打分"在机制上正交，不存在冲突面。

#### 6.3.6 模型打分的风险与校验（v3 新增）

模型打分换来了零额外调用，也换来一个新风险：**它可能把普通事件打得过高，压过真正重要的信息**。量化一下：

| # | 事件 | rel | age | 模型 `raw` | 规则 `raw` | 偏差 | `importance` | recency | **score** |
|---|---|---|---|---|---|---|---|---|---|
| A | 玩家的家在村庄东侧（真正的位置事实） | 0.78 | 7d | 9 | 9 | 0 | 0.9 | 0.525 | **0.368** |
| B | 玩家随口说"我在整理箱子"（普通动作） | 0.74 | 2d | **9**（虚高） | 5 | **+4** | 0.9 | 0.829 | **0.552** |

→ 一次虚高就足以让 B 压过 A。所以校验机制不是可选项：

| 机制 | 作用 | 落点 |
|---|---|---|
| **规则兜底 + `clamp(1,10)`** | 挡住"没打分 / 打分越界" | §6.3.0 规则 1 |
| **`importance_drift` 统计**（`|model − rule| ≥ 3`） | 观测模型是否系统性偏高；只统计不覆盖 | 附录 A.5 |
| **分档相对线**（`0.72 × top`） | 让"同层内的重要性差异"不改变分档，弱化单条虚高的破坏力 | §6.4 |
| **强制 Hot 线要求 `raw ≥ 8` 且 `rel ≥ 0.60`** | 高分事件只有在相关性也高时才走特权通道 | §6.3.4 |
| **提示词里给打分锚点** | 用规则表的 5 个锚例（location 8–10 / commitment 7 / action 4–5 / query 3 / noise 1）作为 few-shot 尺度 | §10 G1 |

> 判断标准写在验收里：抽 100 条实际事件，`importance_drift` 占比应 < 15%。超了先改提示词的锚例（成本最低、可灰度），**不要**改成"回退到纯规则表"——那等于放弃 D4 的零额外调用收益。

### 6.4 Hot / Warm / Cold 分档与预算（按新打分重定义）

旧实现是**绝对分数线**（`hot=0.60 / warm=0.35 / cold=0.15`，`AXMemoryRetrievalPolicy.java:31-33`）。在乘法打分下这套线全部作废：一条"同会话 + 高相关 + 位置事实"的事件也只有 `0.82 × 0.910 × 1.0 = 0.746`，而"一月前的普通动作"只有 `0.70 × 0.109 × 0.4 = 0.031`——两者差 24 倍，绝对线会把绝大多数候选一次性打落到 cold 以下。

**新定义 = 相对线 + 绝对地板**（双条件，这是乘法打分唯一可靠的方式）：

```text
top      = 本次查询全部候选的最高 score（top > 0 时才有意义）
hot 线   = max(HOT_FLOOR,  0.72 × top)        HOT_FLOOR  = 0.22
warm 线  = max(WARM_FLOOR, 0.45 × top)        WARM_FLOOR = 0.08
cold 线  = COLD_FLOOR                         COLD_FLOOR = 0.02
subCold  = score < COLD_FLOOR  → 不进候选；其所属 STM 记入 subColdStmIds（沿用现有语义，
                                   AXMemoryRetriever.java:144-149，链式发散时跳过）
```

| 分档 | 条件 | 承接什么 |
|---|---|---|
| **Hot** | `score ≥ hot 线` **或** 命中 §6.3.4 强制 Hot 线 | 当前语义最强、实体最稳的候选 |
| **Warm** | `warm 线 ≤ score < hot 线` | 同簇/近簇的事件，以及"跨一个到两个半衰期"的候选 |
| **Cold** | `cold 线 ≤ score < warm 线` **且** `raw ≥ 4` | 低频但仍有恢复价值的历史片段 |

**相对线的三个数值依据**：

- **0.72**：对应"同一簇内 importance 差 2 分以内"（`0.7/0.9 ≈ 0.78`，取 0.72 留余量），保证同类事件的强弱差异不至于把同类候选踢出 Hot。
- **0.45**：对应"recency 跨 1–2 个半衰期"（`0.288/0.910 ≈ 0.32` 到 `0.525/0.910 ≈ 0.58` 之间取中）。
- **绝对地板 0.22 / 0.08**：相对阈值唯一的失效模式是"全场稀烂但 top 相对高"（top=0.06 时 `0.72×top=0.043`，会把垃圾抬进 Hot）。地板就是挡这个的。

**预算比例（重定义）**：

| 层 | 旧比例 | **新比例** | 依据 |
|---|---|---|---|
| Hot | 0.60 | **0.50** | Hot 现在受 `0.72×top` **和** `0.22` 双重限制，候选数实测上界约为总候选的 20–30%；0.60 会长期用不完而挤占 Warm |
| Warm | 0.30 | **0.35** | 乘法下最容易被饿死的一层（它承接"跨半衰期"与"同簇弱表述"）；旧 0.30 在绝对线时代够用，现在不够 |
| Cold | 0.10 | **0.15** | 受 `recency` 地板 0.05 与 `raw ≥ 4` 双重限制，实际候选只占 ≤15%；给 0.15 刚好覆盖 |

**注入条数与 token 预算（v3 定稿，D2）：注入 Event 列表，且不随档位放大**

```text
T2_TOKEN_BUDGET        = 512        // T2 整块预算，全档位相同（03 §2.2/§4.1）
memInjectItemsMax      = 12         // 条数上限（硬）
memInjectItemTokenMax  = 40         // 单条上限：importance 前缀 + 事件文本（≈66 汉字）
典型体积：12 × 30 = 360 token ≤ 512  ✓
上限体积：12 × 40 = 480 token ≤ 512  ✓   ← 所以不需要任何"按 token 截断"的逻辑
```

**层预算按条数（比例沿用 0.50 / 0.35 / 0.15）**：

| 层 | 比例 | 条数预算（n = 12） |
|---|---|---|
| Hot | 0.50 | **6** |
| Warm | 0.35 | **4**（`round(12 × 0.35) = 4.2`） |
| Cold | 0.15 | **2**（由减法：`12 − 6 − 4`） |

**两条实现硬约束**（不写就会出死层）：

1. **层预算被推成 0 的层不进循环**，其名额并给末尾的全层补位轮。三段减法照旧：`hot = round(n × 0.50)`、`warm = min(n − hot, round(n × 0.35))`、`cold = n − hot − warm`——**cold 必须由减法推得**，不是 `round(n × 0.15)`。
2. **三层走完仍有剩余条数 → 用全层候选补位**（沿用 `AXMemoryRetriever.java:262-266` 的语义；05 §1.7 不一致 #8 已指出文档与实现的差异，本版**以实现为准**）。

**与知识命中分食 `T2` 的顺序（v3 新增，因 D2 合并了槽位）**：

```text
T2 填充顺序：
  1) 记忆 Event 列表先占（典型 ≤360，硬 ≤480）
  2) 剩余额度给知识命中（条数上限仍 ≤3、硬 ≤5；一条 120 字 ≈72 token）
  3) 总 token ≤ 512；放不下的**整条丢弃**并记 t2_dropped（不截条内文本，I10）
```

| 情形 | 记忆 | 知识 | 合计 | 处置 |
|---|---|---|---|---|
| 典型 | 12 条 / 360 | 2 条 / 144 | **504 ✓** | 正常 |
| 上限态 | 12 条 / 480 | 0 条 | 480 ✓ | 记 `t2_trimmed_knowledge`（记忆优先、知识让位） |

### 6.5 链式发散（档位驱动，不再硬编码）

**旧实现的缺陷**：`chainExpansionRadius = 1` 是常量，`AXModule.java:187` 恒用 `new AXMemoryRetriever(memorySystem, ragClient)`（即 `DEFAULT` policy），**没有任何按档位注入的路径**（05 §1.4(c)）。而上一版 §5.3 明确要求"链式发散深度必须与当前模型档位预算挂钩，不能固定成一个全局常量"——这条从未生效。

**本版查表（`AXMemoryRetrievalPolicy.forTier(tier)` 必须提供这四个实例）**：

| 档位 | `chainDepth`（STM 跳数） | 每跳带入事件数 | 理论条数 `1 + 3 × 2d` | **实际条数上界** | 典型 token | `chainExpansionScoreRatio` | `chainExpansionMinScore` |
|---|---|---|---|---|---|---|---|
| 50K | **0**（关闭） | — | 1 | **1** | ≈30 | —（不判） | — |
| **100K** | **1** | ≤3 | 7 | **7** | ≈210 | 0.82 | 0.35 |
| 200K | **2** | ≤3 | 13 | **12**（被条数上限夹住） | ≈360 | 0.82 | 0.35 |
| 500K | **3** | ≤3 | 19 | **12**（被条数上限夹住） | ≈360 | 0.82 | 0.35 |

```
实际条数上界 = min(1 + 3 × 2 × chainDepth, memInjectItemsMax = 12)
同时受 token 约束：实际条数 × memInjectItemTokenMax ≤ 512（12 × 40 = 480 ✓）
```

**规则**：

1. `chainDepth = 0` 表示**只注入命中的那一条事件**，不做发散。50K 档关闭发散的理由：`T2` 里还要给知识命中留位置，且 1 条已足以点住边界接续；50K 档也最看重成本。
2. **发散从命中的 E 出发**（D2 的"沿 EventChain 链式发散"落地方式）：① 先取它所在 STM 的 **EventChain 成员**（同块内相邻事件，零跳）；② 再沿 **STM 链**向前后各跳 ≤ `chainDepth` 跳；③ 每跳从邻块的 EventChain 里取与中心事件语义最近的**至多 3 条**，块内按发生顺序。
3. 遍历骨架是 **STM 链**（`previousStmId / nextStmId`），**不给事件加链指针**（§3.2(a) 的结论不变）。EventChain 提供"候选池与顺序"，STM 链提供"能跳多远"。
4. **顺序必须恢复**：输出按 STM 时序链顺序，块内按事件发生顺序；同一个 E 最多出现一次，**不因分数高把叙事顺序倒置**（沿用上一版 §5.2 的硬约束，现有实现 `AXMemoryRetriever.java:167-173` 已符合）。
5. `subColdStmIds` 里的块在发散时**被跳过**（沿用现有语义 `AXMemoryRetriever.java:345-347`）。
6. **条数 12 与 token 512 同时生效，先到者截断**；截断单位是"整条事件"，**永不切事件内部文本**（I10）。

### 6.6 注入与位置纪律

**这是本版与旧实现差异最大、也最容易踩坑的一处。**

| 内容 | 放哪里 | 每轮是否变 | 前缀影响 |
|---|---|---|---|
| `S` system | `messages[0]` | 否（字节冻结） | 变更瞬间全 miss（正常路径不发生） |
| **摘要块 M** | **`messages[1]`，独立 `user` 消息**（内部是一代集合） | **否**（只在**换代**时整块替换；100K 档约每 **426 轮**一次，见附录 A.3） | 一次：从 M 第一个字节起失效 |
| **压缩窗口** | **`messages[2 .. 2+c−1]`** | 只增长（每轮 +1 轮），**换代时整段移出** | 无（在 `C` 之后追加，前缀天然复用） |
| **保持窗口（v4）** | **紧随压缩窗口之后的最近 `KEEP_rounds` 轮真实原文**（⚑ v6：39/78/157/378） | 边界随新轮左移，但**字节不变**（`renderTurn` 纯函数） | 无 |
| 尾块 `T1 / T2 / Q` | 尾部 | 是 | 本轮尾部未命中 |
| **记忆 Event 列表（v3，D2）** | **在 `T2` 内，与知识命中同一条消息；记忆在前、知识在后** | **每轮可能变** | 仅尾部未命中 |

**为什么记忆注入必须在尾部、不能跟 M 放一起**：检索结果每轮都可能不同。若把它放在 raw 窗口**之前**（挨着 M），那么每次命中变化都会打断**整个 raw 历史**的前缀匹配——那是每轮几百到几千 token 的 miss。放尾部则只影响本轮尾部（03 §2.2 的结论："未命中范围只等于本轮的 `T1+T2+Q`"）。

**v4 更正一处易错点**：`压缩窗口` / `保持窗口` 的**边界移动不产生未命中**。一轮从保持窗口滑到压缩窗口时，它在消息序列中的相对顺序不变（仍在 `M` 之后、按轮 id 升序），渲染字节相同。**分区只是渲染时的切片索引，不是消息重排**——这是"两级窗口"能零成本实现的根本原因。实现里若把两个分区渲染成两批分别拼接，一旦拼接顺序或空段处理不同（例如"压缩窗口为空时是否输出空行"），就会每轮 miss。**空分区必须整段不出现**（对齐 03 的 D7）。

**v3 更正（D2）：取消 `T2m` 独立槽位**。v2 把记忆注入单列成 `T2m` 并要求按档位 512/1024/2048/4096 的独立预算，与 03 §2.2 的 `尾部合计 ≤ 900` 直接冲突（v2 自己登记为待拍板 D2）。改为"注入 Event 列表、并入 `T2`"后，冲突消失：**尾部合计回到 896**，一次预算表更新解决，不需要请 03 改口径。

**当前实现的问题（必须一起改）**：`player_memory` 走 `addContextSection`（`AXPlayerMemoryPromptContributor.java:56`），被合并进**唯一 system**（`AXPromptAssemblyBuilder.java:40-48`）。这意味着**检索命中一变，system 字节就变 → 从第 1 个 token 起全 miss**，与 03 §9 缺陷 C（`game_context` 前置进 system）是同一类错误。这是本版顺带修掉的一个真实成本漏洞。

**注入预算分配（尾部合计，与 03 §2.2 口径对齐）**：

| 槽 | 预算 | 说明 |
|---|---|---|
| `T1` 状态快照 | ≤ 256 | 03 §6.3 |
| **`T2`（记忆 Event 列表 + 知识命中）** | **≤ 512 整块** | 记忆典型 ≤360（硬 ≤480）+ 知识余量；见 §6.4 分配顺序 |
| `Q` 当前输入 | ≤ 128 | 完整保留，不截断 |
| **尾部合计** | **896 ≤ 900 ✓** | 与 03 §2.2 一致（v2 的 1408 冲突已消除） |

**注入的四条硬约束（v3 按 Event 载荷改写）**：

1. **不切事件内部文本**：单条事件渲染后 > 40 token → 该条**跳过**并记 `t2_dropped`，不切片、不省略号截断。
2. 整条放不下就跳过（同 1），不降级成"摘要行"。
3. 同一次 prompt 不重复注入同一个 E。
4. 预算常量集中在 §6.4，**不硬编码在检索器里**（§2.1）。

## 7. 存储、并发与隔离

### 7.1 存储布局（保留）

AX 记忆归属于 AX 模块，不直接写入 LLM 内部 cache 文件。存储根以 `AXStorageLayout` 为准；推荐逻辑位置 `config/Tianshu/module/ax/cache/`，**按 world 分层 + 一层玩家级目录**（v3）：

```text
config/Tianshu/module/ax/cache/
  shared/
  players/<playerUuid>/                # ★v3 新增（D6）：玩家级作用域，键内无 worldId
    preferences.jsonl                  # 偏好事件，append-only，跨世界
  worlds/<worldId>/
    raw_turns/          # 注入窗口 checkpoint（可整份重写）
    raw_archive/        # ★新增：归档段，append-only，永不整体重写
    stm_blocks/         # STM 代次序列（append-only）
    events/             # 权威事件元数据（append-only）
    vectors/
    indexes/
    stats/
```

`raw_archive/` 是 v2 新增的存储单元，理由：现有 checkpoint 是"整份覆盖写"（`AXRawTurnCheckpointStore` 的 `writeJsonLines`），把归档混进去等于把永久保留的原文放进会被整体重写的文件——一旦重写出错就永久丢失，直接违反 §2.4。归档必须是**独立文件 + append-only**，且允许启动时跳过/修复尾部半行。

`players/<playerUuid>/` 是 v3 为 D6 新增的**唯一**玩家级目录：只有 `kind=preference` 的事件落在这里。它**不在 `worlds/` 之下**——这是 D6 的全部含义（换存档仍在、换玩家隔离）。检索侧对应一条硬约束：偏好类事件按 `playerUuid` 单独加载与过滤，与按 `worldId` 加载的普通事件**不走同一次目录遍历**（否则"偏好跨世界"会在实现里被目录结构悄悄否掉）。

### 7.2 权威与派生（保留）

- 权威：Raw Turn（含归档）、STM、E。
- 派生：embedding 向量、L1/L2 聚类投影、stats、检索索引。
- 派生数据 schema 或 embedding namespace 不兼容时**失效重建**，不牵连删除权威记忆。

持久化红线（沿用上一版 §8，全部保留）：只增字段不删语义；读路径容忍旧 `schemaVersion` 与未知字段；迁移逻辑集中在存储层；任何全量重写先写临时文件再原子替换；不得因数据来自旧版本就清空归档/STM/事件。

### 7.3 聚类（保留）

双层 E 聚类是索引结构，不是历史裁剪机制：

- L1 粗簇：场景级路由，减少全库扫描。
- L2 细簇：极相似 E 的候选到代表的有效映射依据。

`l1ClusterThreshold=0.56 / l2EffectiveMappingThreshold=0.92 / minRoutedL1Clusters=4`（现实现值）本版不改。**L2 细簇内的多条 E 仍然是真实事件**：本查询可选择代表 E 建立有效映射，但不能删除其他 E——这条与"事件不去重"（§2.4）完全一致，是本版唯一不用改的既有语义。

### 7.4 隔离边界（保留）

玩家个人记忆必须与动态环境、静态知识库隔离注入：

- AX 私有动态记忆的**权威数据**不写入 LLM RAG cache；只有可重建的检索投影（`uid + entryId`）可以。
- 外部静态知识库可复用 shared LLM RAG cache，但不得与玩家记忆混为同一存储或同一注入区。
- `AXGameContext` 与 `AXMemory` 在一期 baseline 中是并列模块，模块内不互相传递检索结果。

### 7.5 并发与模型切换（保留 + 一条新增）

压缩与事件抽取走后台 `lane=TASK`。要求（沿用上一版 §7）：

- 使用只读快照（`AXRawTurnBatch` 已是显式只读快照类型）。
- 主对话链路不等待压缩完成。**v4 补充**：单元压缩**不得改动 prompt**（`commitUnit` 前后 `promptHash` 相等），这是比"不等待"更强的约束。
- 任务失败不修改现有记忆。
- **重试必须幂等**——本版把它具体化为 §10 G7 的幂等键（旧版只有"必须幂等"这句话，没有键的定义）。
- STM 链更新必须避免断链。

新增：**两级压缩事务互斥闸**（对齐 03 §5.11，池化到记忆侧）

| 闸 | 机制 |
|---|---|
| ① 单飞 | `unitCompactInFlight` / `generationSwitchInFlight` 各自 per-scope `AtomicBoolean`，`compareAndSet` 抢占，`finally` 无条件释放。**v4：两把独立锁**，粒度分别是"一个压缩单元"与"一次换代" |
| ② 提交前复核 | 单元压缩：`generation` 未变；换代：压缩窗口首轮 id 仍等于 `snapshot.fromTurnId` 且 `generationUnitsReady == k`。任一不成立即 abort |
| ③ 冷却与退避 | **换代**两次起点间隔 ≥ 8 轮；失败退避 3 / 10 / 降级（§5.7）。**单元压缩不受冷却约束**（60 轮节拍已是天然节流），失败退避按单元计（§5.4 规则 5） |

**新增：压缩队列与两把锁（v3 建队列，v4 拆两级）**

| 项 | 规则 |
|---|---|
| **锁**（v4） | **两把独立锁**：`unitCompactInFlight`（单元压缩）与 `generationSwitchInFlight`（换代）。**不得合并成一把**：一次 2–4s 的单元压缩不应阻塞换代，而换代才是"一发生就做完"的动作（03 §5.10） |
| 队列粒度 | **每 scope 一条 FIFO**，元素 = 一个压缩单元 |
| 并发度 | 单元压缩 **同一时刻只有 1 个在跑**；**单元压缩与换代可并行**（前者不改 prompt，见 03 §5.11.2） |
| 入队时机（v4） | **每攒够 60 轮就入队 1 个单元**（持续节拍），不再"滑出判定成立时一次性入队一批" |
| 出队失败 | 该单元按 §5.7 退避，队列继续推进后续单元；不整队回滚 |
| **换代守卫**（v4） | 换代要求 `generationUnitsReady == k`；**队列没排空就不换代**（记 `generationSwitchPending`）——这既是正确性约束（P3），也让队列深度天然有界（≤ 本代单元数） |
| 可观测 | `memoCompactionQueueDepth`（队列深度）、`memoCompactionBacklog`（卡住单元个数）、**`generationSwitchPending`**（v4） |
| 与进程重启 | 队列**不持久化**：重启后按"压缩窗口内尚未出摘要的轮次"重新切单元，靠幂等键（§10 G7）避免重复写事件 |

模型切换只调整窗口与预算：大模型切小模型 → 保留最新完整轮次，超出部分进入后台压缩；小模型切大模型 → 扩大窗口与注入预算，不解冻已压缩数据。

## 8. 写入安全（保留）

持久文件写入必须保证不会出现半写入状态：

```text
读取当前文件
  -> 内存中生成新内容
  -> 写入临时文件
  -> flush / close
  -> 原子替换目标文件
```

- append-only 文件（`raw_archive` / `stm_blocks` / `events`）用追加 + fsync，不需要原子替换；但**写完才能推进水位**（§5.6 顺序约束）。
- 普通日志禁止输出完整玩家输入、prompt、记忆正文、摘要正文、RAG hit 明细和完整 LLM response（沿用一期 §10）。
- 诊断只允许输出计数、长度、枚举与脱敏 ID。

## 9. 与 LLM 协议的关系（保留）

AX 对 LLM 的所有访问必须经过协议中心。

允许：`ProtocolCapabilities.LLM_REQUEST`、`LLM_PRIMITIVE_QUERY`、`LLM_CACHE_MANAGE`。

禁止：直接调用 `LLMService`、直接访问 `JavaLlamaServer`、直接写 LLM RAG cache 二进制文件、让 UI/TTS 直接订阅底层 LLM stream。

底层能力映射（不变）：

- `LLM_PRIMITIVE_QUERY / TOKEN_COUNT`：text / message-only 的无副作用计数。**注意本版对它降级**：所有容量判断的主判据改用轮数（§4.6），因为它当前不可用（03 §9 缺陷 B）。
- `LLM_PRIMITIVE_QUERY / EMBED`：批量向量化，返回维度与 embedding 空间标识。
- `LLM_PRIMITIVE_QUERY / STATUS`：模型、上下文配置与 embedding 空间快照。
- `LLM_CACHE_MANAGE` / RAG 检索能力：静态知识库；以及 AX 私有检索投影的 `uid/entryId` 命中。
- `LLM_REQUEST` 的 result / stream terminal usage：观察 CHAT / TASK 实际成本。

后台压缩使用 `lane=TASK`（`taskPriority=500`，可抢占，自加 120s 超时）。玩家可见对话使用 `lane=CHAT` 并携带 IA 授权上下文。

## 10. 护栏 G1–G8（一段式必须同时上线）

> 这 8 条是"一段式能不能裸上"的分界线。缺任何一条，本版的失败模式都会从"可检测"退化为"静默"。

### G1 事件判定规则资源化（不写进 Java）

- 落 `ax_memory_tasks.json` 新键 `memory.compact.system` / `memory.compact.user`；`memory.compress.*` 与 `memory.extract.*` 全部删除（§11.1 A1–A5）。
- **规则表与 schema 必须在同一个 system 提示词里**，不允许拆成两份（拆了就是把旧的"两处漂移"换成新的"两处漂移"）。
- 规则表内容 = §3.2 的"必抽 / 不抽 / 默认抽"清单 + §5.2 的 schema + §5.3.2 的摘要铁律 + **§6.3 的打分锚例**。
- **提示词里必须显式要求 `importance`**（D4）：给出 1–10 的语义与 5 个锚例（`location` 8–10 / `commitment`·`preference` 7 / `state` 5 / `action`·`world_event` 4 / `query`·`other` 3 / 噪声 1），并要求"只给整数、不给理由"。锚例直接抄 §6.3.1 的 `base` 表——**同一份数值，一处维护**。
- **代码里不允许出现任何中文规则文本**（AGENTS.md 硬编码红线）。
- 版本号随 schema 一起递增；旧版本资源不被静默覆盖（内置资源可更新，已释放的玩家文件不得覆盖，缺失 key 走内置回退）。

必抽 / 不抽 / 默认抽清单（写进提示词，代码侧只做校验）：

| 类 | 判据 | 动作 |
|---|---|---|
| 动作 | 玩家/AX 做了什么（放置、取走、进入、击杀、死亡、合成、丢弃） | **必抽** |
| 状态变更 | 数量、耐久、等级、归属、位置变化 | **必抽**（带新旧值） |
| 承诺/计划 | 说要做什么、未完成 | **必抽**（记"谁提出"） |
| 偏好/禁止 | 玩家**明示**喜欢/讨厌/不许 | **必抽**（`confidence=explicit`） |
| 位置/归属 | 家、矿洞、箱子、领地 | **必抽**（带维度/坐标粗信息） |
| 询问 | 玩家问了什么（不是答案） | **必抽**（记"玩家问了 X"） |
| 世界事件 | 死亡、维度跨越、成就 | **必抽**（一次一条，不去重） |
| 寒暄/确认 | 嗯、好的、收到、复述 | **不抽** |
| 模型自评/元讨论 | 关于记忆机制、prompt、能力的对话 | **不抽** |
| 其他 | —— | **默认抽并标 `kind=other`**（宁可多留，§2.4） |

### G2 压缩单元双判据（v3：60 轮主判据）

`60 轮（主判据）/ 40,000 token（安全阀）/ 66,800 字符（tokenizer 不可用时的等效安全阀）`（§5.4），切点必落轮边界，多单元走 FIFO 串行队列。这是**一条配置修三个问题**：① 防"一段式输出装不下"（60 轮 × 45 token ≈ 2,700 ≤ 4,096 输出预算）；② 修掉旧字符分支无上限（05 §1.7 不一致 #9）；③ 让摘要长度可预测（D3 的前提）。

### G3 JSON 版本号

- `schemaVersion` 顶层必填，本版 `2`，与 `AXStmBlock.SCHEMA_VERSION` / `AXMemoryEvent.SCHEMA_VERSION` 同族同源。
- **未知版本 → 整批不提交 + 诊断**。拒绝静默降级：静默降级等于用旧解析器读新 schema，字段会静默丢。

### G4 provenance（轮级溯源）

- 每条 event 必须带 `turnRefs`（`≥1`）。
- 校验：① 空 `turnRefs` 的 event **一律拒绝**（除 `batch.turnCount == 0`）；② `turnRefs` 里出现本批之外的 id → **整条拒绝 + 诊断**（防模型编造轮 id）；③ 落库写入 `AXMemoryEvent.turnRefs`（新增字段，只加不删）。
- 老数据：历史事件无 `turnRefs` → 留空，检索不受影响，**不需要迁移脚本**（派生可重建、权威不删，§7.2）。

### G5 分字段提交 + 字段级降级

```
parsed = parse(rawOutput)                     // §5.2
if parsed.summary  ok      → 提交 M（追加 STM 代次）
if parsed.eventChain ok    → 提交事件（不去重，按幂等键）；importance 缺失则规则兜底
if parsed.preferences ok   → 展开为 kind=preference 的事件提交
if summary 坏              → 该单元不提交；raw 保持"在窗口"；不消费窗口
if eventChain 坏 && summary ok
   → 提交 M；标记 batch = pending_extraction
   → 下次维护用 raw 走"纯抽取小请求"补抽（不重跑压缩，不碰 M，不破坏前缀）
if error 出现在队列中间单元 → 只影响该单元，队列继续（§5.4 规则 4）
```

### G6 覆盖自检与低产出诊断

```
eventsPerTurn = eventChain.size() / batch.turnCount
coverage.turnsWithEvent + coverage.turnsWithoutEvent == batch.turnCount   // R8
if eventsPerTurn < 0.15  → 记 extraction_low_yield（不自动重试，防风暴）
if coverage 缺失或不等 → 记 coverage_mismatch（不阻塞提交，但进告警）
```

**为什么不自动重试**：重试会放大成本且掩盖提示词问题；正确的处置是"记下来 + 人工看规则表"。这条对齐 03 §5.10 的退避思路（失败后降级而不是立刻重发）。

### G7 幂等键（**是幂等键，不是去重键**）

```
idempotencyKey = sha256(batchId + "|" + turnRef + "|" + factHash)
```

| 场景 | 键是否相同 | 结果 | 是否符合预期 |
|---|---|---|---|
| 同一次压缩被重放（超时误判后重跑） | 相同 | 跳过 | ✅ 幂等 |
| 同一批里模型把同一轮的同一句话抽了两遍 | 相同 | 合并为一条 | ✅ 这是解析噪声，不是两次真实发生 |
| **同一件事真实发生两次**（同一天死两次） | **不同**（`turnRefs` 不同 → `batchId+turnRef` 不同） | **两条都留** | ✅ 这正是"事件不去重" |
| 不同批次抽到相同文本 | 不同（`batchId` 不同） | 两条都留 | ✅ 不同时段的真相不能合并 |

**必须写进代码注释**：幂等键的语义是"防止同一份输入被写两遍"，**不是**"文本相同就合并"。键里含批次与轮次，正是为了让真实重复事件无法被合并。
