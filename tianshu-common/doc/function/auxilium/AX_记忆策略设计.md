# AX 记忆策略设计

## 1. 文档定位

本文是一份 AX 记忆系统的架构大纲，不是最终字段协议或实现规格。它用于约束方向、职责边界和数据流，具体字段、阈值、索引结构、打分参数需要在实现阶段结合现有代码、模型能力和实际数据量逐步冻结。

AX 是记忆策略的所有者；LLM 模块只提供推理、embedding、RAG cache 与协议通信能力，不决定 AX 记住什么，不维护 AX 记忆生命周期。

总体思路：

```text
Raw Turn -> STM -> E -> 检索 -> STM 注入
```

其中：

- Raw Turn 负责保真。
- STM 负责语境。
- E 负责定位。
- STM 链负责恢复前因后果。
- 检索预算负责控制 prompt 成本。

## 2. 设计原则

### 2.1 模型无关

2B、本地 12B、云端模型走同一套流水线。模型切换只影响窗口大小、prompt 复杂度和注入预算，不改变记忆架构。

不同模型档位可以拥有不同的检索预算布局，例如 Hot / Warm / Cold 的召回比例、STM 链式发散深度和记忆注入上限，但这些都必须通过配置或预算策略提供，不能硬编码进检索代码。

### 2.2 工程代码兜底

时空坐标、世界归属、实体标签、记忆选择、聚类、预算分配和链式扩展由 AX 代码负责。

LLM 只做两类工作：

- 将原始对话压缩为 STM 文本。
- 从 STM 中抽取客观事实列表。

### 2.3 只存客观事实

长期记忆只保存客观事实型原子事件。

允许：

- 玩家把钻石镐放进末影箱。
- 玩家在下界死亡一次。
- 玩家说自己正在寻找村庄。
- AX 曾提醒玩家带食物。

避免：

- 主观重要性判断。
- 情绪价值判断。
- “应该永远记住”这类保留建议。
- 由模型自行推断出的偏好和性格结论。

### 2.4 真实历史不可篡改

相似事件只要真实发生，就都应保留。存储层不为了“去重”删除真实历史。

检索层可以为了本次 prompt 预算做候选到 STM 的有效映射、代表选择和结构化截断，但这只影响本次注入，不改变记忆本体。

### 2.5 不过早冻结细节

本设计只固定概念和边界。以下内容不在文档阶段硬编码：

- 具体 token 阈值。
- 具体相似度阈值。
- 具体热度公式。
- 具体实体 boost 倍率。
- 具体文件字段全集。
- 具体聚类分裂/合并参数。

## 3. 核心对象

### 3.1 Raw Turn

Raw Turn 是玩家与 AX 的原始对话轮次记录。它是最接近真实历史的保真层。

Raw Turn 至少需要表达：

- 角色。
- 文本。
- 可选发送者，用于游戏聊天 topic 等非 AX/玩家二元对话来源。
- 时间。
- 与 IA session / turn 的关联。
- 精确 token 或可用于窗口控制的长度信息。

Raw Turn 可被压缩、归档或按容量裁剪，但压缩任务必须基于只读快照执行，不能阻塞当前对话。

游戏聊天 topic 捕获到的聊天消息属于 Raw Turn 来源之一。它不等同于世界事件，也不直接作为附属事件或 E；它应保留发送者和文本，参与 STM 压缩。进入 prompt 时应与 AX/玩家对话一起渲染到近期对话时间线中，按时间交错呈现；不再单独作为 `game_chat` 区块注入。

### 3.2 STM

STM 是短期记忆块，保存一段连续对话的压缩语境。它不是事实库，而是后续检索命中后恢复前因后果的叙事容器。

STM 需要具备：

- 稳定 ID。
- 稳定内容哈希，用于幂等和按哈希校验/获取。
- 生成时间和来源时间范围。
- 与前后 STM 的时序链关系。
- 完整压缩文本。
- 可携带附属事件视图，尤其是从当前窗口抽离出的世界事件流。

附属事件不是 E，也不是长期事实本体。它是挂在某个 STM 压缩窗口上的结构化旁证，用来让“世界侧发生了什么”和“同一时间玩家/AX 聊了什么”保持同一滚动窗口边界。附属事件可以有稳定 ID、类型、去重键、发生时间、世界/维度/位置、原生 ID 和短文本。是否把某个附属事件直接写入该 STM 的 E 集，由 AX 策略决定。

初期不在文档里写死全部世界事件类型。建议边界是：

- 成就 / advancement 这类一次性、可回忆价值高、原生 ID 稳定的事件，可以在绑定到 STM 后绕过 LLM 事实抽取，直接作为该 STM 的 E 集成员写入；该 E 必须带有所属 STM ID，命中后仍然折回该 STM。
- 玩家死亡这类高频、可能重复发生的事件，优先作为附属事件去重后跟随 STM，后续再由统计、聚合或明确策略决定是否生成 E。
- 其他事件暂按附属事件或动态环境事实处理，不急于进入 LTM。

STM 链是逻辑链，不要求实现为数据库双向链表。只要能从一个 STM 找到相邻 STM，即可满足链式发散。

### 3.3 E

E 是原子事件，来自 STM 抽取或硬事件直通。E 是检索探针，用于精准定位，不负责承载完整语境。

E 需要具备：

- 稳定 ID。
- 文本事实。
- 所属 STM 的 ID 或可校验引用。
- 时间、世界、维度、可选位置。
- 是否空间绑定。
- 可选 MC 实体标签。
- embedding 引用或可重建 embedding 的版本信息。
- embedding 空间标识，用于校验持久化向量是否仍属于同一向量空间。

E 不应该保存完整父 STM 文本。需要恢复语境时，通过所属 STM 引用回到 STM 层。

### 3.4 Token 统计

所有带正文的历史对象都应保留 `tokenCount` 容量统计信息。`tokenCount` 表示通过 LLM 层 tokenizer / chat template 能力取得的真实 token 数；如果当前无法取得真实计数，应写入 `0` 表示未知，不在 AX 内做近似推断。

用途：

- 实时窗口容量判断。
- STM 压缩触发和剥离。
- 记忆注入预算计算。
- 后台任务成本估计。

历史对象上的 `tokenCount` 是 AX 的工程容量元数据，用于提前控制窗口和注入预算。最终 message-only prompt 的预算准入同样通过协议中心调用 `LLM_PRIMITIVE_QUERY / TOKEN_COUNT` 获取当前 tokenizer / chat template 下的真实计数；该能力不用于带 `rag` chunk 的完整请求，也不要求提供 embedding token count。

模型切换时，历史 `tokenCount` 不需要强制后台重算。AX 可以继续使用既有真实计数，并在新写入或关键预算计算时按需更新；未知值仍保持为 `0`。CHAT / TASK 的 usage 回传可作为本次调用成本观察，不应成为记忆主链路的硬依赖。

## 4. 三级流转

### 4.1 实时上下文窗口

实时窗口保存最近完整对话轮次。

规则：

- 用纯对话容量监控窗口。
- 以完整问答轮为切割粒度；同一个 IA turn 下的 user/assistant 以及夹在中间的游戏聊天消息必须作为同一边界处理，不能只截掉半个问答。
- 世界事件可以借道进入当前上下文，让 LLM 立即感知。
- 借道事件不计入纯对话压缩阈值。
- 借道事件不进入纯聊天压缩通道。
- 抽离出的世界事件流应先作为 STM 的附属事件视图，再跟随 STM 进入短期记忆滚动窗口。

### 4.2 STM 压缩池

当窗口达到上限时，AX 从最老对话开始剥离完整轮次，直到窗口回落到目标范围。

剥离内容分两路：

| 通道 | 来源 | 处理 |
|---|---|---|
| 世界事件流 | 成就、死亡、维度跨越等明确世界事件 | 代码抽离并绑定到对应 STM，作为附属事件跟随 STM |
| 纯聊天压缩 | 剥离出的普通对话 | LLM 压缩为 STM |

STM 队列保留近期若干块。超过保留范围的旧 STM 进入 LTM 原子化流程。

世界事件流是 STM 的附属事实源，不等同于 E。哪些事件可以在绑定 STM 后直接写入该 STM 的 E 集，由 AX 策略决定：一次性、可回忆价值高的事件可以成为直接 E；高频重复事件可以保留为 STM 附属视图、统计项或后续聚合输入，避免把 LTM 变成事件日志。

### 4.3 LTM 原子化

旧 STM 进入后台任务，由 LLM 抽取客观事实列表，再由代码补齐元数据并生成 E。

流程：

```text
Old STM
  -> LLM 抽取客观事实列表
  -> 代码切分和校验
  -> 代码补齐时空、实体、父 STM 引用
  -> 合并 STM 原子事实 + 策略允许直写 E 的附属世界事件
  -> 生成同属该 STM 的 E，或保留为附属事件/统计输入
  -> embedding
  -> 入库
```

LLM 不输出重要性、标签权重、保留建议或主观判断。

## 5. 检索与注入

### 5.1 基础检索

玩家提问时，AX 根据 query 检索 E。实现上不能退化成全局向量 Top-K；必须先经由双层 E 聚类索引路由，再在候选簇内做精排与预算分配。

打分因子可以包括：

- 语义相似度。
- 实体标签匹配。
- 时间衰减。
- 条件式空间衰减。
- 簇级热度。

这些因子是检索策略，不改变 E 本体。实体锚定必须是软加权，不是硬过滤。

检索阶段要支持 Hot / Warm / Cold 分层召回：

- Hot 优先承接当前语义最强、实体最稳的候选。
- Warm 用于补足同簇或近簇的相关 STM。
- Cold 用于低频但仍有恢复价值的历史片段。

各层比例、阈值和发散深度由预算策略配置化决定，不写死在代码里。

### 5.2 从 E 映射到 STM

E 命中后，AX 不直接把零散 E 全部塞进 prompt，而是先映射回所属 STM。

原因：

- E 适合定位，但缺少前因后果。
- STM 是一段压缩语境，适合让 LLM 理解发生过什么。
- 多个 E 命中同一 STM 时，本次注入只需要一次该 STM。

这里的映射不是存储去重，只是本次检索视图中的预算代表选择。
当多个 E 命中同一 STM 时，STM 还需要先计算自己的贡献分，再参与后续排序；贡献分应由该 STM 下命中的 E 集合聚合得到，而不能只看某一个弱 E。具体聚合公式留给实现阶段冻结。

贡献分只负责决定候选 STM 是否值得进入预算。最终注入时应按 STM 的时序链恢复顺序，并做物理去重：同一次 prompt 中，同一个 STM 最多出现一次；命中 `e1 -> s2`、`e2 -> s3` 时，最终注入应是连续且不重复的 `s2, s3`，而不是多个 `s2` 或多个 `s3`，也不应因为 `s3` 分数更高就把叙事顺序倒置。

`AXPromptAssemblyBuilder` 不负责理解 E，它只消费已经折叠成 STM 的文本块。

### 5.3 STM 链式发散

当命中非常集中且置信度较高时，AX 可以从中心 STM 向前后相邻 STM 扩展，以恢复故事线。

适合：

- 玩家问具体历史事件。
- 多个命中 E 指向同一 STM 或相邻 STM。
- query 带有明确实体、地点或时间线索。

当命中分散或问题宽泛时，AX 应优先选择多个不同 STM，而不是沿单点链路扩展。

链式发散深度必须与当前模型档位预算挂钩，不能固定成一个全局常量。

适合：

- “我最近做了什么？”
- “我这周有什么计划？”
- “我们之前聊过哪些重要事情？”

### 5.4 注入预算

记忆注入必须受 token 预算控制。

原则：

- 不截断 STM 正文内部。
- 完整 STM 放不下时跳过。
- 同一次 prompt 不重复注入同一个 STM。
- 预算策略由当前模型能力和请求类型决定。

### 5.5 与外部上下文的隔离边界

玩家个人记忆必须与动态环境、静态知识库等外部来源隔离注入。

本文只约束玩家记忆侧的选择、映射和注入边界。动态环境匹配、静态知识库 RAG 召回、prompt 标签排版属于 AX 模块请求编排策略，应在模块架构文档中定义。

AX 私有动态记忆的权威数据不写入 LLM RAG cache。玩家个人经历由 AX 自己持有 Raw Turn、STM、E，并在检索命中后映射 STM、拼接为普通 message chunk；LLM RAG 只可保存 AX 私有、可重建的检索投影，用于按 `uid + entryId` 返回二级簇或 eventId。外部静态知识库可以复用 shared LLM RAG cache，但不得与玩家记忆混为同一存储或同一注入区。

`AXGameContext` 与 `AXMemory` 在一期 baseline 中是并列模块，不应在模块内互相传递检索结果。

## 6. 聚类与高级检索

双层 E 聚类是合理方向，但不作为首批实现前提。


- L1 粗簇：场景级路由，减少全库扫描。
- L2 细簇：极相似 E 的候选到代表的有效映射依据。

注意：

- 聚类是索引结构，不是历史裁剪机制。
- L1 和 L2 都可以有聚合与分裂能力；聚合用于减少候选面，分裂用于避免旧簇过宽导致召回污染。
- L2 细簇内的多个 E 仍然是真实事件。
- 本次查询可选择代表 E 建立有效映射，但不能删除其他 E。
- 细簇的作用更接近“有效映射/候选代表选择”，不应被理解成对历史事件做物理去冗余。

后续还可以引入：

- Hot/Warm/Cold 时间预算。
- 实体图谱软锚定。
- 条件式空间衰减。
- 簇级热度。

这些都属于检索增强，不应影响 Raw Turn、STM、E 的基本流转。

## 7. 并发与模型切换

压缩和 LTM 原子化应走后台任务。

要求：

- 使用 Raw Turn 或 STM 的只读快照。
- 主对话链路不等待压缩完成。
- 任务失败不修改现有记忆。
- 重试必须幂等。
- STM 链更新必须避免断链。

模型切换时只调整窗口和预算：

- 大模型切小模型：保留最新完整轮次，超出部分进入后台压缩。
- 小模型切大模型：扩大窗口和注入预算，不解冻已压缩数据。

## 8. 存储原则

AX 记忆应归属于 AX 模块，不直接写入 LLM 内部 cache 文件。存储根以 `AXStorageLayout` 为准；推荐逻辑位置是 `config/Tianshu/module/ax/cache/`，再按 world 分层。现有实现若仍使用旧路径，应通过 `AXStorageLayout` 统一迁移或兼容，不在业务代码中散落硬编码路径。

推荐采用“权威数据 + 派生索引”的分层：

```text
config/Tianshu/module/ax/cache/
  shared/
  worlds/<worldId>/
    raw_turns/
    stm_blocks/
    events/
    vectors/
    indexes/
    stats/
```

具体文件名、字段名、索引格式可以在实现阶段根据现有 `AXStorageLayout` 和迁移成本确定。文档只约束逻辑归属，不要求上层直接拼接物理路径。

持久化格式一旦进入正式版本，就应按向后兼容处理：

- 权威记录只允许新增字段或新增记录类型，不允许删除旧字段含义。
- 读路径必须容忍旧 `schemaVersion`、缺失新增字段和未知字段。
- 写路径写当前版本字段；迁移逻辑集中在存储层或迁移器，不散落在业务流程。
- 任何全量重写、compaction 或迁移都必须先写临时文件，再原子替换目标文件。
- 可重建索引可以替换，但 Raw Turn、STM、E 和向量组元数据不能被索引重建过程破坏。

### 8.1 权威数据

Raw Turn、STM、E 都属于可追溯历史的来源，但不要求每次新增一条就立刻同步写盘。更稳的做法是先进入内存滚动窗口，在压缩触发、周期 checkpoint、会话暂停或关闭时再批量落盘。

建议：

- Raw Turn 适合按批 checkpoint，而不是逐条同步持久化。
- STM 可以使用 JSONL 或分段 JSONL，按块追加。
- E 可以使用 JSONL 保存元数据，但不建议把完整向量内联进 JSONL。
- STM 和 E 都应携带真实 `tokenCount`，便于离线预算统计；无法取得真实计数时写入 `0`，不在 AX 内推断。

JSONL 的优势是简单、可检查、易迁移；缺点是随机读取和大规模向量存储不适合。因此 JSONL 更适合作为权威元数据，而不是高性能索引。追加式 JSONL 应允许启动时跳过或修复尾部半行；需要整体重写、裁剪或 compaction 时，必须写临时文件后再替换目标文件。

### 8.2 向量与聚类

E 需要先获得 embedding，才能参与向量检索和后续聚类。向量结果应被视为 E 的派生数据，但建议持久化，避免每次启动都重新 embedding。

建议：

- E 元数据中保存向量引用、向量维度和 embedding 空间标识。
- 向量本体放在独立的向量文件或向量段中。
- 向量按 embedding 空间分组缓存，不同空间的向量不能混排。
- embedding 空间不匹配时，旧向量组仍可保留，但不参与当前空间检索。
- 新 embedding 空间首次启用时，历史 E 向量按批渐进重建；批次之间应让出调度，允许 CHAT、TASK 或其他请求插入。
- 聚类结果属于派生索引，可持久化快照，也应能由 E 元数据和向量重建。

向量不是 LLM prompt result 的必备返回值。AX 如需跨模块边界拿到向量，应通过协议中心调用 `LLM_PRIMITIVE_QUERY / EMBED`，不要把它混进普通对话返回。

### 8.3 读写策略

为减少磁盘写入，主记录应尽量不可变：

- Raw Turn 追加。
- STM 追加。
- E 追加。
- 向量批量写入。
- 聚类和统计按批次 checkpoint。

命中次数、热度、lastHit 等高频变化不应频繁改写主 JSONL，可以放入独立 stats 区域，在内存中累积后定期落盘。即使 stats 丢失，也不应破坏记忆本体。

查询时不应临时扫描 JSONL。活跃世界应在加载时构建内存视图：

- `stmId/hash -> STM` 或 `stmId/hash -> 文件偏移`。
- `eventId -> E`。
- `E -> owner STM`。
- 向量矩阵或可 mmap 的向量视图。
- 聚类和有效映射索引。

这样查询路径可以主要走内存索引，磁盘只作为启动加载、懒加载或缺页兜底。

写入路径应优先合并小写入：Raw Turn、STM、E、向量、stats 都可以在内存中短暂累积后按批落盘。玩家可见对话链路不等待非必要 checkpoint；崩溃时最多丢失尚未 checkpoint 的短期窗口，不应破坏已落盘的权威数据。

### 8.4 压缩与重建

索引、聚类、offset、stats 都可以视为可重建数据。实现上可以周期性做 compaction，把追加段合并成更适合读取的快照。

原则：

- 权威数据优先保证安全写入。
- 派生索引优先保证读取性能。
- 派生索引损坏时，应能从 Raw Turn、STM、E 和向量数据重建。

外部静态知识库和 AX 私有检索投影都只能通过 `ProtocolCapabilities.LLM_CACHE_MANAGE` 写入或检索，不能直接修改 LLM cache 二进制文件。动态环境事实不属于 AX 长期记忆；AX 动态记忆权威数据也不写入 LLM RAG cache。

## 9. 与 LLM 协议的关系

AX 对 LLM 的所有访问都必须经过协议中心。

允许：

- `ProtocolCapabilities.LLM_REQUEST`
- `ProtocolCapabilities.LLM_PRIMITIVE_QUERY`
- `ProtocolCapabilities.LLM_CACHE_MANAGE`

禁止：

- 直接调用 `LLMService`。
- 直接访问 `JavaLlamaServer`。
- 直接写 LLM RAG cache 二进制文件。
- 让 UI/TTS 直接订阅底层 LLM stream。

当前协议层可支撑 AX 记忆的底层能力包括：

- `LLM_PRIMITIVE_QUERY / TOKEN_COUNT`：用于 text / message-only 的无副作用 token 计数。
- `LLM_PRIMITIVE_QUERY / EMBED`：用于批量文本向量化，并返回向量维度与 embedding 空间标识。
- `LLM_PRIMITIVE_QUERY / STATUS`：用于获取模型、上下文配置和 embedding 空间快照。
- `LLM_CACHE_MANAGE` / RAG 检索能力：用于复用 LLM 模块的 shared 静态知识库能力，以及 AX 私有记忆检索投影的 uid/entryId 命中；玩家可见 CHAT 的最终 prompt 由 AX 组装为 message-only。
- `LLM_REQUEST` 的 result / stream terminal usage：用于观察 CHAT / TASK 的实际调用成本。

embedding 向量不混入普通 prompt result。AX 私有记忆由 AX 自己加载权威 E、映射 STM、拼接后作为普通 message chunk 注入；LLM 私有 RAG 投影只负责返回候选 entryId。外部知识库、规则库和模组资料可以复用 LLM 的静态知识检索或 cache 管理能力，但玩家可见 CHAT 的最终 prompt 仍由 AX 整理为 message-only。静态知识检索结果进入 prompt 前应先被适配为 AX 自己的知识命中对象，再按直接静态路径或动态事实路径渲染进 `<game_context>`，不要把 LLM rag chunk 当作 AX prompt 编排层的内部结构。

后台压缩使用 `lane=TASK`。玩家可见对话使用 `lane=CHAT`，并携带 IA 授权上下文。

## 10. 写入安全

持久文件写入必须保证不会出现半写入状态。

推荐策略：

```text
读取当前文件
  -> 内存中生成新内容
  -> 写入临时文件
  -> flush / close
  -> 替换目标文件
```

普通日志禁止输出完整玩家输入、prompt、记忆正文、RAG hit 明细和完整 LLM response。

## 11. 禁止事项

- 禁止 LLM 模块决定 AX 记忆生命周期。
- 禁止把临时动态事实直接写入 LTM。
- 禁止把所有聊天原文无限追加进 LTM。
- 禁止删除真实发生过的相似历史来追求“去重”。
- 禁止让单条记忆维护动态热度或动态 importance。
- 禁止跨世界共享 AX 记忆，除非有明确配置和权限。
- 禁止在未获得 IA 授权时生成玩家可见的记忆相关回复。

## 12. 落地建议

实现时建议按风险递增：

1. 先打通 Raw Turn、STM、E 的基本流转。
2. 再做 E 检索和 STM 映射注入。
3. 再加入 STM 链式发散。
4. 数据量上来后再做双层 E 聚类。
5. 最后再加时间预算、空间衰减、实体图谱和簇级热度。

每一步都应保持前一步可独立运行，不让高级检索策略成为基础记忆链路的前置依赖。
