# 对话式 AI 记忆与上下文策略 — 技术调研

> 目标场景：Minecraft 语音助手（单会话、实时语音、云端 LLM DeepSeek、已有本地 RAG `bge-large-zh`、后续要接工具调用与后台任务）
> 调研时间：2026-10（文内链接均为本次实测可访问）
> 产出定位：为工程决策提供可追溯依据，不含任何实现代码

---

## 0. 结论速览

1. **前缀缓存是这个项目最大的成本杠杆，而不是记忆算法。** DeepSeek 文档给出的价格中，缓存命中与未命中同为 1M 输入 token 时相差 **50 倍**（`deepseek-flash` 峰时 $0.006 vs $0.3）。所有"每轮改写历史"的记忆方案在这个价格结构下都是负收益；改用 append-only 前缀，等于把每轮成本压到 1/50（[DeepSeek 定价](https://api-docs.deepseek.com/quick_start/pricing)、[上下文硬盘缓存](https://api-docs.deepseek.com/guides/kv_cache)）。
2. **所有"自主编辑上下文"的记忆系统（MemGPT/Letta、A-MEM、Mem0-graph 的实体回写）都天然反缓存**——因为它们的记忆槽位被**前置**到 prompt 里（Letta 明确写"memory blocks are simply prepended to the agent's prompt"），改一个字符，后面全部失效。
3. **值得引入的不是某个系统的实现，而是两条纯本地的机制**：(a) Generative Agents 的 recency/importance/relevance 三因子检索打分 + MemoryBank 的遗忘曲线——零额外 LLM 调用、不进 prompt 前缀、可复用现有 `bge-large-zh`；(b) Anthropic 的 compaction + 工具结果裁剪（放后台线程）——工具调用上线后必然需要。
4. **Zep/Graphiti 的双时序边失效（`t_valid`/`t_invalid`）思想值得抄，图数据库不值得上**。玩法状态变更用"失效标记 + 时间戳"在 SQLite 里就能表达。
5. **中文有三个具体坑**：汉字 ≈ 0.6 token（DeepSeek 官方换算）；`bge-large-zh-v1.5` 的 `max_position_embeddings=512` 硬顶，单条 chunk 不能超过约 500 字；ASR 同音错字会直接打穿向量检索，Minecraft 专有名词必须走"精确/拼音/别名词典"兜底。
6. **Java 侧没有可用的现成轮子**：Mem0 只有 Python/Node SDK、Graphiti 是 Python 3.10+ 且强依赖 Neo4j/FalkorDB、Cognee 是 Python、LangMem 依赖 LangGraph。Letta 有 REST API 但会接管 agent 主循环，与我们的前缀缓存策略冲突。**结论：自研，借鉴机制，不引入依赖。**

## 2. 对话记忆系统逐项分析

统一模板：**定位 → 机制 → 取舍 → 缓存友好度 → 对我们是否适用**

### 2.1 MemGPT / Letta

**定位**：把 LLM 上下文当"虚拟内存"管理的操作系统式方案，是"分层记忆 + 自主编辑上下文"这条线的起点。

**机制**（源自 [arXiv:2310.08560](https://arxiv.org/abs/2310.08560) 正文）：

- **主上下文（main context）= prompt tokens**，被切成三段连续区：`system instructions`（只读、静态）+ `working context`（可编辑的槽位）+ `FIFO queue`（滚动消息历史）。
- **FIFO 队列的第 0 位放一条系统消息，内容是"被驱逐消息的递归摘要"**——这是滚动摘要在学术方案里的原型。
- **外部上下文 = archival storage（向量库）+ recall storage（完整历史库）**，只能通过函数调用显式搬进主上下文。
- **内存压力机制**：当 prompt tokens 超过窗口的 **70%** 时，系统向队列插入"即将驱逐"的系统消息警告 LLM，由 LLM 自己决定压缩/搬移。
- **`request_heartbeat=true`** 允许 LLM 连续发起推理、链式调用函数（多步检索），不必把控制权交回用户。
- 评测 DMR（Deep Memory Retrieval）**93.4%**。

**Letta 的工程化**（[memory blocks 文档](https://docs.letta.com/v1-sdk/memory/memory-blocks/)）：

- 记忆被抽象成 **memory block**：`label` + `description` + `value` + `limit`(字符数)。
- **关键事实："memory blocks are simply prepended to the agent's prompt in an XML-like format"**，并且 `<metadata>` 里还会写入 `chars_current` / `chars_limit`——即**块内字符数变化本身就会改变 prompt 字节**。
- 现在（2026-10）Letta 已把记忆演进为 **MemFS（git-backed 记忆文件系统）**，并引入 **dreaming**：后台子代理在"完成 N 步后或上下文被压缩时"复盘对话、整合记忆；另有 `/doctor` 专门"审计记忆放置、重复与 **system-prompt token 用量**"（[配置文档](https://docs.letta.com/configuration/memory)）。

**取舍**：

| 得到 | 付出 |
|---|---|
| 记忆规模不受窗口限制；上下文由模型自主取舍，能处理"超长文档分析" | 每轮可能触发额外 LLM 调用（编辑记忆=又一次推理），延迟不可控 |
| 记忆是"结构化可读"的，人可审计 | 记忆写入质量完全依赖模型判断，容易写坏/写冗 |
| 分层清晰（热/温/冷） | 实现复杂度高：函数调度、错误回灌、状态机、驱逐策略都要自己写 |

**缓存友好度：差（在默认用法下）**。

- 每轮变化的：`working context`（模型随时改写）+ `FIFO queue`（追加）+ `<metadata>` 里的 `chars_current`。
- `working context` 在 **prompt 最前端**（system instructions 之后），它一变，**后面整段历史的前缀全部失效**。
- Letta 自己有"dreaming"这种把记忆整合挪到后台的设计，方向正确，但**并没有改变"记忆在 prompt 前缀里"这个事实**。
- 唯一稳定的部分是 `system instructions`（只读静态），它能持续命中——这恰好证明我们的思路：**易变内容必须挪到尾部，稳定内容留在头部。**

**对我们是否适用**：**机制借鉴，系统不引入**。

- 借鉴：三层记忆划分（热槽位 / 可检索历史 / 归档）、70% 水位告警、递归摘要。
- 不引入：Java 侧只能走 Letta 的 REST API（官方客户端是 Python `letta-client` 与 TypeScript `@letta-ai/letta-client`，见 memory-blocks 文档示例），而且 Letta 要接管 agent 主循环与工具调度——这会把我们的 prompt 布局权交出去，直接放弃前缀缓存控制权。语音场景对首 token 延迟极敏感，额外一次"编辑记忆"的 LLM 往返不可接受。

### 2.2 Mem0

**定位**：把对话"抽取成事实条目"再检索的记忆中间层，工程化和产品化程度最高。

**机制**（[arXiv:2504.19413](https://arxiv.org/abs/2504.19413) + [官方 docs](https://docs.mem0.ai/core-concepts/memory-types)）：

- 两阶段：**extraction（抽取）→ update（更新）**。
- 抽取：以 `(m_{t-1}, m_t)` 消息对为单位，附带**两路上下文**（历史消息 + 相似已有记忆）让 LLM 产出候选事实。
- 更新：对每条候选事实先向量检索 **top s = 10** 条语义相似记忆，再由 LLM 以 **tool call** 形式决定操作——**ADD / UPDATE / DELETE / NOOP**（论文 Algorithm 1 显式含 NOOP）。
- 默认配置：`m = 10` 条历史消息、`s = 10` 条相似记忆、推理用 GPT-4o-mini、向量库存稠密 embedding。
- 图变体 **Mem0^g**：抽取实体与关系三元组，冲突检测 + 解析写回 Neo4j。
- 报告收益：相对 OpenAI 记忆 `LLM-as-a-Judge` **+26% 相对提升**；图变体再 **+约 2%**；相对 full-context 方案 **p95 延迟 −91%**、**token 成本 −90%+**。
- 开源版默认栈（[OSS overview](https://docs.mem0.ai/open-source/overview)）：LLM `gpt-5-mini`、embedding `text-embedding-3-small`、向量库本地 Qdrant、历史库 SQLite——**`pip install mem0ai` / `npm install mem0ai`，无 Java 实现**。

**取舍**：

| 得到 | 付出 |
|---|---|
| 存储的是"事实"而非原文，检索极省 token | 每轮/每对消息至少 **2 次额外 LLM 调用**（抽取 + 更新判定），延迟与成本叠加 |
| 去重、冲突消解、可更新，长期一致性最好 | 事实抽取会**丢语气、丢上下文、丢多义**——"我腰疼"压成"用户腰疼"就丢了严重程度 |
| 有明确的写入门控（NOOP），抑制记忆膨胀 | 需要向量库 + 关系库两套存储；图变体还要图库 |

**缓存友好度：中性偏好（因为它根本不改历史）**。

- Mem0 的哲学是"不要重放 transcript"，所以它**不会把记忆前置进 prompt**；记忆是每次 search 出来拼在**用户消息之前或之内**（尾部），历史本身可以保持 append-only。
- 每轮变化的只有尾部的"检索到的记忆块"。**这正是缓存友好的形态**——但会带来一个问题：**同一份记忆在不同轮次被检索出来，排序/内容可能不同，尾部每次都变**，虽然不破坏前缀，但会让"带记忆的这一段"永远 miss。
- 优化方向：把检索结果**按会话固定**（同一话题内不重复检索），或只在用户输入"意图切换"时检索一次。

**对我们是否适用**：**机制借鉴（写入门控 + ADD/UPDATE/DELETE/NOOP 语义），系统不引入**。

- 借鉴点最实在：**"先查 top-k 相似记忆，再决定写不写"** 这个去重逻辑，用 `bge` + SQLite 就能实现，不需要 LLM 也能做 80 分的版本（相似度阈值 + 冲突标记）。
- 不引入理由：Java 无 SDK；抽取阶段必需 LLM，会翻倍语音回合的响应链；且 Mem0 的强项是**跨会话长期用户画像**，我们是**单会话**，收益被摊薄。

### 2.3 Zep / Graphiti

**定位**：时序知识图谱记忆，是目前"信息随时间演化"这件事上形式化程度最高的方案。

**机制**（[arXiv:2501.13956](https://arxiv.org/abs/2501.13956)）：

- 图 `G = (N, E, φ)`，分三层子图：
  - **Episode 子图**：原始消息/文本/JSON 作为"无损"数据源节点；
  - **Semantic Entity 子图**：从 episode 抽取的实体与事实边（事实可被多次抽取 → 实现 hyper-edge）；
  - **Community 子图**：强连通实体簇的高层摘要，社区检测用 **label propagation**（而非 GraphRAG 的 Leiden），理由是"支持动态扩展"。
- **双时序（bi-temporal）**：时间线 `T` 是事件发生顺序，`T'` 是摄入顺序；每条边记 **4 个时间戳**：`t_valid` / `t_invalid` / `t'_created_at` / `t'_expired_at`。
- **边失效（edge invalidation）**：新边与语义相关旧边交给 LLM 判断是否矛盾；矛盾则把旧边 `t_invalid` 置为新边的 `t_valid`——**不删除，只失效，保留历史**。
- 实体抽取时带上**最近 n = 4 条消息**作为上下文（两个完整对话轮）；实体名嵌入 **1024 维**，再叠加全文检索找候选，最后消解。
- 报告结果：DMR **94.8% vs MemGPT 93.4%**；LongMemEval 准确率提升最高 **18.5%**，同时延迟降低 **90%**。
- Graphiti 工程要求（[README](https://github.com/getzep/graphiti)）：**Python 3.10+**；图库 **Neo4j 5.26 / FalkorDB 1.1.2 / Amazon Neptune / Kuzu 0.11.2（已弃用）** + 全文检索后端；默认用 OpenAI 做 LLM 与 embedding，"最适合支持 Structured Output 的模型服务"。
- 检索是 **semantic embedding + BM25 + 图遍历的 hybrid**，官方强调"不依赖 LLM 摘要"。

**取舍**：

| 得到 | 付出 |
|---|---|
| 真正处理"事实会变"：搬家、换工作、改设定，历史可追溯 | 每轮摄入要跑实体消解 + 事实抽取 + 冲突判定，**LLM 调用量与延迟都最高** |
| hybrid 检索精度高，不需 LLM 摘要做压缩 | 运维一整套图数据库 + 全文检索，对一个 Minecraft 模组是灾难级依赖 |
| 双层时序建模干净 | 中文实体消解没有公开评测（见 §1.4） |

**缓存友好度：差**。

- 每轮变化：可能回写的**实体摘要节点**与**社区摘要**。这些摘要如果被放进 prompt（Graphiti 的 community summary 用法正是如此），就落进了前缀区。
- 但它有一个**缓存友好**的部分：**它把"总结"换成了"图检索"**，所以不需要每 N 轮跑一次摘要重写——**减少了一次全局前缀重写**。这是它相对"滚动摘要"路线的隐性优势。

**对我们是否适用**：**只抄数据模型，不抄系统**。

- 值得抄：`t_valid` / `t_invalid` 的**失效而非删除**语义。Minecraft 场景里"玩家把基地从 A 搬到 B"、"当前装备从铁剑换成钻石剑"，用一张 `state_facts(entity, attr, value, t_valid, t_invalid)` 表就能表达，不需要图库也不需要 LLM 判矛盾——**规则可判定（同主键新值覆盖旧值）**，比 LLM 判矛盾更可靠、更便宜。
- 不引入理由：Python + 图数据库 + OpenAI key 三件套，Java 模组里等于外挂一个服务；单会话场景也没有"跨会话事实演化"的强需求。

### 2.4 A-MEM

**定位**：Zettelkasten（卡片盒）风格的"代理式"记忆，让记忆自己长出链接并互相改写。

**机制**（[arXiv:2502.12110](https://arxiv.org/abs/2502.12110)）：

- **Note Construction**：每条记忆不是一个字符串，而是一个结构化笔记 `m_i = (c_i, t_i, K_i, G_i, X_i, L_i)`——原始内容、时间戳、**LLM 生成的关键词**、**LLM 生成的标签**、**LLM 生成的上下文描述**、**链接集合**。
- **Link Generation**：先检索最相关的历史记忆，再由 LLM 判断是否建立连接。
- **Memory Evolution**：新记忆写入时，**反向触发已有记忆的上下文描述更新**——这是它区别于其他系统的核心，也是"记忆会互相改写"的来源。
- 检索 top-k = 10；报告每次记忆操作约 **1,200 tokens**，相对 LoCoMo/MemGPT 的 16,900 tokens **省 85–93%**。

**取舍**：

| 得到 | 付出 |
|---|---|
| 记忆是"带语义注释的图"，检索时不需要长原文 | 写入路径极重：一条记忆要 3~4 次 LLM 调用（建笔记 + 生成关键词/标签/描述 + 判连边 + 演化旧笔记） |
| 演化机制让旧记忆保持"当前视角" | **"演化"= 悄悄改写历史**，不可逆、难审计，出问题无法回溯 |

**缓存友好度：差，且是四种里最差的**。

- `Memory Evolution` 会**在写入新记忆时改写旧记忆**。如果记忆内容进 prompt，这等于**无预警地重写前缀**——比"每轮追加"恶劣得多，因为它连"什么时候变"都不可预期。
- 论文的省 token 是真的（1,200 vs 16,900），但那是"检索出的内容少"，不是"前缀稳定"。

**对我们是否适用**：**不适用，机制也不建议抄**。

- 语音助手场景里"记忆自我改写"是纯风险：玩家说"我刚才是开玩笑的"，系统已经把上一句演化成事实，无法撤销。
- 我们要的是**可撤销、可审计、可回滚**的记忆，这与"演化"的哲学相反。

### 2.5 MemoryBank

**定位**：面向"长期陪伴/心理咨询"的记忆系统，是**唯一明确声明中英双语能力**的方案，因此对中文项目参考价值被低估。

**机制**（[arXiv:2305.10250](https://arxiv.org/abs/2305.10250)）：

- 三支柱：**记忆存储**（历史对话 + **事件摘要** + **用户画像**）、**记忆检索**、**记忆更新**。
- **遗忘机制直接搬 Ebbinghaus 遗忘曲线**：`R = e^(-t/S)`，`R` 是留存率、`t` 是距学习的时间、`S` 是记忆强度。
  - `S` 被简化为离散值，**首次提及初始化为 1**，被召回时增强（对应"间隔效应"：复习会让曲线变平）。
  - 论文自己声明这是"探索性的、高度简化的模型"。
- **保留的是三个层次的东西**：原始对话、摘要出的"事件"、以及从交互中总结的**用户人格画像**。
- 明确声明三项泛化能力：开源/闭源 LLM 都可用、**中英双语**、有无遗忘机制都可用。

**取舍**：

| 得到 | 付出 |
|---|---|
| 遗忘曲线给出**无需 LLM 的**记忆淘汰规则，成本≈0 | 指数衰减参数（`S` 的增长幅度、半衰期）需要按场景调，论文没有给通用值 |
| "事件摘要 + 用户画像"分层，比纯原文检索省 token | 摘要仍要 LLM 生成（异步可接受） |
| 有中文实验 | 规模小、年代早（2023），绝对效果不代表今天 |

**缓存友好度：中（取决于画像放哪）**。

- 检索出的记忆条目放尾部 → 友好。
- 但**用户画像如果是"每轮刷新后前置到 system prompt" → 灾难**（每轮全 miss）。正确做法是画像**只在一段对话开始时计算一次**，或者作为尾部一条消息注入。

**对我们是否适用**：**强烈建议借鉴其遗忘曲线 + 三层存储**。

- 复用成本极低：`S` 只做加法，`R` 一次 `exp` 调用，纯本地、零 LLM。
- 中文证据虽是 2023 年的，但它是**唯一给了中文评测**的记忆论文，可作为"中文场景下这条路走得通"的弱证据。

### 2.6 Generative Agents 的 memory stream

**定位**：不是"对话记忆系统"，而是**智能体行为的记忆检索打分函数**。它是本次调研中**最可直接落地、性价比最高**的成果。

**机制**（[arXiv:2304.03442](https://arxiv.org/abs/2304.03442)）：

- **memory stream**：以自然语言记录智能体的**完整经历**（observation / plan / reflection 三类）。
- **检索三因子**，各自归一化到 `[0,1]`（min-max）后线性加权：

  ```
  score = α_recency · recency + α_importance · importance + α_relevance · relevance
  ```

  - **recency**：以"内存最后被检索以来经过的游戏小时数"做**指数衰减**，衰减因子 **0.995**。
  - **importance**：创建时由 LLM 打 **1~10 分**（例："整理房间" = 2，"约暗恋对象出去" = 8）。
  - **relevance**：以"当前 query 记忆"为条件做 embedding 相似度。
  - **实现中所有 α 都设为 1**；取分数最高的若干条填满上下文窗口。
- **reflection**：当最近感知事件的**importance 累计超过阈值（实现取 150）**时触发反思，把观察递归综合成高层认知；实测约每天 2~3 次。

**取舍**：

| 得到 | 付出 |
|---|---|
| 打分函数是**纯本地数学**（除 importance 一次性打分外），零延迟、零额外调用 | 需要为每条记忆存 `importance`、`last_access_time`、`embedding` 三个字段 |
| 三因子可解释、可调权，出问题能定位 | `0.995` 是按"游戏小时"标的，需要重标到真实时间尺度 |
| relevance 直接复用已有 embedding 模型 | importance 打分要一次 LLM 调用（可批量、可离线） |

**缓存友好度：完美（本调研中最好）**。

- 整个打分发生在**检索阶段**，产物是"若干条记忆文本"，注入到 prompt **尾部**。
- 记忆库的写入/更新**完全不触碰 prompt 前缀**。
- 唯一要守住的是：**注入的记忆集合在同一轮内不要变**（不要在一次请求里检索两次）。

**对我们是否适用**：**首选引入（打分函数），立刻可做**。

- recency 用真实时间（游戏刻/秒）重标衰减率；relevance 用现成 `bge-large-zh`；importance 可以先**用规则近似**（例：涉及"承诺/偏好/坐标/物品归属"→ 高分；寒暄 → 低分），完全避免 LLM 调用，后续再决定是否接 LLM 打分。
- 这套东西在 Java 里就是几十行数学 + 一个 `ORDER BY`，**没有架构负担**。

### 2.7 Cognee

**定位**：将"文档/代码/对话"统一转成可检索知识图谱的**自托管记忆平台**，主打 ECL（Extract–Cognify–Load）流水线与多后端解耦。

**机制**（[README](https://github.com/topoteretes/cognee)）：

- 三类数据三类产物：**文本 → 实体/关系/可检索 chunk**；**代码 → 符号与依赖图**；**会话 → 蒸馏出的经验（session distillation）**。
- 对外操作抽象为 `cognify`（建图）、`recall`（检索，支持自动路由或指定策略）、`improve`（用反馈增强记忆、把会话知识桥接进图）。
- 强调"不需要同时运维图库+向量库+Redis+关系库"的一体化，但也承认 **Postgres 作为图存储目前是 demo 特性，生产版为授权产品**。
- 提供 **COGX 交换格式**，可导入 Mem0 / Letta / Zep / Graphiti 的记忆——**说明这四家的数据模型已被业界视为可互换的"事实+关系"形态**。
- 支持无 LLM key 的本地小模型（GLiNER 抽取）运行，但官方注明"生产级准确率需联系商务"。

**取舍**：一体化降低运维，但自托管小模型质量与商业版有明确差距（官方自述），且 `improve` 环节会回写图——仍是"会改写状态"的系统。

**缓存友好度：差**（同 Zep 类：社区/实体摘要会回写并可能进 prompt）。

**对我们是否适用**：**不适用**。Python 生态，图+向量+关系三套存储，为 Minecraft 语音助手引入等于自建数据平台。它的 `recall` 抽象（自动路由检索策略）是好的接口设计参考，但仅此而已。

### 2.8 LangMem / LangGraph 的 memory 抽象

**定位**：目前**概念划分最清晰**的一层抽象，适合抄"术语与分层"，不适合引入运行时。

**机制**（[LangGraph 记忆概念](https://langchain-ai.github.io/langgraph/concepts/memory/) + [LangMem README](https://github.com/langchain-ai/langmem)）：

- **按作用域二分**：
  - **短期记忆**：**thread 作用域**，作为 agent state 的一部分，由 **checkpointer** 持久化，可随时恢复；
  - **长期记忆**：**自定义 namespace 作用域**，跨 thread 共享，存于 **store**（JSON 文档 + namespace/key 层级组织）。
- **按类型三分**（对齐 CoALA 论文）：**semantic**（事实）、**episodic**（经历）、**procedural**（指令 / system prompt）。
- **按写入时机二分**，并明确给出权衡：
  - **hot path（热路径）**：实时可用、可告知用户，但**增加 agent 复杂度、影响延迟、且要"一心二用"导致记忆质量下降**；
  - **background（后台）**：不占主路径延迟、逻辑解耦、可择时去重，但**写入频率难定**、其他线程可能看不到新上下文。
- LangMem 提供：可插拔的 core memory API（配任意存储）、hot path 用的 `create_manage_memory_tool` / `create_search_memory_tool`、**后台 memory manager（自动抽取/整合/更新）**、以及 prompt 优化器。

**取舍**：抽象极好，实现重（Python/JS）；`store` 是通用 KV，语义检索能力依赖外部索引配置。

**缓存友好度：中性**——取决于你把 store 内容放哪。LangGraph 的常见实践（把检索到的记忆拼进 system prompt）是**反缓存**的，需要主动规避。

**对我们是否适用**：**照抄术语与二分法，不用其代码**。

- 采用它的四象限做我们的设计坐标系：**作用域（会话 / 玩家）× 类型（事实 / 经历 / 规程）× 写入时机（热 / 后台）**。
- **"hot path 会拖慢并降低记忆质量"** 这条结论对我们极关键：语音场景**默认走 background**，只有"玩家明确说'记住'"才走 hot path。

### 2.9 向量检索之外的三条路线

#### 2.9.1 滚动摘要 / compaction

- **MemGPT 的递归摘要**（FIFO 队列第 0 位）：被驱逐消息压成一条不断自我更新的系统消息（[arXiv:2310.08560](https://arxiv.org/abs/2310.08560)）。
- **Anthropic 的 compaction 定义**："拿一段接近窗口上限的对话，总结它，然后用摘要重新开一个窗口"。Claude Code 的实现是"把消息历史交给模型压缩，保留**架构决策、未解决的 bug、实现细节**，丢弃冗余工具输出与消息"，压缩后**加上"最近访问的 5 个文件"继续**。并给了工程建议：**先在真实 agent trace 上把 recall 调到最大，再迭代提升 precision**；**"clear 工具调用与结果"是最安全、最轻的 compaction 形式**（[Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。
- **Cursor 的做法更狠**：压缩时**把 chat history 当文件引用**交给 agent——摘要是有损的，agent 若发现缺细节，可以**回头去搜那份历史文件**；另外"把长工具响应写成文件，让 agent 用 `tail` 自己看"（[Cursor: Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)）。

**缓存后果**：**compaction 是唯一"故意让前缀全部失效"的合法操作**。它每触发一次，整个上下文前缀作废、全量重算。因此必须：① 只在**确实超限时**触发，不要周期性触发；② 触发点选在**会话自然断点**（玩家退出/静音/切场景）；③ 压缩产物尽量小且**稳定**，避免压缩后紧接着又变。

#### 2.9.2 KV / 状态压缩（提示压缩）

- **LLMLingua**：粗到细的提示压缩——**budget controller** 控制压缩率、**token 级迭代压缩**建模 token 间依赖、并做**指令微调的分布对齐**（[arXiv:2310.05736](https://arxiv.org/abs/2310.05736)）。
- **LLMLingua-2**：批评"用因果语言模型的信息熵做压缩指标"是次优的（只有单向上下文、与压缩目标不对齐），改为**数据蒸馏 + 把压缩表述为 token 分类问题**，保证忠实性与任务无关性（[arXiv:2403.12968](https://arxiv.org/abs/2403.12968)）。

**关键判断**：**提示压缩与"吃满前缀缓存"是互斥的两种省钱方式。**

- 压缩省的是"每次都要付的输入 token"；
- 缓存省的是"重复前缀的 prefill 算力与单价"（DeepSeek 命中单价是未命中的 1/50）。
- **DeepSeek 的价格结构下，缓存完胜压缩**：只要前缀稳定，省 98% 成本；而压缩要额外跑一个模型、还有信息损失。**结论：不做提示压缩，做前缀稳定。**

#### 2.9.3 结构化槽位记忆

- **Letta memory blocks** 是"结构化槽位"的正式形态：`label` + `description` + `value` + `limit(字符)`，模型通过内置工具读写，**始终可见无需检索**（[docs](https://docs.letta.com/v1-sdk/memory/memory-blocks/)）。
- **MemoryBank 的用户画像 + 事件摘要**是"槽位的语义分层"：画像慢变、事件中变、原文快变（[arXiv:2305.10250](https://arxiv.org/abs/2305.10250)）。
- **Codex 的 `AGENTS.md` 是"槽位的静态形态"**：启动时按 全局 → 项目根 → 逐级下钻 构建**指令链**，靠近当前目录的覆盖前面的，累计上限 `project_doc_max_bytes` **默认 32 KiB**（[Codex 文档](https://developers.openai.com/codex/agent-configuration/agents-md)）。

**缓存后果**：**槽位本身是缓存杀手，槽位的"位置"决定它是不是杀手。**

- 槽位**前置**在 system prompt 里 → 每次槽位变更 = 全 prefix 失效（Letta 默认行为）。
- 槽位**追加在对话尾部**（作为一条"当前状态"消息）、且**只在变更时追加** → 前缀始终稳定，命中率保持 100%。**这是我们该采用的形式。**

### 2.10 业界公开指引与实证结论

#### 2.10.1 Anthropic：《Effective context engineering for AI agents》

（[原文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，2025-09-29）

可直接采用的观点：

- **上下文是有限且边际收益递减的资源**，LLM 有"**注意力预算（attention budget）**"；目标是"**找到最小的高信号 token 集合**"。
- **"context rot"**：随输入 token 增加，模型从上下文中准确回忆信息的能力下降。
- 架构性解释：transformer 的 n² 注意力关系随长度摊薄；位置编码插值可扩长但会削弱位置理解。
- **长任务的三件套**：**compaction（压缩重开窗口）**、**structured note-taking（把笔记落到窗口外，如 NOTES.md）**、**sub-agent 架构（子代理用几万 token 探索，只回吐 1,000–2,000 token 摘要）**。
- **工具设计要"token 高效"**：工具集臃肿是最常见失败模式；返回值要精简。
- 决策边界："**上下文动态内容少**的领域（法律、金融）更适合混合策略；**能做的就做最简单的"。
- 明确说明 Claude Code 是**混合策略**：`CLAUDE.md` 静态前置，`glob`/`grep` 做 just-in-time 检索。

#### 2.10.2 Anthropic：《Managing context on the Claude Developer Platform》

（[原文](https://www.anthropic.com/news/context-management)）

- **context editing**：接近 token 上限时**自动清理陈旧工具调用与结果**，保留对话流。
- **memory tool**：**完全 client-side**，通过工具调用在开发者自己的存储后端做文件 CRUD。
- **效果数字（内部评测，不可独立复现）**：memory tool + context editing 组合相对 baseline **+39%**；仅 context editing **+29%**；在**100 轮**网页搜索评测里，context editing 让任务**从失败变为完成**，同时**token 消耗 −84%**。

#### 2.10.3 OpenAI

- 《A practical guide to building agents》给的是**编排与 guardrail** 视角（model / tools / instructions 三要素、single-agent 优先、guardrail 分层），**不谈上下文裁剪**（[PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)）。
- 其 API 文档把对话状态管理拆成 **`previous_response_id` 串联**与 **Compaction** 两条路，并明确提示 **"即便用 `previous_response_id`，链上所有历史 input token 仍按输入 token 计费"**（[conversation state 文档](https://platform.openai.com/docs/guides/conversation-state)）。**这条对我们是重要旁证：串接不会自动省钱，只有服务端前缀缓存才会。**
- **Compaction 专页在登录墙后，正文不可取——不计入结论。**

#### 2.10.4 Lost in the Middle（U 型曲线）

（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)）

- 相关信息的**位置**显著影响表现：**开头（primacy bias）与结尾（recency bias）最好，中间最差**，形成 **U 型**。
- 极端数据：把相关信息放中段时，**GPT-3.5-Turbo 在多文档问答上比"完全没有文档"（closed-book，56.1%）还差**。
- **检索饱和度**：从 20 篇增加到 50 篇检索文档，GPT-3.5-Turbo 仅提升 **约 1.5%**，Claude 系 **约 1%**——**模型在检索器 recall 饱和之前就饱和了**。
- 位置效应在 **encoder-decoder 模型、训练长度内**较稳健；超出训练长度也出现 U 型；**甚至 base model（未指令微调）也有 U 型**。

#### 2.10.5 Context Rot（Chroma）

（[research.trychroma.com/context-rot](https://research.trychroma.com/context-rot)）

- 覆盖 **18 个 LLM**，在**固定任务复杂度、只变输入长度**的受控设置下：**所有实验里性能都随长度单调/非均匀下降**。
- **needle-question 相似度越低，随长度下降越快**（即"需要推理/隐含关联"的检索最先崩）。
- **干扰项（distractor）影响非均匀**：即使**单个**干扰项也降低表现，4 个干扰项叠加更差；且**长度越长、放大越明显**，包括最新 SOTA 模型。
- **反直觉但一致**：**打乱 haystack（破坏局部连贯性）反而让模型表现更好**，18 个模型全部如此——说明"看起来更连贯的长上下文"更容易让 needle 被淹没。
- LongMemEval 部分：把"同样的问题"放进 **focused input** 时模型几乎全对，放进**完整 113k token 输入**时一致下降——**下降来自"多了一步检索"，而不是问题本身变难**。

#### 2.10.6 RULER（声称长度 ≠ 有效长度）

（[arXiv:2404.06654](https://arxiv.org/abs/2404.06654)）

- **17 个长上下文模型**、**13 个任务**、长度 **4K–128K**、每任务每长度 500 例。
- 结论：**"所有模型都声称 ≥32K，但只有一半能有效处理 32K；且几乎所有模型在到达声称长度之前就已跌破阈值。"**
- 方法学价值：**用"固定阈值 + 加权平均"把"声称上下文"和"有效上下文"分开**——这正是我们该对自己做的：**别按 64K 设计，按"有效可用长度"设计**。

## 3. 通用策略与实证结论（横向归纳）

### 3.1 位置

- 中段是垃圾场。**重要且稳定的内容放头尾**；检索进来的候选若多于 3~5 条，宁可少放（§2.10.4 显示 20→50 篇只值 1.5%）。
- 对我们的直接含义：**"当前任务状态/玩家即时意图"必须放在消息流末尾**（正是 recency bias 受益区），不要塞进 system prompt 中段。

### 3.2 检索

- 纯向量检索在**长上下文里最先失效**（低相似度对下降最快）。因此**混合检索（向量 + 精确匹配/BM25）** 不是锦上添花，是必需——Zep/Graphiti 明确采用 hybrid（semantic + BM25 + 图遍历）并强调不依赖 LLM 摘要（[README](https://github.com/getzep/graphiti)）。
- Minecraft 场景的专有名词（方块/物品/模组名）**几乎总有精确串可匹配**，混合检索的收益比通用场景更高。

### 3.3 何时压缩 / 何时裁剪 / 何时缓存

| 手段 | 触发条件 | 代价 | 优先级 |
|---|---|---|---|
| **前缀缓存** | 总是（默认开启） | 0，只需保持前缀字节稳定 | **P0** |
| **工具结果裁剪**（清空老旧 tool result） | 工具调用 ≥ N 次 / 上下文超水位 | 一次本地改写历史 → **一次全 miss** | **P0**（工具上线后必有） |
| **滚动摘要 / compaction** | 触达有效长度上限（不是声称上限） | 一次全 miss + 信息有损 | **P1** |
| **提示压缩（LLMLingua 类）** | 仅当无法缓存（如每次内容全新） | 额外模型 + 信息损失 | **P2 / 不建议** |
| **外部化（笔记/文件）** | 长任务、跨会话 | 需要 agent 会读写 | **P1** |

### 3.4 写入时机（hot path vs background）

LangGraph 的权衡表述可直接当作规约（[来源](https://langchain-ai.github.io/langgraph/concepts/memory/)）：

- hot path：实时可见、可告知用户；但**增加复杂度、拖慢延迟、且"一心二用"降低记忆质量**。
- background：不占主路径；但**频率难定、其他线程可能读不到最新**。

**语音场景的结论：默认 background，例外条款（玩家显式"记住/别忘了"）走 hot path。** 这与 Anthropic 的 "structured note-taking"（agent 自己写 NOTES.md，之后读回）在方向上一致。

### 3.5 前缀缓存的前置条件（DeepSeek 的实测规则，最硬的一条）

（[DeepSeek: Context Caching on Disk](https://api-docs.deepseek.com/guides/kv_cache)）

- 缓存**默认开启**，无需改代码；**重叠前缀从缓存取，计为命中**。
- 命中要求 **"完全匹配某个 cache prefix unit"**。前缀单元在三个时机被持久化：
  1. **请求边界**：用户输入结束位置、模型输出结束位置各产出一个单元；
  2. **公共前缀检测**：系统检测到多个请求共享前缀时，把该公共前缀**单独**持久化；
  3. **固定 token 间隔**：长输入/长输出按固定间隔切单元，避免"永远到不了结尾导致完全不可缓存"。
- **文档给的判例非常重要**：
  - `A+B` → `A+B+C`：**完全命中** `A+B`。
  - `A+B` → `A+C`：**不命中**；但系统会检测出公共前缀 `A` 并持久化，于是第三次 `A+D` 可命中 `A`。
- `usage` 暴露 **`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`**（可直接做监控指标）。
- **注意**：缓存是 **best-effort，不保证 100% 命中**；构建缓存需数秒；不用后"数小时到数天"内清理。**因此不能把正确性建立在缓存上，只能把成本/延迟建立在缓存上。**

**照此推出的工程设计（这就是 §6 的核心）**：

1. **头部字节恒定**：system prompt + 工具定义**一个字符都不许变**（包括日期、玩家名、在线人数这类会变的东西——全部禁止写入 system prompt）。
2. **只追加不修改**：消息历史严格 append-only。任何"回头改第 3 条消息"的操作（清 tool result、插摘要、改槽位）都会让**其后所有内容**失效。
3. **易变内容放尾部**：本轮 ASR 文本、本轮检索片段、本轮状态快照，全部作为末尾消息。
4. **变更有边界**：真需要改前缀区时，**整段会话一次性改**（compaction 点），而不是逐渐漂移。
5. **可观测**：每轮记录 `prompt_cache_hit_tokens / (hit+miss)`，这是唯一能证明"设计生效"的指标。

## 4. 干活向参考（agentic / task）

### 4.1 计划与 scratchpad

- **Anthropic 的 structured note-taking**：agent 把笔记写到窗口外持久存储，"像 Claude Code 写 to-do list，或自定义 agent 维护 NOTES.md"；并强调"**上下文重置后 agent 读自己的笔记继续**"是长任务连贯性的关键（[来源](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。
- **Letta 的 scratchpad 块**：明确把"在 scratchpad 块里维护工作记忆"列为 memory block 的用途之一（[来源](https://docs.letta.com/v1-sdk/memory/memory-blocks/)）。
- **对 Minecraft 的映射**：玩家的**多步指令**（"去挖 20 个铁矿，然后做成铁锭，放到箱子里"）天然需要一个**外置任务清单**，加载到尾部消息里。**清单在尾部 → 缓存仍命中；清单在前缀 → 每步都全 miss。**

### 4.2 任务状态外置

- **LangGraph checkpointer**：state 持久化到数据库，thread 可随时恢复（[来源](https://langchain-ai.github.io/langgraph/concepts/memory/)）。
- **Letta MemFS**：git-backed 记忆文件系统，agent 可检视与编辑（[来源](https://docs.letta.com/configuration/memory)）。
- **Cursor**：把"长工具响应"写成文件，agent 用 `tail` 先看尾部再决定要不要读全（[来源](https://cursor.com/blog/dynamic-context-discovery)）。
- **共性模式：上下文里只放"句柄"，实体放外部。** Anthropic 称之为 **"just-in-time" 上下文**：维护轻量标识符（文件路径、存储查询、web 链接），运行时用工具按需取数据；并指出**元数据本身就是信号**（`tests/test_utils.py` 与 `src/core_logic/` 下的同名文件含义不同）。
- **权衡（原文）**：**运行时探索比预计算检索慢**，且需要精心设计工具与启发式，否则 agent 会"浪费上下文、追死胡同、找错信息"。→ **语音场景不能全靠 just-in-time（实时性不够），必须混合：会话开始预取，中途按需。**

### 4.3 子代理委派

- **Anthropic 明确给了数字**：子代理"可能花掉几万 token 探索，**只回吐 1,000–2,000 token 的浓缩摘要**"，主 agent 专注综合；并称该模式在其多代理研究系统上"相对单 agent 有实质提升"（[来源](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。
- **适用判据（原文）**：**compaction 适合长来回；note-taking 适合有清晰里程碑的迭代开发；多代理适合并行探索**。
- **对 Minecraft 的映射**：真正适合"子代理"的不是对话，而是**后台任务**（"帮我看看周围有什么"= 后台采样 + 摘要回吐），**主对话链保持轻**。语音回合内**绝不做**子代理。

### 4.4 工具结果裁剪（tool result pruning）

- **Anthropic context editing**：进入上限时**自动清除陈旧工具调用与结果**；官方称这是"**最安全最轻的 compaction 形式**"（[来源1](https://www.anthropic.com/news/context-management)、[来源2](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。
- **Cursor 的替代做法**：不截断（会丢信息），而是**写文件 + 让 agent 自己读**；效果是"**更少不必要的摘要触发**"（[来源](https://cursor.com/blog/dynamic-context-discovery)）。
- **Anthropic 工具设计原则**（[Writing tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）：**工具返回值要 token 高效**，输入参数要"有描述性、无歧义、契合模型强项"。
- **对我们的关键权衡**：裁剪工具结果 = **改写历史 = 破坏前缀**。所以：**优先在"源头"让工具结果就小**（返回结构化摘要而非原始 JSON），而不是事后裁剪；必须裁剪时，攒到 compaction 点一次性做。

### 4.5 编码代理的仓库地图（有公开资料的部分）

| 工具 | 公开机制 | 来源 |

### 5.2 通用策略

| 策略 | 省什么 | 缓存影响 | 信息损失 | 需要 LLM | 语音场景可用性 |
|---|---|---|---|---|---|
| **前缀缓存（字节稳定 + append-only）** | 输入单价（DeepSeek 命中 ≈ 1/50）+ prefill 延迟 | **正面（唯一正面项）** | 无 | 否 | **必须做** |
| 滚动摘要 / compaction | 输入 token 绝对值 | **一次全失效** | 中–高（有损） | 是 | 可做，但要在会话断点 |
| 工具结果裁剪 | 输入 token（且抑制后续摘要触发） | **一次全失效** | 低（丢的是原始数据） | 否 | 必做，攒批做 |
| 提示压缩（LLMLingua 类） | 输入 token | **破坏前缀**（压缩后字节变了） | 中 | 是（额外小模型） | **不建议** |

| 三因子检索打分 | 无关记忆的 token | 无（检索侧） | 无 | **否**（importance 可规则化） | **强烈建议** |
| 外置笔记 / 文件句柄 | 长任务历史 | 中性（句柄在尾部） | 低 | 视实现 | 后台任务适用 |

## 6. 对我们的推荐组合与理由

### 6.1 先把场景硬约束钉死

| 约束 | 现状 | 由本调研带来的修正 |
|---|---|---|
| 单会话 | 玩家一次登录内的连续对话 | 长期画像收益低 → **Mem0/Zep 的跨会话优势不成立** |
| 实时语音 | 首 token 延迟敏感 | **hot path 的额外 LLM 调用一律禁止**；后台化是默认 |
| 云端 DeepSeek | 用户假设 64K 窗口 | **DeepSeek 官方文档当前标注 context length 1M**（`deepseek-flash` / `deepseek-v4-pro`，[定价页](https://api-docs.deepseek.com/quick_start/pricing)）。**64K 若是工程自设上限，属保守假设，不改变任何结论**；但请按 RULER 的教训把它当"**有效长度**"而非"声称长度"，仍按 64K 甚至更小做预算 |
| 已有本地 RAG（`bge-large-zh`） | 中文向量检索可用 | **relevance 因子免费**；但要注意 `max_position_embeddings=512`（见 §6.5） |
| 将来加工具调用 + 后台任务 | 未实现 | **工具结果裁剪、任务状态外置要从一开始就设计进去**，否则后期改造要重写整条消息链 |

### 6.2 每轮 token 布局（本文档最可执行的一条）

```
┌─────────────────────────────────────────────┐
│ S1  系统人格 + 行为规约        ← 永不变化（字节恒定） │  命中
│ S2  工具定义（顺序/字段固定）  ← 仅发版变化          │  命中
│ S3  长期记忆摘要（低频）      ← 仅会话/话题边界变化   │  命中（S3 不变时）
├─────────────────────────────────────────────┤
│ H   历史消息（严格 append-only）                 │  命中（逐轮增长）
├─────────────────────────────────────────────┤
│ T1  本轮状态快照（任务清单/坐标/背包摘要）        │  miss
│ T2  本轮检索片段（RAG top-k，≤3 条）             │  miss
│ Q   本轮 ASR 文本（完整句，非增量）              │  miss
└─────────────────────────────────────────────┘
```

四条铁律：

1. **S1/S2 里禁止任何动态值**（时间、玩家名、在线人数、随机 ID、格式化浮点数）。这些一律下沉到 `T1`。
2. **`T1/T2/Q` 每轮必变是正常的**——它们只占尾部一小段，代价 = `miss_tokens × 未命中单价`，可控。
3. **`S3` 变更 = 其后全部失效**。按 DeepSeek 的"公共前缀检测"规则，`S1+S2` 仍可作为独立 cache prefix unit 命中，但**这是 best-effort，不要赌**。所以 `S3` 要么足够小，要么变更足够少。
4. **`H` 只追加**。任何"回头改历史"（清 tool result、插摘要）都要**攒到 compaction 点一次做完**。

**监控指标**：每轮记录 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`（DeepSeek 在 `usage` 中直接返回）。**稳态目标：命中率 ≥ 90%**；若低于此，第一个怀疑对象永远是"有人在改前缀"。

### 6.3 缓存友好性自检清单（上线前逐条勾）

- [ ] system prompt 是常量字符串，**不含**插值；
- [ ] 工具定义按固定顺序序列化，字段顺序稳定，**不因版本升级重排**；
- [ ] 消息列表是 append-only 的 `ArrayList` 语义（**禁止 `insert(0, …)`**）；
- [ ] 检索片段/状态快照**只加在尾部**；
- [ ] ASR 增量结果**不在服务端拼成多轮**——等一句话说完，只发一次；
- [ ] 后台任务结果**不插回历史中段**，而是作为新的一轮尾部消息追加；
- [ ] compaction 有明确触发条件（有效长度水位），**不是周期性**；
- [ ] 有 `hit/miss` 打点与告警。

### 6.4 推荐方案（分优先级）

#### P0 — 必做（低成本、高收益、无新依赖）

1. **前缀稳定化 + append-only 上下文骨架**（§6.2）。这不是"记忆方案"，是**成本与延迟的地基**。收益：DeepSeek 缓存命中单价 ≈ 未命中的 **1/50**（[定价页](https://api-docs.deepseek.com/quick_start/pricing)），且命中直接跳过前缀 prefill。
2. **三因子检索打分（借鉴 Generative Agents）+ 遗忘衰减（借鉴 MemoryBank）**。
   - `score = α_r·recency + α_i·importance + α_v·relevance`，三者 min-max 归一化（[arXiv:2304.03442](https://arxiv.org/abs/2304.03442)）。
   - `recency` 用 `exp(-Δt/S)`（[arXiv:2305.10250](https://arxiv.org/abs/2305.10250)），`S` 在记忆被召回时递增。
   - `relevance` 直接用现成 `bge-large-zh` 余弦。
   - `importance` **先用规则**（涉及坐标/承诺/偏好/物品归属 → 高；寒暄 → 低），**不引入 LLM**。
   - **为什么值得**：完全本地、零延迟、不进前缀、可解释、可调参；且我们**已经付过 embedding 的钱**。
3. **工具结果"源头精简"**：工具返回结构化摘要而不是原始 JSON（Anthropic 的"工具要 token 高效"）。在工具设计期做，比事后裁剪便宜一个数量级。

#### P1 — 工具调用上线后必做

4. **工具结果攒批裁剪 + compaction**（借鉴 Anthropic context editing / compaction）。
   - **只在触达有效长度水位时触发**；触发点选在会话自然断点。
   - 优先级：先清**最老的 tool result**（信息熵最低），再压缩对话摘要，最后才动 `S3`。
   - 有意接受"一次全 miss"，但把它当作**显式成本事件**记账。
5. **任务状态外置**（借鉴 LangGraph checkpointer / Letta MemFS / Cursor 文件化）：
   - 多步指令存本地（SQLite/NBT），上下文里只放**当前一步 + 剩余步骤的句柄**。
   - 参考 Codex `AGENTS.md` 的**静态指令 + 大小上限**思路给"项目知识"设硬上限。

#### P2 — 观测到真实需求再做

6. **状态事实的时序化（借鉴 Zep 的 `t_valid`/`t_invalid`，不引入图库）**：
   - 一张 `state_facts(entity, attr, value, t_valid, t_invalid)`，新值把旧值的 `t_invalid` 置为当前时间。
   - **规则可判定**（同主键覆盖），不需要 LLM 判矛盾——比 Zep 更便宜也更可靠。
7. **子代理只用于后台任务**（"看看周围有什么"、"算一下够不够造 20 个铁锭"），**回合内不用**。摘要回吐控制在 1–2K token（Anthropic 给的量级）。

#### 明确不建议引入

| 方案 | 否决理由（按重要性排序） |
|---|---|
| **A-MEM** | ① "memory evolution" 会**不可预期地改写旧记忆**，不可审计不可回滚；② 写入路径 3–4 次 LLM 调用；③ 与"可撤销记忆"的产品直觉冲突 |
| **MemGPT / Letta 作为运行时** | ① 槽位**前置**在 prompt → 与缓存策略正面冲突；② 夺取 agent 主循环控制权；③ 无 Java SDK；④ 单会话场景用不上分层收益 |
| **Zep / Graphiti 作为系统** | ① Python + 图数据库 + 全文索引，对 Java 模组是灾难依赖；② 单会话无跨会话事实演化需求。**只抄数据模型** |
| **Mem0 作为系统** | ① Java 无 SDK；② 抽取阶段需 LLM → 语音回合延迟翻倍；③ 其强项（跨会话用户画像）在本场景被摊薄。**只抄写入门控语义** |
| **Cognee** | Python + 三套存储；`improve` 回写；官方自述自托管小模型质量与商业版有差距 |
| **LLMLingua 类提示压缩** | 与"吃满前缀缓存"互斥，且 DeepSeek 价格结构下缓存收益（50×）远大于压缩收益；还额外引入一个模型和信息损失 |
| **LangMem / LangGraph 运行时** | Python/JS 生态。**抄它的四象限术语与 hot-path/background 权衡即可** |

### 6.5 中文场景的坑（逐条附来源）

1. **token 密度与直觉不符**：DeepSeek 官方换算 **1 汉字 ≈ 0.6 token、1 英文字符 ≈ 0.3 token**（[token 用量文档](https://api-docs.deepseek.com/quick_start/token_usage)）。
   → **含义**：64K token ≈ **10 万+ 汉字**，比英文场景"更耐塞"，容易让人误以为可以不做裁剪。**别被这个数骗了**——RULER/context rot 说的是"有效长度"衰减，与字符数无关。
2. **`bge-large-zh-v1.5` 有 512 硬顶**：`config.json` 中 `max_position_embeddings: 512`、`hidden_size: 1024`（[config.json](https://huggingface.co/BAAI/bge-large-zh-v1.5/raw/main/config.json)）。
   → **含义**：中文 BERT 分词器下 1 字 ≈ 1 token，**单条 chunk 必须 ≤ 约 500 字**，否则尾部被静默截断。记忆条目的"事件摘要"长度要按此设计。
3. **query instruction 要用对地方**：bge 的检索 instruction（"为这个句子生成表示以用于检索相关文章："）**只加在 query 上，passage 一律不加**；模型卡说明 v1.5 已经"改善了不用 instruction 时的检索能力，仅轻微下降"，但"短查询建议加 instruction"，并给出最终判据：**"选在你任务上表现更好的那个设置"**（[模型卡](https://huggingface.co/BAAI/bge-large-zh-v1.5)）。
   → **含义**：语音输入是**短查询**——**必须加 instruction**，且要实测确认。
4. **ASR 同音错字直接打穿向量检索**：中文语音识别的"铁镐/铁稿"、"红石/红十"这类错误会同时破坏**精确匹配**与**embedding 语义**。**未找到**关于该问题的公开量化研究。
   → **缓解（基于工程判断，非引用）**：Minecraft 专有名词建**别名词典 + 拼音/编辑距离兜底**，走 hybrid 检索（Zep 的 hybrid 做法可作参考），并让 LLM 在工具调用前做一次"实体归一"。
5. **中文记忆摘要的压缩率与忠实度无公开基准**：所有 compaction 数字（39%/29%/84%）都来自 Anthropic 的内部英文评测，**中文场景不可直接套用**。→ 上线后必须自建小评测集。
6. **时间/序数表达**：中文"前两天"、"上上次"这类相对时间在 Zep 的 bi-temporal 抽取里需要 `t_ref` 锚定（Zep 论文明确用消息时间戳解析 "next Thursday" / "last summer" 这类表达）。**中文的相对时间词更依赖上下文**，抽取必须带锚点时间戳，否则会写成错误事实。

### 6.6 在 Java 模组里的实现成本估算

| 组件 | 估算 | 依据 |
|---|---|---|
| 前缀稳定骨架 + append-only 消息链 | **小**（数据结构的纪律，不是功能） | 无外部依赖 |
| 三因子打分 + 遗忘衰减 | **小**（向量已有，剩数学与 SQL） | `exp` + 归一化 + `ORDER BY` |
| 状态快照 / 任务清单（尾部注入） | **中**（要定义快照 schema 与序列化） | 需设计 schema |
| 工具结果裁剪 + compaction | **中**（要判水位、要重写历史、要保证只在断点触发） | Anthropic 只给了原则，无参考实现 |
| hybrid 检索（向量 + 精确/拼音） | **中**（拼音/别名要建词典） | 需自建资源 |
| 时序状态事实表 | **小**（一张表 + 两个时间戳） | 规则可判定 |
| 若强行接入 Mem0/Zep/Graphiti | **大**（Python 服务 + 图库/向量库 + 跨进程协议 + 故障域扩大） | 各家 README 的运行时要求 |

### 6.7 这份调研没有解决、需要实验回答的问题

1. **DeepSeek 侧的实际命中率**：我们的布局在真实对话节奏下（含 ASR 抖动、断连重连）能到多少？→ 需要上线打点。
2. **`S3`（长期记忆摘要）该多大、多久变一次**：变大则命中率降，变小则能力降。→ 需要 A/B。
3. **importance 规则化的准确度**：纯规则 vs 一次批量 LLM 打分，在 Minecraft 语料上的差距。→ 需要标注 200~500 条真实语音转写。
4. **中文段落的压缩忠实度**：compaction 后玩家能否察觉"系统忘了刚才说的"。→ 需要小规模人评。
5. **混合检索权重**：向量 vs 精确匹配在 Minecraft 名词上的最优配比。→ 需要检索集。
6. **语音场景下 `T1/T2/Q` 尾部的实际 token 量级**：若尾部本身就有 2~3K token，则"50× 折扣"只作用在头部，实际账单折价远小于 50×——**必须算清这个账，不能直接套用"便宜 50 倍"的结论。**
